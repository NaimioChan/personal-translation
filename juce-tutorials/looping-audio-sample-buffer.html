使用 AudioSampleBuffer 类循环播放音频

本教程展示如何播放并循环存储在 AudioSampleBuffer 对象中的音频。对于处理已录制音频数据的采样应用来说，这是一个有用的基础。

难度：中级
平台：Windows、macOS、Linux
类：AudioBuffer, AudioFormatReader, AudioAppComponent

入门

本教程假定你已完成教程：构建白噪声发生器和教程：构建音频播放器。如果还没有，你应该先阅读这些内容。

在此处下载本教程的演示项目：PIP | ZIP 。解压项目并在 Projucer 中打开第一个头文件。

如果你在这一步需要帮助，请参阅教程：Projucer 第 1 部分：Projucer 入门。

演示项目

本教程的演示项目允许用户打开声音文件，把整个文件读入一个 AudioSampleBuffer 对象，并循环播放它。在教程：构建音频播放器中，我们使用连接到 AudioTransportSource 对象的 AudioFormatReaderSource 对象来播放声音。用这种方法也可以实现循环：启用 AudioFormatReaderSource 对象的循环标志——使用 AudioFormatReaderSource::setLooping() 函数。

本教程讨论所涉及的所有代码都在演示项目的 MainContentComponent 类中。

将采样数据加载到内存

在很多情况下，使用内置的声音文件播放类可能更好。有时你可能需要自己来做，本教程介绍其中一些技术。采样器应用通常这样把声音文件数据加载到内存中，尤其是当声音相对较短时（示例参见 SamplerSound 类）。合成声音也可以通过把波表存储在 AudioSampleBuffer 对象中，并以适当的速率循环播放来产生所需的音高。教程：波表合成对此进行了探讨。

本教程还强调了在把文件访问与音频线程上的音频处理结合起来时可能遇到的一些多线程问题。其中一些问题表面上看起来简单，但往往需要谨慎应用的技术才能避免崩溃和音频毛刺。这些技术将在教程：使用 AudioSampleBuffer 类循环播放音频（进阶）中进一步探讨。

为什么有长度限制？

演示项目把你可加载的声音文件长度限制在 2 秒以内。这个限制相当随意，但大致有两个原因：

  1. 如果整个文件非常大，你的计算机可能会耗尽物理内存。当然，在真实应用中你可以使用高得多的限制。一个 2 秒的立体声音频文件，采样率为 44.1kHz，加载到 AudioSampleBuffer 对象中只占用 705,600 字节内存。（见注释）
  2. 即使加载相当短的文件，所花的时间也并非微不足道。

关于第 1 点：如果我们超过计算机拥有的物理内存量，它可能开始使用虚拟内存（即硬盘等二级存储）。这就完全违背了把数据加载到内存中的初衷！当然，在某些设备上，如果内存耗尽，该操作可能直接失败。

关于第 2 点：我们让示例保持简单，在 FileChooser::browseForFileToOpen() 函数返回用户选择的文件之后，直接加载音频数据。这意味着消息线程将被阻塞，直到所有音频都从磁盘读入 AudioSampleBuffer 对象。即使声音很短，我们也确实应该在后台线程上做这件事，以尽可能保持用户界面的响应性。对于长声音，延迟和无响应会非常明显。增加另一个（后台）线程会增加本示例的复杂度。有关如何以这种方式在后台线程加载文件的示例，请参见教程：使用 AudioSampleBuffer 类循环播放音频（进阶）。

练习：为保持简单，演示项目在你尝试加载较长文件时不会报告错误——它只是失败。添加这样的错误报告留作你的额外练习。

读取声音文件

当用户点击打开…按钮时，会向他们显示文件选择器。然后整个文件被读入我们 MainContentComponent 类中的 AudioSampleBuffer 成员 fileBuffer。

void openButtonClicked()
{
    shutdownAudio(); // [1]
    chooser = std::make_unique<juce::FileChooser> ("Select a Wave file shorter than 2 seconds to play...",
        juce::File {},
        "*.wav");
    auto chooserFlags = juce::FileBrowserComponent::openMode
                        | juce::FileBrowserComponent::canSelectFiles;
    chooser->launchAsync (chooserFlags, [this] (const juce::FileChooser& fc) {
        auto file = fc.getResult();
        if (file == juce::File {})
            return;
        std::unique_ptr<juce::AudioFormatReader> reader (formatManager.createReaderFor (file)); // [2]
        if (reader.get() != nullptr)
        {
            auto duration = (float) reader->lengthInSamples / reader->sampleRate; // [3]
            if (duration < 2)
            {
                fileBuffer.setSize ((int) reader->numChannels, (int) reader->lengthInSamples); // [4]
                reader->read (&fileBuffer, // [5]
                    0, // [5.1]
                    (int) reader->lengthInSamples, // [5.2]
                    0, // [5.3]
                    true, // [5.4]
                    true); // [5.5]
                position = 0; // [6]
                setAudioChannels (0, (int) reader->numChannels); // [7]
            }
            else
            {
                // handle the error that the file is 2 seconds or longer..
            }
        }
    });
}
  • [1]：注意，每次打开新文件时，我们都会为 AudioAppComponent 对象关闭音频系统。这是为了避免前面暗示的一些多线程问题。音频系统关闭后，就不会有危险：当我们还处于 Button::onClick lambda 函数调用中时（该函数会从消息线程调用这个 openButtonClicked() 函数），我们的 getNextAudioBlock() 函数不会在音频线程上被调用。
  • [2]：这里我们使用 AudioFormatManager 对象创建 AudioFormatReader 对象。注意，我们将其存储在 std::unique_ptr 对象中，因为我们需要自己管理这个对象。（在教程：构建音频播放器中，我们把 AudioFormatReader 对象交给 AudioFormatReaderSource 对象替我们管理。）该操作可能无法创建读取器对象，因此我们必须在下一行检查 reader 指针不是 nullptr 值。
  • [3]：这里我们通过用文件长度（以采样计）除以其采样率来计算声音文件的时长。我们在下一行检查它小于 2 秒。
  • [4]：这里我们使用 AudioFormatReader 对象中的通道数和长度，调用 AudioSampleBuffer::setSize() 函数来调整 AudioSampleBuffer 对象的大小。
  • [5]：这里我们使用 AudioFormatReader::read() 函数把音频数据从 AudioFormatReader 对象读入我们的 AudioSampleBuffer fileBuffer 成员。参数为：
    • [5.1]：AudioSampleBuffer 对象中数据开始写入的目标起始采样。
    • [5.2]：要读取的采样数。
    • [5.3]：AudioFormatReader 对象中开始读取的起始采样。
    • [5.4]：对于立体声（或其他双通道）文件，该标志指示是否读取左通道。
    • [5.5]：对于立体声文件，该标志指示是否读取右通道。
  • [6]：播放时需要保存缓冲区中最近的读取位置。这里把 position 成员重置为零。
  • [7]：这里重新启动音频系统。此时我们有机会使用声音文件中的通道数，尝试把音频设备配置为相同数量的通道。

处理音频

在 getNextAudioBlock() 函数中，从 fileBuffer AudioSampleBuffer 成员读取适当数量的采样，并写入 AudioSourceChannelInfo 结构体中的 AudioSampleBuffer 对象。

从文件读取音频数据时，我们用 position 成员跟踪当前读取位置（注意在为指定采样块处理完所有通道之后更新它）：

void getNextAudioBlock (const juce::AudioSourceChannelInfo& bufferToFill) override
{
    auto numInputChannels = fileBuffer.getNumChannels();
    auto numOutputChannels = bufferToFill.buffer->getNumChannels();
    auto outputSamplesRemaining = bufferToFill.numSamples; // [8]
    auto outputSamplesOffset = bufferToFill.startSample; // [9]
    while (outputSamplesRemaining > 0)
    {
        auto bufferSamplesRemaining = fileBuffer.getNumSamples() - position; // [10]
        auto samplesThisTime = juce::jmin (outputSamplesRemaining, bufferSamplesRemaining); // [11]
        for (auto channel = 0; channel < numOutputChannels; ++channel)
        {
            bufferToFill.buffer->copyFrom (channel, // [12]
                outputSamplesOffset, // [12.1]
                fileBuffer, // [12.2]
                channel % numInputChannels, // [12.3]
                position, // [12.4]
                samplesThisTime); // [12.5]
        }
        outputSamplesRemaining -= samplesThisTime; // [13]
        outputSamplesOffset += samplesThisTime; // [14]
        position += samplesThisTime; // [15]
        if (position == fileBuffer.getNumSamples())
            position = 0; // [16]
    }
}
  • [8]：outputSamplesRemaining 变量存储 getNextAudioBlock() 函数需要输出的采样总数，取自 AudioSourceChannelInfo 结构体。我们用它检查是否需要退出下一行开始的 while() 循环。
  • [9]：我们还复制了 AudioSourceChannelInfo::startSample 值，用作目标缓冲区内的偏移量。
  • [10]：这里我们计算正在读取的缓冲区中还剩多少采样。
  • [11]：对于 while() 循环的这一轮，我们需要输出本次调用 getNextAudioBlock() 的剩余采样与缓冲区中剩余采样两者中的较小值——使用 jmin() 函数。如果该值小于本次调用 getNextAudioBlock() 的采样总数，那么在退出之前还会再执行一轮 while() 循环。
  • [12]：对每个输出通道，我们使用 AudioSampleBuffer::copyFrom() 函数把一个缓冲区的一个通道的数据段复制到另一个缓冲区的一个通道。这里我们指定目标通道索引。
    • [12.1]：目标缓冲区内的采样偏移量。
    • [12.2]：要复制的源 AudioSampleBuffer 对象。
    • [12.3]：源缓冲区的通道索引。如果源缓冲区的通道数少于目标缓冲区，我们使用这个取模计算。例如，单声道源缓冲区意味着这里始终为零，把相同数据复制到每个输出通道。
    • [12.4]：源缓冲区中开始读取的位置。
    • [12.5]：我们先前计算出的要读取的采样数。
  • [13]：现在从 outputSamplesRemaining 变量中减去我们刚处理的采样数。
  • [14]：把 outputSamplesOffset 增加相同的量，以防 while() 循环还有下一轮。
  • [15]：也把 position 成员偏移相同的量。
  • [16]：最后，检查 position 成员是否到达 fileBuffer AudioSampleBuffer 对象的末尾，如有必要则将其重置为零以形成循环。

练习：添加一个电平滑块来控制音频文件的播放电平（参见教程：控制音频电平）。你可以使用 AudioSampleBuffer::applyGain() 或 AudioSampleBuffer::applyGainRamp() 函数对 AudioSampleBuffer 对象中的数据应用增益。

多线程问题

如前所述，本教程通过在用户每次点击打开…按钮时关闭并重启音频来避免多线程问题。但如果我们不这样做会怎样——可能发生什么？有很多事情可能出错，所有这些都与以下事实有关：getNextAudioBlock() 和 openButtonClicked() 两个函数可能在不同线程中同时运行。以下是一些例子：

  • 假设应用已经在播放音频文件，用户点击打开…按钮并选择了一个新文件。假设音频线程在 [4] 和 [5] 之间中断了这个函数。缓冲区已被调整大小，但数据尚未写入缓冲区。缓冲区可能仍包含上一个文件的音频数据，但这取决于调整大小时是否需要移动缓冲区的内存。无论哪种情况，我们大概都会听到毛刺。
  • getNextAudioBlock() 函数可能被 openButtonClicked() 函数中的代码中断。假设这发生在 [11]之后，而 openButtonClicked() 函数刚刚执行到 [4]。缓冲区可能被调整为比原来更短，但我们在前几行已经计算好了起始点。这可能导致内存访问错误，应用可能崩溃。
  • getNextAudioBlock() 函数可能在调用 AudioSampleBuffer::copyFrom() 函数时被中断。同样，取决于它的实现，我们最终可能访问不该访问的内存。

还有其他一些事情可能出错。你可能熟悉使用临界区来同步线程之间的内存访问。这只是一个可能的解决方案，但在音频代码中使用临界区要小心，因为它可能导致优先级反转，从而造成音频丢音。我们在教程：使用 AudioSampleBuffer 类循环播放音频（进阶）中研究了一种避免临界区的方案。

注释

44.1kHz 的 2 秒立体声音频在 AudioSampleBuffer 对象中会占用 705,600 字节，因为有：

  • 2 个通道
  • 2 秒
  • 44,100 个采样
  • 每采样 4 字节（使用 float 类型）

把它们相乘，结果是：2 x 2 x 44100 x 4 = 705600
