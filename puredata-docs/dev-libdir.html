libdir

libdir - Pd 库的通用格式

既然越来越多的人在构建用 Pd 编写的对象集合，有一个通用的库格式就是合理的。这个库格式应当易于创建、安装和使用。它既应当在被安装到全局路径（即 pd/extra）时可用，也应当在被复制到项目文件夹本地时可用。它应当能配合用任何受支持语言编写的对象工作（即二进制文件、.pd，以及像 pdlua 和 pdtcl 这样的各种加载器）。

“dirlib” 方式

libdir 可以不加任何修改地用于 “dirlib” 方式。这种方式使用 [declare] 把每个库的文件夹加入给定 patch 的路径，而不是像加载库那样加载 libdir。

包含在帮助浏览器中

有了标准的库格式，帮助浏览器的树形结构就可以根据已安装的库动态构建。要让这件事运作良好，就必须有一个标准，否则代码会过于复杂。这又为在帮助浏览器中使用更多元数据打开了大门。

基本布局

下面是一个 libdir 的基本结构：

mylibrary-\
          |\_mylibrary.pd_linux  (shared binary lib)
          |
          |\_mylibrary-meta.pd
          |
          |\_my_pd_object.pd
          |
          |\_my_pd_object-help.pd
          |
          |\_my_c_object.pd_linux
          |
          |\_my_c_object-help.pd
          |
          |\_README.txt
          |
          |\_LICENSE.txt
          |
          |\_manual--\
          |          |\_index.html
          |          |
          |          |\_etc...
          |
           \_examples
                     |\_awesomeexample.pd
                     |
                     |\_evenbetter.pd
                     |
                     |\_etc...

mylibrary-meta.pd 把这个文件夹标记为一个库。它是一个 Pd patch，包含关于该库的元数据。最基本的元数据是 *作者*、*描述*、*许可证* 等。如果对象不是 Pd patch 或编译好的 DLL（.pd_darwin、.pd_linux、.dll 等），meta patch 还会包含对加载器的引用。也就是说，它会在 patch 里有 [loader/python] 这个对象。

目前能用的部分

最终，meta 文件会被读取以获取元数据，特别是给自动生成的帮助系统、加载器使用，也许还有其他用途。目前，它包含一些人类可读的信息，并被用作一个标记，表示某个目录是一个库。另外，这样实现要容易得多，我可以使用 open_via_path() 而不用写一个新函数。宏伟的计划是让一个目录容纳对象、帮助文件、手册等，使它成为一个自包含的库。

目前有两条路径被加入 helppath。第一条支持把帮助文件放在完整的库目录格式里，也就是所有东西都在一个文件夹中。要让它在新的 Help 菜单/浏览器系统中工作，还需要实现帮助 meta 系统。最终，为了让这件事正常工作，/path/to/extra 必须被加入 sys_helppath。

评论

META 数据 --bbogart, Thu, 23 Mar 2006 21:13:51 +0100

我认为，如果元数据适用于整个目录（libdir），并且只包含 META 数据，而不用作文档的分区入口，那它就应该是纯文本。对我来说，为了能编辑 metafile 而付出解析一个 PD 文件来获取纯文本信息的低效代价，理由并不充分。

meta 文件用 .pd 格式 --hans, Thu, 23 Mar 2006 21:49:44 +0100

用 .pd 格式的好处是，它让加载特定语言的加载器变得非常简单。基本上，当 Pd 打开一个 libdir 时，它首先打开 meta 文件。在 meta 文件中，加载器是作为一个对象包含在内的。所以 Pd 打开 meta patch 就加载了加载器。就像你在对象框里输入 [Gem] 会加载 Gem 库一样。这一点将来可能会变，但它在实现过程中提供了便利。
