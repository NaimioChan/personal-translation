Git 工作流程

Miller 现在把他的 git 仓库推送到 pure-data SourceForge 项目，所以我们可以用 git 保持同步并生成补丁。本页记录的是对向 Pd 核心贡献代码有用的 git 工作流程。

直接从 Miller 的仓库生成补丁

如果你想基于 Miller 的 git 添加某个功能，再把这个功能作为补丁提交到 patch tracker，这就是生成补丁的做法：

  • git clone git://pure-data.git.sourceforge.net/gitroot/pure-data/pure-data（获取一份新的源代码副本）

  • cd pure-data

  • git checkout -b new_branch（新建分支）

  • git commit（把所有改动提交到本地分支）

  • git rebase -i（把分支里的提交整理成单个干净的补丁）

  • git log -n2（查看最近两次提交的日志）

  • git format-patch <id of the second to last commit>

  • 提交到 patch tracker

使用自己 fork 的仓库时生成补丁

下面是基于某个功能生成补丁的一种思路。基本上就是：为一个功能建一个本地分支，大量提交；做完之后 rebase 成干净的补丁并合并进本地 master，然后把补丁提交给 Miller。大致是这样：

  • git pull pure-data master（从 Miller 那里更新到最新代码）

  • git checkout -b new_branch（新建分支）

  • git commit（把所有改动提交到本地分支）

  • git rebase -i（“把分支里的提交 "rebase" 成干净的补丁”）

  • git checkout master（切换到 master 分支）

  • git pull pure-data master（从 Miller 那里更新到最新代码）

  • git checkout new_branch（切回 new_branch）

  • git rebase master（把刚拉进 master 的改动合并进 new_branch）

  • git checkout master（切回 master）

  • git merge new_branch（把 new_branch 合并进本地 master）

  • git branch -d new_branch（删除分支）

  • git push（把改动推送到你自己的远端仓库）

现在生成补丁：

  • git log -n2（查看最近两次提交的日志）

  • git format-patch <id of the second to last commit>

  • 提交到 patch tracker

让你的改动始终领先于 pure-data master 分支

如果你不想与像 pure-data 这样的上游仓库合并，而是想让自己的改动始终领先于 pure-data 的 master 分支，可以使用这种做法。git 手册把这种方式称为 Keeping a patch series up to date using git rebase。当其他人没有基于你的 master 提交改动时，这套工作流程效果很好。它假定你已经克隆了 pure-data，把 origin 设成了某个远端仓库（比如 gitorious），并在 .git/config 里把 pure-data 添加为一个 remote。

  • git checkout -b new_branch （新建分支）

  • 写代码

  • git commit （把所有改动提交到本地分支）

  • git rebase -i （“把分支里的提交 rebase 成干净的补丁”）

  • git checkout master （切换到 master 分支）

  • git pull origin master （从 origin 更新到最新代码）

  • git checkout new_branch （切回 new_branch）

  • git rebase master （把刚拉进 master 的改动合并进 new_branch）

  • git checkout master （切回 master）

  • git merge new_branch （把 new_branch 合并进本地 master）

  • git branch -d new_branch （删除分支）

  • git push （把改动推送到你自己的远端仓库）

现在生成补丁：

  • git log -n2 （查看最近两次提交的日志）

  • git format-patch <id of the second to last commit>

  • 提交到 patch tracker

现在从 pure-data 更新到最新代码

  • git checkout pure-data （切换到 pure-data 跟踪分支）

  • git pull pure-data master （从 Miller 那里取最新代码，但不合并）

  • git checkout master （切回 master）

  • git rebase pure-data （把 pd-extended 的代码 rebase 成基于 pure-data 的补丁）

  • git push origin master （把改动推送到 pd-extended.git）

  • git push origin pure-data （更新 pd-extended.git 里的 pure-data 分支）

Pd-extended

Pd-extended 使用的是上面那套“patch series”工作流程的修改版。rebase 在一个长期存在的 patch_series 分支里进行，然后内容被合并到 master，这样大家就可以基于 master 工作。这种情况下，patch_series 分支作为参考，但人们不应该在 patch_series 上提交，而始终应该在 master 上提交。

  • git clone git://pure-data.git.sourceforge.net/gitroot/pure-data/pd-extended.git

  • git checkout -b new_branch （新建分支）

  • 写代码……

  • git commit （把所有改动提交到本地分支）

  • git rebase -i （“把分支里的提交 rebase 成干净的补丁”）

  • git checkout master （切换到 master 分支）

  • git pull origin master （从 origin 更新到最新代码）

  • git checkout new_branch （切回 new_branch）

  • git rebase master （把 new_branch 的提交 rebase 到 master 的最新提交之上）

  • git checkout master （切回 master）

  • git merge new_branch （把 new_branch 合并进本地 master）

  • git branch -d new_branch （删除分支）

现在生成补丁：

  • git log -n2 （查看最近两次提交的日志）

  • git format-patch <id of the second to last commit>

  • 提交到 patch tracker

下面是 Hans 从 pure-data 更新到最新代码的工作流程：

  • git checkout pure-data （切换到 pure-data 跟踪分支）

  • git pull pure-data master （从 Miller 那里取最新代码，但不合并）

  • git checkout patch_series （切回“patch series”分支）

  • git rebase pure-data （把 pd-extended 的代码 rebase 成基于 pure-data 的 patch_series）

  • git checkout master （切换到 master 分支）

  • git merge pure-data （把 pure-data 里的所有改动合并到 master 分支）

  • git merge patch_series （把所有改动合并到 master 分支）

  • git diff patch_series..master （确认代码已同步）

  • git push origin master:master （把改动推送到 pd-extended.git）

  • git push origin pure-data:pure-data （推送到 pd-extended.git 上的 pure-data 分支）

  • git push origin patch_series:patch_series （推送到 pd-extended.git 上的 patch_series 分支）

下面是 Hans 往 Pd-extended 里添加内容的工作流程：

  • git checkout patch_series （切回“patch series”分支）

  • git checkout -b new_branch （新建分支）

  • 写代码……

  • git commit （把所有改动提交到本地分支）

  • git rebase -i （“把分支里的提交 rebase 成干净的补丁”）

  • git checkout patch_series （切换到 patch_series 分支）

  • git merge new_branch （把 new_branch 合并进本地 master）

  • git branch -d new_branch （删除分支）

为你的 git 配置公开仓库

如果你开始维护一个保存自己对 pure-data 所做改动的 git 仓库，那么把它发布到某个地方、方便别人从你这里拉取，可能是合理的。这样你就需要能推送到自己的公开仓库（例如 gitorious），同时仍能从 Miller 的仓库拉取。要做到这一点，可以像上面的例子那样，再设置一个名为 pure-data 的 remote。下面是需要加到你的 pure-data.git/.git/config 里的内容：

[remote "origin"]
        url = git@gitorious.org:pdvanilla-hcs/pdvanilla-hcs.git
        fetch = +refs/heads/*:refs/remotes/origin/*

[remote "pure-data"]
        url = git://pure-data.git.sourceforge.net/gitroot/pure-data/pure-data
        fetch = +refs/heads/*:refs/remotes/origin/*

[branch "master"]
      remote = origin
      merge = refs/heads/master

另一种方法

还有一种方式，可以在你自己的 master fork 里工作：

  • 把 master 仓库克隆到本地（git clone）

  • 在 gitorious 或 github 上 fork 这个仓库

  • 写代码、提交，并把改动推送到你自己的 fork（git add; git commit -m; git push url-of-my-fork）

  • 通过 gitorious 或 github 网站向上游发起 pull request

  • 等待你的提交被合并

  • （并定期用 git pull 拉取上游）
