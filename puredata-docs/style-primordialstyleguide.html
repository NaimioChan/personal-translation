原始样式指南

风格的领域

美元符号参数、抽象对象、子 patch、入口／出口、Trigger、视觉布局、patch 组织、文件系统组织、Send/Receive/Value/Table 命名约定、抽象对象／子 patch 命名约定、接口（例如 API 和 patch 间通信）、通用的「编程建议」（例如计数器、初始化、取反以及其他日常事项）

命名

Frank Barknecht：

我有时用下划线风格，但更常用简单的「短横线」风格：写成 "r some-thing" 而不是 camelCase。我的理由是：在德语键盘上它不需要任何 Shift 组合键，而且我觉得 camelCase 难读。我总是用 "$0-" 把 $0 分隔开。$0myGod 很容易被误解。

Enrique Erne：

$1. 还是 $1- 还是 $1_（用哪个分隔符？）

Chris McCormick：

不过总的来说，我觉得用 '/' 作分隔符比 '.'、'-' 或 '_' 更令人满意，因为它与 OSC 的做法以及整个 libdir 那套更一致，虽然这可能反而更让人困惑。唔。我以前用 '-'，所以那些 s-抽象对象的名字就是这样来的。

Luke Iannini：

分隔符有两类：分隔层级的，和起空格作用的。我赞成把 "-" 当作等同于「空格」，因为它看起来最常见。至于层级分隔符，我认为要么总是用 "/"，要么把 "/" 留给 OSC 地址，在构建 "Pure.data.hierarchy" 时用 "."。

还有一点：分隔 $0 或 $1 等应该用层级分隔符，而不是空格分隔符。

全局变量

Frank Barknecht：

我倾向于把全局变量写成全大写。

Send/Receive 配对

Frank Barknecht：

当我要给配对的 send/receive 命名时，我用 $0-some-s 和 $0-some-r。

Luke Iannini：

我喜欢 Frank 的建议：给一对 send 和 receive 都加后缀，因为这样你看到 "-s" 就知道有对应的 "-r"，反之亦然。我想我只在使用 GUI 对象时才这么做，所以对我来说，这也有助于识别某个 send/receive 属于 GUI 对象。

参数

Frank Barknecht：

对，按数字顺序没问题，但把 $0 放在最前面意味着：在抽象对象内部使用 $1 得到的是父级的 $0，抽象对象内部的 $2 是那个叫 $1 的值，$3 = $2，依此类推。把 $0 放在最后，那么在像上面那样的抽象对象树／层级里就能让 $1 = $1、$2 = $2，依此类推。

Enrique Erne：

现在说点个人的：我不喜欢 $0 :) 。作为 patch 内的命名空间它没问题，但我常常需要从「外部」访问某些东西，于是只能把 $0 到处传递，这很难看。我更愿意用一个全局 receiver，然后把一切都路由过去。所以我把 patch 的名字传给它的抽象对象。抽象对象会得到一个内部带 $1 的全局 receiver，$1 就是母 patch 的名字。这有助于辨认方向，比如看窗口标题：

yourabstraction.pd (mother) 是不是比 yourabstraction.pd (1284) 更好

你甚至可以对 [sssad $1/vol] 这样用，而不必担心 $0 把你的 sssad 键变成不可用的名字。如果我在 GOP 里放 GUI，每个滑块的 send 和 receive 名字都以 $1. 或 $1- 或 $1_（请给个准则！）开头，这样就有可能从另一个 patch 劫持这个 patch。比如 midilearn 或 automator patch 就能控制这套设置里的任何滑块。

抽象对象

Matt Barber：

有一种打 patch 的风格主张，抽象对象的行为应尽可能接近内置对象，而在 vanilla 中内置对象通常基本上也不了解周围的环境

GUI 元素

Enrique Erne：

对于滑块这类 GUI 元素，我从没后悔过使用某种名字层级（$1.vol），通常是 mypatch-myabs-myparameter 或 mypatch.myabs.myparameter 或 mypatch_myabs_myparameter 之类。这样你可以用任何东西劫持你通道的 aux-sender。

但这也意味着你不能多次打开同一个 patch，对我来说没问题，因为我的代码总是通过抽象对象复用。

音频通道（throw~/catch~、s~/r~）

Matt Barber：

立体声不应被突显为优先情形……还可以用很多其他更通用的命名法，例如 ch1 ch2 ch3 ch4（对喜欢通道数组的人用 ch0 ch1 等），或者只用数字，或者别的什么。这样将来就能比较放心地把来自立体声环境的代码取出来用在多声道空间里。另外一般来说，不该把扬声器与通道号的实际对应关系写死。到如今「标准」且可接受的配置太多了，无法钦定某一种优于其他。

调试

Matt Barber：

把用于调试的数字框和 bang 与 patch 的运作解耦

抽象对象

Matt Barber：

另外，我忘了提，我认为抽象对象（或许子 patch 程度稍轻）在输入／输出上应遵循 Pd 对象的从右到左惯例，即使这会让父级里的布局变复杂。比如在我看来 cyclone 里的 [gate] 就是糟糕的 Pd 风格，而一个模仿它的抽象对象（比如 [gator]）应该更像多出口的 [spigot] 那样设计。就连 [timer] 也仍然让我不舒服，不过我猜那是个特例。

抽象对象／子 patch 命名约定

Matt Barber：

我认为抽象对象应尽可能避免与 extended 中的名字冲突，即使这个 patch 是为 vanilla 设计的。另外，我认为当涉及音频信号时，在抽象对象名字里加上波浪号（~）是有帮助的。

编程建议

Matt Barber、Enrique Erne：

一对多连接一律使用 trigger

Luke Iannini：

要取反一个 toggle，使用 [== 0]。用两个抽象对象共同的父级的 loadbang 来初始化两个或更多相互依赖的抽象对象。

动态打 patch

IOhannes M. Zmoelnig：

可能有人会改变 Pd 从文件构建 patch 的方式，或者改变文件格式。

非官方／不受支持并不意味着它不能工作。它的意思是：如果它在未来的版本里停止工作，那是你（用户）自己的责任。

视觉布局

Marius Schebella：

在对象的间距和对齐上我很较真。我开始用 ctrl+方向键来调整所有对象的间距。这样所有对象都像在网格上一样排列，彼此间距总是 10px 的整数倍。我不知道这该不该写进样式指南，但对于教程这类「官方」patch 或许可以这么要求。我几乎没法看 montreal 的那批抽象对象……

不要把 patch 存成位置 <0/0。有些窗口管理器不允许拖动 patch 窗口。（哦，还有，请不要把对象放在画布外，尤其不要放在 <0/0，为了看到 patch 的开头而必须向左滚动会让人心脏病发作。）而且不是所有人都有宽屏或高分辨率显示器，所以我认为 patch 的最大宽度应该是 1024。

Frank Barknecht：

至少把相连的对象左对齐就能带来很多好处。你会得到一个干净的左侧，由于热入口在左边，这个左侧对大多数 Pd 对象来说都是重要的一侧。这样即便因为平台／版本问题，[t b a a a a] 里的 "a" 之类不再对齐，你左侧的主逻辑流依然布局清晰。

在对象和注释的右侧多留一点空间以避免框重叠也是好的。我认为在 Linux 上用 10px 字体时，Pd-extended 显示得比 Pd-vanilla 窄不少，而我用的就是这个字体。（不过我自己也常常没在右侧留够空间。）

组织

Marius Schebella：

我还想指出良好分组的重要性。有时我用背景画布来强调某些对象属于一组（执行某种变换或算法）。

如果我做的是作为装置运行的大 patch（没有界面），父 patch 基本上是空的，它只显示作品信息和致谢，所有东西都在一个叫 [MACHINE] 的子 patch 里。那通常更像是对空间的视觉呈现（按照传感器／音箱的位置），或者是对 patch 结构的基本概览，并简短说明各个子 patch 在做什么。

Matt Barber：

这点很好。事实上，对于某些 patch，比如要发给不靠 Pd 吃饭的音乐家的互动作品 —— =o) —— 我倾向于把所有东西放进一个带有 GOP 控制面的子 patch 里。我认为反对「蜘蛛网」风格是有益的，但主 patch 上有太多对象和连线多少也显得有些浪费。放一个可以用 bng 打开的子 patch 很好，那基本上就是一份 readme。我给抽象对象也这么做，只是不加 bng —— 就放点东西描述它在 patch 内部是怎么工作的，算是帮助文件的一个快速替代。

文档

Marius Schebella：

尽管人人都说 Pd patch 本身就是文档，因为一切都看得见，但事实并非如此，写注释应该是打 patch 的重要部分（cyclone 的 comment 允许使用不同的字体、字号、颜色和注释宽度）。

对于要便于移植的 patch，有些事项很重要。请注明用到了哪些库，并考虑用 declare 来加载对象。

文件系统组织

Marius Schebella：

然后，对于依赖抽象对象的 patch，*也许* 给它们取唯一的名字、或者放进子文件夹里会比较好。（我得说，我自己并不真的遵守这条规则。但至少有一点：主 patch 应该总是容易认出来，我通常用大写字母，这样人们知道该从哪个 patch 开始。

资源（图像、文本文件、数据）也可以放在子文件夹里。（想想 GEM 的例子，经常有某个图像或视频找不到。——至少过去是这样。）

Matt Barber：

当 0.39 逐渐淡出（这样就能用 [declare] 了），把抽象对象放在子文件夹里也许是有益的，或许 control 的放一个、tilde 的放另一个。如你所建议，文本文件、qlists、图像和声音文件也可以这样。这样主 patch 就干干净净地摆在那里，给除你之外任何可能要用它的人，对音乐家尤其友好。

待商议

Matt Barber：

如果抽象对象已经能给出足够的解决方案，是否应该用它而不是外部对象？在教学情境中，学生可能从相当精简的一组 unit generator 中学习受益，这时答案会不同吗？当性能高于一切时，答案会不同吗？

对于 GOP 抽象对象，用一个画布盖住抽象对象的名字和参数是不好的做法吗？如果把这些东西作为标签印在画布上呢？
