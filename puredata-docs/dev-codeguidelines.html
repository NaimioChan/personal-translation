代码规范

关于在这个邮件列表上逐渐形成的仓库规范，下面列出其中一些（它们都应该被正式记录下来）：

命名：

  • 一般 —— 对象名往往存放在文件系统上；要记住，有些常见的文件系统不允许使用特殊字符或某些名字；有些文件系统没有大小写敏感的概念，另一些则有。

    • - 所有库名以及仓库中的所有分区一律小写（在网页等地方你想怎么命名都行，但库名和 /externals/ 下的目录必须全小写（据我所知只有三个例外：Gem、miXed 和 OSCx，它们都是历史遗留）） - 类名应该全小写（cyclone 除外，为了兼容 Max/MSP 它必须使用大写） - 名字中包含多个单词的类名应该用下划线分隔单词（即 [iem_anything_kernel]、[curve_log]、[define_loudspeakers]、[my_canvas] 等） - 类名不应该包含空格

    conversions —— 对于做类型转换的对象，已经确立了好几种命名约定。到底该用哪一种**仍有讨论**。请从可用的形式里选择一种。

    • - Pd 原生对象使用「旧类型 + "to" + 新类型」的约定，即 [ftom]。

      • （简单，但可读性不太好：它是 "a-to-m"，还是 "a-tom"，还是 "at-om"，甚至是 "atom"？）

      - 另一种流行的形式是「旧类型 + "2" + 新类型」，即 [list2symbol]。

      • （旧类型和新类型之间分隔得很好，只要两个名字里都不涉及数字：例如 [m22i2] 可能表示平方米与平方英寸之间的换算，但也可能表示很多别的东西）

      - 「旧类型 + "->" + 新类型」，即 [cart->pol]、[mapping->radians]、[gem->pdp]。

      • （旧类型和新类型之间分隔得很好，但受文件系统限制需要用十六进制字符替换）

      - 类型之间不应该有空格或下划线！
    file layout —— 关于是把对象组织成大型库（一个（1）文件里包含若干对象）更好，还是组织成单个外部对象（每个对象类都有自己的文件）更好，人们争论了很多。

    • 对于 pd-patch，答案很简单，因为一个 '.pd' 文件只能定义单个对象。不过，编译型对象（例如用 C 写的）两种方式都可以组织，而且各有优劣。为了让两种做法的差异不至于太大： - 文件应该与对象同名，[hid] = hid.c，[moog~] = moog~.c - 这些类应该能够按「单类单文件」的格式编译（另外再提供「多类单文件」的格式也没问题）

    namespaces —— 在不同库中名字相似但功能不同的对象

    • - geiger 命名空间让 "sp_" 这样的类名前缀变得没有必要。 - 如果你想把自己的类与另一个同名的类区分开，更好的办法是起一个更有描述性的名字。

代码格式

  • 缩进 —— Pd 核心源代码使用的格式是制表符宽度 8、缩进 4。其他代码的风格千差万别，或好或坏。
