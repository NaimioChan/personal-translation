调度与服务器计时

服务器捆绑延迟与 OSC 时序，逻辑时间与物理时间

参见：Server、TempoClock

为确保服务器上事件的正确时序，OSC 消息可以附带时间戳发送，以指明声音预计到达硬件输出的精确时间。

Latency

在 SuperCollider 语言中，时间戳是在后台基于一个名为 "latency" 的参数生成的。

要理解延迟是如何工作的，我们需要理解逻辑时间与物理时间的概念。

SuperCollider 中的每个时钟都同时具有逻辑时间和物理时间。

物理时间

始终推进，表示真实时间。

逻辑时间

仅当调度线程唤醒时才推进。

在已调度的函数或事件执行期间，逻辑时间保持在“预期”值不变。也就是说，如果事件被调度为正好 60 秒，那么在整个事件执行期间，逻辑时间都将是 60 秒。如果事件执行耗时 2 秒（非常罕见），那么在事件结束时，逻辑时间仍将是 60 秒，但物理时间将是 62 秒。如果下一个事件要在第一个事件开始后 3 秒发生，其逻辑时间将是 63 秒。逻辑时间不受系统性能波动的影响。

这个时序示例说明了其中的差异。它被故意写得低效，以便更清楚地暴露问题。同一个例程的两份副本同时启动。在一台理论上完美的机器上，操作不耗时，我们会听到两个声道完全同步。但这样的机器并不存在，而你听的时候显然也不是这种情况。这些例程还会在播放一个颗粒之前打印出逻辑时间（clock.beats）和物理时间（clock.elapsedBeats）。

s.boot;

SynthDef(\sinGrain, { |out = 0, freq = 440, amp = 0.5, dur = 1|
    Out.ar(out, SinOsc.ar(freq, 0, amp) * EnvGen.kr(Env.sine(1), timeScale:dur, doneAction: Done.freeSelf));
}).add;

2.do({ |chan|
    var rout;
    rout = Routine({
        var freq;
        {   freq = 0;
            rrand(400, 1000).do({ freq = freq + 1 });
            [thisThread.clock.beats, thisThread.clock.elapsedBeats].postln;
            Synth(\sinGrain, [\out, chan, \freq, freq, \dur, 0.005]);
            0.1.wait;
        }.loop;
    });
    TempoClock.default.schedAbs(TempoClock.default.elapsedBeats.roundUp(1), rout);
});

请注意，即使左右声道模式被调度在完全相同的时间，事件也不会同时完成执行。此外，Synth(...) 调用指示服务器在收到时立即播放 synth，因此右声道每个事件将比左声道滞后约 2 ms——而且每次滞后的量并不相同。因此，时序总是略微不精确。

此版本相同，但它为每个 synth 生成一个 1/4 秒的延迟参数：

2.do({ |chan|
    var rout;
    rout = Routine({
        var freq;
        {   freq = 0;
            rrand(400, 1000).do({ freq = freq + 1 });
            [thisThread.clock.beats, thisThread.clock.elapsedBeats].postln;
            s.makeBundle(0.25, { Synth(\sinGrain, [\out, chan, \freq, freq, \dur, 0.005]); });
            0.1.wait;
        }.loop;
    });
    TempoClock.default.schedAbs(TempoClock.default.elapsedBeats.roundUp(1), rout);
});

通过使用时间参数为 0.25 的 makeBundle，左右声道对应的 \s_new 消息会以相同的时间戳发送：即时钟的当前逻辑时间加上时间参数。请注意在表格中，两个声道自始至终具有相同的逻辑时间，因此两个声道完全同步。

这些例程是故意写得很糟糕的。如果将它们做到最大效率，即使没有延迟因子，同步也会更紧密，但永远不会完美。然而，如果你有多个例程在执行且其中几个被期望同时执行，你也会看到这个问题。有些会比其它更早执行，但它们的逻辑时间都相同。如果它们都使用相同的延迟量，你仍然会同时听到它们。

一般来说，所有由实时输入（MIDI、GUI、HID）触发的 synth 都应指定零延迟，以便它们尽快执行。所有序列化例程都应使用延迟以确保精确的定时。

延迟值应当留出足够的时间，让事件得以执行并生成 OSC bundle，并让服务器及时解释消息并渲染音频，从而准时到达硬件输出。如果客户端和服务器位于同一台机器上，这个值可以相当低。通过网络运行时，你必须留出更多时间。（延迟也会补偿网络时序抖动。）

Pbind 会自动从服务器的 latency 变量中导入 latency 参数。你可以像这样为事件模式设置默认 latency：

myServer.latency = 0.2;  // 0.2 是默认值

以下是用 latency 参数播放 synth 的三种方式：

// 消息传递风格
// s.nextNodeID 是从服务器获取下一个未使用节点 ID 的方法
s.sendBundle(latency, [\s_new, defName, s.nextNodeID, targetID, addAction, arguments]);

// 对象风格，向对象请求消息
synth = Synth.basicNew(defName, s);
s.sendBundle(latency, synth.newMsg(target, arguments, addAction));

// 对象风格，使用自动打包
// 与上一个示例一样，当它完成时，你将在 synth 变量中获得 Synth 对象
s.makeBundle(latency, { synth = Synth(defName, arguments, target, addAction); });
