客户端与服务器

客户端与服务器架构及操作

“SuperCollider”这一名称实际上用于指代五种不同的事物（图 1）：

  1. 音频服务器
  2. 一种音频编程语言
  3. 语言的解释器，即能够解释该语言的程序
  4. 作为服务器客户端的解释器程序
  5. 包含这两个程序并提供所提及功能的应用程序

因此，SuperCollider 应用程序由两个不同、自主的组件组成：服务器和客户端。对于前者，我们可以在 scsynth（SC-synthesizer）和 supernova 之间选择；对于后者，我们有 sclang（SC-language）。

说明

SuperCollider 应用程序采用客户端/服务器架构，将两个功能分开，分别由一方提供服务、另一方请求服务。客户端和服务器通过网络进行通信。

图 2 描绘了一个通用网络架构：若干客户端通过网络交换消息与服务器通信。在 SuperCollider 中，客户端和服务器使用 CNMAT 的 Open Sound Control (OSC) 协议的一个特定子集进行通信（通过 TCP 或 UDP）。因此，你会在帮助文件中看到许多对“OSC 消息”的引用。

为避免任何可能的混淆：网络是在抽象层面上定义的。这意味着客户端和服务器可以在同一台物理机器上执行。这正是在你使用 SuperCollider 应用程序时通常发生的情况：两个程序将在你的机器上运行，即 scsynth（或 supernova）和 sclang。

服务器应用程序 scsynth 或 supernova 是一个精简高效、专用于音频合成与处理的命令行程序。它对 SC 代码、对象、面向对象编程或任何与 SC 语言相关的内容一无所知。

此服务器的客户端是 sclang。Sclang 执行两项不同的任务：

Client

它是服务器的客户端，即它向服务器发送 OSC 消息。要写一封信给服务器，你需要一张纸和一个信封：sclang 两者兼备。

Interpreter

它是 SuperCollider 编程语言的解释器，即允许用户用上述语言编写代码并交互式执行所产生的命令，例如控制音频服务器。特别地，OSC 消息写起来可能很繁琐，因为它们与服务器一样处于低层视角。SuperCollider 语言是一种高层、功能完备的面向对象语言，使用户能获得比 OSC 消息强大得多的表达能力。通常，解释器将 SuperCollider 语言的代码转换为供服务器使用的 OSC 消息。用户用 SuperCollider 语言写诗（打个比方），然后由 sclang 解释器改写成 OSC 散文，发送给服务器。

在 sclang 内部，可以通过以下方式启动服务器应用：

s = Server.default; // 创建一个新的 Server 对象并将其赋值给变量 s
s.boot;             // 启动服务器应用，即告诉服务器准备好工作

sclang 解释器可以通过两种方式向服务器发送 OSC 消息：

directly

在这种情况下，sclang 提供了一个薄语法层，使人们能够处理原始 OSC 消息。此时，服务器的所有功能都可以通过 Server 的 .sendMsg 方法以及其他类似消息“手动”使用。

n = s.nextNodeID;                   // 从服务器获取一个可用的 nodeID 并赋值给 n
s.sendMsg("/s_new", "default", n);  // 使用 SynthDef "default" 创建一个 ID 为 n 的 synth
s.sendMsg("/n_free", n);            // 释放合成器 n
indirectly

语言应用为你提供了便捷的 OOP 功能，用于跟踪和操作服务器上的事物。高层语法由 sclang 翻译成低层 OSC 消息并发送到服务器（语言封装）。

x = Synth("default");   // 在默认服务器 (s) 上创建 synth 并为其分配一个 ID
x.free;                 // 释放 synth、其 ID 和资源

以这种方式工作，你获得了一些功能。它会自动为你提供一个节点 ID，允许你以语法优雅且高效的方式控制 Synth（参见 Synth 和 Node 帮助文档），并在这样做时能够利用面向对象编程的所有优势。封装复杂性和簿记工作大大降低了你自己代码中出现错误的机会。

语言封装允许用户用极少的代码访问复杂的行为。图 3（暂时忽略 sclang 被表示为其他可能客户端中的一个客户端这一点，详见后文）示意性地表示了当你求值如下音频函数时会发生什么：

// 假设服务器已经启动
{SinOsc.ar}.play ;

在这种情况下，许多服务器操作都被隐藏了。要理解这段代码求值过程中涉及的内容，请参阅 04. Functions and Other Functionality 和 10. SynthDefs and Synths（Scott Wilson 教程的一部分）。

OOP 风格也有少量开销。它需要客户端的 CPU 周期和内存来创建和操作一个对象。通常这并不显著，但有时你可能更愿意使用不那么优雅、也更廉价的第一种方法，例如在创建大量只需播放然后自行释放的 grain 时。

因此，只要愿意自己完成所需的维护工作，就可以在服务器上创建 synth 节点而不实际创建 Synth 对象。组节点、缓冲区和总线也是如此。关于这些概念的更详细讨论，可参见 Node Messaging 帮助文件。

总之，要记住的关键是区分节点、总线、缓冲区和服务器这类事物与语言应用中表示它们的对象（即 Node、Bus、Buffer 和 Server 的实例；这些被称为“服务器抽象对象”）。在概念上保持它们的区分将有助于避免许多困惑。

Pros/Cons

客户端/服务器架构提供三个主要优势：

stability

如果客户端崩溃，服务器会继续工作，即音频不会停止。这在现场演出场景中直观上很重要。反之，服务器可以崩溃，而你仍可从客户端管理该情况。

modularity

合成是一回事，控制是另一回事。将这两个方面分离，可以（例如）从 sclang 以外的应用程序控制服务器。唯一重要的是它们能够向服务器发送正确的 OSC 消息。

远程控制

客户端/服务器网络可以位于你的计算机之外，例如通过互联网。这使得例如可以在印度的一个客户端（sclang 或其他）控制阿拉斯加的音频服务器。

有两个明显的缺点：

latency

消息传递过程会引入少量延迟。这不应与音频延迟混淆，音频延迟可以相当低。它只是意味着在一侧发送消息与另一侧接收并对其作出响应之间存在一个小的、通常可忽略的延迟。（可以通过使用“internal”服务器将其最小化。详情请参见 Server。）

异步执行

在某些情况下，客户端可能需要知道服务器上的某个任务（例如处理一个大声音文件）已经完成，然后才能继续执行另一个任务。由于某些任务完成所需的时间不确定，因此需要一种回复机制。这可能会给你的代码增加一些复杂性，但原则上不是问题。（参见 OSCFunc 和 OSCdef。）一些服务器抽象对象（如 Buffer）通过 'action' 函数自动提供这一机制，这些函数会等待完成后再执行。

给进阶读者的最后一点说明

除 sclang 之外，还可以从任何其他提供 OSC 消息传递的客户端（例如 Java、Python、Max/MSP 等）控制服务器。关于网络连接，请参见 Server Architecture、NetAddr、OSCFunc。

不过一般而言，sclang 是与服务器通信的更可取方式，原因有三：

  • 它赋予你 SuperCollider 语言的表现力；
  • 该语言明确地适配服务器的需求（更重要的是，适配音乐家的需求）
  • 它允许创建 SynthDef 并将其加载到服务器上（参见 SynthDef），而并非所有客户端应用都能做到这一点
