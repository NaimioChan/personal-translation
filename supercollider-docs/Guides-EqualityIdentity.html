SuperCollider 中的同一性与相等性

SuperCollider 中引用相等（“identity”，===）与值相等（“equality”，==）的区别

参见：Event、Float、Introduction to Objects

同一性与相等性之间的区别与哲学、逻辑学和计算机科学中更广泛的问题相关。1

目前的讨论更狭义地关注 SuperCollider 中如何理解这一区别的概述。

两个彼此相等的对象不一定完全相同。

注意： 此处的“对象”一词指的是类的实例，而不是抽象类 Object。参见 Introduction to Objects。

一家工厂每天可能生产数千把螺丝刀，就某项规格而言它们彼此相等；但每一把螺丝刀只与自身同一（因为它占据此时此地的特定位置，或刻有特定的序列号）。因此我们可以说，同一性，即对象与自身的关系，比相等性，即一个对象与另一个对象就某种共同属性而言的关系，更为严格。

同样，在 SuperCollider 中，在 sclang 中创建的对象的同一性是通过它们在内存中的位置来确定的。2

a = [1,2,3];
b = [1,2,3];
a === a // -> true：同一性作为对象（a）与自身的关系。
a == a // -> true；相同的对象必然相等。
a === b // -> false；因为 a 和 b 由于内存位置不同而是不同的对象。
a == b // -> true；相等的对象不必是同一对象。

在上面的例子中，a 和 b 是 不同的 Array 类实例，各自拥有自己的内存地址。你可以通过 .dump 方法查询该地址：

a.dump;
b.dump;

对于编程新手来说，了解这一区别可能就足够了：

===（同一性）和 ==（相等性）方法不可互换，它们含义不同。

在大多数情况下，== 的行为符合“朴素”预期。例如，从高中数学我们知道，5 == 5.0 应返回 true；它确实如此。3

另一方面，=== 的行为更多取决于底层实现，在某些情况下起初可能显得反直觉。

下面两个示例针对两个相关的用例进一步说明了这一区别：复制变量的内容，而不仅仅是将其赋给另一个变量（这是编程中的一个基本区别，不仅限于 SuperCollider）；以及对 IdentityDictionary 或 Event 的实例进行索引访问（这是 SuperCollider 特有的）。

区别所在之处：使用 .copy 方法从一个变量中给定的对象创建多个实例

上面的示例将每个变量赋值为数组 [1,2,3] 的一个实例，并表明这些变量现在指向不同的内存位置，因此它们的内容并不相同。然而，当把一个变量赋值给另一个变量而不是对象实例时，不会创建新实例；相反，两个变量将引用同一个对象，位于内存中的同一位置。这在实际中是有意义的：当你想要以多种不同方式修改某个给定列表，但该列表只存在于一个变量中时。此时问题就变成如何仅从这个变量创建多个相等但不相同的实例。下面的示例无法按预期工作：

x = ['C', 'E', 'G']; // C major
y = x; // 这稍后会引起麻烦。
z = x; // 这个也是。
// 此时 x 等于 y 和 z。
// 现在把 y 中最后一个音符改为小三度：
y[2] = 'A'; // -> ['C', 'E', 'A'] ... OK
//更改 z 中的第一个音符以获得 e 小调；
z[0] = 'B'; // -> ['B', 'E', 'A'] ... ; NOT what we wanted.
//为什么这没有按预期工作：
x === y; // -> true：x 和 y 指向同一个 List。
y === z; // z 也是如此。
//我们最终修改了原始列表两次，
//尽管我们想保留原始的 x，
//并从中得到两个不同的变换……

堆叠四度很好听，但我们这里想保持无聊，只用三和弦。我们需要做的是使用 .copy 方法来创建由 x 引用的 Array 对象的副本，这些副本与其相等但并不相同，以便我们可以分别修改它们：

x = ['C', 'E', 'G']; //C major
y = x.copy;
z = x.copy;
x == y; // -> true
x === y; // -> false
// 现在将 y 中的最后一个音符改为得到小调：
y[2] = 'A'; // -> ['C', 'E', 'A'] ... OK
// 更改 z 中的第一个音符以获得 e 小调；
z[0] = 'B'; // -> ['B', 'E', 'G'] ... OK

因此，相等与同一性之间的区别隐含在诸如“把这把螺丝刀漆成绿色，那把漆成红色”这样简单的指令中。（计算机只需要以更正式的方式被告知这些事情。）

区别所在：不要将字符串用作 IdentityDictionary 和 Event 的键。

在 Dictionary 及其子类中，查找算法的选择会影响性能。使用同一性作为该算法（如 IdentityDictionary 和 Event 所做的那样）通常比使用相等性（如 Dictionary 所做的那样）更快。因此，在使用 IdentityDictionary 和 Event 时，键不应该是 String，而应该是 Symbol。下面的例子说明了原因：

"String" == "String"; // -> true
//接下来发生的事可能会让你惊讶：
"String" === "String"; // -> false
//因为每个 String 对象都是单独的实例。

//以 String 为键的 Dictionary（可行）：
x = Dictionary.new();
x.put("String",1234);
x["String"] // -> 1234

//使用 String 键的 IdentityDictionary（无法工作）：
y = IdentityDictionary.new();
y.put("String",1234);
y["String"] // -> nil

//使用 String 键的 Event（不会工作）：
z = (); //z = Event.new() 的简写
z.put("String", 1234) // -> ("String":1234)
z["String"] // -> nil
//... 因为 String 实例并不完全相同！

//Symbols 来救场：
z.put('Symbol', 5678) // -> ('Symbol':5678)
z['Symbol'] // -> 5678

实现细节

具有唯一表示形式的值：Symbol、SimpleNumber 等。

为什么 Symbol 可以作为 IdentityDictionary 的索引，而 String 却不能？因为每个 Symbol 都具有唯一的表示，使得 'symbol' 和 'symbol' 始终指向同一内存位置，无论它们位于代码中的何处。因此，传递给字典的 .at 方法参数的实例，与作为字典键参数的实例是完全相同的，而不仅仅是相等。

具有唯一表示的类的其它例子是 SimpleNumber 及其子类（Integer、Float）：对给定值（比如 1.234）的 Float 的每个引用都指向同一个实例。（当然，该实例与不同值的浮点数不同，例如 1.23400001。）

正如我们所见，对于String而言情况并非如此，代码中每次出现的String都会创建一个新实例，而不是指向具有相同值的现有实例。对于Collection来说通常也并非如此。我们已经在Array中看到了这一点；下面是一个针对Set的类似示例。

Set[1,2,3] === Set[1,2,3] // -> false

除非被子类重写，否则相等性检查默认采用同一性检查。

并非所有类都显式实现了 == 方法。在这种情况下，== 仅默认等同于 ===。一个实例是 Function，4 其以下行为可能令人意外：

{1} == {1} // -> false!

要理解这种行为，我们必须知道两件事：第一，Function的实例没有唯一的表示，也就是说，和String（上面提到的）一样，代码中的每个{1}表达式都会被分配一个单独的实例。因此{1} === {1}会返回false。第二，与String不同，Function没有实现==方法，因此它的==默认等同于===。所以{1} == {1}实际上是在问这两个函数是否指向内存中的同一个对象实例，即{1} === {1}是否成立——而正如我们刚刚了解到的，它会返回false。

[1] - 关于哲学背景，请参见 Noonan/Curtis 2022。SuperCollider 所称的 Identity 和 Equality 大致分别对应哲学所称的“数值同一性”和“相对同一性”；更准确地说，分别对应计算机科学所称的“引用相等”和“值相等”。（例如 Miller/Goldman 2023，访问于 2025 年 5 月。）

[2] - 例外：对于原语（例如数字和符号），对象的身份直接与其值绑定。

[3] - 一个重要的例外是浮点运算，其中像 0.1 * 3 == 0.3 这样的表达式可能返回 false。然而，严格来说，这并不是相等性的问题，而是浮点表示的问题（参见 Float）。

[4] - 其原因（至少对函数而言）最终在于“停机问题”的不可判定性。参见 Immermann2021。
