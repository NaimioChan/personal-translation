CondVar

条件变量：阻塞一个或多个线程，直到某个条件为真

Object

CondVar 是一个条件变量，一种低层同步工具，允许一个或多个线程等待直到某个条件变为真。虽然名称中有“变量”，但条件变量并不像例如 FlowVar 那样包装一个变量。这里所指的条件完全在 CondVar 对象之外，可以是代码中任意状态。CondVar 支持两种基本操作：等待和发信号。等待是指挂起当前线程的执行，直到相关条件在未来某一时刻变为真。发信号是指向其他线程表明条件现在已为真，它们应当继续执行。

在等待 CondVar 时，你可以选择传入一个谓词（一个对象，通常是一个 Function，用 value 求值时返回 Boolean）作为参数。这带来了使用 CondVar 的两种常见方式：

  • 手动检查你的条件

    1. 首先，检查条件，以防它已经为真。
    2. 如果条件为假，则调用不带谓词的 wait 或 waitFor。这会挂起当前线程的执行。
    3. 当 CondVar 被信号通知或超时到期时，线程会继续执行。此时应再次检查条件，若不满足则继续等待。

    这通常采取如下形式的 while 循环：while { /* condition is false */ } { /* wait on condition */ }。

  • 让 CondVar 为你检查条件：使用带谓词的 wait 或 waitFor 调用，它会处理上述三个步骤。

以下代码说明了这两种方法：

// 版本 1：`wait` 不带谓词——需要 while 循环
(
var c = CondVar();
// 我们这里的资源将是一个 "message"，在可用时设置为某个字符串，
// 在不可用时设置为空。此资源
// 初始时不可用。
var message = "";

// 我们添加这些延迟是为了明确哪个线程先运行。试着
// 更改这些值，看看会发生什么！
var waitThreadDelay = 1;
var signalThreadDelay = 2;

// 这两个分叉线程将共享条件变量 `c`
// 以及条件状态 `message`。
fork {
    waitThreadDelay.wait;
    while { message.isEmpty } {
        "Resource is unavailable, waiting now".postln;
        c.wait;
    };
    "Resource is available, message is: '%'\n".postf(message);
};

fork {
    signalThreadDelay.wait;
    message = "meow, world!";
    c.signalOne;
    "Resource was made available and waiting thread was signaled".postln;
};
)

// 版本 2：`wait` 带谓词——不需要 while 循环
(
var c = CondVar(), message = "";
var waitThreadDelay = 1;
var signalThreadDelay = 2;

fork {
    waitThreadDelay.wait;
    c.wait({ message.notEmpty });
    "Resource is available, message is: '%'\n".postf(message);
};

fork {
    signalThreadDelay.wait;
    message = "meow, world!";
    c.signalOne;
    "Resource was made available and waiting thread was signaled".postln;
};
)

在内部，CondVar 不过是一个等待条件变为 true 的线程队列。在发送信号时，你可以选择只唤醒队列中下一个等待的线程（如果存在）（signalOne），或者唤醒队列中所有等待的线程（signalAll）。

注意，队列中的线程不会在收到信号后立即恢复。它们被安排在发出信号的线程放弃控制权之后立即恢复，无论是通过 yield 还是 wait，或者到达正在运行的 Routine 的末尾。在上面的示例中，signalOne Routine 直接结束，因此无需 yield 任何内容。

在其他语言中，你可能会看到条件变量也使用互斥锁进行同步。这通常是保护对条件状态共享访问所必需的。然而，由于 SuperCollider 的解释器是单线程的，每个运行中的线程都隐式持有全局解释器互斥锁，因此更细粒度的互斥锁是不必要的。

类方法

CondVar.new

创建一个新实例。

实例方法

.wait(predicate)

其行为取决于是否给出了 predicate。如果没有给出 predicate，此方法只是阻塞当前线程，直到它被 signalOne 或 signalAll 唤醒。否则，此方法等价于 while { predicate.value.not } { cond.wait }。换句话说，只有当谓词为假时线程才会阻塞，否则它会阻塞，并且只有在线程已被信号通知且谓词为 true 时才继续执行。

此方法只能在 Routine 或 Routine 包装器（例如 Task 或 Tdef）内调用。

参数：

predicate

在阻塞之前、以及在由 signalOne 或 signalAll 唤醒后恢复之前要检查的条件。如果 predicate.value.not 为 true，则恢复执行。通常，这是一个返回布尔值的 Function。

predicate 总是在调用 wait 的线程上执行。如果对 predicate 求值抛出异常，该异常将在调用 wait 的线程上向上传播，并且该线程将不再等待此 CondVar。

当 wait 返回时，谓词为真。稍后可能不再为真，例如当它依赖于系统时间或服务器状态等外部因素时。

返回值：

此对象

.waitFor(timeoutBeats, predicate)

类似于 wait，但如果相对超时 timeoutBeats 到期，线程也会解除阻塞。

如果 predicate 为 nil，此方法会阻塞当前线程，直到它被 signalOne 或 signalAll 唤醒，或者超时到期。如果 predicate 不为 nil，则当 predicate.value 为 true 时此方法立即返回，否则将阻塞，直到超时到期，或者直到线程被 signalOne 或 signalAll 唤醒且 predicate.value 为 true。

由于解释器的线程调度器不是抢占式的，到期的超时只会在其他线程空闲时唤醒线程。不能保证线程会在超时时间到期附近被唤醒，甚至不能保证它会被唤醒。例如，如果其他线程进入无限循环且永不 yield，就可能发生这种情况。

此方法只能在 Routine 或 Routine 包装器（例如 Task 或 Tdef）内调用。

参数：

timeoutBeats

超时前要等待的时长，以拍为单位。该值按以下规则转换：如果它的类是 Integer 或 Float，则保持不变；否则，如果它响应 asInteger，则调用该方法；否则，如果它响应 asFloat，则调用该方法。在此之后，如果得到的值不是 Integer 或 Float，则抛出错误。如果得到的值是 inf 或不是数字（NaN），也会抛出错误。如果得到的值小于或等于 0，那么当 predicate 不为 nil 时，waitFor 立即返回 predicate.value 的结果，否则返回 false。

进行这些严格检查是为了保护处理超时的线程。

predicate

在阻塞之前、以及在由 signalOne 或 signalAll 或超时唤醒后恢复之前要检查的条件。通常，这是一个返回 Boolean 的 Function。

predicate 总是在调用 wait 的线程上执行。如果对 predicate 求值抛出异常，该异常将在调用 wait 的线程上向上传播，并且该线程将不再等待此 CondVar。

返回值：

如果线程是因为超时到期而被唤醒，那么在给定了 predicate.value 的情况下返回它；如果 predicate 为 nil，则返回 false。否则返回 true。

换句话说，如果 predicate 非 nil，返回值为 true 表示在线程恢复时 predicate.value 为真。

.signalOne

唤醒一个正在等待此 Condition 的线程。线程按照调用 wait 或 waitFor 的顺序被唤醒。如果一个线程被唤醒并且之前是带谓词等待的，而该谓词仍为 false，它将再次 wait 并被放到等待此 CondVar 的线程队列末尾。在这种情况下，不会唤醒另一个线程。

返回值：

此对象

.signalAll

唤醒所有在该 Condition 上等待的线程。线程按调用 wait 或 waitFor 的顺序被唤醒。如果线程以谓词形式等待，且被唤醒后其谓词仍为 false，它们将以调用此方法之前的相同顺序再次阻塞。

返回值：

此对象

.shallowCopy

.copy

示例

简单的交互示例

(
c = CondVar();

Routine {
    1.wait;
    "waited for 1 second".postln;
    1.wait;
    "waited for another second, now waiting for you to run 'c.signalOne'...".postln;
    c.wait;
    "the condition is no longer waiting".postln;
    1.wait;
    "waited for another second, now waiting for you...".postln;
    c.wait;
    "the condition is no longer waiting".postln;
    1.wait;
    "the end".postln;
}.play;
)

// 运行此行以解除例程阻塞
c.signalOne;

生产者-消费者队列：单生产者、单消费者

以下示例展示了使用 CondVar 管理一个简单的生产者-消费者队列，其中有一个消费者和一个生产者。

生产者线程将“任务”添加到队列，而消费者线程则移除并“处理”它们。当没有工作要做时，消费者必须等待直到有工作可用。当工作太多时，生产者线程应避免创建更多任务。试着调整每个线程的等待时间，看看会发生什么。

(
var full = CondVar(), empty = CondVar();
var queue = Array();
var maxQueueSize = 5;
// producer 和 consumer 会在任务之间等待一段时长，
// 该时长处于这些范围中的某处。随着时间推移，你会看到队列在 0 到 maxQueueSize 之间
// 增长和缩小，但 CondVar 会让一切保持
// 同步。
var producerWaitTimeRange = [0.1, 1];
var consumerWaitTimeRange = [0.1, 1];

// 每个线程中的 "wait" 模拟异步执行某些任务，
// 在此期间可能创建其他任务。如果我们的任务
// 总是同步创建和/或执行，就不需要
// 在两个线程之间共享队列。

// 生产者线程
fork {
    var counter = 0; // 我们的“任务”目前只是一个递增的数字
    var task;
    loop {
        // 这保证了当我们从 `wait` 返回时，
        // 队列中有足够的空间来添加另一个任务。为了越过
        // 这一点，我们必须等待消费者调用
        // signalOne。
        full.wait({ queue.size < maxQueueSize });

        task = counter;
        counter = counter + 1;
        queue = queue.add(task);
        postf("Producer created a task: %. Current queue size: %\n",
            task, queue.size);

        // Now that we've added a task to the queue, we have to let
        // the consumer thread know in case it was waiting on us.
        empty.signalOne;

        wait(rrand(producerWaitTimeRange[0], producerWaitTimeRange[1]));
    }
};

// 消费者线程
fork {
    var task;
    loop {
        // 与生产者线程中一样，这会阻塞我们，直到
        // 队列中有内容，并且我们已经收到
        // 生产者的信号。
        empty.wait({ queue.notEmpty });

        task = queue.removeAt(0);
        postf("Consumer processed a task: %. Current queue size: %\n",
            task, queue.size);

        // 我们需要向生产者发出信号，以防它正在等待
        // 我们向队列插入某些内容。
        full.signalOne;

        wait(rrand(consumerWaitTimeRange[0], consumerWaitTimeRange[1]));
    }
};
)

生产者-消费者队列：多个生产者，多个消费者

这里是另一个生产者-消费者示例，包含多个生产者和多个消费者。注意上面的代码可以多么容易地被泛化。

(
var full = CondVar(), empty = CondVar();
var queue = Array();
var counter = 0; // 这次 task 计数器在所有 producers 之间共享

// 尝试对这些参数进行实验
var maxQueueSize = 10;
var numProducers = 3;
var numConsumers = 3;
var producerWaitTimeRange = [0.3, 1.5];
var consumerWaitTimeRange = [0.3, 1.5];

// 生产者线程
numProducers.do { |index|
    fork {
        var task;
        loop {
            full.wait({ queue.size < maxQueueSize });

            task = counter;
            counter = counter + 1;
            queue = queue.add(task);
            postf("Producer % created a task: %. Current queue size: %\n",
                index, task, queue.size);

            // 尽管可能有多个消费者等待
            // 在这个条件上，但其中只有一个能真正利用
            // 我们刚刚创建的新任务。所以我们使用
            // signalOne 而不是 signalAll。
            empty.signalOne;

            wait(rrand(producerWaitTimeRange[0], producerWaitTimeRange[1]));
        }
    }
};

// 消费者线程
numConsumers.do { |index|
    fork {
        var task;
        loop {
            empty.wait({ queue.notEmpty });

            task = queue.removeAt(0);
            postf("Consumer % processed a task: %. Current queue size: %\n",
                index, task, queue.size);

            full.signalOne;

            wait(rrand(consumerWaitTimeRange[0], consumerWaitTimeRange[1]));
        }
    }
}
)

使用超时

有时，你想等待一个可能永远不会成立的外部条件，或者想在等待了很长时间后做点别的事情。这时使用 waitFor 很合适。在我们的示例中，我们使用一个有时无法设置所需条件的例程来模拟这个“不可靠”的任务。一些实际例子可能是服务器上的长时间异步任务，或者对 unixCmd 的调用没有及时完成，或者没有产生我们想要的结果。

(
var condition = CondVar();

// 我们这个“不可靠”的任务有一半时间会通知我们它已完成，
// 但另一半时间它会通知失败。
fork {
    var coinFlip;
    1.wait;
    coinFlip = 0.5.coin;
    postf("Flip gave us: % ; %signalling the condition\n", coinFlip,
        if(coinFlip, "not ", ""));
    if(coinFlip) { condition.signalOne };
};

fork {
    // 在这种情况下，随机硬币投掷成功就是我们的整个
    // 条件，因此我们不向 waitFor 传递任何谓词。
    if(condition.waitFor(2)) {
        "Coin flip succeeded!".postln
    } {
        "Coin flip failed, and we timed out".postln
    };
};
)

我们也可以重写此示例，使得无论如何都会收到信号，但条件仍可能不会成立。

(
var condition = CondVar();
var coinFlip = false;

fork {
    // 现在抛硬币有多次成功的机会，但它仍
    // 可能不会在我们 2 秒的时间窗口内成功。
    5.do { |i|
        0.2.wait;
        coinFlip = 0.25.coin;
        "Flip number %: got %\n".postf(i + 1, coinFlip);
        condition.signalOne;
    }
};

fork {
    // 除非超时，或者我们被通知
    // *并且*谓词为真，否则我们不会退出 `waitFor`。
    if(condition.waitFor(2, { coinFlip })) {
        "Coin flip succeeded!".postln
    } {
        "Coin flip failed, and we timed out".postln
    };
};
)
