用户 FAQ

一些常见问题与常见错误

错误：原语 'BasicNew' 失败。索引不是整数

如果你正在编写 SynthDef

很可能这个错误意味着你试图在 SynthDef 内部动态改变通道数量，而这是做不到的——SynthDef 必须具有固定的布局。例如，下面是一个在可变数量的通道上生成粉红噪声的简单尝试：

(
SynthDef(\thiswillfail, { |out=0, numChannels=2|
    Out.ar(out, {PinkNoise.ar}.dup(numChannels))
}).add
)

它失败是因为我们试图让涉及的粉红噪声发生器的数量真正可变。这是做不到的——当 SynthDef 被编译时，语言需要确切知道将涉及多少个 UGen 以及它们如何连接。这是因为 SynthDef 表示一个高效的固定布局 synth，服务器可以实例化它。

那么该怎么做？

将 SynthDef 视为微小、固定的可复用组件，并设计你的逻辑以按需以任意组合复用它们。

要回到上面的简单示例（粉红噪声生成器），你可以直接这样做：

(
SynthDef(\simplepink, { |out=0|
    Out.ar(out, PinkNoise.ar)
}).add
)

并为每个声道创建一个 \simplepink synth。或者，你可以为你预期使用的每种声道数各创建一个 SynthDef。例如，如果你可能使用 1 到 5 个声道：

(
(1..5).do{ |n|
SynthDef("simplepink_%".format(n).asSymbol, { |out=0|
    Out.ar(out, {PinkNoise.ar}.dup(n))
}).add
}
)

然后你需要按需调用 \simplepink_4 或类似的东西。

语言（客户端）问题

从 SystemClock 例程中调用 GUI 原语

从 SystemClock 例程中调用 GUI 原语时会导致错误：

SystemClock.sched(0,{ Window.new.front })
ERROR: Qt: You can not use this Qt functionality in the current thread. Try scheduling on AppClock instead.
ERROR: Primitive '_QWindow_AvailableGeometry' failed.

为避免此问题，请使用 AppClock：

AppClock.sched(0,{ Window.new.front })

或 defer 方法：

SystemClock.sched(0,{ { Window.new.front }.defer })

二元运算顺序

由于 SuperCollider 求值表达式的方式，数学表达式的通常执行顺序并不被遵循。在 SuperCollider 中一切都是对象，求值从左到右进行，因此：

5 + 3 * 2

将求值为 (5 + 3 ) * 2。

出现这种情况是因为表达式变为：

5.performBinaryOpOnSimpleNumber('+',3).performBinaryOpOnSimpleNumber('*',2)

因此，在代数表达式中，当从左到右的顺序不是期望的顺序时，必须使用括号：

5 + (3 * 2)

SynthDef 问题

SynthDef 内部的 "If" 语句

用户迟早会尝试在 SynthDef 中写出类似这样的东西

SynthDef(\kablooie, { |x = 0|
    var signal;
    if(x > 0) {
        signal = SinOsc.ar
    } {
        signal = Saw.ar
    };
});

... 结果是令人不安的：ERROR: Non Boolean in test.

“测试中不是布尔值”？但 x > 0 是一个比较，理应产生一个布尔值，对吧？

这应当是首要线索：服务器中的布尔逻辑与客户端（语言中）所谓的条件判断的“常规”用法截然不同。

服务器中的布尔值是什么？

事实上，并不存在这样的东西。服务器处理的是浮点数。它没有真或假的实体。

由于服务器中的一切都是数字，比较的结果也必须是数字。服务器遵循与其他 DSP 环境（Max/MSP、pd 等）相同的约定：

- True 用 1.0 表示 - False 用 0.0 表示

为什么在“test”中 x > 0 是“非布尔值”？

这要回到处理服务器中运算符的一般性问题。SynthDef 中的数学运算符不是现在要执行的计算。它们描述的是将来要执行的计算，会执行成千上万次。

var x = 1;
x > 0;
// -> true
SynthDef(\kablooie, { |x = 0|
    "x: ".post; x.postln;
    "(x > 0): ".post; (x > 0).postln;
});
x: an OutputProxy
(x > 0): a BinaryOpUGen

在你执行 SynthDef 代码时，x 的精确值是未知的。x 实际上代表无限多个值，这些值将通过参数列表提供给 Synth。因此，一劳永逸地确定 x > 0 是否成立是没有意义的。x 现在可能 > 0，而瞬间之后可能 < 1。所以，x > 0 不会产生布尔值，而是产生一个二元操作符 UGen，它会反复执行该比较。

回到这里：

if (aBinaryOpUGen) { ... } { ... };

要做到这一点，语言必须知道要执行哪个函数（true 或 false）。但无法预知 BinaryOpUGen 会是哪一个。因此，SuperCollider 会抛出错误。

如果你不能分支，那么在服务器中进行比较又有什么用呢？

实际上，比较有很多用途。

- 从两个信号中选择一个：这是我们在服务器中最接近 if-then-else 的做法。then 和 else 都必须持续运行。这是服务器工作方式的要求：单个 Synth 内单元生成器的数量和排列不能改变。相反，你可以选择这些信号中哪一个向下游传递。一个会被使用，另一个被忽略。由于 true 为 1、false 为 0，你可以用条件来通过 Select 索引数组。

Select.kr(aKrSignal > anotherKrSignal, [false_signal, true_signal]);

- 生成触发器：每当信号 <= 0 然后变为 > 0 时，就会产生一个触发器。将其扩展到比较运算，意味着当比较在持续一段时间内为假、然后变为真时，就会产生一个触发器。因此，在触发器有效的任何地方，都可以将信号与阈值进行比较。举个简单的例子，考虑当麦克风输入的幅度超过阈值时向语言发送消息的情况。

var mic = In.ar(8, 1), amplitude = Amplitude.kr(mic);
SendTrig.kr(amplitude > 0.2, 0, amplitude);

- 传递或抑制触发：你可能需要持续生成触发，但只允许在满足某个条件时才让触发生效。乘法可以很好地处理这一点：condition * trigger。由于条件为 false 时求值为 0，触发会被替换为 0，什么也不会发生，正合预期。

对于一个简单的例子，让我们改进麦克风振幅示例，抑制在前一次触发后 1/4 秒内发生的触发。

var mic = In.ar(8, 1),
    amplitude = Amplitude.kr(mic),
    trig = amplitude > 0.2,
    timer = Timer.kr(trig), // 距离上次触发有多久了？
    filteredTrig = (timer > 0.25) * trig;

SendTrig.kr(filteredTrig, 0, amplitude);

逻辑运算符：And、Or、Not、Xor

逻辑运算符有简单的算术等价形式。

- And = 乘法：(x > 0) * (y > 0) 表示两个条件都必须为真（非零），结果才为非零。

- Or = 加法：(x > 0) + (y > 0) 表示任一条件非零就足以使结果非零。

注意： 如果两者都为真，则结果为 2，而不是 1。在某些情况下，2 可能不可接受。可以通过将 Or 包裹在另一个比较中来解决——((x > 0) + (y > 0)) > 0——因为 2 > 0 求值为 1！

- Not：我倾向于通过将条件与零比较来取反：condition <= 0。0 <= 0 为 1（即非 0），1 <= 0 为 0（非 1）。如果你确定逻辑表达式只会精确地取 0 或 1，也可以用减法取反：1 - condition。

- Xor：异或运算在其中一个条件为真、但不同时为真时为真。我们可以将两个条件相加并与 1 比较。语法有点棘手，因为 == 不会自动转换为 BinaryOpUGen。我们必须手动创建 BinaryOpUGen。

BinaryOpUGen('==', (x > 0) + (y > 0), 1)

错误：未找到 SynthDef

向服务器发送 SynthDef 需要一点时间，这意味着同时包含 SynthDef 定义和这些 SynthDef 实例的一段代码，如果不考虑这一点点延迟，就不能保证正常运行。有两种主要方法可以做到：

第一种方法：将 SynthDef 和主代码放入一个 Task 中，并在它们之间放置某种 .wait 时间。

Task({
    // 将你的 SynthDefs 放在这里
    0.2.wait;
    // 将你的其余代码放在这里
}).play;

第二种方式：使用 .sync：

Routine({
    // 将你的 SynthDefs 放在这里
    s.sync; // 假设 's' 是服务器
    // 将你的其余代码放在这里
}).play

FAILURE /s_new 分配失败，请增加服务器的内存分配

含义：在初始化新 Synth 节点中的单元生成器时，服务器耗尽了实时内存。

解决方案：增加服务器可用的实时内存量。正如错误消息所述，该大小在与服务器关联的 ServerOptions 对象中设置。它是一个服务器启动选项；你必须退出服务器并重新启动它，否则新设置不会生效。

myServer.quit;
myServer.options.memSize = 65536;  // 例如，对你来说可能不同
myServer.boot;

myServer.options.memSize 以 KB 为单位。默认值为 8192KB，即 8MB。

它的真正含义：许多单元生成器需要内部内存缓冲区，例如延迟线、梳状滤波器、全通延迟、某些 FFT 操作器、混响单元等。这些内部缓冲区并非直接从操作系统分配，而是从一个“实时内存池”中分配。这是因为通过 malloc() 等函数直接从操作系统分配并不是实时安全的。操作系统可能返回新内存块耗时过长，从而导致音频出现故障。为解决此问题，服务器在启动时分配一大块内存，并按需将其分发给各单元生成器。

如果你使用大量延迟，服务器可能会耗尽实时内存。默认的 8192KB 设置在 44.1 kHz 采样率下可以支持 47.55 秒的延迟。当使用大量带有多个延迟通道的 synth 时，这些内存会很快耗尽。

替代方案：对于延迟单元，你可以使用预分配的延迟缓冲区——Buffer.alloc()——以及“Buf”延迟单元：BufDelayN、BufDelayL、BufDelayC、BufCombL 等。Buffer.alloc() 不使用实时池，也不受 memSize 限制。这种方法对 FFT 单元没有帮助。

数组参数

有时，你需要向 SynthDef 中的一系列 Control 输入发送一个数组（通常称为“_数组参数_”）。

Synth(\xyz, [freqs: [300, 400, 500]]);

有两种主要方式可以做到这一点：

- 在函数中为该参数名提供一个字面量数组作为默认值——\#[1, 2, 3]。这一点在 SynthDef 的帮助文件中有讨论。

SynthDef(\xyz, { |freqs = #[1, 2, 3]|
    // ...
})

- 或者使用 NamedControl。如果你想动态构造数组的大小，或基于变量来构造，这是唯一的方法。参见 NamedControl。

SynthDef(\xyz, {
    var freqs = NamedControl.kr(\freqs, #[1, 2, 3]);
    // ...
});

为什么它必须是字面量数组？

原因来自构建 SynthDef 的过程：

1. 首先，查看函数参数以确定 Control 输入应该是什么。2. 然后创建 Control 单元（通常只需一个，如果它们都是没有前缀或特殊速率的普通参数）。每个通道由一个 OutputProxy 表示。3. 然后运行 SynthDef 函数，将输出代理传递给参数。4. 然后将 UGen 按正确顺序排序，等等等等。

要完成步骤 \#1 和 \#2，SynthDef 构建器必须在运行函数之前知道数组参数的大小。只有当它是字面量数组时才有可能：\#[1, 2, 3, 4, 5]。任何其他数组表示法都会在运行函数时创建数组（步骤 \#3）。但那时已经太晚了——SynthDef 构建器已经为它创建了非数组的控制通道！

SynthDef(\notArray, { |a = (1..5)|
    a.debug("a is");
});

a is: an OutputProxy

SynthDef(\array, { |a = #[1, 2, 3, 4, 5]|
   a.debug("a is");
});

a is: [ an OutputProxy, an OutputProxy, an OutputProxy, an OutputProxy, an OutputProxy ]

（注意，如果 'a' 打印为 [ 1, 2, 3, 4, 5 ]，那么你就无法使用 .set 改变 Synth 中的值！）

服务器问题

如何从服务器触发函数

第一点也是最重要的一点：函数仅存在于客户端。服务器不知道函数是什么、不理解它们，也无法执行它们。只有客户端才能执行函数。

因此，如果你希望当服务器中发生某事时执行一个函数，唯一的方法就是让服务器通知客户端采取行动。

服务器可以使用两种单元生成器之一将消息回传给客户端：SendTrig 和 SendReply。SendTrig 更简单但灵活性较差（它只能发送 /tr 消息，且只能携带一个数据值）。SendReply 允许你随意命名消息，并可以随消息发送数组。此处我们将使用 SendReply，因为它更灵活。

在语言内部，你还需要一个对象来接收消息并对其做出反应。通常是 OSCFunc 或 OSCdef。在此示例中，OSCdef 不仅根据名称 /bleep 过滤消息，还根据 synth 的 ID 过滤。这样，你可以拥有多个触发 synth，每个 synth 有不同的响应器和不同的动作。

(
a = {
    var trig = Dust.kr(8),
    decay = Decay2.kr(trig, 0.01, 0.1),
    sig = SinOsc.ar(TExpRand.kr(200, 600, trig), 0, 0.1) * decay;
    SendReply.kr(trig, '/bleep', trig);
    sig ! 2
}.play;

o = OSCdef(\bleepResponder, { |msg|
    msg.postln;
}, '/bleep', s.addr, argTemplate: [a.nodeID]);
)

a.free; o.remove;

帮助文件引用：

- SendTrig、SendReply

- OSCresponderNode、OSCpathResponder、OSCresponder、OSC Communication

错误：无法打开 UDP 套接字：地址已被占用

有时在启动服务器时会收到消息：Error: failed to open UDP socket: addess in use。

这通常是由一个已挂起但尚未释放 osc 端口的 scsynth 实例导致的，可能是 SuperCollider 崩溃所致。你可以使用 SuperCollider（sclang）运行 Server.killAll 来终止所有正在运行的服务器。你也可以使用终端或操作系统的任务管理器终止 scsynth。

其他问题

加载共享库时出错：libsclang.so：无法打开共享对象文件

这种情况通常发生在 Linux 上构建之后，它意味着你的系统尚未感知到新安装的共享库。以 root 身份运行 ldconfig 即可解决该问题：

/sbin/ldconfig
