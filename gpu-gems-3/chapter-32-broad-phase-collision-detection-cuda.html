第 32 章　基于 CUDA 的粗筛阶段碰撞检测

Scott Le Grand
NVIDIA Corporation

在众多三维物体之间做碰撞检测，是物理仿真、计算机辅助设计、分子建模等应用的重要组成部分。大多数高效实现采用两阶段做法：先粗筛阶段，再精筛阶段。粗筛阶段的碰撞测试是保守的——通常只基于包围体——但速度快，以尽快剔除互不相碰的物体对。粗筛阶段的输出是可能相碰的物体对集合。精筛阶段的碰撞测试是精确的——通常计算精确的接触点与法线——因此代价高得多，但只对可能相碰集合中的物体对执行。当大量物体实际上并不相碰时——实践中的情况正是如此——这种做法非常合适，许多物体对在粗筛阶段就被排除掉了。

本章介绍一种基于 CUDA 的粗筛阶段碰撞检测（简称「粗筛」）的 GPU 实现，它比 CPU 实现快一个数量级。

32.1 粗筛算法

n 个物体的粗筛暴力实现要做 n(n-1)/2 次碰撞测试，因此复杂度为 O(n 2)。其他算法，如排序并扫描（见 32.1.1 节）或空间细分（见 32.1.2 节），平均复杂度可达 O(n log n)（最坏情况仍是 O(n 2)）。32.1.3 节概述空间细分的并行实现带来的麻烦以及我们的应对方式。我们的并行空间细分 CUDA 实现见 32.2 节。

32.1.1 排序并扫描

如前所述，粗筛的一种做法是排序并扫描算法（Witkin 和 Baraff 1997）。在这种做法中，每个物体 i 的包围体被投影到 x、y 或 z 轴上，从而确定该物体沿此轴的一维碰撞区间 [bi , ei ]；bi 标记碰撞区间的起点，ei 标记终点。碰撞区间不重叠的两个物体不可能相碰，由此得到下面的算法。把每个物体的两个标记插入一个含 2n 个条目的列表（每个物体两个标记），然后把列表按升序排序，最后从头到尾遍历。每当在列表中遇到 bi 标记，就把物体 i 加入活跃物体列表；每当遇到 ei 标记，就把物体 i 从活跃物体列表中移除。对物体 i 的碰撞测试，只在物体 i 自身被加入活跃物体列表的那一刻，针对 i 与当时活跃列表中的所有物体进行。三个物体的例子见图 32-1。

排序并扫描实现简单，是粗筛碰撞检测算法的良好起点。此外，由于相邻两帧仿真之间存在空间连贯性，列表大多已接近有序，此时插入排序这类 O(n 2) 排序的性能会改善到 O(n)，因此常能高效地用来加速算法。

32.1.2 空间细分

空间细分是排序并扫描之外的另一条路。空间细分把空间划分为均匀网格，使一个网格单元至少与最大的物体一样大。每个单元保存质心落在该单元内的物体列表，只有属于同一单元或两个相邻单元的物体之间才做碰撞测试。另一种做法——也是本章后续采用的做法——是给每个单元保存包围体与该单元相交的所有物体的列表。此时一个物体最多可出现在 2 d 个单元中，其中 d 是空间细分的维数（例如三维世界中 d = 3），见图 32-2。

只有当两个物体出现在同一单元中、且其中至少一个的质心在该单元内时，才对它们做碰撞测试。例如在图 32-3 中，物体 o 1 与 o 2 之间要做测试，因为两者质心都在单元 1 内；物体 o 2 与 o 3 之间也要做，因为两者都出现在单元 5 中且 o 3 的质心在单元 5 内。但 o 2 与 o 4 之间不做测试，因为虽然两者都出现在单元 2 中，双方的质心都不在单元 2 内。

空间细分最简单的实现，是把物体 ID 列表连同其所在单元 ID 的哈希一起保存，按单元 ID 排序，然后遍历单元 ID 相同的连续段，对共享同一单元 ID 的所有物体做碰撞测试。

单元必须至少与最大物体的包围体一样大，这在各物体尺寸差异悬殊时会造成不必要的计算。一个例子是被成千上万颗小得多的陨石环绕的巨大行星。层次网格（Mirtich 1996）可以解决这个问题，但已超出本章范围。

32.1.3 并行空间细分

并行化空间细分会使算法稍复杂一些。第一个麻烦来自这一点：如果单个物体与多个单元重叠、而这些单元又被并行处理，它就可能同时参与不止一次碰撞测试。因此必须有某种机制，防止两个或更多计算线程同时更新同一物体的状态。为处理这个问题，我们利用单元的空间间隔。由于每个单元保证至少与计算中最大物体的包围体一样大，那么只要在一次计算过程中处理的每个单元与同时处理的其他单元之间至少隔着一个单元，就能保证每个物体所在的单元在同一时刻只有一个在被更新。在二维中，这意味着需要四趟计算才能覆盖所有可能的单元，见图 32-4：所有带相同数字标签（1 到 4）的单元，即同一单元类型，可以在同一趟中处理。该图展示了一个简单情形：物体 2 有两处潜在碰撞，必须分别处理。三维中需要八趟，因为二维的重复单元从编号 1 到 4 的 2x2 单元方块，变成编号 1 到 8 的 2x2x2 单元立方体，见图 32-5。

有两种特殊情况会改变对单元遍历顺序的要求。第一，如果我们不改变物体状态、只做碰撞测试，这 2 d 趟可以合并成一趟。第二，如果我们用这套碰撞系统做 Jacobi 与 Gauss-Seidel 物理积分（Erleben 等 2005），也可以一趟处理所有单元。不过那种情况下有个前提：每个物体有 2 d 个速度冲量输出（对应它可能占据的 2 d 个碰撞单元），碰撞处理完成后要为每个物体把这些输出相加。

并行执行带来的另一个麻烦，是必须避免在两个物体之间重复执行同一次碰撞测试。当两个物体占据的单元集合有重叠、而它们的质心又不在同一单元时，就会出现这种情况。

我们按下面的办法处理这种可能：

  1. 给每个物体关联 d + 2 d 个控制位；其中 d 位保存其质心所在单元的类型，即归属单元；2 d 位指明其包围体所交叠单元的类型。
  2. 把每个物体的包围球按 sqrt(2) 缩放，并确保网格单元至少是最大物体缩放后包围球的 1.5 倍大。

在第 T 趟中对两个物体做碰撞测试之前，我们先判断其中一个物体的归属单元类型（设其为 T'）是否既小于 T、又属于两物体共有的单元类型（把双方各 2 d 个控制位做 AND 得到）。若是，就跳过测试：或者两物体共享类型为 T' 的单元，那么测试已在第 T' 趟做过；或者它们不共享类型为 T' 的单元，那么由刚才第 2 点可知它们的包围体不可能重叠。前一种情况由物体 o 1 与 o 2 展示，见图 32-6。第 T = 3 趟跳过测试，因为两物体共享单元类型 1 和 3，而 o 2 的归属单元类型是 T'= 1；跳过是安全的，因为测试已在第 1 趟做过。后一种情况由物体 o 3 与 o 4 展示，见图 32-6。第 T = 4 趟跳过测试，因为两物体共享单元类型 3 和 4，而 o 4 的归属单元类型是 T'= 3；跳过确实安全，因为两物体不可能相碰：它们重叠的是不同的类型 3 单元，质心间距大于最大物体的直径。

32.2 空间细分的 CUDA 实现

本节给出我们用 CUDA 实现的细节。32.2.1 节说明如何把物体 ID 与单元 ID 列表存放在设备内存中；32.2.2 节说明如何由物体的包围盒构建单元 ID 列表；32.2.3 节深入描述我们用来排序该列表的算法；32.2.4 节说明如何构建索引表，以便按 32.2.5 节所述遍历这个已排序列表，并为精筛阶段安排更严格的碰撞检测物体对。本节中说明整个过程的所有图都对应图 32-7 与 32-8 中的例子。

32.2.1 初始化

每个物体的属性是：ID（用于在底层碰撞测试与下文所述单元 ID 数组构建过程中访问包围体等附加属性）、控制位（用于存放各种位状态，如前面 32.1.2 节末尾提到的归属单元类型与其他被占据的单元类型），以及其包围体所覆盖的最多 2 d 个单元 ID。最自然的存放方式是结构体数组。不过为降低排序这个数组时的带宽需求，最好把这些属性分成两个独立的数组，各含 (n x 2 d ) 个元素：

  • 第一个数组是单元 ID 数组，先放第一个物体的单元 ID，接着放第二个物体的，依此类推。
  • 第二个数组是物体 ID 数组，存放每个物体的 ID 与控制位，物体占据几个单元就重复几次。

在算法描述的其余部分中隐含这样一个前提：每当单元 ID 数组的元素被重排，物体 ID 数组的元素也按同样方式重排。

32.2.2 构建单元 ID 数组

分配好足够的存储之后，碰撞检测的第一步是填充单元 ID 数组。对给定物体，有些单元与其包围体重叠但不是它的归属单元，即 H 单元。我们把这类重叠单元叫做该物体的幽灵单元，即 P 单元。如前所述，如果一个单元对一个物体是 P 单元、对另一个物体也是 P 单元，那么这两个物体在这个单元里绝不可能相碰，因为两者的质心至少隔着一个单元；按设计，单元直径至少是最大物体半径的两倍。

每个物体的 H 单元 ID 就是其质心坐标的哈希。典型的三维哈希大致如下：


GLuint hash = ((GLuint)(pos.x / CELLSIZE) << XSHIFT) |
              ((GLuint)(pos.y / CELLSIZE) << YSHIFT) |
              ((GLuint)(pos.z / CELLSIZE) << ZSHIFT);

其中 pos 表示物体的位置；CELLSIZE 是单元的尺寸；XSHIFT、YSHIFT 和 ZSHIFT 是预定义常量，决定每个维度坐标的哈希各分到多少位。这个哈希作为每个物体的第一个单元 ID 存入单元 ID 数组；同时，物体 ID 数组中对应元素被更新为物体 ID，并置一个控制位，表示这是该物体的 H 单元。

接着，测试每个物体的包围体是否与其 H 单元的 3 d - 1 个直接邻居重叠，把得到的 P 单元 ID 存入单元 ID 数组。既然单元尺寸至少与最大包围体一样大，一个物体一次只能触及 2d 个单元，也就是说一个物体有一个 H 单元、最多可有 2d - 1 个 P 单元。如果物体的 P 单元少于 2 d - 1 个，多余的单元 ID 标为 0xffffffff，表示无效。

这些 H 与 P 单元 ID 的生成对每个物体由一个线程完成。为应对物体数多于线程数的情况，每个线程处理多个物体。更准确地说，线程块 i 中的线程 j 处理物体 iB + j、iB + j + nT、iB + j + 2nT，依此类推，其中 B 是每块线程数，T 是线程总数。

图 32-9 展示了单元 ID 数组构建的结果。

所有单元 ID 创建完毕后，需要对它们计数，算出总数，供 32.2.4 节创建碰撞单元列表时使用。在并行机器上把多个值相加，最高效的办法是并行归约。在 CUDA 中，线程块内的线程可以通过共享内存协作，得到非常快的并行归约实现。（细节见本书第 39 章「基于 CUDA 的并行前缀和（扫描）」。）因此我们先算出每个线程块创建的单元 ID 数，把每个块的计数写入全局内存；等所有块完成后，再启动一个块把前面各块的结果相加。

32.2.3 排序单元 ID 数组

接下来按单元 ID 排序单元 ID 数组。当然，一般来说每个单元 ID 会在数组中出现多次——每有一个以上的包围体与该单元相交就出现一次。我们希望单元 ID 相同的元素按单元 ID 类型排序（H 在 P 之前），因为这样能简化 32.2.5 节的碰撞单元处理：那里要遍历所有 H 单元 ID，去对照全部 H 与 P 单元 ID 的总数。由于我们已经先按物体 ID、再按单元 ID 类型（H 或 P）排好了单元 ID 数组，排序算法的选择就限于稳定排序。稳定排序保证排序结束时，相同的单元 ID 仍保持排序开始时的相对次序。图 32-10 展示了把排序过程应用到图 32-9 的单元 ID 数组的情形。

我们先概述基数排序算法，再详细描述我们的并行实现。

基数排序算法

基数排序把 B 位的键——在我们的情形是 32 位单元 ID——按其中每 L 位一组来处理（L < B—），有几组就跑几趟。例如，对 32 位键常见的基数排序会把 L 设为 8，因为此时 B/L 等于 4，于是得到四趟基数排序（Sedgewick 1992）。

基数排序最令人意外的特点是它先排低位再排高位。前面提到的稳定性保证了这种看似反常的排序方向可行：已经按最低 8 位排好序的键，在后续趟次按更高位再排序时不会丢失这个次序。

基数排序的每一趟都把每个键中当前 L 位之外的所有位屏蔽掉，然后统计屏蔽后 2 L 个可能取值各自出现的次数。得到的基数计数器数组随后被处理，把每个值转换成相对数组起始的偏移量。换句话说，表中每个值都被替换为它前面所有值之和；这个操作叫做前缀和。最后，用这些偏移量确定本趟各键的新位置，并按此重排键数组。

并行基数排序算法

每一趟以一个单元 ID 数组为输入，把重排后的元素输出到另一个单元 ID 数组。第一趟的输入是 32.2.2 节构建的单元 ID 数组；除最后一趟外，每趟之后输入与输出数组都互换。最终的输出数组作为下一步（见 32.2.4 节）的输入。

一趟由三个阶段实现，每个阶段对应一次内核调用。下面三小节分别描述这些阶段。

阶段 1：设置与制表

串行基数排序一趟的第一个阶段，是统计键列表中每个基数值出现的次数。这意味着算法至少需要 Num_Radices = 2 L 个 32 位基数计数器。这个阶段通过在 Num_Blocks 个 CUDA 线程块之间分摊工作来并行化，给每个 CUDA 线程分配输入单元 ID 数组的一部分，由每个线程负责统计其所在部分内各基数值的出现次数。

每个线程都需要自己的一套计数器，否则线程可能互相破坏对方的计数。因此在整个过程里，并行基数排序需要

Num_Blocks x Num_Threads_Per_Block x Num_Radices

个计数器，其中 Num_Threads_Per_Block 是每块线程数。

这些计数器显然该放在每个多处理器的共享内存里。GeForce 8800 GTX 上每个多处理器有 16 K 共享内存，其中一小部分用于块的簿记，因此每个多处理器剩下略少于 4,096 个 32 位计数器的空间。这对 L 和 Num_Threads_Per_Block 都构成约束。此外，希望 Num_Threads_Per_Block 是 64 的倍数。若用 256 个线程，把略少于 4,096 个 32 位计数器除以每块 256 个线程，可算出每个线程只有 16 个计数器的空间，这会把 L 限制为 4，总共要八趟。

为了减少趟数，只能让线程之间共享计数器。为此我们把每个线程块分成若干含 R 个线程的组（于是每块有 Num_Groups_Per_Block = Num_Threads_Per_Block/R 个线程组），同组内的线程共享同一套 Num_Radices 个计数器。在我们的情形里，R 取 16 最合适，这样就能选 L 等于 8，用每块 192 个线程、每块共 12 个线程组做 8 位基数排序。如此把趟数减到四趟，排序算法的性能几乎翻倍。确实，共享计数器带来的额外计算只出现在受内存限制的内核里，因此性能代价很小。

为避免同一线程组内线程之间的读后写或写后读冲突，我们必须为每个线程组构造基数计数器的串行化自增。这个过程见图 32-11。每组线程依次通过这段代码，各自唯一地递增各计数器，不会被其他线程覆盖。

阶段 2：基数求和

阶段 3 中，各块将按与阶段 1 相同的方式读取输入单元 ID 数组，并把各自的单元 ID 输出到输出单元 ID 数组中的正确位置。这些位置由输出单元 ID 数组中的偏移量决定，而计算这些偏移量需要以下内容：

工作的划分方式是让每个块负责 Num_Radices_Per_Block = Num_Radices/Num_Blocks 个基数——在我们的情形是 16 个基数，见图 32-16。

每个基数的基数计数器个数等于线程组数，也就是说每个基数有 Num_Groups = Num_Blocks x Num_Groups_Per_Block 个基数计数器。因此每个块在共享内存中分配 Num_Groups 个 32 位值，然后遍历分配给它的 Num_Radices_Per_Block 个基数，对每一个执行下面的操作：

  1. 把该基数的 Num_Groups 个计数器从全局内存读入共享内存。
  2. 计算这 Num_Groups 个计数器的前缀和。
  3. 用前缀和的结果覆写全局内存中的这 Num_Groups 个计数器。
  4. 这 Num_Groups 个计数器的总和，用最后一个计数器在前缀和之前的值与其在前缀和之后的值相加即可得到。

第 1 步中的读取经过组织，使 ID 连续的线程读取内存中连续的计数器，以获得适当的内存合并。

第 2 步采用 CUDA 中工作高效的前缀和并行实现，例如第 39 章详述的那一种。如该章所述，为尽量限制 bank 冲突，存放 Num_Groups 个计数器的共享内存数组需要适当填充（因此必须分配更多内存）。

每个块还在共享内存中分配一个含 Num_Radices_Per_Block 个 32 位值的数组，存放第 4 步算出的 Num_Radices_Per_Block 个总和的前缀和。这个前缀和的计算很简单：把第 N 次迭代末尾算出的总和加到数组的第 N - 1 个元素上。

于是本阶段结束时，每个线程块已对其负责的 Num_Radices_Per_Block 个计数器算好前缀和，见图 32-17；但要得到输出单元 ID 数组中的绝对偏移量，还需把之前所有线程块的总和加到该前缀和的每个元素上。由于这需要线程块之间的同步，只能把本阶段各块算出的前缀和存入全局内存，再调用另一个内核；因此这件事留到下一阶段。

阶段 3：重排

每一趟的最后阶段，根据阶段 1 与阶段 2 所做的基数制表重排输入单元 ID 数组。

如阶段 2 末尾所述，每个块必须先完成（阶段 2 中部分完成的）计算 Num_Radices 个基数计数器前缀和的工作，以得到输出单元 ID 数组中的绝对偏移量。为此，它从全局内存把阶段 2 中各块算出的 Num_Blocks 个前缀和（每个由 Num_Radices_Per_Block 个值组成）读入共享内存，对这些前缀和的最后一个值做并行前缀和，再用它适当地偏移每个前缀和的各个值。这里做的并行前缀和由每个块重复执行，只用 Num_Blocks 个线程，效率不高，但因为运算很少，速度很快。

接着，每个块把自己的 Num_Groups_Per_Block x Num_Radices 个基数计数器从全局内存读入共享内存（即 Num_Blocks 列之一，见图 32-17），并用先前算出的相应绝对偏移量逐一偏移。

最后，每个线程块按与阶段 1 相同的顺序，从全局内存读取它在阶段 1 读过的同一段输入单元 ID 数组，并对每个单元 ID 执行以下操作：

  1. 读取与该单元 ID 所属线程组和基数对应的基数计数器的值
  2. 把该单元 ID 写入输出单元 ID 数组中该基数计数器所指的偏移处
  3. 递增该基数计数器

第 2 步的写入与第 3 步的递增，必须按半 warp 内的每个线程串行化，见图 32-18；这既是避免同一半 warp 内线程之间出现共享内存与全局内存冒险所必需，也是保持基数相同的单元 ID 次序所必需。

第 2 步产生的全局内存写入极度分散、无法合并，造成大约 50% 的性能损失，但整个算法趟数少，完全足以弥补。

32.2.4 创建碰撞单元列表

碰撞单元是在精筛阶段需要处理的单元，换句话说，是含有不止一个物体的单元。所有碰撞单元的列表按下述方式由已排序的单元 ID 数组生成。扫描已排序的单元 ID 数组，寻找单元 ID 的变化处；每次变化标记着一个单元占据者列表的结束与另一个的开始。为把这个任务并行化，我们给每个线程块的每个线程分配单元 ID 数组中大致相等的一段，去扫描变化。由于我们希望同一段相同单元 ID 的起点和终点都由同一线程找到，每个线程会越过自己那段的终点继续扫到一个变化为止，并跳过自己的第一个变化，假定它会被前一个线程找到并记录。唯一的例外是第一个线程块的第一个线程，它处理单元 ID 数组的开头，因此不跳过第一个变化。此外，由于我们在 32.2.2 节算过有效单元数，从这里开始可以忽略所有无效的单元 ID。

已排序的单元 ID 数组实际上要扫描两遍。第一遍统计每个碰撞单元含有多少个物体，并通过分若干趟的并行前缀和把它们转换成数组中的偏移量，很像我们在基数排序阶段 2 里做的。第二遍在新数组中为每个碰撞单元建立条目，记录其起始位置、H 占据者个数和 P 占据者个数，见图 32-19。如 32.1.3 节所述，这些单元还可以选择性地分成 2 d 个互不作用的单元列表，碰撞处理随之进行 2 d 趟，每趟专注于其中一个列表。

32.2.5 遍历碰撞单元列表

接下来遍历每个碰撞单元列表，把碰撞单元按线程逐个分配处理，见图 32-20。在分子动力学或粒子仿真这类应用中，潜在碰撞可以立即处理，于是遍历本身即可充当精筛阶段的碰撞检测。对更高层的仿真，遍历只记录所有通过包围体重叠检查的碰撞，留待后续精筛阶段做更细致的处理；这类仿真已超出本章范围。

由于每个碰撞单元只有一个线程，只有存在成千上万个碰撞单元待处理时才能充分利用 GPU。这个问题在 Gauss-Seidel 物理处理时更明显，此时碰撞单元要分八趟处理。

32.3 性能结果

我们用 Gauss-Seidel 物理在 3,072 到 30,720 个分散但可能相碰的物体这样典型配置下测试了算法。对后者，粗筛阶段把 450,000,000 个潜在碰撞平均剪到约 203,000 个，我们在 GeForce 8800 GTX 上得到约 79 帧/秒的帧率。这比同期编写、作为相对性能基准的 CPU 实现快约 26 倍。如图 32-21 所示，物体数减少时帧率大幅提升，在 3,072 个物体时达到 487 帧/秒的峰值。

图 32-22 展示了算法各阶段所耗的总时间。很明显，单元 ID 数组排序与碰撞单元遍历最耗时，因此它们显然是日后优化的目标。

32.4 结论

本章表明，CUDA 是高速碰撞检测的优秀平台。后续工作将集中于在多个线程之间共享碰撞单元处理，以及探索空间细分的其他做法。
