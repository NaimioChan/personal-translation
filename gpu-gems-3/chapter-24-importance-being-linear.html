24.1 引言

现代 GPU 的性能与可编程性使高度逼真的光照与着色能实时实现。不过，几乎每一台采集或显示数字图像的设备都有一种微妙的非线性特性，这就要求仔细处理纹理与帧缓冲，以确保所有这些光照与着色被正确计算和显示。恰当的伽马校正大概是实时应用中改善图像质量最简单、最廉价、适用范围最广的技术。

24.2 光、显示与色彩空间

24.2.1 数字图像采集、创建与显示中的问题

如果你关心高质量渲染，你也许想知道显示在 CRT、LCD、胶片或纸上的图像所产生的光图案，是否与「真实世界」的情形足够接近，让你的眼睛觉得真实。你可能会惊讶地发现，数字图像创建的管线中有好几个环节都可能出问题。具体来说：

  • 光的采集（由相机、扫描仪等完成）所产生的数字图像，其数值是否准确表示当时光强的相对水平？如果打到传感器上的光子数翻倍，它的数值会翻倍吗？
  • 合成图像的生成者，例如渲染器，所创建的数字图像，其像素值是否与它模拟的情形中光的真实行为成正比？
  • 显示设备是否准确地把数字图像变回光？如果一个像素的数值翻倍，CRT、LCD 或其他类似设备显示的图像看起来会亮一倍吗？

出乎意料的是，这些问题的答案大概都是否。具体来说，采集（扫描、绘制与数字摄影）与显示（CRT、LCD 或其他）很可能都不是线性过程，如果在这两个环节上不留心，就会导致错误、不真实的图像。

这种非线性足够微妙，常被有意或无意地忽略，在实时图形中尤其如此。但它对渲染的影响，特别是在像 图 24-1 这类动态范围充裕的场景中，相当明显，而修正它所需的简单步骤非常值得一做。

24.2.2 题外话：什么是线性？

在数学意义上，线性变换是指输入与输出之间的关系满足：

  • 输入之和的输出等于各输入各自输出之和。即 f (x + y) = f (x) + f (y)。
  • 输入按某一因子缩放时，输出按同一因子缩放（对标量 k）：f(k x x) = k x f (x)。

光传输是线性的。场景中两个光源的照明贡献会相加。它们不会以难以察觉的方式相乘、相减或相互干涉。[1]

24.2.3 显示器是非线性的，渲染器是线性的

CRT 在把电压转换为光强时并非线性行为。而 LCD 虽然本身没有这一特性，通常也被构造成模仿 CRT 的响应。

显示器的响应更接近指数曲线，如 图 24-2 所示，这个指数称为 伽马。典型的伽马 2.2 意味着，强度 50% 的像素发出的光不到强度 100% 的像素的四分之一——而不是你预期的二分之一！每台显示设备的伽马都不同，[2] 但通常在 2.0 到 2.4 之间。针对这一非线性特性的影响所做的调整称为伽马校正。

注意无论施加什么指数，黑（零）与白（一）的值始终不变。被修正或扭曲的是中间色调的值。

渲染器、着色器与合成器都喜欢在线性数据上工作。它们把多个光源的贡献相加，并把光值乘以反射率（例如一个常量值，或从表示漫反射率的纹理中查出）。

但其中藏着一些未明说的假设——例如，表示反射率在表面上如何变化的纹理图，其刻度也是线性的。又例如，显示时观众看到的光强确实与渲染器存进帧缓冲的值成正比。

关键在于，如果你的输入是非线性的，那么渲染器、着色器或合成器就会「算错」。这妨碍你得到真实的结果。

以一幅数字绘画为例。如果你在创作时没有按「恰当的伽马校正」来观看，这幅画里就含有「隐藏的」非线性。这幅画在你的显示器上也许看着没问题，但在别的显示器上可能看起来不同，用于三维渲染时也可能与你的预期不符。如果渲染器假定图像是线性的，它实际上不会正确使用这些数值。同样，如果你把渲染器隐含为线性的输出不做伽马校正就显示，结果看起来会太暗——但不是均匀地偏暗，所以仅仅把它调亮并不够。

如果你在成像管线的两端都出错——在伽马（非线性）空间中绘制或采集图像，在线性空间中渲染，然后显示渲染图像时又不做校正——结果乍看也许还行。为什么？因为非线性的绘制/采集与非线性的显示可能在一定程度上相互抵消。但整个渲染与显示过程中会散布着细微的瑕疵，包括非线性输入被光照调亮或调暗时颜色发生变化，alpha 通道值不对（合成瑕疵），以及 mipmap 生成错误（纹理瑕疵）。此外，任何追求真实感光照的尝试——例如高动态范围（HDR）与基于图像的光照——实际上都没有做出你预期的效果。

而且，你的结果在每个显示它的人眼里都可能不同，因为画作与输出在某种意义上都内建了对某台特定显示器的参照——而创作画作与做三维光照所用的未必是同一台显示器！

24.3 症状

如果你忽视这个问题——在显示器空间里绘制或打光，也在显示器空间里显示——可能会遇到以下症状。

24.3.1 非线性的输入纹理

普通用户没有经过校准的显示器，也从没听说过伽马校正；因此许多视觉素材都替他们预先校正过了。例如按惯例，所有 JPEG 文件都按伽马 2.2 预先校正。这对任何显示器都不精确，但大致在那个范围内，所以图像在大多数显示器上大概都能接受。这意味着 JPEG 图像（包括扫描件和数码相机拍的照片）不是线性的，因此不应被假定线性输入的着色器用作纹理贴图。

这种预先校正的格式便于在普通 LCD 或 CRT 显示器上直接显示图像。对 8 位图像的存储来说，它还能在暗部提供更多「颜色分辨率」，而眼睛对暗部小幅度强度变化更敏感。不过，这种格式要求这些图像在用于任何渲染或合成操作之前先经过处理。

24.3.2 mipmap

创建 mipmap 时，逐级缩小最直白的做法是让每个更低层的纹素等于更高分辨率上「上面」四个纹素之和的四分之一。假设在高分辨率层上有一条边：两个像素为 1.0，两个为 0.0。低分辨率像素应当是 0.5，对吧？亮度减半，因为它一半全亮、一半全暗。你生成 mipmap 时肯定就是这么算的。啊哈，可那是线性运算。如果你处在伽马比如为 2.0 的非线性色彩空间中，那么粗层那个值为 0.5 的纹素显示出来只有 25% 的亮度。于是在低分辨率的 mipmap 层上，你会看到并不微妙的误差：那里的强度根本不是高分辨率层正确滤波的结果。渲染物体的亮度会沿轮廓边缘变化，也会随与三维相机的距离变化。

此外，即便你在创建 mipmap 时已设法校正非线性，在 GPU（甚至 CPU 渲染器）上对非线性纹理做纹理滤波仍有一个微妙的问题。GPU 用纹理查找的滤波范围来选择纹理细节层次（LOD），也就是「mipmap 层」，必要时会在相邻两层 mipmap 之间混合。我们希望到这里你已经抓住了我们论证的要点，明白如果渲染时的混合本身也假定线性运算——而两个纹理输入又是非线性的——结果就得不到正确的颜色强度。这种情况会导致纹理在 mipmap 层之间过渡时强度微微脉动。

24.3.3 光照

考虑一个简单兰伯特球体的照明，如 图 24-3 所示。[3] 如果反射光与 N · L 成正比，那么球面上 A 点（此处 N 与 L 成 60 度角）应向相机反射一半的光。于是它看起来应只有球面上 B 点亮度的一半，那里 N 正对光源。如果这些图像值被线性地转换为光，观看这张图像时它应当看起来像具有那些反射特性的真实物体。但如果你在伽马为 2.0 的显示器上显示这张图，A 实际上只有 0.5 gamma 的亮度，也就是 B 的四分之一。

换句话说，如果你渲染时假定光的属性是线性的，却显示在非线性显示器上，那么计算机生成（CG）的材质与灯光就根本不会与真实材质和灯光的外观相符。总体上场景会比准确模拟的结果更暗。然而，仅仅用一个常量因子把它调亮并不够：亮部会比中间亮度更准确。阴影过渡带与强度变化会比真实世界更锐利——例如从亮到暗的过渡会更快。角落会显得太暗。而且你用的光照技术越「先进」（例如 HDR、任何形式的全局光照、次表面散射），为保证与你那套复杂光照的线性计算相匹配，坚守线性色彩空间就越关键。

24.3.4 两个错误不等于一个正确

渲染中最常见的伽马错误，是用非线性颜色纹理做着色，然后又不给最终图像施加伽马校正。这种双重错误比只犯其中之一的错误要明显得多，因为两者所需的校正大致相反。不过这种情形会带来许多本可轻易避免的问题。

图 24-4 展示了两幅使用逼真皮肤着色器的实时渲染之间的比较。（关于皮肤着色器的更多信息，见本书第 14 章「面向逼真实时皮肤渲染的高级技术」。）左图把漫反射颜色纹理转换到了线性空间，因为该纹理由若干 JPEG 照片而来。光照（包括次表面散射）与着色都正确地在线性空间中完成，然后对最终图像做伽马校正，以便在普通非线性显示设备上显示。

右图这两项校正都没做，暴露出若干问题。彩色照片中的肤色发生了变化，因为光照是在非线性空间中完成的，当光把颜色值调亮或调暗时，颜色被无意中改变了。（肤色的红色分量高于绿色与蓝色分量，因此在被光照与阴影调亮或调暗时得到不同程度的提升。）白色的镜面光加到漫反射光照上之后变成黄色。阴影区域变得太暗，而次表面散射（特别是渗入阴影区域的细微红色扩散）几乎完全消失，因为它在显示时被伽马曲线压扁了。

在非线性空间中调整光照会变得很麻烦。如果我们把 图 24-4 中同样的场景现在把光强提高再渲染，非线性版本中的问题会变得更糟，如 图 24-5 所示。一般规律是：如果同一物体被调亮或调暗时色调发生变化，那么很可能光照是在非线性空间中做的，需要伽马校正。

用次表面散射做皮肤渲染时（在忽略伽马校正的情况下）常遇到的一个问题，是阴影边缘周围出现蓝绿色辉光、皮肤显得过于蜡质，如 图 24-6 所示。当散射参数被调整到让阴影边缘呈现所需程度的红色渗漏（如 图 24-5 所示）时，就会出现这些问题。这种效果在非线性色彩空间中很难做到，需要在红色通道中对辐照度做权重很高的宽模糊。结果导致面部亮区扩散过度（显得蜡质），并且在接近阴影边缘时红色过暗（留下蓝绿色辉光）。

24.4 疗法

伽马校正的做法是：在图像像素被显示之前，对它们施加显示器变换的逆。也就是说，如果我们在显示前把像素值取 1/gamma 次幂，那么显示时隐含的 gamma 次幂正好把它抵消，总体上得到线性响应（见 图 24-2）。

通常的实现是让你的窗口系统应用包含伽马校正的色彩校正查找表（LUT）。这一调整让所有渲染、合成或其他图像操作都能使用线性运算，并让任何线性扫描的图像、画作或渲染图像正确显示。

动画与视觉效果工作室以及商业发行商对这道工序非常谨慎。通常有专职人员负责理解其显示器、合成管线、胶片与视频扫描以及最终输出的色彩管理。事实上对高端应用来说，简单伽马校正还不够。合成师常用复杂得多的三维颜色 LUT，它由对各个显示器或胶片素材色彩响应曲线的仔细测量得出。[4] 与影视视觉效果和动画相反，游戏开发者常把这道工序做错，从而引出本章讨论的那些瑕疵。这是多数（但不是全部）影视 CG 看起来比游戏好得多的原因之一——这个原因与多边形数量、着色或游戏创作者的美术功力都无关。（这有时也是某些本来做得不错的影视 CG 看起来很差的原因——因为色彩配置与伽马被粗心的合成师弄错了。）

普通玩家没有校准过的显示器。我们不知道他的显示器该套用哪个 LUT，而且无论如何，他都不想给整个显示应用伽马校正 LUT。为什么？因为那样一来，用网页浏览器等观看的普通 JPEG 文件会显得发灰褪色，而他不会明白为什么。（电影公司不在乎互联网上的随机图像在美术的工作站上看起来不对，只要他们真正的工作成果——电影本身——在有完全掌控的影院里完美呈现。）但对「普通」显示器做简单伽马校正，就能让我们完成大部分工作。本章余下部分将给出在你在开发的游戏中改善并避免这些瑕疵的最简便方案。

24.4.1 输入图像（扫描件、画作与数字照片）

你用扫描或数字摄影采集的大多数图像多半已经过伽马校正（尤其是到你手上时已是 JPEG 的），因此处在非线性色彩空间中。（数码相机的 JPEG 通常还被相机做过锐化，采集纹理时尽量用 RAW 文件格式，免得意外。）如果你绘制纹理时没用伽马 LUT，那些画作也处在显示器色彩空间中。如果一张图像在你的显示器上用网页浏览器看起来正常，那它很可能已做过伽马校正，是非线性的。

任何已经过伽马校正的输入纹理，在被用于着色或合成之前都需要回到线性色彩空间。你要对用于（线性）光照计算的纹理值做这一调整。颜色值（例如光强与漫反射率颜色）在用于着色之前，总应当先反校正到线性空间。alpha 通道、法线贴图、置换值（等等）几乎肯定已是线性的，不应再做校正；你小心地按线性方式绘制或采集的那些纹理也不应再校正。

所有现代 GPU 都支持 sRGB 纹理格式。这些格式允许把已做伽马校正的像素数据直接绑定为纹理，由硬件在纹理取数结果用于着色之前施加恰当的伽马。在 NVIDIA GeForce 8 级（及以后）硬件上，纹理滤波操作中用到的所有样本都先线性化再滤波，以确保滤波正确（较早的 GPU 在滤波之后才施加伽马）。所施加的校正是 IEC 标准（IEC 61966-2-1），相当于约 2.2 的伽马，对非线性颜色数据是稳妥的选择。若存在 alpha 值，则不做校正。

在 OpenGL 与 DirectX 中，所有 8 位纹理格式（RGB、RGBA、亮度、亮度 alpha 以及 DXT 压缩）都定义了相应的 sRGB 格式。例如把 GL_SRGB_EXT 而非 GL_RGB 传给 glTexImage2D，就能确保着色器对该纹理的任何访问都返回线性像素值。

sRGB 自动校正是免费的，而且优于在着色器中每次纹理访问之后手动校正（如代码清单 24-1 所示），因为每条 pow 指令都是标量运算，会展开成两条指令。而且手动校正发生在滤波之后，而滤波本身是在非线性空间中错误地进行的。sRGB 格式也可能优于在加载前把纹理预转换为线性版本。把线性像素存回 8 位图像，实际上会在低光水平上损失精度，当像素被转换回显示器空间或用于进一步着色时可能造成色带。

示例 24-1. 手动把颜色值转换到线性空间

纹理查找可以施加反向伽马校正，让你着色器的其余部分都在线性值上工作。不过使用 sRGB 纹理更快，能实现正确的线性纹理滤波（GeForce 8 及以后），而且不需要额外的着色器代码。


float3 diffuseCol =
    pow(f3tex2D(diffTex, texCoord),
        2.2); // 或者（更省，但假设伽马为 2.0 而非 2.2）
float3 diffuseCol = f3tex2D(diffTex, texCoord);
diffuseCol = diffuseCol * diffuseCol;

管理需要混合线性与非线性输入的着色器，对提供纹理的引擎程序员与美术来说可能是一件丑陋的杂活。许多情况下最简单的方案，是干脆要求所有纹理在交付用于渲染之前预先校正到线性空间。

24.4.2 输出图像（最终渲染）

显示前的最后一步是对最终像素值做伽马校正，这样当它们显示在响应非线性的显示器上时，图像看起来才「正确」。指定 sRGB 帧缓冲就把校正交给 GPU，无需改动着色器。着色器返回的任何值都在存入帧缓冲（或渲染到纹理的缓冲）之前做伽马校正。此外在 GeForce 8 级及以后的硬件上，若启用了混合，先前存入的值会先转回线性再混合，混合结果再做伽马校正。启用 sRGB 缓冲时，alpha 值不做伽马校正。如果没有 sRGB 缓冲，你可以采用更昂贵的方案，用自定义着色器代码（如代码清单 24-2 所示）；不过此时若启用了混合，混合计算会是错误的。

示例 24-2. 末级输出的伽马校正

如果没有 sRGB 帧缓冲（或者暴露了用户自定义的伽马值），下面的代码将完成伽马校正。


float3 finalCol = do_all_lighting_and_shading();
float pixelAlpha = compute_pixel_alpha();
return float4(
    pow(finalCol, 1.0 / 2.2),
    pixelAlpha); // 或者（更省，但假设伽马为 2.0 而非 2.2）
return float4(sqrt(finalCol), pixelAlpha);

24.4.3 中间颜色缓冲

有几点微妙之处需要记住。如果你要对图像做任何后处理遍，伽马校正应当作为最后一道后处理遍的最后一步。不要渲染、校正，然后又把结果当作线性图像继续做运算。

另外，如果你是渲染生成一张纹理，那么要么（a）做伽马校正，之后对它做任何进一步处理时把该纹理当作非线性输入；要么（b）不做伽马校正，之后把它当作线性输入处理。中间颜色缓冲若存为 8 位线性图像，在暗部可能比存为伽马校正图像损失精度。因此，用 16 位浮点或 sRGB 帧缓冲与 sRGB 纹理格式来渲染和访问中间颜色缓冲可能更好。

24.5 小结

OpenGL、DirectX 以及你写的任何着色器，很可能都在假定所有纹理输入、光与材质交互以及输出都是线性的前提下做运算（也就是光强相加、漫反射率相乘）。但你的纹理输入很可能是非线性的，而你的用户那台未校准、未校正的显示器几乎肯定施加了非线性色彩空间变换。这种局面会导致各种瑕疵与不准确，有些微妙（例如 mipmap 滤波误差），有些错得离谱（例如严重错误的光衰减）。

我们强烈建议开发者采取以下简单步骤：

  1. 假定多数游戏玩家用的都是未校准、未校正的显示器，大致可以用伽马 = 2.2 的指数响应来刻画。（想要更高质量的终端用户体验：让你的游戏设置显示一张伽马校准图，让用户自己选一个合适的伽马值。）
  2. 从表示光或颜色值的非线性纹理（那些在未校正显示器上看起来「正常」的纹理）做查找时，把结果取 gamma 次幂，得到可供着色器使用的线性值。对已在线性色彩空间中的值，例如某些高动态范围光照图，或含有法线、凹凸高度及其他非颜色数据的图像，不要做这一调整。尽可能使用 sRGB 纹理格式，以提升性能并在 GeForce 8 GPU（及以后）上获得正确的纹理滤波。
  3. 在显示之前最后一步对最终像素值施加伽马校正（也就是取 1/gamma 次幂）。使用 sRGB 帧缓冲扩展，以高效地自动完成伽马校正并获得正确的混合。

认真遵循这些步骤，对改善游戏观感至关重要，尤其是对提高你着色器中任何光照或材质计算的准确度。
