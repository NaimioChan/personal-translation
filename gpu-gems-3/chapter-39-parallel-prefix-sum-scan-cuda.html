39.1 引言

一个简单而常见的并行算法构件是全前缀和操作。本章定义并说明这个操作，并详细讨论用 NVIDIA CUDA 的高效实现。Blelloch（1990）把全前缀和描述为一个看似本质上串行、却存在高效并行算法的计算的绝佳例子。他如下定义全前缀和操作：

全前缀和操作取一个具有单位元 I 的二元结合算子 ⊕，以及一个含 n 个元素的数组

即 [a 0, a 1,..., a n–1],

并返回数组

即 [I, a 0, (a 0 ⊕ a 1),..., (a 0 ⊕ a 1 ⊕ ... ⊕ a n–2)]

例如若 ⊕ 是加法，那么对数组

[3 1 7 0 4 1 6 3]

做全前缀和操作将返回

[0 3 4 11 11 15 16 22].

对数组数据的全前缀和操作通常称为扫描。本章余下部分使用这个更简单的说法（它来自 APL 编程语言 [Iverson 1962]）。刚刚定义的扫描是排他扫描，因为结果的每个元素 j 是输入数组中该元素之前、不含 j 的所有元素之和。在包含扫描中，所有包含 j 的元素都被求和。排他扫描可以由包含扫描生成：把结果数组右移一个元素，并插入单位元。同样，包含扫描可以由排他扫描生成：把结果数组左移，并在末尾插入扫描最后一个元素与输入数组最后一个元素之和（Blelloch 1990）。本章余下部分我们专注于排他扫描的实现，除非特别说明，简称为「扫描」。

扫描有很多用途，包括但不限于排序、词法分析、字符串比较、多项式求值、流压缩，以及并行构建直方图和数据结构（图、树等）。应用示例请参见 Blelloch（1990）的综述。本章我们讨论求和面积表（用于可变宽度图像滤波）、流压缩和基数排序。

一般来说，全前缀和可以把某些串行计算转换成等价但并行的计算，如图 39-1 所示。

39.1.1 串行扫描与工作量效率

实现扫描的串行版本（例如可以在 CPU 的单个线程中运行）是件小事。我们只需遍历输入数组的所有元素，把输入数组前一个元素的值加到为输出数组前一个元素算出的和上，再把这个和写入输出数组的当前元素。

out[0] := 0 for k := 1 to n do
out[k] := in[k-1] + out[k-1]

对长度为 n 的数组，这段代码恰好执行 n 次加法；这是生成扫描后数组所需的最少加法次数。开发并行版扫描时，我们希望它是工作量高效的。如果一个并行计算渐近地做的工作（这里是加法操作）不比串行版本多，它就是工作量高效的。换句话说，两种实现应具有相同的工作量复杂度 O(n)。

39.2 实现

串行扫描算法不太适合 GPU，因为它没有利用 GPU 的数据并行性。我们希望找到能利用 GPU 并行处理器加速计算的并行扫描版本。本节逐步介绍并行扫描算法的 CUDA 实现。我们先介绍一个简单但低效的实现，然后给出算法与 CUDA 实现两方面的改进。

39.2.1 朴素并行扫描

算法 1 中的伪代码是对并行扫描的第一次尝试。这个算法基于 Hillis 和 Steele（1986）提出的扫描算法，并由 Horn（2005）在 GPU 上演示。图 39-2 说明了这个操作。检查算法 1 的工作量复杂度，问题就明显了。该算法执行 O(n log2 n) 次加法操作。记住串行扫描只执行 O(n) 次加法。因此这个朴素实现不是工作量高效的。log2 n 这个因子可能对性能有很大影响。

示例 1. 一个非工作量高效的求和扫描算法

1: for d = 1 至 log2 n do
2: for all k 并行 do
3: if k ≥ 2 d then
4: x[k] = x[k – 2 d-1] + x[k]

算法 1 假设处理器数量与数据元素一样多。对于在 CUDA 上运行的大数组，通常并非如此。程序员必须把计算划分给若干线程块，每个线程块在 GPU 的一个多处理器上扫描数组的一部分。即便如此，一个多处理器中的处理器数通常远小于每块的线程数，因此硬件会自动把「for all」语句分成小的并行批次（称为 warp），在多处理器上顺序执行。一块 NVIDIA 8 系列 GPU 并行执行 32 个线程的 warp。因为对于大于 warp 尺寸的数组并非所有线程同时运行，算法 1 无法工作，因为它是在数组上原地扫描。一个 warp 的结果会被另一个 warp 的线程覆盖。

为解决这个问题，我们需要用两个临时数组对正在扫描的数组做双缓冲。算法 2 给出了伪代码，代码清单 39-1 给出了朴素扫描的 CUDA C 代码。注意这段代码只在 GPU 的单个线程块上运行，因此能处理的数组规模有限（在 NVIDIA 8 系列 GPU 上为 512 个元素）。把扫描扩展到大型数组见 39.2.4 节。

示例 2. 算法 1 求和扫描的双缓冲版本

1: for d = 1 至 log2 n do
2: for all k 并行 do
3: if k ≥ 2 d then
4: x[out][k] = x[in][k – 2 d-1] + x[in][k]
5: else
6: x[out][k] = x[in][k]

示例 39-1. 朴素扫描算法的 CUDA C 代码

这个版本只能处理单个线程块在 GPU 的一个多处理器上运行所能处理的数组规模。


__global__ void scan(float *g_odata, float *g_idata, int n)
{
  extern __shared__ float temp[]; // 调用时分配
  int thid = threadIdx.x;
  int pout = 0, pin = 1;
  // 把输入载入共享内存。
  // 这是排他扫描，因此右移一位
  // 并把第一个元素置为 0
  temp[pout * n + thid] = (thid > 0) ? g_idata[thid - 1] : 0;
  __syncthreads();
  for (int offset = 1; offset < n; offset *= 2)
  {
    pout = 1 - pout; // 交换双缓冲索引
    pin = 1 - pout;
    if (thid > = offset)
      temp[pout * n + thid] += temp[pin * n + thid - offset];
    else
      temp[pout * n + thid] = temp[pin * n + thid];
    __syncthreads();
  }
  g_odata[thid] = temp[pout * n + thid]; // 写出输出
}

39.2.2 工作量高效的并行扫描

我们在 39.2.1 节中的扫描实现由于工作量不高效，在大数组上大概会表现很差。我们希望找到一个既能接近串行算法效率、又能利用 GPU 并行性的算法。本节的目标是为 CUDA 开发一个工作量高效的扫描算法，避免朴素算法多出的 log2 n 倍工作量。这个算法基于 Blelloch（1990）提出的算法。为此我们使用并行计算中经常出现的一种算法模式：平衡树。思路是在输入数据上建一棵平衡二叉树，然后向根和从根各扫一遍来计算前缀和。含 n 个叶子的二叉树有 d = log2 n 层，第 d 层有 2 d 个节点。如果每个节点做一次加法，那么遍历树一次就执行 O(n) 次加法。

我们建的树不是实际的数据结构，而是用来确定每个线程在遍历的每一步做什么的概念。在这个工作量高效的扫描算法中，我们直接在共享内存中的数组上原地操作。算法分两个阶段：归约阶段（也称上扫阶段）和下扫阶段。归约阶段中，我们从叶子向根遍历树，在树的内部节点计算部分和，如 图 39-3 所示。这也称为并行归约，因为这一阶段之后，根节点（数组的最后一个节点）持有数组中所有节点之和。归约阶段的伪代码见算法 3。

示例 3. 工作量高效求和扫描算法的上扫（归约）阶段（依照 Blelloch 1990）

1: for d = 0 至 log2 n – 1 do
2: for all k = 0 至 n – 1 步长 2 d+1 并行 do
3: x[k + 2 d+1 – 1] = x[k + 2 d – 1] + x[k + 2 d +1 – 1]

在下扫阶段，我们从根沿树往回遍历，用归约阶段的部分和在数组上原地构建扫描。先在树的根处插入零，然后每一步中，当前层的每个节点把自己的值传给左孩子，把自己的值与左孩子原值之和传给右孩子。下扫如 图 39-4 所示，伪代码见算法 4。完整算法的 CUDA C 代码见代码清单 39-2。与 39.2.1 节的朴素扫描代码一样，代码清单 39-2 的代码只在单个线程块上运行。由于每个线程处理两个元素，这段代码在 NVIDIA 8 系列 GPU 上能扫描的最大数组规模是 1,024 个元素。更大数组的扫描见 39.2.4 节。

示例 4. 工作量高效并行求和扫描算法的下扫阶段（依照 Blelloch 1990）

1: x[n – 1] ← 0
2: for d = log2 n – 1 降至 0 do
3: for all k = 0 至 n – 1 步长 2 d +1 并行 do
4: t = x[k + 2 d – 1]
5: x[k + 2 d – 1] = x[k + 2 d +1 – 1]
6: x[k + 2 d +1 – 1] = t + x[k + 2 d +1 – 1]

算法 4 中的扫描算法执行 O(n) 次操作（2 x (n – 1) 次加法和 n – 1 次交换）；因此它是工作量高效的，对大数组应当比上一节的朴素算法表现好得多。算法效率还不够；我们还必须高效地使用硬件。如果检查这个扫描在运行 CUDA 的 GPU 上的执行情况，会发现它遭受大量共享内存 bank 冲突。这些冲突会损害每次共享内存访问的性能，显著影响整体性能。下一节我们看一些对内存地址计算做的简单改动，可以找回大部分损失的性能。

39.2.3 避免 bank 冲突

上一节的扫描算法所做的工作量与最优串行算法大致相当。尽管工作量高效，它在 NVIDIA GPU 硬件上还不够高效，原因在于其内存访问模式。如 NVIDIA CUDA Programming Guide（NVIDIA 2007）所述，这个扫描算法所用的共享内存由多个 bank 组成。同一 warp 中的多个线程访问同一个 bank 时，除非该 warp 的所有线程访问同一个 32 位字内的同一地址，否则就发生 bank 冲突。访问单个 bank 的线程数称为 bank 冲突的度。bank 冲突会使对该内存 bank 的多次访问串行化，因此一次度为 n 的 bank 冲突的共享内存访问，处理所需的周期是一次无冲突访问的 n 倍。在 NVIDIA 8 系列 GPU 上，半个 warp 并行执行 16 个线程，最坏情况是度为 16 的 bank 冲突。

像我们的工作量高效扫描这样的二叉树算法，在树的每一层把内存访问的步长加倍，同时也使访问同一 bank 的线程数加倍。对于较深的树，当我们接近树的中间层时，bank 冲突的度上升，然后在靠近根的地方又下降，因为那里活跃线程数减少（由于代码清单 39-2 中的 if 语句）。例如扫描一个 512 元素的数组时，代码清单 39-2 内层循环中的共享内存读写会经历最高 16 路的 bank 冲突。这对性能有显著影响。

在多数 CUDA 计算中，只要在访问 __shared__ 内存数组时留心，bank 冲突是可以避免的。在扫描中，我们可以给计算出的每个共享内存数组索引加上可变数量的填充来避免大部分 bank 冲突。具体做法是给索引加上该索引除以共享内存 bank 数的值。这在 图 39-5 中演示。我们从代码清单 39-2 的工作量高效扫描代码出发，只修改高亮显示的代码块 A 到 E。为简化代码改动，我们定义一个宏 CONFLICT_FREE_OFFSET，如代码清单 39-3 所示。

示例 39-3. 用于计算无 bank 冲突的共享内存数组索引的宏

#define NUM_BANKS 16
#define LOG_NUM_BANKS 4
#define CONFLICT_FREE_OFFSET(n)((n) >>
NUM_BANKS + (n) >>
(2 * LOG_NUM_BANKS))

代码清单 39-2 中的代码块 A 到 E 需要用这个宏修改，以避免 bank 冲突。代码块 A 要作两处改动。每个线程从 __global__ 数组 g_idata 中把两个数组元素载入 __shared__ 数组 temp。在原来的代码中，每个线程载入两个相邻元素，导致共享内存数组的交错索引，产生两路 bank 冲突。改为从数组的两个不同半区各载入一个元素，就避免了这些 bank 冲突。此外，为避免树遍历期间的 bank 冲突，我们需要每 NUM_BANKS（16）个元素给共享内存数组加一次填充。我们用代码清单 39-3 中的宏来做，如代码清单 39-4 所示。注意我们保存了共享内存索引的偏移量，以便在扫描末尾、代码块 E 中把结果写回输出数组 g_odata 时再次使用。

39.2.4 任意规模的数组

前面几节给出的算法在单个线程块内扫描一个数组。这对小数组没问题，最大到线程块中最大线程数的两倍（因为每个线程载入并处理两个元素）。在 NVIDIA 8 系列 GPU 上，这把我们限制在最多 1,024 个元素。此外，数组规模必须是 2 的幂。本节说明如何把算法扩展到大数组，规模任意（不要求是 2 的幂）。这个算法基于 Blelloch（1990）给出的说明。

基本思路很简单。我们把大数组划分成若干块，每块可由一个线程块扫描，然后扫描这些块，并把每块的总和写入另一个存放块和的数组。接着扫描这些块和，生成一个块增量数组，把这些增量加到各自块内的所有元素上。更详细地说，设 N 为输入数组的元素数，B 为一块中处理的元素数。我们分配 N/B 个线程块，每块 B/2 个线程。（这里假设 N 是 B 的整数倍，任意规模的情形在下一段扩展。）在 NVIDIA 8 系列 GPU 上 B 的典型取值是 128。我们用前几节的扫描算法独立扫描每个块 i，把得到的扫描结果存到输出数组的连续位置。我们对扫描算法作一处小改动。在把块 i 的最后一个元素清零之前（代码清单 39-2 中标为 B 的代码块），我们把该值（块 i 的总和）存入辅助数组 SUMS。然后以同样方式扫描 SUMS，把结果写入数组 INCR。接着用一个简单的均匀加法内核，把 INCR[i] 加到块 i 的所有元素上，该内核调用在 N/B 个每块 B/2 线程的线程块上。这在 图 39-6 中演示。实现细节请见 http://www.gpgpu.org/scan-gpugems3/ 上的源代码。

处理非 2 的幂的规模很容易。我们只需把数组填充到块大小 B 的下一个倍数。扫描算法不依赖数组末尾之后的元素，因此不必为最后一块做特殊处理。

39.2.5 进一步优化与性能结果

在优化共享内存访问之后，扫描代码剩下的主要瓶颈是全局内存延迟，以及循环和地址计算指令带来的指令开销。为更好地覆盖全局内存访问延迟、提高整体效率，我们需要每个线程做更多计算。我们采用 David Lichterman 建议的一种做法：每个线程载入两个 float4 元素而不是两个 float 元素，从而处理八个元素而不是两个（Lichterman 2007）。每个线程对每个 float4 做一次串行扫描，把每次扫描的前三个元素存入寄存器，并把总和插入共享内存数组。用共享内存中来自所有线程的部分和，我们执行与代码清单 39-2 相同的基于树的扫描。随后每个线程把共享内存中对应的扫描后元素分别加到寄存器里保存的各个部分和上，构造出两个 float4 值。最后把这两个 float4 值写入全局内存。这种做法比前面给出的代码快一倍以上，它是 Brent 定理的结果，也是提高并行算法效率的常用技术（Quinn 1994）。

为减少簿记与循环指令开销，我们展开算法 3 和算法 4 中的循环。由于块大小固定，我们可以完全展开这些循环，大大减少在循环中遍历树所需的额外指令。

我们在 CUDA 中打造高效扫描实现的努力得到了回报。性能比在快速 CPU 上运行的串行版扫描快最多 20 倍，如 图 39-7 中的曲线所示。此外，得益于 CUDA 提供的优势，我们比在同一块 GPU 上运行的优化 OpenGL 实现快最多七倍。图中还给出了我们对每块使用 39.2.1 节朴素扫描实现时达到的性能。由于朴素扫描和工作量高效扫描都必须在相同线程数的块之间划分，朴素扫描的性能只慢 O(log2 B) 倍（B 为块大小），而不是 O(log2 n) 倍。图 39-8 比较了我们最好的 CUDA 实现与缺少 bank 冲突避免和循环展开的版本。

39.2.6 CUDA 相对 OpenGL 实现的优势

在 CUDA 出现之前，若干研究者用 OpenGL 和 Direct3D 等图形 API 实现扫描（更多内容见 39.3.4 节）。为说明 CUDA 相对这些 API 在扫描这类计算上的优势，本节简要介绍 Sengupta 等（2006）的工作量高效 OpenGL 包含扫描实现。他们的实现是一种混合算法，先按可配置的次数执行归约步骤，如算法 5 所示。然后对归约步骤的结果运行前面算法 2 所示的求和扫描双缓冲版本。最后执行算法 6 所示的下扫。

示例 5. OpenGL 扫描算法的归约步骤

1: for d = 1 至 log2 n do
2: for all k = 1 至 n/2 d – 1 并行 do
3: a[d][k] = a[d – 1][2k] + a[d – 1][2k + 1]]

示例 6. OpenGL 扫描算法的下扫步骤

1: for d = log2 n – 1 降至 0 do
2: for all k = 0 至 n/2 d – 1 并行 do
3: if i > 0 then
4: if k mod 2 ≠ 0 then
5: a[d][k] = a[d + 1][k/2]
6: else
7: a[d][i] = a[d + 1][k/2 – 1]

OpenGL 的扫描计算用像素着色器实现，每个 a[d] 数组是 GPU 上的一幅二维纹理。向这些数组写入通过 OpenGL 的渲染到纹理完成。因此算法 5 和算法 2 的每次循环迭代都需要从一幅纹理读取、向另一幅纹理写入。

CUDA 相对 OpenGL 的主要优势在于片内共享内存、线程同步功能，以及向内存的分散写，这些都是 OpenGL 像素着色器无法使用的。CUDA 把大规模扫描的工作划分到许多块，每块在任何数据写入片外内存之前，完全由单个多处理器在片内处理完。在 OpenGL 中，所有内存更新都是片外内存更新。因此 OpenGL 实现使用的带宽高得多，性能也就更低，如前面 图 39-7 所示。

39.3 扫描的应用

正如引言所述，扫描有非常广泛的应用。本节讨论扫描的三个应用：流压缩、求和面积表和基数排序。

39.3.1 流压缩

流压缩是各种通用应用中的重要基础操作，包括碰撞检测和稀疏矩阵压缩。事实上，流压缩正是以往 GPU 上扫描工作的大多数关注点（见 39.3.4 节）。流压缩是把含多种元素类型的异构向量转换成同构向量的主要方法，同构向量中每个元素的类型相同。这对那些部分元素是有用的、而大量元素无用的向量尤其有用。流压缩产生一个只含有用元素的更小向量。有了这个更小的向量，计算更高效，因为我们只在有用的元素上计算，因而传输开销、尤其是 GPU 与 CPU 之间的传输开销，有可能大大降低。

通俗地说，流压缩是一种过滤操作：从输入向量中选出它的一个子集，并把这个子集打包进一个紧凑的输出向量。图 39-9 给出一个例子。更形式化地说，流压缩取一个输入向量 vi 和一个谓词 p，只输出 vi 中使 p(vi ) 为真的那些元素，并保持输入元素的顺序。Horn（2005）详细描述了这个操作。

流压缩需要两步：一次扫描和一次分散写。

  1. 第一步生成一个临时向量，其中通过谓词的元素置为 1，其余元素置为 0。然后我们扫描这个临时向量。对每个通过谓词的元素，扫描结果现在包含该元素在输出向量中的目标地址。
  2. 第二步用扫描生成的地址把输入元素分散写到输出向量。

图 39-10 详细展示了这个过程。

Horn 在 2005 年实现流压缩时所用的 GPU 没有分散写能力，因此 Horn 改用一系列聚集读步骤来模拟分散写。压缩 n 个元素需要 log n 个聚集读步骤，虽然这些步骤可以在一个片元程序中实现，但这种「聚集搜索」操作相当昂贵，而且需要更多内存操作。近期 GPU 加入了原生分散写，使流压缩高效得多。我们的流压缩测试性能见 图 39-11。

39.3.2 求和面积表

求和面积表（SAT）是由输入图像生成的二维表，表中每一项存放该项位置与输入图像左下角之间所有像素之和。求和面积表由 Crow（1984）提出，他展示了如何用它在上做任意宽度的盒式滤波。求和面积表的威力在于，用它可以在每个像素上以常数时间完成不同宽度的滤波。Hensley 等（2005）演示了用 GPU 快速生成的求和面积表交互式渲染有光泽的环境反射与折射。他们的 GPU 实现使用的扫描操作等价于 39.2.1 节中的朴素实现。用 CUDA 的工作量高效实现可以达到更高性能。本节介绍如何在 CUDA 中用扫描计算求和面积表，并演示用它渲染近似的景深。

要计算二维图像的求和面积表，我们只需对图像所有行做一次求和扫描，再对结果的所有列做一次求和扫描。为在 CUDA 中高效完成，我们把扫描的基本实现扩展成并行执行许多独立扫描。得益于 CUDA 提供的「线程块网格」语义，这很容易；我们用一个二维线程块网格，网格的每一行扫描图像的一行。为此修改扫描，只需修改每块中待扫描数据所在全局内存索引的计算。若把扫描扩展为也支持扫描列，性能会很差，因为按列扫描要求线程之间在内存中有很大的步长，导致非合并的内存读取（NVIDIA 2007）。因此我们在扫描完各行之后，简单地转置图像，然后扫描转置图像的各行。

39.3.3 基数排序

以往基于 GPU 的排序例程主要使用双调排序的变体（Govindaraju 等 2006，Greß 和 Zachmann 2006），这是一种适合并行处理器的高效无视数据分布的排序算法。扫描这个基础操作可以作为 GPU 上另一种高效排序算法——基数排序——的构件。

我们的实现先用基数排序对输入数组的各个块排序。各块由多个线程块并行排序。块的大小以能装进 GPU 上单个多处理器的共享内存为限。排完各块之后，我们用并行双调归并把块两两合并。重复这一合并，直到产生一个有序数组。

第 1 步：对块做基数排序

基数排序特别适合位数很少的小排序键，例如小整数。从高层看，基数排序的工作方式如下。我们先从每个键中取出一个位来考虑，从最低有效位开始。用这一位把键分区，使该位为 0 的所有键排在该位为 1 的所有键之前，其余保持键的原有顺序。见 图 39-13。然后移到下一个较低的有效位，重复这一过程。

因此对于 k 位的键，基数排序需要 k 步。我们的实现每一步需要一次扫描。

我们用来实现基数排序每一步的基本操作是 split 操作。split 的输入是一组排序键以及它们在这一步所关心的位值 b，取值为真或假。输出是一组新的排序键，其中所有假排序键都排在所有真排序键之前。

我们在 GPU 上按下面的方式实现 split，如 图 39-14 所示。

  1. 在共享内存的一块临时缓冲里，我们为所有假排序键（b = 0）置 1，为所有真排序键置 0。
  2. 然后我们扫描这块缓冲。这就是 enumerate 操作；每个假排序键现在在扫描输出中包含自己的目标地址，我们称之为 f。前两步等价于对所有假排序键做一次流压缩。
  3. 扫描输出的最后一个元素现在包含假排序键的总数。[1] 我们把这个值写入一个共享变量 totalFalses。
  4. 现在我们计算真排序键的目标地址。对索引为 i 的排序键，该地址为 t = i - f + totalFalses。然后我们根据 b 的值在 t 与 f 之间选择，得到每个片元的目标地址 d。
  5. 最后我们把原始排序键分散写到目标地址 d。这个分散模式是输入的一个完美置换，因此这次分散写没有写冲突。

有了 split，我们可以很容易地实现基数排序。先从一个块大小的输入块从全局内存载入共享内存。然后把当前位初始化为键的最低有效位，按键做 split，检查输出是否已有序，若未有序则把当前位左移一位再次迭代。完成之后，把排序好的数据复制回全局内存。输入很大时，每块映射到一个线程块，与其他块并行运行。

第 2 步：合并已排序的块

每个块大小的块排好序之后，我们用递归归并排序把两个已排序块合并成一个。若有 b 个大小为 n 的已排序块，我们需要 log2 b 步归并，才能在最后得到一个有序输出。第一步并行做 b/2 次归并，每次处理两路 n 元素的已排序输入流，产生 2n 个有序输出元素。下一步并行做 b/4 次归并，每次处理两路 2n 元素的已排序输入流，产生 4n 个有序输出元素，依此类推。

因此我们的归并内核必须处理位于 GPU 主存中的两个任意长度的输入。从高层看，我们的实现用两块共享内存缓冲，每个输入一块，并用并行双调排序归并每块缓冲中最小的那些元素。然后在需要时从主存重新填满缓冲，重复直到两个输入都耗尽。所有从全局内存读入共享内存、以及所有写入全局内存的操作都是有凝聚的、成块的；我们还保证每个输入元素只从全局内存读一次，每个输出元素只写一次。

在我们的归并内核中，我们并行运行 p 个线程。实现中最有意思的部分，是从输入缓冲的两条已排序序列中计算并排序出 p 个最小元素。图 39-15 展示了这一过程。对 p 个元素，两条已排序序列两两并行比较的输出是双调的，因而可以用 log2 p 次并行操作高效排序。

39.3.4 以往的工作

扫描最早由 Iverson 于 1950 年代中期提出，是 APL 编程语言的一部分（Iverson 1962）。Blelloch 是用扫描这个基础操作开发高效算法的主要研究者之一（Blelloch 1990），包括本章所述的基于扫描的基数排序（Blelloch 1989）。

在 GPU 上，最早发表的扫描工作是 Horn 2005 年的实现（Horn 2005）。Horn 的扫描被用作一个非均匀流压缩操作的构件，后者又用于一个碰撞检测应用。Horn 的扫描实现工作量复杂度为 O(n log n)。同年晚些时候，Hensley 等（2005）把扫描用于生成求和面积表，通过剪除不必要的工作提高了 Horn 实现的整体效率。不过与 Horn 一样，Hensley 等人技术的整体工作量复杂度也是 O(n log n)。

GPU 上最早发表的 O(n) 扫描实现来自 Sengupta 等（2006），也用于流压缩。他们表明，在 NVIDIA GeForce 7 系列这类 GPU 上，工作量高效（O(n) 次操作、2n 步）与步骤高效（O(n log n) 次操作、n 步）混合的实现在性能上最佳。Sengupta 等人的实现被用在一个分层阴影贴图算法中，把一串阴影页（其中一些需要细化、一些不需要）压缩成只含需要细化的阴影页的一串。同年晚些时候，Greß 等（2006）也在一个基于 GPU 的碰撞检测应用的背景下，为流压缩提出了 O(n) 扫描实现。与以往基于 GPU 的一维扫描实现不同，Greß 等人的应用需要二维流归约，使总步数更少。Greß 等人还把他们的扫描实现用于流压缩，这里的任务是从一串更大的可能重叠的碰撞元素对中，计算出有效重叠的碰撞元素对。

39.4 结论

扫描操作是一个简单而强大的并行基础操作，应用范围很广。本章说明了用 CUDA 的高效扫描实现，相对快速 CPU 上的串行实现，以及同一块 GPU 上的 OpenGL 并行实现，都取得了显著加速。由于 GPU 这类商品化并行处理器的能力不断增强，我们预期扫描这类数据并行算法在未来几年会越来越重要。
