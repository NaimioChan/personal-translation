31.1 引言

N 体仿真对一个由彼此持续相互作用的物体组成的系统做数值近似演化。一个熟悉的例子是天体物理仿真，其中每个物体代表一个星系或一颗恒星，物体之间通过引力相互吸引，如图 31-1 所示。N 体仿真还出现在许多其它计算科学问题中。例如研究蛋白质折叠时用 N 体仿真计算静电作用力与范德华力。湍流仿真与计算机图形学中的全局光照计算，也是使用 N 体仿真的其它问题实例。

N 体仿真的全对方法是一种暴力技术，计算 N 个物体之间所有两两相互作用。它方法相对简单，但由于 O(N 2) 的计算复杂度，一般不会单独用于大系统的仿真。全对方法通常作为一个内核，用来确定近距离相互作用中的力。它与一种基于远场近似的更快方法结合使用，后者对较远距离的力有效，且只在系统中彼此分得很开的部分之间成立。这类快速 N 体算法包括 Barnes-Hut 方法（BH）（Barnes 与 Hut 1986）、快速多极方法（FMM）（Greengard 1987）以及质点网格方法（Hockney 与 Eastwood 1981，Darden 等 1993）。

刚才提到的这些算法中，全对部分需要大量计算时间，因此是加速的好目标。提升全对部分的性能也会提升远场部分的性能，因为远场与近场（全对）之间的平衡可以被移动，把更多工作分给更快的全对部分。加速一个部分会为其它部分卸下工作，所以整个应用都能从加速单个内核中受益。

本章我们聚焦全对计算内核及其使用 NVIDIA CUDA 编程模型的实现。我们说明如何用 CUDA 模型表达全对计算内核中可用的并行性，以及如何选择各种参数来有效调用 NVIDIA GeForce 8800 GTX GPU 的全部资源。我们报告用于天体物理仿真的全对 N 体内核的性能，展示若干提升性能的优化。对这个问题，GeForce 8800 GTX 在 N = 16,384 时每秒计算超过 100 亿次相互作用，每秒执行 38 个积分时间步。按每次相互作用 20 次浮点运算计算，这相当于超过 200 gigaflops 的持续性能。这个结果接近 GeForce 8800 GTX GPU 的理论峰值性能。

31.3 全对 N 体算法的 CUDA 实现

我们可以把全对算法看作计算每个元素 f ij，它位于一张 NxN 的所有两两作用力网格中。 [1] 那么总力 F i（或加速度 a i）施加在物体 i 上，由第 i 行所有元素求和得到。每个元素可独立计算，因此有 O(N 2) 的可用并行性。然而这种做法需要 O(N 2) 的内存，会受到内存带宽的严重限制。我们改为把部分计算串行化，以获得达到算术单元峰值性能所需的数据复用，并减少所需的内存带宽。

因此我们引入计算瓦片的概念，即两两作用力网格中由 p 行 p 列组成的正方形区域。只需 2p 个物体描述，即可求出瓦片中的全部 p 2 次相互作用（其中 p 个之后还能复用）。这些物体描述可以存在共享内存或寄存器里。瓦片中相互作用对 p 个物体的总效果，体现为对 p 个加速度矢量的更新。

为达到最优的数据复用，我们这样安排瓦片的计算：每行中的相互作用按顺序求值并更新加速度矢量，而不同的行并行求值。在图 31-2 中，左图展示求值策略，右图展示一个瓦片计算的输入与输出。

本节其余部分按自底向上的顺序讲述完整计算，逐层打包可用的并行性并使用合适的局部内存。

31.3.1 物体-物体受力计算

31.2 节所述的一对物体之间的相互作用，实现为完全串行的计算。代码清单 31-1 中的代码计算物体 i 因与物体 j 相互作用而受到的力，并据此更新加速度 a i，即物体 i 因这次相互作用而产生的加速度。这段代码中有 20 次浮点运算，包括加法、乘法、sqrtf() 调用以及除法（或求倒数）。

示例 31-1. 因与另一物体相互作用而更新一个物体的加速度


   __device__ float3
bodyBodyInteraction(float4 bi, float4 bj, float3 ai)
{
  float3 r;
  // r_ij  [3 FLOPS]
  r.x = bj.x - bi.x;
  r.y = bj.y - bi.y;
  r.z = bj.z - bi.z;
  // distSqr = dot(r_ij, r_ij) + EPS^2  [6 FLOPS]
   float distSqr = r.x * r.x + r.y * r.y + r.z * r.z + EPS2;
  // invDistCube =1/distSqr^(3/2)  [4 FLOPS (2 mul, 1 sqrt, 1 inv)]
   float distSixth = distSqr * distSqr * distSqr;
  float invDistCube = 1.0f/sqrtf(distSixth);
  // s = m_j * invDistCube [1 FLOP]
   float s = bj.w * invDistCube;
  // a_i =  a_i + s * r_ij [6 FLOPS]
  ai.x += r.x * s;
  ai.y += r.y * s;
  ai.z += r.z * s;
  return ai;
}

我们使用 CUDA 的 float4 数据类型来存放存于 GPU 设备内存中的物体描述与加速度。我们把每个物体的质量存在其 w 字段里，该字段属于物体的 float4 位置。使用 float4（而非 float3）数据可以让设备内存中的数据数组实现合并访问，从而得到高效的内存请求与传输。（关于合并内存请求的细节，见 CUDA Programming Guide（NVIDIA 2007）。）存在局部变量里的三维矢量则以 float3 变量存放，因为寄存器空间紧张，而且这里不需要合并访问。

31.3.2 瓦片计算

一个瓦片由 p 个线程对不同的数据执行相同的操作序列来求值。每个线程因与 p 个其它物体相互作用而更新一个物体的加速度。我们从 GPU 设备内存加载 p 个物体描述，存进 CUDA 模型中提供给每个线程块的共享内存。块中每个线程对 p 次连续相互作用求值。瓦片计算的结果是 p 个更新后的加速度。

瓦片计算的代码见代码清单 31-2。输入参数 myPosition 保存执行线程所对应物体的位置，数组 shPosition 是共享内存中的物体描述数组。回想一下，p 个线程并行执行函数体，每个线程遍历同样的 p 个物体，计算自己那个物体因与 p 个其它物体相互作用而产生的加速度。

示例 31-2. 在 pxp 瓦片中求相互作用


   __device__ float3
tile_calculation(float4 myPosition, float3 accel)
{
  int i;
  extern __shared__ float4[] shPosition;
  for (i = 0; i < blockDim.x; i++) {
    accel = bodyBodyInteraction(myPosition, shPosition[i], accel);
  }
  return accel;
}

G80 GPU 架构支持多个线程同时读取同一个共享内存地址，因此求相互作用时不存在共享内存 bank 冲突。（关于这里所用的共享内存广播机制，详见 CUDA Programming Guide（NVIDIA 2007）。）

31.3.3 把瓦片组织成线程块

我们把一个线程块定义为有 p 个线程、依次执行若干瓦片。瓦片的尺寸要在并行性与数据复用之间取得平衡。并行度（即行数）必须足够大，以便多个 warp 可以交错执行，掩盖求相互作用时的延迟。数据复用量随列数增长，这个参数也决定物体从设备内存传入共享内存的传输量大小。最后，瓦片尺寸还决定所需的寄存器空间与共享内存。本实现中我们使用 p 乘 p 的正方形瓦片。执行一个瓦片之前，每个线程把一个物体取进共享内存，随后线程同步。因此每个瓦片开始时，共享内存里有连续的 p 个物体。

图 31-3 展示一个正在执行多个瓦片代码的线程块。水平方向是时间，垂直方向是并行性。粗线划出各计算瓦片，标出加载共享内存与执行屏障同步的位置。一个线程块中有 N/p 个瓦片，p 个线程计算 p 个物体所受的力（每个物体一个线程）。每个线程计算一个物体的全部 N 次相互作用。

为一个线程块计算 N 体作用力的代码见代码清单 31-3。这段代码就是由主机调用的 CUDA 内核。

函数 calculate_forces() 的参数是指向全局设备内存的指针，分别存放物体的位置 devX 与加速度 devA。我们用类型转换把它们赋给局部指针，以便按数组索引。遍历瓦片的循环需要两个同步点。第一个同步确保在引力计算进行之前所有共享内存位置都已填好，第二个同步确保所有线程在进入下一个瓦片之前完成各自的引力计算。若没有第二个同步，先完成瓦片计算中自己那部分的线程可能会覆写其它线程仍在读取的共享内存。

示例 31-3. 由含 p 个线程的线程块执行的 CUDA 内核，计算 p 个物体在全部 N 次相互作用下的引力加速度


   __global__ void
calculate_forces(void *devX, void *devA)
{
  extern __shared__ float4[] shPosition;
  float4 *globalX = (float4 *)devX;
  float4 *globalA = (float4 *)devA;
  float4 myPosition;
  int i, tile;
  float3 acc = {0.0f, 0.0f, 0.0f};
  int gtid = blockIdx.x * blockDim.x + threadIdx.x;
  myPosition = globalX[gtid];
  for (i = 0, tile = 0; i < N; i += p, tile++) {
    int idx = tile * blockDim.x + threadIdx.x;
    shPosition[threadIdx.x] = globalX[idx];
    __syncthreads();
    acc = tile_calculation(myPosition, acc);
    __syncthreads();
  }
  // 把结果保存到全局内存，供积分步骤使用。
   float4 acc4 = {acc.x, acc.y, acc.z, 0.0f};
  globalA[gtid] = acc4;
}

31.3.4 定义线程块网格

代码清单 31-3 中的内核程序计算系统中 p 个物体的加速度，这些加速度由它们与系统中全部 N 个物体的相互作用产生。我们在一张线程块网格上调用这个程序，以计算全部 N 个物体的加速度。由于每块有 p 个线程、每个物体一个线程，完成全部 N 个物体所需的线程块数为 N/p，因此我们定义一个尺寸为 N/p 的一维网格。结果总共有 N 个线程，各自做 N 次受力计算，合计 N 2 次相互作用。

对整个相互作用网格的求值可以像图 31-4 那样可视化。垂直方向是 N/p 个独立线程块（每个含 p 个线程）构成的一维网格的并行性。水平方向是每个线程中 N 次受力计算的顺序处理。一个线程块每 p 步重新加载一次共享内存，以共享 p 个位置的数据。

31.4 性能结果

只要看看 GeForce 8800 GTX GPU 的时钟与规模，就能算出它具备 172.8 gigaflops 的能力（128 个处理器，每个 1.35 GHz，每个处理器每周期完成一次浮点运算）。乘加指令（MAD）每时钟周期执行两次浮点运算，把潜在性能翻倍。所幸 N 体代码中有若干处由编译器生成了 MAD 指令，把性能上限抬到远超 172.8 gigaflops 的水平。

反之，平方根倒数这类复杂指令需要多个时钟周期。CUDA 编程指南（NVIDIA 2007）指出，每个含 32 个线程的 warp 要按 16 个时钟周期来估算，是较简单运算所需时间的四倍。我们的代码每次相互作用用掉一条平方根倒数指令。

比较 gigaflops 时，我们只数高层代码里列出的浮点运算。数一遍 bodyBodyInteraction 代码（代码清单 31-1）中的浮点运算，可以看到九次加法、九次乘法、一次平方根和一次除法。除法和平方根显然比加法或乘法更费时，但我们仍各记作 1 次浮点运算，[2] 于是每次成对力计算共 20 次浮点运算。本章通篇用这个值把每秒相互作用次数换算成 gigaflops。

31.4.1 优化

我们的第一个实现在 16,384 个天体上达到 163 gigaflops。这是很好的结果，但还有几项优化可以提高性能。

循环展开带来的性能提升

第一项改进来自循环展开：把内层循环里单次天体–天体相互作用调用换成 2 到 32 次调用，以减少循环开销。小展开因子下的性能曲线见图 31-5。

我们检查了 CUDA 编译器为连续 4 次调用天体–天体相互作用函数而展开的代码。4 个内联调用共含 60 条指令，其中 56 条是浮点指令，包含 20 条乘加指令和 4 条平方根倒数指令。我们最好的期望是：循环中非平方根倒数的浮点指令需 52 个周期，4 条平方根倒数指令需 16 个周期，循环控制需 4 个周期，合计 72 个周期完成 80 次浮点运算。

若能实现这一性能，G80 GPU 每秒将完成约 100 亿次天体–天体相互作用（128 个处理器、1350 MHz，72 个时钟周期算 4 次天体–天体相互作用），即超过 200 gigaflops。对 N > 8192，我们观察到的正是这样的性能，见图 31-6。

块大小变化时的性能提升

另一个性能调优参数是 p 的取值，即瓦片大小。算法每个积分时间步取入的总内存量为 N 2/p，所以增大 p 能减少访存流量。GeForce 8800 GTX GPU 上有 16 个多处理器，因此 p 不能任意大，必须小到使 N/p 为 16 或更大，否则会有多处理器空转。

保持 p 较小的另一个原因，是线程块到多处理器的并发分配。当一个线程块只占用多处理器的一部分资源（如寄存器、线程槽和共享内存）时，多个线程块会被放到同一个多处理器上。这种做法让硬件有更多机会隐藏流水线指令执行与访存的延迟。图 31-7 给出 N = 1024、4096 和 16,384 时改变 p 的性能变化。

提升小 N 时的性能

我们最后实现的一项优化——每个天体用多个线程——试图改善 N < 4096 时的性能。随着 N 减小，每个天体一个线程已不足以充分遮盖 GeForce 8800 GTX GPU 上的全部延迟，性能迅速下降。因此我们在天体受力计算的每一行上使用多个线程，以增加活跃线程数。如果多出来的线程属于同一个线程块，访存请求数与 warp 数都会增加，延迟便重新被遮盖。当前的寄存器用量把 8800 GTX GPU 上每块线程数限制在 256（512 线程的块无法运行），所以我们把每一行拆成 q 段，保持 p x q ≤ 256。

拆分行带来了预期的收益。用两个线程分担工作，使 N = 1024 时的性能提高 44%。再继续细分，改善迅速变小。当然，对 N > 4096，拆分几乎无效，因为代码已接近峰值性能。所幸拆分行并未降低大 N 时的性能。图 31-8 用曲线展示了这些性能增益。

31.4.2 性能结果分析

评估改用 GeForce 8800 GTX GPU 带来的性能增益时，最令人意外也最令人满意的结果是 N 体算法相对 CPU 的加速比。这个差距远大于 GeForce 8800 GTX GPU 与 Intel 处理器之间峰值浮点速率的比较。我们推测主要原因在于，Intel 处理器的除法和平方根运算需要几十个非流水线时钟周期，而 GPU 有一条指令直接完成平方根倒数。Intel 的 Streaming SIMD Extensions（SSE）指令集包含一条四时钟周期的 1/sqrt(x) 指令（向量与标量），但精度只有 12 位。Intel 的一份技术报告（Intel 1999）提出一种在有限域上提高精度的方法，但代价估计为 16 个时钟周期。

31.5 以往用 GPU 做 N 体仿真的方法

N 体问题在计算技术发展的整个历史中一直有人研究。1980 年代提出了若干层次式与网格式算法，成功降低了 O(N 2) 复杂度。N 体问题的并行性也自并行计算机出现以来一直被研究。我们的回顾只限于与用 GPU 硬件获得高性能相关的先前工作。

2004 年我们用 Cg 和 OpenGL 为 GPU 构建了一个 N 体应用（Nyland、Harris 和 Prins 2004）。Cg 虽然提供了当时更强大的 GPU 编程语言，但在图形环境中构建这个应用有几处不便。所有数据要么只读要么只写，因此必须采用双缓冲方案。所有计算都通过绘制一个矩形来启动，其像素值由着色器程序算出，需要 O(N 2) 的内存。由于在图形 API 中编写复杂算法很困难，我们对所有成对加速度做了简单的暴力计算，写入一张大纹理，再用并行求和归约得到总加速度向量。由于缺少片上共享内存，这次求和归约完全受带宽限制。GPU 的最大纹理尺寸限制使我们一次能处理的天体数上限为 2048。用核外方法可以突破这个限制。

Stanford 大学的一个小组（Elsen 等 2006）用 BrookGPU 编程语言（Buck 等 2004）构建了与本章类似的 N 体方案，并在 ATI X1900 XTX GPU 上运行取得性能数据。他们的结论是循环展开能显著提升性能。他们还认为 N < 4096 时很难取得好的性能，并提出了与我们类似的解决办法，得到相近的改善。该小组把他们的 GPU 实现与高度调优的 CPU 实现（SSE 汇编，达到 3.8 gigaflops，这个指标我们达不到）作比较，观察到 GPU 比 CPU 快 25 倍。他们提供了代码（用 BrookGPU 编写），并分析了代码与硬件在做什么。他们所用的 GPU 硬件接近 100 gigaflops。他们还提醒我们，CPU 利用 f ij = -f ji 的对称性，把力的计算次数减少到 GPU 的一半。

GeForce 8800 GTX GPU 与 CUDA 发布以来，出现了若干 N 体应用的实现。引起我们注意的两个是 Hamada 和 Iitaka 2007 以及 Portegies Zwart 等 2007。两者都模仿 Gravity Pipe（GRAPE）硬件（Makino 等 2000），认为 GeForce 8800 GTX GPU 可以取代 GRAPE 专用硬件。它们的 N 体方法采用多时间步方案，不同天体的积分步发生在不同时刻，因此与这两种方法的对比只能通过比较每秒成对力相互作用次数来做。我们相信我们达到的性能约为所引工作的两倍。

31.6 层次式 N 体方法

许多实用的 N 体应用采用层次式做法，把空间递归划分为子区域，直到满足某个判据（例如该空间内天体少于 k 个）。叶单元内部的相互作用用全对方法处理，通常还加上一层或数层相邻叶单元。与更远子空间的相互作用使用远场近似。流行的层次式方法是 Barnes-Hut（Barnes 和 Hut 1986）与 Greengard 的快速多极方法（Greengard 1987；Greengard 和 Huang 2002）。

两种算法都必须决定如何与远处的叶单元相互作用。一般结果是，许多天体–单元或单元–单元相互作用仍需要全对解法来算力。算法的节省来自对远处天体产生的势做多极展开，而不是逐个与远处天体相互作用。

以三维为例，考虑 218 个天体（256 K）的仿真，分解为一棵深度为 3 的八叉树，含 512 个叶单元、每单元 512 个天体。一层深的最近邻域至少含 27 个叶单元，但实际很可能用得多得多。每个叶单元至少要算 27 x 512 x 512 次成对力相互作用，即每个叶单元超过 700 万次相互作用；在我们的实现中求解这些不到 1 毫秒。全部 512 个叶单元所需总时间不到半秒。

与此对比，我们的全对实现 [3] 运行在 Intel Core 2 Duo [4] 上，约每秒 2000 万次相互作用；同一计算估计需要约 90 秒（别忘了 CPU 只算一半的成对相互作用）。即便是每秒 1 亿次相互作用的高性能实现，也要 18 秒。减轻负载的一种办法是加深层次分解、更多依赖远场近似，使叶单元里的粒子更少。当然，树越深，远场部分的工作越多。

我们认为，从 CPU 转到 GPU 带来的节省不仅来自更强的算力，也来自叶单元尺寸变大，使层次分解更浅，从而在远场求值上也省时间。在后续工作中我们希望实现 BH 或 FMM 算法，以评估更高效算法带来的节省。

31.7 结论

很难想象还有哪个实际算法比全对 N 体算法更适合在 G80 架构上执行。本章展示了该算法帮助它取得如此高效率的三个特点：

  • 直接的并行性配合顺序访存模式
  • 数据复用让算术单元保持忙碌
  • 完全流水线化的算术，包括平方根倒数这类复杂运算，在 GeForce 8800 GTX GPU 上逐时钟比较远快于 CPU

结果是该算法的运行速度比高度调优的串行实现（Elsen 等 2006）快 50 倍以上，比我们的可移植 C 实现快 250 倍。在这个性能水平上，含大量粒子的三维仿真可以交互运行，为引力、静电或其他相互作用力系统提供三维可视化。
