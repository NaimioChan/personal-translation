AudioProcessorParameter() [2/2]

juce::AudioProcessorParameter::AudioProcessorParameter (int versionHint) inline explicit

传给此构造函数的版本提示用于 Audio Unit 插件，在未启用 JUCE_FORCE_USE_LEGACY_PARAM_IDS 时帮助对参数标识符排序。

当添加先前版本的 Audio Unit 中不存在的参数时，必须确保提供的版本提示高于任何先前插件版本中任何参数的版本提示。

例如，在插件的第一个发行版中，每个参数都以 "1" 作为版本提示创建。如果你在插件的第二个发行版中添加了一些参数，所有新参数的版本提示都应为 "2"。后续插件版本中添加的额外参数应使用 "3"、"4" 等，单调递增。

请注意，添加或移除版本提示低于所有参数最大版本提示的参数，会破坏某些宿主中已保存的自动化，所以要小心！

版本提示 "0" 将被视为未显式设置版本提示。面向 AU 格式时，调试构建中可能会在运行时检查版本提示，以确保其已设置。

理由：

根据 Apple's Documentation：

Audio Unit 参数由其作用域、元素和 ID 的组合唯一标识。

然而，Logic Pro 和 GarageBand 存在一个已知限制，导致它们使用参数索引而非 ID 来标识参数。其影响是：如果现有参数的索引发生变化，向插件的后续版本添加参数可能会破坏用早期版本保存的自动化。从将在这些宿主中使用的 Audio Unit 插件中移除参数是 always 不安全的，因为移除参数总会修改后续参数的索引。

为了绕过这一限制，AUv2 插件中的参数首先按版本提示排序，然后按其字符串标识符的哈希排序。只要插件后续版本的参数始终具有比早期版本参数更高的版本提示，自动化数据的召回在 Logic 和 GarageBand 中就会按预期工作。

请注意，我们不能直接使用 JUCE 参数索引来保持顺序。这将要求所有新参数都添加到参数列表末尾，从而使向现有参数组添加参数变得不可能。这也会使代码结构难以合理组织，抵消基于字符串的参数标识符的所有好处。

撰写本文时，AUv3 插件似乎也受同一问题影响，但该格式似乎没有任何 API 可以控制参数索引。因此，在构建 AUv3 插件时，如果你希望支持 Logic 和 GarageBand，则不得在后续插件版本中添加或移除参数。

setValue()

virtual void juce::AudioProcessorParameter::setValue (float newValue) pure virtual

宿主将调用此方法来更改参数的值。

宿主可能在任何时候调用此方法，包括在音频处理回调期间，因此你的实现必须非常高效地处理，并避免任何形式的锁定。

如果你想在内部设置参数值（例如从编辑器组件），则不要直接调用此方法 — 而应使用 setValueNotifyingHost() 方法，它还会向宿主发送一条告知更改的消息。如果不发送该消息，宿主将无法正确自动化你的参数。

传入的值将在 0 到 1.0 之间。

在 juce::LegacyAudioParameter 中实现。

setValueNotifyingHost()

void juce::AudioProcessorParameter::setValueNotifyingHost (float newValue)

处理器需要在更改其某个参数时调用此方法。

当编辑器或其他内部操作更改参数时，可能会发生这种情况。此方法将调用 setValue() 方法更改该值，然后向宿主发送一条告知更改的消息。

请注意，为确保宿主正确处理自动化，你应调用 beginChangeGesture() 和 endChangeGesture() 方法，在用户开始和停止更改参数时告知宿主。

void juce::AudioProcessorParameter::beginChangeGesture ()
