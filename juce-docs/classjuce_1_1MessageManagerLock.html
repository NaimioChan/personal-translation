juce::MessageManagerLock 类参考

详细说明

用于确保调用线程对消息循环拥有独占访问权。

由于从消息线程以外的线程调用任何 Component 或其他 UI 类都不是线程安全的，因此可以用其中一个对象来锁定消息循环，从而允许这样做。消息线程在 MessageManagerLock 对象的生命周期内会被挂起，所以像这样在栈上创建一个：

void MyThread::run()
{
    someData = 1234;

 const MessageManagerLock mmLock;
 // the event loop will now be locked so it's safe to make a few calls

    myComponent->setBounds (newBounds);
    myComponent->repaint();

 // the event loop will now be unlocked as the MessageManagerLock goes out of scope
}

显然要注意不要创建了却一直留着不用，否则你的应用会卡死！

MessageManagerLock 是可重入的，因此如果当前线程已持有锁，可以安全地嵌套。

另一个注意点是，把它与其他 CriticalSection 一起使用会产生许多有趣的死锁方式！尤其是，如果你的消息线程对一个使用了这些锁的线程调用 stopThread()，你会遇到（偶尔的）死锁。

MessageManagerLock() [1/2]

juce::MessageManagerLock::MessageManagerLock (Thread * threadToCheckForExitSignal = nullptr)

尝试获取消息管理器上的锁。

构造函数会尝试获取消息循环上的锁，该锁在此对象的生命周期内保持。

可选地，你可以在这里传入一个线程对象，在等待获取锁期间，此方法会持续检查该线程是否已被给予 Thread::signalThreadShouldExit() 信号。如果出现这种情况，它将不获取锁直接返回。如果传入了线程，你必须调用 lockWasGained() 来检查锁是否成功获取。如果为 false，说明你的线程被要求终止，此时应采取应对措施。

如果为线程对象传入 nullptr，它会无限期等待锁——这样做要小心，因为如果你的消息线程恰好在某个线程试图获取消息锁时对该线程调用 stopThread()，很容易死锁。

如果调用线程已持有锁，则什么也不做，因此递归使用这些锁是安全且快速的。

例如

void run()
{
    ...

 while (! threadShouldExit())
    {
 MessageManagerLock mml (Thread::getCurrentThread());

 if (! mml.lockWasGained())
 return; // another thread is trying to kill us!

        ...do some locked stuff here...
    }

    ...and now the MM is now unlocked...
}
