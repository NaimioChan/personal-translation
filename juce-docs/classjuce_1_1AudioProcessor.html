详细说明

音频处理类或插件的基类。

它旨在作为音频处理器的基类，足够通用，可以被包装为 VST、AU、AAX 等，也可以在内部使用。

插件托管代码也使用它作为已加载插件实例的包装器。

你应该从该基类派生自己的类；如果你在构建插件，还应实现一个名为 createPluginFilter() 的全局函数，该函数创建并返回你的子类的新实例。

processBlock() [1/2]

virtual void juce::AudioProcessor::processBlock (AudioBuffer < float > & buffer, MidiBuffer & midiMessages) pure virtual

渲染下一个块。

调用此方法时，缓冲区包含的通道数至少与本处理器正在使用的最大输入和输出通道数一样多。它将填入处理器的输入数据，并应替换为处理器的输出。

例如，如果你的处理器总共有 2 个输入通道和 4 个输出通道，则缓冲区将包含 4 个通道，前两个通道填入输入数据。你的处理器应读取这些数据，进行处理，并用其输出替换全部 4 个通道的内容。

或者，如果你的处理器总共有 5 个输入和 2 个输出，则缓冲区将有 5 个通道，全部填入数据，你的处理器应将其输出写入前 2 个通道并覆盖原有内容。但要非常小心，不要向最后 3 个通道写入任何内容，因为它们可能映射到宿主认为是只读的内存！

如果你的插件有多个输入或输出总线，则传递给 processBlock 方法的缓冲区将包含每个总线所有通道的集合。使用 getBusBuffer 获取特定总线的音频缓冲区。

请注意，如果输出多于输入，则只有那些与输入通道对应的通道保证包含合理的数据 — 例如在 2 个输入和 4 个输出的情况下，前两个通道包含输入，但后两个通道可能包含垃圾数据，因此你要小心，不要让这些数据未经覆盖或清除就通过。

另请注意，缓冲区的通道数可能多于严格必要的数量，但你只应读写处理器应使用的那些通道。

这些缓冲区中的采样数并不保证每次回调都相同，可能多于或少于传给 prepareToPlay() 的估计值。你的代码必须能够处理可变大小的块，否则会出现咔嗒声和崩溃！

另请注意，某些宿主偶尔会决定传入包含零个采样的缓冲区，因此请确保你的算法能够处理这种情况！

如果处理器接收到 MIDI 输入，则 midiMessages 数组将填入此块的 MIDI 消息。每条消息的时间戳将以距块起始位置的采样数表示该消息的时间。

此方法结束时仍留在 MIDI 缓冲区中的任何消息都被视为处理器的 MIDI 输出。这意味着，如果你的处理器不希望传入消息被继续传递，就应注意从数组中清除它们。

如果你实现了 getBypassParameter 方法，则需要在此回调中检查该参数的值，并在参数值为非零时旁路处理。

请注意，以宿主身份调用此方法时，结果仍可能被旁路，因为控制旁路的参数可能为非零。

在此回调中做什么要非常小心 — 它将由音频线程调用，因此任何形式的 UI 交互都绝对不行。如果你在此处更改参数并需要通知 UI 更新自身，最好的方法可能是继承 ChangeBroadcaster，让 UI 组件注册为监听器，然后在 processBlock() 方法中调用 sendChangeMessage() 发送异步消息。你也可以用类似的方式使用 AsyncUpdater 类。

或者，如果你的处理器有 5 个输入和 2 个输出，则缓冲区将有 5 个通道，全部填入数据，你的处理器应将其输出写入前 2 个通道并覆盖原有内容。但要非常小心，不要向最后 3 个通道写入任何内容，因为它们可能映射到宿主认为是只读的内存！

如果你的插件有多个输入或输出总线，则传递给 processBlock 方法的缓冲区将包含每个总线所有通道的集合。使用 getBusBuffer 获取特定总线的音频缓冲区。

请注意，如果输出多于输入，则只有那些与输入通道对应的通道保证包含合理的数据 — 例如在 2 个输入和 4 个输出的情况下，前两个通道包含输入，但后两个通道可能包含垃圾数据，因此你要小心，不要让这些数据未经覆盖或清除就通过。

另请注意，缓冲区的通道数可能多于严格必要的数量，但你只应读写处理器应使用的那些通道。

如果你的插件使用总线，则应使用 getBusBuffer() 或 getChannelIndexInProcessBlockBuffer() 来确定哪些输入和输出通道对应哪些总线。

这些缓冲区中的采样数并不保证每次回调都相同，可能多于或少于传给 prepareToPlay() 的估计值。你的代码必须能够处理可变大小的块，否则会出现咔嗒声和崩溃！

另请注意，某些宿主偶尔会决定传入包含零个采样的缓冲区，因此请确保你的算法能够处理这种情况！

如果处理器接收到 MIDI 输入，则 midiMessages 数组将填入此块的 MIDI 消息。每条消息的时间戳将以距块起始位置的采样数表示该消息的时间。

此方法结束时仍留在 MIDI 缓冲区中的任何消息都被视为处理器的 MIDI 输出。这意味着，如果你的处理器不希望传入消息被继续传递，就应注意从数组中清除它们。

如果你实现了 getBypassParameter 方法，则需要在此回调中检查该参数的值，并在参数值为非零时旁路处理。

请注意，以宿主身份调用此方法时，结果仍可能被旁路，因为控制旁路的参数可能为非零。

在此回调中做什么要非常小心 — 它将由音频线程调用，因此任何形式的 UI 交互都绝对不行。如果你在此处更改参数并需要通知 UI 更新自身，最好的方法可能是继承 ChangeBroadcaster，让 UI 组件注册为监听器，然后在 processBlock() 方法中调用 sendChangeMessage() 发送异步消息。你也可以用类似的方式使用 AsyncUpdater 类。

canApplyBusesLayout()

virtual bool juce::AudioProcessor::canApplyBusesLayout (const BusesLayout & layouts) const inline protected virtual

用于检查当前是否可以应用某种总线布局的回调。

大多数子类不需要重写此方法，而应重写 isBusesLayoutSupported 回调来拒绝某些布局更改。

当用户请求布局更改时，会调用此回调。仅当 AudioProcessor 的处理已被先前的 releaseResources 调用停止，或在 AudioProcessor 构造之后，才会调用它。它将在实际布局更改之前调用。通过返回 false，你将中止布局更改，setBusesLayout 将返回 false，表示布局更改未成功。

默认实现仅调用 isBusesLayoutSupported。

只有当你的 AudioProcessor 可能不接受某个布局，尽管你之前已通过 isBusesLayoutSupported 回调声称支持它时，才需要重写此方法。如果你的 AudioProcessor 支持的布局依赖于其他插件参数，而这些参数自上次调用 isBusesLayoutSupported 以来可能已更改（例如用户可在 AudioProcessor 编辑器中选择的音频文件格式），就会出现这种情况。此回调让 AudioProcessor 在条件已改变时获得拒绝布局的最后机会，因为它总是在实际布局更改之前被调用。

由于在 AudioProcessor 处理音频时绝不会调用它，它也可用于包装其他插件格式的 AudioProcessor，以将当前布局应用于底层插件。此回调让此类 AudioProcessor 在布局更改期间底层插件出错时有机会拒绝该布局更改。

canApplyBusCountChange()

virtual bool juce::AudioProcessor::canApplyBusCountChange (bool isInput, bool isAddingBuses, BusProperties & outNewBusProperties) protected virtual

用于查询当前是否可以添加/移除总线的回调。

当宿主调用 addBus 或 removeBus 时会调用此回调。与 canApplyBusesLayout 类似，此回调仅在 AudioProcessor 停止时调用，并给处理器最后一次机会拒绝请求的总线更改。它也可用于将总线数量更改应用于底层包装的插件。

添加总线时，isAddingBuses 将为 true，插件应填充 outNewBusProperties，填入在此回调成功返回后即将创建的总线属性。

AudioProcessor 的实现很少需要重写此方法。仅当你的处理器支持添加和移除总线，并且需要更细粒度地控制新总线的命名，或可能在 canAddBus 或 canRemoveBus 返回 true 时仍拒绝总线数量更改时，才重写此方法。

如果 canAddBus/canRemoveBus 返回 false（默认行为），则默认实现返回 false。否则，此方法对输入总线返回 "Input #busIndex"，对输出总线返回 "Output #busIndex"，其中 busIndex 是新创建总线的索引。此情况下的默认布局将与同方向前一个总线的布局相同。
