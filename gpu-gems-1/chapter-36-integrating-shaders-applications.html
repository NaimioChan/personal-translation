第 36 章　把着色器集成到应用程序中

John O'Rorke
Monolith Productions

36.1 引言

本章讨论在应用程序中加入着色器支持时涉及的问题，目的是提高灵活性、便于维护。本章不涉及处理着色器和着色语言的各个 API，而是从较高层面看待应用程序与着色器之间所需的通信层——正是它支撑起一个灵活、强大、数据驱动的渲染器。写这一章的动机很简单：在设计着色器驱动的渲染器时，我找到了大量关于编写着色器和使用相关 API 的文档。但没有任何材料讨论过，应用程序需要提供什么，才能稳健地处理不同的着色器。很多文章讲了如何从效果中取得变量名和标注，却从未提到应用程序该如何利用这些信息向着色器提供所需数据。要让应用程序以灵活的方式支持着色器，必须投入相当多的工作。本章试图逐项识别这些方面，并给出高效而强大的方案建议。

本章描述的管理着色器的技术，来自我个人的试错经验、与其他工程师的讨论，以及对执行类似任务的其他应用程序的分析。它们被设计成应用程序技术设计与所选着色器 API 之间的黏合剂。

36.2 关于着色器

在把着色器集成到应用程序之前，我们先考察它的作用。着色器的用途是规定一种渲染一组几何体的方式。如果放到合适的尺度上看，着色器让我们可以把渲染状态当作一种资源。这非常强大，因为它使应用程序的渲染器几乎完全由资源驱动。

过去，只有外部资源文件能控制渲染的某些方面，例如纹理和网格。如今有了着色器，连负责渲染实际几何体的设备设置也可以当作外部资源。这一技术长期惠及电影工业（借 RenderMan Shading Language 这类语言），也大幅提升了实时渲染的灵活性。这种着色器驱动的方式让渲染场景时可以有更多变化，因为不必往应用程序里加自定义代码。此外，它还让我们能方便地添加和维护更多渲染方法，并快速试验新效果和优化。将来随着更好的工具出现，这项能力甚至可能把渲染的完全控制权交给美术。

36.2.1 着色语言

实时着色语言已经种类繁多，将来必然还会出现更多。这些着色语言可以归为两类：单独的程序与效果文件。

单独的程序

单独程序的做法由一组文件构成，每个文件实现一次渲染所需的顶点着色器或像素着色器。例如 Cg 编程语言以及标准的顶点、像素着色器文件。此外，由于实现简单，许多自定义的着色语言实现也属于这一类。不过这种做法的缺点是：以此方式构建和管理大量复杂效果会变得困难，因为每一遍通常需要两个源文件，一个给顶点单元，一个给像素单元。

不过这一做法的主要问题在于：填充模式、剔除模式这类设备状态并不绑定到单个顶点或像素着色器程序上，因此很难用单独的文件来控制这些状态。设想一个对象要渲染两遍：第一遍是实心 Gouraud 填充，第二遍是平面线框颜色。这个简单的过程最多需要四个独立的着色器：两个给顶点单元，两个给像素单元。而且应用程序里还要有逻辑，在使用这些着色器时把第二遍渲染的设备填充模式改为线框。

可以看到，如果把某种渲染风格所需的全部程序整齐地打包成一个着色器资源，并让它能控制整个设备状态，那该多好。效果文件正是为此而生。

效果文件：为何要用

效果文件最流行的实现是 Microsoft 的效果框架（Microsoft 2003）与 NVIDIA 的 CgFX（NVIDIA 2003），后者是 Microsoft 效果框架的超集。效果文件的做法允许把一个个像素程序和顶点程序放进同一个文件。这些顶点与像素着色器随后可以编组成遍与技术。通过引入技术与遍这两个概念，效果文件允许按遍指定设备状态，因此相比一堆零散的顶点、像素着色器文件，这种做法更易管理、更由资源驱动，最终也更强大。代码清单 36-1 是一个效果文件的示例。

示例 36-1. 一个效果文件示例

// 我们的顶点格式
struct SVertex
{
  float3 Position : POSITION;
  float4 Color : COLOR0;
} ShaderVertex;
// 场景参数
float4x4 CameraTrans : WorldViewProjection;
// 材质参数
float4 FillColor : MaterialParam;
// 选定的渲染技术
struct SVSOut
{
  float4 Position : POSITION;
  float4 Color : COLOR0;
};
SVSOut Selected_VS(MaterialVertex IN)
{
  SVSOut OUT;
  OUT.Position = mul(CameraTrans, float4(IN.Pos, 1.0f));
  OUT.Color = FillColor * IN.Color;
  return OUT;
}
struct SPSOut
{
  float4 Color : COLOR;
};
SPSOut Selected_PS(SVSOut IN)
{
  SPSOut OUT;
  OUT.Color = IN.Color;
  return OUT;
}
technique Selected
{
  pass p0
  {
    CullMode = CCW;
    BlendEnable = false;
    VertexShader = compile vs_1_1 Selected_VS();
    PixelShader = compile ps_1_1 Selected_PS();
  }
}

本章余下部分将依据 Microsoft 与 NVIDIA 确立的标准，考察把效果文件纳入应用程序的技术。本章之所以使用效果文件，是因为效果文件提供的每一项功能——从协调每一遍该用哪些着色器，到设置设备状态——在任何要集成进应用程序的稳健着色器系统里都必须得到支持。

从个人经验出发，我建议使用这些效果系统，而不是自己造一套实现。用得得当，它们可以非常高效、非常易用，编写着色器快得多，也更不容易出错。使用这些着色语言的 API 也很容易上手，能显著缩短开发时间。此外，采用外部实现有助于应用程序面向未来，因为它把应用程序与底层平台相关的 API 隔离开来。不过在某些平台上，目前可能无法使用现成的 API，这种情况下就必须自行实现。即便如此，如果确实需要自制系统，也应当仔细研究效果文件标准，把它作为稳健、灵活着色器系统的模型基础。

36.3 效果文件的解剖

本节分析我们将要用到的效果文件的各个部分，逐一考察其中与着色器和应用程序之间通信相关的组件。本节不讨论效果文件格式的完整语法，只指出相关组件。

再次强调，即使不使用效果格式的系统，也可以并且应当设法包含等价的构造，以便集成到自己的应用程序中。

36.3.1 变量

效果文件中的变量与其他编程语言中的变量作用相同。每个变量有唯一的名字和关联的值，类型可以是字符串、结构体、多维数组等多种之一。全局作用域中的所有变量都可以由应用程序枚举，其值也可由应用程序读写。这些全局变量是向着色器传递数据的主要手段，例如该用哪张纹理，或者当前的相机变换是什么。

应用程序不仅能确定全局参数的值，还能确定每个变量的类型，这样在向着色器写出数据或从着色器读入数据时可以保证类型安全。效果文件中的全局变量带有一个其他语言里没有的关联标签，称为语义。语义是一个额外的文本符号，可以与变量关联，供应用程序查询。应用程序可以把语义用于任何目的，但它通常用来说明某个变量该怎么用，或者该变量需要什么数据。下面是一个带有名为 LightRadius 的语义的变量示例，应用程序可以在运行时读入它：

float Radius = 1.0 : LightRadius;

36.3.2 结构体

效果文件的结构体与 C 风格结构体类似。它们包含一组变量，结构体每实例化一次，这些变量就实例化一次。结构体中的每个条目也可以带语义，与全局参数很像。但应用程序不能直接访问结构体，关于结构体的信息必须通过它的一个实例来获取。所以，如果某个结构体的定义对应用程序很重要，就必须在着色器中定义一个该结构体的变量实例，再由应用程序检查这个变量。

36.3.3 遍

遍表示着色器在一次渲染中的设备状态，包含相关的顶点与像素管线设置。每个遍可以有一个唯一的名字，并可由应用程序访问。遍是渲染的原子单位。它最终是设备状态的来源；要渲染一个对象，就必须有一个活动的遍来说明该如何渲染它。

36.3.4 技术

以某种风格渲染往往需要多个遍，因此需要某种把遍分组的手段。这就是技术所扮演的角色。技术是一组遍的具名包装，是设备验证的原子单位。这意味着，当效果 API 检查某个设备是否支持时，技术中的每个遍都会被检查能否在该设备上运行。只要有一个遍不被该设备支持，整个技术就被视为在该设备上不受支持。正是出于验证的考虑，遍不能存在于技术之外。运行时，技术还支持遍历其中包含的每个遍，并访问每个遍的信息。

36.3.5 标注

标注是附着在效果文件的技术、遍和全局变量上的用户数据。标注让着色器作者可以提供额外的数据，这些数据可以从着色器导出；其形式为 type name = value; 。应用程序随后可以查询任何技术、遍或参数的标注。运行时，每个标注都可以查询名字、类型和值。这些标注是常量，应用程序只能只读地查看。下面的代码是一个标注示例：

float Alpha = 1.0 < string Description = "Opacity of the object";
> ;

36.4 着色器数据的类型

我们已经找出了可用于着色器与应用程序之间通信的基本构件，但还没有说明需要传递哪些信息。本节辨识信息本身；把这些信息传入和传出的技术稍后讨论。图 36-1 是数据在应用程序与着色器之间如何互通的总体示意。

36.4.1 场景信息

必须由应用程序传给着色器的第一类数据是场景信息。场景信息包含渲染某个着色器所需的任何渲染状态，实际上充当应用程序与着色器之间的契约。着色器必须知道，它可以依赖应用程序通过特定变量提供某些信息，才能完成自己的任务。没有这些场景信息，着色器就在真空中运转，连最简单的操作也做不了。

场景信息的例子包括物体空间到裁剪空间的变换、骨骼变换、相机位置、当前物体颜色，以及应用程序维护的其他与着色器相关的数据。这些数据是单向的，从应用程序流向着色器；每次场景信息变化，都必须在着色器中更新。

36.4.2 材质

场景信息涵盖的是应用程序生成的信息，但不包括一组关键的数据——正是它让着色器可以被定制。这类数据包括着色器中任何参数化、可交美术控制的方面。例如着色器要用的纹理、表面的镜面反射强度，或者滚动纹理的速度。材质数据的传递比场景信息更双向。因为着色器定义了材质可以提供的变量，这些变量必须由某个应用程序或工具读取出来；然后材质为这些变量定义取值，取值又必须传回着色器。

材质通常以下面的方式嵌入内容创作与渲染管线：工具检查着色器，确定哪些值应作为材质参数提供给着色器，然后让内容创作者指定这些参数。渲染时，当某个材质被激活，它就把美术在着色器中填入的所有值填好。这一流程让着色器可以拥有各自独特而多样的数据，而这些数据能被内容创作者直接、方便地控制。

36.4.3 渲染器上下文

到目前为止，传给着色器的所有信息都来自变量。但有时着色器需要完成无法用数据驱动的任务。为解决这个问题，引入了上下文的概念。

上下文让着色器可以针对不同情况采用不同类型渲染。设想一个应用程序，场景里有一大堆着色器。每个着色器有自己的外观，按特定方式渲染。但应用程序需要一种效果，在用户选中的任何对象上播放，同时又必须让每个着色器保持自己的独特外观。因此着色器必须有上下文的概念，在这里就是两种状态之一：「选中」或「未选中」。着色器随后可以基于当前上下文执行完全不同的渲染技术。

36.4.4 顶点数据

着色器需要的另一种数据当然是顶点数据本身。不同的着色器可能要求差别很大的信息，所以着色器必须能指明自己需要哪些顶点分量。例如，凹凸贴图着色器可能需要每个顶点一个完整切线空间和一组纹理坐标，而另一个着色器可能只需要位置、法线和两组纹理坐标。如果每个着色器都能指明所需的分量，应用程序就可以只生成必要的顶点分量，从而节省带宽和内存。

36.5 与着色器通信

现在我们已经辨识出需要送往着色器并从着色器取回的数据，以及可用于这种通信的手段，接下来考察搭建应用程序以支持着色器的过程。

36.5.1 场景信息

第一个问题是如何把场景信息送给着色器。着色器如果没有正确的变换和其他必需数据，什么也做不了。这些数据将通过全局变量传给着色器，因为这是着色器从应用程序获得取值的唯一通信方式。窍门在于找出着色器中预期承载所需场景信息的那些变量。

使用变量名

确定哪些变量应承载场景信息，最直接的做法就是用全局变量的名字和类型。例如，应用程序可以枚举着色器中的全局变量，当它发现一个名为 CameraTransform 的 4x4 矩阵变量时，就把相机变换矩阵装入该变量。

这种做法要求所有着色器保持一致，因为要让其正常工作，应用程序使用的所有着色器在变量命名上必须一致。对大型着色器库来说，如果由不同的人编写或维护，这种方法是有用的。

使用语义或标注

更灵活的做法是使用与全局变量关联的语义或标注。例如，标注里可以有一个键值对，形如 string Usage = "CameraTransform"。或者变量可以带一个指明用途的特定语义。运行时读取这个用途值，就能确定该往变量里装入什么值。

这种做法更灵活，因为它让着色器作者随意命名变量，只要正确指明用途即可。FX Composer（由 NVIDIA 开发）就采用语义的做法。（见第 31 章「使用 FX Composer」。）下面的变量声明示例使用了可与 FX Composer 配合的语义，在运行时接收相机变换：

float4x4 wvp : WorldViewProjection;

优化场景通信

把变量解析到它的值可能代价很高，因为这可能涉及遍历大量变量并执行许多字符串操作。所以，这种映射只应在创建着色器时做一次。当前所有效果 API 都支持句柄，可以直接访问变量、技术、遍乃至标注。但这些句柄不能在着色器之间传递，所以无法创建一个句柄来跨所有着色器指向某个特定变量。相反，必须为每个着色器中的每个变量各创建一个句柄。这种缓存机制的一种简单实现是为每个着色器建一张句柄表，表中每个条目指向一个特定变量。这样，当场景信息中的某个值变化时，可以直接按正在设置的变量去索引当前活动着色器的句柄表，找到相应句柄，再用它把新数据传给着色器。此外，当前活动的着色器切换时，所有场景信息都必须在新着色器中重新设置。做法是遍历句柄表，为每一项场景信息提供对应的数据。

36.5.2 材质参数

与场景信息参数一样，材质参数也要传给着色器；但与场景信息不同的是，这些数据通常来自内容创作者设置好的材质资源。因此必须有某种机制，把数据从资源映射到着色器的全局变量中。对材质参数来说，用名字并不是好办法，因为材质参数在不同着色器之间差别很大，而且往往只与某一个着色器相关。

改用标注或某个表示材质参数的语义。这样，凡带有特定标注或语义集的变量都当作材质参数处理，允许在材质中为其指定取值。

标注还可以改造用于材质参数的许多其他目的。字符串标注可以为工具提供参数说明，方便给出帮助信息。或者在没有值时指定一个默认值。标注中需要哪些信息，取决于应用程序打算支持的功能，但一般来说，最好至少为每个变量准备一个默认值和一段说明。下面的示例展示了如何设置一个材质参数，用语义表明它是材质参数；标注则提供可供材质创作工具或运行时应用程序使用的信息。

float Specular = 4.0 : MaterialParam < float Default = 4.0;
string Desc = "Specular power of the surface";
float Min = 2.0;
float Max = 8.0;
> ;

36.5.3 顶点格式

确定某个着色器需要哪些顶点数据，有很多不同办法。第一种是专门用变量名来表明不同的顶点分量。例如可以有一组预定义的变量名，如 Vertex_Normal、Vertex_Position 等。然后检查每个着色器包含哪些变量，对其中每一个，把相应的顶点信息加入该着色器渲染的所有顶点。

更优雅的做法是建立一个结构体，为每个需要的顶点元素设置一个条目。这些变量的名字或它们关联的语义，可用来确定所需的顶点分量。这大概是最直观的方法，因为顶点数据的概念很适合用结构体表达，而且多数着色器本来就用某种结构体来表示传入的顶点数据。唯一需要注意的是结构体不能被直接检查，因此必须定义一个该结构体的实例。示例如下：

struct SVertex
{
  float3 vPosition : Position;
  float3 vNormal : Normal;
};
SVertex VertexDecl;

指定所需顶点数据的其他一些可能做法：用一个包含可解析的分隔分量列表的字符串变量，或者用一个变量并通过标注来指明各分量。

用上述任一方法，我们都能确定着色器要渲染的任何几何体中每个顶点需要提供哪些信息。如果在预处理时就知道将绑定到该几何体的着色器，这些数据就可以在预处理阶段使用，从而只生成并打包着色器需要的那些顶点分量。这种做法能大幅减少多数着色器存储几何体所需的内存，同时仍能支持需要复杂顶点信息的着色器。但如果预处理时不知道着色器，我们就得使用包含所有可能顶点数据的顶点格式，或者需要运行时支持来生成顶点信息，这两者都不是最优方案。

36.5.4 上下文

上下文的概念直接对应到技术。应用程序需要多少个上下文，就要在着色器中放入多少个对应的技术。沿用前面那个上下文的例子：应用程序要求每个着色器在对象被选中时以不同风格渲染。着色器里可以有两个不同的技术：Selected 和 Unselected。到了渲染该对象的时候，根据对象状态激活相应的技术，然后按该技术进行渲染。这让每个着色器都能为应用程序所需的任何上下文实现合适的渲染风格。此外，它也让应用程序能确保着色器改变其运作方式，以适应所需的任何情形。不过要做到这一点，着色器与渲染器之间必须存在契约。它的运作方式很像场景变量：渲染器在特定情形下调用某个上下文，以某种方式渲染，作为回报，着色器应在每种情形下正常工作。但着色器与渲染器之间的这份契约取决于各个应用程序，这也使这种上下文绑定方法具有很强的应用特定性。

36.5.5 用于上下文的技术与遍之比较

可以主张用遍而非技术来表示着色器中的上下文。理由是什么？技术是作为整体验证的，因此可以避免出现某个上下文验证通过而另一个上下文失败的情况。那种情况会让对象在一个上下文里可见，在另一个上下文里却不可见。

用遍来表示上下文会增加工作量，也多少降低清晰度，但可以通过对遍名使用命名约定来轻松实现。命名约定应表明上下文名和遍编号。下面的代码是一个包含两个上下文的技术示例，其中 Selected 上下文需要两个遍：

technique SomeShader
{
  pass Selected_0{...} pass Selected_1{...} pass Unselected_0 { ... }
}

然后，当应用程序加载着色器时，会为当前设备找到一个有效的技术，并解析其中的遍。解析确定了在某个上下文被使用时，需要渲染哪些遍、以什么顺序渲染。这种做法使在同一着色器文件内加入回退支持变得更容易。在支持各种硬件时，我们推荐这种做法。

36.6 扩展效果文件格式

用本章讨论的方法，我们可以把完整的着色器系统集成到应用程序中，做出非常强大而灵活的渲染器。不过，我们还可以给应用程序和着色器再加几项扩展，让着色器的开发和管理轻松得多。

36.6.1 支持预处理器

为着色器提供预处理器支持的应用程序极有价值。只要应用程序为 include 指令提供某些钩子，当前所有效果 API 都允许支持预处理器。这些钩子让应用程序可以实现自己的文件系统，而添加对钩子的支持通常很简单。一个重要考虑是当前工作目录，它被定义为相对于当前正在编译的文件。

一旦应用程序加入了预处理器支持，就能很快建起一个完整的工具函数库，包含标准定义和函数。这有助于减小单个着色器的体积和复杂度。例如，我们可以创建一个包含着色器蒙皮工具函数的文件。任何需要蒙皮的着色器都可以包含这个文件，从而减小每个着色器的体积，减少着色器之间重复的代码。

36.6.2 支持着色器变体

只要设置得当，预处理器可以让同一个着色器同时用于刚体对象和蒙皮对象。蒙皮网格与刚体网格的唯一差别，在于与几何相关的数据（包括顶点位置和切线空间）的获取方式。因此在刚体网格中，几何数据按顶点中指定的值使用；而在蒙皮网格中，顶点数据使用前必须先经过蒙皮处理。于是，对所有几何信息的访问都可以藏在条件编译的代码后面：要么对顶点数据执行蒙皮，要么直接返回存储的顶点数据。

此外还需要骨骼权重数据（可能还有骨骼索引数据）。这可以用宏来添加：对刚体着色器，宏展开为空；对骨骼着色器，宏展开为声明顶点数据所需的相应定义。这样只需开发一个着色器。用不同的预处理器定义来编译它，就能让它支持蒙皮网格或刚体网格，如代码清单 36-2 所示。

示例 36-2. 用预处理器支持骨骼着色器变体

#ifdef SKELETAL
// 在顶点结构体中用于指示该顶点的权重
#define DECLARE_SKELETAL_WEIGHTS float4 Weights : BLENDWEIGHT
// 凡是需要从顶点访问点数据的地方都用到它
#define SKIN_POINT(Point, Vert) SkinPoint(Point, Vert.Weights)
// 凡是需要从顶点访问向量数据的地方都用到它
#define SKIN_VECTOR(Vector, Vert) SkinVector(Vector, Vert.Weights) #else
// 我们不支持骨骼动画
#define DECLARE_SKELETAL_WEIGHTS
#define SKIN_POINT(Point, Vert) (Point)
#define SKIN_VECTOR(Vector, Vert) (Vector) #endif

对渲染的灯光数量也可以采用类似做法。可以用一个宏定义支持的灯光数，着色器只需迭代到该宏指定的数量。这样只用一个着色器源文件就能得到众多灯光变体。

36.6.3 加入着色器继承

另一项有用的扩展是继承的概念。想法是：如果某个着色器无法通过验证，或者需要用更省的着色器，就可以用一个回退着色器替换指定的着色器。这可以在全局层面实现，用一个字符串参数指明该着色器将回退到哪个着色器文件。也可以在每个技术层面实现，用相应的标注指定回退着色器。不过，如果着色器使用了继承，其材质参数和顶点声明就必须取它派生自的所有着色器与自身数据的并集，因为事先并不知道什么时候会用到回退着色器。

继承的实现通常很简单，却能大幅提升硬件的可伸缩性和性能。将来这一点会越来越重要，因为市场上的硬件能力必然差距悬殊。

36.7 结论

开发支持着色器的通信层需要投入相当多的工作。不过只要遵循这些准则，任务就很直接，而且能得到一个极其灵活、强大的渲染器。

着色器是实时渲染的未来。现在就把着色器集成到渲染管线中，能让应用程序在能力和灵活性上再进一步。这样做不仅让应用程序更具竞争力，也能简化渲染器的开发，并容纳各种各样的效果。
