第 33 章　把制作级 RenderMan 着色器转为实时着色器

Stephen Marshall
Sony Pictures Imageworks

33.1 引言

自 20 世纪 80 年代末以来，视觉特效公司一直使用着色语言为电影行业生成令人信服的图像。这些着色语言极其强大，但为了产出有新意的图像所需的复杂度，往往导致渲染时间漫长。此外，随着对更大更好效果的需求，这些着色器的复杂度也在增加。

如果渲染每帧要花上几个小时，那么能以最少的时间可视化逐步的改动就至关重要。因此，视觉特效公司正在考虑用实时游戏技术来做优化的可视化。尤其是图形硬件技术近来的进步与硬件着色语言的发展，在实时效果与制作级效果之间建立起了可辨认的对应关系。

本章说明把 Pixar RenderMan 表面着色器转换成硬件着色器是可行的。所用的硬件着色语言是 Cg。使用 Cg 并不限制本章的范围，因为 Cg 编译器能生成许多不同形式的着色器指令，包括符合 OpenGL ARB_fragment 程序规范的代码。详见 NVIDIA 2002。我们提出的概念同样适用于其他着色语言。

本章提到的每个代码清单都能在本书附带的 CD 或网站的相应子目录中找到。例如，包含 Stuart Little 毛发着色器的代码清单 33-1 就在第 33 章的 listing1 子目录中。

33.1.1 以实例讲解转换

本章始终以电影 Stuart Little 中的 RenderMan 毛发着色器为例，讲解如何把 RenderMan 着色器转换为 Cg 程序（毛发着色器的描述见 Berney 与 Redd 2000）。涉及的主题如下：

  • 与频率无关的问题，特别是多光源的处理
  • 顶点程序与片元程序的比较，重点关注硬件相关的优化（这对良好性能是必需的）
  • 对结果的分析，涵盖原始 Cg 着色器与其优化版本之间的差异，以及 Cg 与 RenderMan 结果之间的差异

33.2 光源

截至本文写作，在编写 Cg 代码时，光源及其处理方式可以说是与 RenderMan 规范偏离最大的部分。因为这些 RenderMan 构造没有对应的映射。本节讨论光源与光源着色器。

33.2.1 光源

在 RenderMan 中，光源由 illuminance 语句遍历。illuminance 语句让表面着色器在被着色点处对场景中所有光源采集样本。除光源颜色和光方向向量之外的额外信息，可以通过消息传递在表面与光源之间交换。关于这一主题的更多信息见 Upstill 1990。

RenderMan 毛发着色器代码中唯一的 illuminance 语句是：

// RenderMan illuminance 语句 illuminance (P, norm_hair,
// radians(illum_width))

这条语句表示，下面的代码会对场景中满足 illuminance 条件的所有光源执行。遗憾的是，Cg 中没有等价的语句。在编写着色器之前必须先知道场景中的光源数量。而且每个光源可能都有一组相似的参数，只是取值不同。例如，如果场景中所有光源都是简单的方向光，参数表中每个光源至少需要一个光方向向量。如果场景中有十个光源，参数表可能长这样：

// Cg 着色器参数列表示例 Output cgProgram(Input In,
uniform float3 lightDir[10],
    ..., // 其他程序参数

可以循环遍历这十个光源，但这样做不灵活。如果需要多于十个光源，就必须修改 Cg 程序。

另一种做法是以多通道方式执行程序。如果所有光源参数相似，就只把当前光源的参数绑定到当前渲染状态。该通道的结果随后累加到帧缓冲中。这样 Cg 程序就无需指定场景中的光源数量。现在这项工作交给应用来管理。这还有个好处，就是能把 Cg 程序的参数表简化为：

// 考虑多趟渲染的 Cg 着色器参数列表示例 Output
cgProgram(Input In,
uniform float3 lightDir,
// 其他程序参数

注意，虽然这解决了重写 Cg 程序的需求，但多次运行程序的通道必然带来性能损失。场景中光源数量增加时，如果 Cg 程序复杂，就应预期应用性能显著下降。

33.2.2 光源着色器

同样，Cg 中也没有与 RenderMan 光源着色器概念等价的语句。对光源着色器可以作与光源类似的假设——场景中所有光源共享同一个着色器。

对制作使用来说，这看起来可能是个严重限制。然而，常见做法是有一个主光源着色器，把全部可用的光照参数都封装进去。可以写一个 Cg 函数来实现这个通用的复杂光照公式。关于这一主题实现的更多信息见 Barzel 1997 与 Gritz 1998。

33.2.3 额外的光照参数

复杂的光源着色器可能给 Cg 程序加上许多参数。着色器预处理器通过定义多个光源着色器参数表，可以管理这种复杂度，也有助于可读性。下面定义了两个表，用来简化程序的参数表：

// uber_light 参数列表
#define DEFINE_UBER_LIGHT_PARAMS
uniform float3 lightColor, uniform float lightIntensity,
    uniform float lightConeInner, uniform float lightConeOuter,
    uniform float lightConeRoundness,
    ...
// uber_light 的参数
#define UBER_LIGHT_PARAMS
    lightColor,
    lightIntensity, lightConeInner, lightConeOuter, lightConeRoundness, ...

Cg 着色器入口点随后可简化为：

// 考虑多趟渲染的 Cg 着色器参数列表示例 Output
cgProgram(Input In,
DEFINE_UBER_LIGHT_PARAMS,
// ...,
// 其他程序参数

cgProgram 块中对光源实现的调用可能长这样：

// 考虑多趟渲染的 Cg 着色器参数列表示例
float3 lightColor = uber_light(UBER_LIGHT_PARAMS,
. . . , // 其他参数

最后，RenderMan 中的消息传递机制必须替换掉。这很简单，因为着色器已经知道当前光源的参数值。这些参数值封装在前面 Cg 程序的参数表定义中。

33.3 顶点程序与片元程序

编写 Cg 程序（而不是 RenderMan 着色器）涉及不同的计算频率概念。RenderMan 中着色器的执行率由 ShadingRate 参数控制（Apodaca 与 Gritz 2000）。这个参数是一个浮点值，指定一个着色样本可以代表多大的面积（以像素计）。

与之相对，GPU 中着色发生的频率由所用的程序类型决定。例如，顶点程序的所有操作都在从 API（OpenGL、Microsoft DirectX 等）传给 GPU 的顶点数据上执行。而片元程序的所有操作都在与最终图像中像素直接相关的图元上执行。

在硬件上，顶点程序与片元程序未必具有相同的能力。很多情况下，这些程序必须协同工作，才能提供单个 RenderMan 表面着色器所提供的功能。顶点程序接管图形管线中的变换与光照部分。因此，至少必须为输入顶点提供齐次裁剪空间位置。所以管线的变换部分必须手动完成：把模型视图投影矩阵传给程序，变换传入的顶点，并把新的顶点位置赋给输出顶点位置寄存器。这与 RenderMan 不同，因为在 RenderMan 中除了最终颜色不必操心着色器的输出。

与之相对，片元程序接管图形管线中的多重纹理部分，因此任何纹理操作都必须手动完成。执行片元程序的结果是该片元的颜色，可能还有新的深度。这个新颜色必须绑定到输出颜色寄存器。

Cg 是与硬件无关的语言。只有通过硬件配置，编译器才知道自己是为哪个平台构建。关于硬件限制的更多细节见 NVIDIA 2002 的附录 B。建议读者在编写硬件着色器之前阅读并理解这些细节。

33.4 使用顶点程序与片元程序

如前所述，通常需要同时编写顶点程序和片元程序，才能实现与 RenderMan 着色器相同的功能。在我们的毛发例子中，顶点程序为光栅化过程做准备，着色计算则在片元程序中实现。代码清单 33-2 给出了一个顶点程序的初步实现，用于为片元程序准备好光栅化器。

顶点程序处理两类数据。第一类是在顶点程序中生成的属性值。例如片元着色器需要的光方向（L）和视线方向（V），都取决于输入顶点的位置。由于这种依赖关系，这些值在运行时于顶点程序中计算。

其他逐顶点数据可以以数据流的形式经顶点着色器传给片元着色器。这些属性直接传递并赋给顶点程序的输出，不再做进一步处理。在我们的毛发例子中，这些属性是归一化的毛发切线（T）、毛发参数值（v）和表面法线（nSN）。这类似于在 RenderMan 中给几何体赋额外的图元变量。RenderMan 与顶点程序的区别在于，RenderMan 中可以通过插值方案生成这些值（例如对 NURBS 曲面控制点上指定的数据做插值）。顶点程序只是接收从应用传入的、未插值的数据。

GPU 的数据插值发生在片元程序之前的片元光栅化阶段。用户无法控制中间片元值如何计算。通过标准图形管线传递的值沿扫描线做线性插值。这意味着输入几何体的采样率会影响图像的最终质量。

最后一个组成部分是片元程序本身，大部分着色计算在这里进行。代码清单 33-3 给出了 Cg 片元程序，它与原来的 RenderMan 着色器几乎完全相同。初步转换非常容易，因为 Cg 提供了许多与 RenderMan 相同的标准库函数。唯一重要的差别是与顶点程序的交互、程序类型名称不同，以及引入了 saturate、dot 和 cross 函数。saturate 函数开销极小，在需要把值限制在 0 与 1 之间时应使用它。dot 和 cross 函数用于替代 RenderMan 着色语言中的 . 和 ^ 运算符。

33.5 片元程序的优化技术

当前片元程序的实现看起来可能够用了；不过它会跑得很慢。起初这也许让人失望，但要记住 GPU 不是普通处理器。虽然转换毛发着色器很容易，但并没有考虑硬件的架构。GPU 由两个处理器组成：顶点处理器和片元处理器。最好尽可能在顶点处理器中做计算，因为它只在每个顶点上执行，而模型中顶点数通常远少于最终图像中的片元数。顶点处理可以辅以片元程序中的一定量高质量处理，因为片元程序在所有生成的片元上执行——无论可见与否。另外，在交互过程中不变化的计算应移到应用层；每次执行顶点或片元程序都重新计算它们是浪费。

考虑 GPU 的向量化特性也很重要。一般来说，GPU 执行一组四条算术指令的时间与执行一组一、二、三条指令相同。着色器源码应组织得有助于编译器识别并针对这些情形优化。最后，由于 GPU 上的纹理贴图查找极其高效，1D、2D 和 3D 纹理可以分别用作一、二、三个变量的复杂函数的查找表。

目标是缩减片元程序的规模。一般来说程序越短，执行越快。如果使用 fp30 配置，我们原始片元程序编译后的大小为 104 条指令。如果用户对硬件有更深入的理解，就能在规模上缩减并提升效率。

33.5.1 把代码移到应用层

在片元程序的第一部分，可以明显看出即使视线或光源变化，这段代码也不变：

// Fragment Program 的代码行
float3 S = cross(IN.nSN, IN.T);
float3 N_hair = cross(IN.T, S);
float l = saturate(dot(IN.nSN, IN.T));
float3 hairNorm = normalize((l * IN.nSN) + ((1.0f - l) * N_hair));

因此这部分可以移到应用层，新的属性 hairNorm 会被传给顶点程序。

33.5.2 把代码移到顶点程序

接下来那组点积计算不能移到应用层，因为 L 和 V 向量分别取决于光源位置与眼位置：

float T_Dot_nL = saturate(dot(IN.T, IN.L));
float T_Dot_nV = saturate(dot(IN.T, IN.V));

不过这组计算可以移到顶点程序，因为对于由单段曲线生成的各个片元，这些向量通常变化缓慢。一般来说，沿曲线的采样率越高，这种插值引入的误差越小。

33.5.3 通过纹理查找优化

Kajiya-Kay 毛发着色模型包含一些基于两个变量 T_Dot_nL 与 T_Dot_e 的复杂函数的项。

float Alpha = acos(T_Dot_nL);
float Beta = acos(T_Dot_e);
float Kajiya = T_Dot_nL * T_Dot_e + sin(Alpha) * sin(Beta);

更详细的推导见 Kajiya 与 Kay 1989。

这一组看起来是纹理查找的理想候选。可以为这个应用生成一张浮点纹理。随后就能在两个自变量上以 0 到 1 的区间采样该纹理函数。

可以用与上一节类似的分析来确定函数查找的采样率与合适的纹理尺寸；不过那样过于复杂。取而代之，可以写一个单独的程序，用一个简单的片元程序计算函数纹理查找与完整计算 Kajiya-Kay 各项之间的差。这个差可以显示为最终片元的颜色。通过简单的目视比较就能选出误差最小的合适纹理尺寸，如图 33-1 所示。

现在可以通过这次查找得到纹理中的 Kajiya-Kay 各项：

float2 Kajiya = texRECT(kajiyaTexture, IN.dots);

注意，33.5.2 节中在顶点程序里算出的点积被用作纹理查找参数。还要注意这里用 texRECT() 函数做纹理查找。因此纹理查找必须在未归一化的纹理空间中完成。做法是把纹理查找参数（顶点程序中的点积）乘以 Kajiya-Kay 纹理的尺寸。

33.5.4 针对向量化优化

下面的幂函数计算着色项中的镜面反射分量：

float3 Cspec = (spec.x * lightColor * pow(Kajiya, iroughness.x)) +
               (spec.y * lightColor * pow(Kajiya, iroughness.y));

这个函数可以重新排列，以利用乘法的向量形式。具体来说，幂函数的结果可以与 spec 各分量并行相乘：

float2 powVal = spec * pow(Kajiya, iroughness);
float3 Cspec = lightColor * powVal.x + lightColor * powVal.y;

33.5.5 最终优化

着色项的漫反射分量计算在函数 fnc_diffuselgt 中完成，该函数定义在代码清单 33-3 的开头。这个函数也用到了光方向与毛发法线之间的点积。由 33.5.2 节的点积分析可知，这个函数可以移到顶点程序中。传给片元程序的 varying 属性名为 dComp。

Kd 乘法与 final_c 计算（减去变暗项）可以移到顶点程序以提升性能。Kd 必须乘以先前已移到顶点程序的漫反射分量。中间的毛发颜色值存放在 varying 属性 hairCol 中。顶点程序代码现在长这样：

OUT.hairCol = ((1.0 - IN.v) * rootColor) + (IN.v * tipColor);
OUT.dComp = saturate(dot(lDir, IN.hairNorm)) * Kd;

最后，看完整的片元颜色：

OUT.col.xyz = saturate((Kd * Cdiff + staticAmbient) * final_c +
                       (In.v * Kspec * Cspec * specularColor));

IN.v * Kspec 的计算可以移到顶点程序，镜面反射值可以存放在 varying 属性 specColor 中，得到：

OUT.col.xyz = saturate((Cdiff + staticAmbient) * final_c +
                       (In.specColor * Cspec * specularColor));

注意没有使用条件语句来消除不必要的计算。遗憾的是，当前 GPU 在片元程序中不原生支持条件代码。因此无论条件结果如何，条件语句的 if 与 else 两个分支都会被计算。条件语句没有性能收益（甚至可能因它变慢），所以计算应改用更复杂的版本。

33.6 结果与结论

本应用在配备 2.8 GHz Xeon 处理器的 Intel Pentium 4 上运行，并在 Linux 上用 NVIDIA Quadro FX 2000 与 NVIDIA Quadro 4 980 测试。使用 Cg 1.1.0003 版编译器生成 27,488 条 b 样条曲线，每条有十个均匀采样点。

虽然从 RenderMan 着色器到片元程序的转换很直接，最初的性能却令人失望。不过，通过本章讨论的各种优化技术，片元程序的规模从 104 条指令减到 42 条。这显著提升了性能。优化对图像质量作了一些让步。但这些差异在实践中并未被发现。

图 33-2 与图 33-3 分别显示片元程序的原始版本与优化版本，图 33-4 显示两个版本所生成图像之间的差异。可以看到差异可以忽略。

同样有意思的是片元程序与 RenderMan 所生成渲染结果之间的差异。使用相同的曲线几何体，图 33-5 用 Pixar 的 PRMan 渲染耗时 20 秒。虽然片元程序的图像与 RenderMan 图像略有不同，但 RenderMan 图像中所有重要的高光与颜色变化都出现在片元程序图像的正确位置上。很容易看出，硬件版本用一小部分时间就给出了对 PRMan 渲染的合理近似。

制作级角色往往有数百万根毛发。即使经过剔除，仍有数十万根毛发需要着色。优化后的片元程序对这类角色来说太慢，所以我们在顶点程序中实现了完整的毛发着色器，如代码清单 33-4 所示。结果见图 33-6。虽然这种做法不如片元程序精确，性能提升却很显著。

注意，如果着色器作者做了手工优化，片元程序就与原来的 RenderMan 表面着色器差别很大。如果之后必须修改原来的 RenderMan 着色器代码，可能不容易判断硬件着色器中该改哪一段代码才能做出等价改动。这意味着作者必须非常了解 RenderMan 的工作方式，也要非常了解硬件着色器的工作方式。

本章没有提到 RenderMan 的着色算子（shadeop）。着色算子是用 C 或 C++ 编写的用户自定义函数，为标准库添加功能。它的形式是用户创建的共享库，由 RenderMan 渲染器在运行时动态载入。问题在哪？当前 GPU 不允许这种可编程性。如果着色算子的参数表能简化，33.5.3 节所述的纹理查找方法或许可以替代它。
