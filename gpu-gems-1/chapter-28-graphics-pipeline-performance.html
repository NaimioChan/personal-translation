第 28 章　图形管线性能

Cem Cebenoyan
NVIDIA

28.1 概述

过去几年里，硬件加速的渲染管线复杂度迅速上升，随之而来的是越来越精细、也可能令人困惑的性能特征。过去，提升性能只意味着减少渲染器内层循环的 CPU 周期；如今它变成了一轮又一轮地确定瓶颈并系统地攻克它们。这个由识别与优化构成的循环，是调优异构多处理器系统的根本；其出发点在于：一条管线按其定义，只和它最慢的那个阶段一样快。因此，在单处理器系统里过早且不聚焦的优化可能只带来极小的性能提升，而在多处理器系统里，这类优化往往带来零收益。

在图形优化上费尽力气却看不到任何性能提升，实在不好受。本章的目的就是让你别落到那一步。

28.1.1 管线

管线在最宏观的层面上可以分为两部分：CPU 与 GPU。尽管 CPU 优化是应用优化中关键的一环，本章不把它作为重点，因为其中很大一部分与图形管线关系不大。

图 28-1 显示，GPU 内部有若干并行工作的功能单元，它们实质上相当于各自独立的专用处理器，同时也有一些可能出现瓶颈的位置。这些位置包括顶点与索引取数、顶点着色（变换与光照，即 T&L）、片元着色，以及光栅操作（ROP）。

28.1.2 方法

没有正确识别瓶颈就动手优化，是大量开发工作被浪费的原因，因此我们把这一过程形式化为下面这个基本的识别与优化循环：

  1. 找出瓶颈。对管线中的每个阶段，改变它的负载或其计算能力（即时钟频率）。如果性能随之变化，你就找到了一个瓶颈。
  2. 优化。针对成为瓶颈的阶段，削减其负载，直到性能不再提升，或达到你想要的性能水平。
  3. 重复。再次执行第 1、2 步，直到达到期望的性能水平。

28.2 定位瓶颈

定位瓶颈是优化工作的一半，因为它让你能明智地决定把真正的优化力气投向哪里。图 28-2 是一张流程图，描绘了在你的应用中定位确切瓶颈所需的步骤序列。注意，我们从管线的后端开始，也就是帧缓冲操作（也称光栅操作），最后到 CPU。同样要注意，虽然按定义任何单个图元（通常是三角形）只有一个瓶颈，但在一个帧的过程中瓶颈很可能发生变化。因此，改动管线中一个以上阶段的负载，常常会影响性能。例如，低面数的天空盒通常受限于片元着色或帧缓冲访问；屏幕上只占几个像素的蒙皮网格通常受限于 CPU 或顶点处理。正因如此，逐物体或逐材质地改变负载往往很有帮助。

对每个管线阶段，我们还会提到与它相关的 GPU 时钟（即核心频率或显存频率）。这些信息与 PowerStrip（EnTech Taiwan 2003）这类工具配合使用很有用——它允许你降低相关时钟频率，观察应用性能的变化。

28.2.1 光栅操作

管线最靠后的一端是光栅操作（常称为 ROP），负责读写深度与模板、做深度与模板比较、读写颜色，以及做 alpha 混合与测试。可以看到，ROP 的大量工作都压在可用的帧缓冲带宽上。

要测试应用是否受帧缓冲带宽限制，最好的办法是改变颜色缓冲或深度缓冲的位深，或两者都改。如果把位深从 32 位降到 16 位后性能显著提升，那你肯定是受帧缓冲带宽限制。

帧缓冲带宽是 GPU 显存时钟的函数，因此改动显存时钟也是帮助识别这一瓶颈的手段。

28.2.2 纹理带宽

只要有纹理取数请求发往存储器，就会消耗纹理带宽。虽然现代 GPU 有纹理缓存来尽量减少多余的内存请求，但这些请求显然仍会发生，并消耗相当多的内存带宽。

修改纹理格式可能比修改帧缓冲格式更棘手（我们检查 ROP 时用的就是后者）；我们建议改为用大量正的 mipmap 细节层次（LOD）偏置来改变有效纹理尺寸。这会让纹理取数访问 mipmap 金字塔中很粗的层级，从而有效减小纹理尺寸。如果这样改动后性能显著提升，你就受纹理带宽限制。

纹理带宽同样是 GPU 显存时钟的函数。

28.2.3 片元着色

片元着色指生成一个片元及其相关颜色与深度值的实际开销，也就是运行「像素着色器」或「片元着色器」的开销。注意，片元着色与帧缓冲带宽常被笼统地归在填充率名下，因为两者都是屏幕分辨率的函数。然而它们是管线中两个不同的阶段，能区分二者对有效优化至关重要。

在高度可编程的片元处理 GPU 出现之前，受片元着色限制的情况很少见。造成屏幕分辨率与性能之间那种必然关联的，往往是帧缓冲带宽。如今这个钟摆开始摆向片元着色：新获得的灵活性让开发者可以大把地耗费周期去打造花哨的像素。

判断片元着色是否为瓶颈的第一步，就是改变分辨率。由于我们已经通过尝试不同的帧缓冲位深排除了帧缓冲带宽，如果调整分辨率引起性能变化，元凶最可能是片元着色。补充办法是改动片元程序的长度，看它是否影响性能。但要小心，别加入那些会被聪明的设备驱动轻易优化掉的指令。

片元着色的速度是 GPU 核心频率的函数。

28.2.4 顶点处理

渲染管线的顶点变换阶段负责接收一组输入的顶点属性（如模型空间位置、顶点法线、纹理坐标等），并生成一组适合裁剪与光栅化的属性（如齐次裁剪空间位置、顶点光照结果、纹理坐标等）。自然，这一阶段的性能取决于每个顶点所做的工作，以及被处理的顶点数量。

在使用可编程变换时，判断顶点处理是否为瓶颈只需改动顶点程序的长度。如果性能变化，你就是受顶点处理限制。如果要加指令，务必加那些真正做有意义工作的指令；否则这些指令可能被编译器或驱动优化掉。例如，引用常量寄存器的空操作（比如加上一个值为零的常量寄存器）往往无法被优化掉，因为驱动在程序编译时通常并不知道常量的值。

如果你用的是固定功能变换，就稍微麻烦些。可以试着通过修改顶点工作量来改变负载，例如镜面反射光照或纹理坐标生成的开关状态。

顶点处理的速度是 GPU 核心频率的函数。

28.2.5 顶点与索引传输

顶点与索引是 GPU 在管线 GPU 侧的第一步取来的。顶点与索引取数的性能会随它们实际放置的位置而变化。它们通常要么放在系统内存里——这意味着要经 AGP 或 PCI Express 这类总线传到 GPU——要么放在本地帧缓冲内存里。尤其在 PC 平台上，这个决定常常交给设备驱动而不是应用，尽管现代图形 API 允许应用提供用途提示，帮助驱动选择正确的内存类型。

判断顶点或索引取数是否为应用的瓶颈，要改动顶点格式的大小。

如果数据放在系统内存里，顶点与索引取数的性能是 AGP/PCI Express 速率的函数；如果数据放在本地帧缓冲内存里，则是显存时钟的函数。

如果这些测试都没有显著影响性能，那你主要受 CPU 限制。可以降低 CPU 频率来验证：如果性能成比例变化，你就是受 CPU 限制。

28.3 优化

既然已经找出了瓶颈，就必须优化那个特定阶段来提升应用性能。下面的建议按受限阶段分类。

28.3.1 在 CPU 上优化

许多应用受 CPU 限制——有时理由正当，比如复杂的物理或 AI，有时则是因为批处理或资源管理做得不好。如果你发现应用受 CPU 限制，可以试试下面的建议来减少渲染管线中的 CPU 工作。

减少资源锁定

任何时候执行需要访问 GPU 资源的同步操作，都有可能让 GPU 管线严重停顿，既浪费 CPU 周期也浪费 GPU 周期。浪费 CPU 周期是因为 CPU 必须原地空转等待（非常深的）GPU 管线空闲下来并交还所请求的资源；浪费 GPU 周期是因为管线空闲之后还得重新填充。

只要你做下面这些事，就可能发生这种锁定：

  • 锁定或读取你先前正在向其渲染的表面
  • 写入 GPU 正在读取的表面，例如纹理或顶点缓冲

总的来说，应避免在渲染期间访问 GPU 正在使用的资源。

最大化批次大小

这条建议也可以叫「最小化批次数」。批次是用一次 API 渲染调用（例如 DirectX 9 中的 DrawIndexedPrimitive）渲染的一组图元。批次的大小是它包含的图元数量。正如一位智者所说：「Batch, Batch, Batch!」（Wloka 2003）。每一次绘制几何体的 API 函数调用都带有相应的 CPU 开销，所以让每次绘制调用提交的三角形尽可能多，就能在渲染给定数量三角形时把 CPU 工作降到最低。

几个最大化批次大小的提示：

  • 若使用三角带，用退化三角形把不相接的三角带缝合起来。这样只要它们共用材质，就能在一次绘制调用里提交多条三角带。
  • 使用纹理页。当不同物体使用不同纹理时，批次经常被打断。把许多纹理排进一张 2D 纹理并相应设置纹理坐标，就能在一次绘制调用里提交使用多张纹理的几何体。注意这一技术可能在 mipmap 与抗锯齿方面带来问题。一个能绕开其中许多问题的办法，是把各张 2D 纹理打包进立方体贴图的每个面。
  • 利用 GPU 的着色器分支来增大批次。现代 GPU 的顶点与片元处理管线灵活，允许在着色器内部分支。例如，若两个批次分开是因为一个需要四骨骼蒙皮的顶点着色器、另一个需要两骨骼蒙皮的顶点着色器，你可以改为写一个顶点着色器，按所需骨骼数循环累加混合权重，当权重和为一时跳出循环。这样两个批次就能合并成一个。在不支持着色器分支的架构上，也能以耗费着色器周期为代价实现类似功能：对所有物体都用四骨骼顶点着色器，简单地把骨骼影响少于四个的顶点上多余的骨骼权重置零。
  • 把顶点着色器的常量内存当作矩阵查找表。当许多小物体共用全部材质属性、仅在矩阵状态上不同时，批次常常被打断（例如一片相似的树林，或一个粒子系统）。这种情况下，可以把 n 个各不相同的矩阵载入顶点着色器常量内存，并在每个物体的顶点格式里存入指向常量内存的索引。然后在顶点着色器里用这个索引查常量内存，取用正确的变换矩阵，从而一次渲染 n 个物体。
  • 把决策尽量推迟到管线的更下游。用纹理的 alpha 通道作为光泽度因子，比为了设置一个像素着色器的光泽度常量而打断批次要快。同样，把着色数据放进纹理与顶点里，也能让批次提交得更大。

28.3.2 降低顶点传输的开销

顶点传输很少成为应用的瓶颈，但也绝非不可能。如果顶点传输——不太可能是索引传输——是你的瓶颈，试试下面这些：

  • 顶点格式里用尽可能少的字节。如果一个字节就够用（比如颜色），就别什么都用浮点数。
  • 在顶点程序里生成可推导的顶点属性，而不是把它们存进输入顶点格式。例如，切向量、副法线和法线往往无需全存：给出其中任意两个，第三个就能在顶点程序里用一次简单的叉积推出。这一技术用顶点处理速度换顶点传输速率。
  • 用 16 位索引代替 32 位索引。16 位索引取数更便宜、搬运更便宜，占用内存也更少。
  • 以相对顺序的方式访问顶点数据。现代 GPU 在取顶点时会缓存内存访问。如同任何存储层次，引用的空间局部性有助于最大化缓存命中，从而降低带宽需求。

28.3.3 优化顶点处理

在现代 GPU 上顶点处理很少成为瓶颈，但视你的使用方式与目标硬件，它也可能发生。

如果你发现顶点处理是应用的瓶颈，试试这些建议：

  • 针对 post-T&L 顶点缓存做优化。现代 GPU 有一个小的先进先出（FIFO）缓存，存放最近变换过的顶点结果；命中这个缓存可以省掉全部变换与光照工作，以及管线更早阶段的所有工作。要利用这个缓存，必须使用索引图元，并且必须对顶点排序，使网格上的引用局部性最大。有一些工具可以帮上忙，包括 D3DX 与 NVTriStrip（NVIDIA 2003）。
  • 减少处理的顶点数量。这很少是根本问题，但采用简单的细节层次方案，例如一组静态 LOD，肯定有助于减轻顶点处理负载。
  • 使用顶点处理 LOD。除了对处理的顶点数量使用 LOD，还可以试着对顶点计算本身做 LOD。例如，远处角色很可能不必做完整的四骨骼蒙皮，光照大概也可以用更便宜的近似。如果你的材质是多遍的，对远处较低 LOD 减少遍数也能降低顶点处理开销。
  • 把逐物体的计算提到 CPU 上。常常有些每物体或每帧只变一次的计算，为了方便就放在顶点着色器里做。例如把平行光向量变换到眼空间，有时在顶点着色器里做，尽管这个计算的结果每帧只变一次。
  • 使用正确的坐标空间。坐标空间的选择常常影响顶点程序里计算一个值所需的指令数。例如做顶点光照时，如果顶点法线存在物体空间、光向量存在眼空间，你就得在顶点着色器里变换其中一个向量。如果改为在 CPU 上每物体一次把光向量变换到物体空间，就不需要逐顶点变换，省下 GPU 的顶点指令。
  • 用顶点分支「提前退出」计算。如果你在顶点着色器里循环处理若干光源，做普通的低动态范围 [0..1] 光照，可以检查是否饱和到 1——或者是否背对光源——然后跳出后续计算。蒙皮也有类似的优化：当权重和为 1 时就可以跳出（此后所有权重都为 0）。注意这取决于 GPU 如何实现顶点分支，并不保证在所有架构上都能提升性能。

28.3.4 加速片元着色

如果你使用的是又长又复杂的片元着色器，很可能受片元着色限制。若是这样，试试这些建议：

  • 先渲染深度。在渲染主要的着色遍之前先做一次只写深度（不写颜色）的遍，可以显著提升性能，尤其在深度复杂度高的场景里，因为它减少了需要执行的片元着色与帧缓冲内存访问。要充分获得只写深度遍的好处，仅关闭对帧缓冲的颜色写入还不够；还应关闭片元上的所有着色，包括同时影响深度与颜色的着色（例如 alpha 测试）。
  • 帮助 early-z 优化丢弃片元处理。现代 GPU 有专门的硅片设计来避免对已被遮挡的片元着色，但这些优化依赖于到当前点为止的场景信息；大致按从前到后的顺序渲染能大幅改善它们。此外，单独一遍先铺好深度（见上一条）能通过把后续着色遍的有效着色深度复杂度降到 1，实质性地加快它们（那里才做所有昂贵的着色）。
  • 把复杂函数存进纹理。纹理作为查找表极其有用，而且结果可以免费得到滤波。经典的例子是归一化立方体贴图，它以一次纹理查找的代价，让你以高精度归一化任意向量。
  • 把逐片元的工作移到顶点着色器。正如顶点着色器里的逐物体工作应移到 CPU 上，逐顶点的计算（以及能在屏幕空间正确线性插值的计算）应移到顶点着色器。常见的例子包括计算向量，以及在坐标系之间变换向量。
  • 使用所需的最低精度。DirectX 9 这类 API 允许在片元着色器代码中，为可用较低精度完成的量或计算指定精度提示。许多 GPU 能利用这些提示降低内部精度、提升性能。
  • 避免过度归一化。一个常见错误是「归一化上瘾」：做一次计算时，每一步都对每个向量归一化。要认清哪些变换保持长度（例如用正交基做的变换），哪些计算不依赖向量长度（例如立方体贴图查找）。
  • 考虑使用片元着色器细节层次。虽然它的性价比不如顶点 LOD（原因很简单：由于透视，远处物体在像素处理上天然就自我 LOD 了），但降低远处着色器的复杂度、减少在一个表面上的遍数，可以减轻片元处理负载。
  • 在不需要的地方关闭三线性滤波。在多数现代 GPU 架构上，三线性滤波即便不额外消耗纹理带宽，在片元着色器里计算也要多花周期。在 mip 层级过渡不易察觉的纹理上，关掉三线性滤波以节省填充率。
  • 使用尽可能简单的着色器类型。在 Direct3D 与 OpenGL 中，给片元着色的方式有好几种。例如在 Direct3D 9 中，可以按复杂度与能力递增的顺序，用纹理阶段状态、1.x 版像素着色器（ps.1.1 – ps.1.4）、2.x 版像素着色器或 3.0 版像素着色器来指定片元着色。一般应使用能实现预期效果的最简单着色器类型。较简单的着色器类型带有一些隐含假设，常使 GPU 驱动能把它们编译成更快的原生像素处理代码。一个不错的副产品是，这些着色器随后能工作在更广泛的硬件上。

28.3.5 降低纹理带宽

如果你发现自己受内存带宽限制，而且主要是在从纹理取数时，考虑这些优化：

  • 减小纹理尺寸。考虑你的目标分辨率与纹理坐标。用户真的会看到你最高的 mip 层级吗？如果不会，就考虑把纹理尺寸调小。如果过载的帧缓冲内存迫使纹理从非本地内存取（例如经 AGP 或 PCI Express 总线的系统内存），这一条尤其有用。NVPerfHUD 工具（NVIDIA 2003）能帮助诊断这一问题，因为它会显示驱动在各内存堆中分配的内存量。
  • 压缩所有颜色纹理。所有只用作贴花或细节纹理的纹理都应压缩，按具体纹理的 alpha 需求使用 DXT1、DXT3 或 DXT5。这一步会降低内存占用、减少纹理带宽需求，并提高纹理缓存效率。
  • 非必要不使用昂贵的纹理格式。大纹理格式，例如 64 位或 128 位浮点格式，取数显然要花多得多的带宽。只在必要时使用。
  • 对任何可能被缩小的表面始终使用 mipmap。mipmap 除了通过减少纹理走样来提升质量，还能通过让被缩小纹理的纹理内存访问模式局部化来提高纹理缓存利用率。如果你发现某些表面的 mipmap 让它们看起来发虚，不要因此关掉 mipmap 或加大负 LOD 偏置。应改用各向异性滤波，并按批次适当调整各向异性的级别。

28.3.6 优化帧缓冲带宽

管线中的最后一个阶段 ROP 直接与帧缓冲内存打交道，是帧缓冲带宽最大的单一消耗者。因此，如果应用里带宽成了问题，常常可以追到 ROP 上。以下是如何针对帧缓冲带宽做优化：

  • 先渲染深度。这一步不仅降低片元着色开销（见上一节），也降低帧缓冲带宽开销。
  • 减少 alpha 混合。注意，只要目标混合因子不是 0，alpha 混合就需要对帧缓冲既读又写，因而可能消耗双倍带宽。只在确实需要时使用 alpha 混合，并警惕 alpha 混合的深度复杂度偏高。
  • 尽可能关闭深度写入。写深度是额外的带宽消耗者，在多遍渲染（此时最终深度已在深度缓冲里）、渲染粒子这类 alpha 混合效果、以及把物体渲染进阴影贴图时都应关闭（事实上，向基于颜色的阴影贴图渲染时，你连深度读取都可以关掉）。
  • 避免多余的颜色缓冲清除。如果你的应用保证帧缓冲里每个像素都会被覆盖，那就不要清除颜色，因为它会耗费宝贵的带宽。但要注意，深度与模板缓冲则应尽可能清除，因为许多 early-z 优化依赖已清除深度缓冲的确定性内容。
  • 大致按从前到后渲染。除上一节提到的片元着色好处之外，对帧缓冲带宽也有类似好处。early-z 的硬件优化可以丢弃多余的帧缓冲读写。事实上，即便缺少这些优化的较老硬件也能从这一步获益，因为会有更多片元未通过深度测试，从而减少对帧缓冲的颜色与深度写入。
  • 优化天空盒渲染。天空盒常常受帧缓冲带宽限制，但你必须决定怎么优化：(1) 最后渲染，读取（但不写入）深度，让 early-z 优化与常规深度缓冲一起来节省带宽；或 (2) 最先渲染天空盒，关闭所有深度读取与写入。哪种方案省下的带宽更多，取决于目标硬件以及最终画面中天空盒可见的比例。如果天空盒有大片被遮挡，第一种技术大概更好；否则第二种可能更省带宽。
  • 只在必要时使用浮点帧缓冲。这类格式显然比更小的整数格式消耗多得多的带宽。多重渲染目标也是同理。
  • 尽可能使用 16 位深度缓冲。深度事务是带宽的巨大消耗者，所以用 16 位代替 32 位可能是巨大的收益，而对不需要模板的小尺度室内场景，16 位往往够用。对需要深度的渲染到纹理效果，例如动态立方体贴图，16 位深度缓冲也常常够用。
  • 尽可能使用 16 位颜色。这条建议尤其适用于渲染到纹理的效果，因为其中许多（如动态立方体贴图和投影颜色阴影贴图）用 16 位颜色完全没问题。

28.4 结论

随着现代 GPU 的算力与可编程性提升，要从机器里榨出每一点性能也越发复杂。无论你的目标是提升一个缓慢应用的性能，还是寻找能「免费」改善画质的地方，都需要深入理解图形管线的内部运作。随着 GPU 管线继续演进，优化的基本思路仍然适用：首先通过改变各单位负载或计算能力来找出瓶颈；然后借助你对各管线单元行为的理解，系统地攻克这些瓶颈。
