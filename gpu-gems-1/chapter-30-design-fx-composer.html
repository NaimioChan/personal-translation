第 30 章　FX Composer 的设计

Christopher Maughan
NVIDIA

FX Composer 是一个帮助开发者与美术创建 Direct3D 效果的工具。这些效果存在 .fx 文件中，文件里包含如何把着色器应用到给定 3D 模型上的完整信息。FX Composer 本质上是一个 IDE，外观与操作感类似 Microsoft 的 Visual Studio .NET。在开发 FX Composer 时，我们希望让人在友好的环境里交互式地编辑效果，也想为将来扩展到着色器调试与性能剖析等领域打下坚实的基础。

本章描述 FX Composer 工具的设计，并解释我们一路所做决定背后的理由。通过讨论我们遇到的问题以及所采取的解决办法，我们希望让你了解开发大型 Direct3D 应用的复杂性。注意：Direct3D 9 SDK 的帮助文档及其他支持材料详细讲解了 .fx 文件，并说明如何在 3D 应用中使用它们。因此本章不探讨 .fx 文件使用的具体细节。

30.1 工具开发

工具开发者的首要职责，是给最终用户一个能高效使用的应用。因此，工具的设计与演进可能与典型游戏大不相同——游戏的主要关注点通常是开发一个功能集固定的快引擎。工具开发有意思的地方在于，它让工具开发者可以在没有「必须以 x FPS 运行」这条紧箍咒的情况下设计软件。在工具程序里，功能与稳定性优先于执行速度。因此，FX Composer 开发的首要关注点是做出一个有用的工具，它可以扩展以跟上未来 Direct3D API 的变化，并有一个干净、公开的接口供将来扩展。

30.2 初始功能与目标用户

开始 FX Composer 项目时，我们的主要设计目标是：

  1. 一个熟悉的 IDE，外观与操作感类似 .NET。
  2. 一个可扩展的引擎。
  3. 一个用于创建 .fx 文件并可视化结果的稳定环境。

FX Composer 的目标用户是有一定编程知识的软件开发者与技术美术。考虑到这一点，工具需要把 .fx 文件编辑能力与编辑着色器属性的用户界面结合起来。为支持这一功能，类 .NET 的 IDE 应允许用户添加功能，这些功能可以方便地停靠在窗口面板中，需要时再隐藏起来。最初计划的应用功能如下：

  • 一个材质面板，显示多个 .fx 文件在 3D 物体上的渲染结果。
  • 一个纹理面板，显示渲染目标以及材质纹理。
  • 一个编辑器窗口，具备常见功能：撤销/重做、书签、语法高亮等。
  • 一个渲染窗口，显示应用了效果的简单场景。

30.3 对象设计

FX Composer 几乎完全由接口与对象构成。这一模型非常贴近 Microsoft COM 规范的原则，由一个核心运行时实现对象创建与注册功能。这种基于接口的做法有若干好处，也能带来非常干净的设计，我们稍后会展示。我们设计的一个关键成果是干净的插件模型，它贯穿整个 FX Composer 应用。应用中几乎每个组件都是插件，便于集成新功能与外部编写的扩展。

SDK 中的一个简化接口如代码清单 30-1 所示。

示例 30-1. 一个示例接口

class INVImportScene : public INVObject
{
public:

  virtual bool ImportScene(INVScenePtr &pScene, const char *pszFileName) = 0;
  virtual bool GetFileExtension(unsigned int i, const char **pszName,
                                const char **pszExtension) const = 0;
  virtual unsigned int GetNumFileExtensions() const = 0;
};

系统中任何想实现 INVImportScene 的对象，都可以通过继承这个纯抽象基类并实现其方法做到。所有引擎接口都是纯抽象的，且都继承自基接口 INVObject。INVObject 有三个 COM 程序员都熟悉的方法：AddRef、Release 与 QueryInterface。它们通过引用计数实现生命周期控制，并允许向系统中任何已实例化的对象询问它是否实现了某个特定接口。因此，系统中任何对象至少必须实现 INVObject 接口，这样它才能随时被查询以取得指向其他接口的指针，也才能被引用计数。

一个典型的引擎对象若要实现 INVImportScene 接口，写法如代码清单 30-2 所示。

额外的函数 CreateNVObject 通常用宏来声明，运行时调用它来创建该对象的新实例，并在支持时返回所请求接口的指针。

所有插件——在我们的情形里是动态链接库（DLL）——都必须导出两个函数：RegisterNVObjects 与 UnRegisterNVObjects。启动时，运行时会加载插件，让它们注册每一个可创建的对象类型。与 COM 一样，每个对象与每个接口都有全局唯一标识符（GUID）。

示例 30-2. XFileImporter 对象

class XFileImporter : public INVImportScene
{
public:

  // 实现 INVImportScene 的方法
  ...
      // 声明 INVObject（addref/release/queryinterface）
      ...
      // 一个静态创建函数
      static bool
      CreateNVObject(INVCreatorPtr, NVGUID &Interface, void **ppObject);
};

本质上，FX Composer 框架中的每个对象都是插件——从文件导入器这样复杂的对象，到字符串容器这样简单的对象。可加载的 DLL 中包含任意多个这样的对象，每个对象可实现任意多个接口。此外，所有对象都有可读的字符串以及一个可选的类别，类别把某一类型的对象归到一起，便于查找。每种对象类型都声明一个对象工厂，由它实现 INVCreator 接口，可按需用它生产已注册的对象。FX Composer 系统是可插拔类工厂的一个实例。

举个例子。在 FX Composer 中能创建的所有形状都属于类别 geopipeobject_shape。下面的代码展示了 FX Composer 如何找到可用的形状插件列表：

INVCreatorArrayPtr pCreators =
    GetSYSInterface()->GetCreatorsInCategory("geopipeobject_shape");

对 GetSYSInterface 的调用是全局的，可以在任何地方进行，返回指向 nv_sys 运行时的指针。返回的对象创建器数组随后可用于创建形状，显示在材质与渲染视口中。因此，创建一个能生成独特形状的插件对象、并让它在 FX Composer 里立即可用，是相当简单的过程。此外，这个形状可以保存到项目文件，并在重新加载时带上它的全部相关参数。

这些组件的技术实现细节超出本章范围，但归根结底是几个简单的宏，用来声明对象及其接口。我们取了 COM 规范中有用的部分，避开较复杂的特性，例如聚合以及通过注册表进行组件注册。为进一步简化使用，我们用智能指针免去了调用 AddRef/Release 的必要，并让接口查询自动化。例如，下面的代码片段检查一个场景导入器对象是否支持 INVProperties 接口：

INVSceneImporterPtr pImporter = GetImporter();
INVPropertiesPtr pProps = pImporter;
if (pProps)
{
  ...
}

从导入器指针到属性指针的赋值，会对导入器对象隐式调用 QueryInterface，成功时返回有效指针。所有额外的引用都由智能指针的引用计数特性清理（接口名上的 Ptr 后缀即为标志）。FX Composer 中每个接口都声明了等价的智能指针，很少不通过它就直接引用接口。

30.3.1 接口做法的好处

并非人人都喜欢基于接口/COM 的做法。对 FX Composer 而言，它最终成了一个很棒的特性，让底层实现变得干净容易。借助基于接口的编程，我们以非常易用的方式暴露了 FX Composer 的对象，使扩展与新功能容易添加。

下面是我们这套做法的一些优点。

对象查询

在 FX Composer 中，任何对象都可以支持任何接口，带来极大的可扩展性。IDE 的属性面板就是一个好例子。选中一个材质时，会收到一条「对象选中」消息，其中包含 INVObjectPtr。属性面板现在可以把它转换成 INVPropertiesPtr，如果成功，就能用这个标准接口遍历属性值列表，并让它们在 GUI 中可编辑。这对任何选择向系统暴露属性的对象都适用。例如，我们加入形状插件时，让它们暴露尺寸、剖分方式等，只是举手之劳。这些形状被加载并选中后，属性面板就允许用户修改其数值。因此，FX Composer 系统中许多对象都支持属性接口，结果是在用户界面里给出了有用的信息。

这一特性一次又一次带来回报。当我们加入把场景保存为 XML 文件的能力时，只需让可序列化的对象支持 INVXMLStreamable 接口，就能把对象流式写入 XML 格式的文件。当我们想克隆对象时，就加了一个 INVClone 接口，让对象自己控制如何被复制。

未来关于接口的想法包括一个 INVScript 接口，让系统对象暴露它们的脚本函数。

对象生命周期

由于所有组件都被引用计数，而智能指针通常指向它们，我们的内存泄漏非常少——泄漏通常出现在外部代码里。当然，引用计数也有缺点：传递接口指针总有固定开销；有时很难在你想让对象消失时让它消失；循环引用常会成为问题——比如两个对象互相持有引用。遇到这些问题时，我们偶尔用「弱」指针绕过——也就是持有指向对象的指针，但不「智能」、不带引用计数。这种做法感觉有点像绕路，但实践中并不常需要。如前所述，额外开销对这个工具来说不是考虑因素。

插件管理

FX Composer 中的插件基本上随我们使用的对象模型免费得来。每个对象向系统注册自己，之后任何感兴趣的一方都可以使用它。创建一个新插件很简单：声明一个新接口，指定关联的类别，再写几行简单代码加载该类别中的对象并使用它们。核心运行时负责跟踪对象，事实上它始终持有系统中每个已实例化对象以及所有已加载插件模块的内部列表。这是一个有用的调试特性，因为随时都可以分析运行时系统。FX Composer 中还有一个额外的调试对话框，以树状视图呈现当前系统对象，我们已多次用它分析行为、追查 bug。

我们的做法有一个缺点：要把它用好确实需要一点理解，尤其当开发者不熟悉这类编程时。为了让这个适应过程更容易，我们加了几个宏，使对象与接口的创建尽可能简单；还附带了一个注释详尽的示例插件。

连接参数

从一开始我们就决定，FX Composer 应当处理场景、蒙皮角色以及材质参数的动画。为此我们设计了一种连接参数类型，与 D3DX 效果参数类型紧密对应，并完整支持动画。结果是，FX Composer 中几乎任何参数都可以用时间键与各种类型的插值器做动画，在两个独立键之间生成中间值。例如，可以把一个效果应用到蒙皮网格上，再让效果里「凹凸高度」这样的值做动画。角色会动，效果也会实时变化。连接参数还有若干附加属性，例如语义、注解与名称，与 .fx 文件中一样，使它们成为对象中任一项数据的通用容器。

FX Composer 支持的连接参数在好几方面都很有用：

  • 我们的属性窗口可以向任何对象查询参数列表并以合理的方式显示。只要对象支持 INVProperties 接口，就能让自己的参数通过一个通用的属性表窗口编辑。这让用户在编辑材质、形状、灯光、相机等不同类型的对象时获得一致的外观与操作感。
  • 项目文件的流式代码可以轻而易举地保存或恢复连接参数，使多数对象的序列化成为简单过程。
  • 连接参数可以按类型、语义、名称、注解等进行比较。这在把一组连接参数映射到另一组时特别有用，而这种情形经常发生。一个典型场景是：重新加载的项目文件引用了已被修改的 .fx 效果。此时我们想尽量保留已保存的数据，同时配合新的 .fx 文件工作。我们的做法是把旧参数列表映射到新列表。出现冲突时，再提示用户解决。另一个映射场景发生在把材质参数以合理方式与场景中的对象匹配时，例如把一盏灯接到材质的位置参数上。

消息发送者与接收者

对 FX Composer 引擎这样复杂的系统，各组件之间良好的通信至关重要。我们对这个问题采取了两手策略。起初，我们开发了一套全局消息广播系统，让任何对象都能以「发后即忘」的方式向所有感兴趣的一方发送消息。NewScene 消息就是一个好例子，许多组件可能想知道新场景已经创建。

这套方案起初运行良好，但由于广播的通用性，很快就变得臃肿。为改进系统，我们又开发了一套附加的消息协议，让两个感兴趣的一方之间建立紧密联系。在系统中，任何对象都可以实现 INVMessageReceiver 接口，任何对象也都可以实现 INVMessageSender 接口。感兴趣的一方随后可以向对象注册自己，了解它们想知道的事件。这类方案的常见问题都会出现，因此必须小心维护通信链路的两端。必须注意让参与者不要失去同步，以致持有指向已不存在或对自己已无意义的对象的引用。这套消息发送者/接收者系统，是 Design Patterns 一书（Gamma 等 1995）中所述「发布/订阅」模式的一个实例。

30.4 文件格式

我们决定 FX Composer 需要自己的文件格式，用来保存与恢复当前场景、材质调色板、文件路径，以及可选的当前媒体集。这个文件将容纳整个工作区，并允许用户把纹理、.fx 文件与其他项目打包进一个文件——这对我们的开发者关系团队是个额外好处，他们经常想给开发者发送自包含的示例。这种工作区格式的扩展名是「.fxcomposer」。

我们考虑的第一种文件格式完全由 XML 数据构成，但因为场景中二进制数据量很大而被否掉了；这类数据用 XML 编码效果不好。于是我们实现了一种混合做法，兼得两者之长。FX Composer 项目文件是一种复合格式，所有数据实际上存在一个 .zip 文件中（尽管扩展名是 .fxcomposer）。这个 .zip 文件里有一份 XML 场景描述，其中以二进制块内偏移量的形式引用一些外部二进制数据。二进制块也编码在同一个 .zip 文件中。为进一步简化设计，系统中的对象可以支持 XML 流式接口，能够以 XML 格式写出自己的数据。它们为此使用的接口还允许把数据加入压缩的二进制文件，并返回一个偏移量供之后取回。保存整个工作区只需遍历对象层次，为每个对象构建 XML。重新加载也差不多简单：每个对象根据 XML 数据重新加载自己。作为进一步的抽象，XML 中每个元素都有一个 ObjectID，可以从文件末尾取回。这样，FX Composer 可以提前检查必要的插件是否已加载、自己能否支持从工作区文件流式读入的对象。这一步可以防止这类问题：例如保存了一个包含「茶壶形状」插件的场景，却试图在一个没装该插件的 FX Composer 版本上重新加载它。这种情形下，程序可以告知用户缺少某个插件，然后尝试加载场景的其余部分。

新文件格式的一个有趣副作用是它的效率。由于公共数据被压缩进一个不与场景数据交错的二进制块，文件大小相当紧凑，压缩后的存储需求甚至小于原始网格文件。考虑到 .fxcomposer 文件不仅包含网格，还包含调色板中的材质，这种紧凑程度令人印象深刻。以导入的 .x 文件为例，与我们内部开发的 .nvb 格式相比收益最大，而保存下来的文件实际上还以切向量和副法线向量的形式包含了更多网格数据。

30.5 用户界面

通常，工具项目涉及大量用户界面工作。这类工作可能很枯燥，而且若做得不好，常常导致工具不完整、界面难用。结果往往取决于开发者的 Windows 编程经验。我们一开始就知道 FX Composer 需要复杂的 UI，并且希望支持浮动与停靠窗口，以节省空间并给用户一个熟悉的开发环境。

我们考虑过自己写 MFC 代码，但这样复杂的任务需要单独立项。另一种可能是给 VC.NET 写扩展，但我们无法完全确定 .NET IDE 能满足实时 3D 应用的各种不同需求——而且光是为了回答这个初步问题，我们就得爬一段陡峭的学习曲线。

最终，BCGSoft（www.bcgsoft.com）用它的 BCGControlBar Professional MFC 扩展库救了我们。这个健壮的组件实现了 Visual Studio .NET 这类高级 IDE 中的许多功能。它能处理浮动与停靠窗口，还额外附带一个支持书签、撤销/重做乃至 IntelliSense 的编辑器。到目前为止，我们对结果非常满意。事实上 BCGControlBar 太大了，我们并没有把工具包里所有可用功能都打开——我们想在需要之前控制住复杂度。例如，SDK 支持完全可定制的菜单与热键布局，用户可以修改它们，做出合自己口味的外观与操作感，就像在 .NET 里一样。

使用这样复杂的工具包，除了增加应用复杂度，还有一个副作用：测试负担。有这么多窗口以不同方式排列——每一个都可能在任何时刻打开、关闭或隐藏，包括在应用启动时——就需要有一套彻底的测试方法来确保所有布局组合都能工作。我们正从几个方面着手解决这个问题：质量保证、手动修改应用以暴露潜在问题，以及自动化测试。我们想实施的一个计划是对象层面的单元测试框架。借助像 INVUnitTest 这样简单的接口，应能让系统的各组件以干净的方式运行自动化测试。之后 FX Composer 就可以在调试版本中定期测试系统中所有对象的完整性，或在按键时触发测试。

30.6 Direct3D 图形实现

FX Composer 本质上是一个图形应用，而且由于有多个设备窗口，还是一个相当复杂的图形应用。它还负责管理 .fx 文件列表及所有相关媒体。在当前系统上，任一时刻最多可能用到四个 Direct3D 设备：媒体面板、纹理面板、渲染面板，以及着色器性能栏——后者能把 .fx 文件反汇编，并显示 NVIDIA GPU 的性能剖析信息。

30.6.1 设备窗口

考虑到需要简化各独立组件的实现，我们决定为应用中的每个面板使用独立的 Direct3D 设备。这种做法看似耗费资源，但确实允许用户把应用中任意单个面板「撕下来」，例如在第二台显示器上全屏运行。它还便于让参考光栅化器与硬件加速的设备窗口并排运行，以便验证效果，或运行当前硬件不支持的着色器。

独立设备的代价体现在材质面板与渲染窗口面板上。这两个窗口可能包含共享材质纹理的副本。例如，把 DiffTex.fx 文件载入材质面板，纹理会载入材质面板的设备。如果该材质随后被应用到场景中的网格上，纹理也会在渲染窗口中实例化。除此之外，如果该材质被选中，纹理还会在纹理面板中创建。当着色器性能面板加载材质以分析效果时，它也可能出现——尽管做这件事并不一定需要加载纹理，也不必长时间持有该材质。着色器性能面板与纹理面板一次只显示一个材质，所以这不是大问题。

因此，材质面板与渲染面板是资源可能重复的主要地方——尤其是纹理。实践中这没成为问题，要让它成为问题需要相当大的场景。此外，除渲染目标之外，多数纹理都是托管的；它们在使用之前不一定会实例化到设备上，必要时还可以换出。将来我们可能会研究跨设备共享纹理——Direct3D 允许这么做——或让一个设备在多个窗口间共享。这会给设计增加一定程度的不灵活与复杂度，而我们目前认为没有必要——尤其因为 FX Composer 面向的是在配备合理现代硬件、拥有充足显存的开发机上工作的开发者与美术。

30.6.2 Direct3D 效果

FX Composer 的主要工作是管理 .fx 文件。D3DX 提供了丰富的 API 来处理 .fx 文件，FX Composer 很好地利用了它们。D3DX 中的关键概念是能够分两步加载效果。虽然这不是唯一的做法，但 FX Composer 采用了这种方式。

首先，FX Composer 创建一个材质。我们把材质理解为 .fx 文件的一个实例，以及该材质独有的关联参数。任一时刻，我们可能从同一个 .fx 文件创建多个材质，每个都有不同的连接参数集。例如，假设我们有两个不同的卡通材质，都引用名为 cartoon.fx 的文件。每个材质可以在 .fx 文件的漫反射参数上取不同颜色，让卡通角色呈现不同的外观。这模仿了美术在典型 CAD 软件包中的工作方式：先选一种材质类型，再调整参数得到正确的外观。此时材质与任何具体的 Direct3D 设备都没有关联，无论多少窗口引用它，代表材质的对象只有一个。

30.6.3 ID3DXEffectCompiler

拿到材质之后，我们用 ID3DXEffectCompiler 接口载入 .fx 文件。这样就能编译效果文件并检查错误，而不必在设备上实例化该效果。效果编译器会生成效果的紧凑表示，之后可用它创建设备相关的效果。但这里有个问题：我们希望效果只有一组材质参数，因此必须为 .fx 文件保留一组连接参数。这组参数成为我们的主参数集，引擎各部分都修改它。之所以必须这样做，是因为一旦把效果添加到某个设备，就会为该设备新建一组参数，我们需要把当前这组映射到设备那组。

为简化在设备上渲染材质的过程，我们给材质接口加了一个 API，名为 ApplyToDevice。材质在某个设备窗口上使用之前会调用这个 API。如果此时该材质尚未在这个窗口上用过，它就会用 ID3DXEffectCompiler 编译好的效果，为该设备创建一个效果。此时 D3DX 会把紧凑的效果表示转成 ID3DXEffect 接口，我们就可以用它渲染效果。由于此前已经编译过 .fx 文件，这一步实际上比从 .fx 文件直接创建 ID3DXEffect 更快；这也意味着无论有多少窗口在渲染这个效果，我们只编译一次。

30.6.4 ID3DXEffect

现在我们有了设备相关的接口，还附带若干额外的 API。在这里可以查看效果应用于当前设备的情形，并检查它能否在该设备的能力范围内渲染。如果效果所需的设备能力不可用，FX Composer 会用蓝色线框绘制对象；如果上一步编译失败，结果为红色线框。D3DX 效果按技术划分，每种技术的资源需求可能不同。因此我们还会为当前设备维护一份可用技术列表，以便在界面中列出它们，并在当前选择不可用时换用另一种。

30.7 场景管理

FX Composer 自带场景图，实现方式相当直接。额外的导入器可以把 .nvb 与 .x 格式的文件导入场景图；将来我们会根据开发者需求提供更多格式。场景本质上是一锅「节点汤」，包含几何体、摄像机、光源等。连接节点的是变换链接，靠它们遍历场景图。系统足够灵活，将来可以根据需要以不同方式遍历节点。例如，我们可能想以光源的视角从前到后遍历场景。当前的场景图并不妨碍这种做法，因为节点和链接是彼此独立的实体。

节点和节点链接也有标准的可动画连接参数，因此可以在不同关键帧上打动画，从而实现场景动画、蒙皮、摄像机平移等效果。

30.7.1 几何管道

D3DX 效果通过语义完整规定了从应用程序到顶点着色器输入的接口。用名为 D3DXGetShaderInputSemantics 的 API 可以查出效果所需的顶点缓冲布局。既然如此，FX Composer 理应能处理复杂的几何数据流，并把它们映射到当前的 .fx 文件。为此，FX Composer 实现了 几何管道节点的概念。一个几何管道节点由若干几何管道对象组成，每个对象都能修改一个 几何管道束。束是一组几何数据的集合，每种数据类型对应一个流对象。典型的束可能包含位置流、法线流和纹理坐标流。几何数据沿管线向上流动时，几何管道对象可以通过添加、修改或删除数据来改动束。最终位于管线顶端的束会被转换成 Direct3D 顶点缓冲，并使其与该几何管道上使用的效果文件相匹配。为了协助在几何束与 .fx 文件的输入格式之间做匹配，几何束的各个流带有语义索引与用途索引。

这种做法允许创建插件来满足当前效果的使用场景。例如，应该可以写一个插件，为毛发着色器加上「鳍片」。插件作者还可以往束里加一条几何流来标明鳍片的存在，或者加一条三角形流来渲染它。

栈底始终放着一类特殊的几何管道插件。这个插件要么是「形状」，要么是「网格」。它是几何束向上流动之前的起点。形状插件非常紧凑，只包含如何构建该形状的简单信息。网格插件通常由导入器根据预载的几何数据创建，不过也没有什么能阻止插件作者创建过程化网格对象。

蒙皮

.fx 文件的一个常见问题是如何处理蒙皮。FX Composer 采用三种做法之一：

  1. 如果当前几何束包含骨骼与权重，而指定的 .fx 文件并不把它们作为输入，FX Composer 会在主机上先做好蒙皮，再传给效果。
  2. 如果当前 .fx 文件带骨骼权重而当前几何流没有，FX Composer 会把骨骼权重设为 1，并把当前变换填入骨骼矩阵调色板，从而保证未蒙皮的角色也能用在蒙皮效果上。
  3. 如果当前 .fx 文件包含骨骼权重，模型也有相同数量的骨骼权重，FX Composer 会把数据直接发给效果，前提是当前硬件能处理该骨骼调色板的大小。

30.8 结论

借助 FX Composer，我们希望做出一个开发者可用来为应用创建出色效果的工具。我们一直努力把应用程序设计成能随未来的 API 和 GPU 一同成长，使我们能继续提供有用的工具。插件特性让开发者可以把自己的工作流程与 FX Composer 集成，并以简单的方式把资源带进来。

我们希望本章让你了解了我们编写这个复杂 Direct3D 工具的思路，也希望它能为使用 .fx 文件的实现带来一些有趣的启发。Direct3D 效果提供了强大的效果创作功能，像 FX Composer 这样的工具应当有助于推动它们在 3D 应用中广泛使用。凭借用于构建效果的丰富 IDE 与面向未来开发者工具的坚实框架，我们相信 FX Composer 已经达成了目标。
