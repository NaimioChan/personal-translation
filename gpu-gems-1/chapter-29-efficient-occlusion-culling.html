第 29 章　高效遮挡剔除

Dean Sekulic
Croteam

29.1 什么是遮挡剔除？

多数图形算法告诉我们怎样快速地渲染某样东西，或怎样让它好看。有些技术偏向性能，有些追求质量，难点在于如何在两者之间取得平衡。

遮挡剔除提升渲染性能的办法很简单：不渲染视野锥之外、或被更靠近相机的物体挡住的几何体。两种常见的遮挡剔除是遮挡查询与early-z 剔除。

本章考察遮挡查询以及如何正确使用它，并给出两个例子证明遮挡剔除可以多么高效。由于其中一个例子大量依赖包围盒，为便于理解，包围盒也会一并讲到。

29.1.1 遮挡查询

从 GeForce3 开始，所有 NVIDIA GPU（以及其他厂商的许多 GPU）都带有遮挡查询功能，它让我们可以不去渲染被遮挡的物体。跳过被遮挡物体的整个渲染过程，就能减轻 GPU 的渲染负载。

29.1.2 Early-Z 剔除

自 GeForce3 起，多数 GPU 也支持 early-z 剔除。在渲染过程的光栅化阶段，early-z 把将要渲染的片元的深度值，与 z 缓冲中当前存着的值做比较。如果该片元不可见（因为深度测试失败），就在不为该片元取纹理、也不执行片元程序的情况下将它剔除。结果是：在逐片元层面省下了内存带宽。

遮挡查询与 early-z 剔除之间有很大差别。遮挡查询在几何体层面剔除多边形，而 early-z 发生在光栅化层面。此外，通过遮挡查询剔除几何体需要应用做更多控制。

两种做法都要求程序员把物体从前到后排序。但要注意，因为深度缓冲与模板缓冲常存在一起，使用模板缓冲可能降低 early-z 的性能。（另外，early-z 剔除往往需要更多前提条件，不过这些与本章主题没有直接关系。）对 early-z 剔除来说，程序员该做的做完了，剩下的交给 GPU。

但对遮挡查询来说，还有很长的路要走……

29.2 遮挡查询如何工作？

在 OpenGL 中，ARB_occlusion_query 扩展（它基于 NVIDIA 的 NV_occlusion_query 扩展，后者是 Hewlett-Packard 最初的 HP_occlusion_test 扩展大幅改进后的形式）在 GPU 上实现遮挡查询这一思路并取回查询结果。（更多内容见 NVIDIA 2003。）Microsoft 在 DirectX 9 中加入了同样的功能。（更多内容见 Microsoft 2003。）

遮挡查询本质上很简单。GPU 告诉我们最终应该有多少像素在屏幕上可见。这些像素在管线末端成功通过了各项测试——例如视锥可见性测试、剪裁测试、alpha 测试、模板测试与深度测试。这一路可不容易！

过程如下：

  1. 创建一个查询。
  2. 关闭向屏幕渲染（把所有通道的颜色掩码设为 False）。
  3. 关闭深度缓冲写入（只与深度缓冲做测试，不更新它）。
  4. 发起查询开始（这会重置可见像素计数器）。
  5. 「渲染」物体的包围盒（它只做深度测试；通过深度测试的像素不会渲染到屏幕上，因为渲染与深度写入都已关闭）。
  6. 结束查询（停止统计可见像素）。
  7. 恢复向屏幕渲染。
  8. 恢复深度写入（如需要）。
  9. 取回查询结果（「可见」像素的数量）。
  10. 若可见像素数大于 0（或某个阈值），
    1. 渲染完整物体。

这些步骤让我们用一个简单的包围盒代替几何复杂的物体。这个包围盒将决定我们是否需要渲染物体本身。如果物体的包围盒被屏幕上其他多边形完全挡住，我们就可以整个跳过该物体。

问题在哪？在测试物体包围盒时，千万注意不要更新颜色或深度缓冲——这正是我们关闭颜色与深度写入的原因。

在接下来的几节里，我们先从一次朴素的使用遮挡查询的尝试开始，再把做法逐步改进为稳健的、可用于实际的实现。

29.3 开始使用遮挡查询

真正的问题在于 GPU 管线刷新。正常情况下 CPU 与 GPU 并行工作：当 CPU 向 GPU 发出命令（例如「渲染一些三角形」），它并不等待 GPU 完成。CPU 一侧的驱动把命令与三角形喂进 GPU 命令队列，让 CPU 继续做别的事。当 GPU 准备好处理已存的命令时，三角形才被渲染到屏幕上。

然而遮挡查询的渲染过程不同。GPU 需要告诉 CPU 有多少像素画到了屏幕上，这意味着它必须先把它们渲染出来。问题在哪？CPU 必须等待 GPU 完成遮挡查询所用三角形的渲染——不只是那些三角形，还有在遮挡测试之前交给 GPU 的所有三角形。

这可不妙。试图让 GPU「省下」渲染被遮挡物体的工作，并不能加快渲染过程。事实是，即便被测物体大多都被遮挡，渲染反而慢得多，因为 CPU 与 GPU 不再并行工作。

显然，朴素的做法不会太好用。那么真正的问题是……

29.3.1 如何正确使用遮挡查询

好消息是 OpenGL 与 DirectX 9 都支持多个未完成的查询。这意味着我们可以先启动若干个计数器统计可见像素，稍后再去取计数器。

于是算法变成下面这样：

  1. 创建 n 个查询。
  2. 关闭向屏幕渲染。
  3. 关闭深度缓冲写入。
  4. 对 n 次查询中的每一次，
    1. 发起查询开始。
    2. 「渲染」物体的包围盒。
    3. 结束查询。
    （查询循环结束）
  5. 恢复向屏幕渲染。
  6. 恢复深度写入（如需要）。
  7. 对 n 次查询中的每一次，
    1. 取回查询结果。
    2. 若可见像素数大于 0，
      1. 渲染完整物体。
    （查询循环结束）

这一做法比原先好得多，但仍不能给 GPU 足够的时间真正渲染完 CPU 喂给它的全部几何体，也就是说停顿并未完全消除。

而且还有另一个问题……

29.3.2 遮挡体与被遮挡体

基本做法的问题在于，包围盒不能写入深度缓冲，因为存在一些非常奇怪的情况：一个包围盒完全遮挡了另一个包围盒，但遮挡体包围盒内的物体实际上并没有挡住被遮挡体包围盒内的物体，如图 29-1 所示。

所以，有些场景几何体需要先渲染在前面，且不做遮挡剔除。这些几何体会充当遮挡体，因此它们应该是最终在屏幕上占很大面积的东西。（一堵高墙或一栋大楼就是好例子。）这些物体渲染完之后，就可以开始对较小的物体做遮挡查询。

不过这一切都让事情稍微复杂了些，也降低了遮挡剔除的效果（连一个大物体本身有时也会被完全遮挡）。因此我们需要另一种做法。

29.4 再进一步

为了稳妥，确保 GPU 已经渲染完我们让它做的一切，我们要做一件相当激进的事：在下一帧才检查遮挡查询结果！

游戏循环现在大致是这样（为简单起见，只展示一个查询）：

  1. 创建查询。
  2. 游戏循环：
    1. 做 AI。
    2. 做物理。
    3. 渲染：
      1. 检查上一帧的查询结果。

      2. 发起查询开始：

        1. 若该物体在上一帧可见：
          1. 恢复向屏幕渲染。
          2. 开启或关闭深度缓冲写入（取决于物体是半透明还是不透明）。
          3. 渲染物体本身。
        2. 若该物体在上一帧不可见：
          1. 关闭向屏幕渲染。
          2. 关闭深度缓冲写入。
          3. 「渲染」物体的包围盒。

        （结束查询）

        （对场景中每个物体重复。）

    4. 交换缓冲。
    （游戏循环结束）

频繁检查物体是否仍然可见并不重要，所以我们大可放心地假设：上一帧可见的物体在本帧仍然可见。不过这一做法有缺点：已经不可见的几何体仍可能被送到 GPU。此外还可以加一项优化：每隔几帧才检查一次某物体是否不可见。这样任一时刻未完成的遮挡查询都更少。但对已被遮挡（不可见）物体的测试必须每帧都做！我们不能假设该物体在本帧仍被遮挡，否则会引入过度的「渲染」错误（也就是物体凭空出现）。

总的来说，落后一帧、剔除掉可见物体的问题（「你看到的并不完全是你得到的」）并不严重。这一帧没看到某个物体、下一帧看到了，并不太要紧，尤其当帧率超过每秒 30 帧时。这只是一点点「现在你看不见我、现在你看见了」的现象，因此这种突然出现不应太显眼。

有时即便只是下一帧才测试也会引起停顿，因为有些驱动实际上会把 SwapBuffers 请求排队，让 GPU 落后两三帧渲染。这可能成为问题，但性能损失通常低于 10%，考虑到遮挡查询带来的加速，这是可以接受的。

你可能已经注意到，测试上一帧可见物体的遮挡，是在物体本身上做的；而测试先前不可见物体的遮挡，是在物体的包围盒上做的。除了本身就是一种优化（不必既渲染物体又渲染包围盒！），这一做法对判断哪些物体是潜在遮挡体、哪些是被遮挡体至关重要。

29.4.1 理清顺序

这一改进后的做法自动免去了把潜在遮挡体与被遮挡体实际分开的需要（如 29.3.2 节所述），因为每个已被渲染为可见的物体，只要写入了深度缓冲，就充当了遮挡体。因此我们不必让遮挡体（不做遮挡测试的物体）在被遮挡体之前渲染。不过为了让算法顺利些，我们需要按距离对物体排序。

一旦拿到了当前场景中需要渲染的全部物体（即通过视锥剔除的那些），我们需要把它们分成两组：不透明物体与半透明物体。因为半透明物体能看穿（而且它们不能写入深度缓冲！），它们只能充当被遮挡体，不能充当遮挡体。反之，不透明物体既可以是遮挡体也可以是被遮挡体，这意味着它们应按从前到后排序，并在半透明物体之前渲染。之后半透明物体按从后到前排序，同样渲染到屏幕上。

这一做法很好地利用了遮挡查询功能：潜在遮挡体先被渲染，使许多其他物体成为潜在被遮挡体，而它们的渲染可以被遮挡测试剔除。所有不透明物体渲染完之后，它们自动开始充当所有半透明物体的潜在遮挡体。

29.4.2 一点注意事项

有时从某些视点看，物体被遮住了，但它的包围盒可见。当包围盒比物体大得多时就会出现这种情况。这时物体每隔一帧才被渲染一次：包围盒得到「可见」的结果，于是下一帧需要渲染物体本身；但下一帧渲染的物体得到「不可见」的结果，这意味着下一帧又要渲染包围盒，如此往复。虽然我们的方法可能带来一点帧率波动，但它是一种不错的优化，因为物体与包围盒都不必每帧都画。

29.5 关于包围盒

包围盒可以是静态的也可以是动态的，它们往往远大于所包含的物体，所以值得考虑为它们做几项优化。

29.5.1 静态物体

对静态物体，包围盒通常不会比物体大太多。但在金字塔这个经典例子里，我们可能想用多个盒子来高效表示它的范围，如图 29-2 所示。

使用这些子包围盒时要小心，因为测试它们引入的开销可能比只测一个大包围盒更多。当然，这完全取决于物体几何体的复杂度。金字塔这个案例只是让道理更明显的例子，因为用若干包围盒来表示金字塔的五个多边形肯定不是最优。

29.5.2 动态物体

动态物体更复杂。计算动态物体包围盒的好办法是什么？方法很多，下面举几个。

  1. 为每个动画的每一帧计算包围盒。

    这可能变得复杂且耗费 CPU，尤其当物体的骨骼动画系统被纳入 GPU 顶点着色器时。用 CPU 驱动这个物体动画（以便计算包围盒）所引入的开销，可能远高于渲染该物体本身。

  2. 为每个动画的所有帧只存一个包围盒。

    这是最简单、最快的做法。但结果可能不准确，因为包围盒可能明显大于物体，导致物体实际上被遮挡时却判定为可见。

    我们可以通过让物体「原地」做动画来稍微缩小包围盒——换句话说，通过动画程序来平移物体，而不是在动画本身里平移。例如我们射中一个敌人，他会飞过空中，落在几米之外。如果用一段动画把敌人从空中搬过去，最后会得到一个巨大的包围盒。反之，如果让敌人的飞行在原地完成（不平移他），包围盒就小，可以在动画触发时由动画代码做实际的平移。见图 29-3。

  3. 为每个动画各存一个包围盒。

    这是最好的方案，但带来一个小问题：混合多个动画时，我们需要计算各动画包围盒的并集。这不算大问题，考虑到省下的力气——一个动画的包围盒往往远小于所有动画的包围盒。

最好的办法是把第二种与第三种方法结合起来，看哪种对特定物体最优。

有些情况下，如果我们需要为某个物体渲染多遍，而第一遍相当简单，我们可以用这第一遍（而不是包围盒）来做可见性测试。但仍要注意那一遍中的多边形数量；记住，我们想省的是几何体吞吐。

29.6 其他问题

29.6.1 CPU 开销过高

我们需要考虑向 GPU 发送渲染请求时产生的 CPU 开销。如果物体很容易渲染，那么直接渲染它可能比画包围盒再做遮挡测试更便宜。例如在当今的 GPU 上，渲染 12 个三角形（一个包围盒）与渲染约 200 个三角形（甚至更多！）所花的时间几乎一样。大部分时间花在 CPU 上，仅仅是准备物体以供渲染。

不过，有时无论实际物体有多少多边形，测试它的包围盒都是必须的。如果被渲染的物体有非常复杂的像素着色器，并占据屏幕上相当大的一块呢？这种情形下，即便包围盒要画的像素更多，这些像素的渲染也可能比物体本身快得多（尤其因为它们只写深度缓冲！），而物体本身会让 GPU 在每像素上承担大量运算。

29.6.2 在高分辨率下渲染

当我们以高分辨率渲染但像素着色器很简单时，应用可能变得受填充率限制。渲染整个包围盒所需的像素可能远多于只渲染盒内的物体；GPU 在逐像素层面要做的工作更多。

经验法则是：不受填充率限制的物体（也就是不使用复杂片元程序、没有许多纹理层等的物体）在高分辨率下不应做遮挡测试。这是因为高分辨率下要填的像素更多，GPU 渲染物体包围盒的时间很可能超过渲染物体本身。要记住，如果物体被遮挡，early-z 剔除会在逐像素层面起作用，从而避免处理复杂的片元程序。

填充率问题还可能更糟，因为有时包围盒需要用正面与背面多边形从两侧渲染！问题在于，当你测试一个非常靠近视点的物体时，观察者最终会处在包围盒内部。这就是我们还需要渲染背面的原因；否则由于背面剔除，屏幕上不会画出任何像素，我们会得到错误结果。稳妥起见，对离观察者太近的模型跳过遮挡测试；它很可能弊大于利，而那么近的物体肯定是可见的。

29.6.3 快速的深度写入性能

但也不全是坏消息。当只进行深度测试或模板写入时，一些新 GPU（例如 GeForce FX 系列）会走一条更高性能的渲染路径。过去，在测试包围盒可见性期间关闭颜色缓冲，硬件获益不大，因为颜色与深度值的输出电路在同一条管线里。如今在新硬件上，如果关闭颜色缓冲输出，管线就用于深度测试，包围盒测试会更快。

29.6.4 视锥剔除

尽管遮挡测试能剔除视野锥之外的像素，但不建议用它来做视锥剔除。渲染物体的包围盒所引入的开销，可能比在 CPU 上用常规做法把包围盒与视锥裁剪平面做测试更大。此外，有些包围盒可以方便地换成包围球，使 CPU 式的视锥测试更快。

一种做法是先把包围球与视锥做测试。如果球完全在内部，我们就直接渲染整个物体（当然配合遮挡剔除）。如果球完全在视野锥之外，这是平凡的剔除情形，直接处理下一个物体。但如果球与视锥相交（更准确地说，与一个或多个裁剪平面相交），我们就得检查物体的包围盒是否有一维远大于另外两维。如果是，说明包围球比物体本身大得多！这时最好也把包围盒与视野锥做测试，因为它可能被剔除。一个很好的例子是高柱子，如图 29-4 所示。

29.7 一点提醒

记住，遮挡剔除在物体含大量多边形时效果最好。对比如 300 个三角形的物体，即便屏幕上有几百个，遮挡查询也帮不上多少忙。速度可能略有提升，但取决于 CPU 负载以及 CPU 与 GPU 之间的速度比。一块快 GPU 配上慢 CPU 会让应用受 CPU 限制，遮挡测试就帮不上什么忙了。

反之，如果每个模型的多边形很多（超过 1,000 个是个不错的起点），遮挡剔除就能尽显威力。加速可能超过一倍（当然取决于场景），而且几乎是免费的。渲染也不会有明显变慢——即便所有被测物体最终都可见！

29.8 一个应用：镜头光晕

遮挡查询技术的另一个有用应用是渲染镜头光晕。见图 29-5 与图 29-6。镜头光晕是很好的效果，能帮游戏增加真实感，但要想准确渲染它们，很容易深陷问题之中。

问题在于，镜头光晕不只是光源周围漂亮的光环：它是相机镜头的效果，这意味着它们不能被场景中的物体部分遮挡。因此镜头光晕要么完全可见，要么完全不可见，所以镜头光晕必须叠加在先前已渲染的场景之上。

渲染一个镜头光晕并不难：你只需渲染一个矩形，用漂亮的镜头光晕辉光或光环纹理填好。但问题出现在判断镜头光晕可见性的时候。理论上听起来不算太糟，因为你「只需」渲染整个场景，然后把每个带镜头光晕的光源的深度值，与深度缓冲中存的值做比较。如果光源的深度值更靠近观察者，光晕就可见。

不幸的是，检查深度缓冲的值需要从深度缓冲读取——这对 GPU 不太友好。另一个选择是绕开深度缓冲的值，改为从每个光源向观察者投射一条射线。如果射线能到达观察者，镜头光晕就可见。这听起来也相对简单，但当你要穿过一个带 alpha 测试纹理的多边形（例如树叶）投射射线时，问题就来了。因为 alpha 测试会在纹理 alpha 通道值低于某个阈值（通常是 0.5）的地方剔除像素，纹理只会在某些位置写入深度缓冲。要在 CPU 上准确模拟这一点，就得做完整的纹理映射，那是极其缓慢的操作。

那么，我们究竟怎样高效地测试镜头光晕的可见性？

29.8.1 用老办法渲染镜头光晕

不用遮挡查询，我们肯定需要访问深度缓冲来判断可见性。但从深度缓冲读取不可避免地会让图形管线停顿，因为 GPU 需要渲染完队列中的所有多边形，才能生成正确的深度缓冲图像。更麻烦的是，Direct3D API 起初根本不允许从深度缓冲读取（好吧，少数场合可以，但实际完全不可用）。有办法绕过这一限制，但那真是奇怪的做法，超出本章范围。好吧——看来我们陷进死胡同了。

OpenGL 让从深度缓冲读取变得容易，所以我们有机会绕过这个 GPU 停顿。我们可以把所有深度缓冲读取批量推迟到帧末，甚至放在镜头光晕实际渲染之后。这会让镜头光晕的可见性结果落后一帧，但在这种情境下完全可以接受。遗憾的是，尽管这一优化带来一些速度提升，却并不大，我们还得再激进一些。又一次。

读深度缓冲值的时机可以放在之后，即 SwapBuffers 调用之后、下一帧渲染开始之前。这会给我们争取一些时间，因为 GPU 可能正好渲染完上一帧，而这段时间 CPU 还在为当前帧计算 AI 之类的工作。于是，渲染一帧的算法大致如下：

  1. 做 AI、物理与碰撞检测。
  2. 做渲染之外的其他事情。
  3. 读取镜头光晕的深度值（这些来自上一帧）。
  4. 清除深度缓冲。
  5. 做渲染。
  6. 渲染镜头光晕。
  7. 交换缓冲。

尽管这一做法能消除相当一部分 GPU 停顿，仍有问题。GPU 停顿的开销取决于 GPU 与 CPU 速度之比。讽刺的是，这意味着在更快的 GPU 上停顿的代价更大。另一个问题更严重：没人保证 SwapBuffers 调用之后深度缓冲的内容仍然完好！在当今所有 GPU 上，深度缓冲内容都能在 SwapBuffers 之后存活，但你不能指望这一点，因为情况会变。更糟的是，多重采样抗锯齿方式在交换之后的深度缓冲内容上可能产生一些讨厌的副作用。基本上，这是有风险的做法，只应作为最后的退路。

总结起来：我们确实需要遮挡查询来救场！

29.8.2 用新办法渲染镜头光晕

到这里你大概能看出思路了。我们可以用遮挡查询功能，在镜头光晕光源的屏幕位置与深度处「渲染」一个像素（开启深度测试，但关闭深度写入与颜色写入），来测试光晕的可见性。然后看有多少像素通过了遮挡测试。如果有一个像素通过，镜头光晕就可见。为把 GPU 停顿的影响降到最小，我们在本帧发起遮挡查询，在下一帧读取结果。

何必止步于此？由于性能损失太大，直接读深度没给我们多少实验空间，所以每个镜头光晕读多个像素是根本不可能的。但用遮挡查询，我们就能查明一个镜头光晕实际有多少可见。不必只查一个像素得到是或否的答案，我们可以渲染一块像素（比如 16x16），看其中实际渲染成功的比例。然后可以用这个比例来调制镜头光晕的亮度。这样光晕的过渡更平滑，也不必费心写专门的淡入淡出程序来防止光晕突然出现或消失。要测试的像素数，可以很容易地由镜头光晕在屏幕上的大小、或光晕光源到观察者的距离，或两者共同确定。

这是很好的实验土壤，但有一点是肯定的：效果会很好看，而且几乎不会给 GPU 带来什么负担。

29.9 结论

乍看之下，遮挡查询像是非常强大的工具——它确实是。但与任何工具一样，要有效使用它需要一定的技巧与知识。你需要能识别出它能派上用场的场合。

本章只给出了两个高效使用这一技术的例子。当然，你不必止步于此：它能做的事还有很多。例如，遮挡查询可以用来根据物体占据的像素数确定几何细节层次。你甚至可以在可见表面判定算法里使用它。

与任何技术一样，遮挡查询会演进。起初它会被用于相当简单的任务。但随着各种障碍被清除，我们预期程序员会为它找到惊人的新应用。运气好的话，本章已经帮你开了个头。接下来真正的探索就靠你了。
