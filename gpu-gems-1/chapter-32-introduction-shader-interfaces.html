第 32 章　着色器接口入门

Matt Pharr
NVIDIA

Cg 1.2 的发布为 Cg 编程语言引入了一项重要的新特性，称为着色器接口。着色器接口提供的功能类似 Java 或 C# 的接口类以及 C++ 的抽象基类：它们允许编写调用抽象接口的代码，而不必知道该接口的具体实现是什么。用户必须把实现了程序中用到的接口的对象提供给 Cg 运行时，运行时随后负责组合出最终在硬件上运行的着色器代码。

面向对象语言为开发大型软件系统提供这类抽象机制，动机与此不同：把这项特性加入 Cg，是为了让在运行时用多份源码片段拼装着色器变得容易。着色器接口允许应用通过组合实现了明确功能块的模块化片段来构建着色器，从而在创建着色效果时给应用更大的灵活性，并帮助隐藏硬件配置的限制，同时不降低最终在 GPU 上运行的编译代码的质量与效率。

例如，考虑编写一个片元程序，它需要计算表面的着色颜色，同时支持多种不同类型的光源：点光源、聚光灯、带阴影贴图与过程化定义的距离开关函数的复杂投影光源等等。一种很低效的做法是往程序里传入「光源类型」参数，再用一串 if 判断决定使用哪种光源模型。另一种做法是用预处理器，让应用借助 #ifdef 保护，根据实际使用的光源模型手动编译一个专用版本的程序。这种做法有些笨重，而且不能优雅地扩展到多个光源——尤其是当光源数量事先也未知时。

着色器接口为这类问题提供了类型安全的解决方案。它们的做法既减轻了程序员的负担，又不牺牲性能。开发者可以编写通用着色器，把大部分功能以着色器对象接口（例如一个基本的「光源」接口）的形式表达出来。随着这些接口有了新的具体实现，旧着色器无需重写就能使用它们。使用这项特性的应用也不必再实现字符串拼接例程来即时合成 Cg 源码以解决这个问题——从而避开既容易出错又笨重的做法。

本章介绍着色器接口的基本语法，以及它们如何与 Cg 编译器和运行时配合使用。为了说明着色器接口可能的应用，我们随后给出三个在 Cg 中使用它们的例子：(1) 在两种向量归一化方法之间选择；(2) 在着色器中支持数量可变的光源；(3) 以通用、分层的方式描述材质与纹理。

Cg 1.2 的另外两项新特性与着色器接口相辅相成，同时提升了着色器的灵活性与效率。第一项是可变长数组，允许程序员声明和使用没有固定大小的数组。数组大小必须在程序执行之前提供给 Cg 运行时。这项特性在编写使用数量可变的光照参数组、蒙皮矩阵等的着色器时特别方便。第二项特性是能把着色器参数标记为常量值；编译器可以利用某个参数是常量这一信息，大幅改进代码优化效果。例如，仅基于常量参数的 if 判断可以在编译期完整求值，编译器可以据判断结果丢弃 if 之后代码块中的全部代码，或者无条件执行它。

32.1 着色器接口基础

我们从一个简单例子开始：一个片元程序用着色器接口在两种向量归一化方法之间选择，一种基于立方体贴图查找，一种基于数值计算归一化向量。应用可能想根据可用图形硬件的能力，在运行时在这两种向量归一化方法之间选择，以获得最佳性能。这是个简单的例子，但有助于传达着色器接口背后的一些关键想法。

首先，我们需要描述一个用于向量归一化的通用接口。关键字 interface 引入一个新接口，它必须用一个合法标识符命名。接口提供的方法随后在花括号之间声明，接口声明以分号结束。

interface Normalizer { float3 nrm(float3 v); };

接口内部可以声明多个方法，适用通常的函数重载规则。例如，我们也可以声明一个 half3 nrm(half3) 函数，编译器会根据传入向量的类型选择合适的那个。

有了这个声明，我们就可以编写一个把 Normalizer 接口实例作为参数的 Cg 程序。代码清单 32-1 展示了一个非常简单的片元程序，它从单个点光源计算漫反射光照项。Normalizer 接口中的 nrm() 函数被调用了两次：一次用于归一化从光源位置指向被着色点的光线向量，一次用于归一化顶点着色器传来的插值法线。

借助着色器对象接口，这段着色器可以基于某种绑定到 normalizer 的 Normalizer 实现来编写，而不必知道运行时实际会如何做归一化。

接下来我们需要定义该接口的一两个实现。首先是 StdNormalizer，它用 Cg 标准库例程 normalize() 对向量做归一化，该例程用向量的长度去除它的各分量。我们定义一个新结构体，并在结构体名后用冒号加上它所提供接口的名字，以此表明它实现了 Normalizer 接口。既然承诺实现该接口，结构体就必须为接口中声明的所有函数给出实现。与 Java 和 C# 一样，方法的实现必须定义在结构体定义内部。

示例 32-1　用着色器接口隐藏向量归一化技术细节的简单片元程序

float4 main(float3 Pworld
            : TEXCOORD0, float3 Nworld
            : TEXCOORD1, float3 Kd
            : COLOR0, uniform float3 Plight, uniform Normalizer normalizer)
    : COLOR
{
  float3 L = normalizer.nrm(Plight - Pworld);
  float3 C = Kd * max(0, dot(L, normalizer.nrm(Nworld)));
  return float4(C, 1);
}
struct StdNormalizer : Normalize
{
  float3 nrm(float3 v) { return normalize(v); }
};

我们也可以定义一个用立方体贴图归一化向量的着色器对象，其中纹理的各个面已被初始化，使其保存对应方向上的归一化向量。在下一段代码中，CubeNormalizer 在其结构体内声明了一个 samplerCUBE 参数来保存这张立方体贴图，它对 nrm() 的实现则按通常方式使用它。

struct CubeNormalizer : Normalize
{
  samplerCUBE normCube;
  float3 nrm(float3 v) { return texCUBE(normCube, v).xyz; }
};

对于像前面代码中 normalizer 这样带接口参数的程序，我们需要用 Cg 运行时在程序执行前指定接口的某个具体实现。首先，我们要告诉运行时在我们调用 cgCreateProgram() 或 cgCreateProgramFromFile() 时不要像默认那样立刻尝试编译传入的程序。否则编译会失败，因为接口还没有绑定到具体实现。cgSetAutoCompile() 例程控制这一行为；这里我们把它设为在我们明确要求之前不编译程序。（cgSetAutoCompile() 还有其他设置，可以按需自动重新编译程序，不过可能要付出多余重编译的代价。）

cgSetAutoCompile(context, CG_COMPILE_MANUAL);
CGprogram prog =
    cgCreateProgramFromFile(context, CG_SOURCE, "frag.cg", profile, NULL, NULL);

cgCreateProgramFromFile() 返回的 CGprogram 句柄此时还不能载入 GPU；我们需要先把一个 StdNormalizer 结构体实例连接到程序的 normalizer 参数上。幸运的是，运行时允许我们完全通过 Cg 运行时 API 调用创建 StdNormalizer 结构体实例。我们用 cgGetNamedUserType() 调用把字符串类型名「StdNormalizer」转成 CGtype 值，再用该类型调用 cgCreateParameter()，凭空创建一个 StdNormalizer 实例。

CGtype nrmType = cgGetNamedUserType(prog, "StdNormalizer");
CGparameter stdNorm = cgCreateParameter(context, nrmType);

如果 StdNormalizer 的结构体内部带有参数，我们现在就可以用 cgSetParameter*() 例程或配置相关的参数设置例程来初始化它们，包括把纹理单元绑定到采样器的例程，不过对 StdNormalizer 我们不必操心这些。（但对 CubeNormalizer 结构体的 normCube 参数，我们确实需要绑定一张合适的立方体贴图。）

创建好 StdNormalizer 实例之后，剩下的就是从 main() 例程的参数表中取得该接口的参数句柄，并把刚创建的 StdNormalizer 连接到它上面。

CGparameter normIface = cgGetNamedParameter(prog, "normalizer");
cgConnectParameter(stdNorm, normIface);

现在程序已完全确定，没有未绑定实现的接口参数。最后我们手动编译该程序。完成之后，就可以按常规方式使用程序，把它载入 GPU 并用于渲染。

cgCompileProgram(prog);

如果之后想为这个程序实例换入另一个 Normalizer 实现，只需再次调用 cgConnectParameter() 连接新参数并重新编译新程序。此外，如果同一个 CGcontext 中有多个程序，它们都能共享同一个 StdNormalizer 实例，只需通过多次调用 cgConnectParameter() 把它连接到多个参数上——不必创建多个 StdNormalizer 实例。

32.2 灵活的光源描述

着色器接口更有意思的一个应用，是用它们来处理编写支持任意类型光源的 Cg 程序这一问题。结合 Cg 1.2 的另一项新特性——可变长数组，着色器接口为编写支持任意数量光源（且每个光源可以是完全不同类型的光源）的通用问题提供了一个干净的解决方案。

此前，这个问题的一种解法是为每个光源渲染一次场景，再把各通道的结果相加得到最终图像。这种做法效率低，因为它需要多次运行顶点程序，而且每次都要在片元程序中做不必要的重复计算。它也很笨重，因为新增一种光源就意味着要为已有每一个表面着色器针对新光照模型写一个新版本。有了着色器接口，如果我们用同一个光源接口实现了多种不同的表面反射模型，那么新增一种光源就不需要修改任何已有着色器的源码。

一个基本的通用接口，为多种不同类型光源的行为提供了良好的抽象：它把被着色点 P 传给光源。光源则负责初始化变量 L（给出 P 处入射光的方向），并返回到达 P 的光量。图 32-1 显示了以此方式从光源计算照明的典型设置。

interface Light { float3 illuminate(float3 P, out float3 L); };

有了这个接口，我们就可以定义一个实现它的简单阴影贴图聚光灯。这个聚光灯持有一张用于阴影贴图的 sampler2D，并用立方体贴图描述光的角向分布。光源的 3D 位置和它的颜色补全了光源的定义。本例中我们假定光源位置与被着色点的位置已在同一坐标系中表达，这样就不必操心把它们变换到共同坐标系。

这个光源的实现相当直接；光方向 L 用光源位置很容易算出，而到达 P 的光量是三者之积：光源颜色、阴影贴图查找得到的可见性因子，以及沿指向受光点的方向对聚光灯强度所做的纹理查找。见代码清单 32-2。

示例 32-2　作为 Light 接口实现定义的 SpotLight 光源

struct SpotLight : Light
{
  sampler2D shadow;
  samplerCUBE distribution;
  float3 Plight, Clight;
  float3 illuminate(float3 P, out float3 L)
  {
    L = normalize(Plight - P);
    return Clight * tex2D(shadow, P).xxx * texCUBE(distribution, L).xyz;
  }
};

用这个接口可以轻松实现各种各样的光源类型：点光源、方向光、把纹理投影到场景中的光源、线性或平方衰减的光源、用 1D 纹理贴图定义衰减的光源，以及许多其他类型。

在代码清单 32-3 的片元程序中，Cg 代码遍历照亮表面的所有光源，调用每个光源的 illuminate() 函数，然后累加每个光源的基本漫反射着色项。Cg 新的可变长数组特性让我们能在数组名 lights 之后用 [] 语法表示数组长度，从而声明长度不确定的数组。稍后我们会看到，在着色器最终执行之前，可以用 Cg 运行时在运行时设定可变长数组的元素个数。还要注意数组有一个 length 成员，给出其中的元素个数；这让我们能对可变长数组中的所有元素写循环，即使在不原生支持可变循环次数的配置上也可以。

示例 32-3　接受任意数量 Light 接口参数的片元着色器

float4 main(float3 Pworld
            : TEXCOORD0, float3 Nworld
            : TEXCOORD1, float2 uv
            : TEXCOORD2, uniform sampler2D diffuse, uniform Light lights[])
    : COLOR
{
  float3 C = float3(0, 0, 0);
  Nworld = normalize(Nworld);
  float3 Kd = tex2D(diffuse, uv).xyz;
  for (int i = 0; i < lights.length; ++i)
  {
    float3 L, Cl;
    Cl = lights[i].illuminate(Pworld, L);
    C += Kd * Cl * max(0, dot(Nworld, L));
  }
  return float4(C, 1);
}

在这个着色器能用于程序之前，必须用 Cg 运行时做两件事。第一，必须设定可变长 lights[] 数组的最终长度；第二，必须把数组中每个接口实例绑定到一个实现了 Light 接口的结构体实例上。对于第一个问题，Cg 运行时有一个设置可变长数组长度的例程：

void cgSetArraySize(CGparameter param, int size);

第二个问题按前一个例子的方式解决：调用 cgCreateParameter() 创建各个光源实例，再调用 cgConnectParameter() 把实例连接到光源接口数组中对应每个光源的条目。与前一个例子一样，同一个光源实例可以由同一 Cg 上下文中的多个程序共享。

由于这个着色器使用了着色器接口和可变长数组，我们可以编写能与 Light 接口的任何实现配合的着色器，也能轻松编写不需要硬编码绑定光源数量的着色器。我们以干净的方式写出了非常灵活的 Cg 程序，而且不必在运行时付出效率代价。只有在具体的光源数量及其各自类型确定之后，才会为程序生成最终的 GPU 指令，因此使用着色器对象和可变长数组特性没有性能代价。

注意，如果我们改用每个光源重渲染一次场景的方式解决这个问题，那么每一通道都得重新归一化 Nworld，并为 Kd 重做纹理查找。如果片元程序执行比这里更复杂的纹理操作，性能代价会相应更差。

32.3 材质树

最后一个例子展示接口的组合如何引出有趣的材质描述方式。图形学中描述复杂材质与纹理最成功的方法之一，是把它们分解成树或网络：把一组节点连起来，通过各节点执行较简单操作来计算复杂的着色模型。（Maya 的 HyperShade 和 3ds max 的材质编辑器是这种做法的两个著名例子。）这不仅是在内容创作应用中描述复杂材质的便捷方式，也是在应用中组织材质与纹理库的优雅方式，让它们在运行时构建表面描述时拥有很大灵活性。在着色器接口加入 Cg 之前，没有干净的办法在 Cg 程序中表达以这种方式描述的材质。

本节展示着色器接口如何让这种材质描述方法干净地映射到 Cg。这里我们区分材质与纹理：材质代表表面如何响应光照的完整过程化描述，纹理代表一个函数，它在某一点计算某个值，材质用它来体现表面属性在表面上的变化。

首先，我们需要定义一个材质接口。材质的职责是计算给定点处反射光的颜色，并考虑材质属性与来自光源的照明。它需要关于表面局部几何的信息（至少包括被着色点 P、该位置处的表面法线 N 和纹理坐标 uv），以及入射视线方向 I 和照亮该点的光源信息。注意我们把 Light 接口的可变长数组 lights[] 传给了材质接口的 color() 方法。

interface Material
{
  float3 color(float3 P, float3 N, float3 I, float2 uv, Light lights[]);
};

使用 Material 计算着色的片元程序很简单；我们只需要少量胶水代码，把正确的插值参数传入材质，并把结果作为片元颜色返回，如代码清单 32-4 所示。

示例 32-4　把几乎全部计算都委托给 Material 接口实现的片元着色器

float4 main(float3 Pworld
            : TEXCOORD0, float3 Nworld
            : TEXCOORD1, float3 Iworld
            : TEXCOORD2, float2 uv
            : TEXCOORD3, uniform Light lights[], uniform Material material)
    : COLOR
{
  Nworld = normalize(Nworld);
  float3 C = material.color(Pworld, Nworld, Iworld, uv, lights);
  return float4(C, 1);
}

我们可能先实现一个基本的 DiffuseMaterial，把漫反射颜色 Kd 来自何处的信息抽象出去。这样我们就不必为常量 Kd 的表面、由纹理贴图定义的 Kd、由过程化棋盘函数定义的 Kd 等等分别准备不同的 DiffuseMaterial 对象，而是定义一个 Texture 接口来隐藏这些可能变化的颜色值如何计算的细节。

interface Texture { float3 eval(float3 P, float3 N, float3 uv); };

现在 DiffuseMaterial 只需调用该接口的 eval() 函数，然后做通常的漫反射计算，如代码清单 32-5 所示。

以这种方式设计材质，我们就很容易把 DiffuseMaterial 与我们将来可能开发的任何 Texture 配合使用，无需修改其源码。随着我们积累起大量不同的 Material 实现（例如实现复杂 BRDF 模型的材质），这种正交性会越来越重要。

示例 32-5　表达为通用 Material 接口实现的漫反射着色模型——用 Texture 接口的一个实例来计算着色点处的漫反射系数。

struct DiffuseMaterial : Material
{
  Texture diffuse;
  float3 color(float3 P, float3 N, float3 I, float2 uv, Light lights[])
  {
    float3 Kd = diffuse.eval(P, N, uv);
    float3 C = float3(0, 0, 0);
    for (float i = 0; i < lights.length; ++i)
    {
      float3 L;
      float3 Cl = lights[i].illuminate(P, L);
      C += Kd * max(0, dot(N, L));
    }
    return C;
  }
};

要把这个 DiffuseMaterial 连接到代码清单 32-4 中 main() 的 material 参数上，我们需要先创建一个 DiffuseMaterial 结构体实例，再把 Texture 接口某个实现的实例连接到它的 diffuse 参数上。然后就可以把 DiffuseMaterial 连接到 main() 的 material 参数。

一个现成可用的 Texture 自然实现是 ImageTexture，它从 sampler2D 返回颜色。

struct ImageTexture : Texture
{
  sampler2D map;
  float3 eval(float3 P, float3 N, float3 uv) { return tex2D(map, uv).xyz; }
};

为方便起见，我们可能还想要一个总是返回常量颜色的纹理。这样当颜色是常量时，我们总能使用通用的 DiffuseMaterial，而不必另写一个 Material 实现。幸运的是，这样组织代码没有运行时性能代价。

struct ConstantTexture : Texture
{
  float3 C;
  float3 eval(float3 P, float3 N, float3 uv) { return C; }
};

更有意思的是，我们可以定义一个自身使用 Texture 接口来完成工作的 Texture 实现。在下面这段代码中，BlendTexture 按第三个 Texture 指定的混合量在两个 Texture 之间混合。当然，这里的三个 Texture 每一个都可以是完全不同的类型：一个可能从 2D 图像贴图中查找值，一个可能总是返回常量值，第三个可能过程化地计算值。

struct BlendTexture : Texture
{
  Texture map1, map2, amt;
  float3 eval(float3 P, float3 N, float3 uv)
  {
    return lerp(map1.eval(P, N, uv), map2.eval(P, N, uv), amt.eval(P, N, uv));
  }
};

着色器接口让我们能以通用方式实现 BlendTexture，无需事先知道某个 BlendTexture 实例会用到哪些具体的 Texture 类型。与在 DiffuseMaterial 中初始化 Texture 接口参数一样，我们需要用 Cg 运行时把实现了 Texture 接口的结构体实例连接到 map1、map2 和 amt。要扩展系统中可用的纹理类型也很容易，只需实现新的 Texture 类型，并扩展应用以创建它们并按需连接到接口参数上。无需修改任何已有的类型。

既然已经开始编写自身持有接口的接口实现，我们就可以把这个想法用到许多其他地方。例如，我们可以实现一个 Material，把雾的大气模型应用到任何其他 Material 上，如代码清单 32-6 所做的那样。

这样我们就不必为所有材质都加上雾的支持。只需用 FogMaterial 做一次，把一个 FogMaterial 实例连接到程序 main() 函数的参数上，并把 FogMaterial 的 base 实例变量设为原本没有雾的材质。

示例 32-6　修改另一个 Material 返回值并混入雾项的 Material

struct FogMaterial : Material
{
  Material base;
  float3 fogAtten, fogColor;
  float3 color(float3 P, float3 N, float3 I, float2 uv, Light lights[])
  {
    float3 C = base.color(P, N, I, uv, lights);
    float fogFactor = exp(-P.z * fogAtten);
    return lerp(C, fogColor, fogFactor);
  }
};

32.4 结论

着色器接口和可变长数组并没有让 Cg 能写出此前写不出的程序。但它们让应用更容易在运行时用代码片段拼装着色器，从而大大简化了许多经典过程化着色做法的实现。它们以高效的方式提供这些功能，在 GPU 上没有性能损失；唯一的代价是编译时的一些运行时与编译器开销。

本章描述了这项功能的几个例子。应用可能要求更复杂的光源接口——例如，加入一种方式来表达只贡献漫反射、不产生镜面高光的光源，如 Barzel 1997 所述。应用也可能要求更复杂的纹理接口，带有被着色点处表面偏导数的信息。可以在我们这里例子所用的接口上加入许多推广。

例如，Texture 接口可以推广，把纹理坐标从何而来的决定也抽象出去：增加一个描述纹理坐标生成的接口（例如球面映射、柱面映射等）。该接口的一个纹理坐标变换实现，可以通过矩阵、过程或纹理贴图查找来变换生成的纹理坐标。

还可以实现许多有用的 Material 接口，例如双面材质，根据看到的是表面哪一侧在两个其他材质之间选择；或者混合材质，按某个 Texture 或菲涅尔反射项在两个材质之间混合。用这些接口以通用方式表达凹凸贴图大概也会很有用。

《Cg 1.2 用户手册》对着色器接口与可变长数组的语言语法有详尽说明，也描述了为这些特性新增的 Cg 运行时调用。
