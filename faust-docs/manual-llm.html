配合 LLM 使用 Faust

大语言模型（LLM）可以帮助编写、解释、调试和记录 Faust 程序。它们适合把某个音乐或信号处理的想法变成初稿、提出变体、查找标准库函数，并驱动一个简短的「编译—试听—修改」循环。

它们不应取代 Faust 编译器、库文档或试听测试。生成的 DSP 代码仍然必须编译、检查、测量并试听。

Faust 很适合作为 LLM 辅助编程的目标，因为它紧凑、是文本形式的，并且围绕信号流组织。一个 .dsp 文件不只是模型生成的代码：它是模型、Faust 编译器与人类审阅者共享的可审计产物。组合算子描述路由，编译器检查元数与反馈结构，SVG 框图让不简单的信号流变得可见。

对 DSP 来说，这通常比让 LLM 写出完整的 C++ 实现更好的分工。LLM 写一份紧凑的 Faust 描述，Faust 编译器再生成 C++、WebAssembly、LLVM IR、Rust、Cmajor、JAX 或其他目标。

典型用途

当任务有明确的声音、界面或诊断目标时，LLM 最有用：

  • 起草振荡器、滤波器、效果器、乐器、物理模型或分析补丁；
  • 把已有的 Faust 代码按信号流解释清楚；
  • 把框图想法翻译成 Faust 组合算子；
  • 为某项任务推荐标准库函数；
  • 添加控件、元数据、MIDI 映射或复音结构；
  • 调试编译器错误以及元数/路由问题；
  • 在保持现有接口的前提下生成小的变体；
  • 为用户或维护者编写 DSP 文档。

效率最高的循环是：

prompt -> generated Faust -> compile -> inspect JSON/SVG -> listen/measure
       -> targeted correction -> repeat

为 Faust 代码写提示词

提示词中包含 Faust 特有的约束时效果更好：

  • 想要的声音或处理任务；
  • 输入与输出的数量；
  • 控件名称、范围与默认值；
  • 是否使用 import("stdfaust.lib");；
  • MIDI、复音、元数据或目标平台的要求；
  • 可读性与优化哪个更重要。

示例：

Write a Faust stereo chorus effect.
Requirements:
- use import("stdfaust.lib");
- two audio inputs and two audio outputs;
- controls: rate [0.05..8] Hz, depth [0..1], feedback [0..0.95], mix [0..1];
- keep the code readable;
- return only the .dsp code.

调试时，附上编译器诊断信息和当前完整程序：

This Faust program fails to compile. Explain the error and return a corrected
version. Preserve the public controls and stereo I/O.

<paste compiler diagnostic>
<paste Faust code>

做细化时，要求做最小改动：

Modify only the filter section so the resonance is safer at high cutoff values.
Keep all UI paths and control ranges unchanged.

需要检查什么

LLM 常常生成看起来像样的 Faust 代码，但仍需修正。常见问题包括：

  • 缺少 import("stdfaust.lib");；
  • 编造的库名或错误的函数元数；
  • 输入或输出数量不对；
  • : / , / <: / :> / ~ 使用不当；
  • 延迟或反馈的拓扑不对，尤其是在 ~ 附近；
  • 不安全的界面范围或默认值；
  • 代码能编译，但会削波、自激、出现非规格化数或输出静音；
  • 库调用的参数顺序或单位有误，代码能干净地编译，实现的却是错误的 DSP。

一定要跑编译器。可能的话，还要检查 JSON 元数据和 SVG 框图：

faust -lang cpp mypatch.dsp -o /tmp/mypatch.cpp
faust -json mypatch.dsp -o /tmp/mypatch.json
faust -svg mypatch.dsp

编译器能廉价证明的东西就把它当作权威：语法、符号是否存在、元数、路由，以及许多反馈形状错误。它无法证明音乐品味、参数缩放是否正确、预期的单位、在任意参数轨迹下的稳定性，也无法判断是否选用了最合适的库基元。

让 LLM 使用库文档

当 LLM 能查阅真实的 Faust 库文档而不是靠记忆时，可靠性高得多。一个实用的检索流程是：

  1. 载入库的通用 LLM 入口；
  2. 在生成的库索引中搜索相关函数；
  3. 提供准确的名称、签名、I/O 形状、参数含义、示例和许可信息；
  4. 要求模型只使用这些函数；
  5. 编译结果，并把诊断信息反馈到对话中。

Faust 库站点在 Contributing / LLMs 一节中说明了其面向 LLM 的导出内容，并发布了一个专用入口：

https: // faustlibraries.grame.fr/llms.txt

库仓库也可以从 .lib 源文件生成机器可读的 JSON 导出。生成器从 stdfaust.lib 出发，顺着 library("...") 与 import("...") 指令，提取有文档的符号，字段包括摘要、用法、参数、注释、可推导时的 I/O 数量、测试代码、参考、源码位置，以及每个符号的许可元数据。

在 Faust 库的本地检出中常用的命令：

make doc-index
make doc-index-split
make doc-index-commercial

拆分式布局通常最适合 LLM 工作流，因为它先加载紧凑的全局索引，再按需检索某个模块或符号。商业兼容的导出对许可敏感的生成很有用；它是一种实用的过滤，而不是法律意见。

本地查询工具可以直接使用：

python3 scripts/faust_doc_api.py --pretty search_faust_lib reverb --limit 5
python3 scripts/faust_doc_api.py --pretty get_faust_symbol de.delay
python3 scripts/faust_doc_api.py --pretty list_faust_module delays --limit 20
python3 scripts/faust_doc_api.py --pretty get_faust_examples delay
python3 scripts/faust_doc_api.py --pretty explain_faust_symbol_for_goal \
  re.springreverb "build a metallic spring reverb"

写提示词时，优先使用简洁的检索上下文：准确的签名、参数顺序、单位、I/O 形状、一句话用途、用法示例和许可状态。只给一串名字用处不大，因为未知符号编译器本来就会拒绝。真正有价值的信息是发现性、语义，以及模型在训练中没见过的自定义库文档。

示例：

Use only these retrieved Faust functions:
- fi.lowpass(...)
- de.delay(...)
- si.smoo

All functions above are acceptable for the target license policy.
Build a mono tape-delay effect with delay time, feedback, tone, and wet/dry mix.
Do not invent other library functions.

Claude Code 的 Faust 插件

Julius O. Smith 的 /faust 技能也打包成了可安装的 Claude Code 插件。在 Claude Code 中：

/plugin marketplace add josmithiii/gists
/plugin install faust@josmithiii-gists

安装之后，Faust 技能会在遇到 Faust 相关请求时自动触发，无需显式调用。它带有上文所述的同样简洁的 Faust 入门材料和惯用示例，因此模型在生成或审阅 Faust 代码之前就已具备关于语法、元数、组合算子、递归和标准库用法的有用背景。

MCP 与交互式会话

模型上下文协议（MCP）让 LLM 可以调用工具，而不只是生成文本。对 Faust 而言，MCP 工具可以：

  • 检查语法；
  • 编译 DSP；
  • 在浏览器或 Node/WebAudio 运行时中启动音频；
  • 从生成的 JSON 中列出界面参数；
  • 设置并读取参数值；
  • 返回音频指标；
  • 搜索 Faust 库文档。

一次最简单的交互可以是这样的：

compile_and_start(faust_code="process = os.osc(440) * 0.2;")
get_param_values()
set_param(path="/freq", value=220)
set_param(path="/gain", value=0.1)

这样就形成了两个反馈回路：

  • 符号层面：源码 -> 编译器 -> 错误、JSON、生成的代码、框图；
  • 感知层面：音频 -> 试听、峰值/RMS、频谱、稳定性检查。

基于浏览器的 MCP 系统，如 faustbrowser-mcp 或 faustcode，把音频执行交给真实的浏览器运行时。一个小型服务器暴露 MCP 工具，并用 Web Audio、可用时的 Web MIDI、控件、电平表和框图，把 LLM 客户端与浏览器 UI 连接起来。这非常适合做原型、教学和音色设计，但生成的 DSP 在用于生产之前仍需审阅。

实际验证

对于生成或修改过的 Faust 代码，要检查：

  • 用目标 Faust 版本编译；
  • 输入/输出元数；
  • 界面名称、范围和默认值；
  • 静音、削波、NaN 和失控的反馈；
  • 极端参数值；
  • 若使用，MIDI 与复音元数据；
  • 受限目标平台上的 CPU 开销；
  • 不简单路由的框图。

对于不简单的补丁，让 LLM 用 Faust 的五种组合算子解释信号图：

~   feedback
,   parallel composition
:   sequential composition
<:  split
:>  merge

然后把解释与生成的框图对照。不一致通常意味着代码或解释有一个是错的。

提示词模式

生成：

Write a Faust DSP for a mono-in/stereo-out shimmer reverb prototype.
Use import("stdfaust.lib"). Keep the code compact and compilable.
Controls: mix, decay, shimmer, tone. Return only Faust code.

解释：

Explain this Faust program as a signal-flow graph. Identify inputs, outputs,
UI controls, and feedback paths.

修复：

This code does not compile with Faust. Fix the smallest possible part.
Preserve all UI labels and ranges.

审阅：

Review this Faust effect for unsafe feedback, clipping risk, parameter ranges,
and library calls that may have wrong units or argument order.

使用检索到的文档：

Here are the exact library functions available:
<paste retrieved docs>

Use only these functions. Do not invent library names.

配合 LLM 使用 Faust 的项目

若干公开产品与应用开始采用上文所述的同一套总体循环：自然语言提示、生成或受控的 DSP、自动检查、浏览器或硬件预览，以及导出为可运行的结果。例子包括：

  • Chaos Audio AI FX Builder，面向 Stratus 与 Nimbus 硬件平台。Chaos Audio 描述的系统是：用户用平实的英文写出效果器提示，服务在 Faust 中生成新的效果算法，自动迭代调试并改进，然后把结果部署到踏板。该构建器还会把生成的 Faust 代码展示出来，供想检查或编辑 DSP 的用户使用。
  • pluginmaker.ai，一个基于浏览器的 AI 平台，可从文本提示生成 VST/AU 乐器与效果器。其工作流面向音乐人而非 DSP 开发者：描述插件，在浏览器中预览，定制声音与界面，然后导出供 DAW 使用的插件。
  • MAGDA 及其开源的 magda-core 仓库。MAGDA 是一个围绕自动化、变换和快速音乐迭代构建的 DAW。它包含能理解会话、在内部 DSL 中生成命令、并可操作音乐结构与设备的 AI 代理。Faust 作为其效果器组和实验性 Faust 设备的 DSP 层出现，这又是一个 LLM 控制更大的音乐环境、而 Faust 仍是可审计的音频处理语言的例子。
  • Persistent Faust 由 KageProduction 开发，是一个可编程的 DSP 平台，而非固定的单一用途音频效果器。它可以根据用户需要实时变形成多种插件。用户可以制作 EQ、压缩器、调制效果、混合效果和实验性音频工具。内置的网页 GPT 助手帮助生成和改进 Faust DSP 代码，即使不是程序员也能用。
  • WebAssembly Music——一次代理式作曲。一首用 WebAssembly Music 完成的歌——那是一个浏览器 DAW，音符、编曲、合成器音色（用 Faust DSP 语言编写）和响应式视觉效果全都是编译成 WebAssembly 并在页面中实时运行的代码。这首曲子是通过与浏览器内的 AI 代理对话做出来的。整个故事——包括代理编写乐器、编辑编曲并推送到 GitHub 的截图——都在这篇文章里。
  • Pulp 是一个跨平台的音频插件与应用框架。MIT 许可，C++20 核心，Apple 平台用 Swift，JS 脚本化的 GPU 界面。这个技能让 Pulp 能用 FAUST 函数式语言并借助离线 C++ 代码生成，实现高性能音频信号处理。
  • FaustWave IDE 是一个以 Faust 为核心、本地优先的音频 DSP IDE——可视化节点图与原始 Faust 源码并排显示，通过共享主总线输出实时音频，还有步进音序器、MIDI、带每轨效果器的调音台、设备端知识库，以及用于分享补丁、库和包集的 Hub。
  • Incant Audio 把自然语言描述变成实时的 VST3 音频效果器和复音合成器。用平实的英文描述你想要的声音或信号处理器，Incant Audio 就会生成 Faust DSP、校验、JIT 编译，并把原生机器码加载进运行中的音频插件——配有动态 GUI 控件——全程不中断播放。
  • Radium V8.0 是 Kjetil Matheussen 的 tracker 式音乐编辑器，它附带了一个新的 Faust Dev 2 乐器，使用 Faust 自带的库来生成声音。它提供一个 LLM 提示框：输入诸如「Autotune」「more wobbly」「more professional」或「give me a dreamy atmospheric sound」这样的指令，几秒后就能生成可用的 Faust 代码并运行起来——无需手动编码。该 LLM 请求经过精心调校，即使使用更小更快的模型也能生成合法、好听的 Faust 代码（免费用的是不带思考的 DeepSeek Flash），该乐器也可以配置成使用用户自己账号访问的其他模型。
  • nagi 是一个本地优先的桌面应用，用节点图和 Faust 源码来设计 VST3 与 CLAP 插件。它的设备端 AI 助手可以根据自然语言指令起草 Faust DSP 例程或界面布局；结果可以在浏览器中预览，并构建为原生插件。
  • Han-Vibe 由 Zhengyang Ma 提出（ICMI 2026），它把通过 DawDreamer 进行的 Faust DSP 编辑与 LLM 驱动的参数、音序和代码改动结合起来，用于现场音乐演出。作者的 HANMAI-LIVE 原型源码包含 Python 引擎和八件 Faust 乐器。

这些项目对 Faust 来说是有用的参照，因为它们展示了 LLM 如何从孤立的代码片段走向完整的产品工作流。它们也让本页的审阅规则更加重要：生成的 DSP 在交付给用户之前，应当编译、测试、检查，并核对许可约束。

局限

Faust 降低了一些 LLM 风险，但并没有免除审阅。它的编译器能证明关于连线、元数和反馈形式的重要结构性事实；它不能证明混响好听、压缩器手感符合预期，也不能证明物理模型与目标乐器相符。

当前的 LLM 在 Faust 上的训练数据也比 Python、JavaScript 或 C++ 少。它们通常知道基本算子，但在惯用的 stdfaust.lib 用法、递归模式和长尾库函数上可能不够熟练。更多公开、许可清晰、写法地道的 Faust 示例，以及带测试的「提示词到 Faust」示例，能直接改善这一状况。

把 LLM 的输出当作草稿：编译它、测试它、检查元数据和框图、批判性地试听，并让人工审阅始终留在循环中。
