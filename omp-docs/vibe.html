Vibe 模式

把一个 omp 会话变成一位总监，协调持续运行的快速和强力编码工作者，检查它们的工作，并让每条工作流持续推进。

从一次对话指挥多个工作者

Vibe 模式适合受益于委派的工作：包含独立前端和后端改动的功能、迁移加审查，或可以拆分为文件互不相交工作流的大型清理。你的主 omp 会话会变成一位总监。它读取并验证仓库，而持续运行的工作者负责搜索、编辑、运行命令和构建。

在同一条命令中直接开始任务：

/vibe Split this release into independent workstreams. Have a fast worker update the mechanical call sites and a good worker review the migration and compatibility risks. Verify both before reporting done.

也可以先进入模式，再描述工作：

/vibe

模式启用时，状态行会显示Vibe。准备离开时再次运行 /vibe；omp 会停止剩余的工作者，并恢复进入模式前启用的工具。

Vibe 模式会增加协调、模型使用和监督开销。对于小型的顺序编辑，普通的 omp 提示词通常更简单。

选择 fast 或 good

你不需要启动单独的终端，也不需要提供机器可读的请求。用日常语言告诉总监你想要哪类工作者：

工作者适合的工作典型指令
fast机械、定义明确且批量大的工作：重命名、直接的测试、样板代码、数据收集，以及应用已经决定的模式。“使用快速工作者更新 packages/ui 中的每个调用方；不要改变公共 API。”
good设计、调试、审查、有风险的改动、多文件重构，以及判断比延迟更重要的工作。“使用强力工作者追踪这个竞态，提出最小的源代码修复，并用现有的复现验证。”

快速工作者不只是优先级较低的任务：它通常使用你的小型低延迟模型角色。强力工作者通常使用你的任务/强力模型路径。如果快速工作者停滞或遇到架构决策，让总监把决策或审查交给强力工作者，不要反复重启同一项工作。

每个工作者都有自己的对话，并会记住后续指令。让一个工作者专注一条工作流，这样上下文才有用。工作者启动时没有总监对话，因此总监必须为每个工作者提供一份自包含的简报。

提供能够独立完成的工作流

一条有用的首个提示词会说明所有权、边界和证明方式：

Coordinate these in parallel:

1. Fast worker: own `packages/parser/src/` and update the mechanical API call sites. Preserve behavior and run the parser's focused tests.
2. Good worker: own `packages/server/src/` and design the compatibility change. Do not edit parser files. Exercise the failing request after the fix.
3. When both finish, read their changed files, check that the contracts agree, and have the good worker review the integration.

Do not let both workers edit the same file. Stop and ask me if the shared interface must change.

在相关时务必包含这些细节：

  • 工作者负责的文件或子系统；
  • 结果和可观察的验收标准；
  • 不得改变的 API、格式或行为；
  • 证明结果的命令或场景；
  • 明确的非目标和安全边界；
  • 另一条工作流将要使用的契约。

并行工作者共享同一个工作树，除非总监选择了其他受支持的隔离策略。两个工作者编辑同一个文件可能互相覆盖或产生冲突。优先按文件分离所有权，在派发前决定共享接口，并指定一个工作者来整合任何无法避免的共享文件。

监督工作

工作者运行时，你可以继续与总监对话。派发是异步的：总监可以启动另一条独立工作流，而不必等待第一条完成。

有用的提示词包括：

Show me every Vibe worker, its fast/good tier, current state, model, queued follow-ups, and latest activity.

Steer the parser worker now: preserve the legacy error code and add a boundary case before continuing.

When the server worker becomes idle, ask it to review the parser worker's final diff. Keep it in the same worker session.

Stop the docs worker; that workstream is no longer needed.

活动进行中发送的修正会尽可能被引导进正在运行的轮次。如果工作者无法立即接受，omp 会把它排队为下一轮。空闲的工作者会带着后续指令开始新一轮。你不需要判断属于哪种投递情况。

工作者的结果会自动返回总监对话。可见的工作者视图会区分正在启动、运行中、空闲或已终止的工作者，并包含它们的层级、轮次数、排队的工作、解析出的模型和最近活动。工作者名称或状态不清楚时，随时再次询问工作者名册。

不要把“工作者完成了”当成“任务已验证”。让总监：

  1. 读取工作者声称改动的文件；
  2. 将结果与原始约束进行比较；
  3. 解决跨工作流的假设；
  4. 把修正发回同一个工作者；
  5. 在报告完成之前运行或委派验收场景。

Vibe 模式下，总监有意使用面向读取的工具集。它负责验证和协调；工作者负责变更和命令执行。

停止工作并安全离开

这里有三种不同的控制方式：

  • 引导一个工作者：描述修正内容，并指出工作者或工作流。它的持久对话会保留。
  • 停止一个工作者：说“停止 <name> 工作者”。它的活动轮次和排队的后续指令会被取消，但其他工作者继续运行。
  • 退出模式：运行 /vibe。必要时，omp 会中止总监的活动轮次，停止每个剩余的 Vibe 工作者，将它们记录为终止状态，移除仅 Vibe 模式的控制，并恢复 Vibe 之前的完整工具集。

退出是安全的完成边界。不要仅仅假设空闲工作者已经消失：空闲意味着准备开始下一轮，而不是已终止。反过来，有意运行 /vibe 退出对该工作者作用域来说是最终操作；重新进入会启动新的工作者，而不会复活退出时被杀死的工作者。

如果你中断了总监当前的响应，Vibe 模式本身仍然开启。检查Vibe状态指示，询问工作者名册，然后继续监督，或运行 /vibe 执行完整拆除。

持久化、恢复与会话变更

Vibe 模式和工作者生命周期记录会随父会话保存。当你重新打开一个当前模式为 Vibe 的已保存会话时：

  • 已完成的工作者对话会作为带有子对话记录的空闲/停放工作者返回；
  • 总监可以用另一条自然语言指令继续这些工作者；
  • 进程停止时正在运行的工作会被标记为中断，不会自动重启；
  • 明确停止的工作者，或因有意退出 Vibe 而停止的工作者，会保持终止状态。

重启后，从这里开始：

List the restored Vibe workers. Summarize their last completed work, identify any turn interrupted by the restart, and wait for my approval before continuing it.

切换会话会让当前会话的 Vibe 工作者进入静默状态，并在适用时恢复目标会话记录的模式和工作者作用域。不过，在 Vibe 启用时，创建或结构性移动会话的操作会被阻止：启动新会话、分叉、移动和交接都要求你先运行 /vibe。这样可以防止工作者脱离拥有它们的父会话。

计划模式和目标模式与 Vibe 模式互斥，即使计划模式或目标模式处于暂停状态也一样。进入 /vibe 前先退出已有模式；进入 /plan 或 /goal 前先退出 Vibe。Vibe 活跃时，重置式循环也不可用。

模型与成本

快速和强力工作者会独立发起模型请求，因此并行工作者可以同时消耗 token。它们的成本会额外计入总监的模型使用量。对于紧密耦合的工作，使用更少的持久工作者；完成后停止工作者；快速工作者足够时，将强力工作者留给设计或审查。

默认设置遵循 omp 的正常工作者路由：

  • fast 使用捆绑的 sonic 工作者，通常通过小型模型角色解析；
  • good 使用捆绑的 task 工作者，通常通过任务角色或活动/默认模型回退解析。

在角色中设置具体选择器，并在~/.omp/agent/config.yml中将两个工作者定义路由到它们：

modelRoles:
  fast_worker: openai/gpt-5-mini
  good_worker: anthropic/claude-sonnet-4-5:high

task:
  agentModelOverrides:
    sonic: "@fast_worker"
    task: "@good_worker"

这样既能让面向用户的 fast 和 good 选项保持稳定，又允许你在一个地方更换提供商或模型。正常的重试和回退设置会应用到工作者请求。路由令人意外时，让总监显示解析出的模型。使用 /stats 检查一次运行之后或运行中的会话和工作者成本；/usage 报告的是提供商账户限额，而不是单条 Vibe 工作流的成本。

安全与权限

工作者是完整的编码代理：它们可以读取和写入文件、运行命令，并使用简报所需的其他已启用能力。总监的只读姿态不会让工作者也变成只读。

工作者会在派发后以无头方式运行，因此不要依赖每条命令执行时都会出现交互式确认。你配置的逐工具策略仍然有效。对于工作者绝不能使用的能力，请使用明确的 deny 策略；让凭据和敏感路径位于其作用域之外，并为提示词设置自己的边界。关于设置中的 tools.approval和审批模式，见相关说明。

在敏感代码上使用 Vibe 之前：

  • 选择获准接收仓库内容的模型和提供商；
  • 按工作流拆分访问权限，并避免在提示词中放入不必要的密钥；
  • 在配置中拒绝危险工具或命令类别，而不是只依赖文字说明；
  • 要求进行针对性验证和总监的最终通读；
  • 如果工作者的活动或输出不再符合简报，立即停止它。

启动多个工作者会同时增加能够修改工作树的参与者数量，以及编辑互相重叠的可能性。在高并发运行前提交或以其他方式保存重要工作，但不要让多个工作者并发操作同一个 Git 状态。

故障排查

  • /vibe 提示先退出计划模式或目标模式——这也包括已暂停的模式。完全退出该模式，然后再次运行 /vibe。
  • Vibe 指示器亮起，但没有工作开始——给总监明确的工作流、层级、文件、约束和验收检查。如果在你的审批模式下派发需要授权，请批准或拒绝可见的请求。
  • 工作者使用了错误的模型——要求显示解析出的工作者模型。检查快速工作者的 task.agentModelOverrides.sonic 和强力工作者的 .task，然后确认每个引用的 modelRoles 选择器都存在、提供商已启用且认证可用。新的工作者会采用修正后的路由。
  • 工作者处于空闲状态——空闲是健康且持久的状态；它已完成上一轮，正在等待。向同一个工作者发送下一条指令，或者如果工作流已完成就停止它。
  • 修正没有改变当前步骤——它可能因为当时无法引导轮次而进入了排队。询问工作者排队的后续指令并等待当前轮次结束，或者如果继续不安全就停止它。
  • 工作者已终止或找不到——让总监提供当前会话的名册。工作者所有权与父会话绑定；有意停止的工作者无法恢复。需要时，用一份新的自包含简报启动新的工作者。
  • omp 在轮次中重启——重新打开父会话并要求列出恢复的工作者。在明确继续之前，检查中断工作者的对话记录和仓库状态；omp 不会重放被中断的轮次。
  • 两个工作者修改了同一个文件——停止进一步的重叠工作，选择一个整合负责人，检查实际文件，并让该负责人根据两条工作流的契约协调改动。不要再启动更多重叠的编辑。
  • 工作者似乎卡住了——询问它最近的活动，并引导它完成更小的下一步。如果仍然没有进展，就停止它，带着已经收集的证据把剩余工作重新分配给强力工作者。
  • 无法启动、分叉、移动或交接会话——运行 /vibe 退出并停止它的工作者作用域，然后重试会话操作。
  • 你中断了 omp，不确定什么还保留着——Vibe徽章表示模式仍然活跃。继续前询问名册，或者运行 /vibe 执行确定性的拆除。
