子代理与 Agent Hub

把独立的工作委派给专家会话，观察它的进展，并且不必离开主对话就能引导或停止每个工作进程。

子代理让 omp 把较大的任务拆分成专注的子会话。当研究、实现或审查可以独立推进时使用它们：你能得到并行进展和专家关注，同时主会话仍然负责集成。

先用日常语言提出要求。说明结果、哪些部分可以并行，以及任何归属或安全边界：

把这个迁移并行化。给每个工作进程一个文件互不重叠的包，编辑时使用隔离的工作区，让主会话集成并验证结果。

用 scout 梳理每个认证入口点，然后用 security-reviewer 检查提议的修复。研究阶段不要编辑。

让 designer 实现响应式状态，同时让 reviewer 检查现有的无障碍行为。不要让他们碰同样的文件。

你不需要描述 omp 内部的委派协议。主会话会选择扇出方式，给每个工作进程分配任务，并收集结果。

何时适合委派

合适的候选任务有清晰的边界，并且无需反复向其他工作进程索取未完成的信息就能取得进展：

  • 独立的仓库调研、外部 API 调研，或相互竞争的调查；
  • 跨包或跨功能的、文件互不重叠的实现；
  • 一次专家检查，例如设计、代码审查或安全审查；
  • 可以按目录或生成产物拆分的机械性改动；
  • 实现完成后的独立审查。

当工作是小型顺序改动、多个步骤必须持续修改同一个文件，或每个决定都依赖上一个结果时，请把工作留在主会话里。更多的工作进程并不能让依赖链变成并行，重叠的写入者会带来合并风险。

子会话不会继承主对话。omp 会传递任务和相关共享上下文，而子会话可以看到被允许的工作区和项目指令。当上下文容易被忽略时，请明确说出来：

把这件工作委派出去，但告诉每个工作进程：packages/api/schema.ts 是事实来源，生成的文件不得编辑。

选择专家

你可以在提示词中指定专家，也可以让 omp 选择。当前内置的集合是：

专家适用场景
scout快速、只读的仓库探索与压缩后的发现。
designerUI/UX 实现、无障碍与视觉打磨。
reviewer有证据支撑的正确性与质量审查。
security-reviewer只读的漏洞发现与安全分析。
librarian对第三方库和 API 的、经来源核实的研究。
task使用全部可用能力集的通用多步骤工作。
sonic几乎不需要推理的严格机械性编辑或数据收集。

例如：“用 librarian 核实上游的重试语义”“让 reviewer 只检查当前的 diff”，或“用 sonic 工作进程更新这些文件互不重叠的 fixture”。自定义名称区分大小写。

打开 /agents 查看可用的定义、它们的来源、是否启用，以及它们的模型、prewalk 和顾问路由。在磁盘上修改定义后，在那里按 Ctrl+R。要创建或自定义专家，见 编写子代理。

如果你不确定该改专家定义，还是只改它背后的模型，见 代理与模型角色。

工作进程运行时你能看到什么

后台委派默认启用。主对话记录会先报告哪些具名工作进程已启动，然后它的任务显示会随实时活动更新。完成的结果会被送回主对话；主代理可以总结它们、调和分歧并继续工作。/jobs 会打印后台任务的简要快照，但 Agent Hub 才是详细的视图。

按 Alt+A 打开 Agent Hub。Ctrl+S 通过旧的会话观察绑定打开同一个视图。当主编辑器为空且会话有可显示的代理时，双击 ← 也会打开它。运行 /hotkeys 可以确认或重新映射当前生效的组合键。

名册的每一行显示工作进程的状态、任务或当前活动、模型、存在时长、token 与请求用量、工具调用次数、活动时间，以及在有数据时的成本。检查器会补充当前工具、重试状态、上下文窗口用量、父/子谱系，以及任何隔离工作区的补丁或分支信息。按 t 在平铺名册与父/子树之间切换。

控制动作
j/k、方向键或滚轮选择一个工作进程。
Enter 或点击打开它实时或已保存的对话记录。打开一个已停靠的工作进程会在可能时唤醒它。
Tab在窄终端上显示或隐藏检查器。
PageUp/PageDown滚动检查器。
r唤醒选中的已停靠工作进程。
x必要时中止，然后杀死并释放该工作进程。立即生效。
Esc关闭检查器，再关闭 Agent Hub。

各状态含义不同：

  • running——工作进程处于活动轮次中；
  • idle——它的轮次已结束，但实时会话仍在内存中，可以继续跟进；
  • parked——它的会话已保存到磁盘，通常可以被唤醒；
  • aborted——它已被停止且处于终态，但对话记录仍然可查看。

已完成的工作进程仍与会话关联。恢复该会话后，Agent Hub 会发现它们已保存的对话记录并恢复其谱系。

阅读、引导、跟进或停止

从 Agent Hub 打开一个工作进程以聚焦它的会话。你可以阅读它的对话记录和当前工具活动，然后输入一条普通消息并按 Enter：

别再改 API 包了。只完成客户端测试，并报告还剩什么。

下结论之前，把你的发现与生成的 schema 对比，并引用这两个文件。

发给运行中工作进程的消息是引导，会在安全的步骤边界落地；发给空闲工作进程的消息会开始一次跟进；发给已停靠工作进程的消息会先唤醒它。在编辑器为空时，按 Esc 或双击 ← 返回主会话。返回不会打断工作进程。

当同一个工作进程已经拥有正确的上下文时，优先向它跟进。当它的工作不安全、超出范围、卡住或不再有用时，使用 x。杀死会释放那个工作进程实例，所以如果之后还需要工作，请启动一个新的工作进程。

共享检出还是隔离工作区

默认情况下，子代理与主会话在同一个检出中工作。这很快，也能让所有人看到当前的改动，但并发的写入者可能覆盖彼此的假设，或产生交错的编辑。请给非隔离的工作进程分配文件互不重叠的归属，并把最终集成保留在一个地方。

若要有更强的编辑隔离，打开 /settings，选择 Tasks → Isolation 组，并把 Isolation Mode 设为 Auto。然后直接提出要求：

在隔离的工作区中运行这三个实现工作进程。只应用成功的改动，让主会话解决集成冲突。

隔离的工作进程会收到一个按平台选定的文件系统克隆或覆盖层。omp 会捕获它的改动，并按配置的补丁或分支策略集成。隔离需要 Git 仓库。托管的工作区通常位于 ~/.omp/wt 下；worktree.base 可以更改该位置。在默认配置下，成功的改动会以补丁形式应用到父检出。

隔离保护的是并发的检出编辑；它不是通用的安全沙箱。工作进程仍可能运行命令、使用联网工具，或影响其工具集与凭据所允许的外部服务。隔离的工作进程在完成后也无法被唤醒，因为它的临时工作区已被拆除；它们的对话记录和补丁元数据仍可查看。

即使是隔离的改动，在集成时也可能冲突，尤其是当工作进程触及相同的行时。请先划分归属，审阅产生的 diff，并让主会话验证合并后的行为。

成本、安全与限制

每个工作进程都是一个独立的模型会话，所以并行会成倍增加 token 用量、提供商请求和成本。Agent Hub 会显示实测的每工作进程用量与总用量。从最小的有用扇出开始，只把适合的工作交给 scout 或 sonic，并停止那些任务已过时的工作进程。顾问和 prewalk 路由可能还会增加各自的模型调用。

子代理以无头方式运行，无法为逐个工具的审批暂停等待交互。请把每项任务当作授予的权限：限制其范围，尽可能选择只读的专家，避免把无关的密钥或生产操作交给工作进程，并监督外部的副作用。工作区隔离并不保护远程账户或服务。

重要的默认值如下：

设置默认值作用
async.enabledtrue让普通工作进程在后台继续。
task.maxConcurrency32限制同时运行的工作进程数；超出的工作会排队。0 表示不限制。
task.maxRecursionDepth2限制工作进程可以再次委派的深度。
task.softRequestBudget200要求长时间运行的工作进程收尾，并在达到预算 1.5 倍时强制给出部分结果。0 表示禁用。
task.maxRuntimeMs0每个工作进程的墙钟硬性上限；0 表示不限制。
task.agentIdleTtlMs420000空闲七分钟后停靠工作进程；0 表示保持其存活直到退出。
task.isolation.modenone用 auto 或特定的后端启用隔离工作区。
task.isolation.applytrue把成功的隔离改动应用到父检出。
task.isolation.mergepatch以补丁而不是分支的方式集成隔离改动。

这些控制项请用 /settings，每个代理的启用与模型路由请用 /agents。见 设置，了解如何直接编辑 ~/.omp/agent/config.yml。

故障排查

omp 把工作留在主会话里。 明确要求：“用三个文件互不重叠的工作进程把这件事并行化”，或者点名专家。在 /settings 中，当你想要更积极的委派时，可以把 Prefer Task Delegation 从 default 改为 preferred 或 always。

指定的专家未知或不可用。 打开 /agents，检查确切的区分大小写的名称、作用域和启用状态，然后按 Ctrl+R 重新加载定义。项目定义优先于同名的用户定义或内置定义。

某个工作进程一直排队。 运行中的工作进程已达到 task.maxConcurrency，或模型提供商正在限流请求。减少扇出、等待空位，或谨慎地提高上限。

工作进程产生冲突的编辑。 停止重叠的写入者，给每个工作进程分配文件互不重叠的归属，并在启用隔离后重试。隔离减少了实时检出上的干扰，但不会让重叠的补丁顺利合并。

隔离不可用。 确认 task.isolation.mode 不是 none，并且 omp 运行在 Git 仓库中。计划模式下不提供隔离，它让被委派的工作保持只读。如果自动集成失败，请先检查 Agent Hub 中的补丁或分支信息，再手动应用任何内容。

已完成的工作进程无法被唤醒。 隔离的工作进程在拆除后有意设计为不可唤醒，而被杀死或硬中止的工作进程处于终态。请在提示词中总结旧结果，启动一个新的工作进程。普通的已停靠工作进程可以用 r 唤醒，或打开并向它发送消息。

结果不完整或中途停止。 检查对话记录中是否有软请求预算提示、墙钟超时、提供商错误或手动中止。缩小剩余的任务范围，并在同一个普通工作进程空闲或已停靠时向它跟进；否则启动一个替代者。

Agent Hub 显示为空。 它显示属于当前会话的工作进程。请恢复创建它们的那个会话，或在这里启动一个委派任务。/jobs 可能仍会显示最近的后台进程记录，但它不能替代工作进程的对话记录。
