时间旅行流规则

在 omp 生成某个特定错误的过程中拦住它，注入纠正，让代理在错误生效之前重试。

时间旅行流规则（TTSR）是面向代理实时输出中可识别错误的一道护栏：编辑里出现的禁用 API、不安全的 shell 片段，或散文里反复出现的某个说法。规则匹配时，omp 可以中断该响应，显示触发了哪条规则，提供该规则的 Markdown 指令，并在带着纠正内容的情况下重新开始生成。

适用于以下指导的规则用 TTSR：

  • 只在特定模式出现时才重要；
  • 足够具体，能可靠地检测；以及
  • 在建议的工具调用运行之前最有用。

当指令范围狭窄或很少相关时，这比常驻上下文更好。对于代理在每项任务中都必须始终考虑的约定，常驻上下文更合适，因为 TTSR 是反应式的：在条件出现之前它帮不上忙。

创建最小的有用规则

在项目根目录创建 .omp/rules/no-box-leak.md：

---
description: Prevent permanent Box::leak allocations in Rust edits
condition: 'Box::leak\('
scope:
  - 'tool:edit(*.rs)'
  - 'tool:write(*.rs)'
---

Do not introduce `Box::leak` in production Rust code. Keep ownership explicit;
prefer `Arc<str>`, `Cow<'static, str>`, or a true process-lifetime singleton,
then continue with the option that fits this code.

文件名会成为规则名 no-box-leak。frontmatter 说明何时、何处作出反应；Markdown 正文说明为什么，以及应该改做什么。正文保持简短、可执行——只有当规则触发时，模型才会收到它。

把规则保存在以下原生位置之一：

位置用途
<project>/.omp/rules/<name>.md 或 .mdc项目规则；通常随仓库一起提交。
~/.omp/agent/rules/<name>.md 或 .mdc适用于所有项目的个人规则。该目录跟随当前配置文件和 PI_CODING_AGENT_DIR。

项目规则和用户规则在会话启动时被发现。添加或修改文件后，请启动新会话。

测试、检查并启用它

在依赖自动发现之前，先单独测试规则文件：

omp ttsr test \
  --rule .omp/rules/no-box-leak.md \
  --source tool --tool edit --path src/lib.rs \
  'let value = Box::leak(Box::new(input));'

报告中应在触发的规则下列出 no-box-leak。来源、工具和候选路径都很重要：它们复现了 scope 和 globs 所使用的上下文。其他有用的检查：

# Show every active TTSR rule, its conditions, scope, and source file.
omp ttsr list

# Explain both matching and non-matching rules for a sample.
omp ttsr test --verbose --source tool --tool edit --path src/lib.rs \
  'let value = Box::leak(Box::new(input));'

# Look for existing files that would match the rule.
omp ttsr scan --rule .omp/rules/no-box-leak.md src/

omp ttsr test src/lib.rs 也可以：可识别的源文件扩展名意味着工具/编辑上下文。诊断路径或作用域不匹配时，请使用显式标志。脚本化可使用 --json，--file - 则从标准输入读取样本。

TTSR 默认启用。要显式启用并查看实际生效的值：

omp config set ttsr.enabled true
omp config get ttsr.enabled

omp config set 写入当前配置文件的全局 ~/.omp/agent/config.yml。若只想为项目覆盖，请改为编辑 <project>/.omp/config.yml。在 omp 内部，/extensions 是查看已发现规则及其来源路径的另一种方式。

触发时的表现

在默认的 interruptMode: always 下，匹配的响应会立即停止。TUI 显示 Injecting rule: no-box-leak 通知，部分尝试默认被丢弃，代理使用规则正文生成替代响应。匹配的编辑或写入会在那次不完整的调用执行之前被停止。

这是一次中断并重试，而不是文本替换：规则应当说明安全的替代方案，而不是试图自行重写代码。把触发条件放得足够窄，可以让重试发生在早期且成本低廉。

若只想要针对某个工具的柔和提醒，可在规则上设置 interruptMode: never。omp 会让匹配的工具执行完毕，并把提醒放在该工具结果旁边，供代理下一步参考。对于散文，never 会让响应完成，然后附上纠正。只有在允许匹配动作执行完毕是安全的情况下才使用它。

匹配与作用域

condition 是 JavaScript 正则表达式。它会针对每个被监视输出面的累积内容求值，因此可以跨流式分块匹配。对于 edit 和 write，omp 匹配的是正在引入的源内容，而不是序列化后的命令语法。其他工具则匹配其流式参数。

优先使用最小的独特模式：

condition: 'Box::leak\('

避免像 leak 这样宽泛的模式，它还会命中讨论、日志和不相关的标识符。YAML 单引号能让正则反斜杠最易读。支持开头的 (?i)、(?m) 和 (?s) 标志；其余请使用 JavaScript 正则表达式语法。

规则可以为 condition 提供字符串或列表。多个正则条件是“或”的关系：任意一个都能触发。astCondition 用 ast-grep 模式提供同样的“或”行为。如果两种都存在，在通过作用域和路径检查后，任一种都可以触发。

没有 scope 时，规则监视助手散文和每个工具的参数，但不监视思考过程。显式作用域会替换该默认值。支持的 token 有：

作用域 token监视内容
text助手散文。
thinking提供商会暴露时的模型思考流。
tool 或 toolcall每个工具。
tool:<name>单个工具，例如 tool:bash。也接受裸工具名，例如 bash。
tool:<name>(<glob>)仅当候选路径匹配时的单个工具，例如 tool:edit(src/**/*.ts)。

逗号分隔的字符串和 YAML 列表都可接受。组合多个作用域时优先使用 YAML 列表。路径 glob 匹配规范化后的路径和基本文件名。顶层的 globs 字段是所有作用域之上的额外路径检查；至少有一个候选路径必须匹配它。

当格式化或标识符名称让正则过于脆弱时，AST 匹配很有用：

---
description: Reject TypeScript any assertions
astCondition:
  - '$VALUE as any'
scope:
  - 'tool:edit(*.ts)'
  - 'tool:write(*.ts)'
---

Preserve the real type. Narrow or model it instead of asserting `any`.

astCondition 只对具有可识别文件扩展名的、带源码的编辑/写入内容生效。它检查该调用引入的内容，而不是文件中其他地方未改动的代码。用 --source tool 和 --path 测试它。

重复、冷却与优先级

默认情况下，每条规则在每个会话中触发一次。该已触发状态随会话保存，因此恢复会话时不会意外重新武装它。要在冷却后允许再次注入，请配置全局重复策略：

omp config set ttsr.repeatMode after-gap
omp config set ttsr.repeatGap 10

间隔按已完成的轮次计数，而不是秒数或流式片段。所有 TTSR 规则都使用这套全局重复策略。

优先级是可预期的：

  1. ttsr.disabledRules 中列出的规则会被移除。
  2. 项目原生规则胜过文件名派生名相同的用户原生规则；更一般地说，某个名称下最先被发现的规则胜出。
  3. 带有 condition 或 astCondition 的有效规则就是 TTSR 规则，即使它还写着 alwaysApply: true；它也不会再作为常驻上下文注入。
  4. 规则的 interruptMode 覆盖全局 ttsr.interruptMode。
  5. 如果多条符合条件的规则匹配同一输出，omp 可以注入所有不同的匹配项。只要任一匹配规则要求中断，响应就会被中断。

使用唯一且有描述性的文件名，避免意外遮蔽。用 omp ttsr list 确认实际生效的来源。

完整的规则 frontmatter

除 TTSR 规则至少需要一个可用的 condition 或 astCondition 之外，所有字段都是可选的。标为“list”的字符串字段也接受单个字符串。

字段类型含义
descriptionstring规则检查时显示的人类可读摘要。推荐填写。
conditionstring 或 string 列表JavaScript 正则备选项。也接受旧版拼写 ttsr_trigger，但新规则请使用 condition。
astConditionstring 或 string 列表针对编辑/写入源内容的 ast-grep 模式备选项。
scopestring 或 string 列表输出面以及可选的工具/路径过滤。省略则为 text 加所有工具，不含思考。
globsstring 或 string 列表额外的候选路径检查。它不会替换 scope。
interruptModealways、prose-only、tool-only 或 never按规则覆盖哪些匹配输出面会立即中止。
alwaysApplyboolean通用规则元数据。有效的 TTSR 条件优先，因此同时设置它们并不会让正文变成常驻。
为保持兼容，形如文件 glob 的 condition 值（例如 *.rs）会被视为简写：在该 glob 上以全匹配条件监视 edit 和 write。优先使用显式正则加 scope；这样触发条件的意图和测试上下文都更清楚。

frontmatter 之后的 Markdown 就是注入的指令。规则名和来源路径来自发现过程；不要把它们写进 frontmatter。

完整的全局 TTSR 配置是：

ttsr:
  enabled: true
  contextMode: discard       # discard | keep
  interruptMode: always      # always | prose-only | tool-only | never
  repeatMode: once           # once | after-gap
  repeatGap: 10              # completed turns
  builtinRules: true
  disabledRules: []          # filename-derived rule names

contextMode: keep 会在重试前保留部分响应；discard 会移除它，对大多数护栏更安全。builtinRules: false 只禁用 omp 内置的 TTSR 规则，不影响你自己的文件。要禁用某条规则而不删除它：

omp config set ttsr.disabledRules '["no-box-leak"]'

修改 TTSR 配置后请启动新会话，以便规则发现和会话状态没有歧义。

安全与性能

  • 把危险动作规则限定到相关工具和文件类型。监视所有散文和工具会增加误报和匹配开销。
  • 在不安全片段完成之前中断。TTSR 匹配无法撤销已经结束的工具调用。
  • 保持正则线性且具体。避免像 (.*)+ 这样的嵌套、有歧义的重复，随着输出增长它可能变得非常昂贵。
  • 结构性代码规则优先使用 astCondition，但要用工具和扩展名加以约束；结构匹配的开销高于简单正则。
  • 不要在规则正文中放密钥。规则触发时正文会发送给所选模型，并可能保留在会话中。
  • 启用宽泛的仓库级规则前，先运行 omp ttsr scan。请审查匹配结果，而不是把每一处文本出现都当作违规。
  • 只有在允许匹配的工具动作执行是可以接受的情况下，才使用 interruptMode: never。

故障排查

omp ttsr list 没有显示该规则

  • 确认文件是 .omp/rules/ 或当前配置文件 rules/ 目录中的 .md 或 .mdc。
  • 确保 frontmatter 从第一行开始、有结束的 ---，并且包含非空的 condition 或 astCondition。
  • 检查 omp config get ttsr.enabled、omp config get ttsr.disabledRules 和 omp config get ttsr.builtinRules。
  • 查找另一条文件名派生名相同的已发现规则。
  • 编辑文件后启动新会话。

隔离测试没有触发

用 --verbose 运行，并精确复现实时上下文：

omp ttsr test --verbose --rule .omp/rules/no-box-leak.md \
  --source tool --tool edit --path src/lib.rs 'Box::leak('

检查正则转义、工具名、scope、顶层 globs 和路径扩展名。缺少 --source tool 和文件扩展名的 AST 规则无法推断语言。无效的正则和 AST 模式会被忽略，而不会阻止会话启动。

测试会触发，但实时会话不会

会话可能加载了之前的文件，规则可能已在 repeatMode: once 下触发过，或实时动作使用了不同的工具/路径输出面。启动新会话，用 omp ttsr list 检查，并用相同的 --source、--tool 和 --path 测试。

规则触发过于频繁

收窄 condition，添加工具/路径 scope，或添加 globs。修订期间可用 ttsr.disabledRules 作为即时关闭开关。不要通过让正文变得含糊来解决误报——触发条件应当能识别出违规。

部分响应仍然可见

检查 omp config get ttsr.contextMode。要获得干净的重试，请把它设回 discard。同时检查该输出面所用的规则或全局 interruptMode 是否为 never；不中断的匹配会有意允许当前响应或工具执行完毕。
