钩子

在 omp 会话中定义明确的时机运行可信的 TypeScript：阻止高风险操作、转换上下文或工具结果，并对生命周期事件做出反应。

从一个 force-push 防护开始

钩子让你在 omp 每次工作时都应用一套本地策略：在危险命令运行前拦住它、在输出到达模型前做脱敏、给某个轮次添加上下文，或者记录会话活动。钩子是一个可信的 TypeScript 或 JavaScript 模块，它订阅公开事件。

下面这个项目钩子会阻止git push --force，同时仍然允许--force-with-lease：

// .omp/hooks/pre/force-push.ts
import {
  isToolCallEventType,
  type ExtensionAPI,
} from "@oh-my-pi/pi-coding-agent";

const FORCE_PUSH = /\bgit\s+push\b[^\n]*(?:--force(?:\s|$)|(?:^|\s)-f(?:\s|$))/;

export default function forcePushGuard(pi: ExtensionAPI) {
  pi.on("session_start", (_event, ctx) => {
    if (ctx.hasUI) ctx.ui.notify("Force-push guard active", "info");
  });

  pi.on("tool_call", (event) => {
    if (!isToolCallEventType("bash", event)) return;
    if (!FORCE_PUSH.test(event.input.command)) return;

    return {
      block: true,
      reason: "Blocked git push --force; use --force-with-lease after reviewing the remote branch.",
    };
  });
}

创建该目录、保存文件，然后从那个项目里启动一个新的omp会话。启动通知说明处理器已经运行。打开/extensions可以看到解析出的文件及其源码。

想在安装之前测试一个散装文件，就显式传入它：

omp --hook /absolute/path/to/force-push.ts

然后问：

在这个一次性仓库里运行git push --force。

该命令绝不能运行。omp 会把钩子给出的原因显示为工具错误，代理可以选择更安全的下一步。测试策略时请使用一次性仓库，以防钩子本身有错误。

钩子以你的用户身份执行，可以检查提示词、工具输入、结果、凭据元数据和会话状态。只加载你信任的代码。

安装散装钩子

omp 会自动发现以下目录中的.ts和.js文件（仅限直接子文件）：

作用域目录
当前项目会话工作目录下的.omp/hooks/pre/和.omp/hooks/post/
当前用户配置命名配置使用~/.omp/profiles/<name>/agent/hooks/pre/与post/；默认配置使用~/.omp/agent/hooks/pre/与post/

发现不是递归的。像.omp/hooks/pre/team/guard.ts这样的文件会被忽略。添加或修改钩子之后，请启动一个新会话。

pre和post是组织与发现用的命名空间；它们不会自动选择某个事件或工具。pre/里的文件可以订阅任何事件，而像bash.ts这样的文件名也不会自动过滤调用。事件注册和任何toolName检查都要在代码里完成。按惯例，把拦截与输入转换放在pre/，把观察者或结果转换放在post/。

只想在单次会话中加载，可用--hook <path>或--extension <path>；这两个标志喂给同一套模块加载面。相对路径从会话工作目录解析。要让某个显式钩子长期启用，把它的绝对路径加到~/.omp/agent/config.yml的extensions中：

extensions:
  - /absolute/path/to/force-push.ts

用交互式的/extensions，或从 shell 运行omp -p '/extensions'来检查生效的集合。

模块契约

当前的钩子模块默认导出一个同步或异步工厂，它接收ExtensionAPI。在工厂加载期间注册处理器：

import type { ExtensionAPI } from "@oh-my-pi/pi-coding-agent";

export default function myHook(pi: ExtensionAPI) {
  pi.on("turn_end", async (event, ctx) => {
    pi.logger.debug("turn completed", {
      cwd: ctx.cwd,
      turn: event.turnIndex,
    });
  });
}

处理器接收(event, ctx)。event是下面各表中的类型化载荷。常用且有用的上下文成员有：

成员含义
ctx.cwd当前会话工作目录。
ctx.mode"tui"、"rpc"、"json"或"print"。
ctx.hasUI、ctx.ui是否有交互界面，以及通知、提问、状态、小组件等 UI 方法。交互式调用前要用hasUI或mode === "tui"做判断。
ctx.model、ctx.models当前模型，以及只读的模型查询接口。
ctx.sessionManager只读的会话访问。受支持的写入请使用pi.sendMessage()或pi.appendEntry()。
ctx.isIdle()、ctx.hasPendingMessages()、ctx.abort()当前运行状态与取消控制。
ctx.getContextUsage()、ctx.getSystemPrompt()当前上下文用量与生效的系统提示词各行。
ctx.setTimeout()、ctx.setInterval()、ctx.clearTimer()由会话持有的定时器，其错误会被兜住，并会在关闭时清除。

请使用导出的 TypeScript 类型，而不要把自己的钩子里嵌套载荷类型抄一遍。尤其是工具输入和详情属于可辨识联合；isToolCallEventType("bash", event)可以安全地收窄内置工具的类型。

user_pythoncode、excludeFromContext、cwd返回{ result }可替换执行。第一个返回结果的处理器胜出。它观察的是用户输入的$/$$代码。
tool_calltoolName、toolCallId、类型化的input{ block?, reason?, input? }。第一个 block 会停止派发。否则最后一个返回的结果胜出；所有处理器看到的都是原始事件输入。对模型发起的调用所做的input替换会重新校验，并成为 omp 显示、审批、持久化和实际执行的内容。被阻止的调用会忽略它，computer调用也不会应用它。

context即将发送给模型的messages{ messages }。替换会串联。这只改变那一次模型调用，不改变已存储的会话消息。

session_before_switchreason: "new" | "resume" | "fork"、targetSessionFile?{ cancel: true }会阻止切换。第一个取消胜出。
session_before_branchentryId{ cancel?, skipConversationRestore? }。第一个取消胜出；否则应用最新返回的结果。
session_before_compactpreparation、branchEntries、customInstructions?、signal{ cancel?, compaction? }。取消，或提供一个完整的自定义压缩结果；第一个取消胜出，否则应用最新结果。
session.compactingsessionId、messages{ context?, prompt?, preserveData? }。最新返回的结果会替换先前结果。用它来自定义常规压缩，而不必构造完整的压缩结果。
session_before_treepreparation、signal{ cancel?, summary? }。第一个取消胜出；否则应用最新结果。只有在preparation.userWantsSummary为真时才会使用自定义摘要。
session_stopmessages、turn_id、last_assistant_message?、session_id、session_file?、stop_hook_active、signal{ continue: true, additionalContext }或{ decision: "block", reason }请求一次对模型可见的继续。第一个带非空 context/reason 的可执行继续胜出。

工具拦截细节

tool_call是执行前的策略接缝。它的event.input是用于检查的规范化视图；而处理器返回的input必须是工具将要执行的完整原始参数对象。不要把规范化的、仅供判断用的字段抄进替换值。如果你只需要拒绝某个操作，返回block即可，不要改写输入。

修订后的调用仍然会经过正常的工具 schema 与审批策略。因此用户批准的是实际将要运行的参数。钩子是对 omp 审批设置的补充，而不是绕过它。

tool_result在成功和失败的执行之后都会运行。文本块和图片块位于content；工具专属元数据位于details。请优先返回新的内容对象，而不是就地修改事件。

通知类事件

这些事件的返回值会被忽略。载荷仍然是类型化的，因此钩子可以记录日志、更新 UI、持久化自己的状态，或入队一条受支持的消息。

顺序、超时与错误

在单个模块内，处理器按注册顺序运行。除session_shutdown外，事件处理器逐个等待完成。跨模块时，处理器遵循解析出的加载顺序，但目录枚举与能力去重并不是公开的优先级机制。不要用00-、99-这类文件名前缀在钩子文件之间建立正确性依赖；请把相互依赖的处理器合并到一个模块里。

重复发现的钩子键可能会遮蔽优先级更低的提供商的钩子。在包里请使用有辨识度的文件名。显式列出的路径会按其解析后的绝对路径去重，因此同一个模块不会被有意加载两次。

大多数处理器有 30 秒的活跃工作预算。tool_call使用可配置的extensionHandlers.toolCallTimeoutMs设置，默认同样是 30 秒：

extensionHandlers:
  toolCallTimeoutMs: 10000

tool_call抛异常或超时会失败关闭：omp 阻止该调用，并报告是哪个扩展失败或超时。其他事件的异常和超时会被报告为扩展错误，该处理器不贡献结果，后续处理器继续运行。session_shutdown处理器并发运行，预算两秒，因此清理不会把进程拖住。

加载阶段出现语法/导入错误、工厂抛出异常，或缺少默认工厂，都会导致该模块无法加载；omp 会继续加载其他模块。用/extensions定位缺失的路径，然后用--log-level debug重启以查看加载错误。

打包与分享钩子

要做一个可复用的纯钩子包，请保留惯例目录，并把钩子声明为包入口。这样直接按目录加载可以工作，已安装插件的发现过程也能找到hooks/这个面：

force-push-guard/
  package.json
  hooks/
    pre/
      force-push.ts

{
  "name": "@acme/force-push-guard",
  "version": "1.0.0",
  "omp": {
    "extensions": ["./hooks/pre/force-push.ts"]
  }
}

发布之前先测试该目录：

omp --hook ./force-push-guard

日常本地使用，可以把它作为插件安装：

omp install ./force-push-guard
# Project scope instead of user scope:
omp install -l ./force-push-guard

omp install接受本地路径、npm 包、Git 仓库和插件市场条目。包的导入必须能从已安装的包解析到，且每个运行时文件都必须包含在发布产物中。密钥和与机器相关的策略请放在用户或项目配置里，而不是提交进公开包。

多入口包见编写扩展；安装、作用域、更新与发布见插件。

疑难排查

现象检查
钩子没有出现在/extensions中文件必须是hooks/pre或hooks/post的直接.ts或.js子文件，或者被显式传入。项目发现使用会话的工作目录；用户发现使用活动配置。
钩子出现了，但某个处理器从不运行目录和文件名不会选择事件。确认精确的pi.on("event_name", ...)注册以及任何toolName过滤。
启动时报告扩展无效导出一个默认工厂函数，并修复它的导入/语法错误。用--log-level debug运行以看到失败的路径。
在 print 或 RPC 模式下 UI 调用消失在提问或渲染之前检查ctx.hasUI或ctx.mode。无界面模式请使用日志或持久化状态。
某个工具被扩展失败阻止某个tool_call处理器抛出异常或超出超时。请修好钩子，而不是先调高超时；拦截按设计就是失败关闭的。
两个钩子意见不一致把依赖顺序的逻辑放进同一个模块。对独立模块请记住：第一个 block 胜出，结果/上下文转换按上文所述串联，许多会话结果事件使用最新返回的结果。
