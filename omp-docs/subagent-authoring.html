编写子代理

在一个 Markdown 文件中定义一个命名的专家，只给它需要的工具，然后让 omp 按名称使用它。

当你反复进行同一种委派时，自定义子代理很有用：审查一个 API、检查迁移、研究某个依赖，或进行一种范围严格限定的改动。为这类工作一次性起一个稳定的名字并写好指令，之后每当需求再次出现，就让 omp 使用这个专家。

创建最小的可用代理

要做一个项目专属、只读的 API 审查者，请创建 .omp/agents/api-reviewer.md：

---
name: api-reviewer
description: Review API changes for compatibility, missing tests, and contract drift.
tools: [read, grep, glob]
---

Review the assigned API change.

Check exported types, HTTP behavior, tests, and documented contracts. Report only concrete findings with file and line references. Do not edit files.

只有 name 和 description 是必需的。Markdown 正文是该代理的持久指令。这个示例授予了一套显式的只读工具，而不是继承当前会话可用的所有工具。

保存文件，打开 /agents，按 Ctrl+R。搜索 api-reviewer，确认详情面板显示了预期的文件路径。如果它处于禁用状态，按 Space 启用它。

然后用自然语言提出请求，并使用确切的名称：

Use the api-reviewer subagent to review the current branch. Keep it read-only and report actionable findings.

你不需要特殊的请求格式。点名代理是选中它最清晰的方式；它的 description 也会告诉 omp 这个专家何时适用。

选择存放位置

作用域位置用途
项目<project>/.omp/agents/<name>.md应随项目一起走的仓库专属约定。omp 会从当前目录向上查找，并使用最近的 .omp/agents 目录。
用户~/.omp/agent/agents/<name>.md跨项目可用的个人专家。使用命名配置文件时，请用 ~/.omp/profiles/<profile>/agent/agents/。
OMP 扩展<extension-root>/agents/<name>.md随 OMP 扩展包一起分发的代理。
Claude 插件市场插件<plugin-root>/agents/<name>.md由已启用的 Claude 插件市场插件提供的代理。

对于给定的 name，第一个定义胜出：

  1. 最近的项目 .omp/agents 目录
  2. 当前用户的代理目录
  3. OMP 扩展根，按其配置来源排序：命令行扩展、项目扩展、用户扩展，然后是已安装的 npm/link 插件
  4. Claude 插件市场插件，项目作用域先于用户作用域
  5. omp 自带的代理

名称按精确匹配，并且区分大小写。优先使用小写 kebab-case 名称。在同一个目录内，文件按文件名顺序考虑，因此不要保留两个 name 相同的定义。项目或用户定义可以通过复用名称有意替换插件或自带代理；/agents 会显示哪个文件胜出。

直接的 .claude/agents、.codex/agents 以及类似的跨工具目录不会被扫描。它们的 frontmatter 契约与 omp 的不通用。

编写有效的指令

让正文专注于这个可复用角色。说明：

  • 该代理负责什么、绝不能做什么
  • 它应遵循的检查或工作流
  • 它的回答中应包含哪些证据
  • 它是否可以编辑文件
  • 在任何任务中都成立的项目边界

把会变化的工作放进请求，而不是定义中。例如，把“审查 API 兼容性”留在文件里，把“审查本分支上的分页改动”放进提示词。避免把通用的项目指令复制进每个代理；正常的项目上下文仍然生效。

description 是选择提示，不是第二份系统提示词。使用具体的动词、主题与边界：“Review database migrations for unsafe locks and rollback gaps”比“A helpful database expert.”更有用。

安全地授予工具

显式的 tools 列表是一条能力边界。从能完成任务的最小集合开始：

  • 调查通常需要 read、grep 和 glob
  • 当语义代码导航有用时添加 lsp
  • 只有该代理需要修改文件时才添加 edit 或 write
  • 只有必须运行命令时才添加 bash；shell 访问同样可以修改工作区
  • 只有当外部访问属于该角色的一部分时，才添加 web_search、browser、github 或插件/MCP 工具
  • 只有该专家必须进一步委派时才添加 task，同时也要限制 spawns

省略 tools 时，代理会继承父会话可用的工具。这对通用工作代理很方便，但对审查者来说通常太宽。omp 会自动添加代理所需的私有完成能力；不要自己添加它。

隔离是按单次委派选择的，而不是在代理 frontmatter 中设定。当代理将要做出有风险或独立的改动时，请显式请求它：

Use the migration-fixer subagent in an isolated worktree to fix the failing migration test.

隔离需要一个受支持的 Git 检出以及已配置的任务隔离。它隔离的是文件系统改动；它不会让网络、shell 或凭据访问变得无害，因此请保持工具授予范围狭窄。

frontmatter 参考

frontmatter 键可以使用 camelCase 或 kebab-case。以下是当前公开的字段：

字段含义
name必需。用于选择该代理的精确、区分大小写的标识符。
description必需。简短说明该代理应在何时被使用。
tools允许的工具名，可为 CSV 字符串或 YAML 列表。省略则继承当前会话的工具。
model一个模型选择器、一个 CSV 字符串，或一个按顺序尝试的 YAML 列表。它可以是具体选择器（如 openai/gpt-5-mini），也可以是角色别名（如 "@review"）。省略则使用正常的继承选择。
thinking-levelinherit、off、auto、minimal、low、medium、high、xhigh 或 max。较旧的 thinking 键也被接受。实际支持取决于模型。
spawns该代理可以委派给的代理名，为 CSV 字符串或列表；* 允许任何已发现的代理。省略表示不允许。为兼容性，授予 task 工具但不设置此字段意味着 *，因此请显式设置此字段。
autoload-skills在第一次任务之前要加载的技能名，为 CSV 或列表。未知名称会被忽略。
read-summarize当 read 必须返回逐字代码而不是结构化摘要时设为 false。通常保持启用。
output用于结构化结果的 JSON Schema。适合普通散文式报告时省略。
blocking当调用方应等待该代理（即使已启用异步委派）时设为 true。通常省略。
prewalktrue 会在第一次编辑或写入时把工作交给处于 smol 角色的模型；模型选择器或角色别名可以选择另一个目标。当你希望更强的模型先检查或规划、再由更便宜的模型实现时使用它。
advisortrue 使用配置的 advisor 模型角色；模型选择器或角色别名可以指定某个顾问。子代理在其他情况下运行时没有顾问。

没有单独的 role 字段。把角色别名放进 model，然后在你的用户或项目配置中映射该别名。这样代理指令保持稳定，同时让每个环境选择具体的模型：

---
name: api-reviewer
description: Review API changes for compatibility, missing tests, and contract drift.
tools: [read, grep, glob]
model: "@review"
thinking-level: high
---

Review the assigned API change and report concrete findings with file and line references.

# ~/.omp/agent/config.yml, or the active profile's config.yml
modelRoles:
  review: openai/gpt-5.4

你可以在 /models 的角色视图中分配或更改自定义模型角色。/agents 中心也让你可以覆盖某个已发现代理的模型、prewalk 目标或顾问，而无需编辑共享定义；这些按代理的设置优先于它的 frontmatter。

重新加载与维护定义

每次委派在开始前都会重新读取代理定义，因此保存的编辑会在下一次使用时生效。/agents 界面有自己的显示快照；在添加、重命名或编辑文件后，请在那里按 Ctrl+R。

对于由扩展或插件提供的代理，在安装或更改该包后运行 /reload-plugins，以便 omp 重新加载整个插件面。普通的项目与用户 Markdown 编辑不需要重启 omp。

把项目代理当作代码对待：审查改动、保持描述准确、删除过时的重复文件。如果你想要 omp 自带定义的可编辑副本作为起点，运行 omp agents unpack --project，或用 omp agents unpack 获取用户作用域；只定制你打算覆盖的文件。

故障排除

代理没有出现在 /agents 中。按 Ctrl+R，检查文件是否以 .md 结尾，并确认它直接位于某个 agents 目录中。核实 frontmatter 的 name 和 description 都有非空字符串值。无效的 YAML 或缺失必需字段会跳过该文件，而发现流程会继续。

胜出的是错误定义。在 /agents 中查看来源路径，然后检查优先级更高的项目或用户目录中是否存在完全相同的 name。在 monorepo 中要记住，最近的 .omp/agents 目录才是项目来源。

omp 没有选择该代理。用确切的名称请求它。改进 description，写清任务、主题以及把它与其他代理区分开的边界。同时也在 /agents 中确认该代理已启用。

请求的模型无法解析。打开 /models，确认具体模型或角色别名已配置并已认证。若需要回退行为，在 model 下列出多个选择器。

某个工具不可用。把它的确切注册名添加到 tools，或者，只有当继承完整的父工具集是有意为之的时候，才移除显式列表。插件提供的工具还要求该插件已启用并重新加载。

编辑似乎被忽略了。实际的委派会读取最新定义，但 /agents 清单可能仍显示之前的快照。重新加载该中心。对于扩展或插件包，还要使用 /reload-plugins。
