上下文文件

用 AGENTS.md 给 omp 持久化的项目指令，然后只在你需要时叠加全局、粘性或系统级的指导。

把项目规则一次性告诉 omp

在仓库根目录放一个 AGENTS.md。omp 会自动加载它并在整个会话中应用，这样你就不必在每条提示词里重复构建命令、约定或安全边界。

# Project instructions

## Build and test
- Install dependencies with `bun install`.
- Run unit tests with `bun test`.
- Run the app with `bun run dev`.

## Conventions
- Keep public API changes backward compatible.
- Never edit generated files under `src/generated/`.
- Before finishing, run the narrowest test that covers the change.

在仓库内的任意位置启动 omp，然后正常提问：

Fix the failing invoice test and follow the repository instructions.

对于应当指导该目录树中大多数工作的事实和约束，使用 AGENTS.md。让它保持简短具体：每一条加载的指令都会消耗上下文。

支持的文件

所有指令文件都是纯 Markdown。它们不需要 frontmatter 或配置项。

omp 原生文件

文件推荐的项目位置用户级位置行为
AGENTS.md<repo>/AGENTS.md~/.omp/agent/AGENTS.md常规的常驻指令。独立的项目文件会跨目录层级组合。
AGENTS.md<repo>/.omp/AGENTS.md~/.omp/agent/AGENTS.mdomp 专属的替代位置。在给定目录层级上，它优先于兼容的上下文文件提供商。
RULES.md<repo>/.omp/RULES.md~/.omp/agent/RULES.md粘性、始终应用的规则。用户文件和项目文件可以同时生效。
APPEND_SYSTEM.md<launch-directory>/.omp/APPEND_SYSTEM.md~/.omp/agent/APPEND_SYSTEM.md向 omp 的内置系统指令追加文本。优先使用它，而不是替换内置指令。
SYSTEM.md<launch-directory>/.omp/SYSTEM.md~/.omp/agent/SYSTEM.md替换 omp 的内置指令正文。项目作用域优先于用户作用域。只用于刻意打造的不同代理人格。

~/.omp/agent/ 是默认的用户级目录。使用命名配置文件时，等价目录是 ~/.omp/profiles/<profile>/agent/。自定义的 omp 配置根会以同样方式改变前缀。

对于 SYSTEM.md 和 APPEND_SYSTEM.md，最可预期的做法是从包含 .omp/ 的目录启动 omp。它们的 CLI 直接搜索会按以下顺序先检查项目文件：

  1. <launch-directory>/.omp/
  2. <launch-directory>/.claude/
  3. <launch-directory>/.codex/
  4. <launch-directory>/.gemini/

如果都不存在，omp 会按同样顺序检查相应的用户目录：当前 omp 配置文件的 agent/ 目录、当前 Claude 配置目录、~/.codex/，然后是 ~/.gemini/。它使用第一个匹配的文件名。只有在直接搜索什么都没找到时，已启用的发现提供商才能提供额外的 SYSTEM.md 位置；APPEND_SYSTEM.md 只使用直接搜索。

--system-prompt 和 --append-system-prompt 优先于被发现的文件；两者都既可以接受字面文本，也可以接受可读的文件路径。

SYSTEM.md 会移除内置的行为与工具使用指导，但 omp 仍会围绕它提供项目上下文、规则和环境信息。APPEND_SYSTEM.md 保留内置指导，因此是更安全的默认选择。

兼容的上下文文件

omp 可以复用来自其它代理生态的指令文件。它们是上下文文件来源，而非额外格式：其内容仍然是 Markdown。

提供商 ID项目来源用户级来源项目发现方式
native最近的 .omp/AGENTS.md当前 omp 配置文件的 AGENTS.md向上走到仓库根目录，并使用最近的 .omp 配置目录。
claude.claude/CLAUDE.md当前 Claude 配置目录中的 CLAUDE.md仅启动目录。
agents.agent/AGENTS.md 或 .agents/AGENTS.md~/.agent/AGENTS.md 或 ~/.agents/AGENTS.md从启动目录走到仓库根目录。同一层级上 .agent 优先于 .agents。
codex—~/.codex/AGENTS.md仅用户级。
gemini.gemini/GEMINI.md~/.gemini/GEMINI.md仅启动目录。
opencode—~/.config/opencode/AGENTS.md仅用户级。
github.github/copilot-instructions.md~/.copilot/copilot-instructions.md仅启动目录。COPILOT_HOME 可以重定位用户来源。
agents-mdAGENTS.md—从启动目录向上走。

COPILOT_CUSTOM_INSTRUCTIONS_DIRS 也可以用逗号分隔的目录列表来指定哪些目录的 AGENTS.md 被视为用户级的 GitHub Copilot 上下文。

Cursor 规则、Cline 规则、*.instructions.md 以及类似的路径专属规则文件是作为规则被发现的，而不是作为通用上下文文件。它们在 /extensions 中单独出现，并按其自身的条件生效。

发现与作用域

omp 从会话的工作目录解析上下文。

对于推荐的独立 AGENTS.md 布局，它会向上走并加载每一个适用的文件。在嵌套于你主目录之下的仓库中，扫描可能越过 Git 根目录以拾取工作区指令，但会在把 ~/AGENTS.md 当作项目上下文之前停下。在该情况之外，仓库根就是边界。

例如，在 repo/packages/api 中启动 omp 可能加载：

~/.omp/agent/AGENTS.md       user-wide
~/work/AGENTS.md             enclosing workspace
~/work/repo/AGENTS.md        repository
~/work/repo/packages/api/AGENTS.md

文件按从最宽泛到最局部的方式呈现，因此最近的项目指令拥有最终的、最具体的位置。这让 monorepo 布局变得有用：

  • 把共享的命令和策略放在仓库根目录；
  • 把包专属的命令放在嵌套的 AGENTS.md 中；
  • 避免把根文件复制到每个包中。

改动会在 omp 重建新会话时被拾取。编辑指令文件之后，请使用 /new 或重启 omp，再依赖新的文本。

同一作用域下谁胜出

对每个用户级作用域和每个项目目录深度，只有一个上下文文件提供商能存活。提供商优先级为：

  1. native
  2. claude
  3. agents，然后是 codex
  4. gemini
  5. opencode
  6. github
  7. agents-md

这意味着 <repo>/.omp/AGENTS.md 会在同一仓库层级上遮蔽 <repo>/AGENTS.md；它们不会被拼接。除非这种遮蔽是有意的，否则不要同时创建两者。位于不同祖先层级的独立 AGENTS.md 文件具有不同的作用域，因此会正常组合。

用户级上下文遵循相同的提供商优先级，并且最多贡献一个通用上下文文件。RULES.md 是单独的：用户级规则和最近项目的 .omp/RULES.md 在存在时都会加载。对于 SYSTEM.md 和 APPEND_SYSTEM.md，只选择一个被发现文件，项目作用域优先于用户作用域，且 omp 的 .omp 位置优先于兼容的配置目录。

导入共享指令

使用 @path 标记来包含另一个文件，而无需复制它：

# Project instructions

@docs/agent/testing.md
@docs/agent/style.md

导入行为是可预期的：

  • 相对路径从包含该导入的文件解析，而不是从 omp 的工作目录解析；
  • ~/... 从你的主目录解析，绝对路径也被接受；
  • @ 必须位于行首或跟在空白之后，因此电子邮件地址和 git@github.com 不会被处理；
  • 行内代码或围栏代码块中的导入会作为示例保留，而不会被展开；
  • 嵌套导入最多跟随五层；
  • 循环会被阻止，不可读的导入会以其原始的 @path 标记形式保持可见。

导入的文本会插入到标记所在的位置。用导入来处理小的共享策略，而不是大型生成的文档。

核实加载了什么

  1. 从你打算工作的目录启动 omp。
  2. 在交互式会话中输入 /extensions。
  3. 选择相关的提供商标签页并检查 Context Files（上下文文件）。仪表盘会显示来源路径、它是否已启用，以及是否有更高优先级的文件遮蔽了它。
  4. 改动文件后，使用 /new 或重启 omp，重新打开 /extensions，并确认预期的路径处于活动状态。

你也可以问：

Summarize the repository instructions that apply to this task and name their source files.

/extensions 仪表盘是权威检查；摘要则有助于确认指令本身是否清楚。

故障排除

文件没有出现

  • 检查确切的大小写：受支持的文件名在区分大小写的文件系统上是区分大小写的。
  • 确认 omp 是从预期的目录启动的。标为“仅启动目录”的提供商不会走到父级仓库。
  • 确保该文件是可读的 Markdown，然后开始新会话。
  • 对于 .omp/AGENTS.md 和 .omp/RULES.md，先检查最近的 .omp 目录。更近的项目配置目录会定义原生项目作用域。
  • 如果启用了命名配置文件，请检查它专属的 agent/ 目录，而不是默认的 ~/.omp/agent/。

文件显示为被遮蔽

某个更高优先级的提供商在同一作用域提供了上下文文件。检查器会列出两个来源。删除重复项、把确实更窄的指令移到嵌套目录，或从 /extensions 中禁用不需要的提供商。

提供商切换通过 disabledProviders 设置持久保留。常见 ID 列在上表中；例如禁用 agents-md 会停止对独立 AGENTS.md 的发现，同时保留 .omp/AGENTS.md 可用。

粘性规则缺失

RULES.md 必须位于当前用户的 agent/ 目录，或最近的项目的 .omp/ 目录中。--no-rules 标志会在该次运行中禁用 RULES.md 以及所有其他被发现的规则。

导入保持为 @path

相对于导入它的文件解析该路径，检查文件权限，并确保该标记位于行内代码或围栏代码之外。循环或超过五层递归的链路也会使导入不被展开。

提示词和规则相关标志见命令行参考，设置中的 disabledProviders，以及 /extensions 中已发现的条件规则文件。
