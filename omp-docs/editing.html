结构化编辑

在整个项目中安全地改动同一种代码形态，在改动落地前审阅精确的匹配结果，并且不用脆弱的查找替换就能解决合并冲突。

结构化编辑让 omp 改动语法而不是匹配原始文本。它适用于那些必须在不同空白、注释或格式下依然成立的代码改造，而暂存预览能让意外过宽的匹配在改动落地之前暴露出来。

最小的有用请求就是一句日常语言：

在 src/**/*.ts 中，把对 legacyWrap 的调用替换为 modernWrap，保留所有参数。先展示拟议的结构化编辑，仅当它改动的确实是调用表达式时才应用。

你只需指定结果、作用域和安全条件。omp 会选择合适的编辑机制并操作它；你不需要自己写模式，也不需要自己调用编辑工具。

结构化编辑、符号感知编辑还是文本编辑？

omp 有三种相关的代码修改方式：

  • 结构化编辑匹配的是语法形态。即使格式不同，它也能找到同一种函数调用形式，并一致地重写大量实例。适用于 API 迁移、重复的表达式改动、导入形式更新，或删除某一类语句形态。
  • 符号感知编辑沿着声明的身份追踪它的引用、作用域、导入与再导出。当你需要重命名一个真正的符号，而不是所有拼写相同的代码时，就要求这种方式。见代码智能。
  • 文本或行编辑最适合小范围、已知位置、散文、配置，或没有可用解析器的代码。见处理文件。

结构化匹配是语法感知的，不是绑定感知的。两个互不相关但都叫 legacyWrap 的函数在它眼里可能完全一样。如果身份很重要，就明确说出来：

重命名 src/session.ts 中导出的 createSession 符号，并更新它真正的引用和导入方。不要重命名同名的无关局部函数。

对于存在同名代码的代码改造，给 omp 足够的上下文来收窄范围：

在 packages/api/src/**/*.ts 中，只迁移从 @acme/legacy 导入的 legacyWrap 调用。不要动测试夹具，也不要动本地声明的函数。如果无法证明导入来源，停下来并说明这一歧义。

发起与审阅代码改造

一份有力的请求包含：

  1. 作用域——文件、目录或 glob。
  2. 改动前后的行为——描述代码形态以及必须保留的部分。
  3. 排除项——生成的代码、夹具、另一个拼写相同的 API，或任何其他边界。
  4. 决策规则——当预览满足特定条件时应用，或者只预览然后停下。
  5. 验证——应用之后 omp 应检查的针对性命令或行为。

例如：

在 packages/client/src/**/*.ts 中，仅把那些 response 可能缺失的地方的 response.data 直接读取改为可选访问。保留注释和周围的控制流。先预览；如果替换超过 20 处，或者包含该目录之外的任何文件，就拒绝。应用后运行客户端类型检查。

这些卡片是什么意思

结构化重写在写入磁盘之前会先暂存。TUI 会显示受影响的文件、替换数量，以及删除/新增的行数。

  • Proposed（已提议）表示预览已存在，但改动尚未写入。
  • Accept（已接受）表示 omp 接受了提议，并报告实际写入了什么。
  • Reject（已拒绝）表示暂存的提议被丢弃；该提议没有改动任何文件。

这些标签报告的是状态，不是 shell 命令。用日常语言告诉 omp 你想要什么，比如“仅当所有匹配都位于 src/compat 时才应用”或“拒绝这个提议，并解释那些意外的测试文件匹配”。

如果要明确分两轮审阅，从这句话开始：

只预览这个代码改造。不要应用它。

omp 会展示提议并丢弃它，而不是留下一个悬而未决的旧操作。审阅完文件和数量之后，带着你的批准条件让 omp 再次运行同一个代码改造。第二轮会针对当前工作树生成一份新的预览。

安全地审阅

接受一次大范围重写之前：

  • 对照你的预期检查替换总数和文件数。
  • 展开拟议的卡片，从每一种不同的代码形态或包中至少检查一处匹配。
  • 留意拼写相同但互不相关的符号；必要时改用符号感知重命名。
  • 收窄路径，而不是接受一个意外的匹配并打算事后修补。
  • 接受之后，让 omp 检查产生的 diff，并运行最小相关的类型检查或测试。
  • 审阅时把无关的未提交工作一并看进来。结构化编辑会改到这些文件中匹配到的语法；它不能替代对完整工作树 diff 的检查。

如果预览过期了

接受时，omp 会针对当前文件重新执行重写，而不是盲目重放旧的字节。如果在预览与接受之间另一次编辑改变了匹配结果，omp 会把该预览标记为过期并报告新的结果。

最终结果取决于还有哪些内容仍然匹配：

  • 如果已不再有任何匹配，则不应用任何替换。
  • 如果只有部分预览过的位置仍然匹配，这些当前的匹配可能会被应用，之后 omp 会报告接受结果与预览不同。
  • 如果出现了新的匹配，omp 可能应用比预览所示更多的替换，并标记数量不一致。

把过期结果当作错误处理，而不是把它当作一次成功的全有或全无事务。检查被报告的文件和当前 diff，然后让 omp 重新读取受影响的代码，并生成一份更窄的新预览。不要反复接受那个旧提议。

歧义与过期不同：即使语义上只想改一处，结构化匹配器也可能合法地找到多个语法上完全相同的位置。文件列表和替换数量就是警告。应用之前请细化请求，或改用符号感知编辑。

解决合并冲突

你可以要求得到想要的结果，而不是机械地选边：

解决 src/session.ts 中的冲突。保留我们分支的重试行为，以及传入分支的超时校验。展示最终的 diff 并运行会话测试。

当 omp 读取到包含完整 Git 冲突标记的文件时，它会为每个块分配一个会话内引用，例如 conflict://1。你可以在后续消息中粘贴该引用以消除歧义：

对于 conflict://2，合并双方：保留我们的校验，使用他们的错误消息。改动前重新读取周围的函数。

conflict://1 保留我们的，conflict://3 保留他们的，conflict://4 手动合并，确保两种行为都不丢失。

conflict://* 表示当前会话中登记的全部冲突。谨慎使用它，并说明同一套策略是否真的适用于全部冲突：

解决 conflict://*，但要逐块独立检查。不要整体选边；在两者兼容的地方保留双方行为。

只有 omp 读取并登记了标记块之后，引用才会出现。它们是会话内引用，旧会话的 ID 不应复用。如果某个块在登记之后被编辑或解决，omp 会拒绝拼接它已无法定位的标记区域，并要求重新读取。解决一个块不会使其他无关的已登记块失效。

冲突解决是直接的合并操作，而不是结构化编辑提议。对于高风险合并，先让 omp 说明它打算如何解决，然后再请求编辑并审阅产生的 Git diff。最后搜索是否残留冲突标记并运行相关测试，应当包含在请求中。

配置

结构化编辑默认启用。打开 /settings，然后进入 工具 → 可用工具 → AST Edit 来开启或关闭它。对应的设置项是 astEdit.enabled；如需通过 shell 管理配置：

omp config set astEdit.enabled true
omp config set astEdit.enabled false

配置优先级和文件位置见设置。

一次结构化操作默认最多搜索 1,000 个文件。如果确实是一个更大的仓库需要不同的上限，请在启动 omp 之前设置正整数的 PI_MAX_AST_FILES 环境变量。通常来说，面对上限警告更安全的做法是收窄请求的目录或 glob，而不是提高上限。

受限的 --tools 列表也可能导致结构化编辑不可用，即使该设置已经启用。这种情况下，请恢复正常的编辑工具，或让 omp 提供一个限定范围的替代方案。

限制

  • 结构化编辑理解语法，但不理解类型、运行时行为或符号归属。在这些方面重要时，请使用代码智能和验证。
  • 只有具备受支持解析器的语言才能进行结构化重写。无法干净解析的文件可能会被跳过，并给出解析警告。
  • 重写必须把可识别的语法映射为替换语法。需要生成数据、控制流分析或多个协同语句的跨文件变换，可能更适合用专门的脚本加上经过审阅的 diff 来处理。
  • 注释和格式不会妨碍语法匹配，但重写仍可能改变被替换节点周围的格式。请审阅渲染出的 diff。
  • 过大或过于笼统的请求可能触及文件上限，或产生太多无法安全审阅的合法匹配。请按包或代码形态拆分。
  • 合并冲突引用只识别完整、格式良好的 Git 标记块。不完整或手工损坏的标记必须作为普通文本检查。

故障排查

“未做任何替换”

让 omp 检查一个具体例子，并解释它为何没有匹配。代码可能用了不同的语法，路径可能太窄，或者符号感知编辑才是更合适的操作。在一个有代表性的案例能正确预览之前，不要扩大到整个仓库。

解析警告

让 omp 找出受影响的文件，并确认它们能按其声明的语言解析。先修复损坏的语法，排除生成的或不支持的文件，或在结构化解析不合适时使用范围严格限定的文本编辑。

匹配太多或出现意外匹配

拒绝该提议。在请求中加入导入来源、接收者类型、所在函数、包、文件 glob 或明确的排除项。如果区分点在于符号身份，改用由 LSP 支持的重命名。

“已达上限”

收窄作用域后重新运行。触及搜索上限时预览是不完整的，因此其中的数量不是整个仓库的总数。

“预览已过期”

检查当前的 diff，因为可能已经应用了部分匹配或一组已变化的匹配。然后让 omp 重新读取文件并创建新的预览；只有当新的文件数与替换数符合预期时才接受。

conflict:// 引用未知或已不存在

让 omp 再次读取有冲突的文件。这会刷新会话的冲突索引，避免把某个决定应用到一个标记或周围文件已经变化的块上。
