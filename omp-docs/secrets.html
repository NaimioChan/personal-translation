密钥与认证

安全地登录，弄清 omp 使用的是哪份凭据，并在不暴露提供商密钥的前提下运行共享认证。

推荐的设置方式是让 omp 为你管理提供商登录。启动 omp，运行 /login，选择一个提供商，完成浏览器或 API-key 提示。这样可以避免把 key 放进 shell 命令，让 OAuth 刷新保持自动，并且可以在同一个界面里移除账户。

/login

登录成功后，如果提供商提供了身份信息，omp 会给出账户名称，并打印保存凭据的路径。再次打开 /login 可查看每个提供商的状态与活动来源，例如 login、api key、env、config 或 --api-key。然后用 /model 选择模型。

你也可以直接跳到已知的提供商 ID：

/login anthropic

有些提供商使用 OAuth，有些要求 API key，还有些使用设备码或粘贴码流程。请遵循 omp 显示的提示。只把凭据粘贴到该登录提示中——不要粘贴到聊天消息或 shell 参数里。对 OAuth 提供商重复运行 /login 可以再添加一个账户；omp 在发起请求时可以在已存储的账户之间选择。

凭据存放位置

没有认证代理时，默认存储位置是：

~/.omp/agent/agent.db

配置档、PI_CODING_AGENT_DIR 以及 XDG 数据目录都可以迁移它。/login 的成功消息会显示实际使用的路径。agent.db 也用于存放其他 omp 状态，所以不要仅仅为了登出就删掉整个数据库。

SQLite 中的凭据行包含提供商 ID，以及以下之一：

  • 一个 API key，或
  • OAuth 访问 token、刷新 token、过期时间，以及可用的账户元数据。

本地数据库在静态存储时不加密。在 POSIX 系统上，omp 会以 0700 模式创建其目录，并把数据库改为 0600；Windows 依赖账户的文件系统 ACL。数据库打开期间，SQLite 还会在数据库旁使用 agent.db-wal 和 agent.db-shm。请保护整个目录以及任何备份或同步副本，而不只是 agent.db。

要检查默认路径上的权限：

ls -ld ~/.omp ~/.omp/agent
ls -l ~/.omp/agent/agent.db*

其他用户不应当有访问权限。全盘加密能保护关机状态下的机器，但无法保护凭据免受恶意软件、不受信任的扩展，或已经以你的用户身份运行的其他进程的侵害。

哪些内容会离开本机

常规的提供商登录与请求涉及三条相关流程：

  1. OAuth 登录：你的浏览器打开提供商的授权页。提供商把一个短期授权结果返回给 omp，omp 用它换取 token。对于回环流程，回调会返回到运行 omp 的机器上的本地端口。
  2. 提供商请求：omp 把选定的 API key 或 OAuth 访问 token 放进认证请求头，发送给模型端点。因此自定义的 baseUrl 或代理属于你的信任边界——它会收到凭据和请求内容。
  3. OAuth 刷新：当访问 token 需要续期时，omp 把刷新 token 发送给提供商的 token 端点。刷新后的值会写回凭据存储。

提供商凭据用于认证网络请求；它们不应被放进对话中。在登录完成之前，请把授权 URL、回调 URL、设备码和粘贴的登录码都当作密钥对待。omp 会把 /login <callback-or-code> 命令排除在输入历史之外，但你的终端、剪贴板管理器、屏幕共享或 shell 历史仍可能暴露在别处输入的密钥。

哪份凭据胜出

对某个提供商，omp 按以下顺序使用第一个可用的来源：

优先级来源实际效果
1omp --api-key …针对显式选定模型所属提供商的一次性覆盖（--api-key 需要同时选定模型）。避免在共享系统上使用：命令行可能进入 shell 历史或进程列表。
2models.yml 中的 providers.<name>.apiKey显式的提供商覆盖，常与自定义端点一起使用。优先使用环境变量或密钥管理器引用，而不是字面 key。
3已存储的 OAuth 登录自动刷新，并优先于普通的环境 key。
4由 /login 保存的 API key刻意的交互式登录同样胜过提供商环境变量。
5提供商环境变量例如 ANTHROPIC_API_KEY、OPENAI_API_KEY 或 GEMINI_API_KEY；确切名称因提供商而异。
6其他已存储的静态 API key主要是由认证代理工具导入或迁移的凭据。
7自定义提供商回退为自定义提供商配置的解析器。

这意味着导出一个环境 key 不会替换已有的 /login 凭据。请先用 /logout 移除已存储的账户，或者在你确实想这样做时使用显式的 models.yml/--api-key 覆盖。更改环境后请重启 omp。提供商专属的设置参见环境变量和自定义模型与提供商。

对于本地开发和 CI，提供商环境变量比签入文件中的字面 key 更好。从 CI 密钥库或密码管理器注入它，并确认项目文件、shell 历史、日志和导出的会话对话记录中都不包含它。

登出、吊销与轮换

运行 /logout 并选择要移除的提供商和已存储账户。带上提供商 ID 时，omp 会直接打开该提供商的账户选择器：

/logout anthropic

交互式 /logout 移除的是一份选定的已存储凭据，在你拥有多个账户时这一点很重要。它不会移除环境变量、models.yml 覆盖，或进程启动时传入的 --api-key。移除之后，omp 会报告是否还有剩余的认证来源；如果你想要彻底登出，请移除该来源并重启。

删除本地行并不等同于在提供商那里吊销凭据。对于设备丢失或疑似泄露的情况：

  1. 在提供商的安全控制台中吊销 OAuth 授权或旧的 API key。
  2. 用 /logout 移除已存储的凭据。
  3. 用 /login 创建或授权替代凭据（或更新环境/密钥管理器来源）。
  4. 在 /login 中核对预期的账户，并用所选模型发起一次请求。

对于常规的 API-key 轮换，先创建替代 key，更新来源，验证它，然后吊销旧 key。提供商已经签发的 OAuth 访问 token 可能在提供商使其过期或吊销之前仍然有效。

用认证代理集中管理凭据

当多台受信任的机器需要共享同一个凭据池，或刷新 token 应当留在受控主机上时，就使用认证代理。omp 默认使用本地 SQLite 存储；配置了认证代理后，该进程的凭据存储会切换到认证代理。

在认证代理主机上，登录并启动仅限回环的服务：

omp auth-broker login anthropic
omp auth-broker serve

默认绑定为 127.0.0.1:8765。serve 会在需要时创建一个 bearer token；在另一个 shell 中打印它：

omp auth-broker token

对于远程认证代理，只通过私有网络或终止 TLS 的反向代理暴露它。认证代理协议是 HTTP，自身不添加 TLS。不要把 0.0.0.0:8765 直接发布到互联网。

配置每个客户端，最好通过密钥注入器：

export OMP_AUTH_BROKER_URL='https://auth.example.internal'
export OMP_AUTH_BROKER_TOKEN='…'
omp auth-broker status
omp

等价的配置键是活动代理 config.yml 中的 auth.broker.url 和 auth.broker.token。环境变量优先。如果配置了 URL 却没有 token，启动会失败，而不是静默回退到本地凭据。token 也可以从配置根目录的 auth-broker.token 文件中读取。

当 TUI 客户端由认证代理支持时，/login 会把新凭据上传到认证代理，/logout 会禁用选定的认证代理凭据。要获得更紧的边界，就在认证代理主机本身上执行 OAuth。如果该主机可通过 SSH 访问，但其回环回调必须到达你本地的浏览器，请运行：

omp auth-broker login anthropic --via=user@broker

omp auth-broker login 和 omp auth-broker logout 操作的是运行该命令的主机的本地凭据数据库；在认证代理主机上使用它们进行认证代理管理。omp auth-broker logout <provider> 会移除该提供商的所有活动行，这与 TUI 的单账户选择器不同。

认证代理数据与信任边界

认证代理客户端会收到 API key 和 OAuth 访问 token，以便直接调用提供商。OAuth 刷新 token 留在认证代理上，并在快照中被替换为远程哨兵值。从客户端发起的登录仍必须通过受保护的连接把新签发的凭据发送给认证代理一次。

客户端会在配置根目录的 cache/auth-broker-snapshot.enc（默认 ~/.omp/cache/auth-broker-snapshot.enc）保存一份短期的加密快照缓存。其加密密钥由认证代理的 bearer token 和 URL 派生。这能保护被复制的缓存文件本身；但能读取 bearer token 的进程同样可以解密缓存并查询认证代理。

认证代理的 bearer 是保险库管理员凭据：它可以读取可用凭据并改动存储。请让它远离源代码管理和日志，只分发给受信任的客户端，并在暴露后轮换：

omp auth-broker token --regenerate

运行中的认证代理在启动时读取其允许的 token，因此重新生成后要重启认证代理并更新每个客户端。健康检查端点不需要认证；凭据端点需要 bearer。

在提供商流量前面放一个认证网关

认证代理与受信任的 omp 客户端共享凭据；它不代理它们的模型请求。只有当不受那么信任的客户端必须发出兼容 OpenAI、Anthropic、Responses 或 pi 原生的请求，又不能拿到提供商凭据时，才使用 omp auth-gateway。

该网关需要已配置的认证代理：

omp auth-gateway serve
omp auth-gateway token

它默认绑定到 127.0.0.1:4000，并把入站 bearer 以 0600 模式存到配置根目录的 auth-gateway.token。网关认证客户端，通过认证代理解析提供商凭据，并注入上游认证。客户端的入站 bearer 不会被当作提供商凭据转发。

这减少的是密钥分发，而不是权限：任何持有网关 bearer 的人都能消耗提供商的配额，并通过相关账户发送请求内容。网关操作者可以观察请求内容与响应。在远程暴露之前，请保持默认的回环绑定，或加上私有网络、TLS、访问控制与日志保护。--no-auth 会允许所有能到达该套接字的进程，应当仅限于有意受信任的回环环境。

用 omp auth-gateway token --regenerate 轮换网关 bearer，然后重启网关并更新其客户端。

排查问题

/login 成功，但没有可用模型

打开 /login 检查该提供商的来源/状态，然后打开 /model。确认你登录的是目标模型所使用的那个提供商。如果你设置了环境变量，请从同一环境启动 omp，并使用该提供商所支持的确切变量名。

环境 key 被忽略

运行时覆盖、models.yml 中的 API key、已存储的 OAuth 登录，或通过 /login 保存的 API key 的优先级都高于环境变量。/logout <provider> 会显示已存储的账户；移除它们之后，还要检查自定义模型配置以及 omp 是如何启动的。

/logout 没有完全登出

你可能还有另一个已存储的账户，或某个非存储来源。对剩余账户重复 /logout。在源头移除提供商环境变量或配置覆盖，并在不带 --api-key 的情况下重启。存在剩余来源时，登出后的消息会指出它。

浏览器回调无法完成

使用 omp 显示的完整授权 URL；不要复制视觉上被截断的片段。如果 omp 报告其回调端口被占用，请停止占用该端口的其他进程后重试。在远程或无头系统上，遵循对话框中显示的提供商专属设备/粘贴指示；对于远程认证代理，当该提供商使用回环回调时，使用 auth-broker login --via=user@host。

认证代理启动或请求失败

在客户端运行 omp auth-broker status。检查解析出的 URL、TLS/私有网络可达性，以及客户端 bearer 是否与运行中的认证代理匹配。已配置的认证代理会取代本地认证，而不会回退到 agent.db；缺少 token 属于配置错误。重新生成 token 后，重启认证代理并更新所有客户端。

凭据文件权限过宽

在修复或移动其 SQLite 文件之前先停止 omp。把代理目录限制为你的账户，并把数据库、WAL、SHM、认证代理 token、网关 token 以及加密缓存文件限制为其所有者。同时修复备份和密钥管理器导出文件的权限；只改活动数据库并不能消除已泄露的副本。
