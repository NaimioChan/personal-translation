工具审批

选择哪些能力立即运行、哪些会停下来等待确认、哪些永不运行。

选一种策略

工具审批保护的是这样一条边界：模型提议某个动作，而 omp 用你账户的权限去执行它。审批对变更操作、命令执行、浏览器或桌面控制以及委派出去的工作最有用。它们并不能让模型输出变得可信，也不会把被允许的命令放进沙箱。

内置默认值是 yolo。对于交互式编码会话，更安全的起点是 write：

# ~/.omp/agent/config.yml
tools:
  approvalMode: write

你也可以选择工具审批，入口在 /settings 中。模式名称描述的是无需提示即可运行的最高能力层级：

模式立即运行会提示
always-ask只读调用工作区/会话写入以及可执行动作
write只读调用与工作区/会话写入bash、eval、浏览器控制和 task 等可执行动作
yolo读、写和可执行调用仅按层级判定时，什么都不提示

尽管名字如此，always-ask 并不会为普通读取而询问。未知或格式错误的声明式自定义工具会被当作可执行层级处理，即保守层级。MCP 服务器工具通常是写入层级。

为一次性会话使用启动标志；它会覆盖配置且不保存：

omp --approval-mode always-ask
omp --approval-mode write "fix the failing test"
omp --approval-mode yolo "apply the reviewed migration"

# Aliases that force yolo for this process
omp --auto-approve "run the release script"
omp --yolo "run the release script"

推荐配置

交互式工作

当你希望常规的读取和编辑顺畅进行，但仍想审查命令和其他范围较广的执行时，使用 write。当你希望每一次变更都必须跨过人工边界时，使用 always-ask。

tools:
  approvalMode: write
  approval:
    eval: prompt
    computer: prompt

无人值守的自动化

在没有挂载交互式审批 UI 时，提示无法被回答。请使用显式的 yolo 模式，然后对任务不应使用的能力设为拒绝或提示。在真正无头的场景中，优先使用 deny：prompt 策略会让调用失败，而不是永远等待。

# ci-approvals.yml
tools:
  approvalMode: yolo
  approval:
    computer: deny
    browser: deny
    eval: deny

omp --config ./ci-approvals.yml --print "update generated files and report the diff"

请把这当作权限设计，而不只是抑制提示。请在不那么宽裕的账户或容器中运行自动化，并只授予它需要的工具。

ACP 客户端

ACP 使用相同的全局、项目、叠加层和运行时设置。审批请求由 ACP 客户端呈现：文件系统与 shell 能力在可用时使用客户端的权限请求，而其他 omp 提示在受支持时使用表单征询。拒绝、取消，或某个必需的提示不受支持，都会终止该调用。

schema 的默认值是 yolo，但一个其他方面都取默认值的 ACP 会话，仍然会为 bash、edit、delete 和 move 保留客户端权限闸门。如果客户端本就打算无人值守运行，请显式选择加入：

omp acp --approval-mode yolo
# equivalent:
omp acp --yolo

显式配置的 tools.approvalMode: yolo 也会跳过该 ACP 闸门，除非某个按工具的策略指定了 prompt 或 deny。ACP 在 session/new、session/load 或 session/resume 中没有按会话的审批字段；请启动一个独立的 omp acp 进程，或给它一个会话专属的 --config 叠加层。客户端设置见ACP。

覆盖单个能力

tools.approval 是一个以工具名或挂载能力名称为键的映射。每个取值是：

  • allow — 跳过该模式的层级提示直接运行，除非更强的工具策略另有要求；
  • prompt — 在交互式会话中询问，除非更强的工具策略已经决定了该调用；
  • deny — 在执行前阻止；它总是胜过 allow/prompt 决定。

覆盖在所有模式下都生效，因此它们既能放宽 always-ask，也能收紧 yolo：

tools:
  approvalMode: write
  approval:
    bash: prompt
    read: allow
    eval: deny
    computer: deny
    mcp__filesystem__delete: deny

请使用待处理/已完成调用中显示的确切工具名，或工具索引中的名称。对于挂载的 xd:// 能力，会先检查它自己的策略；如果不存在，则以外层 write 策略作为回退。非法的策略字符串会被忽略，所以只使用 allow、prompt 或 deny，并用下面的命令审计生效的 YAML：

omp config get tools.approvalMode
omp config get tools.approval

对于针对具体命令的 shell 规则，请使用有序的 bash.patterns；第一条匹配的规则生效。deny 和 prompt 规则可以命中复合命令中匹配的某个片段，而 allow 必须匹配完整的、非复合的命令。

tools:
  approvalMode: yolo
  approval:
    eval: deny       # bash rules do not cover a shell spawned through eval

bash:
  patterns:
    - match: "git status*"
      approval: allow
    - match: "rm -rf *"
      approval: deny
    - match: "*deploy*"
      approval: prompt

bash.patterns 规则只管 bash 工具。如果 eval 可能启动 shell，请像上面那样单独为 eval 设置闸门。

审批提示意味着什么

提示是根据真正将要执行的调用构建的，也就是在任何扩展修改其输入之后。它提供批准和拒绝，并显示：

  • Allow tool: <name>；
  • 相关时的 MCP 来源；
  • 提供时的策略或安全原因；
  • 工具特有的细节，例如命令、路径、代码、浏览器动作或子代理分配。

过长的细节在显示时会被截断。请阅读目标、作用域和取值，而不是仅凭工具名就批准。审批只针对那一次调用；它并不构成后续调用具有相同参数的长期承诺。

omp 如何做出决定

对每次调用，omp 先向工具询问其能力层级和任何依赖参数的政策，然后与你的配置结合：

  1. 工具声明的 deny 胜出。
  2. 其次是你按能力设置的 deny 胜出。
  3. 工具声明的安全策略可以显式允许或提示。在非 yolo 模式下，安全覆盖会触发提示，除非工具显式允许。
  4. 当更强的工具策略没有决定该调用时，你有效的 allow 或 prompt 生效。
  5. 否则，模式会将该调用的 read、write 或 exec 层级与上面的模式表比较。

在 yolo 下，工具自身的安全覆盖不会单独触发提示，但工具显式声明的 prompt、你的 prompt、任一种 deny，以及提供商安全检查仍然生效。这一区别解释了为什么对同一工具的两次调用行为可能不同：参数可能选中了不同的层级或策略。 例如，bash 能识别一小类关键形态，例如对绝对路径的递归删除、先远程获取再执行、关闭主机，以及写入敏感的账户文件。该内置检查在非 yolo 模式下会强制提示，但它只是一个裸覆盖，所以 yolo 会跳过它。要让某条边界在 yolo 下也绝对生效，请配置 bash.patterns 的 deny 或按工具的 deny；在需要交互式审查的地方使用 prompt。

工具与扩展的执行约束独立于模式计算。扩展可以阻止一次调用，工具可以拒绝不安全或非法的输入，操作系统或提供商可以不授予权限，运行时错误也可以中止一个已获批准的动作。工具作者可以声明这些边界；见自定义工具。

电脑控制与提供商安全

computer 能力默认禁用。启用后，声明 read_only: true 的调用属于读取层级；会修改的、缺失的或格式错误的声明属于可执行层级。它的审批提示会标记只读调用并显示提交的代码。声明只是选择闸门——它并不能静态地证明任意代码无害。

源自提供商的电脑控制调用还可能带有待处理的安全检查。这些检查始终需要交互式确认，即使在 yolo 下、在设置 computer: allow 时，或在批准了外层挂载能力的分派之后也是如此。提示会列出提供商的检查代码、消息和经过清理的数据。没有交互式 UI 时，omp 会失败关闭。

即使已经批准，重要的现实世界动作仍可能在风险点停下来要求确认，除非你的直接请求已经授权了确切的目标、作用域和取值。网页或桌面上的文本不可信，无法授予该授权。yolo 移除的是 omp 的常规层级提示；它不会覆盖提供商检查、工具或扩展的拒绝、直接用户授权规则、操作系统权限或服务端防护。

无头会话与子代理

无头会话无法满足必需的 omp 提示。该调用会以 requires approval but no interactive UI available 失败；提供商安全检查会报告它们自己的失败关闭错误。请更改模式、添加范围很窄的 allow，或通过交互式 UI 运行——不要仅仅为了掩盖错误而添加宽泛的权限。

子代理同样是无头的。它们把普通层级判定当作 yolo 来执行，因为对父级 task 调用的批准就是它们的授权边界。你的 tools.approval 映射仍会被继承：deny 会阻止，allow 会运行，而 prompt 无法被回答，因此会拒绝该子代理调用。在批准父任务之前，请审阅它的分配和隔离选择。

优先级与审计

从最强到最弱的配置层，审批设置的解析顺序是：

  1. 运行时标志（--approval-mode、--auto-approve、--yolo）；
  2. 较晚的 --config 叠加层，然后是比较早的叠加层；
  3. 项目配置（.omp/config.yml 优先于旧式 .omp/settings.json）；
  4. 全局 ~/.omp/agent/config.yml；
  5. 内置默认值。

映射会深度合并，因此项目可以添加一条 tools.approval 条目而不抹掉无关的全局条目。像 bash.patterns 这样的数组会被更高层整体替换。所有配置位置见设置。

要审计意外结果：

  1. 在同一个工作目录中运行 omp config get tools.approvalMode 和 omp config get tools.approval。
  2. 检查启动标志和每个 --config 文件；运行时标志优先，较晚的叠加层优先。
  3. 匹配确切的工具/能力名称，并检查提示或错误中的任何 Reason:。
  4. 对于 bash，检查第一条匹配的 bash.patterns 规则；然后确认该动作是否实际改用了 eval。
  5. 判断结果来自用户策略、工具/扩展策略、ACP 权限、提供商安全检查，还是缺少交互式 UI。

如果某次调用在 always-ask 或 write 下意外提示，它的参数可能把它提升到了 write 或 exec，或者有显式的提示/安全覆盖在生效。如果某次调用在 yolo 下意外运行，请记住层级提示是被有意跳过的；请添加 tools.approval.<name>: prompt 或 deny。如果某次调用在所有模式下都被拒绝，只有在合适时才移除或更改那条确切的用户 deny——yolo 无法击败权威的工具或提供商边界。
