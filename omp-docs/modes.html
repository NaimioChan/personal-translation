运行模式

选择正确的交互式、一次性或协议模式，然后控制重复工作、单工具轮次和优先服务。

omp 有两种模式：

  1. 启动模式决定你是在终端 UI 中工作、接收一个答案、流式输出机器可读事件，还是把 omp 连接到另一个应用程序。
  2. 交互式轮次控制改变终端会话内工作的运行方式：/loop、/force 或 /fast。

常规编码工作请从终端 UI 开始：

omp

描述你想要的结果，例如："把项目里的 issueToken 重命名为 mintToken，并更新每一处调用。"只有当脚本、编辑器或应用程序——而不是终端前的人——需要消费输出时，才使用其他启动模式。

--mode 恰好接受 text、json、rpc、rpc-ui 或 acp。任何显式的 --mode 都会选择无头模式——即使 --mode text 也是如此。只有当你没有提供 --print、没有选择模式，且 stdin 没有提供提示词时，裸 omp 才是交互式的。

交互式终端 UI

除非你有特定的自动化或集成需求，否则请使用这种方式。

  • Esc 中断当前轮次。它不会退出 omp。
  • Ctrl+C 清空编辑器；在半秒内再次按下则退出。
  • Ctrl+D 退出并保存未发送的草稿，以便会话恢复时还原。
  • /exit、/quit 和 /q 执行同样的有序关闭。

状态行仅在此模式下可用。当 Fast、Plan、Goal、Vibe 和 Loop 等控制项处于活动状态时，其模型区段和模式区段会显示它们。

一次性文本

以下形式是请求纯文本并退出的等价方式：

omp -p "Summarize the last commit"
omp --mode text "Summarize the last commit"
printf '%s\n' "Summarize the last commit" | omp

只有 --print 和 --mode 都没有选择其他方式时，管道 stdin 才会自动选择一次性文本。omp 会等待 EOF 后才开始；如果生产者让 stdin 保持打开，omp 会在 stderr 上报告它仍在读取提示词。请关闭生产者，或按 Ctrl+C。

默认情况下，stdout 只包含最终的助手文本。当脚本确实还需要模型的思考块时，加上 --print-thoughts：

omp -p --print-thoughts "Explain this stack trace"

全新的一次性运行会忽略 plan.defaultOnStartup，因为没有审阅界面。受支持的无头“先计划再执行”流程请使用 --plan-yolo；参见 计划模式。

JSON 事件流

当脚本需要进度和生命周期事件、而不是渲染好的答案时，请使用 JSON：

omp --mode json "Find every TODO under src" > run.jsonl

当会话有头部时，它是第一行 JSON；随后是会话事件。流式更新会省略重复的完整消息快照和提供商私有的重放数据，因此请消费事件流，而不要指望每一行都是完整的对话记录。

RPC、RPC UI 和 ACP

这些是集成传输方式，而不是替代的终端界面：

  • RPC 是 omp 原生的换行分隔协议。它拥有 stdin 和 stdout，并在接受命令前发出 ready。@file 启动参数会被拒绝，因为客户端必须通过协议提供提示词和上下文。参见 RPC 模式。
  • RPC UI 是面向宿主的 RPC，该宿主还会渲染 omp 的交互式扩展和工具 UI 请求。它不是 rpc 的装饰版本；除非宿主实现了这套 UI 交互，否则不要选择它。它还会禁用基于 PTY 的 shell 执行。
  • ACP 是标准的编辑器集成。优先使用 omp acp；omp --mode acp 等价。编辑器启动该进程并通过 stdio 创建会话。手动运行它会在 stderr 上打印说明并等待协议帧。参见 ACP。

关闭 RPC 的 stdin 就是告诉 omp 客户端已经消失：它会拒绝挂起的 UI 请求、处理完已接受的命令、销毁会话并退出。ACP 在对端断开连接时退出。协议的 stdout 请保留给协议使用；把应用程序自身的日志发往别处。

在终端 UI 中控制轮次

这些斜杠控制项不会替代启动模式。它们作用于交互式会话内部。

用 /loop 重复工作

Loop 模式会捕获一个提示词，并在每轮之后再次提交它。把它用于真正可重复、且有可观察停止条件的工作，例如处理队列中的下一个文件，或修复下一个失败的测试。

/loop
Fix the next failing test. If the suite is clean, explain that and stop.

/loop 5 Review the next unreviewed migration
/loop 30m Process the next item in the queue
/loop 1h30m Check the next repository and record the result
/loop 10 minutes Re-run the acceptance check

各形式的含义是：

  • /loop 启用无限循环；下一个普通提示词将成为被重复的提示词。
  • /loop <prompt> 立即以该提示词启动无限循环。
  • /loop <positive-integer> [prompt] 允许在首轮之后自动重新提交那么多次。
  • /loop <duration> [prompt] 在墙钟截止时间到期时停止重新提交。可接受的单位有秒、分钟和小时，包括 s、sec、m、min、h、hr、复数形式、1h30m 这样的紧凑复合形式，以及 10 minutes 这样的带空格形式。

状态行会显示 Loop waiting、Loop running 或 Loop paused，以及剩余次数或时间。斜杠命令自动补全也会描述当前的 Loop 状态。

Loop 的各项控制有意区分开：

  • 在一次迭代过程中按 Esc 可中止该轮次。Loop 保持启用。
  • 在两次迭代之间按 Esc 可暂停、丢弃已捕获的提示词并阻止挂起的重放。下一个普通提示词会成为新的 loop 提示词并恢复它。
  • 再次运行 /loop 可完全禁用 Loop。
  • 次数上限或时长截止会自动禁用 Loop 并说明原因。

默认情况下 loop.mode 为 prompt，因此每次重放都在同一会话中继续。compact 设置会在每次重放前压缩；reset 会在每次重放前启动全新会话。仅当重复的上下文成为问题时才配置这些——参见 设置。

用 /force 强制一次工具调用

当 omp 反复选错活动工具时，把 Force 用作一种范围很窄的纠正手段。先用 /tools 查看可用的名称，然后精确强制一次调用：

/force read Inspect package.json and summarize its scripts
/force:read Inspect package.json and summarize its scripts

两种写法都受支持。没有内联提示词时，强制作用于你提交的下一个提示词：

/force read

Force 不是持久模式。下一次模型调用必须调用该活动工具一次，然后代理轮次结束，不再有另一次工具调用。下一轮恢复正常。没有 Force 徽章，因为不存在持续状态；当下一个轮次被固定时，omp 会显示确认。

当指定工具处于非活动状态，或当前模型无法强制指定工具时，Force 会失败而不是猜测。这在 计划模式中很重要——在那里可写入的工具是有意不可用的。

用 /fast 请求优先服务

Fast 模式要求当前模型系列使用其优先服务路径：

/fast on
/fast off
/fast status
/fast

裸 /fast 是切换。需要确定性状态时优先用 /fast on，因为它是幂等的，并且会在当前模型没有兼容的服务层级控制时给出报告。

该设置按会话持久化，并独立作用于 OpenAI、Anthropic 和 Google 模型系列。如果你在 OpenAI 系列模型上启用 Fast，切换到 Anthropic 模型，之后又切回来，OpenAI 系列的选择仍然处于开启状态；Anthropic 系列保留自己的选择。

当优先服务真正生效时，如果主题提供了 Fast 图标，模型区段会显示它。/fast status 是检查当前模型系列已配置状态的直接方式；当该模型没有兼容的优先服务控制时，/fast on 会给出报告。如果提供商拒绝优先服务，omp 会在不带它的情况下重试，为该系列关闭 Fast，并显示警告。

优先服务可能花费更高，并会计入高级请求的统计。请检查 /usage 或 omp stats，不要想当然地认为更低的延迟是免费的。

这些控制项如何组合

组合结果
Loop + Fast当活动模型支持所选系列的优先层级时，每个重复轮次都使用 Fast。
Loop + Force只有即将到来的第一次模型调用被强制。之后 loop 的重新提交不受强制。
Loop + 活动的 Goal在 Loop 被禁用之前，Loop 优先于自动的 Goal 继续。若想实现目标驱动的自主性，请使用 目标模式，不要毫无理由地把两者叠加。
Loop + Plan、Prewalk、Goal 或 Vibe这些控制项可能仍然活动，但单一模式区段会显示优先级更高的工作状态而不是 Loop。这是显示优先级，不是 Loop 已关闭的证明。
loop.mode: reset + Vibe该组合会被拒绝：omp 会禁用 Loop，并提示你先退出 Vibe 再使用 reset 循环。
Force + PlanForce 只能选择在 Plan 的只读环境中活动的工具。
任一启动 --mode + 另一个启动模式启动模式互斥；只传一个 --mode 值。RPC 和 ACP 拥有 stdin，因此管道传入的字节是协议帧，不是提示词。

Fast 有自己的模型区段图标，因此它独立于单一的工作模式区段保持可见。要确认被另一个工作状态徽章遮住的 Loop，请打开 /loop 的斜杠自动补全；要停止它，运行 /loop。

选择工作模式，而不是传输模式

若干更深层的功能会改变 omp 处理工作的方式。它们在相应的启动模式中可用，并各自拥有控制方式：

  • 计划模式 —— 在实现之前审阅方案。
  • 目标模式 —— 跨轮次推进一个持久目标。
  • Vibe 模式 —— 协调并行工作者。
  • Prewalk —— 把计划好的实现交给更快的模型。
  • 顾问模型 —— 被动审阅工作并提示问题。

这些页面的生命周期与安全控制请参阅对应页面。本页用于选择如何启动 omp，以及当前终端轮次是否应重复、强制一个工具或请求优先服务。

疑难排查

终端 UI 打开了，但我想要的是给脚本用的输出。
用 -p 获取最终文本，或用 --mode json 获取事件。裸的位置参数提示词并不会让 omp 变成无头模式。

管道命令在任何工作开始前看起来卡住了。
omp 必须把 stdin 读到 EOF。检查生产者是否关闭了管道；一秒之后 omp 会在 stderr 上报告它在等待什么。

omp acp 看起来空闲。
那是等待 ACP 客户端的服务器，不是独立 UI。配置你的编辑器来启动它；参见 ACP。

Loop 在重复，但它的徽章消失了。
Plan、Prewalk、Goal 和 Vibe 在单一模式区段中具有显示优先级。在斜杠自动补全中检查 /loop。运行 /loop 禁用它。

/force 说该工具未激活。
运行 /tools。如果当前工作模式有意移除了该工具，请更换工作模式，或选择其中一个活动名称。

/fast on 不可用，或自行关闭了。
当前模型要么没有受支持的优先服务路径，要么其提供商拒绝了请求。继续使用普通层级，或切换到受支持的模型；被拒绝后不要反复切换。
