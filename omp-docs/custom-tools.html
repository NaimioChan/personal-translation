自定义工具

给 omp 一个带类型的、项目专属的动作，然后像使用任何内置能力一样，在普通提示词中使用它。

添加一个 omp 没有的动作

自定义工具是一个小的 TypeScript 或 JavaScript 模块，让 omp 能够调用你控制的代码。它适用于项目专属的工作，例如查询内部服务、检查某个领域不变量，或执行一项范围谨慎界定的操作。

从项目工具开始，这样它的源码可以随仓库一起被审查。创建 .omp/tools/hello/index.ts，从项目里重启 omp，然后让它使用该工具。如果该能力已经存在于某个独立服务中，或需要被多个客户端共享，请改用 MCP 服务器。

自定义工具是受信任的代码。omp 会导入发现的工具模块，并以你用户账户的权限运行它们。在不熟悉的仓库中打开 omp 之前，请审查项目本地的 .omp/tools 代码。

创建最小的工具

在项目根目录执行：

mkdir -p .omp/tools/hello

创建 .omp/tools/hello/index.ts：

import type { CustomToolFactory } from "@oh-my-pi/pi-coding-agent";

const factory: CustomToolFactory = pi => ({
  name: "hello",
  label: "Hello",
  description: "Greet a person by name",
  parameters: pi.zod.object({
    name: pi.zod.string().describe("The person to greet"),
  }),

  async execute(_toolCallId, params) {
    return {
      content: [{ type: "text", text: `Hello, ${params.name}!` }],
      details: { greeted: params.name },
    };
  },
});

export default factory;

这个示例不需要安装任何 schema 包。omp 会把 schema 构建器作为 pi 注入工厂。

加载并测试它

工具发现发生在会话启动时。退出任何正在运行的会话，然后从项目根目录再次启动 omp：

omp

输入 /tools，确认 hello 已被列出。然后提示：

Use the hello tool to greet Ada.

你应该会看到一个 Hello 工具卡片，以及包含 Hello, Ada! 的最终结果。若想做一次性的检查，启动一个新进程：

omp -p 'Use the hello tool to greet Ada.'

你只需编写工厂及其 execute 函数；你不调用 execute，也不输入 JSON 工具请求。模型会根据你的自然语言请求选择工具，构造与 parameters 匹配的参数，omp 在运行你的代码之前会校验这些参数。精确的 description、字段描述和收窄的 schema 会让这一选择更可靠。

选择加载位置

作用域推荐路径适用场景
项目.omp/tools/<name>/index.ts该工具属于一个仓库，并应随它一起被审查。
用户<active-config-dir>/tools/<name>/index.ts你希望该工具在当前 omp 配置文件的每个项目中可用。运行 omp config path 打印当前配置目录；默认是 ~/.omp/agent。

omp 原生目录也接受扁平的 .ts 和 .js 文件，例如 .omp/tools/hello.ts。当工具有配套文件时，使用带 index.ts 的命名子目录更合适。为了兼容性，omp 还会在用户和项目的 .claude/tools 与 .codex/tools 目录中发现扁平的 .ts 与 .js 工具。

被发现的 .md 或 .json 文件是元数据，不是可执行的工具模块。可执行模块必须导出一个工厂函数；默认导出是上面所示受支持且无歧义的形式。

工厂与定义 API

从 @oh-my-pi/pi-coding-agent 导入 CustomToolFactory。一个工厂可以返回一个工具、一个工具数组，或它们之一的 promise。返回的每个工具名在内置工具和所有其他已加载的自定义工具之间必须唯一。

必需字段

字段作者契约
name用于标识该工具的注册名。不要复用内置工具或其他自定义工具的名称。
label在 TUI 中显示的人类可读名称。
description简短、具体的指引，帮助模型判断该工具何时适用。
parameters可接受参数的 schema。omp 由此推导 params 的 TypeScript 类型，并在 execute 之前校验调用。
execute返回 AgentToolResult 的异步实现。

可选行为

字段作用
strict为该工具请求严格的 schema 处理。
hidden让该工具保持禁用，除非被显式选中。
loadMode"discoverable" 让 schema 不进入始终存在的工具集；"essential" 让它保持顶层。自定义工具默认是 "discoverable"。
approval声明能力层级："read"、"write" 或 "exec"；它也可以是决策对象或解析后参数的函数。省略 approval 会被当作 "exec"。
onSession接收用于初始化、状态变化和清理的生命周期事件。
renderCall替换该调用默认的 TUI 渲染。
renderResult替换部分结果与最终结果默认的 TUI 渲染。

renderCall(args, options, theme) 与 renderResult(result, options, theme) 返回来自 @oh-my-pi/pi-tui 的 Component。它们的 options 包含 expanded 与 isPartial；部分渲染还可以收到 spinnerFrame。渲染器影响的是人看到的内容，而不是模型收到的内容。

参数 schema

工厂宿主提供三个公开的 schema 构建器：

构建器说明
pi.zod入门示例中使用的、与 Zod 兼容的构建器。
pi.arktype原生的 omptype/ArkType 构建器。
pi.typebox为基于旧 TypeBox 风格 API 编写的工具提供的兼容层。新工具请优先使用当前的构建器。

在操作允许的范围内尽量保持 schema 小巧。为有限的动作使用枚举，为含义不显然的字段写描述，并在省略具有安全含义时把默认值放进 schema。

parameters: pi.zod.object({
  action: pi.zod.enum(["check", "summarize"]),
  path: pi.zod.string().describe("Repository-relative file path"),
  limit: pi.zod.number().int().positive().optional().default(20),
}),

执行、进度与取消

完整的执行签名是：

async execute(toolCallId, params, onUpdate, ctx, signal) {
  // ...
}
参数用途
toolCallId关联本次调用的日志或 UI 状态。
params已校验、带 schema 类型的参数。
onUpdate可选回调，用于向用户展示部分进度。模型收到的是最终返回的 content，而不是这些进度更新。
ctx供高级的会话感知工具使用的 CustomToolContext。普通工具应优先使用稳定的工厂宿主 API，避免依赖会话内部结构。
signal可选的 AbortSignal。在长时间运行的工作中检查它，并把它转发给可取消的操作。

工厂宿主把会话工作目录暴露为 pi.cwd，把可感知取消的进程 helper 暴露为 pi.exec(command, args, options?)：

async execute(_id, params, onUpdate, _ctx, signal) {
  onUpdate?.({
    content: [{ type: "text", text: `Checking ${params.path}…` }],
  });

  const result = await pi.exec("git", ["status", "--short", "--", params.path], {
    cwd: pi.cwd,
    signal,
  });

  if (result.code !== 0) {
    throw new Error(result.stderr || "git status failed");
  }

  return { content: [{ type: "text", text: result.stdout || "No changes" }] };
}

交互式 UI 方法只在 pi.hasUI 为 true 时通过 pi.ui 提供。Print、RPC 和其他无头模式不提供交互式 UI，因此每一个打算在这些模式下使用的工具都必须有一条非交互路径。

结果与错误

返回一个 AgentToolResult：

return {
  content: [
    { type: "text", text: "Check complete." },
    { type: "image", mimeType: "image/png", data: pngBase64 },
  ],
  details: { checked: 12 },
  isError: false,
};
  • content 是必需的。它包含文本和/或 base64 图片块，是模型在下一步可以使用的结果。
  • details 是可选的、用于 UI 渲染、日志与历史的结构化状态。它不会替代用户可读的 content。
  • isError: true 标记一个预期的、非抛出式失败，同时保留结构化结果。

对于阻止操作产生有用结果的失败，请抛出 Error。omp 会把抛出或被拒绝的错误转换为给模型的失败工具结果，并向用户显示该失败。当你的工具故意捕获某个领域失败、并且自己能够返回清晰的结构化说明时，使用 isError: true。绝不要把失败隐藏在看起来成功的内容背后。

把 signal 转发给 pi.exec 和其他可取消的 API。这样用户的停止操作就能取消子进程工作，而不是让它继续运行。

会话生命周期

只有当工具拥有必须跟随会话变化的资源或状态时，才添加 onSession(event, ctx)。它可以是同步的，也可以是异步的。

onSession(event) {
  if (event.reason === "shutdown") {
    // Close resources created by this factory.
  }
},

event 是一个可辨识联合。当前的原因有：

原因发生时机
start、switch、branch、tree、shutdown会话创建、导航与拆除。这些事件携带 previousSessionFile；它在 switch/branch 时有值，其他情况下可能为 undefined。
auto_compaction_start、auto_compaction_end自动上下文压缩之前与之后。
auto_retry_start、auto_retry_end自动重试处理之前与之后。
ttsr_triggered运行时规则触发时。
todo_reminder发出 todo 提醒时。

生命周期错误会以警告形式记录，不会使会话崩溃。保持清理操作幂等；如果持久状态必须在进程重启后存活，就把它放在内存闭包之外。

故障排除

/tools 没有列出该工具

  1. 重启 omp；直接的自定义工具目录在会话启动时被扫描。
  2. 确认项目会话是从包含 .omp/tools 的目录启动的。
  3. 确认该模块是 .ts 或 .js 文件，并且默认导出一个函数。
  4. 检查工厂返回的对象是否包含 name、description、parameters 和 execute。
  5. 在 ~/.omp/logs/ 下今天的日志中查找 Custom tool load failed。

模块加载了，但这个工具缺失

它的 name 很可能与某个内置工具或先前加载的工具冲突。冲突会被拒绝；没有覆盖标志。重命名该工具并重启 omp。

模型不选择它

让工具的 description 明确说明何时应该使用它，为含义不清的参数写描述，并把宽泛的字符串收窄为枚举或受约束的 schema。测试期间，在自然语言提示词中明确写出工具名。只有当工具必须在每次请求中保持顶层时才使用 loadMode: "essential"；否则保持可发现的默认值。

交互模式下可用，但在 print 或 RPC 模式下失败

实现很可能假设了 TUI 环境。用 pi.hasUI 保护对 pi.ui 的调用，并提供无头行为，或返回一个清晰的错误，说明该操作需要交互式会话。
