上下文压缩

让漫长的omp会话持续有用：让自动上下文维护运行，或使用/compact、/handoff和/shake主动恢复。

长会话最终会包含模型无法一次考虑的过多文本。omp会在保留最近对话的同时压缩较早的上下文，让工作继续进行。通常无需执行任何操作：自动压缩默认已启用。

先运行：

/context

这会显示当前模型上下文窗口的使用量，以及自动维护前剩余的空间。除非omp遗漏了重要细节、上下文被庞大输出占满，或你想选择保留哪些内容，否则请继续正常工作。

自动压缩的作用

当上下文接近当前模型的限制时，omp会先移除可以安全省略的过时文件读取、空搜索和其他庞大结果。随后按配置的方法顺序尝试维护。默认顺序是：

  1. 提供商原生的服务器压缩，当前路由支持时使用；
  2. snapcompact，将较早历史归档为供支持视觉的模型使用的密集图像；
  3. 结构化的交接摘要；
  4. shake，移除可恢复的命令、搜索和文件输出的大块内容，不请求摘要；
  5. soft压缩，使用模型总结较早的历史。

不可用或失败的方法会转到下一个方法。因此，默认顺序无需针对具体模型配置，就能同时适用于纯文本模型和支持视觉的模型。

无论哪种方法成功，当前模型都会保留对话最近部分，并接收较早上下文的紧凑替代内容。较早轮次的确切措辞不再位于模型的实时窗口中，但普通压缩不会删除原始会话记录。

自动维护可能在以下时机发生：

  • 成功响应超过阈值之后；
  • 长轮次涉及许多命令或文件读取时，在模型请求之间；
  • 上下文溢出或输出不完整的响应之后，并在重试之前；
  • 空闲时，但仅当明确启用了空闲压缩。

默认情况下，omp可以在接近阈值前准备摘要，从而缩短可见暂停。阈值维护后，它会自动继续工作。溢出和输出不完整的恢复则会改为重试被中断的工作。

你会看到什么

TUI会显示类似Auto server compaction…、Auto-snapcompact…、Auto-handoff…或Auto-shake…的状态。按Esc可取消。压缩运行期间输入的文本会等待维护完成。

摘要方法成功后，对话记录会围绕类似soft-compacted、remote-compacted或handed-off的细分隔线重建，通常还会显示类似256K→20K的token缩减量。压缩前的历史默认折叠。按Ctrl+O可在分隔线处展开摘要。

自动shake则会报告Auto-shake completed，并用简短占位符替换符合条件的大块区域。使用compaction.autoContinue: true（默认值）时，阈值触发的维护会继续进行，无需等待新的提示词。

/compact：通常的手动选择

运行/compact，立即使用第一个可用的已配置手动方法进行压缩：

/compact

当较早上下文包含多个主题且其中一个最重要时，添加重点说明：

/compact Preserve the API decisions, unresolved test failure, and exact next steps. Treat benchmark experiments as disposable.

你可以一次性选择方法，而不改变设置：

语法适用时机
/compact soft [focus]你想要传统的模型生成摘要，也可以指示摘要重点。
/compact remote [focus]你想在可用时使用提供商原生的OpenAI兼容压缩；不可用时会回退到soft压缩。
/compact snapcompact你想使用支持视觉的模型进行本地图像归档，且不发起摘要请求。它不接受重点文本。

即使禁用了自动压缩，手动/compact仍然有效。如果当前正在运行响应，命令会先中止该响应，再进行压缩。操作期间TUI显示Compacting context… (esc to cancel)；成功后，分隔线和减少后的上下文使用量会确认结果。

/handoff：保留结构化项目状态

当通用对话摘要过于松散时使用/handoff，例如从调查转入实现之前，或长任务包含许多决策和依赖关系时：

/handoff Focus on the accepted design, files already changed, verification still needed, and known risks.

虽然名称如此，手动命令目前会在当前会话中原地压缩。它不会打开后继会话，默认也不会保存Markdown交接文件。运行/handoff前请等待当前响应完成，或先中止响应。关于交接文档的内容和自动交接行为，请参阅交接。

/shake：移除大块内容而不总结对话

/shake默认使用elide：

/shake

它会用简短占位符替换符合条件的命令、搜索和文件读取输出，以及大型围栏代码块或类XML代码块。在可持久化会话中，omp还会尽可能将移除的区域保存为会话工件；占位符包含artifact://…恢复引用。如果之后移除的结果变得重要，请让omp根据该引用恢复指定区域。

针对特定内容的变体破坏性更强：

命令移除内容恢复
/shake elide符合条件的大型结果和大块内容当会话可以持久化工件时，原始区域会保存到工件中。
/shake images会话中的图像块不会创建恢复工件。
/shake thinking存储的推理块不会创建恢复工件。

只有在图像或推理材料不再需要后，才应移除它们。Nothing to shake、No images found或No thinking blocks found等结果表示成功但未执行任何操作，而不是错误。

配置

默认值适合大多数用户。你可以通过/settings、omp config set等 shell 命令，或在~/.omp/agent/config.yml中使用YAML来修改它们（现有的config.yaml也会生效）。项目覆盖配置可以放在<project>/.omp/config.yml中。

例如，以下配置启用空闲维护，同时保留正常的自动行为：

compaction:
  enabled: true
  idleEnabled: true
  idleThresholdTokens: 200000
  idleTimeoutSeconds: 300

从 shell 验证生效值：

omp config get compaction.enabled
omp config get compaction.methodOrder
omp config get compaction.thresholdPercent

在会话中运行/context，验证最终阈值和可用余量。

设置参考

设置默认值作用
compaction.enabledtrue启用自动维护。即使设为false，手动/compact、/handoff和/shake仍可用。
compaction.methodOrder[remote, snapcompact, handoff, shake, soft]自动回退列表的顺序。支持的值为remote、snapcompact、handoff、shake和soft。
compaction.thresholdTokens-1大于零时使用固定触发值。它优先于thresholdPercent。
compaction.thresholdPercent-1大于零时使用百分比触发值。-1使用基于预留量的自动计算。数值会限制在1–99%范围内。
compaction.reserveTokens未设置基于预留量的计算所使用的余量。未设置时，omp通常预留16,384个token或模型窗口的15%中的较大值；较小的窗口则回退到按比例预留。
compaction.keepRecentTokens20000总结式压缩后按原文保留的最近对话目标数量。
compaction.midTurnEnabledtrue允许在涉及许多命令或文件读取的长轮次中，于安全边界执行维护。
compaction.asyncEnabledtrue在阈值前不久准备符合条件的摘要，以缩短压缩提交时的暂停。
compaction.autoContinuetrue阈值维护在轮次结束后自动继续。脚本化或无头运行需要在此停止时设为false。
compaction.idleEnabledfalse启用会话空闲时的维护。
compaction.idleThresholdTokens200000执行空闲维护所需的最小上下文大小。
compaction.idleTimeoutSeconds300开始考虑维护前的空闲时间。
compaction.handoffSaveToDiskfalse将自动交接生成的文档保存到磁盘。它不会让手动/handoff保存文件。
compaction.supersedeReadstrue在再次读取同一文件后，条件允许时省略较早的文件内容副本。
compaction.dropUselesstrue省略不携带有用上下文的已消耗输出，例如空搜索或超时等待。
compaction.remoteEndpoint未设置使用自定义的OpenAI兼容远程压缩端点。大多数用户应保持未设置。
compaction.remoteStreamingV2Enabledtrue在兼容路由上使用流式远程压缩。
compaction.v2RetainedMessageBudget64000限制流式远程压缩保留的最近消息预算。

display.collapseCompacted是相关的外观设置。它默认为true，会在实时对话记录中隐藏压缩前的历史，同时保留摘要分隔线可见。如果你偏好将完整的存储对话记录直接显示在行内，请设为false。

故障排查

自动压缩没有运行

  1. 运行/context。维护不会仅仅因为会话感觉很长就运行；估算使用量必须超过解析后的阈值。
  2. 检查omp config get compaction.enabled和omp config get compaction.methodOrder。
  3. 如果你预期会进行空闲维护，请记住compaction.idleEnabled默认为false，且会话必须超过idleThresholdTokens至少idleTimeoutSeconds指定的时长。
  4. 如果某种方法不可用，让回退列表继续执行。例如，纯文本模型无法使用snapcompact，但可以继续使用交接、shake或soft压缩。

/compact提示会话过小或已经压缩

Nothing to compact (session too small)表示没有足够的较早上下文可供替换。Already compacted表示最新边界之后没有大量新历史。继续工作，稍后再试；无需恢复。

Snapcompact失败

Snapcompact需要支持视觉的当前模型，以及其内置图像字体能够表示的文本。使用/compact soft可获得可预测的文本摘要。当当前提供商支持服务器压缩时，/compact remote也是一种选择。

上下文仍然过大

运行/context，确认是消息还是庞大的历史结果占据主要空间。对于大型输出，先使用/shake；当对话本身很大时，使用/compact soft。如果问题反复出现，请降低compaction.thresholdPercent、减少compaction.keepRecentTokens，或选择上下文窗口更大的模型，而不要等待溢出。

重要的旧细节缺失

在压缩分隔线上按Ctrl+O检查生成的摘要。普通压缩会保留底层会话历史，因此请使用会话树回到较早位置，或从那里创建分支。以后手动压缩时，请加入明确的重点说明，或使用/handoff获得更结构化的延续。被/shake images或/shake thinking移除的内容不会保存在恢复工件中。
