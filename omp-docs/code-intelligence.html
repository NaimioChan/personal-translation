非茗的翻译文档库

代码智能

借助你项目已在使用的语言服务器，为 omp 提供符号感知的导航、重命名、修复和诊断能力。

带着语义上下文做代码改动

代码智能让 omp 能向语言服务器询问：某个符号是什么意思、它在哪里定义、哪些代码引用了它，以及哪些修复是有效的。这比把源代码当作纯文本处理更安全：语义重命名可以区分两个同名的变量，并跨文件更新导入与再导出。

通常你只需安装对应语言的语言服务器，从项目根目录启动 omp，然后说明你想要的结果：

Rename `issueToken` to `mintToken` across the project. Preview the language-server changes before applying them.

omp 还能查找定义与实现、查看推断类型、列出引用、报告诊断、应用服务器提供的修复，并在更新导入的同时重命名文件。对于不以符号为中心的、基于语法的改动，请改用结构化编辑。

自动生效的部分

LSP 支持默认启用。omp 会检查内置的服务器定义，并且只在以下两条同时成立时才选用某个服务器：

  1. 在你启动 omp 的目录中直接存在匹配的项目标记，例如 package.json、Cargo.toml 或 go.mod。
  2. 该服务器可执行文件存在于受支持的项目本地 bin 目录中，或位于 PATH 上。

项目本地的可执行文件优先。这包括 node_modules/.bin、Python 虚拟环境的 bin 目录、Ruby binstub，以及 Go 项目中的项目 bin 目录等位置。

发现过程不会向上遍历父目录，通配标记也只检查启动目录。请在包含该标记的仓库或包根目录启动 omp。

默认情况下，检测到的服务器是惰性的：欢迎面板会把它们列为可用，但 omp 会等到代码智能操作或对匹配文件的编辑确实需要某个服务器时才启动它。当守护进程代理可用时，同一项目的多个 omp 会话会共享服务器；如果共享不可用，omp 会退回到使用私有服务器。

在交互模式下，运行 /session 可以查看检测到的服务器名称、文件类型和启动状态：

状态含义
available已检测到，首次使用时即可启动。
connecting正在主动启动。
ready主动启动已完成。
error启动失败；在有可用信息时该行会包含失败原因。

用自然语言提问

描述你想要的结果，并在能消除歧义时把 omp 指向某个符号或文件。你永远不需要提供协议位置或 LSP 请求细节。

目的示例请求
理解某个符号Explain the inferred type of result in src/parser.ts and show me its definition.
查找影响面Find every reference to PaymentGateway.authorize, including implementations, before changing it.
安全地重命名Rename issueToken to mintToken across the project using code intelligence. Preview first.
移动模块Move src/auth/token.ts to src/security/token.ts and update imports through the language server.
诊断文件Ask the language server why src/server.ts is failing and explain the diagnostics.
应用修复Use the server's quick fix for the missing import in src/routes.ts, then check diagnostics again.
查看契约Find every implementation of StorageAdapter and summarize how they differ.

当某个名字在一行中出现多次时，用文字描述具体是哪一处，例如：“第 88 行第二次调用 parse 的地方。”omp 会解析出确切的源码位置。

你会看到什么

导航请求会返回源码位置、签名、类型或文档，omp 可以在回复中加以解释。引用搜索会给出全项目范围的影响清单。诊断包含服务器的严重级别、消息和位置。

对于重命名，当你想在改动发生前检查将要修改的文件时，可以要求先预览。应用时，omp 会显示常规的已改动文件与 diff 输出。语义重命名可能作为一次由服务器计算的工作区改动而更新多个文件；如果服务器没有返回有效的重命名，omp 不会自行编造语义编辑。

语言服务器无法可靠地发现动态字符串查找、散文式注释、工作区之外生成的代码，或者不在该服务器工作区内的另一个包中的使用方。在大范围改动之后，除了检查诊断，还应让 omp 运行项目的编译器和针对性测试。

配置或覆盖服务器

当内置服务器的标记与可执行文件都能被发现时，无需配置文件。先在项目中或 PATH 上安装该服务器，然后从项目根目录重启 omp。

使用 <project>/.omp/lsp.json 做项目级覆盖。例如，内置定义按服务器名称合并，所以下面的配置只更改 gopls 的设置：

{
  "servers": {
    "gopls": {
      "settings": {
        "gopls": {
          "gofumpt": false,
          "staticcheck": false
        }
      }
    }
  }
}

像 settings、initOptions、capabilities 和 workspaceReadyTimings 这类对象值字段会整体替换该字段，而不是深度合并。请把你想保留的每个值都写进被覆盖的对象里。

要添加 omp 未定义的服务器，请提供其命令、处理的扩展名和项目标记：

# <project>/.omp/lsp.yaml
servers:
  my-language-server:
    command: my-language-server
    args: ["--stdio"]
    fileTypes: [".xyz"]
    languageId: xyz
    rootMarkers: [".xyz-project"]

命令可以是从项目本地 bin 目录或 PATH 解析到的二进制名称，也可以是绝对路径。缺少 command、fileTypes 或 rootMarkers 的新服务器会被忽略并给出警告。

要为某个项目禁用某一个内置服务器，同时保留其他服务器可用：

{
  "servers": {
    "eslint": {
      "disabled": true
    }
  }
}

编辑 LSP 配置后，启动一个新的 omp 会话能得到最清晰的验证。查看欢迎面板或 /session，然后询问：

Confirm which language server handles src/main.ts and check that file for diagnostics.

如果你在已有会话中安装了缺失的可执行文件，可以让 omp 重新加载所有语言服务器并重新读取它们的配置。

选择配置放在哪里

omp 会读取名为 lsp 或 .lsp 的 JSON、YAML 和 YML 文件。各来源按优先级从低到高合并：

优先级位置
最低~/lsp.* 和 ~/.lsp.*
已安装插件提供的 LSP 配置
用户配置目录，包括当前活动的 omp 代理目录，以及受支持的 Claude、Codex 和 Gemini 目录
启动目录的配置目录，例如 <cwd>/.omp、<cwd>/.claude、<cwd>/.codex 和 <cwd>/.gemini
最高<cwd>/lsp.* 和 <cwd>/.lsp.*

对于 omp 自己的配置，优先使用：

  • 项目：<project>/.omp/lsp.json
  • 用户：默认配置档使用 ~/.omp/agent/lsp.json，或使用当前活动配置档的代理目录

在同一位置内，优先级依次为 lsp.json、.lsp.json、lsp.yaml、.lsp.yaml、lsp.yml，最后是 .lsp.yml。服务器条目按名称浅合并。覆盖中未提及的服务器会保留其内置定义，omp 仍会按 disabled、根标记和可执行文件可用性过滤合并后的集合。

顶层的 servers 包装是可选的，但不要混用带包装与扁平的服务器条目。下面两种写法等价：

{
  "servers": {
    "eslint": { "disabled": true }
  },
  "idleTimeoutMs": 300000
}

eslint:
  disabled: true
idleTimeoutMs: 300000

idleTimeoutMs 省略、为零或为负值时，空闲关闭功能保持禁用。

LSP 设置

打开 /settings，然后在文件 → LSP分组中交互式更改这些项。持久设置也可以写入用户级 ~/.omp/agent/config.yml 或项目级 .omp/config.yml；配置档与优先级见设置。

设置默认值作用
lsp.enabledtrue启用符号智能、LSP 格式化和 LSP 诊断。
lsp.lazytrue仅当匹配的文件操作需要时才启动服务器。设为 false 可在交互式启动时于后台预热已检测到的服务器。
lsp.sharedtrue通过守护进程代理为每个项目共享一个服务器，并在不可用时回退到私有服务器。
lsp.formatOnWritefalse在 omp 写入匹配的代码后对其进行格式化。
lsp.diagnosticsOnWritetrue在写入文件后返回诊断。
lsp.diagnosticsOnEditfalse在增量编辑后也返回诊断。
lsp.diagnosticsDeduplicatetrue抑制已经为某文件显示过、且没有变化的诊断。

如需在一次性会话中禁用所有由 LSP 支撑的行为，请这样启动：

omp --no-lsp

服务器配置参考

对内置服务器的部分覆盖可以省略继承来的字段。新服务器则需要下面列出的三个必填字段。

字段类型新服务器是否必填用途
commandstring是可执行文件名称或绝对路径。
fileTypesstring[]是该服务器处理的扩展名，包含前导点号。
rootMarkersstring[]是用于判定启动目录属于匹配项目的文件或目录；支持单层通配。
argsstring[]否传给服务器进程的命令行参数。
languageIdstring否为打开的文件发送的语言标识符；省略时由路径推断。
initOptionsobject否服务器特有的初始化选项。
settingsobject否服务器特有的工作区设置。
disabledboolean否为 true 时排除该服务器。
warmupTimeoutMsnumber否每个服务器的主动启动超时，单位毫秒。
isLinterboolean否标记该服务器仅用于诊断/格式化，不用于类型智能。
capabilitiesobject否启用受支持的可选集成：flycheck、ssr、expandMacro、runnables 和 relatedTests。这些目前用于 rust-analyzer。
workspaceReadyTimingsobject否进阶的 rust-analyzer 时间参数覆盖：timeoutMs、pollMs、settleMs 和 statusRequestTimeoutMs。

故障排查

欢迎面板或 /session 中没有出现任何服务器

  • 从包含预期根标记的目录启动 omp；发现过程不会搜索父目录。
  • 确认该二进制已安装在 omp 能解析到的位置。例如运行 command -v rust-analyzer，或检查项目的本地 bin 目录。
  • 检查自定义服务器的 command、fileTypes 和 rootMarkers 字段是否非空。
  • 检查配置文件名与语法。无法读取或非法的 JSON/YAML 会被忽略，以便其他来源继续加载。
  • 如果安装了多个 Python 或 JavaScript 服务器，请禁用不需要的那些，使服务器选择没有歧义。

服务器显示 available，但什么都没启动

在 lsp.lazy: true 时这是正常的。对匹配的文件请求定义、引用、重命名或诊断。如果你希望在交互式会话打开时就在后台启动，请设置 lsp.lazy: false。

启动失败或诊断始终为空

让 omp 报告它选用了哪个服务器、重新加载它，并显示启动错误。在 omp 之外验证所配置的命令和参数。同时确认文件扩展名在 fileTypes 中，且该文件属于服务器根标记所描述的项目。

标记为 isLinter 的服务器可以提供格式化、诊断和修复，但不提供定义、引用或语义重命名。编译器和测试输出也可能捕获 LSP 不会报告的工作区或构建系统错误。

重命名被拒绝或漏掉了某些文本

内置定义、外部声明、生成的文件以及仅以字符串形式出现的属性名可能无法重命名。先让 omp 显示引用，然后对非语义出现位置使用针对性编辑或结构化编辑。跨项目重命名之后，务必审阅 diff 并运行相关的编译器或测试。
