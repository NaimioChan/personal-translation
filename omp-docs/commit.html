创建提交

预览一次 Conventional Commit，让 omp 把互不相关的已暂存改动拆成有序的原子提交，并在钩子、模型或推送失败时安全恢复。

何时使用 omp commit

当改动已经就绪，但划分提交边界、写出有用的 Conventional Commit 信息比最后的 Git 命令更费心时，就使用 omp commit。默认工作流会把相关的改动放在一起，把无关的文件或 hunk 拆成原子提交，为有依赖关系的提交排序，并更新附近的变更日志。

你需要：

  • 一个包含你打算提交的改动的 Git 仓库；
  • 已配置的 Git 作者名与邮箱；
  • omp 中一个已通过认证且可用的模型；以及
  • 仓库中所有提交钩子都处于可用状态。

使用 --push 时，当前分支还必须有一个可用的上游分支，除非你的 Git 配置能提供。

先预览

把你希望 omp 考虑的确切范围暂存起来，检查一遍，然后跑一次试运行：

git add src/widget.ts test/widget.test.ts
git status --short
omp commit --dry-run

预览会打印一条生成的提交信息，或一份带编号的拆分计划，其中包含每个提交的信息以及被选中的文件或 hunk。它不会创建提交、不会推送，也不会写入变更日志改动。

--dry-run 仍可能改动 Git 索引：如果索引为空，omp commit 会在分析前执行等同于 git add -A 的操作。想要最安全的预览，先自己暂存打算提交的文件。如果你是从空索引开始的，事后用 git status --short 查看。

最短的成功流程

检查完预览后，创建提交：

omp commit

若只想在每个提交都成功后再推送：

omp commit --push

单提交方案会直接提交，不再额外确认。交互式拆分方案会在改动 Git 历史之前要求你确认完整计划。除 y 或 yes 之外的任何回答都会中止拆分。在非交互式 shell 中，有效的拆分计划无需该提示就会继续。试运行从不要求确认。

--push 不会增加额外确认。如果没有改动，omp commit --push 仍会尝试推送已有的本地提交；而单纯的 omp commit 会报告没有可提交的内容。

会考虑哪些改动

索引界定了边界：

  • 如果已有内容被暂存，omp 只考虑已暂存的改动。未暂存和未跟踪的内容不进入该流程。
  • 如果没有任何暂存内容，omp 会像 git add -A 那样，暂存所有已跟踪的修改与删除，以及未被忽略的未跟踪文件。
  • 被 Git 忽略的文件仍被排除。
  • 可识别的依赖锁文件会被排除在语义分析之外，以免生成的内容造成错误的提交边界。它们仍会被提交：拆分计划会尽可能把锁文件附到包含其对应清单文件的提交上，否则附到最后一个提交。

默认工作流可以在文件或 hunk 边界上切分改动。每个已暂存的改动在拆分计划中必须恰好出现一次，一个文件不能被分配到多个提交。依赖关系决定提交顺序；无效依赖和循环会在创建任何提交之前被拒绝。这意味着包含多个互不相关任务的工作区可能变成若干个有序提交，而不是一个大而全的提交。

如果这不是你想要的结果，就暂存更窄的范围再预览一次：

git reset
git add src/widget.ts test/widget.test.ts
omp commit --dry-run

这里的 git reset 只会取消暂存，不会丢弃工作区中的改动。

提交信息与校验

生成的标题采用 Conventional Commit 形式：

fix(parser): handled empty token streams。

支持的类型有 feat、fix、refactor、perf、docs、test、build、ci、chore、style 和 revert。可选的作用域会被校验，摘要会被规范化以去掉重复的类型前缀，必须控制在 72 个字符以内，并且必须以过去式动词开头。针对具体类型的检查会拒绝明显不匹配的情况，例如没有文档文件的 docs，或没有测试文件的 test。提交信息正文（如果存在）是重要细节的简短项目符号列表。无效方案不会被执行。

诸如措辞含糊、细节列表过长，或对 perf 类型证据不足之类的警告会在提交前显示；它们本身不会阻止一个有效方案。

变更日志

除非设置了 --no-changelog，否则 omp 会从每个被改动的文件向上查找最近的 CHANGELOG.md，直到仓库根目录为止。已在暂存集合中的变更日志文件不会再触发一次目标搜索。对每个检测到的、可解析的变更日志，omp 会提议用户可见的条目并把它们合并到未发布小节，避免重复条目，然后把更新后的文件加入暂存。

在拆分流程中，生成的变更日志文件会被放入最后一个提交。变更日志的更新在交互式拆分确认之前就已应用，因此拒绝该确认可能留下一个已修改并已暂存的变更日志，尽管并未创建任何提交。用 git status --short 检查，并按需要保留、取消暂存或还原该文件。

预览会执行变更日志分析，但不会写入文件。如果仓库不使用这种格式，或你想自己编辑发布说明，就跳过所有自动的变更日志检测与更新：

omp commit --dry-run --no-changelog
omp commit --no-changelog

上下文、模型与旧版工作流

用 --context（或 -c）补充 diff 无法体现的简明信息：

omp commit --dry-run --context "This fixes #418 and preserves the old wire format"

用 --model（或 -m）为本次运行选择主模型：

omp commit --model anthropic/claude-opus-4-5

不指定 --model 时，omp 会先解析已配置的 commit 模型角色，再走其常规的角色回退。当前默认工作流在其提交代理上使用已配置的 smol 角色（该角色可用时），并以选定的主模型作为回退。模型选择器可以使用 omp 其他地方同样支持的提供商、模型和思考强度语法。

默认就是上面描述的当前代理式工作流：它能查看单个文件和 hunk，产出一次提交或一份经过校验、按依赖排序的拆分，并在代理失败时回退为机械的单次提交。只有当你确实需要更早的确定性编排时，才使用 --legacy：

omp commit --dry-run --legacy
omp commit --legacy

旧版工作流只创建一次由模型生成的提交，没有原子拆分审阅，也没有在模型生成失败时的机械回退。它仍遵循相同的已暂存改动、变更日志、钩子、试运行和推送规则。

失败与安全恢复

每个生成的提交都会正常运行 Git 钩子。拒绝执行的 pre-commit 或 commit-msg 钩子会打印该钩子自己的消息，并让 omp commit 以非零状态退出。请修复所报告的问题，而不是绕过钩子，然后在重试前检查仓库：

git status --short
git log -5 --oneline

若单个提交失败，原本要提交的改动仍然存在，通常也仍在暂存区。若拆分过程中失败，失败之前已完成的提交会留在历史中；当前失败的那一组仍处于暂存状态，后续各组仍留在工作区。omp 会报告已创建多少个提交，并确认没有改动丢失。不要盲目重跑最初的完整流程。修好钩子或文件，提交或取消暂存当前这组，然后再预览剩余工作：

git status --short
omp commit --dry-run
omp commit

如果大型或二进制的已暂存 diff 无法安全切分，omp 会在创建拆分提交之前中止，并建议把大文件单独提交。缩小索引范围，先提交该文件，然后暂存并预览其余部分。

默认工作流中的模型或代理失败可能创建一个机械的单次回退提交，同时仍以非零状态退出。因此，非零退出并不总是意味着没有创建提交。检查 git log 和 git status，查看回退提交的信息与内容；如果它不合适，就用你惯常的非破坏性 Git 恢复流程修正或撤销它。旧版工作流则相反：模型生成失败时以非零状态退出，且不会创建回退提交。

只有在所有请求的提交都创建完成之后才会推送。如果远端拒绝了推送，或不存在上游分支，本地提交会保持完好，omp 以非零状态退出。修复上游分支或远端状态，然后直接推送：

git push --set-upstream origin HEAD

或者，一旦分支有了可用的上游，就让干净工作区的路径重试推送已有提交：

omp commit --push

在拒绝拆分、钩子失败、发生回退或推送失败之后，再次运行 omp commit 前，务必以 git status 和 git log 为准。避免使用 git reset --hard：这些失败路径都不需要丢弃工作区改动。

选项

选项效果
--dry-run生成提交信息或拆分计划，但不提交、不写入变更日志、不推送。索引为空时可能会暂存所有改动。
--push在提交成功创建后推送；如果没有新内容可提交，则推送已有提交。
--no-changelog禁用变更日志的检测与更新。
--context <text>, -c <text>为本次运行补充意图，用于提交信息、拆分和变更日志的决策。
--model <selector>, -m <selector>覆盖本次运行的主模型选择。
--legacy使用更早的单提交确定性流水线。
--help, -h显示当前命令帮助。
