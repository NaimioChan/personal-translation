RPC 模式

把 omp 作为长期运行的子进程启动，通过 stdin 和 stdout 上按行分隔的 JSON 来控制它。

当你掌控宿主进程时选择 RPC

RPC 模式是嵌入 omp 的通用底线方案。你的程序启动 omp，在 stdin 上每行发送一个 JSON 对象，并在 stdout 上以 JSON 行接收响应和流式事件。任何支持子进程和 JSON 的语言都能用。

途径选择它的时机…
交互式 omp有人在终端中工作，需要 omp 的编辑器、对话框和工具视图。
一次性 text 或 json 模式shell 或 CI 任务只需要一个提示词，然后退出。json 是事件流，但不接受 RPC 命令。
SDK你的 TypeScript 应用可以在进程内运行 omp，并希望获得类型化、直接的 API，而不是进程边界。
ACP你正在构建一个已经支持标准化 Agent Client Protocol 的编辑器或客户端。
RPC你需要长期运行的 omp 会话、流式输出、取消、状态控制或宿主回调，并且要用任意语言实现。

先以无头 RPC 和临时会话开始：

omp --mode rpc --no-session

省略 --no-session 即可把对话保存到 omp 的常规会话存储中。常规的模型、提供商、工作目录和配置选项同样适用；参见 命令行参考。RPC 会拒绝 @file 命令行参数——请改为在提示词中给出文件引用。

--mode rpc-ui 使用同一套线路协议，但会把嵌入的会话标记为支持 UI，并把依赖 UI 的工具与扩展界面接入 RPC UI 网桥。它不会启动 TUI，也不会添加单独的“工具卡片”帧类型。仅当你的宿主实现了这些 UI 行为时才使用它。两种模式都可以发出 extension_ui_request 帧，用于扩展对话框或登录等功能，因此完整的宿主应当理解该子协议。

完成一次提示词

在轮次结束前保持 stdin 打开。持续读取 stdout，把 stderr 单独保留，并在每条命令的末尾换行之后立即刷新。

这是一个最小的有效交互。显示的每一行都是一个完整的 JSON 对象；其他事件（例如 available_commands_update）可能在 ready 之后穿插出现。

{"type":"ready","protocolVersion":1,"supportedProtocolVersions":[1,2],"maxFrameBytes":1048576,"maxReassembledFrameBytes":67108864}
{"id":"p1","type":"prompt","message":"Reply with only the word ok"}
{"id":"p1","type":"response","command":"prompt","success":true}

第一行是 omp 输出的 stdout，第二行来自宿主的 stdin，第三行是 stdout 上可能出现的确认。这个确认表示“已接受”，而不是“已完成”。随后该轮次会流式发出事件，并以一个 agent_end 结束，其 isTerminal 不为 false。

下面是一个只使用 Python 标准库的完整客户端。它有意停留在协议 v1，因为它的提示词只会产生很小的响应；生产客户端应当按下文所述协商 v2。

import json
import subprocess

proc = subprocess.Popen(
    ["omp", "--mode", "rpc", "--no-session"],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    text=True,
    bufsize=1,
)

assert proc.stdin is not None
assert proc.stdout is not None

ready = json.loads(proc.stdout.readline())
if ready.get("type") != "ready":
    raise RuntimeError(f"expected ready, got {ready!r}")

request_id = "p1"
proc.stdin.write(json.dumps({
    "id": request_id,
    "type": "prompt",
    "message": "Reply with only the word ok",
}) + "\n")
proc.stdin.flush()

accepted = False
finished = False
text_parts = []

for line in proc.stdout:
    frame = json.loads(line)

    if frame.get("type") == "response" and frame.get("id") == request_id:
        if not frame.get("success"):
            raise RuntimeError(frame.get("error", "RPC command failed"))
        if frame.get("command") == "prompt":
            accepted = True
            if frame.get("data", {}).get("agentInvoked") is False:
                finished = True

    if frame.get("type") == "message_update":
        event = frame.get("assistantMessageEvent", {})
        if event.get("type") == "text_delta":
            text_parts.append(event["delta"])

    if (frame.get("type") == "prompt_result"
            and frame.get("id") == request_id
            and frame.get("agentInvoked") is False):
        finished = True

    if (frame.get("type") == "agent_end"
            and frame.get("isTerminal") is not False):
        finished = True

    if accepted and finished:
        break

proc.stdin.close()
if proc.wait() != 0:
    raise RuntimeError(f"omp exited with {proc.returncode}")

print("".join(text_parts))

不要假定响应一定在事件之前到达：某些提示词路径可能先开始发出事件。请按 id 匹配命令响应，并独立跟踪提示词的完成情况。

生命周期、队列与取消

进程生命周期

  1. 启动 omp --mode rpc，并为它分配独立的 stdin、stdout 和 stderr 流。
  2. 等待 ready 之后再发送命令。
  3. 持续读取 stdout。在命令尚未完成时，可能会有宿主回调或 UI 请求到达。
  4. 把命令作为紧凑、不分块的 JSON 对象发送，其后跟一个 \n。
  5. 关闭 stdin 即可断开。omp 会拒绝未完成的 UI、工具和 URI 回调，处理完已接受的命令，释放会话，并以退出码 0 退出。

stdout 专属于 JSON 协议通道。日志和诊断信息属于 stderr；绝不要把 stderr 混入 JSON 解析器。

提示词完成

prompt 和 abort_and_prompt 会立即确认已排入调度。一次正常的代理运行只有在以下情况下才算完成：

frame.type == "agent_end" and frame.isTerminal != false

isTerminal: false 表示异步投递或维护会恢复该会话。字段缺省即与终止语义兼容。

提示词也可能被本地处理——例如由斜杠命令处理——此时不会发出 agent_end。可用以下任一方式检测：

  • response.data.agentInvoked === false，或者
  • 之后出现的 { "type": "prompt_result", "id": …, "agentInvoked": false }。

本地命令也可以发出 command_output。agentInvoked: true 表示完成情况将由代理生命周期事件标识。如果该字段缺省，请继续观察事件和 prompt_result。

在轮次进行中提交工作

  • steer 会把一条用户消息插入当前运行。
  • follow_up 会把消息排入当前运行之后的队列。
  • 在流式过程中发送第二个 prompt 时必须包含 streamingBehavior: "steer" 或 "followUp"（驼峰式写法为 followUp）。
  • 引导队列与后续队列默认使用 "one-at-a-time"；它们的 set_*_mode 命令可以切换到 "all"。
  • 中断模式默认使用 "immediate"。"wait" 会把引导推迟到轮次结束后。

bash 是常规命令串行化的例外：它并发运行，因此 abort_bash 可以越过它。它的响应在命令结束时到达，相对其他响应可能乱序。必须按 id 进行关联。

安全取消

  • 发送 abort 可停止当前的代理运行。请同时等待 abort 响应，以及该次运行的终止性 agent_end。
  • 发送 abort_and_prompt 可中止并调度一个替代提示词。它不提供 data.agentInvoked 或 prompt_result；请依赖生命周期事件或同 id 的调度错误。
  • 发送 abort_retry 可停止自动重试的延迟。
  • 发送 abort_bash 可停止当前由 RPC 启动的 shell 命令。
  • 把 host_tool_cancel、host_uri_cancel 以及 UI 的 method: "cancel" 都视为对被引用宿主机侧操作的取消。

错误与恢复

命令失败是普通的响应帧，通常不会让进程不可用：

{"id":"m1","type":"response","command":"set_model","success":false,"error":"Model not found: provider/model"}

所有失败都带有 type: "response"、success: false、一个字符串类型的 command，以及一个人类可读的 error。code 是可选的；get_messages_page 目前使用 session_busy 和 stale_cursor。

重要的边界情况：

  • 格式错误的 JSON 会产生可恢复的失败，带 command: "parse"，且没有 id；下一行有效内容仍会被处理。
  • 未知命令目前不返回关联 id。在本地校验其 type 之前，不要再发送其他命令。
  • 已排入调度的 prompt 或 abort_and_prompt 可能先确认成功，若异步调度失败，随后又会以同一 id 发出失败响应。
  • 扩展运行时失败是一个 extension_error 事件，而不是命令响应。
  • 忽略 extension_ui_request、host_tool_call 或 host_uri_request 的宿主可能让发起该操作的一方死锁。请在处理其他待办命令时也分发这些帧。
  • EOF 是有意断开连接。意外的进程退出或 stdout 中断属于传输故障；任何未解决的请求其完成状态都是未知的。

传输版本与大帧

启动时协议 v1 生效。它每个物理行发出一个 JSON 对象，并把该行（含换行符）限制在公布的 maxFrameBytes（当前为 1 MiB）以内。入站帧始终是单个、不分块的 JSONL 对象，应保持在该上限以下。

能够重组大输出的客户端应在 ready 之后立即协商 v2：

{"id":"protocol-1","type":"negotiate_protocol","protocolVersion":2}
{"id":"protocol-1","type":"response","command":"negotiate_protocol","success":true,"data":{"protocolVersion":2}}

成功响应本身仍是 v1。之后超大的逻辑 stdout 对象会变成一段不中断的 rpc_chunk 帧序列：

{"type":"rpc_chunk","chunkId":"rpc-1","index":0,"count":2,"byteLength":1200000,"data":"BASE64_DATA"}

对每个序列，请校验：

  • chunkId 保持不变且非空；
  • index 从 0 开始，并且无间隔递增；
  • count、byteLength，以及 chunkId 在每个分块上都一致；
  • 没有普通帧打断该序列；
  • 解码后的字节数不超过 maxReassembledFrameBytes（当前为 64 MiB）；
  • 拼接后的字节数等于 byteLength，按严格 UTF-8 解码，并能解析为一个 JSON 对象。

data 是标准 base64。不要把单个分块当作应用事件分发。超过 v2 上限的逻辑帧会改为显式的溢出帧。

在 v1 中，超大响应会以 RPC response exceeded the transport limit 失败；其他帧可能被压缩，或被替换为 rpc_frame_error。超大的 agent_end 可以省略那些已经通过 message_end 投递过的消息，并添加 messageCount。绝不要只把 agent_end.messages 当作对话记录存储：请收集消息事件，或用 get_messages_page 分页取历史。

扩展 UI 子协议

所有请求都带有 type: "extension_ui_request" 和一个 id。只有 select、confirm、input 以及 editor 期望返回值响应。即发即忘的展示类方法无需响应。

method请求字段

在 stdin 上以相同的 id 回复：

Text/select/editor: { type: "extension_ui_response", id, value: string }
Confirmation:       { type: "extension_ui_response", id, confirmed: boolean }
Cancel/timeout:      { type: "extension_ui_response", id, cancelled: true, timedOut?: boolean }

未知的响应 id 会被忽略。当请求带有 timeout 时，宿主应执行该超时，并返回带 timedOut: true 的取消形式。

OAuth 的 login 会发出 open_url，可能发出通知帧，然后可以用 input 请求粘贴重定向地址或授权码。在产生 URL 之前就要求交互输入的提供商在 RPC 模式下会被拒绝；请改用交互式 omp 登录。

宿主工具与宿主 URI

在 set_host_tools 之后，omp 可以请求你的进程执行某个已注册的工具：

{"type":"host_tool_call","id":"host-1","toolCallId":"toolu-1","toolName":"lookup_ticket","arguments":{"id":42}}

你可以流式发送零个或多个更新，然后必须用同一个 id 完成：

{"type":"host_tool_update","id":"host-1","partialResult":{"content":[{"type":"text","text":"looking up ticket"}]}}
{"type":"host_tool_result","id":"host-1","result":{"content":[{"type":"text","text":"ticket 42 is open"}]}}

partialResult 和 result 都是 { content: Array<TextContent | ImageContent>, details?: any, isError?: boolean, providerMetadata?: object, useless?: boolean }。把顶层的 isError: true 设为 host_tool_result 上的顶层字段，以拒绝挂起的调用，并把返回内容作为工具错误暴露。host_tool_cancel 是 { type, id, targetId }；停止由 targetId 标识的操作。

在 set_host_uri_schemes 之后，omp 会把对这些 scheme 的读取和允许的写入路由到你的进程：

Read:  { type: "host_uri_request", id, operation: "read", url }
Write: { type: "host_uri_request", id, operation: "write", url, content }
Cancel:{ type: "host_uri_cancel", id, targetId }

用以下内容回复：

Success read:  { type: "host_uri_result", id, content, contentType?, notes?, immutable? }
Success write: { type: "host_uri_result", id }
Failure:       { type: "host_uri_result", id, isError: true, error?: string, content?: string }

contentType 是 "text/markdown"、"application/json"，或 "text/plain"，默认是纯文本。成功的读取需要 content。结果级的 immutable 会覆盖该次读取所注册的 scheme。edit 工具不会编辑宿主 URI；把该 scheme 注册为可写，才能让整段替换式写入走 write 路径。

子代理帧

转发默认使用 off：

  • progress 会发出 subagent_lifecycle 和 subagent_progress。
  • events 还会发出每一个嵌套的 subagent_event。

subagent_lifecycle.payload 是 { id, agent, agentSource, description?, status: "started" | "completed" | "failed" | "aborted", sessionFile?, parentToolCallId?, index, detached? }。

subagent_progress.payload 是 { index, agent, agentSource, task, parentToolCallId?, assignment?, progress, sessionFile?, detached? }。progress 包含身份/状态、最近的工具与输出摘要、计数、token、成本、时长、模型选择以及可选的重试状态。请把新增的进度指标视为可选。

subagent_event.payload 是 { id, event: AgentSessionEvent }，其中 event 使用与上文相同的生命周期架构。

RpcSubagentSnapshot 由 get_subagents 返回，其值为 { id, index, agent, agentSource, description?, status, task?, assignment?, sessionFile?, lastUpdate, progress?, parentToolCallId? }。

RpcSubagentMessagesResult 是 { sessionFile, fromByte, nextByte, reset, entries, messages }。按 subagentId 或 sessionFile 选择；fromByte 可启用增量读取。如果对话记录缩短到 fromByte 以下，服务器会从字节零重新开始，并设置 reset: true。

宿主实现清单

一个健壮的、与语言无关的客户端应当：

  1. 为每个独立控制的会话启动一个进程，并等待 ready。
  2. 保持 stdin 写入串行、以换行结尾并刷新。
  3. 在有请求待处理时持续读取 stdout；绝不要在服务回调之前等待某个响应。
  4. 生成唯一的字符串 id，并按 id 而不是到达顺序关联响应。
  5. 把提示词的接受状态与终止性完成或仅本地完成区分开跟踪。
  6. 在可能出现大消息时协商 v2 并严格重组分块。
  7. 分发扩展 UI、宿主工具和宿主 URI 请求时不要阻塞读取器。
  8. 为向前兼容，保留未知字段、消息角色、内容块和事件类型。
  9. 有序关闭时先关闭 stdin，再等待进程退出。
