自定义模型与提供商

把 omp 连接到本地服务器、兼容 OpenAI 的网关，或内置目录中不存在的模型。

连接 omp 尚不认识的模型

当你的模型运行在私有 URL、公司网关之后，或使用 omp 未列出的 id 时，请使用自定义提供商。你可以自行声明确切的模型，也可以让 omp 发现服务器暴露的模型。

对于本地推理，你通常不需要这个文件。omp 会自动查找 http://127.0.0.1:11434 上的 Ollama、http://127.0.0.1:8080 上的 llama.cpp，以及 http://127.0.0.1:1234/v1 上的 LM Studio。启动服务器并打开 /model；如果它的模型已经在那里，选一个即可，无需再做别的。

否则，创建 ~/.omp/agent/models.yml。对于一个实现了 OpenAI Chat Completions 的免认证服务器，这是最小的有效配置：

providers:
  local-openai:
    baseUrl: http://127.0.0.1:8000/v1
    api: openai-completions
    auth: none
    models:
      - id: Qwen/Qwen2.5-Coder-32B-Instruct

提供商 id local-openai 由你自选。模型的 id 必须是服务器接受的确切 id。如果服务器实现的是 /v1/responses 而不是 /v1/chat/completions，请改用 openai-responses。

对于新声明的模型，省略的元数据默认采用：以 id 作为显示名称、仅文本输入、无可配置的推理、128,000 token 的上下文窗口、16,384 token 的输出上限，以及零成本。这些默认值使最小条目可用，但当实际情况不同时，你应当设置真实的限制和能力。

验证并选择它

先让 omp 加载该文件并只列出你的提供商：

omp models local-openai

有效且可用的模型会出现在 local-openai 之下，并显示其上下文、输出、思考和图像能力。若出现 YAML 或 schema 问题，则会打印 models.yml validation failed 以及出错的字段。

然后使用精确的选择器测试该端点：

omp -p --model local-openai/Qwen/Qwen2.5-Coder-32B-Instruct "Reply with only OK"

当多个提供商暴露相同的模型 id 时，精确的 provider/model-id 选择器可以避免歧义。要把它设为常规交互模型，请启动 omp，输入 /model，找到该提供商和模型，并将其分配给 Default。模型中心在打开时会重新加载 models.yml，并保存角色分配。/switch（或 Alt+P）只切换当前会话。

参见模型角色，了解如何把同一模型分配给 smol、slow、plan 或其他角色。

添加认证

对于远程的兼容 OpenAI 服务，把 apiKey 指向一个环境变量：

providers:
  myco:
    baseUrl: https://llm.internal.example/v1
    apiKey: MYCO_LLM_API_KEY
    api: openai-responses
    models:
      - id: myco-large
        name: MyCo Large
        reasoning: true
        input: [text, image]
        contextWindow: 200000
        maxTokens: 32000
        cost:
          input: 3
          output: 15
          cacheRead: 0.3
          cacheWrite: 3.75

export MYCO_LLM_API_KEY='…'
omp models myco

apiKey 的解析过程是刻意设计的，但值得了解：

  1. 以 ! 开头的值是一条 shell 命令；其去掉首尾空白的 stdout 即为密钥。
  2. 否则，omp 会查找同名环境变量。
  3. 如果该变量不存在，omp 会把配置的文本当作字面密钥使用。

例如，apiKey: "!op read op://team/llm/key" 从 1Password 读取。请求头的值遵循相同规则。请优先使用环境变量或密钥管理器命令，而不是提交字面凭据。内置提供商认证参见环境变量和模型提供商。

auth 默认为 apiKey。仅对真正免认证的端点使用 auth: none。auth: oauth 只有在 omp 或扩展已经提供该提供商的 OAuth 支持时才有效；models.yml 无法定义新的 OAuth 流程。

仅当网关明确需要把 Authorization: Bearer <resolved-apiKey> 作为普通请求头注入时，才设置 authHeader: true。标准提供商客户端已经应用其常规认证方案。

发现服务器的模型列表

如果兼容 OpenAI 的服务器暴露了 GET /v1/models，发现机制可以免去手工维护 models 列表：

providers:
  lab:
    baseUrl: http://127.0.0.1:8000/v1
    api: openai-completions
    auth: none
    discovery:
      type: openai-models-list

运行 omp models refresh lab 可强制在线刷新并只显示匹配的模型。普通启动在缓存目录仍然新鲜时会使用缓存。

discovery.type 接受：

类型用于
ollamaOllama 原生的 /api/tags 和 /api/show 端点。
llama.cppllama.cpp 原生的模型和属性端点。
lm-studioLM Studio 兼容 OpenAI 的模型列表和元数据。
openai-models-list通用的兼容 OpenAI 的 GET /v1/models 端点。
litellmLiteLLM 网关；使用其更丰富的元数据路由，并回退到 /v1/models。
proxy混合的 OpenAI/Anthropic 代理，其模型行会声明 supported_endpoint_types。

除 proxy 外，发现机制都要求提供商级别的 api。proxy 会从模型声明的端点类型推导其 API，仅把提供商级别的 api 作为回退。可选的 discovery.timeoutMs 必须是正数毫秒值。

不要把一个通用的兼容 OpenAI 服务器标记为 ollama：Ollama 发现机制期望的是 Ollama 的原生端点。请改用 openai-models-list。

覆盖内置提供商

不带 models 的提供商条目会修改已有的提供商，而不是替换其目录。这对于公司网关或修正元数据很有用：

providers:
  openai:
    baseUrl: https://gateway.internal.example/v1
    apiKey: COMPANY_OPENAI_KEY
    headers:
      X-Team: coding
    modelOverrides:
      gpt-5.4:
        contextWindow: 400000

提供商的 headers、compat 和 remoteCompaction 是基线。模型请求头会替换同名的提供商请求头，而 modelOverrides 会修补某一个内置或已发现的模型。如果自定义 models 条目使用了与现有模型相同的提供商和 id，则自定义定义会替换该模型的传输配置。

文件与提供商参考

默认路径是 ~/.omp/agent/models.yml；当 .yml 文件不存在时使用 ~/.omp/agent/models.yaml。如果两个 YAML 文件都不存在，而旧版的 models.json 存在，omp 会把它迁移为 models.yml。根对象只接受 providers。

providers 下的每个键都会成为选择器的提供商部分。

提供商字段含义
baseUrl端点根地址。当 models 非空时为必填。必须是非空字符串。
api声明或发现的模型的默认 API。也可以改为在每个已声明模型上设置。
apiKey环境变量名、!command 或字面凭据。对已声明模型为必填，除非 auth 为 none 或 oauth。
authapiKey（默认）、none 或 oauth。
headers字符串到字符串的请求头。值支持环境变量和 !command 解析。
authHeader为 true 时，从 apiKey 添加 Bearer Authorization 请求头。
models此提供商拥有的完整模型定义。
discovery实时目录配置：type 加上可选的正式 timeoutMs。
modelOverrides从模型 id 到稀疏元数据补丁的映射。
compat高级请求/响应兼容性覆盖；通常省略它，改用 omp 的自动检测。
disableStrictTools为会拒绝严格工具 schema 标记的端点（常见于兼容 Anthropic 的代理）禁用这些标记。
remoteCompaction提供商级别的远程压缩配置。模型上的值会合并在其上。
guardrailIdentifierAmazon Bedrock 护栏 id 或 ARN。
guardrailVersionBedrock 护栏版本；设置护栏时默认为 DRAFT。
guardrailTraceBedrock 跟踪模式：enabled、disabled 或 enabled_full。
transport仅 pi-native；经由兼容的 omp auth-gateway 路由。要求该网关作为 baseUrl，其 bearer 作为 apiKey。

没有模型的提供商仍然必须做点事情：至少设置一个可用的覆盖项，例如 baseUrl、headers、apiKey、auth: none、compat、disableStrictTools、guardrailIdentifier、remoteCompaction、modelOverrides 或 discovery。

API 取值

api 取值端点族
openai-completions兼容 OpenAI 的 Chat Completions。
openai-responses兼容 OpenAI 的 Responses API。
openai-codex-responsesCodex 风格变体的 Responses API。
azure-openai-responses托管在 Azure 上的 Responses API。
anthropic-messagesAnthropic Messages API。
bedrock-converse-streamAmazon Bedrock Converse 流式。
google-generative-aiGemini 公共 API。
google-gemini-cli兼容 Gemini CLI 的 API。
google-vertex经由 Vertex AI 的 Gemini。

这些是内置于 omp 的传输方式。线协议不同的端点需要扩展，而不是在 models.yml 中换一个字符串。

模型字段参考

模型字段含义
id必填，非空的上游模型 id。
name选择器标签；默认为 id。
api为此模型覆盖提供商的 api。
baseUrl为此模型覆盖提供商的 baseUrl。
reasoning将该模型标记为具备推理能力。必须为 true，thinking 控制界面才会应用。
thinking显式的思考强度控制；见下文。省略它则让已知的模型身份和兼容性决定控制项。
input支持的输入：[text] 或 [text, image]。
imageInputDecoder仅 stb；为无法自行解码 WebP 的本地后端转换 WebP 输入。
tokenizer可选的本地 token 估算器：claude-v3、claude-v47、claude-v5、claude-v5-sonnet、qwen3、deepseek-v3、kimi-k2 或 glm5。
supportsTools端点是否支持工具调用。
cost每百万 token 的费率。完整定义需要 input、output、cacheRead 和 cacheWrite。
premiumMultiplier应用于所报告模型成本的乘数。
contextWindow上下文计量和溢出处理所用的正数总上下文 token 上限。
maxTokens正数最大输出 token 数。
omitMaxOutputTokens为 true 时省略请求中的最大输出 token 字段。
headers按模型的请求头，合并在提供商请求头之上。值支持环境变量名和 !command。
compat按模型的兼容性覆盖，合并在提供商 compat 之上。
contextPromotionTarget在压缩之前、发生上下文溢出错误后要切换到的模型 id 或 provider/model-id。
compactionModel压缩时优先使用的模型选择器。
remoteCompaction按模型的远程压缩设置。

modelOverrides 接受除 id、api 和 baseUrl 之外的相同元数据字段。它的 cost 对象可以是部分的，而完整模型定义的 cost 必须包含全部四项费率。

思考字段

新的显式 thinking 块使用这种形状：

reasoning: true
thinking:
  mode: effort
  efforts: [low, medium, high]
  defaultLevel: medium
字段含义
mode必填：effort、budget、google-level、anthropic-adaptive 或 anthropic-budget-effort。
efforts新配置必填：minimal、low、medium、high、xhigh、max 的一个有序非空子集。
defaultLevel从受支持的强度集合中选取的默认值。
effortMap从这些强度名称到提供商专用字符串的可选映射。
supportsDisplay提供商是否接受思考显示偏好。

旧版的 levels，或 minLevel 与 maxLevel 这一对字段，仍会被接受并规范化为 efforts；新文件请优先使用 efforts。

远程压缩字段

remoteCompaction 可以出现在提供商、模型或覆盖层级。它接受 enabled、api、endpoint、model、v2StreamingEnabled、v2Endpoint 和 streamingEndpoint。端点和模型字符串必须非空。除非你的提供商提供兼容的服务端压缩端点，否则请省略这个块。

高级兼容性字段

大多数兼容 OpenAI 的服务无需 compat 即可工作。只有在要匹配有文档记录的端点行为，或解决具体的请求错误时，才设置这些字段。每个字段都是可选的；提供商的值构成基线，模型的值合并在其上。

请求与流式：supportsStore、supportsDeveloperRole、supportsMultipleSystemMessages、maxTokensField（max_completion_tokens 或 max_tokens）、supportsUsageInStreaming、supportsToolChoice、supportsForcedToolChoice、alwaysSendMaxTokens、strictResponsesPairing、streamIdleTimeoutMs、cacheControlFormat（anthropic）、supportsLongPromptCacheRetention、supportsImageDetailOriginal 和 extraBody。

推理：supportsReasoningEffort、supportsReasoningParams、reasoningEffortMap、thinkingFormat（openai、openrouter、zai、qwen 或 qwen-chat-template）、qwenTemplateReasoningEffort、reasoningContentField（reasoning_content、reasoning 或 reasoning_text）、requiresReasoningContentForToolCalls、allowsSyntheticReasoningContentForToolCalls、requiresAssistantContentForToolCalls、disableReasoningOnForcedToolChoice、disableReasoningOnToolChoice 和 whenThinking。whenThinking 包含另一个部分兼容性块，仅在思考活动时应用。

工具与消息历史：requiresToolResultName、requiresMistralToolIds、requiresAssistantAfterToolResult、requiresThinkingAsText、supportsStrictMode、toolStrictMode（all_strict 或 none）和 requiresToolResultId。

流式与兼容 Anthropic 的行为：streamMarkupHealingPattern（kimi、dsml、qwen 或 thinking）、supportsEagerToolInputStreaming、allowAnthropicHeaderOverrides 和 replayUnsignedThinking。

网关路由：openRouterRouting 和 vercelGatewayRouting，二者各带可选的 only 和 order 字符串列表。

Bedrock 提示词缓存：promptCacheMode（none、automatic 或 explicit）、promptCacheMinimumTokens、promptCacheMaximumCheckpoints 和 supportsLongPromptCacheRetention。

疑难排查

提供商没有出现

运行 omp models <provider-id>。一个无效的自定义条目会让该文件中的自定义提供商在本次运行中全部禁用，而内置提供商仍然可用。请先检查这些规则：

  • 带 models 的提供商需要 baseUrl。
  • 它需要 apiKey，除非 auth 为 none 或已受支持的 oauth。
  • 它需要提供商级别的 api，或在每个模型上都有 api。
  • id 必须非空；提供的 contextWindow 和 maxTokens 必须为正数。
  • 根键是 providers；modelRoles 和 modelProviderOrder 这类设置属于 config.yml，而不是 models.yml。

模型出现了，但请求返回 401 或 403

确认 apiKey 指定的环境变量已在启动 omp 的 shell 中导出。请记住，变量名缺失时会回退为字面 token，因此即使该变量不存在，apiKey: MYCO_LLM_API_KEY 仍可能加载成功。检查该服务期望的是其常规 SDK 认证头，还是显式的 Bearer 头；只有后者需要 authHeader: true。

请求返回 404 或“不支持的端点”

把 API 族和 URL 一起检查。openai-completions 需要 Chat Completions，而 openai-responses 需要 Responses。通用的兼容 OpenAI 的基地址通常以 /v1 结尾；llama.cpp 的发现机制接受其原生根地址，并自行规范化模型请求 URL。

发现机制没有返回任何模型

确认服务器正在运行，然后运行 omp models refresh <provider-id>。仅对原生 Ollama 端点使用 ollama，对通用的 /v1/models 服务使用 openai-models-list。如果服务器是远程的或响应较慢，请设置更大的正数 discovery.timeoutMs。

工具调用或推理以 400 失败

对于会拒绝严格工具 schema 的兼容 Anthropic 的代理，设置 disableStrictTools: true。对于兼容 OpenAI 的方言不匹配，只更改服务错误中提到的相关 compat 字段；大范围照搬的兼容性块可能会禁用端点实际支持的功能。

上下文或用量数字看起来不对

被发现端点并不总是报告可靠的元数据。请显式声明该模型，或添加一个 modelOverrides 条目，填入真实的 contextWindow、maxTokens、input、reasoning 和 cost 值。
