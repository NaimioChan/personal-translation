编写 MCP 服务器

构建一个基于标准的工具服务器，把它接到 omp 上，并端到端验证握手与工具调用。

构建一次，供众多客户端使用

MCP 服务器把某个 API、本地服务或工作流变成 omp 可以发现并使用的工具。当这个集成还需要与其他 MCP 客户端配合工作时，请选择 MCP。如果只是给 omp 用，自定义工具通常更轻。

最快的路径是本地 stdio 服务器。官方 SDK 会处理 JSON-RPC 分帧、版本协商和初始化序列，因此你的代码可以专注于工具 schema 与行为。

构建一个最小的 stdio 服务器

在你的项目里安装当前的 TypeScript 服务器 SDK 和 Zod：

npm install @modelcontextprotocol/server zod

把下面的内容保存为mcp/hello-server.mjs：

import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import * as z from "zod/v4";

const server = new McpServer({
  name: "hello",
  version: "1.0.0",
});

server.registerTool(
  "greet",
  {
    description: "Greet one person by name.",
    inputSchema: z.object({
      name: z.string().min(1).describe("The person's name"),
    }),
  },
  async ({ name }) => ({
    content: [{ type: "text", text: `Hello, ${name}!` }],
  }),
);

await server.connect(new StdioServerTransport());

不要在 stdio 服务器里把日志打到 stdout。stdout 承载的是按换行分隔的 MCP 消息；一行调试输出就可能破坏连接。请把诊断信息写到 stderr。

把它接到 omp 上

在.omp/mcp.json添加一份项目配置：

{
  "$schema": "https://raw.githubusercontent.com/can1357/oh-my-pi/main/packages/coding-agent/src/config/mcp-schema.json",
  "mcpServers": {
    "hello": {
      "type": "stdio",
      "command": "node",
      "args": ["./mcp/hello-server.mjs"]
    }
  }
}

在那个项目里启动 omp，然后运行：

/mcp reload
/mcp test hello

/mcp test hello会建立一次临时连接，完成初始化，调用tools/list，并报告服务器身份与发现的工具名。它不会调用任何工具。用一次正常请求来检验处理器：

用 hello 服务器向 Ada 问好。

你应该看到Hello, Ada!。除非服务器配置里设置了cwd，否则子进程在 omp 项目目录下启动，所以上面那些相对的args是从项目根目录解析的。

选择传输方式

传输方式适用于服务端契约omp 配置
stdio为单次 omp 会话启动的本地服务器从 stdin 读取 JSON-RPC，向 stdout 写出按换行分隔的 JSON-RPC，并让诊断信息远离 stdout省略type或使用"type": "stdio"；设置command，可选args、env和cwd
Streamable HTTP常驻守护进程或托管共享服务通过 HTTP POST 接受 MCP JSON-RPC；按 MCP 传输规范的要求支持 JSON 或 SSE 响应使用"type": "http"和url；headers与 OAuth 可选
旧版 HTTP+SSE已有的、为 2024-11-05 传输方式构建的服务器打开一条 SSE 流，其中公布 JSON-RPC POST 端点使用"type": "sse"和url；新服务器不要选这个

type缺省时默认是 stdio。因此一个没有"type": "http"的远程条目会被当作 stdio，并因为没有command而失败。

通过 Streamable HTTP 发布同一个工具

当前 SDK 可以同时服务当前客户端和 2025 年代的客户端。要做一个小的 Node 托管端点，请安装它的 Node 适配器：

npm install @modelcontextprotocol/node

一个最小的回环服务器看起来是这样：

import { createServer } from "node:http";
import {
  localhostHostValidation,
  localhostOriginValidation,
  toNodeHandler,
} from "@modelcontextprotocol/node";
import { createMcpHandler, McpServer } from "@modelcontextprotocol/server";
import * as z from "zod/v4";

const handler = createMcpHandler(() => {
  const server = new McpServer({ name: "hello-http", version: "1.0.0" });
  server.registerTool(
    "greet",
    {
      description: "Greet one person by name.",
      inputSchema: z.object({ name: z.string().min(1) }),
    },
    async ({ name }) => ({
      content: [{ type: "text", text: `Hello, ${name}!` }],
    }),
  );
  return server;
});

const nodeHandler = toNodeHandler(handler);
const validateHost = localhostHostValidation();
const validateOrigin = localhostOriginValidation();

createServer((request, response) => {
  if (!validateHost(request, response) || !validateOrigin(request, response)) return;
  void nodeHandler(request, response);
}).listen(3000, "127.0.0.1");

配置这个正在运行的端点：

{
  "mcpServers": {
    "hello-http": {
      "type": "http",
      "url": "http://127.0.0.1:3000/mcp"
    }
  }
}

面向公网部署时，请校验Host和Origin，在派发给 MCP 处理器之前完成认证，使用 TLS，并且只把已核实的身份传给工具代码。处理器不会替你认证请求。omp 的 header 与 OAuth 配置见 SDK 的HTTP 服务指南以及MCP。

公开协议契约

强烈建议使用 MCP SDK。如果你要自己实现线上协议，以下是 omp 依赖的互操作要点：

阶段服务器必须做什么
initialize接受 JSON-RPC 2.0 请求。omp 目前提供 MCP 协议修订版2025-11-25。用协商后的protocolVersion、serverInfo和capabilities回复。
notifications/initialized在期待后续会话流量之前先接受该通知。通知没有请求 ID，也不会收到响应。
tools/list当声明了capabilities.tools时，返回{ "tools": [...] }。如果结果里有nextCursor，omp 会一直跟进，直到加载完所有页。
tools/call接受{ "name": string, "arguments"?: object }并返回工具结果。每个 JSON-RPC 请求 ID 都要原样回显；有效的 ID 可以是数字或字符串。
服务器发起的请求omp 会应答ping和roots/list。roots/list把当前项目以file: URI 返回。除非客户端已经声明，否则不要假定它支持其他服务器到客户端的方法。
工具变更如果工具会变化，请声明tools.listChanged，并在初始化之后发送notifications/tools/list_changed。omp 随后会重新加载该服务器的工具列表，而无需重启会话。

对于 Streamable HTTP，如果你签发了Mcp-Session-Id就要保留它，并在初始化之后的请求上接受MCP-Protocol-Version: 2025-11-25。请支持公开 MCP 传输规范所定义的 HTTP 方法、状态码、媒体类型和可选的 SSE 通道。官方 SDK 会处理这些细节。

omp 默认发送数字形式的 JSON-RPC 请求 ID。服务器应当同时接受 JSON-RPC 允许的两种形式；只要求某一种会降低与其他客户端的兼容性。

定义便于跨客户端使用的工具

一个列出的工具需要有稳定的name、具体的description，以及顶层为 JSON Schema 对象的inputSchema。使用上面提到的 SDK 时，Zod 这样的 Standard Schema 库会替你生成该 schema。

好的 schema 能帮助客户端选择工具并构造有效参数：

  • 描述用户可见的动作以及何时适用。
  • 使用明确的属性描述、边界、枚举和required字段。
  • 让可选字段真正可选；不要要求客户端发送空占位值。
  • 在处理器里再次校验权限和输入。schema 是指导与校验，不是授权。
  • 一旦用户开始依赖这些名字，就保持它们稳定。

omp 会按服务器给发现的工具加命名空间，把名字转为小写，把[a-z_]之外的字符替换为下划线，并在需要时把挂载名截到 64 个字符并附上稳定哈希后缀。归一化后相同的不同原始名会发生冲突；omp 会保留一个确定性的胜出者。请优先使用简短、互不相同的小写名字，例如search_issues或create_invoice。用户是用自然语言提出这项能力，而不是敲出挂载名。

返回结果与错误

每次成功的调用都应返回content。文本是最通用的内容类型：

return {
  content: [{ type: "text", text: "Created invoice INV-1042." }],
};

omp 也接受 MCP 图片内容（data为 base64，外加mimeType）以及内嵌资源内容。如果你还返回structuredContent，请在content里也给出有用的文本表示；不要让人类可读的结果依赖于结构化输出的支持。

对于可预期的、用户可自行纠正的失败，使用isError: true。这样失败会附着在该工具调用上，并给模型提供可据以行动的信息：

return {
  content: [{ type: "text", text: "Customer C-17 does not exist." }],
  isError: true,
};

抛出异常或返回 JSON-RPC 错误响应，只留给协议违规、依赖不可用和意外的服务器故障。omp 会把可预期的isError结果显示为工具错误；传输层与 JSON-RPC 失败则表现为 MCP 错误。两种形式都不要包含密钥、token 或私有堆栈跟踪。

对于受保护的 HTTP 工具，可以随错误在_meta["mcp/www_authenticate"]中返回一个基于标准的授权质询。omp 能识别这个公开的 MCP 质询，并在服务器配置了 OAuth 时，于重试之前重新完成授权。

调试循环

  1. 独立测试服务器。对 stdio 示例，先运行node --check mcp/hello-server.mjs，然后使用官方检查器：

    npx @modelcontextprotocol/inspector node ./mcp/hello-server.mjs

    确认greet出现，并用{ "name": "Ada" }调用它。

  2. 重新加载发现。编辑.omp/mcp.json之后，运行/mcp reload，再用/mcp list确认服务器名和来源文件。

  3. 测试发现与 schema。运行/mcp test hello。它验证初始化和tools/list，但不验证处理器本身。

  4. 测试真实的用户路径。让 omp 执行该动作，然后检查返回的内容。对动态服务器，/mcp notifications有助于确认列表变更通知。

  5. 只重启发生变化的部分。改动本地服务器代码后用/mcp reconnect hello。改动发现或配置后用/mcp reload。

现象检查
ENOENT或找不到命令核实command、相对项目的路径、可执行权限和cwd。
测试挂起或超时确保服务器应答initialize，然后接受notifications/initialized和tools/list。默认请求超时是 30 秒；先解决卡住的问题，再考虑调大timeout。
JSON 无效或立即断开去掉所有 stdout 日志/横幅。检查每个 stdio 帧都是一个完整的 JSON-RPC 对象后跟一个换行。
测试能连上但真实调用失败/mcp test不调用工具。用 Inspector 复现，并对领域性失败返回可据以行动的isError结果。
工具变更没有出现重连重启后的 stdio 进程，或者声明tools.listChanged并发送notifications/tools/list_changed。
HTTP 401 或 403核实服务端的 token 校验以及客户端的 header/OAuth 配置；托管的 OAuth 可用/mcp reauth <name>。
服务器列出了工具，但工具缺失检查是否存在归一化名称冲突、无效的顶层输入 schema，或有另一个同名服务器定义把它遮蔽了。

发布清单

  • 服务器与 omp 协商2025-11-25，并且在初始化完成前不发送会话流量。
  • stdio 的 stdout 只包含协议帧；托管的 HTTP 具备 TLS、认证以及 Host/Origin 校验。
  • tools/list返回稳定的名字、描述、对象型输入 schema，并正确返回每个分页游标。
  • 每条tools/call路径都返回有用的content；可预期的失败返回isError: true。
  • Inspector 能列出并调用每个工具，/mcp test <name>报告的清单与之相同。
  • 在 omp 中用自然语言发起一次请求，能成功走到真实的处理器。
