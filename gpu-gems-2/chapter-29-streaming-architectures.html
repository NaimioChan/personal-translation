第 29 章　流式架构与技术趋势

John Owens
University of California, Davis

现代技术让当今处理器的设计者能把庞大的计算资源塞进最新的芯片。这些架构师面临的挑战，是把能力的增长转化为性能的增长。过去十年图形处理器的发展表明，GPU 设计者在这项任务上取得了惊人的成功。本章我们分析推动当今 GPU 构建方式的技术与架构趋势，以及我们对未来的预期。

29.1 技术趋势

作为计算机用户，我们已经习惯于每一代新硬件都比上一代跑得更快、能力更强，而且往往价格更低。这种惊人的发展速度之所以可能，是因为底层技术在持续进步，使每块芯片上能放下更多计算能力。每年，半导体行业都会在 International Technology Roadmap for Semiconductors（ITRS）中预测若干关注的芯片指标在未来几年将如何变化，例如晶体管尺寸、每芯片晶体管数和总体功耗（ITRS 2003）。这些预测对制造芯片和芯片制造设备的公司以及下一代芯片的设计者影响巨大。本节我们解释未来可以预期的一些趋势，以及它们对下一代图形处理器开发意味着什么。

29.1.1 核心技术趋势

当今的处理器由数百万个相互连接的开关器件构成，这些器件称为晶体管。随着工艺技术进步，这些晶体管以及它们之间的连线可以在更小的面积上制造出来。1965 年，Gordon Moore 注意到，在单个处理器晶片上经济地制造出的晶体管数量每年翻一番（Moore 1965）。Moore 预测这种增长很可能在未来持续。这个常被引用的预测被称为「摩尔定律」，今天它的含义是：每年可以在单个晶片上多放约 50% 的元件。[1] 在 Moore 做出预测之后的四十年里，每晶片的晶体管数从五十个（1965 年）增长到数亿个（2005 年），而且我们可以预期这种增长速度至少还会持续十年。

新一代芯片不仅增加晶体管数量，还减小晶体管尺寸。由于尺寸更小，这些晶体管能比前代工作得更快，使芯片整体运行更快。历史上，晶体管速度每年提升 15%（Dally and Poulton 1998）。在现代处理器中，一个称为时钟的全局信号同步整个处理器中发生的计算，因此处理器用户看到的晶体管速度提升体现为更快的时钟。晶体管数量与时钟速度的提升合起来，使处理器的能力每年提升 71%。这种逐年能力提升意味着，每年我们都能期待芯片上的计算量比前一年多 71%。

半导体计算机内存用的制造方法与处理器逻辑略有不同，但同样受益于制造技术的类似进步。ITRS 预测，通用动态随机存取存储器（DRAM）的容量将继续每三年翻一番。DRAM 性能可从两方面衡量：带宽，即每秒能传输的数据量；延迟，即从请求数据到数据返回之间的时间长度。DRAM 性能提升不如处理器能力快。DRAM 带宽每年提升 25%（ITRS 2003，表 4c、4d），而 DRAM 延迟每年只改善 5%。

29.1.2 后果

总的来说，刚才描述的趋势大多是正面的：随着每一代制造技术更新，处理器能力、内存带宽和内存延迟都在改善。例如，逐年能力提升带来了单个晶片上极高程度的集成。十五年前，设计者才刚刚开始把浮点运算单元集成到处理器晶片上；如今这样一个单元占用的晶片面积不到一平方毫米，而同一块晶片上可以放上数百个。

然而这些技术趋势最重要的后果，是它们之间的差异。当某个指标的变化速度与另一个不同时，就需要重新思考处理器与系统设计背后的假设。我们可以指出三个将推动未来 GPU 架构的主要问题：计算与通信、延迟与带宽，以及功耗。

计算与通信

随着时钟速度和芯片尺寸同时增大，信号横穿整块芯片所需的时间（以时钟周期计）也在增加。在当今最快的处理器上，把一个信号从芯片一侧送到另一侧通常需要多个时钟周期，而这一时间随每一代工艺更新而增加。我们可以把这一趋势概括为：相对于计算成本，通信成本在上升。其后果是，未来的设计者会越来越多地用廉价晶体管上的计算来替代昂贵的通信。另一个可能的影响是，每字内存带宽所对应的计算量会增加。举个例子，让我们比较 NVIDIA 最近三代旗舰 GPU（2002 年的 GeForce FX 5800、2003 年的 GeForce FX 5950 和 2004 年的 GeForce 6800）实测的峰值可编程浮点性能与片外内存峰值带宽。GeForce FX 5800 每字片外带宽能维持 2 次浮点运算，GeForce FX 5950 能维持 2.66 次，而 GeForce 6800 能维持近 6 次。我们预期这一趋势在未来几代芯片中会延续。图 29-1 给出了系列 GPU 架构实测的每秒浮点运算量与可用内存带宽的历史数据。

延迟与带宽

带宽与延迟两条趋势之间的差距，也将是未来架构的重要驱动力。由于延迟的改善会继续慢于带宽（Patterson 2004），设计者必须实现这样的方案：在等待耗时较长的操作返回数据期间继续做有用的工作，从而容忍越来越大的延迟。

功耗

虽然更小的晶体管比更大的更省电，但单个处理器晶片上晶体管数量的增长，快于每个晶体管功耗下降的幅度。因此每一代处理器都需要更多功耗：ITRS 估计，带散热片的 2004 年芯片允许的最大功耗为 158 瓦，到 2008 年将逐步升至 198 瓦的上限。这一功耗约束将成为未来处理器的主要限制之一；未来的性能指标也许不再是每秒运算次数，而是每瓦每秒运算次数。

29.2 高性能计算的要点

上一节我们看到，现代技术让每一代新硬件的能力都大幅提升。要有效利用这庞大的计算资源，需要解决两个重要目标。首先，我们必须组织好计算资源，使我们关心的应用能获得高性能。不过，仅仅提供大量计算并不够；还要高效地管理通信，才能把数据输送给芯片上的计算资源。本节介绍让我们同时实现高效计算与高效通信的技术，并讨论现代微处理器（CPU）为什么不适配这些目标。

29.2.1 高效计算的方法

在 29.1 节我们看到，如今已经可以把数百到数千个计算单元放在一块芯片上。要让晶体管在计算上发挥最大作用，关键有三点：把尽可能多的硬件用于计算，通过并行让多个计算单元同时工作，以及确保每个计算单元都以最高效率运行。

尽管现代技术让我们能在每块芯片上放置大量晶体管，资源仍不是无限的。晶体管的使用大致可分为三类：控制，用于指挥计算的硬件；数据通路，用于执行计算的硬件；以及存储，用于存放数据的硬件。如果目标是性能最大化，我们在硬件与软件上的决策就必须让数据通路中真正用于执行计算的晶体管尽可能多。

在数据通路内部，我们可以让多个运算同时进行。这种技术称为并行。可以利用并行的方式有几种。图形处理这类复杂任务通常由若干顺序任务组成。运行这类应用时，我们可能让其中几个任务同时处理不同数据（任务并行）。在一个阶段内部，如果某个任务要处理多个数据元素，我们可能让它们同时求值，从而利用数据并行。而在单个数据元素的复杂求值过程中，我们也可能让若干简单运算同时求值（指令并行）。要有效利用数百个计算单元，我们可以借助其中任意一种或全部并行方式。

在每个任务内部，我们可以让每个运算单元完全可编程，从而能执行任何任务。不过，利用专用化能从晶体管中获得更高效率。如果某个特定运算单元只执行一种计算，就可以针对这种计算做专门设计，效率提升相当可观。例如三角形光栅化——把屏幕空间中的一个三角形转换为一组覆盖该三角形的片元——当光栅化任务由专用硬件而非可编程硬件实现时，效率收益极其巨大。

29.2.2 高效通信的方法

正如 29.1.2 节所述，片外带宽的增长慢于片内运算能力，因此高性能处理器必须尽量减少片外通信。降低这项开销最简单的办法是消除它：现代处理器尽量把所需的数据通信都留在片内，只在取用或存放真正全局的数据时才需要片外通信。

另一种缓解通信成本上升的常见办法是缓存：把最近用过的数据在片内保存一份副本，这样再次需要该数据时就不必从片外取。这类数据缓存在未来的架构中会更普遍，并会扩展到局部缓存或用户可控的存储器，以减轻片内通信的需求。这些缓存实际上是用缓存存储器形式的晶体管去换带宽。另一种有力的技术是压缩：只把压缩后的数据传到片外并存放。压缩同样用晶体管（压缩与解压硬件）和计算（压缩/解压操作）去换片外带宽。

29.2.3 与 CPU 的对比

如今的高性能微处理器面向通用应用，其目标与计算机图形管线不同。一般而言，这些通用程序的并行度更低、控制需求更复杂、性能目标也更低。因此，我们前面列举的设计目标并不是 CPU 所追求的，CPU 做出了不同的设计选择，导致它难以映射到图形管线，也难以映射到许多具有类似特征的其他应用。

CPU 的编程模型通常是串行的，无法充分暴露应用中的数据并行。CPU 硬件也反映了这一编程模型：通常情况下，CPU 一次处理一个数据，并不利用数据并行。它们在利用指令并行方面做得相当出色，近来指令集的扩充（如 Intel 的 SSE 和 PowerPC 的 AltiVec）也允许一定程度的数据并行执行，但 CPU 所利用的并行程度远低于 GPU。

并行硬件在 CPU 数据通路中较少见，原因之一是设计者选择把更多晶体管用于控制硬件。CPU 程序的控制需求比 GPU 程序更复杂，因此 CPU 很大一部分晶体管和连线都用于实现分支预测、乱序执行这类复杂控制功能。结果，CPU 芯片上只有不大的比例真正用于计算。

由于 CPU 面向通用程序，它不含针对特定功能的专用硬件。而 GPU 可以为特定任务实现专用硬件，其效率远非通用可编程方案所能企及。

最后，CPU 存储系统优化的是延迟最小，而 GPU 存储系统追求的是吞吐量最大。由于缺乏并行，CPU 程序必须尽快取回存储引用才能继续推进。因此 CPU 存储系统设有多级缓存（占去芯片晶体管的相当大一部分）来压低这一延迟。然而对许多类型的数据来说缓存并不有效，包括图形输入以及只访问一次的数据。对图形管线而言，为所有元素最大化吞吐量、而不是为每个元素最小化延迟，能带来更好的存储系统利用率和整体更高的性能。

29.3 流式计算

上一节我们看到，如今构建高性能处理器既需要高效计算，也需要高效通信。CPU 难以胜任许多这类高性能应用，部分原因在于它的串行编程模型无法暴露应用中的并行与通信模式。本节介绍流编程模型，它组织程序的方式能让计算和通信都达到高效率（Kapasi et al. 2003）。这一编程模型是如今 GPU 编程的基础。

29.3.1 流编程模型

在流编程模型中，所有数据都表示为流，我们把它定义为一组有序的、同一数据类型的数据。这个数据类型可以是简单的（整数或浮点数的流），也可以是复杂的（点、三角形或变换矩阵的流）。流的长度可以任意，但我们会看到，流越长（流中有数百个或更多元素），对流做的操作效率越高。允许对流的操作包括复制、从中派生子流、用另一个索引流对其索引，以及用内核对其做计算。

内核作用于整个流，以一个或多个流为输入，产生一个或多个流作为输出。内核的定义性特征是它作用于元素的整个流，而不是单个元素。内核最典型的用法是对输入流的每个元素求一个函数（即「map」操作）；例如，一个变换内核可以把点流中的每个元素投影到另一个坐标系。其他有用的内核操作还包括扩展（对每个输入元素产生多个输出元素）、归约（把多个元素合并为一个输出元素）以及滤波（只输出输入元素的一个子集）。

内核的输出只是其内核输入的函数，并且在内核内部，对一个流元素的计算从不依赖于对另一个元素的计算。这些限制有两大好处。第一，内核执行所需的数据在内核编写（或编译）时就已完全确定。因此，当输入元素与中间计算数据存放在本地或处于严格受控的全局引用中时，内核可以非常高效。第二，要求单个内核内各流元素的计算彼此独立，使得看起来串行的内核计算能够映射到数据并行硬件上。

在流编程模型中，应用通过把多个内核串接起来构建。例如，要在流编程模型中实现图形管线，就要编写顶点程序内核、三角形装配内核、裁剪内核等等，然后把一个内核的输出接到下一个内核的输入。图 29-3 展示了整条图形管线如何映射到流模型上。这一模型把内核之间的通信显式化，利用了图形管线中内核之间固有的数据局部性。

图形管线与流模型十分契合，原因有几点。图形管线传统上就被组织成若干计算阶段，阶段之间由数据流相连。这种结构与流编程模型中的流和内核抽象对应。图形管线各阶段之间的数据流高度局部化，一个阶段产生的数据立即被下一阶段消费；在流编程模型中，内核之间传递的流也表现出类似行为。而且管线各阶段的计算在不同图元上通常是统一的，这使这些阶段能轻松映射为内核。

高效计算

流模型在多方面实现了高效计算。最重要的是，流暴露了应用中的并行。由于内核作用于整个流，流元素可以用数据并行硬件并行处理。元素众多的长流使这种数据级并行非常高效。在处理单个元素时，我们可以利用指令级并行。而由于应用由多个内核构建，多个内核可以深度流水化并并行处理，利用任务级并行。

把目标应用划分为内核，使硬件实现能够针对一个或多个内核的执行来专门化硬件。专用硬件的效率优于可编程硬件，因此在这一编程模型中可以被恰当地使用。

最后，只允许内核执行中有简单的控制流（例如对每个输入元素做数据并行的函数求值），使硬件实现能把大部分晶体管用于数据通路硬件而非控制硬件。

高效通信

高效通信也是流编程模型的主要目标之一。首先，当整个流而不是单个元素在存储器之间传输时，片外（全局）通信更高效，因为发起一次传输的固定开销可以摊到整个流上，而不是单个元素。其次，把应用组织成内核链，可以让内核之间的中间结果留在片内，不必往返存储器。高效的内核尽量让输入与中间计算数据留在内核执行单元本地；因此内核执行中的数据引用不会像 CPU 中通常那样走到片外或跨芯片去访问数据缓存。最后，深度流水化执行让硬件实现能在等待全局存储器返回数据时继续做有用的工作。这种高度的延迟容忍使硬件实现可以针对吞吐量而非延迟做优化。

29.3.2 构建流处理器

流编程模型组织程序的方式既暴露并行，又允许高效通信。然而，用流模型表达程序只是解决方案的一半。高性能图形硬件必须有效利用流模型所暴露的高运算性能与高效计算。我们该如何组织 GPU 的硬件实现，才能确保整体性能最高？

构建高性能 GPU 的第一步，是把图形管线中的内核映射到单块芯片上独立的功能单元。于是每个内核都实现在芯片的一个独立区域上，这种组织方式称为任务并行，它不仅允许任务级并行（因为所有内核都能同时运行），还使每个功能单元能针对相应内核做硬件专用化。任务并行的组织方式还带来内核之间的高效通信：实现图形管线中相邻内核的功能单元在芯片上也是相邻的，它们无需访问全局存储器就能有效通信。

在图形管线中每个映射到芯片上处理单元的阶段内，GPU 利用各流元素的独立性并行处理多个数据元素。任务级并行与数据级并行的结合，使 GPU 能同时使用数十个功能单元并从中获益。

图形管线的输入必须依次经过每个内核处理。因此，完成单个元素的处理可能要花数千个周期。如果在处理某个元素时需要一次高延迟的存储器引用，处理单元只要在取数期间转而处理其他元素即可。于是现代 GPU 的深流水线能有效容忍高延迟操作。

许多年里，构成图形管线的各个内核在图形硬件中都是以固定功能单元实现的，几乎没有或完全没有用户可编程性。2000 年，GPU 首次让用户有机会对图形管线中的各个内核编程。如今的 GPU 配备了高性能数据并行处理器，在图形管线中实现两个内核：顶点程序让用户对经过管线的每个顶点运行一段程序，片元程序让用户对每个片元运行一段程序。这两个阶段都支持单精度浮点计算。虽然这些新增能力原本是为了给用户提供更灵活的着色与光照计算，但它们能以足够精度在用户指定的程序上维持高计算速率、从而处理通用计算问题，这实际上使它们成为可编程流处理器——也就是说，这类处理器对远不止图形管线的各种应用都具有吸引力。

29.4 未来与挑战

GPU 向可编程流处理器的转变，是若干历史趋势汇聚的结果。第一个趋势是能把大量计算集中到单个处理器芯片上。同样重要的是 GPU 设计者有效利用这些计算资源的能力与才干。每年制造数千万颗处理器所带来的规模经济，使 GPU 的成本降到足以成为当今台式计算机的标准部件。而管线中加入精度尚可的可编程能力，则完成了从硬连线专用处理器到能处理各种任务的强大可编程处理器的转变。

那么，未来的 GPU 发展可以期待什么？

29.4.1 挑战：技术趋势

每一代新硬件都会给 GPU 厂商带来一个挑战：如何有效利用新增的硬件资源来提升性能与功能？新增的晶体管将用于提升性能——很大程度上靠增加并行度——以及用于管线中的新功能。我们也会看到这些架构随技术变化而演进。

正如 29.1.2 节所述，未来的架构会越来越多地用晶体管来替代通信需求。可以预期更激进的缓存技术，不仅缓解片外通信，也减轻部分片内通信的需求。在合适的时候，我们还会看到计算越来越多地取代通信。例如，用纹理存储器作查找表的做法，可能改为动态计算该查找表中的值。又如，与其把数据送到芯片另一端远处的计算资源再把结果送回来，我们也许直接复制该资源、在本地算出结果。在通信与重算/缓存之间的权衡中，我们会越来越多地选择后者。

通信成本的上升也会影响未来芯片的微架构。设计者如今必须明确规划数据跨芯片传输所需的时间；即使本地通信时间在时序预算中也变得可观。

29.4.2 挑战：功耗管理

关于如何使用未来 GPU 晶体管的各种想法，都必须受制于成本现实。随着每一代硬件的功耗需求上升，功耗管理已成为当今 GPU 设计的关键一环。未来可能出现更激进的动态功耗管理，针对各个阶段分别实施；针对 GPU 中耗电大的部分采用更多定制或功耗感知的设计；以及为高端 GPU 设计更精细的散热管理。技术趋势表明，功耗需求只会随未来芯片世代继续上升，因此这一领域的持续工作仍将是一项重要挑战。

29.4.3 挑战：支持更多可编程性与功能

当前这代图形硬件的可编程性远超前几代，但 GPU 的通用可编程性仍远未理想。应对这一趋势的一步，是改善现有两个可编程单元（顶点与片元）内部的功能与灵活性。很可能我们会看到它们的指令集趋于一致并增加功能，控制流能力也会变得更通用。我们甚至可能看到这两个阶段共用可编程硬件，以更好地利用这些资源。不过 GPU 架构师必须留意，这类改进不能影响 GPU 在核心任务上的性能。另一个选项是把可编程性扩展到其他单元。几何图元尤其能从可编程性中受益，因此我们可能很快看到针对曲面、三角形和像素的可编程处理。

随着 GPU 厂商支持更通用的管线和更复杂多样的着色器计算，许多研究者已用 GPU 来处理图形管线范围之外的任务。本书收录了其中许多工作的例子；GPU 通用计算（GPGPU）社群已成功用图形硬件解决了视觉仿真、图像处理、数值方法和数据库方面的问题。可以预期，随着 GPU 性能与功能持续提升，这类工作在未来会增多。

历史上，我们看到 GPU 不断吸纳原本属于 CPU 的功能。早期的消费级图形硬件无法在图形处理器上做几何处理；仅仅五年前，整条图形管线才能在一颗芯片上制造出来。虽然自那时起 GPU 功能的主要增长都指向图形管线内部的可编程性，但我们不应以为 GPU 厂商已经停止寻找更多可集成到 GPU 上的功能。尤其是当今游戏常常需要在物理和人工智能计算上做大量运算。这类计算对未来的 GPU 可能很有吸引力。

29.4.4 挑战：GPU 的功能被 CPU 吸纳（还是反过来）？

可以确信，当 GPU 在未来的芯片上集成更多处理能力与功能时，CPU 厂商不会原地不动。每个工艺世代晶体管数量的不断增长，最终可能引发 CPU 与 GPU 厂商之间的冲突。未来计算机系统的核心是 CPU 吗——即最终可能把 GPU 或流处理功能集成到 CPU 本身？还是未来系统以 GPU 为核心，把 CPU 功能并入 GPU？当我们展望令人兴奋的未来时，这些重大问题将考验下一代处理器架构师。
