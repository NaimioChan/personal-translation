第 25 章　Apple Motion 中的 GPU 图像处理

Pete Warden
Apple Computer

本章介绍我们在编写 Motion 时遇到的一些挑战、找到的解法以及得到的教训。这里写的全是我们刚起步时就希望知道的东西！像素着色器相对于 CPU 渲染带来的速度提升令人惊叹，常常快十到二十倍，但身处前沿也意味着要爬一段陡坡。

我们需要实现复杂的图像处理操作，因此需要能运行灵活、通用像素着色器的 GPU。我们编写 Motion 是在 2003 年和 2004 年初，当时 Mac 上能胜任的显卡有两个系列：ATI R3xx 系列和 NVIDIA NV34。如今 Apple 平台上已有 NVIDIA GeForce 6 系列这类更新的 GPU。讨论实现细节时我主要针对 R3xx 和 NV34，但大部分内容对更新的硬件依然适用。新硬件最大的差别在于资源上限大幅提高、浮点像素支持的出现，以及更高的性能。

25.1 设计

GPU 能比 CPU 更快地解决某些问题，因为它们高度专用、能并行执行许多操作，并且有速度极高的并行内存访问。这些能力是有代价的：GPU 用灵活性换速度。有大量问题它们根本无法处理，因此在规划应用时了解它们的强项与短板至关重要。

25.1.1 偏爱与厌恶

有些图像处理操作很适合映射到 GPU 上，有些则难以写成着色器，甚至根本写不出来。下面说明这几类操作，以及我们把它移植到 GPU 时的难易程度。

图像进，图像出

输入一幅或多幅图像、输出单幅图像的算法，与 GPU 的能力非常直接地对应，很有希望达到峰值性能。当然，这类算法在图像处理中很常见，尤其是图形设计应用所需的那一类。

图像进，统计量出

输入一幅图像、输出某种度量的算法在 GPU 上更难实现。一个典型例子是统计图像中有多少像素取不同的颜色值，即生成直方图。在 CPU 上这很简单：遍历图像的所有像素，按每个像素的颜色值选定数组中的某一项并把它加一。用伪代码写就是：

 for
   <all pixels> arrayIndex = currentPixel.luminance;
 histogram[arrayIndex] += 1;

在像素着色器里做这件事的困难在于，结果必须写到固定位置；你没法做「按像素亮度选择要递增的直方图项」这一步。

GPU 能根据运行时的选择灵活地从许多位置聚集读取输入，但没法同样方便地根据输入数据把输出分散写入不同位置。

几乎所有输出统计量或度量的算法都需要一个分散写的步骤，这使得为它们写出好的 GPU 实现变得困难。关于在 GPU 上实现分散写算法的更多信息，见本书第 32 章「GPU 计算策略与技巧」。

颜色变换

输入单个像素的颜色、对其施加某种函数、再把结果作为新颜色输出的操作，非常适合用 GPU 实现。通常，伽马校正或亮度调整这类简单变换，用像素着色器里几条算术指令就能直接算出。更复杂的变换可以在 CPU 上预先算好，以查找表的形式传入。（另见第 24 章「用查找表加速颜色变换」。）

独立的邻域操作

GPU 很适合读取基准位置周围的多个像素并把它们组合成一个输出值。单个着色器能组合的像素数量也许有限，但我们可以把操作拆成几个着色器、跑多遍来绕过这一点，中间结果写入 OpenGL 像素缓冲（pbuffer），再作为纹理传给后续的遍。我们用这种做法成功实现了边缘检测、高斯模糊等卷积滤波。

顺序邻域操作

凡是需要按特定顺序访问图像中的像素、并在同一遍中用到前面像素结果的算法，都无法在 GPU 上工作。结果必须写入纹理。既无法指定像素的处理顺序，也无法在同一遍中访问其他像素的结果。GPU 的速度有一部分来自并行执行大量操作；为了做到这一点，编程模型不允许着色器依赖这种顺序。

一个不易移植到 GPU 的算法例子是做盒式滤波的滑动盒车法。它依赖沿行、沿列推进，在一个累计和中加上或减去，从而得到每个像素的结果。着色器里既无法保存这样的累计和，也无法保证行和列按正确顺序被访问。

不那么明显的一点是，逐像素随机数生成器也很难实现，因为它们通常依赖保存一个种子值，每次取随机数时更新它，而这个种子值无法在着色器里跨像素保存。

条件执行

任何包含超过几个分支的操作，在我们当时开发所用的大量硬件上都难以容纳。[1] 当时着色器不支持任何分支或跳转指令，对条件执行的全部支持只有一类指令：用一个比较结果决定两个输入中的哪一个进入结果。这意味着要先算出两个可能的结果再做比较，哪怕决策树只是稍微复杂一点，程序也很快就变得非常长。

25.1.2 选择语言

在评估了若干种高级 GPU 编程语言——包括 Cg、GLSL、HLSL、Direct3D 的像素着色器，以及各厂商的汇编语言——之后，我们选择用 OpenGL 的底层 ARB_fragment_program 扩展来写 Motion。

类 C 高级语言的优势很明显：学习曲线更平缓，程序更易维护，编译器能施加高层优化，程序也容易移植到不同硬件上。

但当时这项技术还处在演进早期，早期的高级编译器不如现代 CPU 编译器成熟。有些语言当时只在有限的平台上可用。随着语言技术成熟，这些问题正在缓解，但我们编写 Motion 时它们仍未解决。

用类汇编语言编写代码的缺陷同样众所周知：难学，编写程序琐碎，调试与维护棘手。不过它们也有一些不为人知的优势。对我们来说重要的一点是，处理着色器的底层指令时，理解和绕开特定 GPU 的限制要比在隐藏了这类实现细节的高级语言里容易得多。通过指令集理解 GPU 的强项与短板，也帮助我们修改算法以提升性能。

ARB_fragment_program

我们对为着色器选用 ARB_fragment_program 这个决定很满意。我们得到了 ATI 和 NVIDIA 双方的坚实支持，没有因为实现上的 bug 遭遇重大延误，也学到了很多关于 GPU 工作方式的知识。调试如预料中那样痛苦，但也有一些意外的惊喜。

指令集相当优雅且正交，与我们着手处理的许多图像处理操作对应得很好。不少情况下，GPU 版本甚至比 C 版本更好写！ARB_fragment_program 缺少条件执行指令，迫使我们采用函数式写法，这也带来了一些移植 CPU 算法时不寻常而富有成效的思路。当然，GeForce 6 系列这类更新的 GPU 确实支持条件执行。

25.1.3 CPU 回退

会有一段时间，仍有一些系统的 GPU 无法运行图像处理所需的那类着色器。如果你是在已有的 CPU 程序上添加 GPU 处理，那么在这些系统上直接禁用着色器、使用现有代码即可。如果一个应用主要为支持着色器的硬件而写，又选择支持没有 GPU 的计算机，你就需要决定如何在这些旧系统上运行。

构建 CPU 回退有两条路：为所有算法另写 CPU 版本，或者写一个在 CPU 上运行着色器的 GPU 模拟器。

在实现和调试 GPU 版本时，拥有独立的 CPU 版本极为有用。我们强烈建议你从这种参考实现起步，把它作为开发辅助；当你需要判断某个 bug 是基本算法的缺陷还是着色器实现的问题时，它的价值无可替代。这种做法最大的缺点是实现并维护所有操作的并行版本所需的时间。

编写 GPU 模拟器超出了本章范围，但值得指出的是，图像处理通常只需模拟 GPU 特性的一小部分，而底层着色语言使用的向量指令与 AltiVec 和 SSE 指令集对应得很好。

对 Motion，我们选择只支持具备 GPU 的硬件，因为这覆盖了我们目标市场（视频专业人士）的大部分，这样做也让我们能把开发时间集中在扩展应用能力上。

25.2 实现

在构建 Motion 的过程中，把图像处理算法写成着色器时我们遇到了不少实际问题。

25.2.1 GPU 资源上限

在 ATI R3xx 显卡上，最大的困难来自 ARB_fragment_program 着色器实际运行时所受的限制。GPU 程序最多只能有 64 条算术指令和 32 条纹理访问指令。NVIDIA NV34 的上限高得多，总共可以有 1,024 条指令。实践中我们发现，对我们所需的大多数操作来说，ATI 的指令上限不算大问题，不过少数比较复杂的着色器让我们不得不花时间削减指令数。

有些指令在 GPU 上会映射成多条原生汇编指令，这又添了一点麻烦。例如 ATI 显卡上的 SIN 指令执行的是一段多指令的泰勒级数，而不是 NV34 那样的单指令操作（后者实际得到的结果精度还比泰勒级数更高）。

对我们来说严重得多的是 ATI GPU 上纹理间接寻址最多四层的限制。ARB_fragment_program 规范详细说明了什么算一层纹理间接寻址，但从实用角度看，它把依赖式纹理读取的链条限制在四层以内。依赖式纹理读取用之前某次纹理读取或算术指令的结果作为坐标。下面是一个简单例子：

!!ARBfp1 .0 TEMP inputColor, tableResult;
#Read the input pixel; first level of indirection
TEX inputColor, fragment.texcoord[0], texture[0], 2D;
#Look up a result from a table; second level of indirection
TEX tableResult, inputColor, texture[1], 3D;
#Look up the output in a palette texture; third level of indirection
TEX result.color, tableResult, texture[2], 1D;
END

这是我们要做的典型操作之一，而它距离上限已经只差一层了。

避免纹理间接寻址成了编写着色器时的大麻烦。一个有用的做法是把尽可能多的计算移到顶点层面，因为用插值后的顶点分量或程序常量做读取不会触发间接寻址。由于我们撞上间接寻址上限的次数比指令耗尽的次数更多，我们养成了用算术指令现场算出结果、而不从存在纹理中的预计算表里读取的习惯。作为最后手段，我们也会把算法拆成多遍，用 pbuffer 在着色阶段之间传递中间结果。不过我们尽量避开这一招，因为当时我们平台上可用的 pbuffer 通常是每通道 8 位，而非 NVIDIA GPU 上 IEEE 32 位浮点、ATI GPU 上 24 位浮点的着色器内部精度。跑多遍也意味着性能损失。

25.2.2 除以零

NV34 的指令上限很宽松，对纹理间接寻址层数也没有限制，但它对除以零的处理迫使我们重写了部分着色器。

R3xx 遇到输入为零的 RCP 或 RSQ 指令时，会把结果设成一个非常大的数。NV34 在这种情况下正确遵循 IEEE 浮点标准，输出「非数」（NaN）值，表示正无穷或负无穷，取决于分子的符号。这个 NaN 与 ATI 的大数之间的重大差别是：NaN 会使用到它的任何数学指令的结果也变成 NaN。

在我们具体的着色器里，其实可以利用这种不合 IEEE 规范的行为，因为我们出现除以零的地方，后面都跟着乘以零。常见例子是：取一个预乘 alpha 的颜色输入，把颜色通道除以 alpha 以便在直通 alpha 颜色空间里做计算，然后再乘以同一个输入 alpha，把结果放回预乘空间。在 R3xx 上，alpha 值为零时输出的红、绿、蓝通道也会是零，这正是我们想要的。而 NaN 会传播到输出，在帧缓冲里被存成纯白，这至少可以说是不可接受的。

我们的解决办法是确保这些指令永远不会拿到为零的分母，代价是几条额外指令。总体思路是把分母从零推开一点点：若分母为正，就加上一个很小的 epsilon 值：

CMP epsilonFudge, denominator.x, 0, 0.00001;
ADD denominator.x, denominator.x, epsilonFudge;
RCP reciprocal.x, denominator.x;

这让每次除法多两条指令，但如果你能确定分母永不为负——例如它取自一张 8 位纹理——就可以省掉比较，像这样：

ADD denominator.x, denominator.x, 0.00001;
RCP reciprocal.x, denominator.x;

这看起来像是在牺牲精度，但 epsilon 值小到在实践中所加的任何数只要不是非常接近零，就会在下溢中把它丢掉。

25.2.3 顶点分量丢失

前面提到，把在四边形上插值的顶点分量传入片元程序可能非常有用。OpenGL 中着色器可用的纹理坐标有八组，但我们发现使用 OpenGL「老式」固定功能顶点管线时，在某些 GPU 上只能访问其中前四组。插入一个简单地把八组坐标原样传出的顶点程序就解决了问题。

25.2.4 双线性滤波

用显卡做图像处理的基本做法是：画一个与屏幕对齐的四边形，把图像纹理映射到它上面，渲染到一个用来存放输出图像的帧缓冲里。对我们的合成软件包来说，我们经常想对图像施加简单的几何变换，即平移、缩放或旋转。这在 GPU 上很容易：只需变换四边形的顶点，再交给光栅化器。这些变换可以与片元程序中实现的其他操作搭配，不额外付出代价。为得到像样的输出质量，我们对输入图像使用了双线性滤波，这同样不花代价。由于双线性滤波如此有用又没有性能开销，我们默认处处使用它。这引出了我们最棘手的两个问题：图像变软和 alpha 边缘发丝。

图像变软

我们注意到，即使不做任何变换地绘制图像，也会出现细微的模糊或变软——而且图像经过的渲染管线阶段越多，问题越严重。我们花了一些时间确认顶点位置和纹理坐标设置无误，结果发现问题出在图形硬件光栅化图元时的精度上。图 25-1 说明了这种情况。

四边形内每个像素的纹理坐标，是根据该像素到各顶点的距离以及各顶点上设置的纹理坐标算出的。由于每画一个像素都要做这个计算，一切可能的加速手段都会被用上。不幸的是，图形硬件所采用的一些以精度换速度的优化，对我们的影响远比对 3D 场景渲染大。渲染场景时，所有图元本来都会被变换和扭曲，只要误差是一致的，纹理映射中小于一像素的精度误差就不会被察觉。

但我们想画的是这样的四边形：输入纹理中的每个像素都被画到输出缓冲中的完全相同位置。哪怕偏差只有几分之一像素、偏离纹素中心，双线性滤波也会把相邻像素的一部分渗进结果，造成我们看到的变软。误差大小取决于具体 GPU 实现纹理坐标计算的方式（例如，我们看到 NV34 上的误差比 ATI GPU 小得多，因为 NV34 的亚像素精度位数多得多）。见图 25-2。

在大多数情况下，我们通过改用最近邻滤波解决了这个问题——凡是我们希望一对一映射的地方就这样做。由于误差远小于 1 像素宽，这样就得到了想要的结果。误差似乎随四边形尺寸增大而增大，因此我们尝试过的一种方法是：把大四边形切成许多小四边形组成的网格，在 CPU 上精确完成纹理坐标插值，再把值存入这个网格的顶点。这种做法大大减小了误差。

alpha 边缘发丝

我们遇到的另一个双线性滤波问题，是渲染物体的 alpha 边缘周围出现深色发丝，凡是某种变换触发了滤波的地方都会出现。例子见图 25-3。

我们的管线以存放为非预乘 alpha 格式的 pbuffer 纹理为渲染起点和终点，这原来是问题的根源。要看清楚发生了什么，请观察图 25-4 中被一片完全透明像素包围的那个白色、完全不透明的像素。（由于透明像素的 alpha 为零，而这是直通 alpha 纹理，其颜色通道里放什么都不应有影响，所以我把它设成了黑色。）

双线性滤波取最近的四个像素，按不同比例混合它们得出结果。图 25-5 给出了用双线性滤波把这张纹理放大三倍绘制时得到的值，图 25-6 给出的是用 Over 算子把图 25-5 合成到另一幅图像之上时发生的情况。

双线性插值分别处理所有通道，凡是完全不透明或部分不透明的像素挨着零 alpha 邻居的地方，都会把完全透明像素的颜色混进去。在我们的情形中，混入的黑色导致混合后出现灰色发丝。

常规解法是确保零 alpha 像素若有不透明邻居，其颜色通道里要放合理的值。这在 3D 建模场景中效果很好：内容制作者可以手动修改纹理以符合这一约束，也可以在正常的纹理加载管线中让纹理走一遍自动处理，把值设成合理的。

但在做合成用的图像处理时，纹理的创建是一个动态得多的过程：无法手动干预，而对每张中间纹理跑一遍修补也会严重拖累性能。我们考虑过的一种替代做法是在像素着色器里自行实现双线性滤波，丢弃完全透明像素的影响。这意味着凡是需要双线性滤波的地方，每读取一次纹理都要换成四次读取，还要额外的算术指令来做滤波。我们判定这种做法不实用，放弃了。

我们最终的办法是把管线切换为使用存成预乘 alpha（或称关联 alpha）格式的纹理。用预乘颜色做双线性滤波不会出现发丝问题。见图 25-7。

计算模糊时颜色也需要处在这个格式，不过大多数颜色校正操作都必须在直通 alpha 颜色空间里进行。这次管线改动影响不小，因为它发生在开发后期，但一切稳定下来之后，效果很好。在需要时于着色器里做两种颜色空间的换算并不困难，只是前面讨论过的除以零差异确实让它复杂了些。

25.2.5 高精度存储

Motion 的管线中大多使用每通道 8 位的图像，但有些地方需要更高精度。我们用累积缓冲算法实现运动模糊，而使用 8 位缓冲时色带不可接受。

在写作本书时，R3xx GPU 支持每通道 16 位和 32 位的浮点格式，所以我们只需申请并创建一个 16 位 pbuffer。把渲染管线切换到更高精度运行出奇地容易；在 CPU 图像处理管线里做同样的事则要费劲得多。高精度 pbuffer 的混合与滤波有一些限制，但我们能用两个 pbuffer 做双缓冲，模拟运动模糊所需的加法混合。[2]

我们编写 Motion 时，NV34 的 Mac 驱动只暴露出对每通道 8 位纹理的支持，因此我们需要一个不使用浮点格式的运动模糊替代实现。像素着色器的灵活性派上了用场，它让我们能用两张 8 位纹理模拟一个每通道 16 位的定点 pbuffer。累积缓冲需要累加多至 256 个 8 位样本，所以我们选用 8.8 定点格式，把每个颜色通道的整数部分和小数部分一起打包进 pbuffer 的一个 8 位通道，于是每个颜色通道在存放的纹理中需要占用两个通道。

把值打包进两个通道意味着：把原值除以 256，使整数部分落在一个不会被截断的范围内；再对值取模 1，得到要存的小数部分：

MUL output.x, value.x, reciprocalOf256;
FRC output.y, value.x;

重建打包值时，把存在一个通道里的整数部分乘以 256，再加上小数部分，就得到原值。

MAD value.x, input.x, 256, input.y;

实现累积缓冲算法需要两遍着色：一遍处理红、绿通道，另一遍处理蓝和 alpha，因为当时一个着色器一次只能把结果输出到一个缓冲，而每个缓冲只能容纳两个通道。

25.3 调试

我们花了大量时间琢磨着色器为什么不工作。有一些调试工具可用于 ARB_fragment_program 着色器——特别是 Apple 的 Shader Builder 和开源的 ShaderSmith 项目——但没有任何工具能让我们在应用内部运行时调试 GPU 程序。我们只好退回一些老办法，去撬开 GPU 这个黑箱。

语法错误最好找：无效的程序在使用时输出白色，就和用了无效纹理一样。程序初次加载时，调用 glGetString(GL_PROGRAM_ERROR_STRING) 会返回一条描述所发现语法错误的消息。

理论上，检测程序是否指令过多或纹理间接寻址层数超限，只需要下面这个调用：

glGetProgramivARB(GL_fragment_program_ARB, GL_PROGRAM_UNDER_NATIVE_LIMITS_ARB,
                  &isUnderNativeLimits)

实践中它并不总能检出这类上限被撞到的情况，我们于是学会辨认在 ATI GPU 上超限时得到的全黑输出。我们发现，确认问题是上限而非计算错误的最好办法，是在着色器末尾放一条 MOV result.color, { 1, 1, 0, 1 } 指令。如果输出变黄，说明着色器确实在执行；若仍是黑色，则说明程序因超出 GPU 上限而没有执行。

要弄清撞上的是哪个上限，可以注释掉一些指令再跑一遍程序。最终，当我们削减了足够多的指令后就会看到黄色。最后被削掉的那类指令，就能看出我们撞上的是哪个上限。

最难查的错误是我们逻辑或数学上的失误，因为我们确实需要看到着色器运行时的内部运作才能理解哪里出了错。我们发现，着手调试这类问题的最好办法是有一个已知可用的简单 CPU 版算法；然后一条指令一条指令地步进着色器，用眼睛把每条指令与 CPU 实现中对应阶段的指令作比较。

这类检查不奏效时，从着色器里取出信息只有一条路：写进帧缓冲。首先要注释掉最后的输出指令，改为存入某个你关心的中间值。你可能需要缩放这个值，使它落在普通缓冲能存放的 0–1 范围内。然后可以用 glReadPixels() 取回精确值，不过通常屏幕上显示的大致颜色就足以帮助弄清发生了什么。

如果某件事真的令人费解，就换到不同的 GPU 上试试，以确认问题不是由各厂商实现的差异造成的。

25.4 结论

尝试用为游戏设计的硬件做高质量图像处理，对我们来说既令人沮丧又很有收获。GPU 的速度不只帮我们转换了现有算法，还启发我们尝试新想法。能立刻看到结果，加上在应用运行时重新加载着色器的便利，给了我们一个摆弄图像的绝佳实验室。
