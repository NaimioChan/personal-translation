第 41 章　延迟滤波：从困难数据格式渲染

Joe Kniss
University of Utah

Aaron Lefohn
University of California, Davis

Nathaniel Fout
加州大学戴维斯分校

本章介绍一套技巧，用于交互式渲染以困难格式存储的二维与三维数据集。这些数据格式在 GPGPU 计算中、以及从压缩数据做体绘制时都很常见。GPGPU 的例子包括用于云与火焰仿真的「扁平三维纹理」，以及用于隐式曲面变形的稀疏格式。这些应用使用复杂的数据格式，是为了优化 GPU 计算的效率，而非渲染的效率。然而，这类非标准、困难的格式不容易融入标准渲染管线，尤其是那些需要纹理滤波的管线。本章介绍延迟滤波，以及从这些复杂的自定义数据格式高效渲染高质量图像所需的其他技巧。

41.1 引言

从困难数据格式实现经过滤波的交互式渲染，其核心概念是延迟滤波。延迟滤波是一种两遍渲染方法：第一遍把数据的一个子集重建为常规二维纹理，第二遍利用硬件原生的插值能力，为二维或三维数据生成高质量、经过滤波的渲染结果。该算法是增量的，因此渲染三维数据集所需的内存与渲染二维数据大致相当。

延迟滤波适用于那些用困难或非标准内存布局来模拟或压缩二维、三维效果的 GPGPU 计算，也适用于使用压缩数据格式的体渲染器。相关的 GPGPU 应用包括稀疏计算与扁平三维纹理（见第 33 章「在 GPU 上实现高效的并行数据结构」）。传统上，要对这些数据集做高质量渲染，必须在片元程序里「手工」完成插值，而这又需要重建多个相邻的数据样本。这种做法会产生大量冗余工作。

延迟滤波最早在 Lefohn 等 2004 中描述。该论文给出了交互式计算并渲染可变形隐式曲面的算法。数据以稀疏瓦片格式表示，延迟滤波是论文所述交互式体绘制管线中的关键组成部分。本章扩展并推广了他们对这项技术的描述。

41.2 为何延迟？

让我们考察一个简单的场景：设想你要渲染云或爆炸这类体积效果，而三维数据已用矢量量化压缩过（见 Schneider 与 Westermann 2003）。该方案用一个称为键的单一值来压缩数据块。键值用作码本中的索引，使特征相似的数据块共享同一份内存。重建这些数据需要先从键纹理读取，再从码本纹理中相应的纹素读取。设想重建单个纹素需要四条片元程序指令。

这种做法的一个问题是，你不能简单地开启 GPU 上的线性纹理插值，就指望得到平滑滤波的纹理。相反，线性插值必须以「手工」方式在片元程序中实现。在实践中这代价太高，渲染器往往只能退回到最近邻采样，完全放弃滤波。见图 41-1 右上。所谓「手工」滤波，意味着必须重建 8 个最近的纹素，再做 7 次线性插值（LERP），才能为每个被渲染的片元得到一个三线性滤波后的值。假设原始数据尺寸为 1283 个体素，渲染填充 2562 的视口（即渲染把数据放大了 2 倍），并且我们对每个体素采样两次。被渲染的片元数为 256 x 256 x 128 x 2，总计约 1600 万个片元。再看每个片元的片元程序指令数：8 x 4（8 个纹素乘以每次重建 4 条指令）+ 8（纹理读取）+ 14（三线性插值；LERP 与 ADD），即每次滤波纹理读取 54 条指令。这样总计就是十亿条片元指令，为的只是这一次简单渲染。可以想见，这会给应用的交互性带来不小的打击。

41.3 延迟滤波算法

为了应对上例中纹理滤波所需的片元指令激增，我们主张采用两遍渲染方法。这种两遍方法避免了冗余工作（纹理读取与运算），并利用了硬件原生的滤波能力。第一遍按原始分辨率重建数据的一个局部子集，第二遍使用 GPU 的硬件滤波能力渲染重建后的数据。

在上例中，我们描述了以自定义压缩内存格式存储的三维数据的朴素基于切片的体绘制（见 Ikits 等 2004）。把滤波推迟到另一遍有巨大的好处，但它要求我们换一种方式解决问题。我们不再用任意切片平面渲染体，而是采用轴对齐切片（利用二维纹理）。这种方法沿与视线方向最接近的主轴渲染体切片。与 Rezk 等（2000）一样，我们从两个相邻的二维切片读取，并在片元程序中计算最终的 LERP，从而在体切片之间生成三线性滤波的样本。

图 41-2 描绘了这一过程。算法如下（注意算法中的步骤 A 与 B 对应图 41-2 中的步骤 A 与 B）：

  1. 重建第一张体数据切片，i = 1。
  2. 对每个切片，i = 1 到 number of data slices - 1 ：
    1. 重建切片 i + 1。
    2. 对数据切片 i 与 i + 1 之间的每个采样切片：
      1. 从切片 i 与 i + 1 读取重建后的值。
      2. 执行最终的 LERP（用于三线性滤波）。
      3. 对片元作着色与光照。

现在，我们不再为每个渲染的片元重建并滤波数据，而是按原始分辨率重建数据，让 GPU 的纹理引擎完成大部分滤波。节省非常显著：3 条片元指令（2 次纹理读取与 1 次 LERP），而单遍重建加渲染需要 54 条片元指令。自然，多出的一遍会有一些额外开销，其中必须包含重建代价（但每个纹素只付一次）。请务必用渲染到纹理（例如 pbuffer）为切片纹理 i 与 i + 1 避免不必要的纹理拷贝。

代码清单 41-1 中的函数展示了用延迟滤波读取三线性滤波三维纹理所需的三条指令。注意 axisLerp 变量是个常量。由于我们使用轴对齐切片，我们知道为当前切片渲染的每个片元沿切片轴都具有完全相同的纹理坐标；也就是说，axisLerp 表示切片在当前体素内的位置，在整个切片上恒定（见图 41-2）。

示例 41-1. 用延迟滤波读取三线性滤波三维纹理的 Cg 函数

这段代码用于图 41-2 的步骤 B。

float4 deferredTex3D(float2 texCoord2D, // 切片纹理坐标
                     const uniform float axisLerp,
                     // 主轴位置
                     uniform sampler2D textureI,
                     // 纹理切片“i”
                     uniform sampler2D textureJ)
// 纹理切片“j”
{
  float4 texValI = tex2D(textureI, texCoord);
  float4 texValJ = tex2D(textureJ, texCoord);
  return lerp(texValI, texValJ, axisLerp);
}

当数据集以三维域的二维切片形式存储时，如果首选的切片轴与当初为存储而切片的轴一致，我们就能方便地对其进行体绘制，如图 41-3 的 A 部分所示。当切片轴垂直于存储切片轴时，数据由二维存储布局中的若干行重建，如图 41-3 的 B 部分所示。

虽然分离的重建遍与滤波遍会带来一些开销，但总体而言我们在实践中观察到 2 倍到 10 倍的加速。图 41-4 给出了用延迟滤波从压缩体格式渲染的实现的计时。可以看到，在某些情况下延迟滤波甚至比最近邻滤波更快。这是因为当每体素采样多于一次时，最近邻滤波会执行冗余的重建。

41.4 为何有效

不用延迟滤波而直接重建并滤波自定义数据格式，其主要问题在于：对某个被渲染的片元，往往有许多相邻片元重建出完全相同的值。随着重建代价上升，这种明显低效所带来的负担会大幅增加。

在可预见的未来，GPU 纹理与滤波引擎的硬连线效率将大大超过「手写」的片元程序三线性滤波。把计算从片元程序上移到合适的内置功能单元，几乎总能带来性能收益。在示例与算法中，我们假定使用三线性插值。不过，即使我们实现更高阶的滤波方案，延迟滤波仍然是很大的收益（见 Hadwiger 等 2001）。随着滤波支撑域增大（即滤波所需的数据样本数增加），重建的冗余（因而代价）也随之增大。延迟滤波保证重建代价每个纹素只付一次。

视内存布局而定，还有其他更微妙的问题会起作用。多维缓存一致性是 GPU 取得出色性能所依赖的重要机制。从分散的内存位置读取多个纹素会造成显著的缓存缺失延迟，从而延长渲染时间。延迟滤波未必能完全避免这种影响，但它确保这类问题每个纹素只发生一次，而不是每个片元八次。

41.5 结论：何时延迟

需要以困难格式表示体数据的情形有两种。第一种是数据以压缩格式存储在 GPU 上，如前文的例子。第二种是三维数据由 GPU 生成（即动态体）。动态体出现在用 GPGPU 技术做仿真、图像处理或分割/变形的时候。当前的 GPU 内存模型要求我们把动态体数据存成一组二维纹理，或存成「扁平三维纹理」（详见本书第 33 章「在 GPU 上实现高效的并行数据结构」）。渲染这组二维纹理需要一种新的基于二维纹理的体绘制变体，只使用前面描述的单一一组二维切片。延迟滤波使你不再需要担心自己的 GPGPU 计算数据结构是否适合交互式渲染。延迟滤波让这些数据格式中的任何一种都能被交互式渲染。

延迟滤波在时间与空间上都很高效，因为它几乎消除了重建代价（每个纹素只付一次），并且是增量的（一次只需两张切片）。即使重建代价可以忽略，增加一遍延迟重建也比在片元程序中为每个片元滤波数据更高效。

延迟滤波的一个缺点是需要把片元程序「拆分」。一般情况下这不成问题，因为纹理读取往往发生在其他计算之前。然而当纹理读取依赖于其他计算时，使用延迟滤波可能需要复杂的多遍划分方案（Chan 等 2002，Foley 等 2004，Riffel 等 2004）。
