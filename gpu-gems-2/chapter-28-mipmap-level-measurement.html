第 28 章　mipmap 层测量

Iain Cantlay
Climax Entertainment

在最初的 GPU Gems 中，Cem Cebenoyan 提出一个问题：「你的用户究竟有没有机会看到你最高的 mip 层？」（Cebenoyan 2004）如果答案是没有，那么把这些用不到的 mipmap 层从显存中换出去，就能提升性能、节省内存。

回答这个问题的一种做法是把 mipmap 换成「伪彩色」版本，然后渲染场景。这种 mipmap 让每个 mip 层都取一种不同且对比鲜明的颜色。图 28-1a 显示了某处带纹理地形的视图；图 28-1b 是同一视图换成伪彩色 mipmap 的结果。尽管视点是一个站在地形上的角色，也很容易看出最高细节的黄色 mip 层几乎看不见。

伪彩色技术对制作美术资源很有用，但需要有人参与。本章说明如何用 GPU 把这一过程自动化。随后这项技术可以推广到更一般的问题：哪些 mip 层是可见的？

我们基于 GPU 的做法效率足够高，可以用在游戏引擎里。于是可见的 mip 层可以动态反馈给引擎的纹理管理程序，以减少内存占用。省下的内存可以用来提高别处的纹理分辨率，让场景更丰富。我们最近把这项技术用于 Climax 的 Leviathan 引擎中的地形，节省了 80% 的纹理内存，而视觉质量没有可察觉的损失。

28.1 哪一层 mipmap 可见？

GPU 对 mipmap 层的选择取决于许多因素：屏幕分辨率、抗锯齿设置、纹理滤波选项、各向异性、驱动的巧妙优化、到带纹理多边形的距离，以及多边形的朝向。这些因素大多在用户掌控之下，在在线多人游戏这类高度不可预测的情境中尤其如此。

理论上，所有因素都能在 CPU 上分析，从而让我们预测 GPU 对 mip 层的选择。关于 mipmap 的理论，可参见 Williams 1983。但如果我们想在游戏这类应用里运用这些数学，会有若干实际困难。

首先，并不总能知道所有变量。抗锯齿和纹理滤波选项常常可以从控制面板覆盖，应用很难或根本无法确定这些设置。

其次，尽管 mipmap 的理论广为人知，GPU 却比理论复杂得多。它们含有通常复杂且专有的优化与增强。

最后，现代场景的复杂度使 CPU 上高效的实时分析无从谈起。计算机图形教材讲述的是单个多边形的 mipmap 数学。当前的 3D 应用所显示的物体用到数万到数十万个多边形。虽然我们可以分析一个十万三角形的角色网格中各多边形的朝向和屏幕空间尺寸，但这样做会白白消耗大量 CPU 算力。

28.2 GPU 出手

幸运的是，GPU 恰恰擅长分析十万三角形的网格。它没有哪个显式函数会报告画这个网格将用到哪些 mip 层，但每次绘制物体时它都在隐式地做这项分析。[1] 结果并不以我们需要的形式显式给出，但它隐含在帧缓冲中出现的像素里。诀窍在于设法分析这些像素，把它们变成「mipmap 层 0 和 1 不需要」这样形式的结果。

28.2.1 统计像素

回想引言中举的伪彩色例子。我们的做法大致上是把这一过程自动化。

我们可以给纹理上伪彩色、渲染物体、再把帧缓冲复制到系统内存。然后统计各种颜色的像素，就能得到对可见 mip 层的分析。这确实可行，但并不快。目前从显存复制到系统内存慢得无法接受。注意「目前」二字：PCI Express 改变了显存到系统内存传输的速度。即便如此，用 CPU 统计帧缓冲像素很可能仍然低效。

不过 GPU 可以用遮挡查询高效地统计像素。（严格说统计的是可见片元，但这一区别对我们的做法没有影响。）遮挡查询给出一次绘制调用中有多少像素通过了 z 缓冲测试。这个测试不能直接用来分析我们的颜色帧缓冲，但只要把问题换个说法，就能让它发挥作用。

第一层 mip 可见吗？

先回到更简单的初始问题：最高 mip 层可见吗？如何用遮挡查询来回答？

幸运的是，遮挡查询会考虑管线中的所有渲染状态，其中也包括 alpha 测试。我们的做法正是利用这一点：创建一张特殊的校准纹理，最高层用不透明 alpha（1），其余层用半透明 alpha（0）；启用 alpha 测试并把参考值设为 0；用这张校准纹理替换原纹理渲染目标物体；为这次绘制调用创建遮挡查询。alpha 测试会丢弃完全透明的像素、保留 alpha 大于 0 的像素。于是只有采样了最高 mipmap 层的像素才会被遮挡查询统计到。

图 28-2 展示了在一片地形上的结果。图 28-2a 是原地形；图 28-2b 是所有 mipmap 层都用伪彩色且 alpha 不透明的版本；图 28-2c 是同一物体，只在顶部黄色 mipmap 层使用不透明 alpha。地形较远的部分（以及较平坦的部分）不采样最高 mipmap 层，因此输出的 alpha 值完全透明（0），这些像素不会被渲染。

推广到多个 mipmap 层

我们可以用遮挡查询判断 mipmap 的任意给定层是否可见。要确定哪一层可见，只需对我们关心的每个 mipmap 层重复这一过程。我们的目标是节省纹理内存，所以不必测量 mipmap 的所有层。只要能省下最高的那几层，收益就很显著。例如一张未压缩的 512x512x4 字节纹理，最高的四层分别占 1 MB、256 kB、64 kB 和 16 kB 内存（即 100%、25%、6.3% 和 1.6%）。第三层及其以下各层都无关紧要。

我们不必为每个被测层各做一张校准纹理，而是用一张纹理，让各层依次填入递减的 alpha 值。图 28-3 给出一张示例校准纹理。这样线性 mipmap 滤波会在最高四层之间产生连续的 alpha 梯度，如图 28-4 所示。

算法只关心 alpha 值；各层中不同的 RGB 颜色用于说明和调试。

我们可以让每个 mip 层针对不同的 alpha 参考值做测试。不过我们选择保持 alpha 测试不变，改用像素着色器对每层的 alpha 值做不同的偏移和缩放：

ps .1.1 tex t0 mov r0.rgb, t0 + sub_x4 r0.a, t0, c0

对我们测量的四层，我们分别把 c0 设为 0.75、0.5、0.25 和 0.0。这样正在测量的那一层的 alpha 值就被重映射到 [0,1] 区间。在像素着色器里缩放数值，意味着每层都用上了 alpha 测试中可能用到的整个取值区间。

我们还创建一个基准参考查询，用来在完全不使用 alpha 测试的情况下统计测试物体的所有像素。这个值在解释结果时是必需的。

解释结果

从视觉上看，这些绘制调用的结果可能像图 28-5。遮挡查询为每一层以及参考查询返回一组像素计数。通常类似下面这样：

我们从高层往低层遍历，找出第一个超过显著性阈值的层，就认定它为第一个可见层。阈值对应 mip 层在输出中的视觉显著性。默认情况下我们用参考值的 15% 作为阈值。图 28-6 显示阈值低时视觉保真度损失多么小，而随着阈值提高，图像逐渐变得更模糊。

使用结果

既然测出了某个物体上显示的是哪一层 mip，我们该如何利用这个结果？在 Climax 的 Leviathan 引擎（Climax 2004）中，我们从两方面使用这些结果。

第一，我们使用 Direct3D 的托管资源。因此可以用 IDirect3DBaseTexture9::SetLOD 把 mip 层告诉资源管理器。仅仅调用这个函数，就能让 Direct3D 省下显存。（我们强烈建议使用托管资源。）

第二，我们的 Leviathan 引擎支持一款大型多人在线游戏。与推荐做法相反，我们必须在游戏的渲染循环运行期间即时生成大部分纹理。例如玩家角色必须在任意时刻按需载入。因此我们用纹理 mip 层测量来驱动一部分即时纹理生成。除了节省显存，这也省下 Direct3D 保留的系统内存副本，还省掉了生成无用层的开销。

28.2.2 引擎中的实际考量

测量 mipmap 层背后的概念很简单，但在实时引擎这样的实际环境中应用这个想法并不那么简单。Climax 的 Leviathan 引擎中的实现经过了一年多时间、若干次修订。

发出修改过的绘制调用

要测量某个物体的 mip 层，我们必须用改过的渲染状态把它重画一遍。必须覆盖以下几项：

  1. 像素着色器
  2. alpha 测试的渲染状态（D3DRS_ALPHATESTENABLE、D3DRS_ALPHAFUNC 和 D3DRS_ALPHAREF）
  3. 纹理

此外，还要用 D3DRS_COLORWRITEENABLE 确保校准物体不出现在帧缓冲中。幸运的是，禁用颜色写入并不影响遮挡查询的结果。

Leviathan 引擎的设计天然支持以这种方式覆盖状态。每次绘制调用都会被缓存下来，存成一串抽象状态。因此任何绘制调用都能以略微改动过的渲染状态列表重新发出。

我们可能还想改动另一个渲染状态：视图变换。按现在的样子，位于视锥之外的物体不会被测量。可以把视图变换对准每个物体，这样即使它们在视锥之外也能测量。

摊薄开销

测量物体的 mip 层并不便宜：你必须把目标物体重画好几次。要把游戏的绘制调用数乘以四五倍，我们极不可能承受得起。

幸运的是，不必每帧测量每个物体；随着物体相对位置变化，纹理 mip 层往往变化缓慢且有规律。在我们的游戏中，我们发现把所有待测物体放进一个轮转队列、每帧测一个就够了。我们测四层 mip，所以开销只有每帧五次绘制调用。在典型游戏条件下我们测不出性能影响。

轮转队列会带来一些延迟：移动的物体有时会出现肉眼可见的纹理分辨率跳变。更精细的管理算法大概能解决这个问题；例如可以用优先队列，更频繁地测量快速移动的物体。不过我们在游戏中没有这么做，因为发现这种延迟很少看得出来。

RGB 校准数据

我们的算法只用到校准纹理的 alpha 通道。但这并不意味着我们把 RGB 值留空。它们有两个用处。

第一，RGB 数据对可视化调试有用；我们已经用彩色 mipmap 层画了许多图，实践中伪彩色在开发应用时同样有用。

第二，众所周知驱动会分析纹理，以便让滤波适应某张纹理的特性。若真如此，校准纹理最好能代表我们想测量的实际纹理。实践中我们用一张有代表性图像的 RGB 值填充它，而不是留空。

28.2.3 扩展

放大与二的幂次的腾挪

就目前而言，我们的校准纹理必须与被测纹理尺寸一致。把校准纹理的尺寸相对被测纹理加倍，就能检测一定程度的纹理放大。当目标纹理需要放大滤波时，校准纹理多出的那一层就会显示出来。

减小视口尺寸会得到类似结果。总的说来，我们可以在视口尺寸、校准纹理尺寸和被测层数之间权衡。实践中，同时等量减小视口尺寸和校准纹理尺寸可能合理，因为这样能降低测试的开销。

mip 层速度

设想你在赛车游戏里开车，正高速逼近一堵墙。墙面垂直于视线方向。图 28-7 给出 mip 层随距离的变化。硬件的线性 mipmap 滤波会逐渐改变各可见层的比例，而我们的测量给出阶梯状结果，因为它只是一个简单的阈值判定。

改变校准纹理可以提取更多信息。如图 28-8 所示，我们把一层内的纹素值随机化。每层中的值均匀分布在纹理总范围的某个四分之一区间内。

图 28-9 以直方图形式给出第二层。

每层并不是各自不同的随机图案：它们都是第 3 层图案放大并偏移后的版本。结果是图 28-4 中的数值梯度在每个纹素上被随机偏移。于是纹理总有一部分在跨过我们的阈值判定。

现在，当我们改变到被测物体的距离时，任何微小变化都会让一些被测纹素跨过阈值测试。图 28-7 的阶梯状行为就被平滑掉了。

起初我们以为改造后的校准纹理也许能让我们测出每个 mipmap 层对输出图像的贡献程度。虽然对简单几何体（例如垂直于视线方向的平面多边形）这是可行的，但真正有用的物体行为更复杂，我们认为这些像素计数难以分析。不过改造后的校准纹理可以给出 mipmap 层如何变化的度量；知道 mipmap 层在升高、降低还是不变，可能有用。

导数指令

使用 Shader Model ps_2_x 或更高版本时，可以用 dsx 和 dsy 指令在像素着色器中直接算出 mip 层（也可以用 HLSL 的 ddx() 和 ddy() 调用）。这样就能不用校准纹理，以着色器更复杂为代价减少纹理带宽。从 GPU 取回结果仍然是个问题，需要若干次遮挡查询。

我们没有在 Leviathan 中研究这种做法，因为我们用统一的算法来支持较低的像素着色器模型。

28.3 示例结果

有用的地形往往很平坦，而且在站在地形上的典型视点中，多边形常常是侧对着看的。因此所需的 mipmap 层往往较低。不过任何非平坦表面都会需要更高的 mipmap 层。图 28-10 给出一个典型例子：同一片地形从两个不同位置观看。在视点 A 能看到崖壁，它所需的 mipmap 层比视点 B 更高，尽管两个视点到它的距离相同。

28.4 结论

可以用 GPU 确定正在使用哪些纹理 mipmap 层。我们的做法依靠 GPU 自己的纹理映射硬件产生这一信息。这项技术有两个优点：第一，我们不需要确切知道 GPU 如何选择可见 mip 层。本章有意回避了关于 mipmap 滤波的任何数学讨论，因为按我们的做法并不需要。用 GPU 的第二个优点是它能给出确定而准确的答案，考虑到决定使用哪些 mip 层的所有复杂因素。

这项技术未必适用于每一种应用。例如在赛车游戏中，玩家常常沿固定赛道线性前进，他们能做的、会影响所需 mipmap 层的移动很有限。这种情况下可以用效率较低的方法静态确定所需的 mipmap 层。

然而作为大型多人在线游戏的开发者，我们面对新奇的挑战。我们的玩家比许多其他游戏中的玩家拥有大得多的自由度，结果就是一个无法预先预测纹理尺寸的环境。我们成功地把本章所述技术用于大幅降低内存占用，而生成的图像没有可察觉的退化。
