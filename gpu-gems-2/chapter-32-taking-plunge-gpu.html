第 32 章　投身 GPU 计算

Ian Buck
Stanford University

本章以及本书许多其他章节都展示了如何把 GPU 当作通用计算引擎，但要记住，GPU 主要是为交互式渲染而不是计算设计的。因此，试图把 GPU 当作计算引擎时，你可能会遇到一些绊脚石。GPU 与 CPU 在能力与性能上都有显著差异，从存储带宽、浮点数表示一直到间接存储访问。由于我们移植应用到 GPU 的目标是超过 CPU 实现，理解这些差异并为 GPU 最优地组织计算就很重要。本章讨论其中一些差异，并说明如何编写快速高效的基于 GPU 的应用。

32.1 选择快速算法

既然 GPU 主要为渲染设计，其存储与计算单元都是为着色优化的，而不是为信号处理、复杂线性代数、光线追踪或我们可能想塞进着色器管线的任何东西这类通用计算优化。本节考察 GPU 的一些性能特征，并与 CPU 对比。理解这些特征有助于我们判断某个算法能否利用 GPU 的能力，若能，又该如何为 GPU 最好地组织计算。

32.1.1 局部性，局部性，局部性

在 CPU 上获得良好存储性能，关键始终在于引用的局部性。GPU 也是如此，但有几处重要差异。图 32-1 展示了在 GeForce 6800 Ultra 存储系统上读取单分量浮点纹理数据，与 3.0 GHz Pentium 4 相比在三种访问模式下的性能：带缓存（反复读同一存储位置）、顺序和随机。显然 GPU 的顺序存储访问性能远高于 CPU。这并不奇怪，考虑到 GPU 的关键任务之一就是用连续的纹理数据填充存储区域。不过从计算角度看，要获得峰值存储性能，计算必须围绕顺序存储访问来组织，否则就会因随机存储读取而遭受巨大的性能损失。这对加速线性代数运算（例如把两个大向量相加，数据天然按顺序访问）是好消息。然而，需要大量指针追逐的算法会因随机访问性能差而受累。

GPU 与 CPU 在存储性能上的另一个重要区别是缓存的作用。与 CPU 上的缓存不同，GPU 纹理缓存主要是为加速纹理滤波而存在的。因此 GPU 缓存只需有纹理采样器滤波核那么大（通常只有几个纹素），这对通用计算来说太小了。GPU 缓存格式还针对二维局部性做了优化，而这并不总是我们想要的。这与 Pentium 4 的缓存形成对比：后者运行在高得多的时钟频率下，容纳数兆字节数据。此外，Pentium 4 能缓存读和写两种存储操作，而 GPU 缓存是为只读纹理数据设计的。任何写入存储器的数据（也就是帧缓冲）都不经过缓存，而是直接写出到存储器。

这对 GPU 上的通用计算意味着什么？可读写的 CPU 缓存让程序员能优化算法，使其主要在缓存中运行。例如，如果你的应用数据集相对较小，它可能完全装进 Pentium 4 缓存。即使数据集更大，应用作者也可以把计算「分块」，确保大多数读写都发生在缓存中。相比之下，GPU 缓存容量有限且只读，处于明显劣势。因此，受顺序或随机读取带宽限制更多的应用——例如把两个大向量相加——移植到 GPU 上会看到显著得多的性能提升。向量加法这个例子顺序读写大向量且不复用数据——正是 GPU 上的最优访问模式。

32.1.2 让计算说了算

存储访问模式并不是判断某个算法在 GPU 上还是 CPU 上跑得更快的唯一决定因素。当然，如果应用以计算为主，我们如何访问存储就没那么重要。计算速率正是 GPU 明显胜过 CPU 的地方。如今的 GPU 仅片元程序硬件就提供超过 60 gigaflops（每秒数十亿次浮点运算，即 Gflops）的算力。相比之下，Pentium 4 处理器只有 12 Gflops。[1] 因此，只要 GPU 程序中有足够的计算，存储性能上的任何差异都应察觉不到。

但需要多少计算才不至于受限于存储性能？要回答这个问题，得先回顾 GPU 上存储访问的行为。当我们发出纹理取数指令时，存储读取由纹理子系统处理，它很可能要从片外存储器取出纹素。为隐藏纹理取数的时间，也就是延迟，GPU 在发出纹素读取请求之后就开始处理下一个待着色片元。当纹理数据返回时，GPU 暂停下一个片元的工作，回头继续着色原来的片元。因此，如果我们希望受限于 GPU 的计算性能而不是存储，程序就需要包含足够的算术指令来覆盖我们所做纹理取数的延迟。

正如第 29 章「流式架构与技术趋势」29.1.2 节所解释的，GPU 每从存储器读取一个值所能执行的浮点运算次数在过去几年里不断增加，目前达到七到十倍。从这一落差，我们可以就哪类基于 GPU 的应用可能胜过其 CPU 对应实现得出一些结论。为避免受限于存储系统，我们必须考察给定算法的算术操作与存储操作之比。这个比值称为算法的算术强度。如果算法算术强度高，它执行的算术操作就远多于存储操作。由于如今 GPU 的计算性能是 CPU 的五倍以上，算术强度高的应用很可能在 GPU 上表现良好。此外，我们也更可能用算术指令掩盖任何存储取数的开销。

32.1.3 考虑下载与读回

把 GPU 用作计算平台时最后一个性能考量是下载与读回的问题。在开始在 GPU 上计算之前，我们需要把初始数据传到显卡上。同样，如果 CPU 需要计算结果，我们得把数据从 GPU 读回。在 CPU 上做计算则不需要这些额外操作。与 CPU 比较时，必须考虑下载与读回数据的性能影响。

考虑在 GPU 上把两个大向量相加的例子。执行一段只是取两个浮点值、相加并写出结果的片元程序，肯定会比 CPU 实现跑得快，原因前面已解释。不过，如果把下载向量数据和把结果读回 CPU 的开销也加上，那还不如直接在 CPU 上做向量加法。当今 PCI Express 显卡的纹理下载与读回峰值速率最高约为 3.2 GB/sec。一块 3.0 GHz 的 Pentium 4 能以约 700 megaflops（每秒数百万次浮点运算，即 Mflops）的速率把两个大向量相加。[2] 所以在我们把两个向量都下载到 GPU 之前，CPU 可能早已完成这次向量加法。

要避免这一损失，我们需要把数据下载与读回的开销摊销掉。对仿真应用来说这问题不大，因为这类算法大多要在返回之前对数据迭代多次。不过，如果你打算用 GPU 加速线性代数算子（例如向量加法），请确保你在数据上做的操作足够多，足以抵消下载与读回的额外开销。

还有一个考量是像素格式不同。并非所有纹理与帧缓冲格式都以相同速度工作。某些情况下，图形驱动可能不得不用 CPU 把用户提供的 RGBA 数据转换为 GPU 的原生格式，后者可能是 BGRA。这会显著影响下载与读回性能。原生格式因厂商和不同 GPU 而异。最好试验多种格式，找出最快的那种。

32.2 理解浮点

如今的 GPU 用浮点运算完成全部计算。台式 CPU 一般只支持一种浮点标准，而 GPU 厂商实现了多种浮点格式。理解这些格式之间的差异，既能帮你判断应用能否产生准确结果，也能帮你避开一些较常见的浮点运算错误——在 GPU 上这些错误比在 CPU 上更具隐蔽性。

先回顾一下浮点数的表示。一个浮点数用如下表达式表示：

符号 x 1.尾数 x 2(指数-偏移)。

考虑表示数值 143.5，它在科学计数法中对应 1.435 x 102。其二进制科学表示为 1.00011111 x 2111。于是尾数设为 00011111（前导的 1 隐含），指数以 127 为偏移存储（偏移量由具体浮点格式标准规定），对应 10000110。不同浮点格式分配给尾数与指数的位数不同。例如在多数 CPU 使用的 IEEE 754 标准中，一个 32 位浮点值由 1 个符号位、8 位指数和 23 位尾数组成。尾数与指数可用的位数决定了我们表示数值的精确程度。对 IEEE 754，143.5 可精确表示；而 143.98375329 被舍入为 143.98375，因为尾数只有 23 位可用。如今可用的 GPU 浮点格式如下：

  • NVIDIA fp32：23 位尾数，8 位指数
  • ATI fp24：16 位尾数，7 位指数
  • NVIDIA fp16：10 位尾数，5 位指数

这对基于 GPU 的应用意味着什么？首先，NVIDIA fp32 格式模仿 CPU，因此以该格式完成的计算应精确到约第七位有效数字，这是 23 位尾数的极限。相比之下，ATI fp24 应精确到第五位有效数字，而 NVIDIA fp16 格式精确到第三位。虽然这类较低精度对着色计算完全合理——那里精确的颜色值并不关键——但这些格式引入的误差会严重影响数值应用。表 32-1 展示了用不同格式表示数值 143.98375329 的精确程度。

32.2.1 地址计算

处理地址计算时，这种有限的浮点精度会造成一个特别麻烦的后果。设想我们要为一个存放在二维纹理中的一维大数组计算地址。由于浮点运算精度有限，计算一维地址时，数组中某些元素可能变得无法寻址。例如，使用 NVIDIA 的 fp16 浮点数时，我们无法寻址第 3079 个元素，因为 10 位尾数能表示的最接近的数是 3078 和 3080。这类差一的寻址错误很难追查，因为并非所有计算都会触发它们。即使使用 24 位浮点数，也无法用一维地址寻址一张大尺寸二维纹理中的全部像素。表 32-2 给出各种格式在整数值开始被跳过之前所能表示的最大计数值。

32.3 实现分散写

用 GPU 做通用计算的程序员最早发现的事情之一，是 GPU 无法在片元程序中执行分散写操作。分散写操作又称间接写入，指从计算得到的地址出发的任何内存写操作。例如 C 代码 a[i] = x 就是一个分散写操作，我们把值 x 从计算得到的地址 i 「分散」写入数组 a。即便最基础的算法里也极其常见分散写。例如快速排序、散列、直方图，以及任何必须从计算地址写入内存的算法。

要理解分散写为何难以在片元程序中实现，先看分散写的反面：聚集读。聚集读是间接读取操作，例如 x = a[i]。在片元程序中实现聚集读很直接，因为它对应依赖纹理读取。例如 a 是一张纹理，i 是任意计算值，而 a[i] 就是一条简单的纹理取数指令。在片元程序中实现分散写（a[i] = x）就没那么简单，因为没有纹理写指令。事实上，我们在 GPU 中能做的内存写只发生在预先算好的片元地址上，而片元程序无法改变这个地址。每个片元都写入帧缓冲中的固定位置。本节讨论几种绕开 GPU 这一限制的办法，供需要分散写数据的应用使用。

32.3.1 转换为聚集读

在某些情况下，可以把分散写转换为聚集读。为此，我们以在 GPU 上仿真弹簧-质量系统为例。

图 32-2 画出一个简单的质量-弹簧系统：我们遍历每根弹簧，计算弹簧施加的力，并把这份力累加到与弹簧相连的质量上。在 GPU 上实现这个算法的麻烦在于，弹簧的力被分散写入 mass_force 数组。这种分散写无法在片元程序内完成。

我们可以对先前被分散写入的那个数组再做一遍处理，从而把分散写变成聚集读。如图 32-3 所示，我们不再分散写入各力，而是先把弹簧力输出到内存。第二遍遍历所有质量，聚集读影响该质量的各力值。[3] 一般来说，只要连接关系是静态的，这项技术就成立。由于仿真过程中弹簧的连接关系不变，我们确切知道每个质量需要从力数组的哪个元素聚集读取。

但如果分散写的地址不固定呢？例如，我们实现一个粒子仿真，把空间划分为由长方体体素组成的网格。我们希望算出空间每个体素的净粒子速度。这类操作在处理水平集时很常见。图 32-4 给出一种典型实现。

我们仍可用地址排序把这类分散写转成聚集读。算法与前面的例子类似，只是输出待分散写的数据时，还把分散写地址一并输出。然后按地址对这些「数据–地址」对排序。这样就把所有待分散写的数据排到数组的连续位置上。最后遍历目标数组的每个元素，用二分搜索取出要写入该位置的数据。见图 32-5。

32.3.3 渲染点

片元程序无法改变写入的地址，但顶点程序本质上就能指定在输出图像的何处渲染。因此可以用顶点程序执行分散写。这项技术相当直接：应用只需提交要渲染的点，顶点程序从纹理中取出分散写地址，并连同相应的分散写数据一起把它赋给该点的目标地址。如果 GPU 不支持顶点纹理，可以用顶点缓冲对象与像素缓冲对象扩展把纹理数据重映射到顶点数组。这种做法的缺点在于，渲染点并不能高效利用光栅化硬件。另外，你还得留意分散写地址的冲突（即两个点落到同一位置）。解决冲突的简单办法有两种：用 z 缓冲为它们排定优先级，或用混合操作把数值合并。

总之，若需要分散写，凡是分散写地址固定的场合，都应把它转成聚集读。如果分散写地址不固定，可以用地址排序或点渲染。哪个更快可能因 GPU 而异；但一般来说，若要往一大片内存区域里做的分散写很少，可以考虑渲染点。用点渲染分散写数据所需的时间只取决于待分散写的数值个数。若要分散写的数据很多，用地址排序法可能更好，可避免把数据回读到 CPU，也不受 GPU 渲染点速率的限制。

32.4 结论

本章触及了程序员从基于 CPU 的计算转向基于 GPU 的计算时会遇到的一些挑战。要胜过 CPU，需要理解 GPU 在性能上的长处，特别是偏好内存访问连续、计算与内存操作之比较高的一类算法。此外，我们讨论了 GPU 上可用的几种浮点格式，以及它们如何影响程序的正确性。最后，我们展示了如何绕开 GPU 对分散写支持有限的问题。在你探索如何用 GPU 加速自己的算法时，希望本章所述的策略能帮你借助高效的 GPU 计算改进应用。
