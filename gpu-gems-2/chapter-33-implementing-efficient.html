第 33 章　在 GPU 上实现高效的并行数据结构

Aaron Lefohn
University of California, Davis

Joe Kniss
University of Utah

John Owens
University of California, Davis

现代 GPU 在计算史上第一次把数据并行、流式的计算平台装进了几乎所有台式机与笔记本电脑。近期不少学术论文——以及本书的其他章节——表明，这些流式处理器能加速的应用范围远比它们最初设计的实时渲染要广。不过，要利用这份算力，就得采用一套对许多程序员都很陌生的、根本不同的编程模型。本章试图揭开 CPU 与 GPU 编程之间最根本的差异之一：内存模型。与传统的基于 CPU 的程序不同，基于 GPU 的程序在何时、何处、如何访问内存上有多重限制。本章概述 GPU 内存模型，并说明多维数组、结构体、链表与稀疏数组这些基本数据结构如何在这一数据并行编程模型中表达。

33.1 用流编程

现代图形处理器如今能加速的东西远不止实时计算机图形。图形处理器通用计算（GPGPU）这一新兴领域的近期工作表明，GPU 能加速的应用多种多样，包括流体动力学、高级图像处理、照片级真实渲染，甚至计算化学与计算生物学（Buck et al. 2004, Harris et al. 2004）。要把 GPU 用于实时渲染以外的目的，关键在于把它看作一台流式的数据并行计算机（见本书第 29 章「流式架构与技术趋势」，以及 Dally et al. 2004）。我们在 GPU 程序中组织计算与访问内存的方式，深受这一流式计算模型的影响。因此在讨论基于 GPU 的数据结构之前，我们首先简要概述这一模型。

GPU 这类流式处理器的编程方式，与当今 CPU 这类串行处理器根本不同。大多数程序员熟悉的是这样一种模型：在程序的任何时刻都能写入内存的任意位置。相比之下，为流式处理器编程时，我们访问内存的方式要规整得多。在流模型里，程序被表达为对数据流的一系列操作，如图 33-1 所示。流（即有序的数据数组）中的元素由内核（即一个小程序）中的指令处理。内核作用于流的每个元素，并把结果写入输出流。

流编程模型的这些限制让 GPU 能并行执行内核，从而同时处理许多数据元素。之所以能获得这种数据并行性，是因为保证了对一个流元素的计算不会影响同一流中另一个元素的计算。因此，内核计算中可用的值只有该内核的输入和全局内存读取的结果。此外，GPU 要求各内核的输出相互独立：内核不能随机写入全局内存（换句话说，只能写入输出流中单个流元素的位置）。这一模型带来的数据并行性，是 GPU 相对串行处理器获得加速的根本原因。

下面两段示例代码展示如何把串行程序改写成数据并行的流程序。第一段是串行处理器上遍历数组（例如图像中的像素）的循环。注意循环体中的指令每次只针对单个数据元素：

for (i = 0; i < data.size(); i++)
loopBody(data[i])

下一段用伪代码给出同一段代码在流式处理器上的写法：

inDataStream = specifyInputData() kernel = loopBody() outDataStream =
    apply(kernel, inDataStream)

第一行指定数据流。在我们的图像示例中，流就是图像里的全部像素。第二行指定计算内核，它其实就是第一段中的循环体。最后，第三行把内核应用到输入流的所有元素上，并把结果存入输出流。在图像示例中，这一操作会处理整幅图像，并产生一幅变换后的新图像。

当前的 GPU 片元处理器在先前所述的流模型之外，还有一项额外的编程限制。当前的 GPU 片元处理器是单指令多数据（SIMD）并行处理器。这在传统上意味着所有流元素（即片元）必须由同一串指令处理。近期的 GPU（支持 Pixel Shader 3.0 的那些 [Microsoft 2004a]）略微放宽了这一严格的 SIMD 模型，允许变长循环和有限的片元级分支。但硬件在根本上仍是 SIMD，因此要让分支高效执行，片元之间的分支必须在空间上保持一致（更多信息见本书第 34 章「GPU 流控惯用法」）。当前的顶点处理器（Vertex Shader 3.0 [Microsoft 2004b]）是多指令多数据（MIMD）机器，因此执行内核分支比片元处理器更高效。片元处理器的 SIMD 架构虽然灵活性较差，却非常高效且成本低廉。

由于目前几乎所有 GPGPU 计算都在功能更强的片元处理器上完成，基于 GPU 的数据结构必须适配片元处理器的流式 SIMD 编程模型。因此，本章的所有数据结构都以流的形式表达，对这些数据结构的计算则以 SIMD、数据并行的内核形式给出。

33.2 GPU 内存模型

图形处理器有自己的内存层次，与串行微处理器所用的层次类似，包括主存、缓存和寄存器。不过，这一内存层次是为加速符合流编程模型的图形操作而设计的，并非为通用的串行计算。此外，OpenGL 和 Direct3D 这类图形 API 进一步把这份内存的使用限制在顶点、纹理、帧缓冲等图形专用图元上。本节概述当前的 GPU 内存模型，以及基于流的计算如何嵌入其中。

33.2.1 内存层次

图 33-2 显示 CPU 与 GPU 合并后的内存层次。GPU 的内存系统在现代计算机的内存层次中形成了一个分支。GPU 与 CPU 一样，拥有自己的缓存和寄存器，用于在计算过程中加速数据访问。但 GPU 还拥有自己的主存和自己的地址空间——这意味着程序员必须在开始执行程序之前，显式地把数据复制到 GPU 内存中。这一传输在传统上是许多应用的瓶颈，但新的 PCI Express 总线标准的出现，可能使 CPU 与 GPU 之间共享内存在不久后变得更为可行。

33.2.2 GPU 流类型

与 CPU 内存不同，GPU 内存有多项使用限制，且只能通过图形编程接口的抽象来访问。可以把每一种抽象看作一种不同的流类型，各有自己的访问规则。GPU 程序员能看到的三种流是顶点流、帧缓冲流和纹理流。第四种流即片元流，完全在 GPU 内部产生和消耗。图 33-3 显示现代 GPU 的管线、三种用户可访问的流，以及每种流在管线中可用的位置。

顶点流

顶点流通过图形 API 指定为顶点缓冲。这些流保存顶点位置和各种逐顶点属性。这些属性传统上用于纹理坐标、颜色、法线等，但也可以用来为顶点程序提供任意的输入流数据。

顶点程序不允许对输入顶点做随机索引。直到不久前，顶点流只能通过从 CPU 向 GPU 传输数据来更新。GPU 不允许写入顶点流。不过，近期的 API 增强已使 GPU 能写入顶点流，做法是「复制到顶点缓冲」或「渲染到顶点缓冲」。前一种技术把渲染结果从帧缓冲复制到顶点缓冲；后一种技术则把渲染结果直接写入顶点缓冲。新近加入的 GPU 可写顶点流，第一次让 GPU 能把流结果从管线末端回送到管线起点。

片元流

片元流由光栅化器产生，由片元处理器消耗。它们是片元程序的流输入，但程序员无法直接访问，因为它们完全在图形处理器内部产生和消耗。片元流的值包括顶点处理器输出的全部插值结果：位置、颜色、纹理坐标等。与逐顶点流属性一样，传统上用于纹理坐标的逐片元值，现在可以用于片元程序所需的任何流值。

片元程序无法随机访问片元流。允许随机访问片元流会在片元流元素之间造成依赖，从而破坏编程模型的数据并行保证。如果算法需要随机访问片元流，必须先把该流保存到内存并转换为纹理流。

帧缓冲流

帧缓冲流由片元处理器写入。传统上它们用于保存供屏幕显示的像素。不过，流式 GPU 计算用帧缓冲保存中间计算阶段的结果。此外，现代 GPU 能同时写入多个帧缓冲表面（即多个 RGBA 缓冲）。当前 GPU 每遍渲染最多可写入 16 个浮点标量值（这一数值预计会在未来硬件中提高）。

片元程序和顶点程序都无法随机访问帧缓冲流。但 CPU 可以通过图形 API 直接读写它们。最后，近期的 API 增强允许把一遍渲染直接写入这些流类型中的任意一种，从而开始模糊帧缓冲、顶点缓冲与纹理之间的界限。

纹理流

纹理是唯一能被片元程序随机访问的 GPU 内存，在支持 Vertex Shader 3.0 的 GPU 上也能被顶点程序随机访问。如果程序员需要随机索引顶点流、片元流或帧缓冲流，必须先把它转换成纹理。CPU 或 GPU 都可以读写纹理。GPU 写入纹理有两种方式：不渲染到帧缓冲而直接渲染到纹理，或把数据从帧缓冲复制到纹理内存。

纹理声明为一维、二维或三维流，并分别用一维、二维或三维地址寻址。纹理也可以声明为立方体贴图，它可以当作六个二维纹理组成的数组来处理。

33.2.3 GPU 内核的内存访问

顶点程序与片元程序（内核）是现代 GPU 的主力。顶点程序作用于顶点流元素，并把输出送往光栅化器。片元程序作用于片元流，并把输出写入帧缓冲。这些程序的能力由它们能执行的算术运算和允许访问的内存决定。GPU 内核可用的算术运算种类正在接近 CPU，但内存访问限制仍有很多。如前所述，其中许多限制是为了保住 GPU 维持速度优势所需的并行性。另一些限制则是 GPU 架构演进过程中留下的，几乎肯定会在后续几代中放宽。

下面列出支持 Pixel Shader 3.0 与 Vertex Shader 3.0 功能的 GPU 上，顶点内核与片元内核的内存访问规则（Microsoft 2004a, b）：

  • 不能访问 CPU 主存；不能访问磁盘。
  • GPU 上没有栈，也没有堆。
  • 可从全局纹理内存随机读取。
  • 从常量寄存器读取。
    - 顶点程序可以使用常量寄存器的相对索引。
  • 对临时寄存器读写。
    - 寄存器对正在处理的流元素是局部的。
    - 寄存器不支持相对索引。
  • 从流输入寄存器流式读取。
    - 顶点内核从顶点流读取。
    - 片元内核从片元流（光栅化器的结果）读取。
  • 流式写入（仅在内核末尾）。

    - 写入位置由元素在流中的位置决定，固定不变。

    不能写入计算地址（即没有分散写）。

    - 顶点内核写入顶点输出流。

    最多可写入 12 个四分量浮点值。

    - 片元内核写入帧缓冲流。

    最多可写入 4 个四分量浮点值。

由前面这套规则和 33.2.2 节所述的流类型，还能引出另一种访问模式：指针流（Purcell et al. 2002）。指针流源于把任意输入流用作纹理读取地址的能力。图 33-4 表明，指针流就是取值为内存地址的流。如果指针流是从纹理读取的，这项能力称为依赖纹理。

33.3 基于 GPU 的数据结构

前面几节用优雅的抽象描述了 GPU 及其编程模型，现在我们深入当前 GPU 上真实数据结构的具体细节。33.1 与 33.2 节的抽象对这里的数据结构依然适用，但当前 GPU 的架构限制使实际实现略微复杂一些。

我们先描述基本结构的实现：多维数组和结构体。随后在 33.3.3 与 33.3.4 节转向更高级的结构：静态与动态稀疏结构。

33.3.1 多维数组

GPU 已经提供了一维、二维、三维纹理，为什么还要专门讲多维数组？有两个原因。第一，当前 GPU 只提供二维光栅化和二维帧缓冲。这意味着唯一能方便更新的纹理是二维纹理，因为它是二维帧缓冲的自然替代品。[1] 第二，纹理目前对每个维度上的尺寸都有限制。例如，当前 GPU 不支持元素数超过 4,096 的一维纹理。如果 GPU 能写入任意 N 维（N = 1, 2, 3, …）帧缓冲且不受尺寸限制，这一节就没有必要了。

受这些限制，采用最近邻滤波的二维纹理几乎成了所有基于 GPGPU 的数据结构的基底。[2] 注意，直到不久前，纹理每个维度上的尺寸还被要求为 2 的幂，所幸这一限制已经取消。

下面所有例子都用地址转换把 N 维数组地址转成二维纹理地址。尽管把这一地址转换的开销降到最低很重要，但要记住，基于 CPU 的多维数组同样必须做地址转换，才能在底层一维数组中查值。事实上，GPU 的纹理寻址硬件反而让这些转换非常高效。不过，当前 GPU 在这些地址转换上存在一个问题：浮点寻址的局限。本书第 32 章讨论了用浮点地址而非整数地址带来的重要局限与误差，那些问题同样适用于本节给出的技术。

一维数组

一维数组通过把数据打包进二维纹理来表示，如图 33-5 所示。因此当前 GPU 能表示最多含 16,777,216（4,096x4,096）个元素的一维数组。[3] 每次从片元程序或顶点程序访问这个打包数组时，都必须把一维地址转换成二维纹理坐标。

代码清单 33-1 与 33-2 用 Cg 语法给出这一地址转换的两个版本。代码清单 33-1（Buck et al. 2004）展示使用矩形纹理的代码，矩形纹理使用整数地址，不支持重复平铺的寻址模式。注意 CONV_CONST 是根据纹理尺寸得出的常量，应当预先算好，而不是为每个流元素重新计算。33.4 节介绍一种优雅的做法，可把 CONV_CONST 这类值的计算交给 Cg 编译器的一项程序特化功能。采用这一优化后，代码清单 33-1 会编译成三条汇编指令。

示例 33-1. 整数寻址纹理的一维到二维地址转换

float2 addrTranslation_1DtoRECT(float address1D, float2 texSize)
{
  // 参数说明：
  // “address1D”是大小为 N 的一维数组的下标
  // “texSize”是存放该一维数组的 RECT 纹理的尺寸
  // 步骤 1）把一维地址从 [0,N] 变换到 [0,texSize.y]
  float CONV_CONST = 1.0 / texSize.x;
  float normAddr1D = address1D * CONV_CONST;
  // 步骤 2）把 [0,texSize.y] 的 1D 地址转成 2D。
  // 先做步骤 1，我们就能高效地算出
  // 二维地址，用“frac”和“floor”而不用取模
  // 和除法。注意 y 分量的“floor”是由
  // 纹理系统完成的。
  float2 address2D = float2(frac(normAddr1D) * texSize.x, normAddr1D);
  return address2D;
}

代码清单 33-2 给出可用于传统二维纹理的地址转换例程，这类纹理使用归一化的 [0,1] 寻址。若 CONV_CONST 已预先算好，这一地址转换只需两条片元汇编指令。也可以借助重复平铺寻址模式（例如 GL_REPEAT）去掉代码清单 33-2 中的 frac 指令。这样转换就缩减为一条汇编指令。不过，在某些硬件与纹理配置下这项优化可能出问题，因此应在目标架构上仔细测试。

二维数组

二维数组直接表示为二维纹理。其最大尺寸由 GPU 驱动限制。对当前 GPU，该限制在 2048x2048 到 4096x4096 之间，取决于显示驱动和 GPU。这些限制可以通过图形 API 查询。

示例 33-2. 归一化寻址纹理的一维到二维地址转换

float2 addrTranslation_1Dto2D(float address1D, float2 texSize)
{
  // 参数说明：
  // “address1D”是大小为 N 的一维数组的下标
  // “texSize”是存放该一维数组的二维纹理的尺寸
  // 注意：运行内核之前先算好 CONV_CONST。
float2 CONV_CONST = float2( 1.0 / texSize.x,
1.0 / (texSize.x * texSize.y );
// 返回归一化的 2D 地址（取值在 [0,1] 内）
float2 normAddr2D = address1D * CONV_CONST;
float2 address2D = float2( frac(normAddr2D.x), normAddr2D.y );
return address2D;
}

三维数组

三维数组可以用三种方式之一存储：存进一张三维纹理；每一层各存进一张独立的二维纹理；或打包进单张二维纹理（Harris et al. 2003, Lefohn et al. 2003, Goodnight et al. 2003）。每种技术各有优劣，影响某个应用该用哪种表示最合适。

最简单的做法是使用三维纹理，它有两个明显优势。第一，访问内存时不需要做地址转换计算。第二，可以利用 GPU 原生的三线性滤波，轻松生成数据的高质量体绘制。缺点在于，GPU 每遍渲染最多只能更新体数据的四层——因此要写入整个数组需要很多遍。

第二种方案把三维纹理的每一层存进一张独立的二维纹理，如图 33-6 所示。其优点是：与原生三维表示一样，访问数据时无需地址转换；同时每一层都能方便地更新，不需要 API 支持「渲染到三维纹理的某一层」。缺点是，由于每一层都是独立纹理，体数据不再能真正被随机访问。程序员必须在内核执行前就知道会访问哪些层号，因为片元程序和顶点程序无法在运行时动态计算要访问哪张纹理。

第三种方案把三维数组打包进单张二维纹理，如图 33-7 所示。这一方案每次访问数据都要做地址转换，但整个三维数组可以在一遍渲染中更新，也不需要「渲染到三维纹理某一层」的功能。能在一遍渲染中更新整个体数据，可能带来可观的性能收益，因为处理大流时 GPU 的并行性利用得更好。另外，与二维切片布局不同，内核内部可以随机访问整个三维数组。

第二、第三种方案的共同缺点是，无法用 GPU 原生三线性滤波对数据做高质量体绘制。所幸另一些体绘制算法能从这些复杂的三维纹理格式中高效渲染出高质量、经过滤波的图像（见本书第 41 章「延迟过滤：从难以处理的数据格式渲染」）。

代码清单 33-3 的 Cg 代码给出一种地址转换，把三维地址转成打包表示的二维地址。这种打包与代码清单 33-1、33-2 中用于一维数组的打包相同。它先把三维地址转成一大片一维地址空间，再把该一维空间打包进二维纹理。这一打包方案出现在 Buck et al. 2004 中。注意，按数据纹理的类型（二维或矩形），该方案可以使用代码清单 33-1 或 33-2 中的任一种转换。

示例 33-3. 把三维地址转换为二维地址

float2 addrTranslation_3Dto2D(float3 address3D, float3 sizeTex3D,
                              float2 sizeTex2D)
{
  // 参数说明：
  // “address3D”是三维数组的下标，该数组尺寸为“sizeTex3D”
  // “sizeTex2D”是存放该三维数组的 2D 纹理的尺寸
  // 步骤 1）纹理尺寸常量（这个应当预先算好！）
  float3 SIZE_CONST = float3(1.0, sizeTex3D.x, sizeTex3D.y * sizeTex3D.x);
  // 步骤 2）把 3D 地址转成 [0, sizeTex2D.y] 内的 1D 地址
  float address1D = dot(address3D, SIZE_CONST);
  // 步骤 3）把 [0, texSize.y] 的 1D 地址转成 2D，
  // 用的就是清单 33-1 中定义的一维到二维转换函数。
  return addrTranslation_1Dto2D(address1D, sizeTex2D);
}

代码清单 33-4 给出另一种基于切片的打包方案的 Cg 代码。该方案把三维纹理的各切片打包进二维纹理。这一方案的难点之一是，二维纹理的宽度必须能被三维数组单个切片的宽度整除。优点是在每个切片内部可以使用原生双线性滤波。注意，如果把 sliceAddr 的计算结果存进一张以 address3D.z 索引的一维查找表纹理，并预先算好 nSlicesPerRow，整个地址转换就缩减为两条指令（一次一维纹理查表加一次乘加）。

示例 33-4. 把三维纹理的各切片打包进二维纹理的源码

float2 addrTranslation_slice_3Dto2D(float3 address3D, float3 sizeTex3D,
                                    float2 sizeTex2D)
{
  // 注意：这个应当预先算好
  float nSlicesPerRow = sizeTex2D.x / sizeTex3D.x;
  // 计算切片在其地址空间中的 (x,y)
  float2 sliceAddr = float2(fmod(address3D.z, nSlicesPerRow),
                            floor(address3D.z / nSlicesPerRow));
  // 把 sliceSpace 地址转成 2D 纹理地址
  float2 sliceSize = float2(address3D.x, address3D.y);
  float2 offset = sliceSize * sliceAddr;
  return addr3D.xy + offset;
}

注意，如果 GPU 支持带三维帧缓冲的三维光栅化，或支持把纹理从二维「转换」为三维，就没有理由再把三维数组存进二维纹理。在后一种情况下，GPU 会光栅化数组展平后的二维形式，但允许程序员用三维地址从中读取。

更高维数组

更高维的数组可以用代码清单 33-3 所示打包方案的推广形式打包进二维纹理（Buck et al. 2004）。

33.3.2 结构体

像代码清单 33-5 那样的「结构体流」，必须改定义为代码清单 33-6 那样的「流的结构体」。在这种构造中，每个结构体成员都有一条独立的流。此外，结构体包含的数据不得超过 GPU 每个片元能输出的量。[4] 这些限制源于片元程序无法指定其帧缓冲结果写入的地址（即无法执行分散写操作）。把结构体表示为「流的结构体」后，每个结构体成员具有相同的流索引，因而所有成员都能由同一个片元程序更新。

// “结构体流”在当前 GPU 上不容易更新。
struct Foo
{
  float4 a;
  float4 b;
};
// 这种“结构体流”是有问题的
Foo foo[N];

示例 33-6. 流的结构体

{
  float4 a[N];
  float4 b[N];
};
// 为每个成员定义一条独立的流
float4 Foo_a[N];
float4 Foo_b[N];

33.3.3 稀疏数据结构

到目前为止讨论的数组和结构体都是稠密结构。换句话说，数组地址空间中的所有元素都存有有效数据。不过，有许多问题要想高效求解，需要稀疏数据结构（如链表、树或稀疏矩阵）。稀疏数据结构是许多经过优化的 CPU 算法的重要组成部分；用稠密数据结构顶替它们的蛮力式 GPU 实现，往往比对应的优化 CPU 版本还慢。另外，稀疏数据结构能降低算法的内存需求——考虑到 GPU 可用内存有限，这一点很重要。

尽管重要，稀疏数据结构的 GPU 实现却很棘手。第一个原因是，更新稀疏结构通常涉及向计算出的内存地址写入（即分散写）。第二个难点是，遍历稀疏结构时，访问数据所需的指针解引用次数往往并不一致。这很麻烦，因为如 33.1 节所述，当前片元处理器是 SIMD 机器，必须以完全相同的指令成批处理流元素。尽管如此，研究者近来已证明，不少稀疏结构可以在当前 GPU 上实现。

静态稀疏结构

我们先描述静态的基于 GPU 的稀疏数据结构，其结构在 GPU 计算过程中不变。这类数据结构的例子包括 Purcell 光线加速网格中的三角形列表（Purcell et al. 2002），以及 Bolz et al. 2003 和 Krüger and Westermann 2003 中的稀疏矩阵。在这些结构中，稀疏元素的位置和数量在整个 GPU 计算过程中固定不变。例如，光线追踪场景中三角形的位置和数量不会变化。由于结构是静态的，它们无需向计算出的内存地址写入。

这些结构都用一级或多级间接来在内存中表示稀疏结构。以 Purcell 的光线加速结构为例，它从一张规则的、存有三角形列表指针的三维网格开始，如图 33-8 所示。三维网格纹理中为每个网格单元存放一个指针，指向该单元三角形列表的起始处（列表存在第二张纹理中）。三角形列表中的每一项又含一个指针，指向存在第三张纹理中的顶点数据。类似地，稀疏矩阵结构用固定级数的间接来查找非零矩阵元素。

这些结构用两种方法之一解决不规则访问模式的问题。第一种方法把结构切成块，块内所有元素具有相同的访问模式，因而可以一起处理。第二种方法是让每个流元素在每遍渲染中处理自己列表中的一项。还有更多项要处理的元素会继续计算结果，而已经走到列表末尾的元素则被停用。[5]

分块策略的例子见 Bolz et al. 2003。他们把稀疏矩阵切成非零元素个数相同的块，并对相似的行做填充，使它们布局一致。Purcell et al. 2002 中遍历三角形列表的算法，则是通过条件执行做非一致遍历的例子。所有活跃射线（流元素）在每遍渲染中处理各自列表中的一个元素。射线到达三角形列表末尾后转为不活跃，而还有三角形要处理的射线继续执行。

注意，要求所有流元素具有一致访问模式，是当前 GPU 的 SIMD 执行模型带来的限制。如果未来的 GPU 支持 MIMD 流处理，访问不规则的稀疏数据结构可能会容易得多。例如，Pixel Shader 3.0 GPU 提供的有限分支，已经比前几代 GPU 为数据结构遍历提供了更多选择。

动态稀疏结构

在 GPU 计算过程中被更新的基于 GPU 的稀疏数据结构，是当前活跃的研究领域。两个值得注意的例子是 Purcell et al. 2003 中的光子图，以及 Lefohn et al. 2003、2004 中的可变形隐式曲面表示。本节简要概述这些数据结构及其更新所用的技术。

光子图是一种稀疏的自适应数据结构，用于估计场景中的辐照度（即到达表面的光）。Purcell et al.（2003）描述了一个完全基于 GPU 的光子图渲染器。为在 GPU 上构建光子图，他们设计了两种方案，用于在当前 GPU 上向计算出的内存地址写数据（即分散写）。第一种技术先算出内存地址和要存在这些地址上的数据。然后对这些缓冲做一次数据并行的排序操作，借此完成分散写。第二种技术是模板路由，用顶点处理器在计算出的内存地址所定义的位置绘制大点。它用一个巧妙的模板缓冲技巧解决冲突（即两个数据元素被写到同一地址的情形）：即使数据值被画在同一片元位置，也能把它们路由到各自唯一的槽位（像素位置）。对非一致数据的访问方式，与上一小节所述的三角形列表遍历类似。

另一种基于 GPU 的动态稀疏数据结构，是 Lefohn et al.（2003、2004）用于隐式曲面变形的稀疏体结构。隐式曲面把三维曲面定义为体数据的等值面（或称水平集）。二维等值面最常见的例子是地形图上画的等高线。一条等高线由地图上海拔相同的点构成。类似地，隐式三维曲面就是体素中所存标量值的等值面。从数学角度看，这样表示曲面非常方便，允许曲面自由变形并改变拓扑。

隐式曲面的高效表示使用一种稀疏数据结构，只存曲面附近的体素而不存整个体数据，如图 33-9 所示。Lefohn et al.（2003、2004）描述了一种基于 GPU 的技术，把隐式曲面从一种形状变形为另一种。随着曲面演化，表示它的稀疏数据结构也必须随之演化（因为数据结构的规模与隐式曲面的表面积成正比）。例如，若初始曲面是一个小球，最终形状是一个大正方形，则最终形状所需内存会明显多于初始小球。本节余下部分介绍这一稀疏体结构，以及它如何随移动的曲面演化。

稀疏结构的构建方式是把三维体数据细分成小的二维瓦片（见图 33-9 中标「A」的部分）。CPU 把含有曲面的瓦片（即活跃瓦片）存进 GPU 纹理内存（见图 33-9 中标「B」的部分）。GPU 只对活跃瓦片执行曲面变形计算（见图 33-9 中的第 2 步）。CPU 维护一份活跃瓦片映射，并按 GPU 计算的需要分配/释放瓦片。该方案把 CPU 当作 GPU 的内存管理协处理器，从而解决动态更新的问题。

这套系统的关键环节之一，是 GPU 请求 CPU 分配或释放瓦片的方式。CPU 通过从 GPU 读取一小段编码消息（图像）来接收通信（见图 33-9 中的第 3、4 步）。该图像为每个活跃瓦片对应一个像素，每个像素的值是一段位编码。这段 7 位编码中，1 位对应活跃瓦片本身，6 位对应它在三维体数据中相邻的六个瓦片。每一位的取值指示 CPU 分配或释放相应的瓦片。事实上，CPU 把整幅图像解释为一个位向量。GPU 生成位向量图像的做法是：在每个活跃像素处计算一个内存请求，再用自动 mipmap 生成或 Buck et al. 2004 所述的归约技术，把请求归约成每个瓦片一个。CPU 解码内存请求消息后，分配/释放所请求的瓦片，并把一组新的顶点和纹理坐标发给 GPU（见图 33-9 中的第 1 步）。这些顶点数据表示新的活跃瓦片集合，GPU 在该集合上计算曲面变形。

总之，这一动态稀疏数据结构在 GPU 数据结构需要更新时向 CPU 发送小消息，从而绕开了对分散写功能的需求。该结构采用本节开头讨论的分块策略，把稀疏域上的计算统一起来。这套方案有效，原因有几点。第一，采用压缩的位向量消息格式，把 GPU 与 CPU 之间的通信量降到最低。第二，CPU 只充当内存管理器，让 GPU 承担所有「重」计算。注意，整个变形过程中，隐式曲面数据只驻留在 GPU 上。最后，动态稀疏表示使计算量和内存需求随隐式曲面的表面积增长，而不随其包围盒的体积增长。这是一项重要的优化；一旦忽略它，基于 CPU 的实现就能轻松超过 GPU 版本。

本节所述的两种动态稀疏数据结构都遵循数据并行数据结构的规则：其数据元素可以被并行地独立访问。Purcell 等人的结构以数据并行的方式更新，而 Lefohn 等人的结构一部分并行更新（GPU 用数据并行计算生成内存分配请求），一部分用串行程序更新（CPU 用栈和队列逐个处理这组内存请求）。复杂的、能适配 GPU 的数据结构仍将是活跃的研究领域，因为它们对构造可扩展且经过优化的算法很重要。这些数据结构是完全放在 GPU 内，还是采用 CPU/GPU 混合模式，将在很大程度上取决于 GPU 如何演进，以及 CPU 与 GPU 之间能以何种速度/延迟通信。

33.4 性能考量

最后一节介绍一些底层细节，它们对基于 GPU 的数据结构的整体性能影响很大。

33.4.1 依赖纹理读取

GPU 相对 CPU 的优势之一，是它能掩盖从内存读取缓存之外的数据所带来的开销。它通过发出异步内存读请求，并执行其他无依赖的操作来填补该请求耗时，从而实现这一掩盖。连续执行多次依赖内存访问（即用一次访问的结果作为下一次访问的地址）会减少可用的无依赖工作，从而让 GPU 更难掩盖内存访问延迟。因此，某些类型的依赖纹理读取若不谨慎使用，会让程序严重变慢。

并非所有依赖纹理读取都会拖慢程序。公开的基准测试工具 GPUBench（Fatahalian et al. 2004）指出，依赖纹理读取的开销完全取决于内存访问的缓存一致性。那么，依赖纹理读取的危险在于，它们很容易造成缓存不一致的内存访问。应力求让数据结构中的依赖纹理读取尽可能保持缓存一致。保持缓存一致性的技术包括：把相似计算归入一致的块、使用尽可能小的查找表，以及尽量减少纹理依赖的级数（从而降低不一致访问的风险）。

33.4.2 计算频率与程序特化

33.2.2 节所述的数据流以不同的计算频率被计算。例如，顶点流是比片元流频率更低的流。这意味着顶点流包含的元素比片元流少。GPU 计算可用的计算频率有这几种：常量、uniform、顶点和片元。常量值在编译期已知，uniform 参数则是每次内核执行只计算一次的运行时值。我们可以尽量在最低的频率上计算数值，以利用 GPU 中不同的计算频率。例如，若片元程序要访问多个相邻纹素，在顶点数少于片元数的情况下，通常在顶点程序里计算这些纹素的内存地址比在片元程序里算更高效。

计算频率优化的另一个例子，是在每个数据元素处都算出同一个值的内核代码。这类计算应当在 GPU 内核执行之前，以 uniform 频率在 CPU 上预先算好。前面给出的地址转换代码（代码清单 33-1、33-2、33-3）中常见这种写法。避免这类冗余计算的一种办法是手工预先算出 uniform 结果，并相应修改内核代码（包括内核的参数）。另一种更优雅的选择，是用 Cg 编译器的程序特化功能自动完成这一计算。程序特化（Jones et al. 1993）在「运行时常量」uniform 参数设定之后，于运行时重新编译程序。只依赖这些已知值的代码路径会被执行，常量折叠后的值存入编译产物。在 Cg 中，程序特化可通过 cgSetParameterVariability 这一 API 调用使用（NVIDIA 2004）。注意，这一技术需要重新编译内核，因此只适用于特化后的内核在 uniform 参数两次变更之间被多次使用的情形。该技术往往只适用于那些仅设置一次的 uniform 参数子集（即「运行时常量」）。

33.4.3 pbuffer 生存指南

pbuffer 即像素缓冲，是 OpenGL 中的离屏帧缓冲。这些特殊的帧缓冲除了提供浮点帧缓冲，直到不久前还是 OpenGL 程序员唯一可用的渲染到纹理功能。可惜，pbuffer 并非为许多 GPGPU 应用所需的大量渲染到纹理用法（有时会有数百个 pbuffer）而设计，这样用 pbuffer 会遇到不少性能陷阱。

OpenGL 架构评审委员会（ARB）目前正在研究一种新机制，用于渲染到可显示帧缓冲以外的目标（即纹理、顶点数组等）。这一扩展与顶点缓冲对象、像素缓冲对象扩展结合后，将使渲染到纹理不再需要 pbuffer。尽管如此，我们仍列出下面这组 pbuffer 使用建议，因为当前有大量应用在广泛使用它们。

pbuffer 的根本问题在于，每个 pbuffer 都有自己的 OpenGL 渲染上下文和设备上下文。在这些上下文之间切换代价非常高。传统上把 pbuffer 用于渲染到纹理的做法，是为每张可渲染纹理配一个 pbuffer。结果是从一张可渲染纹理切到下一张时需要进行 GPU 上下文切换——应用性能会变得极差。本节介绍两种技术，通过避免切换上下文大幅降低更换渲染目标的代价。

第一项优化是使用多表面 pbuffer。pbuffer 的表面指它的某个颜色缓冲（如 front、back、aux0 等）。每个 pbuffer 表面都可以充当自己的可渲染纹理，而表面之间切换非常快。务必确保不把同一个表面同时绑定为纹理和渲染目标。这是非法配置，很可能导致结果错误，因为它破坏了流编程模型中「内核不能写入自己的输入流」这一保证。代码清单 33-7 给出创建并使用多表面 pbuffer 完成多遍渲染到纹理的伪代码。

示例 33-7. 在 OpenGL 中用多表面 pbuffer 高效地渲染到纹理

void draw(GLenum readSurface, GLenum writeSurface)
{
  // 1）把 readSurface 绑定为纹理
  wglBindTexImageARB(pbuffer, readSurface);
  // 2）把渲染目标设为 writeSurface
  glDrawBuffer(writeSurface);
  // 3）渲染
  doRenderPass(...);
  // 4）解绑 readSurface 纹理
  wglReleaseTexImageARB(pbuffer, readSurface);
}
// 1）分配并启用多重表面 pbuffer（Front、Back、AUX 缓冲）
Pbuffer pbuff = allocateMultiPbuffer(GL_FRONT, GL_BACK, GL_AUX0, ...);
EnableRenderContext(pbuff);
// 2）从 FRONT 读、往 BACK 写
draw(WGL_FRONT_ARB, GL_BACK);
// 3）从 BACK 读、往 FRONT 写
draw(WGL_BACK_ARB, GL_FRONT);

第二项 pbuffer 优化，是用 33.3.1 节所述把三维纹理展平进二维纹理的打包技术。把数据存进同一个大 pbuffer 的多个「视口」中，可以进一步免去切换 OpenGL 上下文的需要。Goodnight et al.（2003）在他们的多重网格求解器中大量使用这一技术。不过，与基本的多表面 pbuffer 用法一样，必须避免同时读写同一个表面。

33.5 结论

GPU 内存模型基于流式的数据并行计算模型，支持高度的并行性与内存局部性。该模型对内存何时、如何、在何处使用有多项限制。其中许多限制是为了保证并行性，另一些则是因为 GPU 是为实时渲染而非通用高性能计算设计与优化的。随着推动 GPU 销售的应用领域超出实时图形，GPU 很可能变得更通用，这些人为限制也会逐步放宽。

管理多维数组、结构体这类基本 GPU 数据结构的技术已相当成熟。而链表、树、稀疏数组这类复杂 GPU 数据结构的创建、高效使用与更新，仍是活跃的研究领域。
