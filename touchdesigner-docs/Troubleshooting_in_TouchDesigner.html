TouchDesigner 故障排查

TouchDesigner 是一款极为灵活的工具，而这种灵活性也意味着你的创作中可能出现复杂且难以定位的问题。本页简要介绍在构建 TouchDesigner 网络时最重要的故障排查技巧与工具。当然，每个问题都与其上下文相关，因此需要你自己判断哪种方法最适合。为此，本页将让你熟悉可用的各类工具。

故障排查（或称调试、分析崩溃）与优化不同，后者关注让网络高效快速地运行。有关优化的信息请参阅 Optimization。

下文描述的许多（但并非全部）技巧都需要对 Python 有基本了解。

重要： 如果你发现 TouchDesigner 本身的缺陷，请 report it to Derivative。

文档

查找 TouchDesigner 功能信息的首选之处是本 wiki，它是官方的 TouchDesigner documentation。文档常常能为你使用某项功能时遇到的问题提供线索（即使不是答案）。如有需要，你可以 download the entire wiki 以便离线使用。

除了使用 wiki 的搜索功能，TouchDesigner 用户界面中还有直接通往本 wiki 的入口。所有操作符在其 Parameter Dialog 头部都有指向其 wiki 页面的链接：

底部标题栏中最左侧的按钮链接到操作符帮助，向右的下一个按钮链接到 Python 帮助。

此外，Palette 中的某些组件带有一个 Help Page 自定义参数，可打开浏览器访问该组件的 wiki 页面。

论坛

获取 TouchDesigner 帮助或信息的另一个常见去处是 TouchDesigner Forums。那里有强大而乐于助人的用户社区和 Derivative 员工。与任何论坛一样，提问前请先搜索答案；提问时请尽可能清晰简洁。

排查网络问题

在网络中查找错误通常很容易，因为出错的 nodes 会显示错误标记，即带黑色 X 的红色圆圈。要获取错误信息，点击错误标记，或在节点上任意位置中键单击。通常错误修复后，错误标记会立即消失。

如果组件内部任意位置存在错误，该组件会显示错误标记，因此修复错误往往需要逐层进入组件，直到找到错误的真正来源。

Errors 对话框与 Error DAT

Errors Dialog 位于 Dialog 菜单中，可让你查看并跳转到所有当前错误。它还允许按操作符类型、具体操作符和错误消息过滤错误。Error DAT 与 Errors 对话框非常相似，但以 DAT 格式呈现，并具有回调功能。

OP.errors() 和 OP.scriptErrors()

查找网络中所有节点错误的另一种方法是打开 Textport 并输入命令 op('/').errors(recurse=True) 获取所有节点错误，或输入 op('/').scriptErrors(recurse=True) 获取所有 scriptErrors。这会打印所有错误及其关联节点的列表，你也可以指定网络路径并打印该网络下的所有错误。有时你可能会发现某个组件有一个出错的子级，但进入其父级后错误却消失了。错误对话框、Error DAT 或 errors() 方法是无需实际导航到其网络即可查明错误内容的好办法。

使用 Info CHOP、Panel CHOP 和 Info DAT 获取信息

在研究节点错误时，你有时会想观察节点上的值。有几个操作符对此很有用。Info CHOP 保存其 Operator 参数所引用节点的数值信息。类似地，Panel CHOP 保存 Panel 组件面板值的数值信息。提示： 你会注意到 Info CHOP 也保存面板信息，但最好使用 Panel CHOP 来观察面板信息，因为它有时更新得更可靠。

少数操作符包含字符串信息，可使用 Info DAT 查看。在处理 GLSL 操作符时这一点尤为重要

使用 Bypass 与 Cook 标记定位错误

在尝试定位网络中的错误时，你常常希望缩小可能的来源范围。使用 Bypass Flag 缩小活动操作符的范围通常会有帮助。如果你想关闭整个网络以缩小范围，可以关闭父组件的 Cooking Flag。

使用 Chop Execute DAT 与 Parameter Execute DAT 捕获错误

如果你想在某个事件发生时向 Textport 打印调试消息，通常会使用 CHOP Execute DAT 或 Parameter Execute DAT 来观察值。例如，CHOP Execute DAT 可与 Info CHOP 和 Panel CHOP 配合使用，在那些值发生变化时通知你。注意： execute DAT 可用于在变化发生时作出反应，但它们无法直接追踪是什么导致了该变化。不过，知道 when 某事何时发生，对找出其原因很有帮助。

从脚本打印调试消息时，始终建议使用 debug 命令，而不是标准的 Python print 命令。有关 more info 见下文。

在 Perform 模式下排查问题

在 Perform Mode 中排查问题时，编辑器被隐藏，但你仍希望访问通常从编辑器获得的大量信息。这里的主要技巧是使用浮动查看器，它们在你进入 Perform 模式后仍保持打开。因此，如果你在 Editor 模式下打开浮动查看器（使用 RMB 上下文菜单中的 View... 选项）和参数查看器（RMB 上下文菜单 Parameters...），然后进入 Perform 模式，你就能访问想要监视或更改的内容。浮动 Textport 在 Perform 模式下也会保持打开。Perform 模式下的另一个重要技巧是使用 F10 打开鼠标所在面板的网络。你还可以使用 F9 打开该面板的父级，网络视图会聚焦于该面板组件。这些热键让你能轻松访问 Perform 模式控制面板中需要关注的特定部分。

排查消失的错误

有时加载 .toe 文件时，你会看到网络中存在错误，但进入该网络后错误却消失了。这是因为如果节点尚未被要求加载或计算等，就可能出现错误。然而，手动查看该节点或依赖它的内容，会触发该节点更新。

遗憾的是，这些错误通常需要逐一分析，但很多时候它们不会影响启动后的性能。

要查看错误列表，请打开 Error 对话框，而不是进入网络，因为进入网络会触发更新。

如果错误是计算顺序问题且不易解决，你有时可以使用启动脚本按特定顺序强制计算该节点。

计算不足的问题

计算不足是指操作符本应更新，但出于某种原因没有更新。如果你更改了一个操作符中的数据，而它自身或查看该数据的另一个操作符没有更新（计算），则可能是计算不足问题。验证此类问题的一个重要技巧是使用 Info CHOP 监视计算次数。所有计算不足问题都应 reported to Derivative。

如果你的操作符在 Editor 中运行正常，但在 Perform 模式下不正常，请尝试使用 Viewer Flag 关闭 Network Editor 中的所有查看器。因为 TouchDesigner 只计算被使用的节点，可能是节点的查看器在使用该节点，从而使你在 Network Editor 中没有问题。

排查性能不佳的问题

请参阅 Optimize 指南。

排查 Python 问题

因为 TouchDesigner 是实时引擎，且不为 Python 使用断点/单步调试器，调试可能有些棘手。使用 Python 时，Textport 是你最好的朋友，你会希望始终保持一个打开。Python 错误会打印到 Textport（也会显示为节点上的错误标记），你常常需要打印自己的调试消息。提示： 如果你觉得浮动 textport 不方便，可使用 Pane Bar 拆分网络视图，并将其中一个窗格类型改为 Textport and DATs。

网络中的 Python 错误标记

与其他操作符一样，带 Python 脚本的 DAT 出现问题时也会显示错误标记。如果某个 DAT 被用作 Python 脚本并在编译时出错，它会显示错误标记。同样，与其他操作符一样，你可以通过点击错误标记或在节点上中键单击来查看编译错误。编译错误解决后，标记会消失。

当 Python 脚本内部出现运行时错误时，情况略有不同。错误标记会被放置在包含脚本的 DAT 上 where the error started. 这意味着，虽然错误可能发生在某个模块中，标记却会出现在调用它的模块上！幸运的是，完整的错误堆栈（导致错误的 Python 命令链）可以在错误标记信息中找到，通常也会打印到 Textport。

获取调试与错误信息

如上所述，由于 TouchDesigner 的实时特性，从 Python 获取调试信息的方法是在脚本运行时输出。以下是一些重要的命令与技巧：

命令：debug

debug(*objects)

debug 命令把任意数量的对象打印到 textport。它的工作方式与 Python 的 print 命令很像，但会打印对象的字符串「表示」，对某些对象来说更详细。debug 输出还会附加调用 debug 的脚本和行号。
示例：debug("Testcomp:", myComp.path, myComp.par.display)

从 Python 脚本输出信息用于调试时，always use the debug command. 使用 print 时，很容易忘记把所有测试语句放在哪里，最终产生难以追踪的多余 Textport 噪音。由于 debug 总是输出其调用位置，你总能轻松找到并移除调试代码。额外的好处是，对于某些对象，debug 输出的细节比 print 更多。

命令：project.pythonStack

print(project.pythonStack())

有时你会想看到哪些 Python 调用导致运行了你的某个 Python 脚本。要打印 Python 调用栈，使用 print(project.pythonStack)。Python 用户可能会认出，这与 traceback.print_stack 方法相似。使用 project.pythonStack 更安全，因为 Python 版本偶尔会在 TouchDesigner 网络中留下不需要的错误标记。project.pythonStack 方法也经过定制，可为 TouchDesigner 操作符提供额外信息。对应的 project.stack() 会给出正在计算和求值的操作符栈。

输出到 DAT 而不是 Textport

上述方法会自动输出到 Textport，这能满足大多数调试需求。但有时你可能想存储更多调试数据，或让数据保留更久，例如跨文件保存。为此，你会希望输出到 Text DAT 或 Table DAT。使用 Table DAT 可以将调试信息组织成列，很有帮助。

抛出异常

有时你会希望在某一点停止代码执行。为此，只需抛出一个 Python 异常。代码执行将停止，错误会通过 Error Marker 和 Textport 报告。抛出异常时，通常最好添加一条有用的消息。

Example: raise Exception("Width set to zero in " + parent().path)

有关 Python 异常的更多详细信息，请参阅：Python Errors and Exceptions

崩溃与 .toe 文件的排查

偶尔 TouchDesigner 会崩溃。它有一些不错的功能可减少破坏性并便于诊断，本节将加以介绍。此外，每次保存项目时，都会在工作文件夹中保存一个递增版本，并将先前的文件放入 Backup 文件夹。这可确保你能回到之前可用的版本。（如果你对媒体使用相对路径，可能需要将 Backup 中的文件向上一级复制到项目文件夹。）（参见「保存时递增文件名 in Preference).」

如果你确实遇到网络崩溃，尤其是可重复的崩溃，请告知我们——请阅读下文关于报告问题的部分。

崩溃自动保存

对于几乎所有崩溃，TouchDesigner 都会在关闭前自动保存一个 CrashAutoSave.yourproject.toe。CrashAutoSave 文件是你的项目在崩溃瞬间的保存。当你再次用 TouchDesigner 加载它时，它会处于特殊的安全模式，其中大部分功能被旁路。这让你有机会修复可能导致崩溃的任何问题。当你用 File 菜单中的 Save 保存此文件并重新加载后，它会回到正常模式。

诱使 TouchDesigner 以安全模式打开

如果你需要在 CrashAutoSave 安全模式下处理已保存的 .toe 文件，只需将文件名改为以 CrashAutoSave. 为前缀并重新加载。例如，将文件重命名为 CrashAutoSave.yourproject.1.toe。这可确保你总能打开文件并获取其内容。

启动错误对话框

有时你的网络会在 TouchDesigner 初始设置期间出现错误。要在 TouchDesigner 加载时获得完整的错误报告，请从编辑器菜单中选择 Edit 菜单下的 Preferences。在 General 页面上有一个 Show Startup Errors 菜单，可让你选择在有警告或错误时显示 Startup Errors Dialog（Warnings 设置），还是仅在错误时显示（Errors 设置）。下次加载 TouchDesigner 时，如果满足条件，你将看到启动错误对话框。

TouchDesigner 消失

诊断 TouchDesigner 直接消失（启动时或之后）的崩溃，一个好方法是从 Microsoft 商店安装「Windbg Preview」应用。你可以在其中启动应用，并不断按播放按钮，直到捕获到实际崩溃（由于异常，启动时可能会暂停一两次）。从这里可能得到问题所在的线索。更多信息见 Using WinDbg to Debug Crashes。

TouchDesigner 挂起

如果 TouchDesigner 挂起，你可以创建一个 .dmp 文件或崩溃报告。在 Windows 上，可以使用 Windows 任务管理器，右键单击进程并选择「Create Dump File」。也可以使用 WinDbg，见 Using_WinDbg_to_Debug_Crashes。在 macOS 上，见 macOS Crash logs。

内存泄漏

查找潜在内存泄漏时，最好的检查位置是任务管理器「详细信息」页中的「Commit Size」列（macOS 上类似）。相比普通的内存列，它能更准确地衡量是否发生泄漏。默认情况下可能看不到「Commit Size」列，此时你可以右键单击标题栏将其选中。

诊断内存损坏

在极少数情况下，可能存在未被检测到的内存硬件损坏。见 Diagnosing Memory Corruption Using Global Flags。

ToeExpand 与 ToeCollapse 工具

在极少数情况下，你可能想将 .toe 文件拆解为 ASCII 可读的内容。为此，请使用 TouchDesigner 安装目录中随附的 Toeexpand 和 Toecollapse 程序。使用理由包括修复无法加载的文件中的某些内容，或搜索难以找到的文本片段。这还允许你使用「diff」程序比较两个 .toe 文件，找出所有差异。

向 Derivative 报告缺陷

用户报告是了解 TouchDesigner 缺陷的重要信息来源，感谢你的反馈。话虽如此，在将问题报告为软件缺陷之前，请始终尝试使用上述技巧确认问题确实出在软件上。

要报告缺陷，请发送邮件（support@derivative.ca）或在 forums 上发布你的 .toe 文件，并说明如何复现错误，以及创建的 .dmp 文件或崩溃报告（如果是崩溃）。在 Windows 上，.dmp 文件将保存在你的项目目录中。在 macOS 上，你可以通过 Applications->Utilities->Console 找到崩溃报告。崩溃报告位于 User Reports 或 Crash Reports 下，命名为 TouchDesigner_date-xxx.crash|ips。右键单击报告名称可通过 Reveal in Finder 获取文件位置。将问题发布到论坛是最好的，但如果你的项目包含私有数据或技术，也可以发邮件。

报告缺陷时，请尽量做到以下几点：

  • 创建一个尽可能易于复现的案例。让 Derivative 能快速简单地看到你的缺陷。
  • 尽可能精简你的文件。移除一切可以移除的内容，以获得较小的文件大小和易于理解的网络。
  • 确保你的文件不需要额外的媒体文件。许多操作符可以被 "locked" 以保留其数据并消除对外部文件的依赖。如果外部文件确实必要，请创建一个可直接运行的压缩文件夹，包含你的 .toe 文件和所有必需的媒体。
  • 发送压缩文件时，请使用 .zip，而不是 .rar、.7z 等。对于较大的文件，可以使用 Google Drive、Dropbox 或类似服务。
