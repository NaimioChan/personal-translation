色彩空间

另请参阅 Color Space Workflows

概述

色彩空间定义了 RGB 值所指的「真实」颜色。例如 (1, 0, 0) 应该让你的显示设备发出什么波长的光。当 (1, 0, 0) 被转换为光时，不同的色彩空间会产生不同色调的红。为确保图像在一个显示设备上与另一个显示设备上显示的颜色相同，图像/影片必须包含它保存时所使用的色彩空间信息。这样应用程序就能确保把正确的值发送给显示器。例如在一台设备上的 (1, 0, 0)，拿到另一台能显示更深红色的设备上时，可能需要发送 (0.8, 0, 0)，才能得到相同的最终红色。没有色彩空间信息，图像在第二台显示器上看起来会比在第一台上更饱和（更红）。

对于摄像机等捕获图像的设备也是如此。它们需要指明以何种色彩空间保存数据，以便任何使用该内容的人都能正确显示。

与人眼所能看到的颜色相比，显示设备只能显示其中很小一部分。例如大多数商用计算机显示器所限定的 sRGB 色彩空间，只覆盖人眼实际可见颜色的 35%。

色彩入门

人眼可见的颜色范围经过测试并记录在 CIE 1931 color space 中。这张二维图用于通过在其上指定三角形来帮助定义可见色域（色彩空间的两个主要部分之一）。例如 sRGB 可以看作一个比人眼可见范围小得多的三角形。大多数显示器能产生该三角形内的颜色。高端显示器和 HDR 电视通常能产生更大的 DCI-P3 三角形内的颜色。Rec.2020 色域常在应用/设备之间通信时使用，因为它是一个非常大的色域，能容纳应用想要显示、设备也可能显示的所有颜色而不丢失数据。通常只有面向艺术家和剪辑师的非常高端的专业显示器才能显示 Rec.2020。

色彩不正确的显示

看 CIE 图时可能让人困惑的一点是：因为你是在显示器上看它，你能看到渐变一直延伸到记录的人眼范围的边缘，这也许很奇怪，尽管你的显示器无法显示其色域之外那么远的渐变。这里发生的情况，正是非色彩正确的显示设备/应用程序工作方式的一个陷阱。如果那张 CIE 图在你的显示器上被正确显示，你会看到颜色渐变在显示器色彩限制的边界处被截断，通常大约在 sRGB 三角形的位置，那之外只是纯色。然而由于那张图三个角的值分别是 (1, 0, 0) → (0, 1, 0) → (0, 0, 1)，你的显示器会把这些值显示为它能显示的最大红、最大绿和最大蓝。将来当这些页面以更色彩正确的方式显示时，这些值会在显示器上被截断。 目前如果你在另一台色域更宽的显示器上看同一张图，你会看到边缘处更饱和的颜色。

在标准显示器上，你大概可以更改各种设置，例如 Hue、Saturation、Brightness，它们会进一步调整显示的颜色。结果是你看到的颜色很可能不是内容作者预期的实际颜色。

色域

如前所述，色域定义了色彩空间在 CIE 图上所定义的三角形。它定义了 (1, 0, 0)、(0, 1, 0)、(0, 0, 1) 在人眼可见的真实颜色中意味着什么。在支持如此宽色域的显示器上，把 sRGB 色域定义的 (1, 0, 0) 与 Rec.2020 色域定义的 (1, 0, 0) 相比，你实际上会看到，我们多年来在 sRGB 显示器上看到的都只是一种橙色，而不是深红。

色域由 3 个 xy 坐标定义三角形的 3 个角，它们代表三角形的红、绿、蓝角。此外还会为色域在中心选定一个「白点」，对大多数色彩空间来说通常称为 D65 或 D60，它同样用其在 CIE 图中的 xy 坐标定义。例如 Rec.2020 的原色坐标定义为：

xW yW xR yR xG yG xB yB
Rec.2020 0.3127 0.3290 0.708 0.292 0.170 0.797 0.131 0.046

传递函数

除了色域，色彩空间还定义了 Transfer Function。它定义了一条曲线（通常称为 Gamma），数据按这条曲线存储在文件中并发送给显示器。传递函数可以服务于许多不同的目的。对于 8 位数据，sRGB 内容使用 sRGB 传递函数保存，这能让 8 位所提供的有限的 256 级值得到更好的利用。传递函数使更多级数据用于较暗的颜色范围，而人眼对该范围更敏感。这通过在较暗的级别给出更多级、在较亮的级别给出更少的级，帮助减少色带伪影。精度位数更多时，传递函数对保存文件数据的重要性会降低。例如 16 位浮点 EXR 文件通常总是使用线性传递函数。与某个色域按惯例搭配使用的传递函数通常由标准委员会选定，虽然这些选择有其充分理由，但没有直接规定某个色域必须使用某个传递函数。

每当你真正在组合颜色时（例如合成它们，或在光照计算中使用它们），你总是希望使用线性值来做。因此，一个以 sRGB 色域和 sRGB 传递保存的文件，可能会在 GPU 内存中被转换为 sRGB 色域加线性传递，然后才对其内容应用合成。

传递函数的另一个重要用途是与显示器通信。显示器会期望发送给它的数据使用它显示内容时所用的同一传递函数。因此 sRGB 显示器会希望发送给它的值使用 sRGB 传递。这意味着合成之后，线性值会被转换回 sRGB 传递，然后才发送给 sRGB 显示器。

线性与非线性传递之间的转换由两个方程完成（它们互为逆运算。OETF（光电转换传递函数，opto-electronic transfer function）把线性值转换为非线性值，EOTF（电光转换传递函数，electro-optical transfer function）把非线性值转换为线性值。

亮度

理解色彩时另一个重要的概念是亮度如何定义。显示器上的 (1, 1, 1) 应该有多亮？你当然可以调高亮度来调整它，但那可能与内容作者的意图不符。计算机中颜色的亮度用一个称为 Nit 的单位来定义。它也定义为坎德拉每平方米，或 cd/m2。大多数标准显示器能显示 100 到 300 尼特的亮度。消费级 HDR 显示器可能能显示 500-700 尼特，而专业级能显示 1500-2500 尼特。100 瓦的灯泡是 1,600 尼特，而太阳是 16 亿尼特。(1, 1, 1) 应代表多少尼特还取决于观看环境。较暗的房间需要较少的尼特就能达到相同的感知亮度。例如电影院放映机可能只能显示 75 尼特。

计算机和显示器如何显示色彩

过去通常所有内容（例如 JPEG）都以 sRGB 色彩空间保存，显示器也被期望显示 sRGB 色彩空间。因此你可以把那个 JPEG 文件中的值原样发送给显示器而无需任何调整，它们看起来就是正确的。然而现代图像/影片格式常常使用许多不同的色彩空间，显示器可以显示更宽的色域，且可用的最大尼特也各不相同。如果你盲目地把某个文件格式中的 (1, 0, 0) 拿到具有不同色域、传递特性和最大尼特的显示器上显示，你会得到差别很大的红色和亮度。具备色彩空间意识可以通过用已知的色彩空间读取文件，并以显示器期望的色彩空间与显示器通信，在文件的色彩空间和显示器的色彩空间之间进行转换，来纠正这一点。

Windows 和 macOS 都有设置可控制显示器是由 SDR 信号还是 HDR 信号驱动（对支持 HDR 的显示器）。这会改变显示器运行的模式，以及通过线缆发送给显示器的数据类型。

SDR（标准动态范围）显示

SDR 模式本质上是一种「笨」模式，本身不包含任何色彩空间信息。显示器可能有控件来选择它应运行在哪个色彩空间，还可能有其他控件让内容更饱和/更鲜艳。更改这类控件与正在显示的色彩空间没有直接对应关系，而且没有校准工具的话，很可能导致颜色无法正确匹配所需的色彩空间。

由于操作系统与显示器之间不交换色彩空间信息，显示器只会把 (1, 0, 0) 这个值显示为它当前设置所能显示的最亮、最红的红。

要正确显示颜色，你需要通过线缆发送与显示器所显示的色彩空间相同的数据。因此如果你的显示器设为 sRGB，那么你需要发送 sRGB 色彩空间的颜色给它。过去这是通过 ICC 配置文件完成的，用它把应用程序工作所用的色彩空间转换为显示器的色彩空间。

HDR（高动态范围）显示

HDR 是支持 HDR 的显示器可以运行的另一种模式。这是在操作系统的显示设置中进行的设置。处于此模式时，通过线缆发送的信号包含数据所在色彩空间的准确信息，使显示器能正确显示颜色和亮度。通常这些数据以非常宽的色域（Rec.2020）发送，并使用诸如 ST2084 PQ 函数之类的传递函数，这使数据能包含很可能远超显示器能力的颜色，以及远高于显示器能力的亮度值（PQ 最高可达 10,000 尼特）。

当 Window COMP 或编辑器窗口被设为使用 HDR 像素格式时，如果操作系统尚未以 HDR 模式运行某台显示器，它会将该显示器切换到该模式，造成屏幕闪烁。不建议在非 HDR 模式下使用 HDR 像素格式，因为显示器可能会在 SDR 和 HDR 模式之间来回闪烁，取决于当前拥有焦点的每个应用程序所运行的格式。

SDR 与 HDR

人们谈论 HDR 时，主要谈的是亮度。HDR 意在让场景的某些部分（例如灯光或太阳）比其他部分亮得多。这是通过把所需的亮度编码进像素数据来实现的，显示器会在有能力时尝试以所需亮度显示它。

这与 SDR 不同，在 SDR 中 (1, 1, 1) 只是显示器在 SDR 模式下能运行的最大亮度。亮度就是显示器设置所设定的任何亮度。

HDR 通常（但并非必须）也意味着比 SDR 常用色域更宽的色域。同样，SDR 也可以有更宽的色域而不属于 HDR。然而如前所述，由于通过线缆不发送关于当前激活的 SDR 色彩空间的任何信息，HDR 也是驱动宽色域数据的更好方式。HDR 颜色可以超过 (1, 1, 1)，使它们变得「过亮」，并让显示器以比落在常规 [0, 1] 范围内的内容更亮的像素来显示。

参考白

参考白，也常称为「纸白」，是一个用于帮助确定 (1, 1, 1) 应该多亮的概念。处理 SDR 内容时，通常 (1, 1, 1) 应显示在 80 到 120 尼特之间，具体取决于房间亮度。而这就是显示器在当前设置下能达到的最亮。创建 SDR 内容时，(1, 1, 1) 用来产生尽可能亮的像素。

参考白也称为纸白，因为在 HDR 模式下 (1, 1, 1) 预期大约与房间里一张白纸一样亮。因此在 HDR 模式下 (1, 1, 1) 并不要求特别亮，而是一种中性白。这使作者可以更容易地超额驱动数值来制造明亮的高光。在 SDR 显示器上混合制作内容时，与 HDR 内容混合可能无法呈现所需的亮度。关于如何在 SDR 与 HDR 内容下控制参考白的亮度，参见 Color Space Workflows 文章。

像素数据

由于 HDR 内容需要能够定义非常亮的颜色，它使用 16 位或 32 位浮点来制作。这允许选择比参考白亮度亮得多的颜色。例如如果 HDR Reference White 设为 120 尼特，那么像素颜色 (10, 10, 10) 应尝试显示为 1200 尼特，前提是显示器能够做到。

HDR 传递函数

两种最流行的 HDR 传递函数是 ST2084 PQ 和 Hybrid Log Gamma 函数。虽然 HDR 内容使用浮点值制作，但通过线缆发送的数据（HDMI/DisplayPort/SDI/ST2110/NDI）以及保存到大多数压缩文件格式（H264、JPEG）的数据只使用定点数据。这意味着 [0, 1] 之外的值无法存储。因此在设计传递函数时，它可能规定 1.0 这个值有多亮。这可以选为任意值。ST2084 PQ 传递选择为 10,000 尼特。HLG 不规定最大值是多少，但内容通常被制作为使 1.0 为 1,000 或 4,000 尼特。

大多数高端内容使用 2084 PQ 传递曲线保存，因为它有明确定义的亮度且最大亮度很高，使其对未来的显示器具备前向兼容性。PQ 编码的内容如果在 SDR 显示器上原样显示而不做任何转换或色调映射，看起来会不正确。HLG 的好处是，在 SDR 显示器上显示时内容看起来仍然「大致还行」。这是因为该曲线的形状与 SDR 曲线大致相同。

由于定点数能表示的值的数量非常有限（例如 10 位只有 1024 个值），而 PQ 的亮度可以从 0 到 10,000，因此使用非线性曲线来编码数据。这样做是因为大多数像素会在 200 尼特或以下，如果亮度按线性分布，那么 10 位数据的 1024 级中只有最低的 20 级会用于大部分内容，造成严重的色带。

PQ 则把前 512 级 [0, 0.5] 编码为大约 0 到 90 尼特，然后从那里急剧上升。0.6 是 245 尼特，0.7 是 621 尼特，0.8 是 1555 尼特，0.9 是 3910 尼特，1.0 是 10,000 尼特。Perceptual quantizer 中的图表显示了这条曲线。

使用这样的曲线还能让内容更具前向兼容性。随着显示器变得更好，更高的亮度值可以被正确显示，而无需重新编码数据。

色调映射与色域映射

色调映射和色域映射是指：对于亮度非常高（色调映射）或颜色深度远超显示器常规能力（色域映射）的内容，设法让它在无法完全按创作原样显示该内容的显示器上看起来也不错。

在理想世界中不需要色调映射和色域映射，显示器可以直接按创作者的意图显示内容。

色调映射

色调映射是一个常与 HDR 内容一起使用的术语。色调映射接收亮度范围很宽的 HDR 内容，并决定如何在能力有限得多的显示器上显示这些信息。它常用于把 HDR 内容显示在 SDR 显示器上。 现在有了真正的 HDR 显示器，色调映射仍可能用于把以某个峰值亮度（比如 4000 尼特）制作的内容映射到显示器的实际峰值亮度（比如 1000 尼特）。为电子游戏校准 HDR 时，校准工具测量的就是显示器实际的峰值亮度能力。 影片文件通常包含有关可用峰值和平均亮度的元数据。有时这些元数据针对整个文件，而其他标准允许它在整个文件中变化。电视有不同的 HDR 设置，用来控制如何利用这些信息把内容色调映射到它自身已知的能力。 没有色调映射时，一个场景中亮度范围在 1000-4000 尼特的区域，在最高 1000 尼特的显示器上只会把整个区域显示成相同的亮度。这在观看者看来会显得发白。色调映射则把该区域重新映射到 700-1000 尼特之间，使亮度变化仍然可感知。

色域映射

色域映射要鲜为人知得多。很可能是因为内容很少使用远离典型显示器可显示范围的颜色来制作。电子游戏通常用 sRGB，而电影和电视等其他媒体通常用 DCI-P3 或 Display-P3。

在 Rec.2020 色彩空间中，(1, 0, 0) 的红色比 sRGB 色彩空间中的 (1, 0, 0) 深得多。例如如果一张图像有从 (0, 0, 0) 到 (1, 0, 0) 的渐变（Rec.2020 色彩空间），在支持 sRGB 的显示器上该如何显示？两种选择：一是直接截断超出范围的颜色，这意味着渐变在约 75%-80% 处就不再有变化的样子；另一种是重新映射渐变，使颜色变化仍贯穿全程，但这意味着没有任何颜色准确代表源素材。与色调映射一样，截断会看起来像图像发白。

工作色彩空间

这很像做测量相关的工作时，需要先就描述事物所用的「单位」达成一致。英尺、米、英寸等等。如果你引入以另一种单位表示的数据，你会希望把它转换为你内部使用的单位，这样这些值在一起才有意义。你不会想把 1 英尺加到 1 米上。 工作色彩空间是项目中用来描述颜色值的「单位」。它定义了 (1, 0, 0) 这个值意味着什么；该用哪种色调的红。所有数据（图像、影片、颜色值）在组合到一起时都需要被转换为同一个色彩空间，这样组合后的颜色才是在同一空间中相加/相乘等。此外，合成始终应使用线性值完成，因此如果颜色是用非线性传递函数定义的，在参与运算前需要先线性化。

TouchDesigner 支持许多工作色彩空间，例如 sRGB、ACEScg Rec.2020、DCI-P3 和 ACES 2065-1。

关于如何选择工作色彩空间，详见 Color Space Workflows 文章。
