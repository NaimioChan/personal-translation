自定义操作符

概述

可以为 TOP、CHOP、SOP 和 DAT 类型创建 Custom OP。Custom OP 是第三方使用 TouchDesigner 的 C++ API 创建的操作符，但它们的表现与 TouchDesigner 内置操作符完全一样。Custom OP 与 CPlusPlus TOP、CPlusPlus CHOP、CPlusPlus SOP 和 CPlusPlus DAT 操作符非常相似，但它们有自己的独特名称，并出现在 OP Create 菜单中，以便更好地融入 TouchDesigner。像普通内置操作符一样使用它们。

安全与防护

由于 Custom OP 是用二进制代码创建的，并且会在 TouchDesigner 中加载和执行，因此它可能包含恶意代码。为应对这一点，在加载任何二进制文件之前，TouchDesigner 会检查该二进制文件是否曾在这台机器上加载过。如果是首次加载，会弹出对话框询问是否允许加载，若允许，则该二进制文件的签名会保存到 plugins 目录下的 .json 文件中。如果二进制文件发生变化，会再次提示用户加载新的二进制文件。

使用 Custom OP - 插件文件夹位置

使用 Custom OP 只需把插件放在磁盘上的正确位置。TouchDesigner 启动时会检测它们。在 Windows 上，插件是一个 .dll 文件，可能还附带一些额外文件。在 macOS 上，插件是一个 .plugin 文件夹。

Windows 上的位置是：
Documents/Derivative/Plugins
通常是：
C:/Users/<username>/Documents/Derivative/Plugins

在 macOS 上，位置是：
/Users/<username>/Library/Application Support/Derivative/TouchDesigner099/Plugins

如果你的计算机上没有这个目录，直接创建它即可。

插件可以直接放在这个目录中，也可以放在 Plugins 内的其他任意命名的目录中，以便按需组织插件。例如，plugins 目录可以包含： 

Documents/Derivative/Plugins/wave2.dll
Documents/Derivative/Plugins/Company1/feature1.dll
Documents/Derivative/Plugins/Company1/feature2.dll
Documents/Derivative/Plugins/Mine/customMerge.dll

由 wave2.dll、feature1.dll、feature2.dll 和 cusotmMerge.dll 定义的 Custom OP 都会被加载。

项目专用的 Custom OP

除了上面列出的系统级 Plugins 文件夹外，还可以在打开的 .toe 文件旁边放置一个 Plugins 文件夹。搜索插件时，除了系统级 Plugins 目录，也会搜索这个目录。

创建 Custom OP

示例项目

在 following Github repository 可以找到一组示例。在 TouchDesigner 安装目录的 Samples/CPlusPlus 文件夹中还有一些更基础的示例。

除了加载方式不同之外，Custom OP 的创建方式与 CPlusPlus TOP、CPlusPlus CHOP、CPlusPlus SOP 和 CPlusPlus DAT 的创建方式相同。更多信息请参阅 Write a CPlusPlus Plugin。

开发 Custom OP 时，把它加载到 CPlusPlus 节点中可能更方便，这样可以在改动代码后更快地重新编译/重新加载插件，而不必每次都重启 TouchDesigner。开发完成后，再用同一个插件作为 Custom OP。

与 TouchDesigner 版本的前向与后向兼容性

Custom Operator 及其所使用的 API 被设计为对未来的 TouchDesigner 版本前向兼容。因此，用旧版 TouchDesigner 头文件制作的自定义操作符插件仍可在新版 TouchDesigner 中工作。即使头文件在版本之间发生了变化，也是如此。

反之则not成立。用新版 TouchDesigner 头文件制作的自定义操作符可能无法在旧版 TouchDesigner 中工作。只要头文件中有任何改动，它就会失效。因此，自定义操作符应针对你想支持的最旧 TouchDesigner 版本所附带的头文件进行编译。

把现有的旧 CPlusPlus 项目转换为 Custom OP

把现有的 CPlusPlus 项目改造成可用作 Custom OP 的项目，速度相对较快。

头文件

首先，从正确 OP 类型的 Samples/CPlusPlus 文件夹中取出 CPlusPlus_Common.h 和 *_CPlusPlusBase.h 头文件（SOP、TOP、CHOP、DAT，而不是 *），替换你正在升级的项目中的对应版本。

插件信息

接下来，你需要把函数 Get*APIVersion() 或 Get*PluginInfo() 替换为一个包含下列签名之一的新函数（取决于节点类型）： 

void FillTOPPluginInfo(TOP_PluginInfo *info);
void FillCHOPPluginInfo(CHOP_PluginInfo *info);
void FillSOPPluginInfo(SOP_PluginInfo *info);
void FillDATPluginInfo(DAT_PluginInfo *info);

该函数用于定义 Custom OP 的名称/标签，以及诸如允许多少输入之类的其他行为。如何填写这个结构的示例可在前面提到的示例文件夹中找到。

发生变化的函数

你的类所覆盖的许多虚函数会多出一些参数，或参数有所调整（例如 const 变化）。大多数情况下，只要让函数签名与父类中的一致，就能通过编译。

OP_String

为了提供更不易出错的接口，凡是从 Custom OP 向 TouchDesigner 返回字符串、且该内存的生命周期需要超出函数调用的情况，都通过给 TouchDesigner 为你提供的 OP_String 对象赋值来实现。例如： 

chan->name = "chan_name";

会变成： 

chan->name->setString("chan_name");

你可能会遇到编译错误，需要把 = 操作替换为 setString() 函数调用来修复。

在 macOS 上使用 XCode 构建

  • 从 Samples/CPlusPlus 目录中打开一个附带的 .xcodeproj 项目。
  • 在「Product」菜单下选择「Archive」。如果构建成功，会弹出一个新窗口，列出已创建的归档，包括刚创建的那个。
  • 选择刚创建的那个，点击「Distribute Content」按钮。在随后弹出的「Select a method of distribution」对话框中，选择「Build Products」，然后点击「Next」。选择一个位置保存归档并完成操作。
  • 在你保存 Build Products 的文件夹中会有一个「Products」文件夹，里面是 projectname.plugin 文件夹。要把这个 .plugin 文件夹放进你的「Plugins」文件夹，才能将它作为 Custom OP 加载。

加载自定义操作符的问题

加载自定义操作符失败时最常见的问题是缺少依赖项。也就是说，自定义操作符需要一些额外的 .dll（Windows）或 .dylib（macOS）文件，例如 openCV .dll，或 CUDA .dll，但在尝试加载自定义操作符时找不到它们。

Windows

在 Windows 上，依赖项应放在自定义操作符的 .dll 旁边，除非自定义操作符的作者另有说明。用于查找 .dll 所需依赖项的非常有用的工具有：
https://github.com/lucasg/Dependencies
https://www.dependencywalker.com/
用这些工具打开插件二进制文件，就能看到该插件依赖、并且需要能够找到才能加载的 .dll。

加密服务的问题

作为加载 .dll 的一部分，我们需要为它创建签名，以便根据你是否同意加载，来验证每次使用的都是同一个 .dll。如果启动时出现无法打开加密服务的错误，有以下几点需要检查：

  • 确认 Cryptography Service 在 Windows 的「Services」小程序中正在运行。
  • 查看 C:/Users/<username>/AppData/Roaming/Microsoft/Crypto/Keys。这里应该有很多文件。用记事本逐个打开，找出包含「ca.derivative.ecdsa384」文本的那个。把该文件移出这个目录，然后再次尝试启动 TouchDesigner。

延迟加载的库

在 Windows 上构建 .dll 时，它所依赖的其他 .dll 可以设为「延迟加载」（Delay-Loaded）。这是 Visual Studio 项目文件中的一个选项，或命令行上的 /DELAYLOAD。

当 .dll 被指定为延迟加载时，意味着直到执行到真正需要该 .dll 的代码时（例如使用了 .dll 中定义的函数，或使用了该 .dll 定义的类型），才会加载 .dll。这适用于该 .dll 可能并不存在，或你只想在满足特定条件时才让它加载的情况。例如，某个 SDK 提供的 .dll 需要系统上安装驱动（通常在 C:/Windows/System32 中）。

例如，假设 SDK 文件是 SDK.dll，驱动是 Driver.dll，而 SDK.dll 对 Driver.dll 有常规依赖（非延迟加载）。 如果不处理这种情况，你的 Custom Operator 在缺少 Driver.dll 的系统上会完全加载失败。在 Visual Studio 项目中，你可以把 SDK.dll 指定为「延迟加载」。这样自定义操作符就能加载了，但一旦你使用 SDK.dll 提供的任何内容，应用就会崩溃，因为缺少 Driver.dll 会导致 SDK.dll 加载失败。为避免这种情况，应先通过以下方式检查 Driver.dll 是否存在 

 HMODULE lib = LoadLibrary(L"Driver.dll");
 if (lib)
 {
   // 找到 Driver.dll，就可以使用 SDK.dll
 }

这项检查只应做一次，通常放在 Custom Operator 的构造函数中。

延迟加载 .dll 的另一个陷阱是：Custom Operator 插件初次加载时，会在该 .dll 旁边查找依赖的 .dlls，但对延迟加载的 .dlls 并非如此。那个目录不会被搜索。为确保延迟加载的 .dll 能被找到，应在使用该 .dll 中会触发其加载的内容之前，先用 LoadLibrary() 把它们手动加载到进程中。

macOS

如果插件需要链接其他 .dylibs 或框架，它们应包含在插件包中。链接的细节取决于所用的库，也在一定程度上取决于个人偏好，但我们建议使用 rpath 按以下方式操作：

插件构建设置：

  • 在 Xcode 中插件目标的 General 标签页里，把库或框架添加到 Frameworks and Libraries 部分，并确保选中「Embed & Sign」
  • 在 Xcode 中插件目标的 Build Settings 标签页里，为 @loader_path/../Frameworks 添加 Runpath Search Paths 设置，使构建出的插件能用 @rpath 前缀定位库

库或框架设置：

  • 如果你用 Xcode 自行构建库或框架，请把它的 Dynamic Library Install Name Base（在 Xcode 中目标的 Build Settings 里）设为 @rpath，这样计算出的 install name 就是 @rpath/libYourLibrary.dylib（框架则是 @rpath/YourFramework.framework/Versions/A/YourFramework）。如果你使用其他构建系统，通常也会有实现同样效果的设置
  • 如果你使用的是预构建的第三方库或框架，无法改变其构建过程，请修改它的 linker ID，构建插件时链接器会将其嵌入，以便加载时能够定位。它可能已经配置为使用 rpath——可以用 otool -D libYourLibrary.dylib 检查——如果输出显示 @rpath/libYourLibrary.dylib，则无需改动。如果没有，可以用 install_name_tool -id @rpath/libYourLibrary.dylib libYourLibrary.dylib 修改其 ID。

你可以用 otool -L YourPlugin.plugin/Contents/MacOS/YourPlugin 检查已构建插件的链接情况

开源操作符

TouchDesigner 自带的一些操作符是开源的，例如 NVIDIA RTX Video TOP。这让你可以自行修改/调整该节点的行为，以满足特定需求。如果你希望这些改动成为软件自带默认节点的一部分，也欢迎提交 pull request。请注意，这些特定节点可以遵循内部节点与参数的命名标准，允许首字母小写。

要覆盖 TouchDesigner 自带版本的节点，请把你的插件副本放在系统级 Plugins 目录中，如本文前面所述。Project/Plugins 文件夹不能用作覆盖，因为它的加载更晚，在内置 Custom Operator 加载之后。
