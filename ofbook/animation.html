动画

作者：Zach Lieberman

tpltnt、Kayla Lewis 参与修订

背景

animation 一词是中世纪术语，源自拉丁语 animare，意思是“注入生命”。在现代语境中，它用来描述从静止的连续图像中创造出运动的过程。早期的动画创作者使用旋转的圆盘（费纳奇镜）和圆筒（西洋镜），配合连续的画面，借视觉暂留制造出平滑运动的错觉。到了现代，我们已经很熟悉其它技术，比如翻页动画书，以及像定格动画这样的电影技法。越来越多的艺术家开始用计算技术来创作动画——用代码在连续帧中让屏幕上的对象“活起来”。本章将探讨这些技术，并特别尝试回答一个核心问题：我们如何通过代码创造出引人入胜、有机、甚至荒诞的运动？

顺便说一句，我学的是美术、绘画和版画，用上电脑纯属偶然。当我第一次看到可以写代码让某个东西在屏幕上移动——哪怕只是一个傻傻的矩形——我就迷上了。我是在第一次互联网泡沫时期入行的，用 Flash / ActionScript 和 Lingo / Macromedia Director 工作，从此再没回过头。

本章会先解释一些有助于理解 oF 中动画的基本原理，然后尝试给出几个通往有趣方法的入口。

oF 中的动画 / 有用的概念：

绘制循环

关于动画的第一点是：它基于连续的静止帧。在 openFrameworks 中，我们有一个大致基于游戏编程范式的循环。它长这样：

  • setup()
  • update()
  • draw()
  • update()
  • draw()
  • ...

其中 setup() 函数在 oF 应用生命周期开始时只调用一次，而 update() 和 draw() 会被反复调用。有时人们会问，为什么要有两个函数被反复调用，尤其是那些熟悉 Processing 的人——它只有一个 setup 和一个 draw 命令。原因有几点。第一，OpenGL 中的绘制是异步的，也就是说，当你把绘制代码交给电脑时，它可能把执行权交还给你的程序，让程序在绘制的同时做别的事。第二，把绘制代码和非绘制代码分开通常非常实用。如果你需要快速调试——比如代码跑得很慢——你可以把 draw 函数注释掉，只让 update 继续跑。这实际上是把世界的更新与呈现分离开，往往有助于清理和组织代码。可以把它想成一位逐帧动画师，用一台俯拍摄影机：在摄影机不拍摄时摆弄物体，等一切就绪的瞬间按下快门。在 update 函数里你移动东西，在 draw 函数里你按那一刻的样子把东西画出来。

变量

关于动画的第二点是：它需要变量。变量是某个值的占位符，意思是你可以把值放进去，也可以把值取出来。变量对动画至关重要，因为它们在帧与帧之间“持有”值——例如，你在 setup() 函数或 update() 函数里把值放进变量，也可以在 draw() 函数里从内存中把它取出来。看这个例子，其中 xPos（int）已经在头文件中定义：

void ofApp::setup(){
    xPos = 5;  // 水平起始位置
    ofBackground(ofColor::black);  // 黑色背景
}

void ofApp::update(){
    xPos += 2;
    if(xPos > ofGetWidth()){  // 如果水平位置超出了屏幕（宽度）
        xPos = 5;             // 重置水平位置
    }
}

void ofApp::draw(){
    ofSetColor(ofColor::red);  // 所有东西都用红色绘制
    ofDrawCircle(xPos, 100, 10);   // 在（变化的）水平位置画一个圆，距顶部 100 像素，直径 10 像素
}

在这个例子里，一个红色圆点从屏幕左侧移动到右侧。水平位置（xPos）是整数，在 setup() 里被设为初始值 5。而 update() 函数每次都给 xPos 变量加 2，并保存新值，直到它大于屏幕宽度（ofGetWidth()），然后重置水平位置。draw() 函数读取 xPos 变量里存的值，据此绘制红色圆点。

帧率

关于 oF 与动画的第三点是帧率。我们在 openFrameworks 中用连续的帧来制作动画。帧率指的是帧被绘制的速度。oF 中有几个重要函数需要了解。

  • ofGetFrameRate() 返回当前帧率（单位为帧/秒）。
  • ofSetFrameRate( float targetFrameRate ) 设置最大帧率。如果软件动画得比这个更快，ofSetFrameRate 会把它降下来。可以把它想成限速。它不会让你更快，但会阻止你跑得太快。把值设为 0 表示尽可能快地运行。

另外，OpenGL 与输出显示配合工作，会尝试与显示器的刷新率同步——有时称为垂直同步或垂直消隐。如果你不与刷新率同步，就会出现所谓的帧撕裂：不同步意味着帧可能在一次变化之前和之后被绘制。这会产生水平的不连续线条，称为屏幕撕裂。

上图来自 Vanessaezekowitz，以 CC-BY-SA 3.0 许可协议发布。

oF 中有一个函数可以控制这一点。有些显卡驱动（例如 Nvidia 的 PC 驱动）的设置会覆盖应用程序的设置，所以请务必检查你的驱动选项。

  • ofSetVerticalSync (bool bUseSync) 设为 true 表示垂直同步，设为 false 表示尽可能快地绘制。

默认情况下，oF 启用垂直同步并把帧率设为 60 FPS。如果你想动画得更快，可以调整 VSYNC 和帧率设置，但请注意 oF 默认希望尽可能快地运行。如果你绘制一个简单场景而没有启用 VSYNC（并且帧率上限设得很高或已禁用），看到 800 FPS 的帧率并不罕见。

另一个重要但本章难以深入展开的点是帧率无关性。如果你用简单的模型做动画——比如创建一个名为 xPos 的变量，每帧给它增加固定的量然后绘制。

void ofApp::setup(){
    xPos = 100;
}

void ofApp::update(){
    xPos += 0.5;
}

void ofApp::draw(){
    ofRect(xPos, 100, 10, 10);
}

这种动画没问题，但它假设帧率是恒定的。如果你的应用跑得更快，比如从 30 FPS 跳到 60 FPS，对象看起来会快一倍，因为每秒调用 update 和 draw 的次数变成了 2 倍。通常更复杂的动画会考虑这一点，方法是使用时间之类的函数（下文会讲），或者把帧率或经过时间混入 update 中。例如，一种解法可能是这样：

void ofApp::update(){
    xPos += ofGetLastFrameTime() * speed;
}

这里 ofGetLastFrameTime() 返回完成上一帧所花的时间。既然系统里已经过去了这么长时间，我们就用它乘以速度。这样得到的就是矩形（虚拟地）走过的距离。现在无论帧率如何，它实际上都以相同的速度移动。等你上手之后，帧率无关性是相当重要的考虑因素。作为动画的观察者，我们真的能感觉到物体哪怕很轻微地加速或减速，但为了代码简洁，本章会跳过它。

时间函数

最后，还有几个对动画计时有用的函数：

  • ofGetElapsedTimef() 以浮点数返回经过的时间，从应用启动时的 0 开始。
  • ofGetElapsedTimeMillis() 类似，以毫秒为单位返回从 0 开始的经过时间。
  • ofGetFrameNum() 返回软件已经绘制的帧数。比如你想每隔一帧做一件事，可以用取模运算符，例如 if (ofGetFrameNum() % 2 == 0)。

对象

在这些例子里我会大量使用对象。熟悉面向对象编程（OOP）对理解代码很有帮助。用得很多的一个对象是 ofPoint，它包含 x、y、z 三个变量。过去它叫 "ofVec3f"（由三个浮点数组成的 vector），但我们只用更方便的 ofPoint。在一些动画代码里你会看到用到 vector，你应该知道 ofPoint 本质上就是一个 vector。

你还会看到一些带有基本功能和内部变量的对象。我通常会在里面放 setup、update 和 draw。很多时候，写这些对象要么是因为它们是往屏幕上放很多东西的实用配方，要么是因为它们能把所有变量和运动逻辑集中在一处。我喜欢让 ofApp 这一层的代码尽可能少。如果你熟悉 ActionScript / Flash，这就相当于尽量少往主时间轴里放东西。

线性运动

从 a 点到 b 点

谈到动画，最重要的事情之一就是回答一个简单的问题：

如何从 A 点到达 B 点？

本章我们会看运动的动画（随时间改变位置），但同样可以做任何其它数值属性的动画，比如颜色、绘制形状的宽高、圆的半径等等。

动画的第一课，也许也是最重要的一课是：我们热爱0 到 1 之间的数字。

0 到 1 之间的数字的好处是，它们非常适合以有趣的方式使用。我们通常把这类数字称为百分比，你会在代码里看到我用简写 pct，它是一个 0 到 1 之间的浮点数。如果我们要从 A 点走到 B 点，就可以用这个数字来决定用多少比例的一个点和多少比例的另一个点。公式是：

((1-pct) * A) + (pct * B)

更具体地说，如果从 A 到 B 的进度是 0 pct，我们算出

((1-0) * A) + (0 * B)

化简后是 (1*A + 0*B)，也就是 A。如果我们走了 25%，则写成

((1-0.25) * A) + (0.25 * B)

即 A 的 75% 加上 B 的 25%。本质上，通过取一个混合，你就从一个值过渡到另一个值。第一个例子（1_rectangleInterpolate）演示了怎么做。

这个例子里，我们会用一个叫 "rectangle" 的对象。它有一个表示位置的变量，另外还有两个变量（posA 和 posB），代表我们移动的起点 a 和终点 b。

#include "ofMain.h"

class rectangle {

    public:

        rectangle();
        void draw();
        void interpolateByPct(float myPct);

        ofPoint pos;
        ofPoint posa;
        ofPoint	posb;
        float pct;	// 我们在 "a" 与 "b" 之间的百分比位置是多少
};

函数 interpolateByPct() 完成实际的插值：

void rectangle::interpolateByPct(float myPct){
	pos.x = (1-pct) * posa.x + (pct) * posb.x;
	pos.y = (1-pct) * posa.y + (pct) * posb.y;
}

在 ofApp 文件里，我们创建一个叫 pct 的变量并设为 0。每帧我们递增 pct，并在 update 函数里把它传给 rectangle 对象：

pct += 0.01f;		// 每次增加一定的量
if (pct > 1) {
	pct = 0;	// 保持在 0 和 1 之间（0% 和 100%）
}
myRectangle.interpolateByPct(pct);	// 在 pta 与 ptb 之间移动

曲线

0 到 1 之间的数字有一个有趣的特性：它们很容易被调整 / 曲线化。

最容易的办法是把这个数字求幂。你可能还记得数学课上的幂，就是让一个数自乘，例如 2^3 = 2*2*2 = 8。0 到 1 之间的数字有一些有趣的性质。0 的任何次幂都等于 0（0*0*0*0 = 0）。1 也一样（1*1*1*1 = 1），但把 0 到 1 之间的数字求幂，它就会变。例如 0.5 的 2 次幂 = 0.25。

来看看 pct 的 2 次幂的图：

这张图展示了一条数学函数的图像，即 f(x) = y = x²。把图的 x 值（横轴）当作输入，y 值当作输出（纵轴）。输入 0，得到 y 值 0；输入 0.1，得到 y 值 0.01；一直到输入 1 得到 1。不同的数学函数会给出不同的曲线，因此也有不同的映射行为。

顺便说一句，要注意现实世界中的东西往往不是线性运动的。它们不会走“均匀”的步子。在地板上滚一个球，它会慢下来——它在朝负方向加速。有时候东西会加速，比如棒球棒从静止到挥出。把 pct 曲线化会带来有趣的行为。物体到达目的地所花的时间仍然一样，但它们是以更接近生命、非线性的方式完成的。

如果把 0 到 1 之间的输入数字求更高的幂，曲线看起来会更极端。有趣的是，如果把这个 0 到 1 之间的值求分数（有理）次幂（即次幂小于 1 大于 0），它会朝另一个方向弯曲。

用曲线来控制变化是动画中非常重要的原则。它被称为“缓入缓出”，并被明确列为著名的“动画十二基本原则”之一，这些原则出自 Ollie Johnston 和 Frank Thomas 1981 年所著的《The Illusion of Life: Disney Animation》。它基本上是说，物体改变速度天然需要时间，因此在极端位置（发生变化的地方）附近的运动会比运动中间段（没有或较少变化的地方）更慢。

把百分比求幂只是被称为“塑形函数”或“缓动方程”的一大类函数中的一种。Robert Penner 写过并推导了许多这类函数，所以它们也常被称为“Penner 缓动方程”。Easings.net 是一个不错的资源，另外还有几个用于缓动的 openFrameworks addon（例如 ofxEasingFunc）。

芝诺

线性插值的一个小变体，是我称为“Zeno”的技术，它基于 Zeno of Elea 的 二分法悖论：

想象一场赛跑，跑者用一定时间跑完一半的距离，然后用同样的时间跑完剩下距离的一半，再跑完再剩下距离的一半，依此类推。他能跑完吗？总还剩下一段距离可以再分一半。这个想法是说，距离总可以一直切分下去。

如果我们拿线性插值的代码，但改成总是调整自己的位置（例如取当前位置的 50% 加目标位置的 50%），我们就能从一个值动画到另一个值。我在课上通常这样解释这个算法，请某个人来做：

  1. 站在你房间里的某个位置。
  2. 选一个要去的点。
  3. 计算你当前位置和那个点之间的距离。
  4. 朝它走近 50%。
  5. 回到（3）。

在代码里，这基本上就等于说

currentValue = currentValue + ( targetValue - currentValue ) * 0.5.

这里 targetValue - currentValue 就是距离。你也可以改变每次迈出的步子大小，例如用 10% 而不是 50% 的步子：

currentValue = currentValue + ( targetValue - currentValue ) * 0.1.

把表达式展开，你也可以这样写：

currentValue = currentValue * 0.9 + targetValue * 0.1.

这是一种平滑：你取当前值的某个百分比，再取目标值的另一个百分比，把它们相加。这些百分比加起来必须是 100%，所以如果你取当前位置的 95%，就需要取目标的 5%（例如 currentValue * 0.95 + target * 0.05）。

在芝诺悖论里，你其实永远到不了目标，因为总还剩一段距离。在电脑上，由于我们处理的是屏幕上的像素位置和特定范围的浮点数，物体看起来就停住了。

在第 5 个例子（5_rectangleZeno）里，我们给 rectangle 加了一个函数，用 zeno 追上一个点：

void rectangle::zenoToPoint(float catchX, float catchY){
    pos.x = catchUpSpeed * catchX + (1-catchUpSpeed) * pos.x;
    pos.y = catchUpSpeed * catchY + (1-catchUpSpeed) * pos.y;
}

这里有一个值 catchUpSpeed，表示我们追上目标物体的速度。示例代码里它被设为 0.01（1%），意思是取自己位置的 99%、目标位置的 1%，移动到两者之和。改变这个数字，你会看到矩形追上鼠标更快或更慢。值为 0.001 表示慢 10 倍，值为 0.1 表示快 10 倍。

如果你处理的是有噪声的数据——比如传感器——这个技术非常有用。你可以创建一个变量，用 zeno 去追它，把结果平滑掉。我在做硬件传感器 / 物理计算，或者手上数据有噪声时经常这么做。好处是追赶速度变成了一个旋钮，你可以在更实时（数据更嘈杂）和更不实时（数据更平滑）之间调节。有这种控制力相当方便！

基于函数的运动

在本书这一节里，我们看几个展示基于函数运动的例子，也就是用一个函数接收某些输入、返回输出，我们拿输出来做动画。输入方面，我们会传入计数器、经过时间、位置，输出则用来控制位置。

正弦与余弦

在 openFrameworks 里试验运动的另一个有趣而简单的系统，是用 sin(...) 和 cos(...)。

sin(...) 与 cos(...)（正弦和余弦）是三角函数，也就是说它们基于角度。它们是绕圆以恒定半径和速率运动的一个点的 x、y 坐标。这个圆是半径（r）为 1 的单位圆，因此周长是 2*r*PI 或 2*PI。在 oF 里你会看到这个常量写作 TWO_PI，即 6.28318……

顺便说一句，oF 里有些函数用角度制、有些用弧度制，有时容易混淆。sin(...) 与 cos(...) 属于数学库，所以用弧度，而 OpenGL 里大多数旋转用角度制。我们有一些辅助常量，比如 DEG_TO_RAD 和 RAD_TO_DEG，可以帮你互相转换。

下面这张简单的图有助于解释正弦和余弦。

你只需要想象一个单位圆，半径为 1，圆心在 0,0。然后想象一个点以恒定的速度和距离绕这个圆心逆时针运动。如果你看这个点的高度，它从最右边（3 点钟位置）的 0，升到顶部（12 点钟）的 1，回到左边（9 点钟）的 0，再降到最下面（6 点钟）的 -1。所以它是一条在 -1 和 1 之间来回的平滑曲线。就这样。正弦是这个点的高度，余弦是这个点的水平位置。在最右边，这个点的高度是 0，水平位置是 1。当正弦是 1 时，余弦是 0，等等。它们是同步的，只是有偏移。

简单例子

用 sin(...) 来为对象的位置做动画相当容易。

这里我们取经过时间的正弦 sin(ofGetElapsedTimef())。它返回 -1 到 1 之间的数，每 6.28 秒循环一次。我们可以用 ofMap 把它映射到新的范围。例如

void ofApp::draw(){
    float xPos = ofMap(sin(ofGetElapsedTimef()), -1, 1, 0, ofGetWidth());
    ofRect(xPos, ofGetHeight()/2, 10,10);
}

这会绘制一个正弦式地横穿屏幕的矩形，每 6.28 秒来回一次。

你可以用相位偏移（正弦波被移动了多少）做一点简单的事。在例子 7（7_sinExample_phase）里，我们计算了两次时间的正弦，但第二次加了 PI：ofGetElapsedTimef() + PI。这意味着两个值在圆上彼此相差 180 度（想象那个点：一个在最右时另一个在最左，一个在上面时另一个在下面）。这里我们用这两个偏移值设置背景色和一个矩形的颜色。当你开始用正弦和余弦摆弄相位时，这很有用。

//--------------------------------------------------------------
void ofApp::draw(){
    float sinOfTime               = sin( ofGetElapsedTimef() );
    float sinOfTimeMapped         = ofMap(sinOfTime, -1, 1, 0, 255);

    ofBackground(sinOfTimeMapped, sinOfTimeMapped, sinOfTimeMapped);

    float sinOfTime2              = sin( ofGetElapsedTimef() + PI);
    float sinOfTimeMapped2        = ofMap(sinOfTime2, -1, 1, 0, 255);

    ofSetColor(sinOfTimeMapped2, sinOfTimeMapped2, sinOfTimeMapped2);
    ofRect(100,100,ofGetWidth()-200, ofGetHeight()-200);
}

再讲个偏门的细节：浮点数并不是线性地均匀精确，比如 0.0 和 1.0 之间的浮点数个数与 100.0 和 101.0 之间的并不相同。浮点数越大，精度损失越多，所以取经过时间的正弦，运行一段时间后可能就开始显得粗糙了。对于长时间运行的装置，我有时会写这样的代码 sin((ofGetElapsedTimeMillis() % 6283) / 6283.0) 或类似的东西来应对这一点。尽管 ofGetElapsedTimef() 随时间变大，它作为 sin(...) 的输入就越来越糟。ofGetElapsedTimeMillis() 没有这个问题，因为它是整数，0 到 10 之间的整数个数与 1000 到 1010 之间的相同。

圆周运动

既然正弦和余弦来自圆，我们就可以用它们让东西做圆周运动。我们有四个变量需要知道：

  • 圆心（xOrig，yOrig）
  • 圆的半径（radius）
  • 绕圆的角度（angle）

公式相当简单：

xPos = xOrig + radius * cos(angle);
yPos = yOrig + radius * sin(angle);

这样我们就能做出圆周运动的东西。在圆的例子里（12_sinExample_circlePlusPath），我会用这种方式做动画。

float xorig = 500;
float yorig = 300;
float angle = ofGetElapsedTimef()*3.5;
float x = xorig + radius * cos(angle);
float y = yorig + radius * sin(angle);

注意：在 oF 里，左上角是 0,0（y 轴向下递增），所以你会注意到点沿顺时针而不是逆时针运动。如果这让你不舒服（毕竟上面我让你想象它逆时针运动），你可以把这一行 float y = yorig + radius * sin(angle) 改成 float y = yorig + radius * -sin(angle)，就能看到圆朝逆时针方向走。

在这些例子里，我开始用 ofPolyline 对象给物体加一条“轨迹”。我不停地加点，加到一定数量后删掉最旧的。这有助于我们更好地看清物体的运动。

如果我们增大半径，比如这样做：

void ofApp::update(){
    radius = radius + 0.1;
}

就会得到螺旋。

利萨如图形

最后，如果我们以不同的速率改变传给这个公式中 x 和 y 的角度，就能得到有趣的图形，称为“Lissajous”图形，以法国数学家 Jules Antoine Lissajous 命名。这些公式看起来很酷。我常在算法课上跟学生开玩笑说，这其实是一门做酷炫屏保的课。

噪声

噪声和正弦/余弦类似，也是一个接收输入、产生输出的函数，我们可以拿输出来做运动。正弦/余弦的情况是传入一个角度，得到在 -1 和 1 之间来回的结果。在 openFrameworks 里，我们封装了 simplex 噪声，它可与 Perlin 噪声相比，我们有一个函数 ofNoise() 接收输入并产生输出。两种算法（Perlin、Simplex）都提供伪随机噪声图案——它们对动画很有用，因为它们是连续函数，不像 ofRandom 那样只返回随机值。

我说连续函数，意思是如果你传入的输入变化更小，输出变化也更小；传入相同的值就得到相同的结果。例如 sin(1.7) 总是返回同一个值，ofNoise(1.7) 也总是返回相同结果。同样，如果你调用 sin(1.7) 和 sin(1.75)，得到的结果是连续的（意思是你可以调用 sin(1.71) sin(1.72)... sin(1.74) 来获得中间结果）。

用 ofNoise 也能做同样的事——这里我写一个 for 循环把噪声画成一条线。ofNoise 接收一个输入——这里是 i/10——产生一个 0 到 1 之间的输出。ofSignedNoise 类似，但输出在 -1 和 1 之间。

ofBackground(0,0,0);
ofSetColor(255);

ofNoFill();
ofBeginShape();
for (int i = 0; i < 500; i++){
    float x = i;
    float noise = ofNoise(i/10.0);
    float y = ofMap(noise, 0,1, 0, 100);
    ofVertex(x,y);
}
ofEndShape();

如果你改动 i/10.0，就能调整噪声的尺度：要么放大（即 i/100.0），看到更多细节；要么缩小（即 i/5.0），看到更多变化。

我们可以用噪声做动画。例如这里，我们用噪声在屏幕上移动一个物体：

float x = ofMap( ofNoise( ofGetElapsedTimef()), 0, 1, 0, ofGetWidth());
ofDrawCircle(x,200,30);

如果我们用噪声来移动 y，可以取一个离 x 值“较远”的噪声输入值，也就是在这条曲线上更靠后的位置：

float x = ofMap( ofNoise( ofGetElapsedTimef()), 0, 1, 0, ofGetWidth());
float y = ofMap( ofNoise( 1000.0+ ofGetElapsedTimef()), 0, 1, 0, ofGetHeight());
ofDrawCircle(x,y,30);

另外，ofNoise 支持多个维度。下面是一个快速草图，用 ofNoise 的 2D 维度让某个东西沿路径移动：

这个例子的代码（注意 ofNoise 有两个输入，这是一次二维噪声调用。它让我们可以用相同的时间值，却得到不同的结果）：

//--------------------------------------------------------------
void ofApp::setup(){
    ofBackground(0);
    ofSetBackgroundAuto(false);
}

//--------------------------------------------------------------
void ofApp::update(){
}

//--------------------------------------------------------------
void ofApp::draw(){

    float x = ofMap( ofNoise( ofGetElapsedTimef()/2.0, -1000), 0, 1, 0, ofGetWidth());
    float y = ofMap( ofNoise( ofGetElapsedTimef()/2.0, 1000), 0, 1, 0, ofGetHeight());
    ofNoFill();
    ofDrawCircle(x,y,3);

}

噪声还能做非常多的事，这里先放下，但鼓励你去看看 openFrameworks 自带的噪声例子，它们展示了如何用噪声创造栩栩如生的运动。另外，我们也鼓励读者去看看 Ken Perlin 的作品，他是 simplex 噪声算法的作者——他有很多很好的例子，展示如何创造性地、顽皮地使用噪声。

模拟

如果你有一张某个物体在某个时刻的照片，你就知道它的位置。如果你有它在另一个时刻的照片而相机没动，你就能测出它的速度，也就是距离随时间的变化。如果你有三个时刻的照片，你就能测出它的加速度，也就是速度随时间变化了多少。

把这些单独的测量放在一起比较，能告诉我们一些关于运动的信息。现在我们要反着来：想想如何用速度和加速度这样的测量值来控制位置。

如果你知道一个物体跑得多快，就能确定它在某段时间里走了多远。例如，你以每小时 50 英里（约 80 公里/小时）开车，一小时走了多远？很简单，走了 50 英里。两三个小时呢？有一个简单的公式可以算出这段距离：

position = position + (velocity * elapsed time)

例如：

position = position + 50 * 1;   // 跑了一小时

或者

position = position + 50 * 2;   // 开了两小时的车

关键表达式——position = position + velocity——简写就是 p=p+v。

注意经过时间这一项很重要。做动画时我们会经常写 p=p+v，你可能会看到我们为了简化而把它省掉（假设每帧的经过时间都是 1）。这不完全准确，但能让事情简单。更多细节见前面关于帧率（以及帧率无关性）的一节。

另外，如果你以每小时 50 英里行驶（向所有用公里思考的人致歉！），并且每小时加速 5 英里，1 小时后你开多快？答案是 55 mph。2 小时后是 60 mph。在这些例子里，你做的是：

velocity = velocity + acceleration

简写就是 v=v+a。于是我们有两个基于速度来描述运动的重要方程：

p = p + v;   // position = position + velocity
v = v + a;   // velocity = velocity + acceleration

了不起的地方在于，我们刚刚描述了一个可以用加速度控制位置的系统。这为什么有用？如果你还记得物理课，这有用是因为牛顿的运动定律非常简单，其中第二定律说

Force = Mass x Acceleration

简写为 F = M x A。这意味着力和加速度是线性关系。如果我们假设物体质量为 1，那么力就等于加速度。这意味着我们可以用力控制速度，用速度控制位置。

酷、奇妙又漂亮的地方在于，我们能对物体施加很多种力，比如弹簧力、排斥力、对齐力等等。

我有几个用这种方法的粒子例子，虽然不会深入讲，但我会试着解释其中一些你可能觉得有趣的想法。

粒子类

所有例子里的 particle 类都设计得相当直白。来看看头文件（.h）：

class particle{

    public:
        ofVec2f pos;
        ofVec2f vel;
        ofVec2f frc;

        particle();
        void setInitialCondition(float px, float py, float vx, float vy);

        void resetForce();
        void addForce(float x, float y);
        void addDampingForce();

        void update();
        void draw();

        float damping;
};

变量方面，它有 ofPoint 对象来表示位置、速度和力（缩写为 pos、vel 和 frc）。它还有一个阻尼（damping）变量，表示这个物体随时间减慢的程度。阻尼为 0 意味着完全不减速，阻尼越高就越像加了更多摩擦——想象在冰面、水泥地或沙地上滚球，减速的速率各不相同。

函数方面，它有一个构造函数，用来设置一些内部变量，比如 damping 和一个 setInitialCondition(...)，让你设置粒子的位置和速度。可以把它理解为设定初始状态，之后就任粒子自行演化。接下来的三个函数与力有关（后面还会看到更多）——第一个 resetForce() 会清空内部的力变量 frc。力不会跨帧累积，所以每帧开始时我们清空它。addForce(...) 在给定方向上施加一个力，适合恒定的力，比如重力。addDampingForce() 施加一个与速度方向相反的力（阻尼就是与运动方向反向的力）。最后，update 把力加到速度上，把速度加到位置上。draw 只是在位置处画一个点。

这个粒子类非常简单，在这些例子里我们逐步给它增加复杂度。总的来说，你在所有例子里都会看到的公式是

for (int i = 0; i < particles.size(); i++){
    particles[i].resetForce();
}

// <------ 魔法就发生在这里 --------->

for (int i = 0; i < particles.size(); i++){
    particles[i].update();
}

奥妙就发生在 resetForce() 和 update() 之间。这些例子虽然越来越复杂，但做法只是给粒子类加新函数、在 reset 和 update 之间加更多东西。

这是 '19_multiParticles' 例子的运行效果。

简单的力：排斥与吸引

在接下来几个例子里，我给粒子对象加了几个函数：

void addRepulsionForce( float px, float py, float radius, float strength);
void addAttractionForce( float px, float py, float radius, float strength);
void addClockwiseForce( float px, float py, float radius, float strength);
void addCounterClockwiseForce( float px, float py, float radius, float strength);

它们本质上是在施加让粒子朝向或远离你传入的某个点的力，至于顺时针的力，则是绕着一个点。

这些力的计算相当直接——首先算出某个点离力的中心有多远。如果它在作用半径之外，就忽略它。如果在里面，就算出它的百分比，即力与粒子之间的距离除以作用半径。这样得到的数字在靠近圆的外缘时接近 1，靠近中心时接近 0。如果取 1 - 百分比把它反过来，就得到外侧小、越靠近中心越大的数字。

这很有用，因为力往往与距离成比例。例如磁力有一个作用半径，你离磁铁越近，力就越强。

快速看一下其中一个施加力的函数：

void particle::addAttractionForce( float px, float py, float radius, float strength){

    ofVec2f posOfForce;
    posOfForce.set(px, py);
    ofVec2f diff = pos - posOfForce;

    if (diff.length() < radius){
        float pct = 1 - (diff.length() / radius);
        diff.normalize();
        frc.x -= diff.x * pct * strength;
        frc.y -= diff.y * pct * strength;
    }
}

diff 是粒子到力所在位置的一条线。如果 diff 的长度小于半径，我们算出一个 0 到 1 之间的 pct（在作用半径外侧是 0，靠近力的中心是 1）。我们取这条 diff 线并归一化，得到一个“有方向”的 vector，它的长度（距离）是 1，但角度还在。然后把它乘以 pct * strength，得到一条告诉我们如何移动的线。它被加到我们的力上。

你会注意到所有代码都差不多，只是往力上加的东西不同。例如排斥就是吸引的反向：

frc.x += diff.x * pct * strength;
frc.y += diff.y * pct * strength;

我们只是朝相反方向移动。至于顺时针和逆时针的力，我们加上 diff 线的垂直向量。二维 vector 的垂直向量很简单，就是把 x 和 y 交换，再让其中一个取负。

这是 '22_particle_particle' 例子的运行效果。

粒子交互

现在粒子已经能和力交互了，下一步是让它们更多地感知彼此。例如，如果你有一个范围很大的吸引力，它们会全都汇聚到同一个点，完全不理会邻居。诀窍是加一个函数，让粒子能根据邻居感受到力。

我们给粒子对象加了新函数（见头文件）：

void addRepulsionForce(particle &p, float radius, float scale);
void addAttractionForce(particle &p, float radius, float scale);

这看起来和前面的代码很像，只是这里传入的是一个粒子而不是 x、y 坐标。你会注意到我们用的是传引用（用 &）而不是传副本。这是因为内部我们会同时修改调用这个函数的粒子以及粒子 p——也就是说，如果你算了 A 对 B，就不需要再算 B 对 A。

void particle::addRepulsionForce(particle &p, float radius, float scale){

    // ----------- (1) 构造一个表示粒子 p 所在位置的 vector：
    ofVec2f posOfForce;
    posOfForce.set(p.pos.x,p.pos.y);

    // ----------- (2) 计算差值 & 长度
    ofVec2f diff    = pos - posOfForce;
    float length    = diff.length();

    // ----------- (3) 检查是否足够近
    bool bAmCloseEnough = true;
    if (radius > 0){
        if (length > radius){
            bAmCloseEnough = false;
        }
    }

    // ----------- (4) 如果够近，就更新力
    if (bAmCloseEnough == true){
        float pct = 1 - (length / radius);  // 越靠内侧越强
        diff.normalize();
        frc.x = frc.x + diff.x * scale * pct;
        frc.y = frc.y + diff.y * scale * pct;
        p.frc.x = p.frc.x - diff.x * scale * pct;
        p.frc.y = p.frc.y - diff.y * scale * pct;
    }
}

代码应该和之前非常像，只是多了这几行：

frc.x = frc.x + diff.x * scale * pct;
frc.y = frc.y + diff.y * scale * pct;
p.frc.x = p.frc.x - diff.x * scale * pct;
p.frc.y = p.frc.y - diff.y * scale * pct;

这会同时修改你调用该函数的粒子以及被传入的粒子。

这意味着我们可以减少需要计算的粒子交互数量：

for (int i = 0; i < particles.size(); i++){
    for (int j = 0; j < i; j++){
        particles[i].addRepulsionForce(particles[j], 10, 0.4);
    }
}

你会注意到在这个二维 for 循环里，内层循环只数到外层循环，所以当 i 为 0 时，内层循环根本不执行。当 i 为 1 时，我们把它和 0 比较（1 对 0）。当 i 为 2 时，我们把它和 0 和 1 比较（2 对 0，2 对 1）。这样我们永远不会把一个粒子和它自己比较，那毫无意义（虽然我们生活中可能确实认识一些自我吸引或自我排斥特别强的人）。这也避免了不必要的反向比较，例如粒子 3 对粒子 42 与粒子 42 对粒子 3，两者结果相同。

要注意的是，即使减少了计算量，剩下的还是相当多！这个问题不是线性扩展的。在计算机科学里，我们用“O”记号来讨论问题，也就是大 O 记号。这里更像是 O^2 / 2——复杂度大约是平方的一半。如果你有 100 个粒子，就要做近 5000 次计算（100 * 100 / 2）。如果有 1000 个粒子，就是将近 50 万次。不用说，粒子一多就会变慢……

本章没时间展开，但有不同的方法来避免这么多计算。其中很多都与空间哈希有关，也就是快速判断哪些粒子足够远、根本不用考虑（从而省掉一次距离计算）。
