设计理念

作者：Zach Lieberman

openFrameworks 的事业由若干目标引导：它应当是协作的、可用而简单的、一致而直观的、跨平台的、强大的，并且可扩展的。它还由“与他人一起做”（DIWO）的理念驱动。

协作

openFrameworks 的开发是协作式的。它依靠许多人的贡献而繁荣，这些人频繁讨论，并合作开发 addon 和项目。我们鼓励大家把 openFrameworks 变成自己的东西，并为这个生态做贡献。

我们使用 git 这个分布式版本控制系统，这意味着人们可以开分支、做实验、提建议。如果你看 GitHub 上的网络图，它看起来像某种外星图示，满是交织的分支，代码不断分开又汇合。全世界有一个庞大的社区在参与核心代码：修 bug、提交 pull request、按自己希望的样子塑造这个工具。这是一个全球性项目，在美国醒来时，收件箱里塞满来自亚洲和欧洲程序员提交的 pull request 和 issue 邮件是常事。有 70 多人直接为 openFrameworks 核心做过贡献，数百人 fork 过代码或以其他方式参与。

简单

openFrameworks 试图在可用性和简单之间取得平衡。最早的版本把核心当作教 C++ 和 OpenGL 的工具，但随着时间推移，示例成了最好的学习方式，而核心则用上更高级的特性。作为交换，我们为 openFrameworks 提供了多得多的示例，目标是给出简单、可改造的实验起点。

我们希望 openFrameworks 尽可能简单，尤其是对来自其他语言和环境的人。C++ 是一门“大”语言，大是指你可以写出类型差异极大的 C++ 代码。去书店你会看到成百上千本 C++ 书。我们想造一个库，让你不必成为专家，最多需要一两本书，但代码的模式、方法和风格都简单直观。我们尤其在意与 Processing 达到某种对等，许多函数彼此相似，这样从一个框架转到另一个会更容易。

一致而直观

openFrameworks 是一致的、直观的：它应遵循最小惊讶原则，这样你学到 openFrameworks 某一部分的用法，可以套用到其他部分。初学者可以用 openFrameworks 学习常见的编程模式，进阶用户则能把在其他语言和工具包里的经验用上。

学生优先是箴言。指导 openFrameworks 的许多思考是：5 年或 10 年前，我会希望工具有什么样的东西？我们希望编程模式简单，并且尽可能好敲。这意味着要有自解释的函数名，比如视频播放器的“play”和“stop”，以及直观的变量名。我们围绕“直觉”有过很多讨论，动机是让代码尽可能直白。你应该靠敲代码来学，自动补全应该有用，等等。

跨平台

openFrameworks 是一个跨平台工具包。openFrameworks 支持尽可能多的开发环境和操作系统。下载 openFrameworks 时，你可以挑选自己的平台和开发环境，并能拿到现成的项目和示例来学习和把玩。难以移植的代码被挡在核心之外，放进 addon 里。

openFrameworks 被设计为能在众多平台上运行：OS X、Windows、Linux、iOS、Android、嵌入式 ARM Linux 系统，以及 BlackBerry PlayBook 这样的实验性平台。openFrameworks 的开发者想出了一些巧妙的方式与其他语言对接，比如 Android 上的 Java，或 iOS 上的 Objective-C。

跨平台库的乐趣在于，把你的想法从一个平台搬到另一个平台很容易。你可以在笔记本上打草稿，然后立刻在手机上运行。它让想法优先，不必操心让东西跨平台跑起来的苦活。

强大

openFrameworks 很强大：它让你能用上 OpenCV 这样的高级库，高效地使用显卡这类硬件，并连接相机和其他外设。

我们选择 C++，因为它是一门相当底层的语言，却仍能以高层方式编程。由于 C++ 是更早的 C 语言的扩展，你既可以写非常底层的、老派的 C 代码，也可以写更高层的 C++ 代码。在 openFrameworks 里，我们试图把两种方式都利用起来，呈现简单、清晰而强大的代码工作方式。使用 C++ 也更容易对接大量用 C 和 C++ 写成的库，不必依赖为其他语言做的封装。

openFrameworks 本质上封装了 OpenGL、Cairo、FreeType、FreeImage、OpenCV 等库。你可以把 openFrameworks 看作位于用户代码（你要写的代码）与这些库之间的一层代码。这些库风格、惯用法、思路各不相同，我们的工作就是把它们包起来，让它们更一致、更直观。

可扩展

openFrameworks 是可扩展的。当你发现 openFrameworks 缺了点什么，很容易写 addon 来扩展它。openFrameworks 的核心 addon 通常是对库的封装，而非用新奇方式解决问题。openFrameworks 封装库时，会把库暴露出来供进一步改造。

对 openFrameworks 的一种心智图像是脚手架，或者说是可以站上去的肩膀，用来搭建你想要的东西。让核心保持轻量的一个做法是：我们不试图把能塞的都塞进去，而是有一套“addon”系统，让额外的代码、库和思路可以在用户之间共享，并按需织入项目。

一个 openFrameworks addon 可以是一小段代码，也可以封装 OpenNI、Tesseract 或 Box2d 之类复杂得多的库。addon 的名字通常以“ofx”前缀开头，让你容易看出“核心”代码和非核心代码的区别。此外我们还包括“核心 addon”，也就是我们认为大家多半会想用、但并非每个项目都必需的 addon，比如 ofxOpenCv。

我们通过 http://ofxaddons.com 站点来组织和支持开发 addon 的社区，该站点通过查找标题中含有“ofx”的仓库，自动从 GitHub 收集 addon。目前已有 1,500 多个 addon。

与他人一起做（DIWO）

openFrameworks 背后的驱动理念是“与他人一起做”（DIWO）。我们热爱 DIY 文化，Instructables 或 Make 这类教程网站的兴起极大地推动和便利了它。但我们也对“社会性地制作”（“与他人一起”）的想法感到兴奋。我们通过工作坊、开发者大会、hackathon/实验室、编织小组和线下聚会来实践 DIWO，线上则通过邮件列表、论坛帖子等方式。我们甚至有一个帮派手势。因为如果你有一个帮派，就得有一个帮派手势。我们最想强调的是：你并不孤单，外面有一大群很棒的人在学、在教、在改造、在制作、在探索代码的创造性一面。
