用 Git 进行版本控制

作者：Christoph Buchner（bilderbuchi）

在本章中，你将了解什么是版本控制，以及为什么应该使用它。你会得到一份关于 Git 的简短介绍，Git 是 openFrameworks 选用的版本控制系统。本章会解释其中的主要概念和关键词，让你能够借助现有的在线资源轻松深入这个主题。文中还会介绍若干配合 Git 使用的工具。你将了解 Github，一个托管 Git 仓库的 Web 服务，也是“社交化编程”的主要平台之一。你会看到如何开始在 Github 上托管自己的项目，并利用它的各项功能。最后，你会知道如何在你刚学到的东西之上继续前进，以及遇到困难时可以到哪里求助。

什么是版本控制，为什么应该使用它？

你如何记录项目随时间变化的状态？你有没有复制过好几份项目文件夹（或文本文档、Photoshop 文件……）？你是不是把它们命名成 Awesome_project_1、Awesome_project_may10、Awesome_project_final、Awesome_project_final2、Awesome_project_really_final……这样的名字？你有没有把打包成 zip 的项目通过邮件发给合作者，结果在同步他们（或你）期间所做的改动时遇到麻烦？当你不得不回到之前的某个版本、修改内容、再把这些改动复制到另一个版本，或者总体上想盯住各种改动时，有没有遇到过问题？

如果你对其中一些问题点了头，那你就来对地方了——版本控制正是来帮你的！版本控制（也称修订控制）是对文档、计算机程序、大型网站以及其他信息集合所做改动的管理。它用于轻松、高效、可复现地跟踪各类信息的改动（就像一个非常高级的“撤销”功能）。具体到编程中，它（主要）用来跟踪源代码的改动，但它一般适用于你电脑上的大多数文件类型。版本控制还使程序员能够高效地团队协作，因为它提供了分发改动、合并不同开发版本、在两个（或更多）程序员修改同一文件时解决冲突、在计算机之间同步状态等方法。

我想你此刻应该已经同意：在开发程序时采用某种版本控制是个非常好的主意。在下一节里，我会稍微谈谈你在选择具体系统时有哪些不同的选项。

不同的版本控制系统

现存有不少版本控制系统，其中一些你也许已经接触过。它们可以分成两大阵营：“集中式”和“分布式”系统。

在集中式版本控制系统中，一台中央服务器负责调度版本控制系统执行的各种任务，程序员与这台服务器同步。常见操作往往需要与中央服务器建立网络连接。通常，程序员本地只拥有整个项目的一部分。一些流行的集中式版本控制系统有：

  • Concurrent Versions System (CVS)，它把“分支”这个概念引入了版本控制系统。
  • Subversion (SVN)，CVS 的一个流行后继者。

另一方面，分布式版本控制系统采用点对点的方式。它没有中央服务器，每个（本地）仓库都包含全部文件和完整历史（因此也同时充当备份！）。只有在与其他程序员同步改动时才需要网络访问。分布式版本控制系统近来大受欢迎。一些值得注意的系统有：

  • Git 最初由 Linus Torvalds 为 Linux 内核的开发而设计并开发。它的人气近来暴涨。
  • Bazaar 是由 Canonical（Ubuntu 背后的公司）创建的分布式版本控制系统。它主要用于 Launchpad，一个主要围绕 Ubuntu 开发项目的代码托管平台。
  • Mercurial 与 Git 大约同时起步。它与 Git 相当相似，对新手来说尤其如此。

Git 简介

openFrameworks 使用 Git 对代码库进行版本控制，并依赖 Github 作为代码和问题跟踪器的托管平台。在本节中，我会介绍如何对你的 openFrameworks 项目使用版本控制，并在遇到相关概念和命令时逐一介绍它们。

请注意，本章只是一篇介绍，因此无论是所介绍的命令还是它们的选项，都只触及 Git 能力的表层。更详细的信息，包括深度教程和命令参考，都可以在网上找到。本章末尾收集了一些链接，所介绍的大多数命令都带有指向其在线参考文档的链接。

接下来，我会解释 Git 的基本概念。之后，我会以逐步演练的方式展示在 openFrameworks 项目中使用 Git 所涉及的典型操作。然后我会向你展示如何与远程 Git 服务器协作。

基本概念

当你把项目（它位于磁盘上的某个目录中）纳入版本控制时，Git 会在你的项目目录里创建一个仓库。这意味着该文件夹的内容会被 Git 跟踪。与 Git 相关的大部分文件都位于项目根目录下的 .git 文件夹中（开头的点意味着这个文件夹在文件浏览器里默认很可能是隐藏的）。

跟踪仓库历史的基本单位是提交。它本质上是提交那一刻仓库状态的一份快照，其中包含提交信息以及任意父提交。可以把它想成电子游戏里的存档点。它有一个唯一的标识符，称为哈希（或 SHA）。这是根据提交内容计算出的校验和。提交的任何部分一旦改动，哈希就会随之改变，因此不可能在不改变哈希的情况下修改提交。所以，一个提交哈希唯一地定义一个提交以及它之前的全部历史。

随着工作推进，你会不断添加提交，描述你所改动的内容。这些提交会串成一条提交链，构成项目历史。这样一条提交链称为分支，默认分支叫作 master。当你决定从某条开发线岔开、尝试别的东西（例如一个新功能或一个 bug 修复）同时保留项目当前状态时，也可以创建分支。这条新的提交链在原始分支的某个提交处分岔出去，从此形成自己的分支。

分支可以被合并到另一个分支。合并发生时，Git 会分析这两个不同的分支，并把它们各自不同的历史/改动合并到一起。

仓库（位于 .git 目录中）包含所有提交。HEAD 指向你当前所在分支的当前提交。这代表你仓库最近一次提交的状态。如果你创建一个新提交，它会成为这个提交的父提交（而 HEAD 会移动到新提交上）。

工作目录包含处于版本控制之下的文件和文件夹，也就是你为项目写代码时修改和使用的东西。

准备一次提交时，你首先必须把希望该提交包含的改动暂存起来。这意味着这些改动会被放进索引（或称暂存区）。

所以，你在工作目录中修改文件，把这些修改暂存起来放进索引，然后创建提交，从索引中取出文件并存入仓库。要把文件从仓库中取回（也就是把状态恢复到之前某个时间点），你检出文件，把它们放回工作目录。下图以图形方式展示了这一过程：

.gitignore

一开始我们就该做的一件事，是在仓库根目录添加一个名为 .gitignore 的特殊 Git 文件。

重要的是，Git 仓库应包含成功编译我们程序所需的全部文件，但不包含多余的东西。一般来说，这意味着我们手工编辑的文件（例如源文件和头文件、Readme 文件、图片……）应纳入仓库，而由我们的代码生成的文件（例如编译出的二进制文件、由某个源文件生成的 pdf、用我们的程序生成的视频文件或图像序列）则应排除在外。此外，像描述 IDE 中窗口位置的 IDE 文件这类用户相关文件，或者操作系统为我们文件创建的备份副本，其实也不该放进仓库。

如果我们一开始就处理好这件事，就能轻松确保只有“正经”文件进入仓库。Git 通过前面提到的 .gitignore 文件（可以有多个）来处理这种文件排除，文件里包含描述哪些文件被 Git 忽略的模式。被忽略的文件仍然存在于我们的工作目录中，也就是说我们仍然可以使用它们，但 Git 不会跟踪它们。

如果后来我们发现改动列表里冒出了本不该出现的文件，或者似乎无法添加一个本该在仓库里的文件，我们不要强迫 Git 去做它不想做的事，而是去微调 .gitignore 的模式，使之符合我们的预期。注意，.gitignore 的模式不影响已经被提交的文件。

git status

我们会经常用到的一个命令是 git status。这个命令让我们一眼看出仓库的当前状态。它提供了一些标志来微调其输出（和大多数 Git 命令一样）。

好，让我们用 git status -u 看看仓库里发生了什么。-u 标志确保我们能看到所有未跟踪的文件，即使在子目录里也能看到：

$ git status -u
# 位于分支 master
#
# 初始提交
#
# 未跟踪的文件：
#   （使用 "git add <file>..." 将内容加入待提交项）
#
#    .gitignore
#    Makefile
#    addons.make
#    bin/data/.gitkeep
#    config.make
#    demoProject.cbp
#    demoProject.workspace
#    src/main.cpp
#    src/ofApp.cpp
#    src/ofApp.h
nothing added to commit but untracked files present (use "git add" to track)

输出告诉我们当前位于哪个分支（master）、我们还没有提交过任何东西、仓库里有几个未跟踪的文件（也就是 Git 还不认识的文件），而且重要的是，它还告诉我们接下来该做什么。使用 git status -s 可以获得更紧凑的输出。

这份文件列表看起来是对的，目前一切正常！你可能注意到了 bin/data/ 里的 .gitkeep 文件。Git 只跟踪文件，不跟踪目录，这意味着空目录对 Git 是不可见的。如果你希望在仓库里保留空目录（例如用于将来输出的文件），一种常用的变通办法是在其中放一个空文件，这样就能确保该目录可以被加入 Git。把该文件命名为 .gitkeep 只是一种约定，对 Git 没有任何特殊含义。

如果我们现在编译这个 OF 项目，/bin 文件夹里会多出一些文件。因为我们在上一步添加了 .gitignore 文件，这些文件不会被 Git 纳入。我们可以再次运行 git status -u 来验证这一点。

git add

下一步是暂存这些未跟踪的文件，用 git add。这会把那些文件放进索引，如前文所述。

我们用 git add <filespec> 来暂存未跟踪的文件以及对仓库中已有文件的修改，其中 <filespec> 描述一个或多个文件或目录，例如可以是 addons.make、src 或 *.cpp。

我们也可以把仓库中的全部文件和修改都用 git add . 添加，但由于这是一个一网打尽的 filespec，我们必须先检查 git status -u 的输出，确保没有不需要的文件被 .gitignore 模式漏掉、从而溜进仓库！既然我们刚确认过 git status 看起来没问题，那就来吧：

$ git add .

接下来运行 git status，你会注意到变化：

$ git status
# 位于分支 master
#
# 初始提交
#
# 要提交的改动：
#   （使用 "git rm --cached <file>..." 取消暂存）
#
#    新文件:   .gitignore
#    新文件:   Makefile
#    新文件:   addons.make
#    新文件:   bin/data/.gitkeep
#    新文件:   config.make
#    新文件:   demoProject.cbp
#    新文件:   demoProject.workspace
#    新文件:   src/main.cpp
#    新文件:   src/ofApp.cpp
#    新文件:   src/ofApp.h
#

所有那些未跟踪的文件现在都出现在 “Changes to be committed” 区域里，因此（如果我们之前没有取消暂存）它们会进入我们下一次做的提交。

要取消暂存我们不小心暂存的改动，对于新添加的文件用 git rm --cached <file>，对于已修改的文件用 git reset HEAD <file>。和往常一样，git status 会在合适的时候提醒我们这些命令。

git commit

既然我们已经为第一次提交准备好了暂存区/索引，就可以动手了。为此我们使用 git commit。我们可以同时用 -m 标志提供一个必需的提交信息，否则 Git 会打开一个编辑器让我们输入信息（然后保存并退出以继续）。

$ git commit -m "Add initial set of files."
[master (root-commit) 3ef08e9] Add initial set of files.
 10 files changed, 388 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 Makefile
 create mode 100644 addons.make
 create mode 100644 bin/data/.gitkeep
 create mode 100644 config.make
 create mode 100644 demoProject.cbp
 create mode 100644 demoProject.workspace
 create mode 100644 src/main.cpp
 create mode 100644 src/ofApp.cpp
 create mode 100644 src/ofApp.h

输出的第一行显示我们所在的分支（master），以及这是我们的第一次提交，创建了我们提交树的根。此外，我们还能看到刚创建的提交的哈希（也就是唯一 ID，3ef08e9）和提交信息。哈希以短形式给出，因为通常只需提供哈希的前七个字符左右就足以唯一标识一个提交（如果不是这样，Git 会报错）。下一行大致描述了本次提交的改动：改了多少文件、提交了多少插入和删除。其余部分列出了 Git 新增的文件，神秘的 mode 100644 是 unix 风格的文件权限描述，100644 表示普通的、不可执行的文件（100755 则表示可执行文件）。

现在，让我们检查状态，看看仓库里发生了什么：

$ git status
# 位于分支 master
nothing to commit, working directory clean

好耶，这是“一切正常、全部绿灯”的信息！它意味着当前的工作目录已经全部提交到 Git（被忽略的文件除外）。无论何时开始或停止在一个仓库中工作，从这个状态出发往往都是个好主意，因为万一出了问题，你总可以退回到这个点。

既然我们已经完成了最初的提交，就可以对 OF 项目做第一次自定义了。继续！

初次改动

好，现在我们是干净的白纸一张，那就开始把玩我们的 OF 项目吧。编程教程不向世界问声好就不算完整，所以我们就这么做：打开 ofApp.cpp，在 void ofApp::setup() 的实现里加上一条合适的消息，例如 cout << "Hello world";，然后保存文件。

我们刚刚修改了一个 Git 正在跟踪的文件，所以它应该会发现，对吧？用 git status 检查一下（你大概已经猜到这一步了）：

$ git status
# 位于分支 master
# 尚未暂存以备提交的改动：
#   （使用 "git add <file>..." 更新要提交的内容）
#   （使用 "git checkout -- <file>..." 丢弃工作目录中的改动）
#
#    已修改:   src/ofApp.cpp
#
no changes added to commit (use "git add" and/or "git commit -a")

好，Git 告诉我们它知道我们修改了 ofApp.cpp。注意现在这一项位于名为 “Changes not staged for commit” 的区域，而不是之前的 “untracked files”。同样，git status 会给出我们接下来可能想做什么的提示，非常方便。

git diff

现在，让我们弄清我们到底在 ofApp.cpp 里改了什么。这要用 git diff。它可以用来比较各种区域之间的状态（可以看看 man page 的示例部分），但最简单的形式 git diff 让我们查看相对于索引（下一次提交的暂存区）所做的改动。换句话说，这些差异就是我们本可以叫 Git 进一步加入索引、但还没有加入的内容。"（摘自 man page）（使用 --staged 选项可以查看已暂存改动的 diff。）让我们看看吧：

$ git diff
diff --git a/src/ofApp.cpp b/src/ofApp.cpp
index b182cce..8018cf7 100644
--- a/src/ofApp.cpp
+++ b/src/ofApp.cpp
@@ -3,6 +3,7 @@
 //--------------------------------------------------------------
 void ofApp::setup(){

+    cout << "Hello world!";
 }

 //--------------------------------------------------------------

这个输出以统一 diff 格式显示两个文件之间的差异（diff 是一个用于比较文本文件的流行 Unix 工具）。它看起来挺让人困惑，不过我们把它拆开来看，突出最有用的部分。

第一行标明被比较的两个不同文件，记作 a/... 和 b/...。如果我们不是刚重命名了文件，这两个通常会是相同的。

接下来几行进一步界定究竟比较的是什么，但这对我们来说不重要，直到我们来到以 @@ 开头的那一行。这一行定义了一个所谓的“hunk”（块），它告诉我们接下来展示的是文件的哪一部分。在原始状态中（以 - 为前缀），这一段从第 3 行开始，持续 6 行。在新状态中（前缀 +），这一段从第 3 行开始，持续 7 行。

接下来我们看到实际的改动，周围几行用于提供上下文。未改动的行以空格开头，新增的行以 + 开头，删除的行以 - 开头。被修改的行会先显示为一行删除，随后是一行新增。我们可以看到新增了一行包含 hello world 消息的代码。

既然我们已经做了一些改动，就可以编译并运行程序，确认它按预期工作，我们没有弄错。然后，像之前那样为这个修改准备一次提交：

$ git add src/ofApp.cpp

$ git status
# 位于分支 master
# 要提交的改动：
#   （使用 "git reset HEAD <file>..." 取消暂存）
#
#    已修改:   src/ofApp.cpp
#

在再次提交之前，关于提交和提交信息还有几句话要说：

首先，值得记住的一句箴言是“早提交，勤提交”。这意味着每当一个相对自成一体的代码单元完成时（例如实现一个新函数、修一个小 bug、重构某处），你都应该创建小而频繁的提交，而不是按整个功能提交（例如“为我的装置实现光流跟踪”），或把不同的改动混在一起（“更新 Readme、提升性能、移除未使用的 Kinect 交互”）。这样做的道理在于，它形成了一条细粒度的改动轨迹，所以当某些东西坏掉时，更容易找出是哪一个（小的）改动导致的问题（例如借助 git bisect 这类工具），并把它修好。

其次，写好提交信息。这会让其他所有人，以及几个月后的你自己，更容易弄清某个提交做了什么。关于好的提交信息长什么样，有一个简洁而良好的约定，可以在这里找到。简而言之，你应该有一行简短（约 50 个字符以内）、首字母大写、祈使语气的摘要（例如 “Fix bug in the file saving function”）。如果这还不够，就在后面跟一个空行（！）和更详细的说明，把每行控制在约 72 个字符。（如果你的终端支持，省略第二个引号可以让你输入多行。否则，省略 -m 标志，在编辑器里撰写提交信息。）

既然这些都说清楚了，我们就可以提交刚添加的改动，然后检查状态：

$ git commit -m "Add welcome message"
[master e84ba14] Add welcome message
 1 file changed, 1 insertion(+)

$ git status
# 位于分支 master
nothing to commit, working directory clean

分支与合并

分支与合并是 Git 的日常主食，所以你会频繁地分支和合并。频繁分支和合并是 Git 鼓励的一种工作流，因为这些操作在计算上很便宜。我们开始涉及一些稍微高级的东西，所以如果你没能一下子完全弄懂，不必担心。

例如，如果我们想为程序添加某个新功能，或修一个 bug，明智的做法是在一个与主分支分开的分支上开始这项工作。这有几个好处：

  • 我们的工作被限制在这个分支里。
  • 需要时，我们可以快速轻松地切换到另一项工作。
  • 只要没有被合并，主分支就不会受我们的工作影响，所以在此期间正常的工作可以继续进行（例如当我们为别人正在使用的 OF addon 做一个实验性补充时）。

git branch 与 git checkout

要获取仓库中的分支列表，我们不带参数地使用 git branch（* 表示当前分支）。由于我们目前只有一个分支，这没什么好看的：

$ git branch
* master

要创建新分支，我们使用 git branch <branchname>。然后要检出该分支、使其成为当前分支，我们使用 git checkout <branchname>。还有一种更短的写法可以一步完成这两个操作，即 git checkout -b <branchname>，所以我们用它来创建并检出一个名为 celebration 的新分支：

$ git checkout -b celebration
Switched to a new branch 'celebration'

$ git branch
* celebration
  master

为了庆祝一下，我们在 “Hello World” 之后再添加一条消息，例如 cout << "Yeah, it works";。让我们像之前那样用 git diff 确认 Git 已经捕捉到了这个改动：

$ git diff
diff --git a/src/ofApp.cpp b/src/ofApp.cpp
index 8018cf7..59d84fa 100644
--- a/src/ofApp.cpp
+++ b/src/ofApp.cpp
@@ -4,6 +4,7 @@
 void ofApp::setup(){

     cout << "Hello world!";
+    cout << "\nYeah, it works!";
 }

 //--------------------------------------------------------------

如果我们再运行一次 git status，它会显示我们现在位于 celebration 分支上：

$ git status
# 位于分支 celebration
# 尚未暂存以备提交的改动：
#   （使用 "git add <file>..." 更新要提交的内容）
#   （使用 "git checkout -- <file>..." 丢弃工作目录中的改动）
#
#    已修改:   src/ofApp.cpp
#
no changes added to commit (use "git add" and/or "git commit -a")

既然我们已确认待暂存和待提交的改动列表没问题，就可以走个小捷径。使用 -a 标志（git commit），我们可以让 Git 在提交时自动暂存已修改或已删除的文件（新文件不受影响），这样就能跳过 git add 这一步：

$ git commit -am "Let us celebrate!"
[celebration bc636f4] Let us celebrate!
 1 file changed, 1 insertion(+)

$ git status
# 位于分支 celebration
nothing to commit, working directory clean

合并分支

与此同时，我们在 master 分支上添加一个功能。首先，我们检出 master 分支：

$ git checkout master
Switched to branch 'master'

现在，我们可以添加一些代码，在按下空格键时切换背景颜色。你应该能通过 git diff 的输出了解我做了什么。试着大致复现这些改动：

$ git diff
diff --git a/src/ofApp.cpp b/src/ofApp.cpp
index 8018cf7..f7e3dbc 100644
--- a/src/ofApp.cpp
+++ b/src/ofApp.cpp
@@ -18,12 +18,16 @@ void ofApp::draw(){

 //--------------------------------------------------------------
 void ofApp::keyPressed(int key){
-
+    if (key == ' ') {
+        ofBackground(255);
+    }
 }

 //--------------------------------------------------------------
 void ofApp::keyReleased(int key){
-
+    if (key == ' ') {
+        ofBackground(127);
+    }
 }

 //--------------------------------------------------------------

接下来，我们再次快速提交（因为我们已经用 git diff 检查过要提交的修改了）：

$ git commit -am "Add background switching"
[master 7cc405c] Add background switching
 1 file changed, 6 insertions(+), 2 deletions(-)

git log

要显示提交日志，我们可以使用 git log 命令。在其默认形式下，git log 显示一个简单的提交列表，打印各提交的哈希、时间戳、作者和提交信息。它的输出可以大量定制，我们能做的一件好事是用下面这句咒语生成一个简易的树状视图（你可以把它存成别名来缩短它，不过这超出了本教程的范围）：

$ git log --all --graph --decorate --oneline
* bc636f4 (celebration) Let us celebrate!
| * 7cc405c (HEAD, master) Add background switching
|/
* e84ba14 Add welcome message
* 3ef08e9 Add initial set of files.

我们在这里看到仓库的完整历史，展示了分支结构，包括简短的提交信息。我们还能看到括号里的各分支末端，以及当前分支（HEAD 所指向的位置）。我们意识到 “Let us celebrate” 这个提交还没有包含在 master 里，那现在就把它并进来！

git merge

现在我们可以把 celebration 分支合并回 master 分支，让我们的庆祝消息在那边也能用。这通过 git merge 命令完成。我们用 git merge <branchname> 把另一个分支合并到当前分支，就像这样：

$ git merge celebration
Auto-merging src/ofApp.cpp
Merge made by the 'recursive' strategy.
 src/ofApp.cpp | 1 +
 1 file changed, 1 insertion(+)

Git 自动弄清了该如何合并 ofApp.cpp，使 master 现在包含来自两个分支的修改（现在就去看看 ofApp.cpp 吧）。

树状视图现在看起来是这样：

$ git log --all --graph --decorate --oneline
*   1c6d4aa (HEAD, master) Merge branch 'celebration'
|\
| * bc636f4 (celebration) Let us celebrate!
* | 7cc405c Add background switching
|/
* e84ba14 Add welcome message
* 3ef08e9 Add initial set of files.

我们可以看到两个分支已成功合并到一起，所以 master 现在包含我们的全部修改。另外注意，celebration 分支没有受到合并影响，它仍指向自己原来的提交。

接下来，我们要弄清如果合并不那么顺利会发生什么。

git reset

首先，纯粹为了演示，我们用 git reset 撤销刚才做的那个合并提交。这可能是个危险的命令，因为我们能借它抹掉提交，所以必须小心。在 git reset 之前随手跑一次 git status 总是有用的，以便确认仓库处于我们以为的状态。git reset --hard HEAD~<N> 把当前分支回退 <N> 个提交，在此过程中丢弃其余的提交（如果它们不属于其他分支的话）。那些提交仍然可以用 git reflog 找回，不过那稍微太复杂，这里就不演示了。一般来说，你之前提交过的东西很难真正丢掉，所以如果你不小心删掉了某段重要的历史，不要马上绝望。:-)

相反，--soft 标志只是把 HEAD 指针移到另一个提交上，而工作目录和索引保持不变。这很有用，例如可以用于撤销提交。

总之，现在把我们的 master 分支回退一个提交：

$ git reset --hard HEAD~1
HEAD is now at 68d2674 Add background switching

你可以再查一下树状视图，看到那个合并提交已经消失，master 回到了 “Add background switching”。现在，让我们试着让一次合并失败。

合并冲突

Git 在合并分支时相当聪明，但有时（通常是在两个分支以不同方式修改了同一行代码时）它不知道该如何正确合并，这会导致合并冲突。合并冲突得由我们手动解决。

现在，我们来创建一个会导致冲突的提交。我们就在 “Hello world” 语句之后再添加一行输出。由于在 celebration 分支里，“Hello world” 之后也添加了另一条语句，Git 将不知道如何正确解决这个问题。我们的 cout 语句看起来是这样：

$ git diff
diff --git a/src/ofApp.cpp b/src/ofApp.cpp
index f7e3dbc..6e232ba 100644
--- a/src/ofApp.cpp
+++ b/src/ofApp.cpp
@@ -4,6 +4,7 @@
 void ofApp::setup(){

     cout << "Hello world!";
+    cout << "\nThis is not going to end well!";
 }

 //--------------------------------------------------------------

现在我们创建一个提交（我们仍在 master 上）：

$ git commit -am "Trigger a conflict"
[master 2608b52] Trigger a conflict
 1 file changed, 1 insertion(+)

当我们试图把 celebration 合并进 master 时，坏事发生了：

$ git merge celebration
Auto-merging src/ofApp.cpp
CONFLICT (content): Merge conflict in src/ofApp.cpp
Automatic merge failed; fix conflicts and then commit the result.

当 Git 检测到冲突时，它会中止合并过程，并把“冲突标记”写进有冲突的文件。这些标记看起来是这样：

$ head -n 14 src/ofApp.cpp
#include "ofApp.h"

//--------------------------------------------------------------
void ofApp::setup(){

    cout << "Hello world!";
<<<<<<< HEAD
    cout << "\nThis is not going to end well!";
=======
    cout << "\nYeah, it works!";
>>>>>>> celebration
}

//--------------------------------------------------------------

<<< 与 === 之间的部分展示的是文件在 HEAD（我们想合并进去的当前分支）中的样子。=== 与 >>> 之间的部分展示的是文件在所指名的分支（本例中是 celebration）中的样子。我们接下来要做的，是把这个有冲突的段落按对程序合理的方式实现，从而解决冲突，然后删掉冲突标记并保存文件。例如，我们可以让这段冲突内容变成这样：

void ofApp::setup(){

    cout << "Conflict averted!";
    cout << "\nHello world!";
    cout << "\nYeah, it works!";

}

做完这些之后，Git 仍然知道这里发生过冲突，git status 又会告诉我们接下来该做什么：

$ git status
# 位于分支 master
# 你有未合并的路径。
#   （解决冲突并运行 "git commit"）
#
# 未合并的路径：
#   （使用 "git add <file>..." 标记为已解决）
#
#    双方都修改:      src/ofApp.cpp
#
no changes added to commit (use "git add" and/or "git commit -a")

我们乖乖照办，运行 git add src/ofApp.cpp 暂存这个无冲突的文件，并把该冲突标记为已解决。现在，我们可以完成合并了。如果我们省略 -m <message> 这一部分，git commit 会打开一个编辑器（哪一个取决于你的设置），里面有一条预填的提交信息，提到发生过冲突的文件。你可以试试这种方式，也可以像平常那样直接自己写一条提交信息：

$ git commit -m "Merge after resolving conflict"
[master 29d152e] Merge after resolving conflict

剩下的就是检查一切是否正常，并最后看一眼我们的树状视图：

$ git status
# 位于分支 master
nothing to commit, working directory clean

$ git log --all --graph --decorate --oneline
*   29d152e (HEAD, master) Merge after resolving conflict
|\
| * d9be50b (celebration) Let us celebrate!
* | 2608b52 Trigger a conflict
* | e822ea4 Add background switching
|/
* 1964a43 Add welcome message
* f6caa7b Add initial set of files.

恭喜，你刚刚解决了自己的第一个合并冲突！本章的逐步演练部分到此结束，接下来我会继续对 Git 功能做更高层面的讲解。

git tag

在工作中，你会遇到一些特殊的提交，它们标记着项目历史上重要的节点，例如已发布的版本，或你的代码安装到某处、交付给客户时的状态。用 Git 标签可以轻松做到这一点。用 git tag somename 给当前提交打上标签。这个标签此后永久指向该提交，你（基本上）可以在 Git 命令中像使用提交哈希和分支名那样使用它。例如，git checkout v1.2 会把仓库检出到（如果该标签存在）你发布 1.2 版时的状态。

远程仓库与 Github

你的工作可能有很重要的一面是与他人的协作。使用 Git 时，这通常涉及一个或多个远程仓库（简称 remote），你把修改推送到那里，并从那里获取别人的修改。

Git 仓库的若干流行托管平台之一是 Github。Github 提供仓库托管（公开和私有）、项目 wiki 页面、问题跟踪器、社交功能、项目网页等。OpenFrameworks 主要用 Github 托管其源代码仓库和 openFrameworks 问题跟踪器。

深入探讨 Github 的功能会扯得太远，所以我只概述你在与 Github 仓库打交道时会遇到的典型操作。

创建与远程仓库

要在 Github 上开始一个项目，你有几个选择：

  • 如果你想要某个已经在线上的项目的源代码的自己的副本，你可以fork 那个仓库，包括全部历史，最后你的账户下就有了它的一份副本。
  • 如果你想开始一个全新的项目，可以创建一个新仓库。Github 会显示相关说明，告诉你如何创建一个空的本地仓库，或如何把新仓库连接到已有的本地仓库。

如果某处已经有一个 Git 仓库，你也可以克隆那个仓库，在你的本地机器上得到它的一份副本。这个命令并不局限于 Github 仓库，可以用于所有 Git 仓库，见 git clone 文档了解 git clone 能做什么。

远程仓库会以所谓 remotes 的形式添加到本地仓库的配置中（自动添加，或使用 git remote add）。可以把它想成你在使用远程仓库时提供给 Git 命令的目标标识符。一个 remote 就是一个标识符，指向该仓库所在的 Github（或其他）URL。

习惯上，一个“父”仓库（也就是你 Github 账户下的那个仓库）叫作 origin，而你所 fork 的来源仓库叫作 upstream。你可以用 git remote 获取当前 remote 的列表（加上 -v 可以看到更多信息）。

获取与拉取

既然你已经配置好了一个远程仓库，就可以通过 git push 和 git fetch 与它交互。顾名思义，git fetch 从远程获取分支，所以要想取得你 Github 仓库中 master 分支的最新版本，你会执行 git fetch origin master（语法是 git fetch <remote> <branchName>）。如果你转而想从 upstream remote 获取最新的修改，你会执行 git fetch upstream master。这完成之后，你的仓库里会多出一个名为 origin/master 的分支。你可以用 git branch -a 检查这一点——远程分支会以 remotes/ 前缀列出。

要把这个远程分支的最新改动整合进你本地的 master，你先执行 git checkout master，确保你在正确的分支上。然后，你应该用 git status 确认仓库状态正常。接着，像合并任何其他分支那样合并这个远程分支，使用 git merge origin/master。如果一切顺利，你现在就把所有最新改动整合进了 master 分支。如果不顺利，你大概得像上面学过的那样修一些冲突。

对于先后执行 git fetch 和 git merge 这两个操作，一个常用捷径是 git pull——如果你喜欢，可以用它来代替。就我个人而言，我倾向于分开使用 fetch 和 merge，因为这样你对发生的事情有更多控制。

推送

当你有想与他人分享的提交或分支时，你会用 git push 把它们推送到你的远程仓库（例如 Github 上），比如用 git push origin awesome-feature。如果该分支还不存在，它会在远程仓库中被创建，否则会被更新。之后别人就能从你的远程仓库获取这个新分支，整合进他们的仓库。注意，只有提供了 --tags 标志，Git 标签才会被推送到远程。

拉取请求

Github 协作模型的一个核心功能是拉取请求。拉取请求（简称 “PR”）是一种把你的个人改动整合进你所 fork 的仓库的方式（重要的是你要把仓库 fork 到自己的账户下，而不是用其他手段取得副本）。

我们用一个例子来走一遍：假设你在 openFrameworks 里发现了一个 bug，想把它修好。你已经把 openFrameworks fork 到自己的账户，创建了本地副本，创建了一个名为 fix-uglybug 的分支（从 master 分出，遵循我们的贡献指南）（理想情况下先有一个 bug 报告，在其中讨论修复该 bug 的正确方式，不过这部分先放一边）。为了让 openFrameworks 的开发者审阅（并希望整合）你的 bug 修复，你把分支推送到自己的远程（git push origin fix-uglybug），然后在 Github 网页界面里切换到刚上传的分支，点击绿色的 “compare, review, create a pull request” 按钮。按照提示操作，你就能把你的分支与目标分支（通常是 openFrameworks 的 master 分支）比较、审阅你做的改动、撰写拉取请求的描述，然后把它发出去。

拉取请求让审阅你的改动变得容易，并提供了一个讨论平台，在其中可以讨论、更新改动，最后只需一次点击就完成合并，把你的改动并入上游仓库。

流行的图形界面客户端

虽然使用控制台命令能发挥 Git 的全部力量，但有时用带图形界面的应用来完成至少一部分版本控制工作会更方便。市面上有一些图形界面应用（取决于平台），用哪一个往往是个口味问题（也与各个程序的功能有关），所以我只列举几个流行的候选。这里还有一份精挑细选的列表，以及一份相当详尽的列表在这里。

  • git-gui 和 gitk 是随 Git 一起分发的简单界面。
  • Github 为 Windows 和 Mac 提供客户端，它们还提供与 Github（而不只是 Git）的集成。
  • Gitg 是一个 Linux 上的开源 Git 图形界面。
  • Tower 是一个 Mac 上的 Git 图形界面。
  • GitExtensions 是一个 Windows 上的开源 Git 图形界面。
  • smartGit 可在 Windows、Mac、Linux 上运行。

你应该试几种选项，用你最喜欢的那个。就我个人而言，我在 Linux 上把控制台命令和 Gitg 结合使用。我主要用图形界面做分支切换、选择和暂存修改以及提交，而用命令行界面处理远程仓库和更复杂的操作。

提示与技巧

本节零散收集了一些关于避开常见陷阱和使用 Git 的提示与技巧：

  • 与使用不同操作系统的用户协作可能很棘手，因为 MacOS/Linux 与 Windows 用不同的字符表示文件中的换行（分别是 \n 和 \r\n）。你可以按照现有的指南配置 Git，以避免大部分问题。
  • 有些编辑器在保存时会自动删除文件行尾的空白。这可能导致提交中包含非本意的修改，使浏览某个文件的改动历史变得更混乱。大多数相关的 Git 命令（例如 git diff）都接受 -w 标志，用来忽略空白改动。
  • 当你意识到想往上一个提交里再加一些改动时，可以在提交时使用 --amend 标志，把已暂存的改动加入上一个提交并调整提交信息。这会重写那个提交，所以只在你还没推送该提交时才这么做！
  • 当你只想暂存一个文件中的部分修改时，可以使用 git add -p <file>。它会切换到交互视图，你可以决定每一块改动是否要添加。
  • 可以让 Git 为终端输出着色，这相当有用。
  • 删除或移动文件时，分别使用 git rm 和 git mv。如果不这样做，索引不会被正确更新。你可以运行 git add -u 手动更新索引。
