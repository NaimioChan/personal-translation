声音

作者：Adam Carlucci

本章将演示如何使用 openFrameworks 中的声音功能，以及一些你可以用来生成和处理声音的技巧。

下面先快速概览一下 openFrameworks 中可以用于处理声音的类：

ofSoundPlayer 提供对声音文件的简单访问，让你可以轻松加载和播放声音、为应用添加音效，并在文件播放时提取一些关于该文件声音的数据。

ofSoundStream 让你访问计算机的声音硬件，既可以自己生成声音，也可以对从麦克风或 line-in 插孔之类的输入进入计算机的声音作出反应。

ofSoundBuffer 用来存储一段音频采样序列，并对这些采样执行与音频相关的操作（比如重采样）。

从声音文件开始

在 openFrameworks 里播放一个声音文件只需要几行代码。只要让一个 ofSoundPlayer 指向存放在应用 data 文件夹里的文件，然后告诉它播放即可。

class ofApp : public ofBaseApp {
  // ... 其他内容 ...
  ofSoundPlayer soundPlayer;
};

void ofApp::setup() {
  soundPlayer.load("song.mp3");
  soundPlayer.play();
}

如果要给应用加点背景音乐或氛围音，这样已经够了；不过 ofSoundPlayer 还附带几个额外功能，在处理音效时特别趁手。

“Multiplay” 允许同一个文件同时播放好几次。对于任何可能被频繁触发的音效来说这很棒，这样你就不会因为播放器的播放头突然跳回文件开头而卡在一段不自然的截断上。Multiplay 默认不开启，用 soundPlayer.setMultiPlay(true) 启用它。之后你就能用下面这种极简的触发逻辑，得到自然的音效行为：

if ( thingHappened ) {
  soundPlayer.play();
}

ofSoundPlayer 另一个内置功能是速度控制。如果把速度设得比正常快，声音的音高会相应升高，反之亦然（就像黑胶唱片）。播放速度是相对于 “1” 定义的，所以 “0.5” 是一半速度，“2” 是双倍速度。

速度控制和 multiplay 简直是为彼此而生的。同时用上两者，能大大延长单个音效文件的使用寿命。在启用 multiplay 的情况下，每次改变声音播放器的播放速度，之前触发的音效都不受影响地继续播放。于是，把上面的触发逻辑扩展成这样……

if( thingHappened ) {
  soundPlayer.setSpeed(ofRandom(0.8, 1.2));
  soundPlayer.play();
}

……你就能给声音的每个实例增添一点独特的个性。

ofSoundPlayer 还有一个重要功能是便捷的频谱访问。在桌面平台上，你可以用 ofSoundGetSpectrum() 取得应用中所有当前活跃的 ofSoundPlayer 所发出声音的频域表示。本章稍后会解释频域，不过跑一下 openFrameworks 的 soundPlayerFFTExample 就能大致明白。

归根结底，ofSoundPlayer 是在易用性和控制力之间做取舍。你能用上 multiplay 和变调播放，但拿不到极其精确的控制，也访问不到声音文件里的单个采样。若需要这种级别的控制，ofSoundStream 才是合适的工具。

从音频流开始

ofSoundStream 是通往计算机音频硬件的入口，比如麦克风和扬声器。如果你想让应用对实时音频输入作出反应，或者即时生成声音，这一节就是为你准备的！

你可能永远都不需要直接使用 ofSoundStream，但它是负责管理资源的对象，这些资源用于在你的应用上触发 audioOut() 和 audioIn()。这两个函数是 ofApp 的可选成员，就像 keyPressed()、windowResized() 和 mouseMoved()。只要实现它们并启动音频流，它们就会开始被调用。下面是一个发声的 openFrameworks 应用的基本结构：

class ofApp : public ofBaseApp {
  // ... 其他内容 ...
  void audioOut( float * output, int bufferSize, int nChannels );
  double phase;
};

void ofApp::setup() {
  phase = 0;
  ofSoundStreamSetup(2, 0); // 2 个输出声道（立体声），0 个输入声道
}

void ofApp::audioOut( float * output, int bufferSize, int nChannels ) {
  for(int i = 0; i < bufferSize * nChannels; i += 2) {
    float sample = sin(phase); // 生成一个正弦波采样
    output[i] = sample; // 写入左声道
    output[i+1] = sample; // 写入右声道
    phase += 0.05;
  }
}

生成或接收音频时，格式是介于 -1 和 1 之间的浮点数（原因本章稍后会讲）。声音会以缓冲区的形式到达你的应用。缓冲区其实就是数组，但“缓冲区”这个说法暗示每次你拿到的新缓冲区，代表的是上一个缓冲区之后的那段时间。openFrameworks 之所以向你要缓冲区（而不是单个采样），是因为把数据从你的程序搬运到音频硬件存在额外开销，这有点超出本书的范围。

缓冲区大小可以调整，但通常最好保留默认值。默认值并不是某个特定数字，而通常是你的计算机硬件偏好的值。实践中大约是每缓冲区 512 个采样（256 和 1024 也是常见的缓冲区大小）。

openFrameworks 里的声音缓冲区是交错存放的，意思是每个声道的采样紧挨在一起，就像：

[Left] [Right] [Left] [Right] ...

这意味着访问单个声道的方式，与访问 ofPixels 对象中不同颜色的方式很相似（即左声道用 buffer[i]，右声道用 buffer[i + 1]）。你在 audioIn() / audioOut() 里拿到的缓冲区总大小，可以用 bufferSize * nChannels 计算。

使用 ofSoundStream 时要记住一个重要提醒：audioIn() 和 audioOut() 这类音频回调会在另一个线程上被调用，与标准的 setup()、update()、draw() 函数分开。这意味着，如果你想在（比如）update() 和 audioOut() 之间共享数据，就需要用 ofMutex 来避免两个线程互相干扰。本章稍后可以看到它的实际用法，也可以查看 threads 章节获得更深入的说明。

在 openFrameworks 0.9.0 中，有一个新类 ofSoundBuffer，可以用在 audioOut() 里，替代 float * output, int bufferSize, int channels 这种形式。在这种情况下，上面的 audioOut() 函数可以改写成更简单的形式：

void ofApp::audioOut(ofSoundBuffer &outBuffer) {
	for(int i = 0; i < outBuffer.size(); i += 2) {
		float sample = sin(phase); // 生成一个正弦波采样
		outBuffer[i] = sample; // 写入左声道
		outBuffer[i + 1] = sample; // 写入右声道
		phase += 0.05;
	}
}

为什么是 -1 到 1？

要理解为什么 openFrameworks 选择把声音表示为取值在 -1 到 1 之间的连续 float 流，先了解声音在物理层面是如何产生的会很有帮助。

在最基本的层面上，扬声器由纸盆和电磁铁组成。电磁铁推动和拉动纸盆，在气压中产生振动。这些振动传到你的耳朵，被解读为声音。电磁铁关闭时，纸盆就处于“静止”状态，既不拉进也不推出。基本的话筒工作方式很类似：让气压去振动一个由磁铁固定住的物体，从而产生电信号。

从 openFrameworks 应用的角度看，声音硬件的具体电压并不重要。真正重要的只是扬声器纸盆在其“完全推出”和“完全拉进”两个位置之间被驱动，它们分别表示为 1 和 -1。这类似于 animation 章节中把 “1” 作为 100% 表示的概念，只不过声音引入了 -100% 的概念。

另一些系统使用基于整数的表示，在类似 -65535 到 +65535 之间变化，0 仍然是“静止”的表示。Web Audio API 提供无符号 8 位表示，范围在 0 到 255 之间，127 表示“静止”。

声音与视觉内容的一个主要区别是，声音其实没有“静态”的表示。比如，如果你在处理一张 OpenGL 纹理，其中 0 表示“黑”、1 表示“白”，你可以把纹理填满 0 或填满 1，分别得到“黑”或“白”的静态图像。声音不是这样。如果你创建一个全 0、全 1、全 -1 或任何单一数字的声音缓冲区，它们听起来都完全一样：什么都没有。

严格来说，你大概会在开头听到一声“噗”，因为扬声器从“静止”位置跳到了你的缓冲区里填满的那个数字，但缓冲区剩下的部分就只是静音。

这是因为你真正听到的是数值随时间的变化。缓冲区里任何单个采样本身并不真的带有声音。你听到的是它与前一个采样之间的差别。举例来说，声音的“响度”并不必然与缓冲区里各个数字有多“大”有关。一个在 0.9 到 1.0 之间振荡的正弦波，会比一个在 -0.5 到 0.5 之间振荡的正弦波安静得多。

时域与频域

当你把声音表示为 -1 到 1 之间的连续数值流时，你是在所谓的“时域”中处理声音。这意味着你处理的每个数值都指向一个特定的时刻。还有另一种表示声音的方式，在你用声音驱动应用其他方面时非常有用。这种表示叫做“频域”。

在频域中，你能看到输入信号在不同频率上各占多少，它们被切分成一个个独立的“bin”（见上图）。

你可以用一种无处不在的算法把信号从时域变换到频域，它叫快速傅里叶变换（Fast Fourier Transform）。在 ofxFFT 或 ofxFft addon 中，你可以找到可直接用于 openFrameworks 的 FFT 实现（还带例子！），它们分别出自 Lukasz Karluk 和 Kyle McDonald 之手。

在一个 FFT 采样中，索引较高的 bin 表示音高较高的频率（即高频），索引较低的表示低频。每个 bin 究竟代表哪个频率，取决于参与变换的时域采样数量。可以这样计算：

frequency = (binIndex * sampleRate) / totalSampleCount

所以，如果你对采样率 44100Hz、包含 1024 个时域采样的缓冲区做 FFT，bin 3 就代表 129.2Hz（ (3 * 44100) / 1024 ≈ 129.2 ）。这个计算揭示了 FFT 一个非常值得记住的性质：用于计算 FFT 的时域采样越多，得到的频率分辨率就越好（也就是说，每个后续 FFT bin 代表的频率彼此更接近）。用这种方式提高频率分辨率的代价是你会开始失去对时间的把握，因为你的 FFT 表示的是信号中更大的一段。

注意：原始 FFT 通常把输出表示为复数，不过如果你是想做音频可视化之类的事情，这大概不是你想要的。更直观的表示是每个复数的模，它的计算方式为：

magnitude = sqrt( pow(complex.real, 2) + pow(complex.imaginary, 2) )

如果你使用的 FFT 实现直接给你一个 float 数组，那它很可能已经替你完成了这个计算。

你也可以用逆快速傅里叶变换（Inverse Fast Fourier Transform，即 IFFT）把信号从频域变回时域。这不太常见，但有一整类叫做加法合成的音频合成方法就是围绕这个原理建立的（在频域中生成数值，然后对它们跑 IFFT 来产生合成声音）。

频域在很多事情上都很有用，其中最直接的一种是按频率范围分离出声音的特定成分，比如一首歌里的各件乐器。另一个常见用途是分析声音的特质或音色，用来驱动复杂的音频反应式视觉。

傅里叶变换背后的数学有点绕，但一旦理解了概念就相当直白。我觉得这篇对傅里叶变换的解释把底层数学讲得很好，还配了一些可交互的视觉例子。

对实时音频作出反应

RMS

给应用加上音频反应性最简单的方法之一，是计算输入音频数据缓冲区的 RMS。RMS 是 “root mean square”（均方根）的缩写，算法相当直白，能很好地近似“响度”（比求缓冲区平均值或取最大值之类的做法好得多）。算法里“平方”这一步保证输出始终是正值。这意味着你可以忽略原始音频可能含有“负”采样这件事（反正它们听起来和对应的正值一样响）。你可以在 audioInputExample 中看到 RMS 的计算。

// 由 audioInputExample 修改而来
float rms = 0.0;
int numCounted = 0;

for (int i = 0; i < bufferSize; i++){
    float leftSample = input[i * 2] * 0.5;
    float rightSample = input[i * 2 + 1] * 0.5;
    
    rms += leftSample * leftSample;
    rms += rightSample * rightSample;
    numCounted += 2;
}

rms /= (float)numCounted;
rms = sqrt(rms);
// rms 现在计算完毕

起始点检测（即节拍检测）

起始点检测算法试图在音频流中找出起始点出现的时刻，起始点通常是乐器奏出一个音或鼓被敲击的冲量之类。可用的起始点检测算法很多，复杂度和准确度各异，有些针对语音而非音乐做过微调，有些在频域而非时域工作，有些面向离线处理而非实时，等等。

一个简单的实时起始点检测算法，可以建立在上面 RMS 计算的基础之上。

class ofApp : public ofBaseApp {
    // ... audioInputExample 里的其他成员 ...

    float threshold;
    float minimumThreshold;
    float decayRate;
};

void ofApp::setup() {
    // ... audioInputExample 中 setup() 的内容 ...

    decayRate = 0.05;
    minimumThreshold = 0.1;
    threshold = minimumThreshold;
}

void ofApp::audioIn(float * input, int bufferSize, int nChannels) {
    // ... audioInputExample 中 audioIn() 的内容 ...
    
    threshold = ofLerp(threshold, minimumThreshold, decayRate);

    if(rms > threshold) {
        // 检测到起始点！
        threshold = rms;
    }
}

这在单独的鼓轨、稀疏的音乐，或者检测有没有人对着麦克风说话这类场景下大概够用。但在实践中你很可能发现，对于可靠的音频可视化或更精细的音频处理，它并不够用。

你当然可以找一个外部的起始点检测算法（可用的 addon 相当多），但如果你想自己试验，试试把 FFT 引入你的算法。比如，试试把 RMS 换成一段 FFT bin 的平均振幅。

如果你想深入起始点检测算法的世界（以及更大的所谓“音乐信息检索”算法生态），Music Information Retrieval Evaluation eXchange wiki 是个很好的来源。在这个 wiki 上，你能找到年度比赛的结果，这些比赛比较的是起始点检测、调性检测、旋律提取、速度估计等各类算法。

FFT

对输入音频跑 FFT，会返回一个表示输入频率内容的数值缓冲区。单纯的 FFT 不会告诉你一段音乐里有哪些音符，但你能用这些数据把输入的听觉“质感”考虑进去。比如，FFT 数据能以相当细的粒度告诉你输入里有多少“低频”/“中频”/“高频”（实时音频反应式工作中典型的 FFT 会给你 512 到 4096 个独立的频率 bin 可用）。

用 FFT 分析音乐时要记住，FFT 的 bin 是按线性尺度递增的，而人类是按对数尺度感知频率的。所以，如果你用 FFT 把音乐信号分成 512 个 bin，最低的那些（大概 bin 0 到 bin 40）很可能包含大部分数据，剩下的 bin 大多只是高频内容。如果你逐 bin 地分离声音，你能轻易分辨 bin 3 和 bin 4 的声音差别，但 bin 500 和 501 听起来大概完全一样。除非你有一对机器人的耳朵。

还有另一种变换叫常量 Q 变换（Constant Q Transform，即 CQT），概念上与 FFT 相似，但它的 bin 按对数间隔分布，处理音乐时直观得多。比如，你可以在 CQT 中安排结果 bin，让它们依次表示 C、C#、D…… 截至本文写作时，我并不知道有现成的、可直接用于 openFrameworks 的 CQT addon，但如果你想在 FFT 之外探索其他音频可视化选项，这值得记住。我用这个 Constant-Q 实现得到过不错的结果，它属于 Vamp 插件与工具集。

合成音频

这一节会带你做出一个基本的音乐合成器。完整的乐器超出了本书范围，但这里会介绍合成声音的基本构件。

一个简单的合成器可以实现为受包络调制的波形，构成单个振荡器。典型的“真实”合成器会有好几个振荡器，还会引入滤波器，但很多合成器归根结底都是“波形 + 包络”组合的各种变体。

波形

合成器的波形决定了振荡器的“音色”。波形越接近正弦波，产生的音色就越“纯”。波形几乎可以用任何东西构成，很多合成类型都围绕着生成和操纵波形的技术展开。

实现波形的一种常见技术是创建一个查找表，以一定分辨率存下完整波形。用一个相位索引扫描这张表，相位索引递增的速度决定振荡器的音高。

下面是一个合成器应用的起点，我们会在这一节里不断扩展它。它演示了用查找表存储波形的技术，也把波形和最终的音频输出可视化出来。你可以用鼠标改变查找表的分辨率以及渲染的频率。

class ofApp : public ofBaseApp {
public:
    void setup();
    void update();
    void draw();
    
    void updateWaveform(int waveformResolution);
    void audioOut(float * output, int bufferSize, int nChannels);
    
    std::vector<float> waveform; // 这就是查找表
    double phase;
    float frequency;

    ofMutex waveformMutex;
    ofPolyline waveLine;
    ofPolyline outLine;
};

void ofApp::setup() {
    phase = 0;
    updateWaveform(32);
    ofSoundStreamSetup(1, 0); // 单声道输出
}

void ofApp::update() {
    ofScopedLock waveformLock(waveformMutex);
    updateWaveform(ofMap(ofGetMouseX(), 0, ofGetWidth(), 3, 64, true));
    frequency = ofMap(ofGetMouseY(), 0, ofGetHeight(), 60, 700, true);
}

void ofApp::draw() {
    ofBackground(ofColor::black);
    ofSetLineWidth(5);
    ofSetColor(ofColor::lightGreen);
    outLine.draw();
    ofSetColor(ofColor::cyan);
    waveLine.draw();
}

void ofApp::updateWaveform(int waveformResolution) {
    waveform.resize(waveformResolution);
    waveLine.clear();
    
    // "waveformStep" 把 sin() 的一个完整振荡周期映射到波形
    // 查找表的长度
    float waveformStep = (M_PI * 2.) / (float) waveform.size();
    
    for(int i = 0; i < waveform.size(); i++) {
        waveform[i] = sin(i * waveformStep);
        
        waveLine.addVertex(ofMap(i, 0, waveform.size() - 1, 0, ofGetWidth()),
                           ofMap(waveform[i], -1, 1, 0, ofGetHeight()));
    }
}

void ofApp::audioOut(float * output, int bufferSize, int nChannels) {
    ofScopedLock waveformLock(waveformMutex);
    
    float sampleRate = 44100;
    float phaseStep = frequency / sampleRate;
    
    outLine.clear();
    
    for(int i = 0; i < bufferSize * nChannels; i += nChannels) {
        phase += phaseStep;
        int waveformIndex = (int)(phase * waveform.size()) % waveform.size();
        output[i] = waveform[waveformIndex];
        
        outLine.addVertex(ofMap(i, 0, bufferSize - 1, 0, ofGetWidth()),
                          ofMap(output[i], -1, 1, 0, ofGetHeight()));
    }
}

跑起来之后，试试用不同的方式填充波形表（也就是 updateWaveform(...) 里含有 sin(...) 的那一行）。比如，有个好玩的改法是把那一行换成：

waveform[i] = ofSignedNoise(i * waveformStep, ofGetElapsedTimef());

这样你会得到一个随时间自然演化的波形。不过要小心让波形采样保持在 -1 到 1 的范围内，免得炸掉你的扬声器和/或大脑。

包络

现在我们有了一个持续音发生器，但往里面加入一些音量调制，会真正让声音活起来。这能让波形像乐器一样被演奏，或者让它听起来像是一个会对事件作出反应的活物。

我们可以用 ofLerp(...) 做一个简单（但有效）的包络，只要往应用里加入下面的内容：

class ofApp : public ofBaseApp {
    // ... 与之前的应用相同的成员 ...
    
    float volume;
};

void ofApp::setup() {
    // ... 之前 setup() 的其余部分 ...
    
    volume = 0;
}

void ofApp::update() {
    // ... 之前 update() 的其余部分 ...
    
    if(ofGetKeyPressed()) {
        volume = ofLerp(volume, 1, 0.8); // 快速跳到 1
    } else {
        volume = ofLerp(volume, 0, 0.1); // 缓慢淡出到 0
    }    
}

void ofApp::audioOut(float * output, int bufferSize, int nChannels) {
    // ... 把之前那行 "output[i] = " 改成这样：

    output[i] = waveform[waveformIndex] * volume;
}

现在，每当你按下一个键，振荡器就会活跃起来，松开键后逐渐淡出。

控制包络的标准做法是用一个相对简单的状态机，叫 ADSR，即 “Attack, Decay, Sustain, Release”。

  • 起音（Attack）是音符触发后音量达到峰值有多快
  • 衰减（Decay）是音量从峰值落下来要多久
  • 延音（Sustain）是包络的保持音量，在音符释放前保持不变
  • 释音（Release）是音符释放后音量回落到 0 要多久

完整的 ADSR 实现留给读者作为练习，不过 earlevel.com 上的这个例子是很好的参考。

频率控制

你大概能猜到接下来要做什么。既然应用已经能响应按键，我们就可以用这些按键来决定振荡器的频率。这里我们会再多用一点 ofLerp(...)，以获得漂亮的连奏效果。

class ofApp : public ofBaseApp {
    // ... 与之前的应用相同的成员 ...
    
    void keyPressed(int key);
    float frequencyTarget;
};

void ofApp::setup() {
    // ... 之前 setup() 的其余部分 ...
    
    frequency = 0;
    frequencyTarget = frequency;
}

void ofApp::update() {
    // ... 用这个替换之前那行 "frequency = "：
    frequency = ofLerp(frequency, frequencyTarget, 0.4);
}

void ofApp::keyPressed(int key) {
    if(key == 'z') {
        frequencyTarget = 261.63; // C
    } else if(key == 'x') {
        frequencyTarget = 293.67; // D
    } else if(key == 'c') {
        frequencyTarget = 329.63; // E
    } else if(key == 'v') {
        frequencyTarget = 349.23; // F
    } else if(key == 'b') {
        frequencyTarget = 392.00; // G
    } else if(key == 'n') {
        frequencyTarget = 440.00; // A
    } else if(key == 'm') {
        frequencyTarget = 493.88; // B
    }
}

现在我们有了一个基本可用的乐器！

如果你想进一步探索，可以试试这几件事：

  • 不用 keyPressed(...) 来决定振荡器频率，而是用 ofxMidi 响应外部 MIDI 消息。想玩得花一点，可以试试实现弯音，或者用 MIDI CC 消息来控制频率插值的速率。
  • 不要“吸附”到波形查找表里最近的采样，而是尝试在相邻值之间插值，以减少低分辨率查找表产生的噪声杂音
  • 试着用图像或实时摄像头的数据填充波形表（用 ofMap(...) 可以方便地把数据保持在 -1 到 1 范围内）
  • 实现一个复音合成器。也就是用多个振荡器，让你能同时演奏不止一个音符。
  • 保留几份 phase 索引的副本，用 ofSignedNoise(...) 稍微改变它们各自代表的频率。把各个波形在 output 中相加，但用你跟踪的相位数量对结果求平均。

例如：

void ofApp::audioOut(float * output, int bufferSize, int nChannels) {
    ofScopedLock waveformLock(waveformMutex);

    float sampleRate = 44100;
    float t = ofGetElapsedTimef();
    float detune = 5;

    for(int phaseIndex = 0; phaseIndex < phases.size(); phaseIndex++) {
        float phaseFreq = frequency + ofSignedNoise(phaseIndex, t) * detune;
        float phaseStep = phaseFreq / sampleRate;

        for(int i = 0; i < bufferSize * nChannels; i += nChannels) {
            phases[phaseIndex] += phaseStep;
            int waveformIndex = (int)(phases[phaseIndex] * waveform.size()) % waveform.size();
            output[i] += waveform[waveformIndex] * volume;
        }
    }
    
    outLine.clear();
    for(int i = 0; i < bufferSize * nChannels; i+= nChannels) {
        output[i] /= phases.size();
        outLine.addVertex(ofMap(i, 0, bufferSize - 1, 0, ofGetWidth()),
                          ofMap(output[i], -1, 1, 0, ofGetHeight()));
    }
}

音频陷阱

“爆音”

在开始或结束播放合成音频时，你应该试着让缓冲区快速淡入/淡出，而不是突然开始或停止。如果你开始播放一个像 [1.0, 0.9, 0.8...] 这样开头的缓冲区，扬声器做的第一件事就是从 0 这个“静止”位置立刻跳到 1.0。这是一个巨大的跳变，结果很可能是一声比你预期（基于计算机当前音量）响得多的“噗”声。

通常，在约 30ms 的过程中淡入/淡出，就足以消除这类爆音。

如果你在播放中途听到爆音，可以试着找出声音为什么会极其短暂地中断来诊断问题（也就是跳到 0，如果波形之前处于非零值，就会产生爆音）。

“削波”/失真

如果你的采样开始超出 -1 到 1 的范围，你可能就会开始听到所谓的“削波”，它通常听起来是刺耳、令人不适的失真。有些音频硬件会比较宽容地处理，允许你稍微超出 -1 到 1 的范围，但另一些会直接“削”掉你的缓冲区。

假设这不是你想要的，削波一般可以归咎于代码里某个出错的加法或减法。任意两个 -1 到 1 之间的数相乘，结果总还是 -1 到 1 之间的数。

如果你想要失真，更常见的做法是使用波形整形算法，而不是设法让削波听起来好听。

延迟

无论如何，你在应用里产生的声音，都会在触发它的事件之后过一段时间才到达扬声器。从事件到应用再到扬声器的整个往返时间，称为延迟。

实践中这通常不是什么大问题，除非你在做像乐器这样对反应时间要求极严的东西（比如鼓类乐器）。如果你发现应用的声音响应不够快，可以试着降低 ofSoundStream 的缓冲区大小。但要小心！默认缓冲区大小之所以是默认值，通常是因为它被认为是延迟与可靠性之间的最佳折中。如果你用更小的缓冲区，而应用跟不上格外严格的音频截止时间，就可能会遇到“爆音”（如上所述）。
