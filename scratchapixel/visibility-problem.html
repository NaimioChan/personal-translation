可见性问题

前面我们已经解释过可见性问题。要生成照片级真实的图像，就必须确定物体哪些部分从特定视点可见。问题出在：当我们把一个盒子的各个角投影出去，再把投影点连起来画出盒子的棱时，盒子的所有面都变得可见了。然而在现实中，只有正面应该是可见的，背面应当被挡住。

在计算机图形学中，这个问题主要用两种方法解决：光线追踪和光栅化。我们简要说明各自如何工作。虽然很难断定哪种方法更早出现，但在图形学早期，光栅化要流行得多。光线追踪以更高的计算与内存需求著称，比光栅化慢。考虑到早期计算机有限的处理能力与内存，用光线追踪渲染图像在生产环境（例如电影制作）中被认为不可行。因此几乎每个渲染器都用光栅化，光线追踪大多局限于研究项目。不过在模拟反射、软阴影等效果上，光线追踪优于光栅化，更容易做出照片级真实的图像，代价是速度更慢。这种在模拟真实着色与光照效果上的优势，将在下一章进一步讨论。实时渲染 API 与 GPU 一般都偏好光栅化，因为实时应用把速度看得最重。不过光线追踪在 80、90 年代所受的局限如今已不存在。现代计算机的强大算力意味着，今天几乎所有离线渲染器都采用光线追踪，且常常与光栅化组成混合方案。这主要是因为光线追踪是模拟锐利反射与光泽反射、软阴影等关键效果最直接的方法。只要速度不是关键因素，它相对光栅化就有诸多优势，尽管要让光线追踪变得高效仍需相当多的努力。

Pixar 的 PhotoRealistic RenderMan 是 Pixar 为早期长片（《玩具总动员》《海底总动员》《虫虫危机》）开发的渲染器，最初采用光栅化算法。这个算法叫 REYES（Renders Everything You Ever Saw），被认为是有史以来最精巧的可见面判定算法之一。GPU 渲染管线与 REYES 有许多相似之处。不过 Pixar 现在的渲染器 RIS 是纯光线追踪器。光线追踪的引入显著提升了该工作室多年来所出图像的写实度与复杂度。

用光栅化解决可见性问题：它是怎么工作的？

我们已经解释过光栅化与光线追踪的区别（见上一章）。不过再重复一遍：光栅化的做法可以直观地理解为，让一个点沿一条连接几何体表面上的点 \(P\) 与眼睛的直线移动，直到它「躺」在画布表面上。这条线只是隐式的；我们其实从不需要真正构造它，但投影过程可以这样直观地解读。

可见性问题的实质在于：可能出现这样的情况——场景中的若干个点 \(P\)、\(P1\)、\(P2\) 等投影到画布上的同一个点 \(P'\)（记住画布同时也是屏幕的表面）。然而通过相机唯一可见的，是连接眼睛与所有这些点的那条直线上离眼睛最近的那个点，如图 2 所示。

要解决可见性问题，首先需要把 \(P'\) 表示成它在图像中的位置：\(P'\) 落在图像的哪个像素坐标上？记住，把一个点投影到画布表面上得到的是另一个点 \(P'\)，它的坐标是实数。但 \(P'\) 也必然落在最终图像的某个像素之内。那么，如何从用「画布表面上的位置」来表示 \(P's\)，过渡到用「最终图像中的位置」（即 \(P'\) 落在图像中的哪个像素坐标）来定义它们？这一过渡只是一次简单的坐标系变换。

  • 定义该点所用的原始坐标系称为屏幕空间（或图像空间）。它的原点位于画布中心，这个二维系统的所有轴长度都是单位长度。这个系统中任意一点的 \(x\) 或 \(y\) 坐标可以是负的，只要它位于 \(x\) 轴左侧或 \(y\) 轴下方。

  • 光栅空间是以图像的像素网格为参照来定义点的坐标系。它的原点通常在图像左上角，各轴同样取单位长度，一个像素算一个单位。这个系统中画布的实际大小由图像的垂直（高）与水平（宽）尺寸给出，以像素为单位。

把点从屏幕空间转换到光栅空间很直接。由于光栅空间中的 \(P'\) 坐标只能为正，我们先归一化 \(P's\) 的原始坐标，把它们从原来的范围映射到 [0, 1]（这样定义的点位于 NDC 空间中，NDC 即归一化设备坐标）。转换到 NDC 空间之后，把点的坐标变换到光栅空间就很直接：把归一化坐标乘以图像尺寸，再把结果四舍五入到最接近的整数值（像素坐标必须是整数）。\(P'\) 坐标的原始范围取决于屏幕空间中画布的大小。为简单起见，假定画布在每个维度（宽和高）上都是两个单位长，这意味着屏幕空间中的 \(P'\) 坐标落在 \([-1, 1]\) 范围内。下面是把 \(P's\) 坐标从屏幕空间转换到光栅空间的伪代码：


int width = 64, height = 64;  // 图像的尺寸（像素） 
Vec3f P = Vec3f(-1, 2, 10); 
Vec2f P_proj; 
P_proj.x = P.x / P.z;  //-0.1 
P_proj.y = P.y / P.z;  //0.2 
// 从屏幕空间坐标

 to normalized coordinates
Vec2f P_proj_nor; 
P_proj_nor.x = (P_proj.x + 1) / 2;  //(-0.1 + 1) / 2 = 0.45 
P_proj_nor.y = (1 - P_proj.y) / 2;  //(1 - 0.2) / 2 = 0.4 
// 最后转换到光栅空间
Vec2i P_proj_raster; 
P_proj_raster.x = (int)(P_proj_nor.x * width); 
P_proj_raster.y = (int)(P_proj_nor.y * height); 
if (P_proj_raster.x == width) P_proj_raster.x = width - 1; 
if (P_proj_raster.y == height) P_proj_raster.y = height - 1;

这段代码里有几点需要注意。首先，原始点 \(P\)、屏幕空间中的投影点以及 NDC 空间，用的都是 Vec3f 或 Vec2f 类型，其坐标定义为实数（浮点数）。而光栅空间中的最终点用的是 Vec2i 类型，坐标为整数（代表图像中的像素坐标）。编程里的数组从 0 开始索引，也就是说光栅空间中点的坐标绝不应超过图像宽度减一或图像高度减一。当屏幕空间中 \(P's\) 坐标在任一维度上正好等于 1 时，就会出现这种情况。代码处理了这一情形（第 14–15 行），必要时把坐标夹到合适的范围内。另外，NDC 空间的原点位于图像左下角，而光栅空间的原点位于左上角（见图 3）。因此在从 NDC 转换到光栅空间时，\(y\) 坐标需要翻转（注意代码第 8 行与第 9 行之间的调整）。

为什么需要这个转换？为了解决可见性问题，我们采用下面的方法：

  • 把所有点投影到屏幕上。

    • 对每个投影点，把 \(P's\) 坐标从屏幕空间转换到光栅空间。

    • 确定该点映射到哪个像素（用点的光栅坐标），并把该点到眼睛的距离存进为那个像素维护的一个特殊列表（深度列表）。

    「你说把所有点投影到屏幕上。可这些点我们一开始从哪儿来？」

    这确实是个好问题。技术上，我们会把构成物体的三角形或多边形分解成更小的几何元素——投影到屏幕上时不大于一个像素。在实时 API（OpenGL、DirectX、Vulkan、Metal 等）里，这些通常称为片元。更详细的解释见本节讲 REYES 算法的那一课。

  • 在这一过程结束时，按距离递增的顺序把每个像素列表里的点排序。于是对图像中任意给定像素，可见的点就是该像素列表中的第一个点。

「为什么这些点要按深度排序？」

列表需要排序，是因为点投影到屏幕上时并不一定按深度有序。如果插入点的方式是把它加到列表顶部，那就有可能在 \(A\) 已被投影之后，又投影一个比 \(A\) 离眼睛更远的点 \(B\)。这种情况下，\(B\) 会成为列表中的第一个点，尽管它比 \(A\) 离眼睛更远，所以必须排序。

基于这一方法的算法称为深度排序算法——这个名字本身就说明了它做什么。深度排序的概念是所有光栅化算法的基础。其中最著名的有：

  • z 缓冲算法，大概是这一类里用得最广的。本节介绍的 REYES 算法就实现了 z 缓冲算法。它和刚才描述的技术非常接近：物体表面上的点（被细分成极小的表面或片元）被投影到屏幕上，并存入深度列表。

  • 画家算法

  • Newell 算法

  • ……（这个清单还可以继续列下去）

请记住，虽然这些在你听来可能显得过时，但所有显卡都至少用某一种 z 缓冲算法的实现来生成图像。这些算法，尤其是 z 缓冲，至今仍然常用。

为什么我们需要维护一个点列表？

要保存离眼睛距离最短的那个点，其实并不一定需要把所有点都存进一个列表。你确实可以这样做：

  • 对图像中的每个像素，把变量 \(z\) 设为无穷大。

  • 对场景中的每个点：

    • 投影这个点并算出它的光栅坐标。

    • 如果当前点到眼睛的距离 \(z'\) 小于该点所投影到的那个像素里存的 \(z\)，就用 \(z'\) 更新 \(z\)。若 \(z'\) 大于 \(z\)，说明这个点比该像素当前存着的点更远。

这说明，不必保存一份可见点列表再在最后排序，也能得到同样的结果。那我们为什么还要用列表？用列表是因为在我们的例子里，假定场景中所有点都是不透明的。可如果它们不是完全不透明呢？若若干半透明的点投影到同一个像素上，它们可能彼此透见。这时就必须记录透过这个像素可见的所有点，按距离排序，再用一种特殊的合成技术（我们会在讲 REYES 算法的那一课里学到）把它们正确混合。

用光线追踪解决可见性问题：它是怎么工作的？

用光栅化时，点被投影到屏幕上来找出它们在图像平面上的位置。不过我们也可以从相反的方向处理这个问题。不是从点走向像素，而是从像素出发，把它转换成图像平面上的一个点（取像素中心，把它的坐标从光栅空间转换到屏幕空间）。这样得到 \(P'\)。随后我们从眼睛出发追踪一条光线，穿过 \(P'\)，并把它继续延伸进场景（假定 \(P'\) 就是该像素的中心）。如果光线与某个物体相交，那么交点 \(P\) 就是透过该像素可见的点。简而言之，光线追踪就是通过显式地从眼睛向场景追踪光线来求解点的可见性问题的方法。

注意，某种意义上光线追踪与光栅化互为镜像。它们基于同一原理，只是光线追踪从眼睛走向物体，而光栅化从物体走向眼睛。两者都要判定图像中任意给定像素对应哪个可见点，但实现它们要解决的问题截然不同。光线追踪更复杂，因为它涉及求解光线与几何体的求交问题。我们能否找到办法，计算一条光线是否与球体、圆锥或其他形状相交，包括 NURBS、细分曲面和隐式曲面？

多年来，大量研究致力于寻找高效计算光线与所有形状中最简单的那个——三角形——求交的方法，以及直接对 NURBS、隐式曲面等其他类型几何体做光线追踪的方法。另一种思路是在渲染开始前把所有几何体转换成同一种几何表示，让渲染器只需测试光线与这种统一表示的相交。由于三角形是理想的渲染图元，通常所有几何体都会被转成三角网格。这意味着不必为每种几何类型各实现一套光线与物体的求交测试，只需测试光线与三角形的相交，这有许多好处：

  • 第一，如前面所说，三角形具有许多使其成为极具吸引力的几何图元的性质。它是共面的、不可再分的（不像有四五个顶点的面那样，还能通过连接已有顶点造出更多面），也很容易细分成更多三角形。此外，计算三角形重心坐标——纹理映射中要用到——的数学既简单又稳健。

  • 为了找出尽可能好的光线与三角形求交测试，已经做过大量研究。一个好的光线与三角形求交算法必须快速、省内存且稳健，因为要应对浮点运算问题之类的挑战。

  • 从编码角度看，支持一个例程远比编写许多例程来处理所有几何类型有利。只支持三角形能大幅简化代码，也便于设计出总体上最适合三角形的代码。在加速结构上尤其如此——加速结构对于快速排除光线不太可能相交的场景区域、只对光线可能相交的子区域做测试至关重要。这些策略能省下相当多时间，且一般都建立在加速结构之上。值得一提的是，专门为处理光线与三角形求交测试而设计的硬件早已造出，使复杂场景能用光线追踪接近实时地运行。很明显，未来显卡会原生支持光线与三角形求交测试，电子游戏也会朝光线追踪演进。

光栅化与光线追踪的比较

我们已经多次讨论过光线追踪与光栅化的区别。为什么你会选其中一个而不是另一个？如前所述，就解决可见性问题而言，光栅化比光线追踪快。为什么？为配合光栅化算法而转换几何体最终要花一些时间，但投影几何体本身非常快（不过是几次乘法、加法和除法）。相比之下，计算光线与几何体的相交需要多得多的指令，因此代价更高。光线追踪的主要难点在于渲染时间随场景所含几何体数量线性增长。因为我们必须检查任意一条光线是否与场景中的任意一个三角形相交，最终代价就是三角形数量乘以单次光线与三角形求交测试的代价。所幸这个问题可以借助加速结构来缓解。加速结构背后的想法是：空间可以划分成子空间（例如你可以把装着所有几何体的盒子划分成网格——网格的每个格子代表原盒子的一个子空间），而物体可以按它们落入的子空间来归类。这个想法在图 5 中有示意。

如果这些子空间明显大于物体的平均尺寸，那么一个子空间里很可能不止一个物体（当然，这全看它们在空间中如何组织）。这时不必测试场景中的所有物体，我们可以先测试光线是否与某个子空间相交（换句话说，它是否穿过那个子空间）。若相交，再测试光线是否与该子空间里包含的任何物体相交；若不相交，就可以跳过所有这些物体的求交测试。这样只测试场景几何体的一个子集，从而节省时间。

如果加速结构能用来加速光线追踪，那光线追踪不就优于光栅化了吗？既是也不是。首先，它总体上仍然更慢；其次，使用加速结构会带来许多新问题。

  • 第一，构建这个结构需要时间，意味着结构建好之前渲染无法开始：这一般不会超过几秒，但如果你打算在实时应用里用光线追踪，这几秒就已经太多了（如果几何体逐帧变化，每一帧都得重建加速结构）。

  • 第二，加速结构可能占用大量内存。这全看场景复杂度；不过由于相当一部分内存要用于加速结构，可用于其他事情——尤其是存储几何体——的内存就更少了。实践上这意味着，用光线追踪能渲染的几何体数量可能比用光栅化更少。

  • 最后，找到一个好的加速结构非常困难。设想场景一侧只有一个三角形，而其余所有三角形都挤在空间里一个很小的区域。如果为这个场景建一个网格，很多格子会是空的，但主要问题在于：当光线穿过装着那簇三角形的格子时，我们仍然要做大量求交测试。在可能需要几百次测试的情况下省下一次，收益微乎其微，这清楚说明网格作为这类场景的加速结构不是好选择。可以看到，加速结构的效率在很大程度上取决于场景以及物体的散布方式：物体是小还是大，是大小混合，是均匀分布在空间里还是分布得很不均匀？场景是否属于这些情况的某种组合？

人们提出了许多不同的加速结构，你可以想见，它们各有优缺点，当然其中有些比其他更受欢迎。在专门讲光线追踪技术的部分里，你会找到许多专门讨论这个题目的课程。

读完这些，你也许会觉得问题都出在光线追踪身上。可是光线追踪流行是有原因的。首先，从原理上说，它实现起来极其简单。我们在本节第一课里展示过，一个非常基础的光线追踪器几百行代码就能写出来。实际上，我们可以说基于光栅化算法写一个渲染器也不会多很多代码，但光线追踪的概念似乎仍更容易编码，也许因为它更接近「为三维场景生成图像」这件事的自然思路。但更重要的是：如果你用光线追踪，那么像反射或软阴影这类对图像照片级真实感起着关键作用的效果，在光线追踪里模拟起来就是直截了当，而在光栅化里则非常困难。要理解原因，我们得先更细致地看看着色与光传输，那是下一章的主题。

「光栅化快，但支持复杂视觉效果需要聪明才智。光线追踪支持复杂视觉效果，但要快起来需要聪明才智。」——David Luebke（NVIDIA）。

「用光栅化，做得快很容易，但让它好看很难。用光线追踪，让它好看很容易，但要让它快非常难。」

小结

本章我们探讨了光线追踪与光栅化这两种解决三维渲染中可见性问题的主要方法。目前，光栅化是显卡渲染三维场景所采用的主导技术，因为在这项特定任务上它比光线追踪快。不过光线追踪可以借助加速结构来加速，尽管这些结构本身也带来挑战。要找到一个高效、且在场景复杂度（图元数量、尺寸、分布）变化时表现都好的加速结构是很难的。此外，加速结构需要额外的内存，构建它也需要时间。

必须认识到，就解决可见性问题而言，此时光线追踪相对于光栅化并没有任何明显的优势。然而在模拟软阴影、反射这类光照或着色效果方面，光线追踪优于光栅化。所谓「优于」，是指相比光栅化，光线追踪让这些效果的模拟更直接。这并不意味着用光栅化做不到这些效果；只是通常要花更多功夫。这一点澄清很重要，可以纠正一个常见的误解：认为反射之类的效果只能通过光线追踪实现。事实根本不是这样。

综合考虑两种技术的长处，可以设想一种混合方案：在渲染过程中用光栅化做初步的可见性判定，用光线追踪做高级的着色效果。然而，在同一个应用里集成两种方案，会让开发过程比使用统一的渲染框架更复杂。鉴于光线追踪能简化反射等现象的模拟，尽管它有种种复杂性，人们往往仍选择它来同时承担可见性判定与高级着色。
