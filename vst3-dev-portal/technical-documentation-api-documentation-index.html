VST 3 API 是一套为实时音频处理组件设计的接口集合。此类组件可以是音频效果器，也可以是乐器。VST 3 基于一项名为 VST 模块架构（VST-MA）的技术。请阅读 VST-MA 文档 以进一步了解插件系统的一般工作方式。属于 VST 3 的 API 文件位于文件夹 "pluginterfaces/vst" 中。

ⓘ 如果你在找 VST 3 的 C API
参见 https://github.com/steinbergmedia/vst3_c_api。

基本概念

VST 3 音频效果器或乐器基本上由两部分组成：处理部分与编辑控制器部分。对应的接口是：

  • 处理器：Vst:: IAudioProcessor + Vst:: IComponent
  • 控制器：Vst:: IEditController

VST 3 的设计主张通过实现两个组件，把处理器与编辑控制器彻底分离。把一个效果器拆成这两部分需要一些额外的实现工作。不过，这种分离使宿主能够在不同的上下文中运行每个组件，甚至可以在不同的计算机上运行。另一个好处是，在自动化方面可以把参数变化分开处理。处理时这些变化需要以逐采样精确的方式传输，而 GUI 部分可以用低得多的频率更新，并且可以按延迟补偿或其他处理偏移所产生的时间量进行平移。

支持这种分离的插件必须设置 Vst::kDistributable 标志，位置在处理器组件的类信息中（Steinberg::PClassInfo2::classFlags）。当然，并非每个插件都能支持这一点。例如，当它深度依赖无法轻易迁移到另一台计算机的资源时。因此，如果没有设置此标志，宿主绝不能以任何方式尝试分离这些组件。

虽然不推荐，但确实可以在一个组件类中同时实现处理部分与控制器部分。宿主在创建 Vst:: IEditController 之后会尝试查询 Vst:: IAudioProcessor 接口，若成功就把它用作控制器。

ⓘ 注意
宿主在处理插件时，无需实例化该插件的控制器部分。

插件应当做好在控制器部分未被实例化的情况下进行处理的准备。

初始化

Vst:: IComponent 与 Vst:: IEditController 都派生自 Steinberg:: IPluginBase。这个基础接口的用途是初始化组件，并在组件销毁前终止它。

传递给 Steinberg:: IPluginBase::initialize 的上下文参数应当实现 Vst:: IHostApplication 接口。在调用 initialize 之前，宿主不应调用其他函数，唯一的例外是 Vst:: IComponent::setIoMode，它必须在 initialize 之前调用。Vst:: IComponent::getControllerClassId 也可以在之前调用（参见 VST 3 工作流程图）。

插件如何访问 IHostApplication？

//-----------------------------------------------------------------------
tresult PLUGIN_API MyPluginProcessor::initialize (FUnknown* context)
{
    if (auto hostApp = Steinberg::U::cast<IHostApplication> (context))
    {
        String128 name;
        if (hostApp->getName (name) == kResultTrue)
        {
            //...
        }
    }
    //...
}
//-----------------------------------------------------------------------

从宿主视角看创建与初始化

下面是一个宿主实现的示例，它为一个具有给定 classID 的插件创建组件及其关联的控制器：

//-----------------------------------------------------------------------
Vst::IComponent* processorComponent;
Vst::IEditController* editController;
IPluginFactory* factory;
// ...
// 工厂已初始化（在库加载之后，参见 validator 示例）
// ...
// 创建其组件部分
tresult result = factory->createInstance (classID,Vst::IComponent::iid, (void**)&processorComponent);
if (processorComponent && (result == kResultOk))
{
    // 用我们的宿主上下文初始化组件（注意：initialize 紧跟在 creatInstance 之后调用）
    res = (processorComponent->initialize (gStandardPluginContext) == kResultOk);

    // 尝试从组件创建控制器部分
    // 针对未能成功把组件与控制器分离的插件 :-(
    if (processorComponent->queryInterface (Vst::IEditController::iid, (void**)&editController) != kResultTrue)
    {
        // 这是正常情况，控制器与组件是分离的。

        // 查询关联的控制器类 ID（可以在 processorComponent->initialize () 之前调用）
        FUID controllerCID;
        if (processorComponent->getControllerClassId (controllerCID) == kResultTrue && controllerCID.isValid ())
        {
            // 从工厂创建其控制器部分
            result = factory->createInstance (controllerCID, Vst::IEditController::iid, (void**)&editController);
            if (editController && (result == kResultOk))
            {
                // editController 现已创建，我们拥有其所有权，
                // 这意味着在不再使用时必须释放它。

                // 用我们的上下文初始化组件
                res = (editController->initialize (gStandardPluginContext) == kResultOk);

                // 现在 processorComponent 与 editController 都已初始化…… :-)
            }
        }
    }
    else
    {
        // editController 现已创建，我们拥有其所有权，
        // 这意味着在不再使用时必须释放它。
    }
}
//-----------------------------------------------------------------------

ⓘ 注意
请注意，IPluginBase::initialize 与 IPluginBase::terminate 对每个对象实例只能调用一次。因此，如果一个对象同时实现了 IAudioProcessor 与 IEditController，要注意只调用它们一次，如上面的示例所示。

扩展

实现这些基础接口的组件，其功能可以通过若干可选接口来扩展；只有需要这种扩展时才必须实现这些接口。

  • 处理器扩展：
    • Vst:: IConnectionPoint
    • Vst:: IUnitData
    • Vst:: IProgramListData
  • 编辑控制器扩展：
    • Vst:: IConnectionPoint
    • Vst:: IMidiMapping
    • Vst:: IUnitInfo

持久化

宿主在工程文件和预设文件中存储并恢复处理器与控制器的完整状态：

  • Vst:: IComponent::getState + Vst:: IComponent::setState 存储并恢复 DSP 模型。
  • Vst:: IEditController::getState + Vst:: IEditController::setState 存储并恢复与处理器无关的任何 GUI 设置（如滚动位置等）。
  • 恢复：恢复状态时，宿主把处理器状态同时传递给处理器和控制器（Vst:: IEditController::setComponentState）。宿主必须始终先把该状态传递给处理器。随后控制器必须把其参数同步到该状态（但不得执行任何 Vst:: IComponentHandler 回调）。恢复状态后，宿主会重新扫描参数（向控制器查询），以更新其内部表示。

另请参见

  • Steinberg:: IBStream
  • VST 3 中需由插件实现的接口
  • VST 3 中需由宿主实现的接口

处理部分

处理部分由两个相关的接口组成：Vst:: IComponent 与 Vst:: IAudioProcessor。之所以拆成两个，是为了让基础接口 Vst:: IComponent 不仅用于音频插件，也用于其他类型的媒体（例如将来的视频处理）。因此 Vst:: IAudioProcessor 接口表示处理组件中与音频相关的部分。下面我们仔细看看这些概念。

IComponent

Vst:: IComponent 接口允许宿主获取关于该插件的信息：

  1. 编辑控制器关联：为了让宿主能够创建关联的编辑控制器部分，处理组件必须提供匹配的 class-ID。宿主使用模块的类工厂来创建控制器组件。参见 Vst:: IComponent::getControllerClassId

  2. 宿主可以查询总线配置（Vst::BusInfo）。参见 Vst:: IComponent::getBusInfo

  3. 宿主可以查询路由信息（Vst::RoutingInfo）。

  4. 宿主可以激活或停用特定的总线，例如 侧链。被停用的总线不应由插件处理。参见 Vst:: IComponent::activateBus

  5. 宿主可以激活或停用插件（On/Off 按钮）。参见 Vst:: IComponent::setActive

  6. 宿主可以存储并恢复插件的状态（预设与工程持久化）。参见 Vst:: IComponent::getState、Vst:: IComponent::setState

IAudioProcessor

Vst:: IAudioProcessor 接口扩展了 Vst:: IComponent，为处理提供了状态机以及 process 方法：

  1. 设置：开始处理之前必须先配置处理器。只有在处理器处于非活动状态时才允许进行配置（Vst:: IComponent::setActive）。

    • 处理设置：处理器会被告知在处理处于活动状态时不能更改的参数。（Vst::ProcessSetup）。
    • 动态扬声器布置：宿主可以尝试更改音频总线的通道数。默认情况下，扬声器布置由插件定义。为了让插件适应使用不同扬声器布置的环境，宿主可以尝试使用 Vst:: IAudioProcessor::setBusArrangements

  2. 处理器配置完成后，必须将其激活（Vst:: IComponent::setActive）。激活调用表示所有配置已完成。

  3. 除此之外，处理器还有一个「处理状态」。在宿主开始执行处理调用之前，必须通过调用 Vst:: IAudioProcessor::setProcessing（true）来表明这一点。当宿主停止处理时，必须在最后一次处理调用之后调用 Vst:: IAudioProcessor::setProcessing（false）。另请参见：VST 3 工作流程图。在 setProcessing（true）时，插件必须重置其部分内部处理状态（例如清空延迟缓冲区，以便在处理重新开始时处于确定状态）。

  4. 处理：Vst:: IAudioProcessor::process 是实现实际处理的方法。处理所需的任何数据都作为参数 Vst::ProcessData 传递给它。这是必要的，因为处理往往在单独的线程中执行，而这是一种避免线程同步问题的简单方式。

    • 块大小：处理以块为单位进行。一个块中可处理的采样数上限在 Vst:: IAudioProcessor::setupProcessing 中设置。处理块中实际的采样数在处理调用中传递，每次调用可能不同，但必须是 1 到 maxSamplesPerBlock 之间的值。

    • 音频缓冲区：对于插件定义的任何音频总线，宿主都必须提供缓冲区数据——即使总线处于非活动状态。总线按索引寻址，因此省略非活动总线会打乱这些索引。不过实际的数据缓冲区可以指向空指针（参见 Vst::AudioBusBuffers）。

      注意：channelBuffers32（或 channelBuffers64）缓冲区指针在输入和输出上可以相同也可以不同：在 process 函数中必须考虑到这一点（例如，如果输入与输出缓冲区相同，就不要在处理前重置输出！）。对于多个输入或多个输出（在乐器插件的情况下），指针也可以相同——所有输出（或输入）可以共享同一个缓冲区！

      重要：宿主可以在没有缓冲区的情况下调用 Vst:: IAudioProcessor::process（numInputs 与 numOutputs 在 Vst::AudioBusBuffers 中被置零，numSamples 也一样），以便冲刷参数（从宿主到插件）。只有当宿主需要发送参数变化且没有调用处理时，参数才能被冲刷。

    • 参数 & 自动化：任何参数变化都在处理调用中通过接口 Vst:: IParameterChanges 与 Vst:: IParamValueQueue 传递。由 GUI 交互引起的简单参数变化，其传递方式与自动化完全相同。（参见 参数与自动化）。

    • 上下文：对于每个处理块，宿主应当提供关于其状态的信息。参见 Vst::ProcessContext

    • 事件：Vst:: IEventList

编辑部分

编辑控制器负责插件的 GUI 方面。其标准接口是 Vst:: IEditController。宿主必须为编辑控制器提供一个名为 Vst:: IComponentHandler 的回调接口。该 handler 对于与宿主和处理器的通信都至关重要。

  • GUI：控制器可以选择性地定义编辑器视图。方法 Vst:: IEditController::createView 允许宿主通过传入 id 字符串来指定视图类型。目前唯一定义的类型是「editor」（Vst::ViewType::kEditor），但未来的版本中可能会有其他变体（例如「setup」）。另请参见 Steinberg:: IPlugView。

  • 参数：控制器负责参数的管理。插件 GUI 中由用户交互引起的任何参数变化都必须正确报告给 Vst:: IComponentHandler。宿主负责把该变化传递给处理器。为了让自动化录制正常工作，必须按预期顺序调用 beginEdit、performEdit 与 endEdit！而且必须从 UI 线程调用！借助新接口 Vst:: IComponentHandler2（自 VST 3.1 起），插件（在 UI 中）可以把写入自动化时应使用同一宿主时间戳的参数分组，方法是用 beginEdit/performEdit/endEdit 函数（参见 Vst:: IComponentHandler）与 startGroupEdit 和 finishGroupEdit 包起来。更多细节见 参数。

  • 插件结构：如果插件由若干独立的功能部分构成，编辑控制器应当通过实现 Vst:: IUnitInfo 接口来公开这一结构以及各部分所属的参数。更多细节见 VST 3 单位。

VST 3 线程模型

VST 3 使用的线程模型相当简单，要求：

  • 所有初始化/反初始化都在 UI 线程 中完成（有时也称为主线程）。
  • 插件导出的所有函数都由宿主在 UI 线程 中调用，但以下情况除外：
    • Vst:: IAudioProcessor::process：它可能在 音频线程 中调用（有时也称为实时/处理线程），要避免任何内存分配！
    • Vst:: IAudioProcessor::setProcessing：它可能在 音频线程 中调用，要避免任何内存分配！
  • 宿主导出的所有函数都由插件在 UI 线程 中调用。

请查看 音频处理器调用序列 与 编辑控制器调用序列。

组件之间的通信

VST 3 的两个组件（处理器与控制器）需要一种相互通信的方式。处理这件事是宿主的任务。

标准通信

所有标准数据（如参数变化）都通过上面列出的基础接口在处理器与控制器之间传输。

  • 创建处理器和控制器之后，宿主根据处理器的状态设置控制器组件的状态。这是相对于此前 SDK 的一处变化，以前的 SDK 假定创建之后控制器与处理器即处于同步状态。
  • 当宿主设置新的处理器状态（Vst:: IComponent::setState）时，该状态也总会传递给控制器（Vst:: IEditController::setComponentState）。随后控制器必须同步到该状态并调整其参数。
  • 当控制器向宿主传递参数变化时，宿主把新值以 Vst:: IParameterChanges 的形式传给 process 调用，从而同步处理器。
  • 处理器也可以向宿主传递输出的参数变化。（Vst::ProcessData::outputParameterChanges）。这些变化通过调用 Vst:: IEditController::setParamNormalized 传递给编辑控制器。

私有通信

宿主未知的数据可以通过消息传递。通信接口有：

  • Vst:: IConnectionPoint：宿主在处理器与控制器之间建立连接。
  • Vst:: IMessage：表示要发送给对端的消息。
  • Vst:: IAttributeList：属于某条消息的属性列表。

请注意，从处理器发往控制器的消息不得在处理调用期间发送，因为那样不够快，会破坏实时处理。这类任务应在 UI 线程 中处理，或使用 数据交换。

从宿主视角看通信的初始化

下面是一个宿主实现的示例，其中组件部分与控制器部分已连接并同步：

//-----------------------------------------------------------------------
// 组件部分与控制器部分此前已创建并初始化（见上文）
// ...
if (editController)
{
    // 设置宿主 handler
    // 宿主把自己的 handler 设置给控制器
    editController->setComponentHandler (myHostComponentHandler);

    // 连接这两个组件
    Vst::IConnectionPoint* iConnectionPointComponent = nullPtr;
    Vst::IConnectionPoint* iConnectionPointController = nullPtr;

    processorComponent->queryInterface (Vst::IConnectionPoint::iid, (void**)&iConnectionPointComponent);
    editController->queryInterface (Vst::IConnectionPoint::iid, (void**)&iConnectionPointController);

    if (iConnectionPointComponent && iConnectionPointController)
    {
        iConnectionPointComponent->connect (iConnectionPointController);
        iConnectionPointController->connect (iConnectionPointComponent);
    }

    // 使用 setComponentState 让控制器与组件同步
    MemoryStream stream; // 定义于 "public.sdk/source/common/memorystream.h"
    if (processorComponent->getState (&stream) == kResultTrue)
    {
        // 回退到流的开头
        stream.seek (0, IBStream::IStreamSeekMode::kIBSeekSet, nullptr);
        editController->setComponentState (&stream);
    }

    // 现在 processorComponent 与 editController 各部分已连接并同步……:-)
}

ⓘ 注意
请注意，你绝不能依赖「连接直接在处理器组件与编辑控制器之间完成」这一实现细节！
