引言

VST-MA 是一种组件模型系统，在所有 Steinberg 宿主程序中都作为插件支持的基础层。

它是面向对象的、跨平台的，并且（几乎）与编译器无关。
其基本概念与 Microsoft® COM 非常相似，因此如果你熟悉这项技术，理解 VST-MA 应当相当容易。

VST-MA 仅以 C++ 提供。C++ 中的接口以纯虚类（即只包含抽象方法的类）表示。与 COM 不同，目前还不支持 C 或其他语言——原因很简单：到目前为止没有这种需求。但所有 VST-MA 接口都可以转换成不同的表示形式，以防将来某天这变得不可避免。
目前它可用于 Windows、macOS X 和 Linux。

属于 VST-MA 的 C++ 文件位于以下文件夹中：

  • pluginterfaces/base
  • pluginterfaces/gui

注意：「VST 模块架构」这个名称与「Virtual Studio Technology」本身关系不大。
它描述的是 Steinberg 宿主所支持的任何插件类别的基础层。VST-MA 早在被用作 VST 3 自身的基础之前就早已存在。

接口

FUnknown

Steinberg::FUnknown 是 VST-MA 的基本接口。所有其他接口都直接或间接地由它派生。

IID/CID

每个接口都有一个唯一标识符（IID），类型为 Steinberg::FUID。它用于从一个接口获取另一个接口（Steinberg::FUnknown::queryInterface）。重要的是理解接口标识符与组件标识符之间的区别。
组件 ID 或类 ID（CID）用于标识一个具体的实现类，通常会被传递给类工厂，以便创建相应的组件。
因此，许多不同的类（具有不同的类标识符）可以实现相同的接口。

方向

接口可以有 方向，表示该接口预期由插件实现还是由宿主实现。接口的性质按以下方式记录：

  • [host imp]：宿主实现该接口
  • [plug imp]：插件实现该接口

两者都未指定时，该接口可以两种方式使用。

版本与继承

与 C++ 类不同，接口不使用继承来表达对象的特化。继承只用于版本管理。严格的规则之一是：接口一旦发布，就绝不能再改动。为接口添加新功能需要新版本（通常在这种情况下会给名称加上序号，例如 Steinberg:: IPluginFactory3 为 Steinberg:: IPluginFactory2 增加了新特性）。
新版本继承接口的旧版本，因此新旧方法会合并到一个接口中。这就是为什么特化必须建模为独立的接口！如果特化接口也继承基本接口，那么一个需要实现所有这些接口的实现类就会两次继承基接口，导致编译器遇到二义性。因此，特化与基本接口之间的关系只能在文档中表达。

  • ISpecialInterface [extends IBaseInterface] => 表示可以用 IBaseInterface::queryInterface (ISpecialInterface::iid, ...) 获取派生接口。

你可以在这里找到一些示例代码：接口版本与继承。

COM 兼容性

VST-MA 的第一层与 COM 二进制兼容。Vtable 以及 Steinberg::FUnknown 的接口标识符与对应的 COM 接口 IUnknown 一致。主要区别在于宿主程序如何组织和创建组件/插件。VST-MA 不要求任何 Microsoft® COM 源文件。你可以在以下页面找到有关 COM 的信息：

  • https://docs.microsoft.com/en-us/windows/win32/learnwin32/what-is-a-com-interface-

基本接口

  • Steinberg::FUnknown
  • Steinberg:: IPluginBase
  • Steinberg:: IPluginFactory

辅助类

  • Steinberg::FUID
  • Steinberg::FUnknownPtr

另请参阅「如何从接口派生类」。

插件

模块工厂

模块（Windows：动态链接库；macOS：Mach-O Bundle；Linux：包）包含一个或多个组件（例如 VST 3 效果器）的实现。VST-MA 模块必须包含一个类工厂，其中注册了组件的元数据和创建方法。
宿主通过 Steinberg:: IPluginFactory 接口访问该工厂。这是模块的锚点，实现为一个名为 GetPluginFactory 的 C 风格导出函数。你可以在 SDK 中找到导出定义文件——public.sdk/source/main/winexport.def（public.sdk/source/main/macexport.exp），可用它导出该函数；也可以在 cpp 文件中直接使用宏 SMTG_EXPORT_SYMBOL（示例见 public.sdk/source/main/dllmain.cpp）。
GetPluginFactory 的声明如下：

SMTG_EXPORT_SYMBOL IPluginFactory* PLUGIN_API GetPluginFactory ();

除 GetPluginFactory 函数外，插件还可能需要根据平台导出额外的 entry/exit 函数：

在 Windows 上
在 Windows 上，entry/exit 函数名为 InitDll / ExitDll，并且是 可选的！

插件可以导出这些函数。宿主必须在通过 LoadLibrary 加载插件之后直接调用 InitDll 函数，并在调用 GetPluginFactory 之前完成这一调用。ExitDll 函数必须在通过 FreeLibrary 卸载插件之前，或在未调用 FreeLibrary 而程序终止时被调用。

由于 Windows 已经具备此功能（参见 Microsoft 文档中的 DllMain），上述函数是可选的。

在 macOS 上
在 macOS 上，entry/exit 函数名为 bundleEntry / bundleExit，并且是 必需的！

插件必须导出这些函数，宿主必须在加载插件之后直接调用 bundleEntry 函数（插件通过 CFBundleLoadExecutable 加载），并在调用 GetPluginFactory 之前完成这一调用。

必须在卸载插件之前或程序终止时调用 bundleExit 函数。

由于 macOS 在加载 bundle 时没有标准入口函数，上述函数是必需的，宿主必须拒绝未导出这些函数的插件。

在 Linux 上
在 Linux 上，entry/exit 函数名为 ModuleEntry / ModuleExit，并且是 必需的！

插件必须导出这些函数，宿主必须在通过 dlopen 加载插件之后、调用 GetPluginFactory 之前直接调用 ModuleEntry 函数。

必须在通过 dlclose 卸载插件之前或程序终止时调用 ModuleExit 函数。

由于 Linux 在加载动态库时没有标准入口函数，上述函数是必需的，宿主必须拒绝未导出这些函数的插件。

入口函数用于向插件提供平台特定的实例句柄，许多平台 API 都需要它。

插件开发者应使用这些函数，而不要用平台函数来获取实例句柄。

以下示例使用 def/exp 文件，而不是 SMTG_EXPORT_SYMBOL：

Windows 上的 winexport.def 文件

EXPORTS
GetPluginFactory
InitDll
ExitDll

mac 上的 macexport.exp 文件

_GetPluginFactory
_bundleEntry
_bundleExit

位置

组件模块不要求像 DirectX 那样注册。宿主程序期望组件模块位于文件系统的预定义文件夹中。应用程序启动时会扫描这些文件夹及其子文件夹，查找 VST-MA 模块。每个文件夹都有特定用途：

  • 应用程序的 Components 子文件夹（例如 "C:\Program Files\Steinberg\Cubase 12\Components"）用于与应用程序紧密绑定的组件。其他应用程序不应使用它。
  • 在所有 Steinberg 宿主之间共享的组件位于：
    • Win 平台："/Program Files/Common Files/Steinberg/Shared Components"
    • Mac 平台："/Library/Application Support/Steinberg/Components/"
  • 对于特殊用途的插件类型，还定义了其他位置。请参阅相应文档，了解是否使用其他文件夹以及在哪里找到它们。对于 VST 3，参见 VST 3 位置/格式。

类别

工厂可以创建的任何类都归属于某个类别。正是这个类别告诉宿主该类的用途（并暗示它可能实现哪些接口）。
类还用一个名称来描述，并且具有唯一的 id。

  • 例如，导入/导出过滤器的类别是「Project Filter」，VST 3 音频插件的类别是「Audio Module Class」。
  • 「Service」是一个特殊类别。该类别中类的用途对宿主来说完全未知。它会在程序启动时自动加载（前提是用户没有停用它）。
  • 由于工厂可以创建任意数量的类，一个组件库可以包含任意类型的多个组件。

IPluginBase

任何组件类的入口点接口是 Steinberg:: IPluginBase。宿主使用该接口来初始化并终止插件组件。宿主初始化插件时，必须传入所谓的上下文。该上下文包含插件工作所需的任何宿主接口。

用途专用接口

每个插件类别（VST 3 效果器、项目导入/导出过滤器、音频编解码器等）都定义了自己的一组用途专用接口。这些接口不属于基本的 VST-MA 层。

Unicode

从 Cubase 和 Nuendo 第 5 版开始，宿主的内部结构经过修改，以更好地支持国际化。因此，字符串处理改为在传递字符串时使用 Unicode 字符串。结果是，与插件之间的所有接口在调用参数和返回参数上都从使用 ASCI 字符串改为使用 Unicode 字符串。相应地，所有插件都必须改造以支持 Unicode。这带来以下重要后果：

  • Unicode 宿主（Cubase 5 或更高版本）只能与 Unicode 插件配合工作。加载插件时，Unicode 宿主会检查插件类型，不会加载任何非 Unicode 插件。
  • Unicode 插件不会加载到非 Unicode 宿主中。加载时，Unicode 插件会向宿主请求信息，如果未检测到 Unicode 宿主就不会加载。因此，如果插件需要同时适用于旧版和新版宿主，最好提供插件的两个版本。

面向 Unicode 宿主的插件

编写只与 Unicode 宿主配合工作的插件很容易。使用当前版本的此 SDK，像平常一样开发插件即可。确保只向以字符串为调用参数的接口传递 Unicode UTF-16 字符串，并做好准备：这些接口返回的字符串始终是 UTF-16。因此，为简化处理，建议在整个插件实现中都使用 Unicode 字符串，以避免来回转换。此外，使用 Base 模块中的 Steinberg::String 和 Steinberg::ConstString 类，它们被设计为可在 Mac 和 Win 上通用。

从非 Unicode 迁移到 Unicode

在 Steinberg 早于 Cubase 5 发布的 SDK 中，接口函数使用 char 类型的指针向宿主传递字符串和从宿主接收字符串。现在这些已改为使用 Steinberg 定义的类型 tchar，它等价于 char16，即 16 位字符。理论上表示 16 位字符的方式有很多，但我们选择使用行业标准 Unicode，因此字符串预期以 UTF-16 编码。
相应地，插件的实现也需要改造，以正确处理 Unicode 编码的字符串，并且只向宿主传递 Unicode 字符串。

ⓘ 注意
将函数从使用 8 位字符指针改为 16 位字符指针，看起来只是很小的改动，但在接口设计中这是重大侵入，因为接口是对外界的契约，永远不应更改。因此，改为使用 Unicode 字符串的类会被区分出来，并获得新的唯一类 ID。

SDK 向后兼容性

即使使用当前 SDK，仍然可以开发非 Unicode 插件。在文件 pluginterfaces/base/ftypes.h 中，行 "#define UNICODE_OFF" 被注释掉了，但取消注释后即可将所有接口恢复为使用单字节 ASCII 字符串。或者，也可以在项目文件中将 UNICODE_OFF 指定为预处理器定义。
此外，插件的工厂信息现在不再定义 Unicode 标志，因此 Unicode 宿主会把编译出的插件视为非 Unicode。另外，恢复为单字节字符串时，插件的实现也必须相应修改才能正确工作。

ⓘ 注意
取消定义 Unicode 时，类 ID 也会恢复为旧的类 ID。
