引言

在现代插件中，UI 表示与音频处理不直接共享任何数据。这消除了未定义行为，因为它们运行在不同的线程中，任何直接共享的数据都需要由互斥锁保护。但互斥锁没有确定的运行时间，可能把音频线程阻塞过久，造成可听见的爆音，这种情况必须避免。

在 UI 与音频处理之间共享数据的另一个问题在于：音频在被送往监听音箱或耳机之前就已经处理完毕。如果没有同步，可视表示会比它所代表的声音更早显示。为了同步可视表示与音频信号的处理，UI 必须把可视数据排队，直到声音被听到的时刻到来。

对于由宿主自动化的参数，这个问题已经得到解决。宿主会延迟把参数变更发送给编辑控制器，使其与可听的音频保持同步。

但参数能传输的数据量有限，这对于简单的峰值 VU 表显示可能足够，用它来呈现 FFT 曲线则是一场噩梦。

SDK 的 3.7.9 版本包含新的 数据交换 API，可以安全高效地从实时处理函数向控制器发送数据。

由于该 API 需要宿主支持，而且并非所有宿主从一开始就提供此 API，SDK 包含一个向后兼容层：如果可用，就直接使用该 API；否则使用基于 IMessage API 的替代方法来模拟该 API。用法见教程。

数据交换 API

该 API 由两个接口组成：需要由宿主实现的 Vst:: IDataExchangeHandler，以及需要由插件实现的 Vst:: IDataExchangeReceiver。

IDataExchangeHandler

Vst:: IDataExchangeHandler 实现了从音频处理器的实时音频上下文到编辑控制器的非实时音频上下文的直接且线程安全的连接。当编辑控制器需要来自音频处理的连续数据用于可视化或其他「使用场景」时，应使用它。为了绕开主线程上的瓶颈，可以把连接配置为在后台线程上调用编辑控制器，参见下文的 Vst:: IDataExchangeReceiver。

打开队列

插件的主要操作是在插件被激活之前通过 handler 打开一个队列（但当插件采用推荐的编辑控制器与音频处理器分离方式时，必须先通过 Vst:: IConnectionPoint 连接到编辑控制器）。最好的位置是 Vst:: IAudioProcessor::setupProcessing 方法，因为这里也是插件获知采样率和最大块大小的地方，插件可能需要用它们来计算队列的块大小。队列被打开时，编辑控制器会收到通知，控制器可以决定它希望在主线程还是后台线程接收数据。

发送数据

在 Vst:: IAudioProcessor::process 调用中，插件现在可以从 handler 锁定一个块并填充它。完成后，它可以通过 handler 释放该块，handler 随后把块发送给编辑控制器。编辑控制器随后根据队列的设置，在主线程或后台线程上接收该块。宿主保证在插件被停用之前所有块都已发送。

关闭队列

音频处理器必须关闭已打开的队列。这需要在停用处理器之后、在它与编辑控制器断开连接之前完成（见 Vst:: IConnectionPoint）。

队列已满且无法锁定任何块时该怎么办？

插件需要为这种情况做好准备，因为整体系统中的约束可能导致队列过度填满。如果必须把信息传给控制器，可以声明一个隐藏参数，把它设为特殊值，并在音频处理方法中发送该参数变更。

IDataExchangeReceiver

Vst:: IDataExchangeReceiver 接口必须由插件的编辑控制器实现。当处理器打开交换队列时，宿主会调用 queueOpened 方法。之后当处理器关闭队列时，宿主会调用 queueClosed 方法。

队列打开期间，只要处理器发送了数据，宿主就会调用 onDataExchangeBlocksReceived 方法。

编辑控制器可以在调用 queueOpened 时决定宿主应在后台线程还是 UI 线程上传递数据。
