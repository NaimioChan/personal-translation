问：restartComponent 的用途是什么？返回 kNotImplemented 通常可以吗？

默认情况下，如果宿主没有实现某个特定标志，可以返回 kNotImplemented。但强烈建议实现以下标志：

  • kLatencyChanged
  • kParamValuesChanged
  • kParamTitlesChanged
  • kIoChanged

问：宿主可以假定 ClassID 全局唯一，还是应当假定不同模块会复用 class ID？

你必须把 Class ID 视为全局唯一。如果同一个 classID 已被宿主注册，宿主可以忽略它，或尝试比较版本（基于字符串）并保留最新的版本（例如 Cubase 就是这样做的）。宿主中同一时间只应注册一个 VST 3 插件。宿主也可以视需要把重复的 classID 显示给用户。

问：某个插件的所有版本更新都需要新的 classID 吗？

不需要，通常新版本应当并且可以直接用相同的 classID 替换旧版本，参见上一个问题。这才是正确的做法。

有些插件可能会使用新的 classID。如果这些插件是为了替换旧版本而做的，那么新的 Moduleinfo 或 IPluginCompatibility 接口（如果插件使用了它）可以让宿主在加载使用旧版本的项目时，选择新插件作为旧插件的替代（如果不存在或未使用则不然）。

问：宿主应当支持没有 EditController 的插件吗（IComponent::getControllerClassId() 失败，或后续的 IPluginFactory::createInstance() 失败）？

宿主必须检查 IAudioProcessor 是否也实现了 IEditController 接口。插件可以在同一个对象中实现这两个接口（单组件效果器 Single Component Effect）

更多信息参见此处。

当没有可用的 IEditController 时，宿主应当能够处理这种情况。

问：宿主应当支持没有 IPlugView 的插件吗（IEditController::createView() 失败，或 IPlugView::isPlatformTypeSupported() 返回 false）？

插件不需要有自定义编辑器。参见 SDK 中的示例，其中许多都没有自定义编辑器。VST 2 也是如此。因此宿主必须支持这些没有专用 UI 的插件，但可以提供通用 UI。

问：对于给定的参数（ParamID），允许改变什么？名称、步数、是否可自动化、它属于哪个单位？

参见此处。

问：在 kParamTitlesChanged 时可以改变任意/全部 ParameterFlags 吗？

可以，这正是应有的做法：kParamTitlesChanged => 重新检查标题-单位、步数、默认值和标志。

问：ParameterInfo::stepCount 只允许在 kReloadComponent 时改变吗？

不可以，参见上一个问题。

问：有些插件的参数不可自动化（kCanAutomate）。当用户通过 GUI 操作它们时，这些插件会调用 beginEdit/performEdit/endEdit。宿主是否应当响应 performEdit，把值发送到 IAudioProcessor 的 process 调用？

是的，宿主必须把参数变更从控制器传送到处理器。可自动化（kCanAutomate）这一信息只是为了让宿主和用户能为该参数创建关联的自动化轨道。

问：宿主对 restartComponent(kReloadComponent) 返回 kNotImplemented 可以吗？

如果宿主不支持，允许返回 kNotImplemented！插件随后必须相应地处理。

问：大型/重要的插件在正常使用中依赖 kReloadComponent 很常见吗？

不，这不是典型用例。不过，改变自身内部-外部表示（例如改变参数数量、IO 数量……）的插件可能会使用它。对于宿主的初始实现，可以推迟到发布未来版本时再做。

问：单位可以以哪些方式（如果有）变化，比如单位的数量或名称、参数总线到单位的分配等？

插件的单位名称可以在以 restartComponent 调用 kParamTitlesChanged 时改变。当以 restartComponent 调用 kReloadComponent 时，整个结构应被重新生成。

问：IPlugViewContentScaleSupport - 可以用/应当用它为特定插件/实例的 GUI 设置单独的缩放级别，还是只应用来传达 OS 缩放级别（如 editorhost 示例中那样）？

理论上可以把它用于单独的缩放级别，但大多数插件不会这样工作，而且在 macOS 上许多插件根本没有实现这个接口（或忽略它）。

问：如果它只用于传达 OS 缩放因子，那么当插件可以从 OS 获取缩放因子时，为什么还要一个额外的接口？

这个接口的设计早于 Windows 上插件能够访问 OS 缩放的时期。

但这个接口可以被宿主用来尝试重新缩放某个插件或所有插件。在 Cubase 中就是通过更改首选项中的整体应用缩放（直至系统缩放的 50%）来使用它的。

问：在实现宿主专属接口的示例中，FUnknown::addRef() 和 FUnknown::release() 往往被实现为空操作，e.g. {return 1000;} - 这似乎更安全，因为插件无法删除或泄漏位于宿主中的对象。是否存在宿主需要实现真正的 addRef() 和 release()（即实际控制对象生命周期）的情况？

你只能对在宿主整个生命周期内存活、并且会比插件存活更久的对象使用这种引用计数空操作。

问：如果插件没有从 UI 线程调用 ComponentHandler::restartComponent()，宿主应当怎么做？

你可以把插件的错误行为报告给开发者。restartComponent 必须从 UI Thread 调用。作为安全后备，宿主可以把该调用推迟到 UI Thread，并在下一个 UI 空闲阶段处理。

问：有些插件在宿主调用 setComponentState 时返回 kResultFalse。宿主应当直接忽略返回的结果码吗？

是的，这种情况下直接忽略结果即可。不过我们建议把这个问题告知插件开发者。
