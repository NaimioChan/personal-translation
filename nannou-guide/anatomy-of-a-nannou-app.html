nannou 应用剖析

教程信息

  • 作者：tpltnt, mitchmindtree

  • 阅读时间：10 分钟

Nannou 是一个用 Rust 进行创意编程的框架。框架可以被看作一组有助于达成目标的构建块。让我们一起来看看创意编程的这些构建块。

下面是一个打开空窗口的极简 nannou 应用示例：

use nannou::prelude::*;

struct Model {}

fn main() {
    nannou::app(model)
        .simple_window(view)
        .run();
}

fn model(_app: &App) -> Model {
    Model {}
}

fn view(_app: &App, _model: &Model, _window: Entity) {
}

我们从头开始讲起！

导入常用项

# #![allow(unused_imports)]
use nannou::prelude::*;
# fn main() {}

这一行把 nannou 中所有常用的项导入到作用域中。其中包括 App、Frame 等许多我们日后会逐渐了解的项。想查看 prelude 重新导出的完整项列表，请见此处。

注意：与某些其他语言不同，Rust 不会自动包含添加到项目中的库里的所有内容。这种做法带来了非常干净的命名空间，也避免了不同 crate 中不同项之间的冲突。话虽如此，这也意味着我们需要手动把确实想用的每个项导入作用域。通过提供 prelude，nannou 让访问所有常用项变得更容易一些。

Model - 我们的应用状态

# #![allow(dead_code)]
struct Model {}
# fn main() {}

Model 是我们定义应用状态的地方。我们可以把模型看作程序在任意时刻的表示。在程序的整个生命周期中，当某些事件发生时——比如鼠标按下、按键按下或定时更新——我们可以更新模型。然后我们可以用某种输出来呈现模型，例如绘制到屏幕或输出到激光器。这些输入和输出事件我们会在另一篇教程里更详细地了解！我们的示例尽可能简单，没有需要跟踪的状态。因此我们的模型可以保持为空。

注意：struct 描述一组数据。我们的结构体没有字段，因而是空的。这个示例中没有需要跟踪的状态信息。

main - Rust 程序的起点与终点

# use nannou::prelude::*;
# struct Model {}
fn main() {
    nannou::app(model)
        .simple_window(view)
        .run();
}
# fn model(_app: &App) -> Model {
#     Model {}
# }
# fn view(_app: &App, _model: &Model, _window: Entity) {
# }

所有 Rust 程序都从 main 函数的开头开始执行，在 main 函数结束时终止。在大多数 nannou 程序中，main 函数都很小。简而言之，我们先构建应用的描述，然后运行它！

# use nannou::prelude::*;
# struct Model {}
# fn main() {
    nannou::app(model)       // Start building the app and specify our `model`
        .simple_window(view) // Request a simple window to which we'll draw with `view`
        .run();              // Run it!
# }
# fn model(_app: &App) -> Model {
#     Model {}
# }
# fn view(_app: &App, _model: &Model, _window: Entity) {
# }

下面我们会介绍这些 model、event 和 view 函数的作用！

注意：在这个应用构建过程中，我们得以一窥 nannou 应用的基本设计原型。这种方法大致基于模型-视图-控制器（MVC）模式，同时也受到函数式响应式编程（FRP）的启发。

一般来说，这些范式把程序拆分为：

  • 一个描述内部状态的 model（模型）
  • 一个描述如何呈现模型的 view（视图），以及
  • 一个描述在特定事件时如何更新模型的 controller（控制器）。

如果你把视角拉远一点，可以把计算机看作模型，屏幕看作视图，键盘或鼠标看作控制器。用户看着视图，并可以用控制器改变模型的状态。如果程序不需要用户输入，控制器可以用时间或其他应用事件来修改模型。

model - 初始化 Model

# #![allow(dead_code)]
# use nannou::prelude::*;
# struct Model {}
fn model(_app: &App) -> Model {
    Model {}
}
# fn main() {}

model 函数在 nannou 应用开始时运行一次，产生一个我们之前声明的 Model 的全新实例，也就是应用状态。这可以被看作应用的“设置”阶段。在这里，我们可以创建窗口、创建 GUI、加载图像，或做任何我们想在程序开始时进行一次的事情。我们会在未来的教程里学会所有这些做法，但现在我们只返回一个空 Model 的实例。

注意：为了协助创建窗口、GUI、音频流及其他各种 I/O，App 被作为输入提供给该函数。App 类型可以被看作一个辅助类型，它封装了应用中那些繁琐的细节（如建立事件循环、生成 I/O 流等），并在其上提供了一个易于使用的高层 API。通过函数的第一个参数提供对 App 的访问是 nannou API 中的常见做法。

你可以在此处进一步了解 App 负责什么、能做什么。

event - 在应用事件中更新 Model

# #![allow(dead_code)]
# use nannou::prelude::*;
# struct Model {}
// TODO: Add an event function here!
# fn main() {}

event 函数是每当某种应用事件发生时都会运行的一段代码。应用事件有许多不同的种类，包括鼠标和键盘按下、窗口大小调整、定时更新等等。在这些事件发生时，我们可能都希望以某种方式更新 Model。例如，我们可能想在鼠标移动时转动摄像机，或者在按钮按下时开始绘制一个图形，或者在定时更新时推进一段动画。

所有这些事件都由 Event 类型描述。区分当前正在发生哪一种事件的一种方法是对事件进行“模式匹配”，只处理我们关心的那些事件，忽略所有其他事件。更简单的做法是构建应用时根本不注册 event 函数，而是只为我们关心的那些事件注册更具体的函数。

例如，如果我们不想处理所有事件，只想处理定时更新（默认每秒发生 60 次的一种事件），可以把应用构建代码改成这样：

# #![allow(dead_code)]
# use nannou::prelude::*;
# struct Model {}
fn main() {
    nannou::app(model)
        .update(update) // rather than `.event(event)`, now we only subscribe to updates
        .simple_window(view)
        .run();
}
# fn model(_app: &App) -> Model {
#     Model {}
# }
# fn update(_app: &App, _model: &mut Model) {
# }
# fn view(_app: &App, _model: &Model, _window: Entity) {
# }

并移除我们的 event 函数，改为一个 update 函数：

# #![allow(dead_code)]
# use nannou::prelude::*;
# struct Model {}
fn update(_app: &App, _model: &mut Model) {
}
# fn main() {}

现在，我们新的 update 函数将只在每次定时更新发生时运行。

注意：Nannou 提供了一整套可以在以这种方式构建应用或窗口时注册的不同事件。可用事件种类的大多数演示，请见 all_functions.rs 示例。

view - 把 Model 呈现到窗口

# #![allow(dead_code)]
# use nannou::prelude::*;
# struct Model {}
fn view(_app: &App, _model: &Model, _window: Entity) {
}
# fn main() {}

最后，view 允许我们把模型的状态呈现到窗口。每当窗口需要重绘时它都会被调用。在这里我们可以改变背景颜色、使用 Draw API 绘制场景、把 GUI 绘制到窗口，甚至使用 wgpu API 以我们自己的纹理和渲染通道进行绘制。所有这些都会在未来的教程里讲到。
